# 记忆迁移子代理 · 效率规约（v4.1）

> 本文件随插件分发（`package.json` 的 `files` 含 `lib`）。
> 运行时真源在 `lib/migration-prompt.js` 的「阶段 7」，本文件是人类可读副本。
> **改一处必须改两处**，由 `smoke-test-v5-p7-upgrade-prompt-v4.mjs` 的 J 组断言守护（17 条）。

## 为什么有这份规约（实测数据）

| 指标 | 实测值 |
|---|---|
| 子代理总耗时 | **1,516 秒（25 分钟）** |
| 工具调用次数 | **77 次** |
| **真正产出数据盘写的调用** | **3 次（4%）** |
| 探路浪费 | 10% |
| **读插件源码（与本任务无关）** | **16%** |
| 读历史备份（前序子代理已完成） | 25% |
| 会话取证（查「我是谁」） | 13% |

用户裁定（原话）：「**注重效率，提高速度**」「用户可能不耐烦」。

## 三条铁律

### ① 不读插件源码

子代理在做「记忆整理」，不是「开发调试」。

```
❌ 禁止 read/grep lib/ 下任何文件
❌ 禁止查 package.json / 版本号 / 工具 schema 定义
✅ 需要知道工具怎么用，读提示词就够了（提示词是权威）
```

**实测浪费：12 / 77 次调用（16%）**

### ② 不重复前序成果

同一工作区若已存在 `.dsh-memory/migration-*/` 或 `.dsh-memory/backup/*-pre-v4/`，说明已有前序子代理做过一轮。

```
✅ 只做增量——检查还差什么，补上即可
❌ 不要把已完成的备份、报告、五类分拣重新读一遍验证
```

**实测浪费：19 / 77 次调用（25%）**

### ③ 最多 3 次探路

```
第 1 次：pwd + ls 确认工作区（一次搞定，不要分 8 次问）
第 2 次：确认 handoff/ 结构
第 3 次：确认 event-store 现状
⇒ 3 次之内必须开始干活。超过 3 次 = 方向不明，停下来重新想
```

## 时间预算（硬指标）

| 场景 | 目标耗时 | 硬上限 |
|---|---|---|
| 单工作区、< 50 篇账本 | < 3 分钟 | 8 分钟 |
| 单工作区、50–200 篇 | < 8 分钟 | 20 分钟 |
| 单工作区、> 200 篇 | < 20 分钟 | 40 分钟 |

**超时自救**：超过硬上限仍在中途 ⇒ 立刻停止扫描，用已收集的信息先落盘一批。
宁可分两次做完，也不要一次卡死（用户看到 `phase:running` 十几分钟会以为崩溃）。

## 批量化判据（最关键的一条）

```bash
# ❌ 慢：每篇账本一次 read（500 篇 = 500 次调用 = 至少 1 小时）
read handoff-xxx.md

# ✅ 快：一次命令批量提取（1 次调用 ≈ 10 秒）
cd <ws>/handoff && for f in handoff-*.md; do
  echo "=== $f"
  sed -n "/^## 目标/,/^## /p" "$f" | sed -n "2,3p" | cut -c1-100
done
```

**判据：总工具调用次数 ≈ 批数 + 事件数，而不是 ≈ 账本数。**

## 五条禁止行为

```
❌ 为一个信息量重复 grep 同一个文件 3 次以上
❌ 用 find 全盘搜索插件安装位置（不需要知道插件装在哪）
❌ 用 session_trace / session_event_search 查「我自己是谁、在哪个会话」
❌ 读上一个子代理写的 SELFCHECK.md / REPORT-TABLE.md 再逐条核对
❌ 为确认格式去翻 event-store.js 的 schema（用 memory_event 试写一条即可）
❌ 写 Python 脚本反复验证「桶里有没有漏文件」（过度自证）
```

## 正确的最短路径

```
第 1 步（30 秒）：pwd; ls handoff/ | head -5
第 2 步（1 分钟）：批量建索引（见批量化一节的 for 循环）
第 3 步（2-5 分钟）：在脑内归组，不要写脚本验证
第 4 步（批量写盘）：每个事件一次 memory_event(action:create)
第 5 步（30 秒）：守恒自检 ls handoff-*.md | wc -l 对比 members 总和
```

## 进度信号

```
某一步预计超过 60 秒 ⇒ 先输出一行进度再执行：
  「已读 120/500 篇，识别出 23 个候选事件，继续」

沉默超过 3 分钟 = 用户会以为崩溃。
```

## 效率与质量的平衡（是为快但不能丢东西）

```
✅ 可以省的：探路、读源码、重复验证、逐条核对前序成果
❌ 不能省的：
   · 账本守恒自检（丢账本 = 不可接受）
   · 备份（阶段 1 必须做，一次 cp -r 即可，不慢）
   · 事件名质量（垃圾名会让白板难看，返工更慢）
```
