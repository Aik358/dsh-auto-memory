## 一、宿主已提供什么【实测 · 硬证据】

证据来源：`~/.dsh/profiles/.../node_modules/@deepseek-ai/`（DSH `0.1.7-rc.2`，与全局 npm 包同版本）。

| 宿主包 | 版本 | 它是什么 | 对团队版的意义 |
|---|---|---|---|
| `dsh-authorization` | 0.1.7-rc.2 | **授权接缝 `ctx.authorization`**：「plugin-owned flows that obtain a credential through a conversation with the human」 | **插件接身份的正规入口** |
| `dsh-deepseek-account` | 0.1.7-rc.2 | 账号服务：读取账号状态、解析官方 API 凭据；事件 `deepseek-account/signed-out`、`deepseek-account/model-sign-in-required` | **"已登录"状态的真源** |
| `dsh-api-account-controller` | 0.1.7-rc.2 | 「Expose safe account operations over authenticated Remote」，含 `login` / `loginSource` | 前端可发起登录 |
| `dsh-client-ui-settings-account` | 0.1.7-rc.2 | 账号设置界面 | **登录 UI 已存在，不需要我们做** |
| `dsh-anonymous-user-id` | 0.1.7-rc.2 | 共享匿名用户标识（用于遥测/反馈关联） | 匿名场景的既有做法 |
| `dsh-experimental-agent-team` | 0.1.7-rc.2 | **Agent Teams**：roster + durable peer mailbox + shared task DAG | 宿主级"团队"能力的既有参考实现 |

### 1.1 `ctx.authorization` 的契约（摘录自 `dsh-authorization/lib/index.d.ts`）

```ts
const dispose = ctx.authorization.registerFlow({
  key: credentialKey('llm-pi-ai', 'openai-codex'),
  label: 'ChatGPT (Codex)',
  methods: [{ id: 'oauth', label: 'Sign in with ChatGPT' }],
  async run(session) {
    session.notify({ message: 'Continue in your browser', url })
    await commitThroughCredentials(await exchange(session.signal))
  },
})
```

关键语义（**逐条都是团队版验收的硬约束**）：

| 契约 | 内容 | 对我们的影响 |
|---|---|---|
| **flow 由插件注册** | 按 `CredentialKey` 注册，seam 只管会话与生命周期，**不管协议** | 我们可注册自己的团队凭据 flow |
| **一次一个 key 只能有一个进行中的尝试** | `describe(key)?.inFlight`；重复 `begin()` 被拒为 `ALREADY_IN_FLIGHT` | 前端必须做**单飞**：登录按钮防重复点击 |
| **通知能力自带 `code` 字段** | `session.notify({ message, url?, code? })` —— 「a short code the human must enter on that page」 | **设备码流程是宿主原生形态**（旧调研路线 C 得到证实） |
| **提示能力** | `prompt({kind:'text'｜'secret'｜'select'})`，`secret` 会被遮蔽且不进日志 | 输入凭据有正规通道，**插件不必自己收密码** |
| **事件 `authorization/settled`** | 每次尝试结束（含失败）都会触发，携带 `settlement` | 前端可监听它做状态刷新（第二个浏览器标签也能感知） |
| **结束状态** | `authorized` / `cancelled`；失败以**抛错**形式给调用方，旁观者看到 `failed` | 区分"人拒绝了"与"系统坏了"（`AuthorizationDeclinedError` 专表"人说不"） |

> **这条接缝同时废弃了旧调研的两条路线**：
> - 路线 A「为回调开专用例外路由」→ **不需要**（宿主自己处理回调，插件不碰）。
> - 路线 B「本机回环临时监听」→ **不需要**（同上）。
> - 路线 C「设备码」→ **正是宿主原生形态**（`notify.code` 现成）。

### 1.2 旧调研的"回环守卫挡住 OAuth 回调"问题**已自动消解**

旧 R2 实测：10 例真机证明 `Sec-Fetch-Site: cross-site` / 外部 Origin / 内网 IP 与域名 Host **一律 403**，覆盖全部路由。
**本轮结论**：既然登录由宿主接缝提供（回调打在宿主自己的端点上，不由插件路由承载），**这条硬约束对插件不再构成阻塞**。
⇒ 插件侧**不要新增任何对外回调路由**；一切身份相关交互走 `ctx.authorization`。

## 二、成员映射：从"宿主账号"到"团队成员"（插件的唯一职责）

### 2.1 三层身份模型

```
宿主账号（DeepSeek 账号 / 企业 IdP，由宿主管理）
        │  宿主提供
        ▼
设备身份（本机 installation id + 匿名 id，dsh-anonymous-user-id 现成）
        │  插件映射
        ▼
团队成员（team member: teamId + memberId + displayName + role + 设备列表）
```

### 2.2 映射规则（实现要点）

| 规则 | 说明 |
|---|---|
| **不做独立账号体系** | 遵用户裁定 1：「登录由宿主提供，插件不自建账号体系」 |
| **首登生成成员记录** | 第一次带着宿主身份连接团队服务端时，服务端创建成员记录；`memberId` 由服务端发 |
| **一账号多设备** | `memberId` 与设备解耦（同一个人两台机器应是一个成员、两个设备） |
| **无账号时的降级** | 宿主未登录时，插件**必须仍可单人使用**；团队功能整体置灰并说明原因 |
| **退出登录** | 监听 `deepseek-account/signed-out` ⇒ 停止同步、清内存中的令牌，**不删本地记忆** |

### 2.3 与既有 `actor` 字段的衔接（向后兼容）

本仓已有 `addedBy` 字段（双库改造第 1 步落地）——它是**字符串**。
升级路径（**不破坏既有数据**）：

```
旧值：addedBy: "张三"                        ← 保留可读
新值：actor: { id: "m_7f3a", name: "张三" }   ← 新增结构化字段
      addedBy 仍写显示名（兼容旧读取路径）
```

**判据**：任何读 `addedBy` 的旧代码不改也能工作；新代码优先读 `actor.id`（**稳定**，显示名可改）。

## 三、多租户与权限

### 3.1 租户模型

| 概念 | 说明 | 边界 |
|---|---|---|
| **团队（Team）** | 企业/组织，数据隔离的第一层 | `teamId` |
| **项目（Project）** | 团队内的项目，对应插件的"工作区" | `projectId`（见 03 卷 8.3） |
| **成员（Member）** | 人 | `memberId` |
| **设备（Device）** | 一台机器的一个插件实例 | `deviceId` |
| **角色（Role）** | `owner` / `admin` / `member` / `guest` | 决定审批、组织策略、审计可见性 |

### 3.2 权限矩阵

| 能力 | owner | admin | member | guest |
|---|---|---|---|---|
| 读团队库 | ✅ | ✅ | ✅ | ✅（仅被授予项目） |
| 写项目库 | ✅ | ✅ | ✅ | ❌ |
| 写团队通用库 | ✅ | ✅ | ✅（留痕） | ❌ |
| 审批技能晋升 | ✅ | ✅ | ❌ | ❌ |
| 设组织策略（规则层） | ✅ | ✅ | ❌ | ❌ |
| 看团队审计 | ✅ | ✅ | ❌（仅自己） | ❌ |
| 成员管理 | ✅ | ✅ | ❌ | ❌ |
| 团队配额与健康度 | ✅ | ✅ | ❌ | ❌ |
| 导出/删除团队数据 | ✅ | ❌ | ❌ | ❌ |

### 3.3 数据隔离硬判据（企业安全评审会问）

1. **跨团队零可见**：`teamId` 必须进入每一次服务端查询的 where 条件，**不允许在客户端过滤**。
2. **令牌不落明文**：凭据进宿主 `credentials` seam（宿主已有），插件只持 `credentialKey`。
3. **审计不可改**：追加日志，写后不可编辑（只可追加更正记录）。
4. **退出即断**：退出团队后本地缓存标记为"孤儿数据"，由用户决定保留或删除。

## 四、桌面版 / Web 版 / 远程操控 三种形态下的登录

| 形态 | 宿主登录可用性 | 插件的做法 |
|---|---|---|
| **桌面版（本机 19387）** | ✅ 可用 | 直接读账号状态；走 `ctx.authorization` |
| **Web 版** | ✅ 可用 | 同上；注意端口不是 3080（旧记忆已作废） |
| **远程操控**（端口转发 / 内网 IP / 域名） | ⚠️ 取决于宿主 | **登录走宿主（不碰插件路由）**，因此远程形态**不再影响插件登录**；但仍需在设置页显示当前连接方式，便于排障 |

> **旧调研的"阻塞项"（用户当时的远程操控形态是端口转发还是内网 IP？决定 54 条路由是否半坏）在本轮已降级**：身份路径不再经过插件路由，风险面显著缩小。
