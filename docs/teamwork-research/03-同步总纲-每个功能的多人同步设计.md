# 03 · 同步总纲：每个功能的多人同步设计

> 本卷回答你的第 1 个要求：**「明确多人合作（teamwork）时该如何同步」**。
> 覆盖范围：02 卷测绘出的**全部 8 族 38 项功能**，一项不漏。
> 本卷给**规则**（怎么同步、冲突怎么解），04–09 卷给**分族细节**，13 卷给**实施顺序**。

---

## 一、四条第一性判据（先立规矩，后面所有设计都受它约束）

### 判据 1：能重算的，永不搬运
向量、L0 索引、看板 sidecar、重要性评分、覆盖率统计 ⇒ **全部是派生数据**。
搬运派生数据 = 把冲突面从「一份事实」放大成「n 份派生拷贝」。**同步面必须只含事实源。**

### 判据 2：物理分文件是同步的先行条件【已落地】
技能库已改为**物理分文件双库**（`hub/procedures.json` + `workspaces/<ws>/hub/procedures.json`），用户裁定理由即「单文件在团队同步时整个文件都落在冲突面上」。
⇒ 这条经验必须**推广到其余所有共享数据**：一个人的日志不该和另一个人的日志在同一个文件里。

### 判据 3：写入必须携带身份
现有 `addedBy` 字段（双库改造第 1 步已落地）是**身份字段的既有基础**。同步的每条记录都必须有 `actor`（谁）、`at`（何时）、`origin`（哪台设备/哪个工作区）。**没有这三项的数据不参与同步**。

### 判据 4：本地永远可用（本地优先不可退让）
插件当前卖点之一是「本地优先存储」。同步设计**不得**让"云端不可达"变成"记忆不可用"：所有写路径先写本地 → 再进同步队列。**离线可写、可读，联网后收敛。**

## 二、作用域模型（把数据分四类，规则各不相同）

```
S0 本机私有      ——  永不入同步队列（心跳、更新检查、模型缓存、venv、*-pre 遗留、.bak）
S1 个人云        ——  跟随「人」，跨设备同步，但不进团队库（个人日志、反思、个人日历、主题偏好）
S2 团队共享      ——  进团队库，受治理（规则、事实、证据、技能、交接、白板、团队日历）
S3 派生重算      ——  不入同步面，接收变更事件后本地重算（向量、索引、sidecar、评分）
```

**S2 的团队库必须再分两层**（这是既有物理分文件设计的直接延伸）：

| 层 | 物理对应 | 语义 | 谁能写 |
|---|---|---|---|
| 团队通用库 | `hub/`（全局） | 跨项目复用的团队知识 | 成员提交 + 审批/留痕 |
| 团队项目库 | `workspaces/<ws>/hub/` | 本合同/本项目专属 | 项目成员自由写 |

> **重要**：工作区 key（`wsKey`）当前是**按本机路径派生**的（如 `--D--dsh-auto-memory--`）。
> 跨用户同步时，两个人在 D 盘和 C 盘克隆同一个仓库会得到**不同 wsKey** ⇒ **项目库无法自动汇合**。
> **必须引入「团队项目 ID」**（见本卷第 8.2 节），把它作为 S2 项目库的权威键，本机 wsKey 降级为**本地别名**。

## 三、六条同步原语（实现层的全部积木）

| # | 原语 | 适用 | 语义 | 落到本仓 |
|---|---|---|---|---|
| P1 | **字段级 LWW** | 结构化记录的单字段（标题、状态、评分） | 按 `updatedAt` 大者胜，**按字段而非整条**判定 | facts.json / procedures.json 的字段 |
| P2 | **追加日志（append-only + 单调序号）** | 日志、证据、审计、时间线 | 只追加不覆盖，用 `(actorSeq, lamport)` 排序 | 每日日志、evidence、recall 反馈 |
| P3 | **OR-Set（加/删标记）** | 集合型成员（标签、参与者、别名） | 并发 add/remove 用唯一标记解，**不丢并发新增** | 标签、成员、关键词 |
| P4 | **两阶段搬运（先写接收→读回校验→再删源）** | 跨库转移、上云、跨机搬包 | 既有 `scoped.migrate()` 已是这个语义，**直接复用** | 技能晋升/收纳、migrate-pack |
| P5 | **墓碑（tombstone）+ 保留期** | 删除 | **不真删**，写墓碑（谁在何时删），保留 N 天后可清理 | 记忆条目、事实、技能 |
| P6 | **重算（recompute）** | S3 派生 | 收到变更事件 → 本地重算 → 带版本号上报 | 向量、索引、sidecar、评分 |

**关键设计：把「删除」也做成不删。** 本仓已有 `superseded`/`retracted` 的三态治理（用户裁定「返回但标记是正确的」）⇒ 删除走墓碑与三态是**同一套哲学的延伸**，不是新增负担。

## 四、四条通道与延迟预算

| 通道 | 内容 | 延迟预算 | 传输 | 失败降级 |
|---|---|---|---|---|
| **T0 即时** | 在线状态、成员在场、锁/占用 | ≤ 2s | WebSocket/SSE | 降级为 T1 |
| **T1 秒级** | 文本类记忆（日志/笔记/事实/证据/规则） | **≤ 5s** | 增量推送（CDC） | 重试 + 本地队列 |
| **T2 分钟级** | 结构化库（技能/白板/看板 sidecar） | ≤ 60s | 批量 + 摘要 | 本地可用 |
| **T3 异步** | **向量与索引（派生）** | **≤ 5 min** | 事件驱动重算 | 只影响语义召回新鲜度 |

> **「实时同步」的准确定义**（沿 B 卷结论）：**用户可见的事实 ≤5s，语义召回允许 ≤5min 滞后**。
> 这样既满足"两个人同时看到同一条记忆"，又避免把嵌入计算压进同步路径（那才是真正的成本陷阱）。

## 五、架构主线（权威服务端 + CDC）

```
   ┌──────────── 成员 A 本机 ────────────┐        ┌──────────── 成员 B 本机 ────────────┐
   │  插件（本地优先）                    │        │  插件（本地优先）                    │
   │  ├ 本地写 → 立即可用（不等网络）      │        │  ├ 本地写 → 立即可用                 │
   │  ├ 变更 → 本地 outbox 队列            │        │  ├ 变更 → 本地 outbox 队列           │
   │  └ 派生重算（S3，本地）               │        │  └ 派生重算（S3，本地）              │
   └───────────────┬─────────────────────┘        └───────────────┬─────────────────────┘
                   │  HTTPS（增量，带 actor/at/origin）             │
                   ▼                                              ▼
   ┌──────────────────────── 团队权威服务端（企业自建/私有云） ────────────────────────┐
   │  身份与成员映射  │  权威存储（团队库 S2）  │  变更日志 CDC  │  冲突裁决  │  审计   │
   └───────────────┬──────────────────────────────────────────────────────────────────┘
                   │ 变更流（订阅）
                   ▼
   ┌──────── 对象存储（冷数据/证据原文/快照） ┐   ┌──────── 向量库（可选，派生层） ┐
   └──────────────────────────────────────────┘   └─────────────────────────────────┘
```

**为什么不选 CRDT**（沿 B 卷，本轮复核仍成立）：本数据模型以**文档型 + 追加日志**为主，CRDT 的收益集中在「高频协同编辑同一段文本」，而本场景的并发写**很少落在同一段落**上；引入 CRDT 会把全部读写路径改成 CRDT 数据结构，代价远大于收益。**备选**：若未来出现"多人同时编辑同一份白板"的真实需求，再对**白板单文件**局部引入。

## 七、逐功能同步设计（38 项全量）

> 列含义：**同步模式**（用哪条原语）/ **冲突策略** / **前端必须显示**。

### A 族 · 唤回与检索

| 功能 | 同步模式 | 冲突策略 | 前端必须显示 |
|---|---|---|---|
| A1 主动召回 | 召回**本身是本机行为**；被召回的内容来自本地已同步的 S1/S2 | 不冲突 | 每条召回结果标「来源：本地/团队/某人」+ 同步新鲜度徽标（如「团队库 3 秒前」） |
| A2 影子检索 | 同上；影子命中**可上报**（P2 追加）作为团队质量信号 | 不冲突 | 「影子命中」区显示本机与团队两个口径 |
| A3 JS 语义引擎 | 模型资产随包分发（不进团队库）；**索引派生** | P6 重算 | 面板显示「本机语义索引覆盖 x% / 团队 y%」，并说明**滞后时间** |
| A4 Python 语义引擎 | venv 与依赖**纯本机**；仅上报「引擎身份」声明 | P6 | 显示引擎身份（JS/Python）+ 是否与团队一致；**严禁因团队统一而自动切换用户引擎**（铁律） |
| A5 L0 索引 | 派生，P6 | P6 重算 | 显示层级索引的新鲜度 |
| A6 召回统计 | 个人统计 **S1**；团队聚合走 **P2 追加计数** | P2 单调 | 统计页分「我的 / 团队」两栏；团队栏显示成员参与度 |

| 功能 | 同步模式 | 冲突策略 | 前端必须显示 |

## 八、后端改动点全量（**不改本体**，指「未来实施时要改哪里」）

> **前提重申**：本调研**不改动** `lib/` 与 `client.js`（哈希基线见 `_BASELINE-HASHES.json`）。
> 本节列出的是**将来实施**时的改动点清单，用于排期与评估，不是本轮动作。

### 8.1 收口点（只需改 3 处就能承载 56 条路由的同步）

| # | 文件 | 现状 | 要做的改动 | 影响面 |
|---|---|---|---|---|
| B-1 | `lib/datadir.js` | `memoryDir(name)` 是唯一物理路径出口 | 增加**作用域解析层**：返回 `{path, scope}`，其中 scope ∈ S0/S1/S2/S3 | 全插件路径都经此 ⇒ **单点改造** |
| B-2 | `lib/hub-io.js` | 已有 `createScopedHubIoPre`（双库分派） | 扩展为**多作用域分派**（加入 S1 个人云层），并挂 outbox 队列 | 技能/事实读写 |
| B-3 | `lib/config-io.js` | 配置原子写 | 拆**团队策略 / 设备偏好**两个命名空间 | 148 个键的归属划分 |

### 8.2 必须新增的 5 个模块（放在 `lib/`，均为新文件）

| 模块（建议名） | 职责 | 关键设计 |
|---|---|---|
| `team-identity.js` | 成员身份：把宿主的登录身份映射为 `actor` | **不建账号体系**（用户裁定 1）；只做映射 + 注入 + 审计 |
| `sync-outbox.js` | 本地变更队列：写入即入队、离线可写 | 队列项含 `actor/at/origin/op/target/hash`；**幂等键 = 内容 hash + 逻辑时钟** |
| `sync-pull.js` | 拉取与合并：CDC 变更流 → 本地 apply | apply 必须**只走既有写路径**（复用既有校验，不绕过 Gate） |
| `conflict-center.js` | 冲突检测与人工裁决队列 | 只对 4 处需人工裁决的数据类型建队列 |
| `team-project-map.js` | **团队项目 ID ↔ 本机 wsKey 映射** | 解决 wsKey 按路径派生导致跨用户无法汇合的问题（见 8.3） |

### 8.3 ★ 必须解决的两个「身份级」缺陷（否则同步必然出错）

| 缺陷 | 现象 | 后果 | 解法 |
|---|---|---|---|
| **wsKey 按本机路径派生** | A 在 `D:\proj`、B 在 `C:\proj` 打开同一仓库 | 两人各写各的 `workspaces/<wsKey>/`，**项目库永远汇合不了** | 引入**团队项目 ID**（如 git remote + 相对路径 或 显式登记），wsKey 降级为本地别名 |
| **技能 id 由标题+创建时间哈希** | 两人各建同名技能 | 得到**不同 id** ⇒ 同步后**重复两条** | 换为**内容寻址 id**（规范化正文的 hash），标题与时间为元数据 |

> 这两条是旧调研已识别但未解决的**风险项**，本轮给出具体解法；实施时**必须先做**，否则后面所有同步都在错的基础上。

## 十、灰度与回退（企业交付必须给的能力）

| 阶段 | 灰度策略 | 回退手段 |
|---|---|---|
| G0 影子 | 同步**只读**：拉取但不写本地共享库 | 关 `team.enabled` 即回到纯本地 |
| G1 单向 | 本机 → 团队（只推不拉） | 关闭推送 |
| G2 双向 | 全通道开启，冲突走人工 | 逐通道回退（`team.syncChannels`） |
| G3 全员 | 全团队启用 | 保留"退出团队并本地化"能力（**数据不回删**） |

**铁律**：任何阶段都必须保证 **关掉团队开关后，插件与本轮之前的行为逐字节一致**（这是"不破坏单人体验"的验收点）。

## 十一、风险清单（每条给触发条件与对策）

| # | 风险 | 触发条件 | 对策 |
|---|---|---|---|
| R1 | **wsKey 跨机不汇合** | 两人不同盘符/路径克隆同一仓库 | 团队项目 ID（8.3）**必须先做** |
| R2 | **技能 id 撞车产生重复** | 两人各建同名技能 | 内容寻址 id（8.3） |
| R3 | **晋升证据计数互相覆盖** | 两机各自累加同一技能证据 | 证据走 P2 追加日志，**不写计数绝对值** |
| R4 | **项目笔记整篇级冲突** | 两人同时改 MEMORY.md | 分区块 + 人工裁决 + 冲突副本 |
| R5 | **向量漂移导致新旧不可比** | 团队换嵌入模型/模型版本不一致 | 向量带**模型版本号**，版本变更触发全量重算标记 |
| R6 | **本地优先被破坏** | 同步逻辑阻塞写路径 | 写本地 → 入队异步；**同步永不 await** |
| R7 | **老数据目录被同步** | `*-pre`、`.bak-*` 被扫进同步面 | 黑名单 + 白名单双保险（`team.excludedPaths`） |
| R8 | **明文存储被客户质疑** | 客户安全评审 | 遵裁定 2：**主动披露「当前明文」** + 预留加密接口 + 企业自持密钥 |
| R9 | **回环守卫拦住回调** | 走 OAuth 回调式登录 | 走**宿主登录 + 设备码**（无回调），沿 R2 结论 |
| R10 | **配置漂移**：一人主题偏好污染全团队 | 团队策略与设备偏好未拆分 | 配置分两层（B-3） |
