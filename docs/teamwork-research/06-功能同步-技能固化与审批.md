# 06 · 功能同步：技能固化与审批（C 族）

> 覆盖 C1 技能库双库 / C2 技能观测 / C3 技能审批 / C4 SKILL.md 导出。
> **这一族是团队共享的「核心资产」** —— 团队记忆最有价值的产物就是别人验证过的工作方法。

## C1 技能库双库（物理分文件）

### 现状【实测】
- 通用库：`~/.dsh/memory/hub/procedures.json`
- 工作区库：`~/.dsh/memory/workspaces/<wsKey>/hub/procedures.json`
- 模块：`lib/hub-io.js` 的 `createScopedHubIoPre`（合并读 + 按 scope 分派写）
- 用户裁定理由：「单文件在团队同步时整个文件都落在冲突面上」

### 多人同步
物理分文件**已经是同步友好形态**，但仍有两个必须补的洞：

| 洞 | 现象 | 解法 |
|---|---|---|
| **wsKey 按本机路径派生** | 两人不同盘符 ⇒ 项目库不汇合 | 引入**团队项目 ID**（见 03 卷 8.3） |
| **技能 id = 标题 + 创建时间哈希** | 两人各建同名技能 ⇒ 两个 id ⇒ 同步后重复 | 换**内容寻址 id**（规范化正文 hash） |

**同步模式**：工作区库 P1 逐条；通用库 P1 + 审批。**冲突**：见 03 卷冲突矩阵。

### 后端改动点
| # | 位置 | 改动 |
|---|---|---|
| 1 | `procedure-store.js` | id 生成改为内容寻址（保留旧 id 作 `legacyId` 以兼容） |
| 2 | `hub-io.js` | 增加**合并策略钩子**：拉取到本地时走 `scoped` 分派（复用既有两阶段语义） |
| 3 | 记录结构 | 每条加 `actor` / `at` / `rev` / `teamId` / `adoptedBy`（谁采纳了它） |
| 4 | 观测计数 | 拆成「本机观测数」与「团队观测数」两个来源，**不合并成一个绝对值** |

### 前端显示
- 记忆库「技能固化」筛选下，每条显示：**库徽标**（工作区/通用）、作者、创建时间、**团队采纳数**、当前阶段（observed/validated/active/deprecated）。
- 新增筛选：按库、按作者、按「我是否已采纳」。
- 同 id 冲突（历史遗留重复）时显示合并入口，不静默去重。

## C2 技能观测

### 现状
从对话观测候选流程（`procedure-observation.js`、`procedureMinSessions` / `procedureMinSuccess`）。

### 多人同步
- 观测**在本机发生**（你的对话里发现了这个方法）。
- **候选可以贡献给团队**，但必须**先经本人同意**（默认不入 S2）。
- 团队观测数可作为晋升的更硬证据（跨人验证 > 同一人多轮）。

### 后端改动点
1. 观测事件本地记录；提供**按条上报**（不是批量自动上报）。
2. 团队观测数走 **P2 追加**，计入晋升门槛时可配权重。

### 前端显示
- 候选卡显示：`本机观测 4 次 · 团队观测 11 次（3 人）`。
- 「贡献给团队」按钮，附说明：「他人将看到这条方法的步骤，看不到你的原始对话」。

## C3 技能审批（团队治理的核心）

### 现状
`memory_procedure` 的 `action=write|activate`；风险等级 `procedureHighRiskApproval`；`procedureActiveLevel`。
**用户已裁定**：「通用库写入只留痕不审批」—— 即**通用库**写入留痕即可；但**晋升为 active / 高风险的**仍需人工批准。

### 多人同步
审批是**团队动作**，需要状态机：

```
提议(proposed) ──提交→ 待审(pending) ──批准→ 已采纳(active)
                       │                    
                       └──驳回→ 已驳回(rejected)  （不可自动复活）
高风险(riskLevel=high)：必须 ≥1 名管理员批准
```

- **并发批准**必须幂等（两人同时点批准 = 一次批准）。
- **驳回后**同一技能不可自动复活，需显式重开。
- 审批记录走 **P2 追加**（谁在何时批的），状态走 **P1**。

### 后端改动点
| # | 改动 | 说明 |
|---|---|---|
| 1 | 审批记录存储 | 独立追加日志（`hub/approvals.jsonl` 形态），不与技能本体混放 |
| 2 | 幂等键 | `(skillId, approverActor, decision)` 三元组去重 |
| 3 | 权限判定 | 依赖 `team-identity.js` 的角色（成员/管理员） |
| 4 | 通知 | 待审项进成员待办（复用既有 notices 通道） |

### 前端显示
**新增「审批」面板**（建议放在记忆库内的一个 tab，或冲突中心的兄弟页）：
- 待审列表：技能标题、提议人、风险等级、证据数、**步骤差异视图**（与已存在的相似技能对比）。
- 操作：批准 / 驳回（必填理由）/ 要求补充证据。
- 已审历史：谁批的、什么时候、驳回理由。
- 我的待办计数徽标（如「待审 2」）。

## C4 SKILL.md 导出

### 现状
`skill-export.js` / `skill-export-host.js`；`resolveSkillsRootPre`；导出到 `~/.dsh/skills/<name>/SKILL.md`。

### 多人同步
- 导出产物是**文件**，可进 S2（让团队共用技能文件），也可仅本地。
- 同名覆盖走 P1；不同内容同名时**保留双份**并提示（不静默覆盖）。

### 后端改动点
1. 导出时写 `teamId` 与 `sourceSkillId` 元信息头，便于溯源。
2. 团队技能文件的更新走**显式拉取**而非覆盖（避免把本地自定义改掉）。

### 前端显示
- 导出按钮旁显示目标：`导出到：本机技能目录 / 团队技能库（二选一）`。
- 已导出条目显示「团队技能库 v3 · 张三 更新于 2 天前」。

## 本族汇总

| 功能 | 同步模式 | 后端改动 | 前端显示 |
|---|---|---|---|
| C1 技能双库 | 物理分文件 + P1/P4 | 内容寻址 id、身份字段、观测计数拆分 | 库徽标/作者/采纳数/筛选 |
