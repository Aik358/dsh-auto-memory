# 07 · 功能同步：交接与白板（D 族）

> 覆盖 D1 交接账本 / D2 PLAN 白板 / D3 看板泳道 / D4 水位感知 / D5 自动接续。
> **这一族是「跨人接续」的载体**，也是「失败与弯路是一等公民」这条差异化卖点的落点。

---

## D1 交接账本（handoff）

### 现状
`workspaces/<ws>/handoff/*.md`；四段式（任务状态 / 目标 / 已试方案与失败原因 / 进度与下一步）；工具 `memory_note(kind=handoff)`。

### 多人同步
**天然同步友好** —— 账本是**追加新篇**，不同人写不同篇，**结构上不冲突**。

- 走 **P2 追加**：永不修改别人的账本。
- 每篇必须带作者与时间（现在的时间戳已在标题里，需补 `actor`）。
- 「谁在什么时候接手」是最有价值的团队信息 ⇒ 需要显式的**接续事件**。

### 后端改动点
1. 账本文件头补 `actor` / `sessionRef` / `prevHandoff`（指向前一篇）。
2. 新增「接续事件」记录（谁接续了谁的账本）。
3. 拉取他人账本时**只读合并**进本地时间线，不写回原作者文件。

### 前端显示
- 白板页账本时间线：**按人分色**，卡片显示作者头像。
- 每篇顶部显示「上一位：张三 · 4 小时前」+ **接续链**（可一直往回追）。
- 「失败与弯路」段落用**专用语义色**（沿用既有 `--err` 契约色），一眼可辨。
- 团队视图：默认显示本项目所有人的账本（可切换「仅我」）。

## D2 PLAN 白板

### 现状
`workspaces/<ws>/handoff/PLAN.md`；「人能读的项目全貌规划图」；有 `memory_note(kind=plan)` 整体重写语义 + M1 保护门（防丢卡）。

### 多人同步
**这是全插件冲突风险最高的地方** —— 整篇级别的文档，两人同时重写必然冲突。

**解法：分区块 + 整篇重写走人工裁决**

| 操作 | 策略 |
|---|---|
| 改单个卡片 / 某一段 | 区块级 **P1**（按区块 id 判定，不整篇比） |
| 整篇重写（kind=plan） | **人工裁决 + 冲突副本**，禁止静默覆盖 |
| 新增段落 | 追加，不冲突 |
| 删除卡片 | **P5 墓碑 + 必须显式声明**（既有 M1 保护门已有的语义，延续它） |

> **既有契约可复用**：M1 保护门已经要求「重写时必须逐条抄回全部 `<!--memory:mem_*-->` 锚点，缺锚点会被拒绝」——这正是**防丢卡**的机制。团队版只需在它之前加一层「与团队版本比对」。

### 后端改动点
| # | 改动 | 说明 |
|---|---|---|
| 1 | 区块 id 化 | 现有卡片已有 `mem_*` 锚点 ⇒ 直接当区块 id 用，无需新机制 |
| 2 | 三方合并 | 本地基线 / 我的改动 / 团队版本 → 三方合并；冲突区块单独标出 |
| 3 | 冲突副本 | 冲突时生成 `PLAN.conflict-<actor>-<ts>.md`，**两份都留** |
| 4 | 重写前的团队比对 | 重写前先拉团队最新版本，若已变则提示「团队版本已更新，请先合并」 |

### 前端显示
- 白板顶部：「最后更新：张三 · 3 分钟前」+ 团队成员在场指示。
- **冲突时双栏对照**：左「我的版本」右「团队版本」，逐区块高亮差异，操作：保留我的 / 保留团队的 / 两份都留 / 逐区块选。
- 卡片右上角显示**最后编辑者**小头像。
- 「待合并」角标出现在白板页签上。

## D3 看板泳道

### 现状
5 泳道（目标 / 进行中 / 失败与弯路 / 进度与下一步 / 版本归档）；由白板与账本派生的 sidecar 索引（`wb-sidecar.js`、`buildKanbanPre`）；宿主页看板（`kanban-board` / `kanban-card` 路由）。

### 多人同步
- **sidecar 是纯派生数据 ⇒ 不入同步面**（S3）。团队内容变化后本地重算。
- 但「看板卡」上有**人为状态**（如"已完成""进行中"）—— 这部分是**事实**，必须同步。
- ⇒ **要拆开**：派生的展示索引不同步；卡片状态、负责人、截止日 **S2 同步**。

### 后端改动点
1. 把「卡片状态 / 负责人 / 截止」从派生 sidecar 中**抽成独立的事实存储**（否则重算会丢人为状态）。
2. 该事实存储走 P1 字段级。
3. 「失败与弯路」泳道保留（用户已裁定），并补充**谁记录的**这一条弯路。

### 前端显示
- 看板卡：负责人头像、来源（哪本账本/白板）、记录人。
- 泳道头显示团队成员头像堆叠（谁在参与这个项目）。
- 「失败与弯路」卡显示「记录人 · 时间」，让教训可追溯到人。

## D4 水位感知

### 现状
`workbench.json`；`waterLevelWindowTokens` / `waterLevelThreshold` / `officialCompactionRatio` 等；路由 `auto-continue-state` / `auto-continue-decide`。

### 多人同步
- **纯 S0 本机态**：水位是**个人上下文压力**，与团队无关。
- 团队层面只可能有一个东西：**团队统一的建议阈值**（策略 S2，P1 管理员优先），但执行在本机。

### 后端改动点
1. 水位计算不得读取团队配置作为输入（仅可读「建议值」用于显示）。
2. 确保关闭团队后水位行为逐字节不变。

### 前端显示
- 水位卡只显示自己的水位。
- 若团队下发建议阈值：显示一条对照行 `团队建议阈值 60% · 你的设置 61%`，**不自动改**。

## D5 自动接续

### 现状
`auto-continue-done.json` / `cont-seq.json`；`autoContinueEnabled` / `autoContinueThreshold` / `autoContinueRefreshRitual` 等。

### 多人同步
- **纯 S0 本机态**：自动接续是"我一个人接着我自己跑"，与团队无关。
- 唯一关联点：接续时**应拉取团队最新白板/账本**（否则接续的是过期上下文）。

### 后端改动点
1. 接续触发时增加一次「团队库新鲜度检查」，若滞后则先同步再续。
2. 接续记录里带 `teamSyncAt`，便于排查"续跑用了旧记忆"。

### 前端显示
- 接续卡显示：`接续前已同步团队库（3 秒前）`。
- 若团队库不可达：显示「使用本地版本接续，可能滞后」的警告。

## 本族汇总

| 功能 | 同步模式 | 后端改动 | 前端显示 |
|---|---|---|---|
| D1 交接账本 | **P2 追加**（结构上不冲突） | 补 actor / 接续链 / 接续事件 | 按人分色 + 接续链 + 失败色 |
| D2 PLAN 白板 | 区块 P1 / 整篇人工裁决 | 区块 id、三方合并、冲突副本、重写前比对 | **双栏对照** + 编辑者 + 待合并角标 |
| D3 看板泳道 | 派生重算 + 人为状态 S2 | 抽取人为状态为独立存储 | 负责人 / 记录人 / 参与头像 |
| D4 水位感知 | S0 本机 | 不读团队配置做输入 | 仅建议值对照 |
| D5 自动接续 | S0 + 接续前拉取 | 新鲜度检查 + teamSyncAt | 同步状态提示 / 滞后警告 |

**本族待拍板**：

2. 看板的「人为状态」抽取是否需要**独立成页**（当前是派生 sidecar 的一部分）？
