这不是正式版。不上 npm，只发 GitHub。目的不是让普通用户升级，而是让社区先跑起来做核验与研究。

3　设计意图（先读懂，再判断对错）

3.1　三层结构，各管一件事

层单位是否事件化职责
长期记忆事件 evt_xxxxxxxx✅ 是一件事一个容器，跨天可中断再捡起
每日日志日期❌ 否日记类，按天追加
每日反思日期❌ 否日志的蒸馏产物，独立于事件

这是刻意的，不是遗漏。日志与反思的语义单位是「一天」，硬塞进事件会逼模型在写日记时反推「这属于哪件事」——纯噪声。

3.2　事件里装什么

事件 evt_a1b2c3d4
├── name / summary        ← L0 总览，可随时重写
├── sections{goal, doing, dead, next}   ← 反映【当前】状态，非历史累积
├── checkpoints[]         ← append-only，只增不改
├── userPercept[]         ← 人类侧观察
├── agentTrace[]          ← Agent 动作
├── sharedGround[]        ← 已达成的共识
└── commitment[]          ← 对用户的承诺

3.3　两条硬约束

  1. 检查点 append-only —— 历史不重写。要更正就追加新检查点 + supersedes/retract 标记。
  2. 每次 append 后必须重写 sections —— 只追加不刷四段，四段会静默变成陈旧快照，注入的 next 开始指向早就做完的事。

3.4　白板是投影

handoff/PLAN.md 由事件渲染，不是手写文档。手写会丢 <!-- memory:mem_* --> 锚点，卡片体系断裂。

4　已知问题（请优先验这些）

4.1　团队同步的服务端完全未验证 ⚠️

本机 teamEnabled=false、teamServerUrl 为空。未证伪：服务端是否接受未知 kind、能否承载 322 KB 请求体。

node tools/probe-team-baseline.mjs --url <你的服务端> --token <token>

零副作用（用 __probe__ 前缀的包，不碰真实记忆）。三种结果：

结果含义
A_OK现实现直接可用
A_NEEDS_SPLIT基线需分片（约 220 行工作量）
A_BLOCKED_BY_SERVER需服务端放行，或改走对象存储

4.2　B3 升级驱动器故意未实现

lib/team-upgrade-driver.js 的 upgradeLocal / verify 是 fail-closed 的：会明确失败，而不是假装成功。这不是 bug，是设计——但需要有人把它实现完。

4.3　目录体积

artifacts/ 被 git 追踪约 1.16 GB（工作区实体 6.7 GB）。建议浅克隆：

git clone --depth=1 https://github.com/Aik358/dsh-auto-memory.git

git clone --depth=1 https://github.com/Aik358/dsh-auto-memory.git
cd dsh-auto-memory

已知：issue207-processes、sidecar-watchdog、issue384-387-external-import、fullpage-negative、v4-h3-d-memory-usage 在高并发下有资源竞争型假红，单跑会绿。

5.2　功能正确性（label: preview function）

#验什么怎么看对不对
F1事件是否真的被创建调 memory_event(action=create)，看 handoff/event-store.json 里有没有 evt_
F2检查点是否 append-only连 append 两次，第二次不应覆盖第一次
F3四段是否跟随更新append 后看事件头 sections 有没有变
F4白板是否由事件渲染改事件后 PLAN.md 应自己变（而不是你手写）
F5日志/反思是否不进事件写 memory_log 后事件库里不该多出对应事件
F6欢迎向导 10 步是否都可达设置里重开向导，逐步点
F7设置页 v4 分区应有「白板形态（事件投影）」条目

5.3　代码运行正确性（label: preview bug report）

#查什么怎么查
C1未捕获异常开 DevTools，看 Console 有无 ReferenceError / TypeError
C2前端能否加载node tests/smoke/smoke-test-client-loadable.mjs（真执行 factory）
C3竞态两个会话同时写同一事件，看有没有丢更新
C4事务回滚记忆变更中途失败，旧数据是否完整
C5断言质量抽查 tests/smoke/，找「只断言源码含某字符串」的假测试

6　最可能出问题的地方（作者自评）

按风险排序，不是按代码量：

  1. lib/index.js（+25,336 / −21,232） —— 单文件 1.37 MB，改动最大。任何跨模块口径不一致都藏在这里。
  2. 事件与日志的边界 —— 「什么该进事件、什么不该」全靠模型判断，模型判错就会污染事件库。
  3. 白板渲染回写环 —— 曾出现过「白板全文被写成检查点 → 渲染器又读回 → 闭环膨胀」。
  4. 同步的 kind 白名单 —— 曾出现「applier 已注册但被 requestKinds 过滤掉」的半修。
  5. 前端样式变量 —— 曾出现「编造了不存在的 upBtnStyle → ReferenceError → React 整棵树崩 → 插件闪退」。
