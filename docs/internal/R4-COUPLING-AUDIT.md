## 一、判定（结论先行）

### 判定：**两者都有，但性质与严重度完全不同 —— A 是「观感层」，B 是「结构层」，另有一条独立的技术缺陷 C。**

用户那句「把**所有的功能都耦合在了一起**」**不是**「app 里功能互相牵连、改一个坏一个」的意思 —— 在这一点上我可以给出**反证级的证据**：v2 **没有**任何单向/双向的**功能性**耦合。真正的问题是别的：

| 解读 | 判定 | 一句话证据 |
|---|---|---|
| **A · 信息架构耦合** | **成立（真）** | **不是**「层级没做」——L1/L2 两级导航做得很干净（22 屏 ↔ 22 页签**完全双射**，零孤岛零悬空）。真问题是**屏内**：**22 屏全部只有一层扁平内容块**（`<section>` = 0、`h3` = 0、`h4` = 0），`.sec`/`.rule-h` 只是**视觉标题、不产生分组容器**。**最硬的一条证据是回归**：v1 **已经实现**的「分组 + 高级项折叠 + 实时隐藏计数」渐进披露机制（4 个 `.sgroup` 分组 + `expand-all` 全展开按钮 + `#ctl-visible`/`#ctl-hidden` 实时计数），**v2 把 markup 与 JS 100% 丢掉、只留下 6 段 CSS**（详见 A12）。契约 `UI-CONTRACT:127` 明确要求「首屏控件 80 → 约 15」的正是这个手法。 |
| **B · 技术结构耦合** | **成立（真），但基本是既定取舍的必然代价，不是可低成本推翻的缺陷** | 单个 IIFE、**2956 行 JS 里 0 个模块边界**（`require`/`export` **= 0**）、状态只有 `{l1,screen,theme}` 三个键——但**载荷不在 `state`，在 29 个顶层数据常量里**（`CARDS`/`LANES`/`HITS`/`CAL`…）；一个 **228 行、41 分支**的全局 click 代理（`v2:3289-3516`）**统一调度全部 22 屏的动作**。 |
| **C · 全局代理定址缺陷（独立于 A/B）** | **成立（真），已渲染态复现** | 「单一开关不得顺带改变其他功能」是用户**硬性规则**，v2 **实测违反**：`autoContinueEnabled` 开关在 `water` 与 `prefs` **各存在一个**，点击 `prefs` 那个，**标签却在 `water` 屏被改写**（`v2:3306` 用 `$('.js-sw-state[data-for=KEY]')` 取全文档**第一个**匹配）。 |

### 用户批评的归因（按证据强度排序）

1. **「所有功能都被耦合在一起」最贴近的技术表述是**：**「22 屏 × 平均 12 个控件，全部平铺在同一层」** —— 这不是「功能耦合」的字面义，但完全能解释用户为何用这个词：**当一屏里所有东西都同级并列时，用户分不清哪块和哪块是一组的，观感上就是「一堆功能被绑在一起」**。
2. **用户的批评是「像素的」，不是「架构的」。** 两条**独立**的证据方向，指向同一个位置：
   - **① 批评对象的物理位置**：用户第一句是「前端甲方觉得感觉有点杂乱，看着晕晕的」—— 一个对着**渲染结果**说话的人，看到的是**屏内密度**，不是 IIFE 的数量。
   - **② v2 恰好在「屏内」这一层发生了回归**：v2 的**技术结构**确实比 v1 更集中（JS 占比 81.4%、15 处监听器、228 行全局代理；v1 为 14 处监听器、零 `SCREENS` 注册表、零全局分派表），**但技术集中不会让甲方「晕」** —— 它没有可见后果。真正让甲方晕的**屏内降噪机制**，恰恰是 **v1 有、v2 丢掉的**（A12：分组 markup 4 → 0、实时可见/隐藏计数 2 → 0、全部展开 3 → 0）。
   ⇒ **甲方的批评、与「v2 丢了 v1 的降噪」这两件事指向同一处：屏内，而不是架构。**
3. **但 B 也不是无关的**：B 直接**制造**了 3 个用户可见的缺陷（C 是其中之一）。所以正确的表述是：**A 是病，B 是让这个病难以治好、并且自己也在制造新症状的体质。**
