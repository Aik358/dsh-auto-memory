# dsh-auto-memory 组合包拆分 · 源码级可行性研究报告

> 出具日期：2026-10-08 · 基线版本：**v3.2.12**（已发布，npm latest = 3.2.12，GitHub main = tag = `448e49f`）
> 报告性质：**只读测绘 + 方案论证**。本轮**未改动任何代码本体**（无 `lib/`、`skins/`、`package.json` 变更）。
> 全部数字均为本机实测可复算，取证脚本见 `.diag-split/`。

---

## 0. 结论先行（TL;DR）

| 问题 | 结论 |
|---|---|
| **技术上可行吗？** | **可行**。宿主的组合机制（`dsh.bundle.patch` + `config.plugin` + 子路径 `exports`）已在 `@linxin666/dsh-web-all` 上得到**生产验证**，本仓可原样套用。 |
| **该按什么维度拆？** | **按「宿主进程半面 / 浏览器半面」拆是第一刀**（零语义风险、收益最大）；**按功能域拆第二刀**（收益中等、需先做「引擎解耦」前置工程）。 |
| **最大的障碍是什么？** | **不是打包机制，而是 `lib/index.js` 的巨型单类**：`MemoryEngine` **一个类 10,852 行 / 261 个方法**，`ExternalMemory` **5,467 行**。两者合计占 `index.js` 的 **88%**。这是**必须先做的前置重构**，否则拆包只会把「大文件」变成「大文件 + 跨包循环依赖」。 |
| **建议的落地路径** | **三阶段**：①先拆「半面」（低风险、可立即做）→ ②再拆「纯叶子模块」成内部包（低风险）→ ③最后才动 `MemoryEngine`（高风险、单独立项）。 |
| **要警惕的最大陷阱** | **`cordis.patch.yml` 的 `insert` 是「插入一行」，不是「替换」**。同一个包被安装两次会得到**两个 id 相同的行** ⇒ 插件重复注册（本仓历史上 `shell.overlay` 三注入即此类问题的近亲）。搬迁时必须保证**旧行被移除**。 |

## 1. 现状测绘（全部实测）

### 1.1 代码体量

| 维度 | 实测值 |
|---|---|
| `lib/` 文件数 | **110** 个 `.js`（另有 `.bak`/`.tmp` 残留 382 个） |
| `lib/` 源码行数 | **68,097** 行 |
| `lib/` 体积 | **4,925 KB**（源码）／但目录达 **268.7 MB**（含 218.9 MB `client.js.bak-*` 残留） |
| **`lib/index.js`** | **18,525 行 / 1,227 KB**（占 `lib/` 行数 **27.2%**） |
| **`lib/client.js`** | **18,857 行 / 2,133 KB**（生成产物，源在 `skins/iter5/`） |
| 两者合计 | **37,382 行 = `lib/` 的 54.9%** |
| `python/` | **27,714 文件 / 12,478 MB**，其中 **`python/bench/` = 12,477.8 MB（27,697 文件）** |

> **发现 1（可立即收益）**：`lib/` 里躺着 **382 个 `.bak`/`.tmp`/多版本残留 = 218.9 MB**。
> `package.json` 的 `files` 已用 `!**/*.bak` / `!**/*.bak-*` / `!lib/*.*.*` 三重排除 ⇒ **发布包不受影响**（实测发布包 24.7 MB）。
> 但这 218.9 MB **留在开发树里**，且 `release.mjs` 每次构建都要遍历它们（实测日志：`lib/ 排除残留 407 个`）。**清理是零风险的独立收益项。**

### 1.2 模块依赖图

| 指标 | 实测值 |
|---|---|
| 节点（模块） | **110** |
| 边（import 关系） | **158** |
| **零出边的叶子模块** | **68 个**（占 61.8%） |
| 被依赖最多的模块 | `dsh-home.js`(7)、`context-bridge.js`(5)、`datadir.js`(5)、`file-boundary.js`(5)、`m4-corpus.js`(5)、`shadow-retrieval.js`(5) |
| 出边最多的模块 | **`index.js` = 78 条**（编排层），次之 `context-host.js`(9)、`activation-host.js`(7) |

**判读**：依赖图是**健康的星形**——`index.js` 作为唯一编排枢纽向外引 78 个模块，而这些模块**绝大多数互不依赖**（68 个零出边）。
⇒ **这是拆分友好的结构**：叶子模块天然可独立成包。

### 1.3 `index.js` 的真实结构（关键发现）

`index.js` **不是**「一堆函数的集合」，而是**四个类 + 少量工具函数**：

| 类 | 行范围 | 行数 | 方法数 |
|---|---|---|---|
| `ObserverRing` | L1782 → L1974 | 192 | 4 |
| `SessionRuntimeStore` | L1974 → L2206 | 232 | 8 |
| **`MemoryEngine`** | **L2206 → L13058** | **10,852** | **261** |
| **`ExternalMemory`** | **L13058 → L18525** | **5,467** | 13 |

> **发现 2（最重要）**：`MemoryEngine` **单类 10,852 行、261 个方法**，占 `index.js` 的 **58.6%**。
> 这解释了为什么「按行号切分」的直觉是错的：`index.js` 的 **L3000–L12000（9,000 行）** 抽样后**全是 `this.` 方法体**，中间**只有 1 个顶层声明**。
> ⇒ **这个类的存在本身就是「臃肿」的真正来源**，与「包太大」是**两个独立问题**。

**超长方法（拆分难点）**：`recall` **408 行**、`checkWaterLevel` 282 行、`hostAutoContinue` 281 行、`renderMemoryDynamic` 277 行、`consolidateTurn` 261 行、`ensureWorkbench` 245 行。

> **判读**：195 个「未归类」方法说明**方法命名没有统一域前缀** ⇒ **无法靠命名机械切分**，必须**按「它操作哪些成员状态」来切**。`recall` 单方法 408 行，本身就跨了「检索 + 排序 + 注入组装」多个域。

### 1.5 对外能力面

- **19 个工具**（`defineTool`）：`memory_*` **15 个** + `calendar_*` **4 个**
- **宿主注册口**：`ctx.section` ×3、`ctx.context` ×6、`ctx.effect` ×2、`setInterval` ×5、`ctx.on` ×9
- **`ctx.*` 依赖面**：`get`(14)、`on`(9)、`systemPrompt`(6)、`remote`(4)、`tools`(3)、`effect`(3)、`subagents`(2)、`directoryPicker`(2)、`webServer`(2)、`tokenMeter`/`agents`/`policy`/`head`/`sessions` 各 1

> **发现 3**：本插件**没有任何 `ctx.services` 共享容器使用（0 处）**，也**没有模块级单例缓存**。
> ⇒ 跨包共享状态**很少**，这是拆包的**有利条件**。

### 1.6 与 `@linxin666/dsh-web-all`（用户截图那套）的结构对照

| 维度 | `dsh-web-all`（对照组） | `dsh-auto-memory`（本仓） |
|---|---|---|
| 形态 | **1 个聚合包 + 22 个子包** | 1 个单包 |
| 聚合包 `lib/index.js` | **1,208 行**（转发 shell） | 18,525 行（全部逻辑） |
| 子包体积 | 单个 30–300 KB | — |
| `exports` 子路径 | **24 个**（`.settings` `./task-board` …）**全部指向同一个 `./lib/shells/shell.js`** | 4 个（`.` `./client` `./package.json` `./locale/*`） |
| patch 行数 | **24 行**（每个 family 一行，各自带 `config.plugin`） | 1 行 |
| 插件面板显示 | **每条 family 一行独立条目**（用户截图里 20 个组件） | 1 行 |

**组合机制（实测原文）**：

```yaml
# dsh-web-all/cordis.patch.yml（由 scripts/aggregate.mjs 自动生成）
- insert:
    - id: web-ui-task-board                      # ← 面板上这一行的 id
      name: '@linxin666/dsh-web-all/task-board'  # ← 走聚合包的**子路径 exports**
      config:
        plugin: '@linxin666/dsh-client-ui-task-board'   # ← 真正的子包
```

```json
// package.json exports：24 个子路径**全部指向同一个 shell.js**
"./task-board": "./lib/shells/shell.js",
"./ssh":        "./lib/shells/shell.js",
```

> **发现 4（机制核心）**：聚合包**不在自己源码里 import 子包**（`lib/index.js` 里 `require`/`createRequire` 均为 **0 次**）。
> 它靠**两个间接层**转发：
> ① `config.plugin` 让宿主去加载真正的子包；
> ② `exports` 子路径**全部指向同一个 `shell.js`**，由 `shell.js` 在运行时按 `config.plugin` 动态 `await import()`（实测 `import(` 命中 1 次、`await import` 命中 1 次）。
> ⇒ **这意味着：拆包不需要子包之间有编译期依赖，「组合」完全由 patch 行 + 运行时动态加载完成。** 这对本仓是**重大利好**。

### 1.7 最大陷阱（实测确认）

`cordis.patch.yml` 只有 `insert:` 一个动作（本仓与对照组**都只有 insert**，无 `remove`）。

⇒ **搬迁某功能到子包时若只「加新行」而不「删旧行」，宿主会加载两次**：同一份逻辑注册两个 id 不同的插件行，工具/路由/注入面**双份注册**。
> 本仓已有**同类事故的近亲**：`shell.overlay` 三次注入（三个不同 id、order 5/6/7）——那次是**设计如此**（宿主按条目独立错误边界），但**拆包场景下是缺陷**。
> **判定**：拆包必须**成对改动** patch 行（删旧 + 加新），且**必须有守卫断言**（见 §4 验收）。

## 2. 可行性判定（按四个维度）

### 2.1 技术可行性：**成立**

| 前提 | 实测状态 |
|---|---|
| 宿主支持多包组合 | ✅ `dsh-web-all` 22 子包生产运行中 |
| 每一行可独立显示 / 独立开关 | ✅ 截图实测：每 family 一行、各带独立开关与状态点 |
| 子包可独立发版 | ✅ 子包有自己的 `package.json` / `version` / `cordis.patch.yml` |
| 不需要编译期互相 import | ✅ 靠 `config.plugin` + 子路径 exports + 运行时 `import()` |
| 本仓依赖结构是否友好 | ✅ 110 节点 / 158 边，**68 个零出边叶子**，星形拓扑 |

### 2.2 工程可行性：**成立，但有前置条件**

**必须前置的工程**：把 `MemoryEngine`（10,852 行 / 261 方法）**先按状态归属做内部解耦**。
理由（实测支撑）：
- 261 个方法里 **195 个无域前缀** ⇒ 无法机械切分；
- `recall` 单个方法 **408 行**，跨「检索 + 排序 + 组装注入」；
- 若直接把这些方法**整块搬到别的包**，会产生**双向依赖**（A 包的方法要读 B 包的私有字段）——**这是拆包事故的经典形态**。

**判据**：只有当 `MemoryEngine` 的**成员状态可被清晰分组**（例如「runtime 表 / 配置 / 注入缓存 / 白板句柄」各成一组、组间无交叉写），才可安全拆分。

### 2.3 风险：**中等偏低，且集中在第三步**

| 风险 | 等级 | 缓解 |
|---|---|---|
| patch 行重复插入 ⇒ 双份注册 | **高** | 删旧 + 加新**成对**，配守卫断言 |
| `MemoryEngine` 拆分引入跨包私有字段访问 | **高** | 前置解耦；**本阶段不做** |
| 配置键迁移（`~/.dsh/...` 路径不变即可零迁移） | 中 | 保持 `resolveDshHomePre()` 口径不变 |
| 用户升级路径（老包 → 新组合包） | 中 | 保留 `@a9i5k4/dsh-auto-memory` 作为「全功能聚合包」向后兼容 |
| 生成器 `build-iter5-skin.mjs` 的 R2 闸门 | 低 | 前端半面拆分时需同步改生成器路径 |
| 回归套件 321 支的路径假设 | 中 | 拆包会大面积改路径 ⇒ **必须一次性改全**（见 §4） |

### 2.4 收益：**明确，但需要分层看**

| 收益 | 说明 |
|---|---|
| **可单独开关** | 用户能只装「记忆检索」不装「白板看板」，**这是用户诉求的正面回应** |
| **可单独发版** | 前端改版不必带上 12.5 GB 的 python 侧 |
| **降低单包体积** | 当前 24.7 MB 包（243 文件）可切到多包，**首次安装更快** |
| **故障隔离** | 一个子包崩溃不连坐（宿主按条目独立错误边界） |
| **但**：**不会自动减少总代码量** | 拆分是**结构治理**，不是**减重**。`python/bench` 12.5 GB 是**另一个独立问题**（它已在 `files` 里排除，不进包，但占开发树） |

## 3. 拆分方案（三阶段，按风险递增排序）

### 阶段一：**半面拆分**（推荐立即做）

**依据**：本仓天然是「宿主进程半面 + 浏览器半面」双面结构（`package.json` 已声明 `main: lib/index.js` + `dsh.client` 指向 `./client`）。

| 新包 | 内容 | 依据 |
|---|---|---|
| `@a9i5k4/dam-core` | `lib/index.js` 宿主半面（引擎、路由、工具、注入） | `main` |
| `@a9i5k4/dam-ui` | `lib/client.js` 浏览器半面（皮肤、面板、看板 UI） | `dsh.client` |

**为什么这一刀最安全**：两面**已经通过 HTTP 路由通信**（`/api/dsh-auto-memory/*`），**没有共享内存**（实测 `ctx.services` 0 处）⇒ 拆开**不引入新的耦合面**。

**代价**：前端生成器 `tools/build-iter5-skin.mjs` 的输出路径需同步改；回归套件中引用 `lib/client.js` 的断言需改路径。

### 阶段二：**叶子模块包化**（低风险，可与阶段一并行）

**依据**：**68 个零出边叶子模块**，且高被引的叶子本身就自包含：

| 候选子包 | 内容 | 叶子证据 |
|---|---|---|
| `@a9i5k4/dam-boundary` | `file-boundary.js` + `datadir.js` + `dsh-home.js` + `fs-retry.js` | 被引 5/5/7/3，**零出边** |
| `@a9i5k4/dam-config` | `config-io.js` + `config-lock.js` + `shared-state-lock.js` | 零出边、被引 2/2/4 |
| `@a9i5k4/dam-semantic` | `semantic-js.js` + `shadow-retrieval.js`(39 KB) + `python-sidecar-client.js` | 零出边、被引 5 |
| `@a9i5k4/dam-whiteboard` | `wb-sidecar.js`(65 KB) + `wb-contract.js` + `board-mode.js` | 零出边 |
| `@a9i5k4/dam-team` | `team-identity.js` + `team-inject.js` + `team-transport*.js` + `team-outbox.js` | 零出边 |
| `@a9i5k4/dam-integrity` | `degrade.js`(18 KB) + `evidence-store.js` + `intent-clean-safe.js` | 零出边、被引 4 |

**判据**：每个候选包的模块**出边必须为 0**（实测已满足）；若某模块出边 > 0，说明它引了别的域 ⇒ **不放进本阶段**。

### 阶段三：**引擎解耦 + 功能域分包**（高风险，**建议单独立项**）

**前置**：先完成 `MemoryEngine` 的**状态分组**（把 261 个方法的 `this.*` 访问面做成表，按「写同一组成员」聚类），产出**内存耦合矩阵**后再决定边界。

**候选域**（按 §1.4 语义分布，仅列证据充分的）：

| 候选 | 方法数 | 依据 |
|---|---|---|
| 白板/看板 | 8 + `wb-sidecar.js` | 已有独立模块 + 独立 UI 入口 |
| 技能/procedure | 2 + `procedure-store.js`(915 行) + `procedure-*.js` | 已有完整模块族 |
| 团队/team | 多个 transport 模块 | 已是模块族 |
| 日历 | 3 + 4 个工具 | **域最干净**（`calendar_*` 4 工具自成一体），**建议作为阶段三的试点** |
| 反思/固化 | 5 | 与定时任务强耦合，延后 |

> **建议**：阶段三**先拿「日历」开刀**——它 4 个工具、3 个方法、无跨域写，是**最小可验证切片**；跑通后再复制模式。

## 4. 验收判据（每条都必须能失败）

| # | 判据 | 负路径（必须变红） |
|---|---|---|
| V1 | 安装组合包后，插件面板显示**N 行独立条目**（N = 子包数） | 删一行 patch ⇒ 少一行 |

| V6 | 19 个工具的**名称与 schema 逐字节不变** | 改一字节 ⇒ 断言红 |

| V8 | 从**老版单包**升级到组合包后，功能面**零丢失** | 漏搬一个模块 ⇒ 断言红 |

## 5. 明确不建议做的事

1. **不要按行号机械切分 `index.js`** —— 它是四个类，中间 9,000 行全在 `MemoryEngine` 类体内，按行号切会**切断方法**。
2. **不要在没有前置解耦时搬 `MemoryEngine` 的方法** —— 261 方法共享 `this` 私有状态，跨包访问私有字段会形成双向依赖。
3. **不要用「加新行」代替「删旧行」** —— 会导致双份注册（§1.7）。
4. **不要为了「显得拆了」而拆** —— 如果只拆出不常用的模块，收益不足以覆盖路径改动的回归成本。
5. **不要顺手改 `python/bench`** —— 它是 12.5 GB 的开发树占用，**与拆包无关**，且已在 `files` 排除，不进发布包。

## 6. 建议的下一步（需要用户拍板）

| 选项 | 内容 | 工作量 | 风险 |
|---|---|---|---|
| **A** | 只做**阶段一**（半面拆分） | 中 | 低 |
| **B** | **阶段一 + 阶段二**（半面 + 叶子包化） | 中大 | 低-中 |
| **C** | A + B + **阶段三试点**（先拆「日历」域） | 大 | 中 |
| **D** | 暂不拆包，只做**零风险清理**（`lib/` 218.9 MB 残留 + `python/bench` 处置） | 小 | 极低 |

**推荐：先 D 后 B**。
理由：D 是**零风险且立即见效**（218.9 MB 残留 + 12.5 GB bench 占位）；B 在 D 清干净后，路径改动的影响面更小、回归基线更清晰。
