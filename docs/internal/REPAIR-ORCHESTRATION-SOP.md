# 大型修复批编排作业流程（SOP）——"编排者 + 串行子代理 + 亲自闸门 + 小回执"

> **文档性质**：已验证的固化作业流程，可直接改写为 skill（本文件按 skill 可提取的步骤/模板/清单组织）。
> **验证案例**：2026-10-02 审计修复线（40+ issue，S1–S6 七个子代理，全部闸门复跑通过，HEAD 4ec61d8）。
> **来源教训**：融合单批因上下文跑道耗尽中途回退（执行 agent 宿主内每轮注入 ~15k token）；子代理隔离 + 块级闸门是结构性解，压缩只当安全网。

---

## 1. 适用场景与角色

**适用**：任何"方案文档已就绪、改动面 ≥10 文件或涉及多批次"的修复/重构/审计落地批。
**不适用**：单点小修（直接做）；需要跨工具异构团队的场景（用外部编排工具）。

| 角色 | 职责 | 禁止 |
|---|---|---|
| **派发者**（人） | 出方案文档与决策项清单、指定块划分、最终裁决"待复核项" | — |
| **编排 Agent**（主） | 派活、亲自跑闸门、收回执、更新交接账本 | **亲自改产品代码**；替子代理读大 diff/跑长测试 |
| **执行子代理** | 一次只做一个任务块，自带完整上下文 | 并行接活；越权拍板（不确定的事一律写入回执"待复核项"） |
| **复核者** | 裁决待复核项 → 抽验关键落点 → 复跑三件套 → 核对排除项 | 采信自报不复跑 |

## 2. 流程总览

```
前置检查 → 块划分 → [派发子代理 Si → 子代理完成回小回执 → 编排者亲自闸门] ×N →
编排者汇总总回执（待复核项清单） → 复核者复核 → 收尾（issue 回复/关闭 → 发版三件套 → push 需示意）
```

## 3. 前置检查清单（编排者开工第一件事）

1. `git status` 确认干净；**批前已有未提交改动的文件必须先单独 commit**（教训：批前脏文件会被后续修复 commit 吸收，provenance 混合）。
2. 跑一次全量基线（`node tools/run-smoke.mjs`）并记录套件数/已知环境性红。
3. 读方案文档（唯一权威）+ 决策项清单（未拍板项写进每个子代理提示词的红线节）。
4. 建交接账本（`handoff/handoff-<时间戳>.md`）：任务状态/目标/重放清单。

## 4. 任务块划分原则

- **串行，无并行**：共享改动面（本项目 = lib/index.js、lib/client.js、skins/legacy/*.frozen）的块一律串行。
- **单块体量 ≤ 一个上下文窗口的诚实估量**（经验：每轮注入 ~15k + 工具输出，一块 ≈ 5-15 个修复项或一次中等重构；宁可多拆）。
- 块的边界优先按：模块域 > 批次优先级 > 文件交集。依赖者排前（如"基础设施模块（锁/键）"先于其消费者）。
- 每块必须有：明确的完成判据（哪些测试绿/哪些断言更新）+ 一个 commit。

## 5. 子代理提示词模板（通用头 + 任务块）

```
【执行子代理 · 通用头】
仓库：<路径>（<平台+shell>），分支 <分支>，接 HEAD <hash>（基线：全量 <N>/0）。允许 commit，禁止 push。
先读：<方案文档章节>；交接账本 <路径>（重放清单）。行号一律内容匹配（±2 漂移）。
本会话只做下面一个任务块，完成即停：阶段闸门（<生成器 --check 若涉产物> + 全量 smoke 全绿）→ commit（message 点名任务块）→ 更新交接账本 → 回小回执。
通用纪律：
- PR/上游已含的修复以 hunk 移植代替重写；EOL 按方案处理，禁止裸 apply；index 类大文件逐 hunk 核对 before 上下文。
- 改测试必须真阳性验证（旧断言注入故障必红 → 改 → 绿，证据入回执）。
- 生成器纪律：改生成块/注入区必须改源重建；[G2]/[R2] 停机区分「源变了没同步（硬停）」vs「已迁移过（replaceMigrated）」。
- 决策红线（未拍板不得实施）：<逐条列>。
- 不确定的事不自行拍板：记入回执「待复核项」节。

【任务块 <id>】
<目标 / 逐项修法（file:line 以内容匹配）/ 完成判据 / commit message 模板>
```

**子代理小回执格式**（强制）：

```
任务块 <id> 回执
- 逐项：<issue 号/F 号> → 结论 / 改动文件 / 验证证据
- 待复核项：所有不确定处与自行判断（无则写"无"）
- 排除项确认：红线清单逐条"未动"
- 闸门输出摘要：--check / smoke 计数
```

## 6. 编排者闸门清单（每块之间，亲自跑，不采信自报）

1. `git log -1`：commit 存在、message 与块匹配、未 push。
2. `node tools/build-iter5-skin.mjs --check --strict`（涉前端产物的块）。
3. `node --check lib/client.js`（涉前端块）。
4. `node tools/run-smoke.mjs` 全量，计数 ≥ 基线 + 本块预期新增，FAIL 0。
5. grep 抽验该块 1-2 个关键落点（修复必须在码，不是只在回执里）。
6. 任一红 → 停：失败证据写交接账本，报告派发者；**不得带病进下一块**。

## 7. 复核者流程（全部块完成后）

1. 裁决各块回执的"待复核项"（逐条给保留/回退/改法）。
2. 抽验关键 hunks（复核者自选 3-5 个最高风险落点 grep/sed 实看）。
3. 复跑三件套：全量 smoke、`--check --strict`、`release --dry-run`（实测 staging 内容：资源在位/杂物不在）。
4. 核对排除项清单逐条未动。
5. 出总验收结论 + 剩余事项清单（真机抽验/回复 issue/push 示意/未拍板决策项）。

## 8. 收尾流程

1. **issue 回复/关闭**：逐项回复（结论 + commit + 一句话修法 + 验证）；修复的关闭，决策项挂状态评论保持开放；PR 逐 hunk 采纳的以"移植落地说明"关闭并致谢；脚本化操作必须幂等（评论带标记，已有则跳过）。
2. **发版三件套**（发版闸门会强制）：CHANGELOG 小节 → 应用内更新说明字典 → 界面指纹行，然后 `release.mjs <ver> --dry-run` 验 staging。
3. **push**：始终等派发者示意（commit 只入本地）。

## 9. 纪律红线速查（贯穿全程）

- hunk 移植优先于重写；`git apply` 处理 EOL，大文件逐 hunk 核对 before 上下文。
- 改测试必真阳性验证（红→绿证据入回执）。
- 决策红线（未拍板不动）逐块重申；不确定 → 回执"待复核项"，不自行拍板。
- 冻结哈希/计数锁重钉必须带归因注释 + "守卫语义不变"声明；计数锁常量改动必须全仓检索（守卫 + 文档点）。
- 真跑生成器/写产物的测试用临时目录整仓副本（并发假红防护）。
- 死代码裁决三问：全仓引用？是否规划接口？是否行为门禁？——三者有一即保留。
