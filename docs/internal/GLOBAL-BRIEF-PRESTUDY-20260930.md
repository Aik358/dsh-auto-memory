## 0. 需求三问（用户口径 · 2026-10-01 追加）

用户把这条需求表述为**三步走**，实施时必须逐条对上：

| # | 用户要求 | 本文档的对应设计 |
|---|---|---|
| ① | 提示「内容与之前修改过的有变动」，并**说明具体有哪些变动** | §4.2 简报行（headline 级）+ §4.3 **链接模式**（只报「哪里变了 + 绝对路径」） |

## 4. 设计方案：水位驱动的「全局简报」段

### 4.1 核心循环

```
每轮 renderMemoryDynamic 做「便宜检查」（只 stat，零内容读取）:
  对每个启用的源: stat 目标文件 / git rev-parse HEAD 的开销 vs 水位
  有任何新变化 ──→ 组装简报草稿（此时才读内容）→ 暂存 state.draft
                  ──→ 下一次 pushPart 注入草稿 → 注入真实发生后推进水位（原子落盘）
  无新变化 ──→ 零字节、零注入（段不出现）
```

**便宜检查的开销**：外部源 ~13 源 × stat；DSH 桶按 `workspaces-summary.json` 的已知桶列表 stat；git 一次 `rev-parse HEAD`（P1）。全部毫秒级、无 LLM、无网络（S9 纪律不破）。

### 4.2 源清单（P1 范围）

| 源 | 检测目标 | 简报内容（headline 级） | 水位 |
| --- | --- | --- | --- |
| A. DSH 其他工作区桶 | MEMORY.md / 近 5 天日志 / `handoff-*.md` 的 mtime | 「工作区 <名>：账本 ×1、日志 ×3 有更新 → 绝对路径」**不引内容** | 每文件 mtime |
| B. 其他 AI 工具记忆 | `ExternalMemory` 13 源的 md 文件 mtime | 「ZCode 记忆：N 个文件有更新 → 绝对路径」 | 每源最新 mtime |
| C. git 新提交（P1） | cwd 仓库 `git log --oneline -n 8 <lastSeenSha>..HEAD` | 短 SHA + subject + 相对时间，预算内截断 | lastSeen 短 SHA |

### 4.3 隐私与安全边界（承重设计，非可选）

- **链接模式，不灌内容**：A/B 类只报「哪里变了 + 绝对路径」，全文由模型用 read 按需取——与 external-memory 段现行纪律完全一致。理由是硬的：**其他工作区的记忆文件里可能存有凭据**（用户级 MEMORY.md 的既有惯例即如此），任何内容级摘录都可能把密钥带进另一个 agent 的 prompt。
- git subject 天然是 headline 级，但**提交前过一遍密钥模式过滤**（`ghp_` / `github_pat_` / `npm_` / `sk-` / `AKIA` 等命中即整行替换为 `[redacted]`），防止 commit message 里带密钥的场景。
- git 命令**只读**（log / rev-parse），`execFile` + timeout + 失败熔断（连续 N 次失败即静默停用本源，与 sidecar 看门狗同纪律）；无 `.git` ⇒ 静默跳过、零字节。

### 4.4 落点选择：新分区键（推荐） vs 欢迎槽拼接

| | 方案 A：新 PROMPT_SECTION 键 `global-brief`（推荐） | 方案 B：拼进 welcome-title/body 槽 |
| --- | --- | --- |
| 开关粒度 | 独立开关 + 独立预算（「一切皆开关」纪律的正统落点） | 无独立开关，跟暂离阈值绑定 |
| 触发 | 回归 + 新会话首轮（可分开配） | 只有暂离回归（新会话首轮覆盖不了） |
| 改动面 | `PROMPT_SECTION_KEYS_PRE_V1` +1（13→14）；client 镜像 `DEFAULT_PROMPT_LAYERS_CLIENT`（定义 `client.js L2375`）同步（**逐字一致纪律**）；设置页「注入分区」+1 开关（三面：经典档 `SettingsPage` `client.js L17046` / 变体生成块 / 冻结基线块）；守卫 | 几乎零新键，但欢迎段语义被污染（寒暄 + 简报混装） |
| 估行数 | 约 +60（键/镜像/设置页，另加 §5.2 文案） | 约 +10 |

**推荐 A**：B 省的行数会在「新会话首轮也想拿到简报」这个核心诉求上还回去，且混装违反「分区可关」的既有架构。判据（「内容/行为」段、关掉不破坏结构）完全满足。

### 4.5 缓存纪律分析（为什么不动前缀缓存）

动态快照走 `systemPrompt.context()` 以 user-role 追加在**历史尾部**，每轮本来就是新增后缀，不回写旧消息 ⇒ 前缀缓存天然不破。简报段只在这一轮的后缀里多几百字，且「无新变化就不出现」⇒ 静默期零增量。唯一要遵守的是**段内不放假稳定时间戳**（教训：秒级时间戳击穿前缀缓存的旧案）；简报内容只在真有新变化时变，天然合规。

### 4.6 一次性交付语义

- 水位文件 `~/.dsh/memory/global-brief.json`（config-io 原子写），结构 `{ version, sources: { <srcId>: { kind, lastMtime|lastSha, seenAt } }, draft? }`。
- **首见建基线**：水位缺失的源第一次只记录不注入——否则新装用户会被一次性灌进全部历史变化（直接判死刑的细节）。
- **交付后推进**：草稿注入发生（`pushPart` 真实带上）后才推进水位；预算裁剪导致没带上 ⇒ 草稿保留下一轮再试（at-least-once，宁可重复不可丢失；模型侧无感）。
- 崩溃安全：水位与草稿同一 JSON，原子写，写失败 fail-soft 留旧值（最多重复注入一次简报，无害）。

## 5. 触发与文案

### 5.1 触发语义（拍板点 ②）

- **暂离回归**：沿用 `awayMinutes`（回归第一轮注入）——用户原话的直接对应。
- **新会话首轮**：`agent/session-start` 后本会话第一次 `renderMemoryDynamic` 也注入——「切回 DSH 开始对话」常常是开新会话而非回归旧会话，只做回归会漏掉一半场景。
- 两处共用同一条「有无新变化」判定与同一份水位 ⇒ 没有变化时两处都静默。
- 无人值守：**保留注入但剥离寒暄**（与 welcome 相反）——无人值守任务恰恰更需要全局信息，简报是信息不是寒暄；这是与 welcome 剥离纪律的**有意分歧**，需拍板确认。

### 5.2 ★行为指令文案（2026-10-01 新增 · 对应用户三步走的 ②③）

初版只做「通知」，用户要求**显式指示先同步再推进**。建议文案（模板，`{brief}` 为 §4.2 的简报行）：

> 【其他 agent 有新动态】你不在的这段时间，下列位置发生了变化（只列位置，不含内容）：
> `{brief}`
> **请先同步这些变动再推进当前任务**：用 `read` 打开上面的路径确认新进展（必要时用 `memory_recall(scope='handoff')` 定位账本要点），把它们与当前任务合并考虑；**确认无误后**再继续你原本的工作。若上述变化与本任务无关，说明一句后直接推进即可。

**设计要点（三条硬要求）**：
1. **先同步**：句序必须是「read 确认 → 再推进」，不得只通知不指示；
2. **给退路**：末尾那句「无关则说明后直接推进」是必需的——否则每次无关变更都会让模型空转一轮；
3. **不引内容**：指令让模型**去 read**，prompt 里仍只有路径（守 §4.3 凭据纪律）。

**长度**：文案本体约 120 字，计入 `globalBriefChars` 预算（默认 1200）。

### 5.3 双触发下的去重

回归轮与新会话首轮可能连续发生（用户切回即开新会话）⇒ 以**水位**为准去重：第一次交付后水位推进，第二次自然静默。**不引入新的「已提示过」标记**（避免双份状态）。

## 7. 纪律与风险

1. **client 镜像逐字一致**：新增 `snapshotGlobalBriefTitle/Body` 须与 `DEFAULT_PROMPT_LAYERS_CLIENT`（`client.js L2375`）双侧同步（既有硬纪律，漂移 = 设置页显示与实际注入不符）。

3. **fail-soft**：任何源失败只静默跳过该源（diag 留痕），绝不阻塞注入主链；git 不可用/无仓库 = 源不存在。

5. **行号漂移**：本文 `L####` 基准为 2026-10-01。lib/ 改动后**必须重算**；复核时优先用锚点串（函数名/键名/配置键）。

## 9. ★拟合结论（2026-10-01 四轮拟合收敛 · 已拍板，取代 §8 的建议项）

> 用户通过记忆拟合流程逐条裁定。**以下为实施依据，与 §8 建议不一致处一律以本节为准。**

### 9.1 范围口径（★最重要的一条）

- **只盯「本工作区」**，不做跨工作区注入。理由（用户原话转述）：**「本工作区是一个项目，别的工作区是另一个项目。你不能把别的工作区另一个项目的内容嫁接到本工作区的这个项目上，容易造成漂移。」**
- 例外允许：其他 agent 的**日记 / 用户画像类记忆**可每天观察，且可**升格进长期记忆**（用户约束、用户画像一类）—— 即「跨项目通用事实」可收，**项目专属内容不跨区搬运**。
- 这一条**推翻了 §4.2 的「A 源 = DSH 其他工作区桶」**：A 源改为 **本工作区自己的记忆文件 + 项目文档**。

### 9.2 检测与豁免（★技术核心）

- **必须豁免 DSH 自己写的**（用户原话：「肯定只看别的 Agent 软件的变动啊，你 DeepSeek 自己写的肯定要豁免」）。
  - 否则每轮都会提醒自己刚写的白板/账本 ⇒ 疯狂误报。这是本功能**最大的失败风险点**。
  - 实现方向：写入点登记指纹/时间窗 + 检测时跳过；或仅判定「DSH 未运行期间」的变动。**两者取其一即可，优先选实现面小、误报可验证的那个。**
- **检测对象**：插件记忆文件（白板/账本/日志/笔记/MEMORY.md）**+ 项目文档**（docs/、README、交接文档等）。
  - **不含**全仓代码文件的变动（噪音过大）。
- **节流**：同一轮内只查一次；文件 stat 带缓存。

### 9.3 触发与文案

- **触发**：每次都检查，但**只在真有变化时才提醒**（推翻 §5.1 的「仅暂离回归 + 新会话首轮」）。
- **指令强度**：软指示 + 退路句（即 §5.2 文案，用户已确认）。
- **无人值守**：保留简报（与 §5.1 建议一致）。

### 9.4 团队（★推翻 §3.2 缺口 4 的措辞）

- **实测更正**：团队通道**上行已接线**（`index.js:12739` 真调 `_teamSync.start()` 心跳；路由/设置页齐备），但：
  - **下行无驱动**：`pullOnce` 全仓 **0 调用点**（仅 `team-pull.js L245` 作为导出返回）；
  - **outbox 无生产者**：`enqueue` 全仓仅 1 处 = 它自己的定义。
  - ⇒ 准确说法是「**通道已通，但没人在上面跑货**」，**不是「整个通道未接线」**（初版 §3.2 措辞需按此更正）。
- **裁定**：**本批一并补齐团队欠账**（用户原话：「把团队的欠账补上吧，然后一起做」）。
  - 团队维度要看的是**远端队友的白板/账本变动** ⇒ 依赖补完下行驱动 + 远端条目落盘。

### 9.5 设置面

- **新增独立一块**（用户裁定：这是比较独立的功能，不塞进「注入分区」或「自动化」）。
- 粒度：**四类各一个大开关 + 每类内部再细分**。
- 按既有硬纪律，**三款皮肤设置面全部同步**（经典档 + 变体生成块 + 冻结基线块），并过 `settings-parity` 守卫。

### 9.6 批次

- **一次做完**：豁免机制 + 本工作区简报 + 团队下行驱动（用户裁定）。
- 另需一并落地：**精简版注入路径补 diag**（用户要求，用于计量与实验 —— 当前精简版分支零 diag，导致无法量化触发频率）。

### 9.7 长期愿景（本期不实现，仅记录）

用户希望本插件未来演化为**「一个大插件里带多个可独立开关的小插件」**的模块化形态。本期先把功能落地，不做架构改造。
