## 二、内容硬约束（写错就是错）

### 2.1 定位口径（统一用这套词，不得自创）

- 产品名：**dsh-auto-memory**（`@a9i5k4/dsh-auto-memory`）
- 一句话：**主动联想记忆 + Astra 式上下文管理**——模型开口前就把该记的递到眼前；自动唤回 / 自动沉淀 / 技能固化；交接账本与白板让长会话跨窗口续命。
- 三个卖点层级（**团队版是本次新故事**）：
  1. **单人**：零提示唤回、三层自动沉淀、技能固化、水位感知
  2. **团队（新）**：成员身份 + 团队共享记忆 + 「失败与弯路」一等公民
  3. **企业交付（新）**：Google / 阿里云登录、审计追溯、阿里云优先多云兼容

### 2.2 ★ 三条必须写对的技术事实（写错会在客户面前出丑）

1. **登录由宿主提供，插件不自建账号体系。**
   依据：用户 2026-09-23 明确「0.1.7-alpha.2 就可以登录了」。
   ⇒ 表述口径：**「复用 DSH 宿主已有身份（DeepSeek 账号 / Google / 阿里云），插件只做成员映射与审计，本地只留接口」**。
   ⚠️ **不得**写成「我们自建了一套 SSO」——那不是事实。

2. **开源不加密，加密交给客户。**
   依据：用户 2026-09-23 明确「开源系统不需要加密，客户可以自己加密，本地只留接口就行」。
   ⇒ 表述口径：**「记忆数据本地明文存储（开源可审计），企业如需加密由客户自行在存储层加密；我们预留加解密接口」**。
   ⚠️ **不得**写成「我们做了端到端加密」。
   ⚠️ 但**必须**向客户披露「当前为明文」，这是诚实底线。

3. **审计能力的真实边界**（防止过度承诺）：
   提交单据保证的是**「写入路径上的 actor 不可伪造」**，**不是磁盘防篡改**——任何能读到文件的进程都能绕过。
   ⇒ 表述口径：**「审计级追溯（谁写了什么、什么时候），非防篡改级」**。

### 2.3 「人无我有」四条差异化（proposal 的论证骨架）

1. **记忆三态治理**：`current / superseded / retracted` —— 过时结论**返回但标记**，不静默丢
2. **防记忆劫持**：无模型参与的 Tier-0 写入结构性不可能（大厂靠模型对齐，我们只能在数据层解）
3. **「失败与弯路」是一等公民**：四段账本 + `deadend` 泳道（业界把失败当负资产，我们让它进入看板）
4. **可信度可量化**：证据公开、可复核

> **基石判断（写进 proposal 但不点名竞品）**：大厂的企业检索产品基本是**只读检索系统**——人写记忆、AI 只读，所以「过时/冲突」在它们的数据模型里不存在。我们处理的是**会写、会错、会改**的记忆。

### 3.2 字体

- 标题：`'Space Grotesk'`（fallback `'Manrope', system-ui`）
- 正文：`'Manrope'`
- 代码/数字：`'JetBrains Mono'`

### 3.3 硬性技术约束

| 约束 | 原因 |
|---|---|
| **单文件 HTML**，内联 `<style>` 与 `<script>` | 客户双击即开，无需服务器 |
| **零外部依赖**（不引 CDN 字体/JS 库） | 客户内网可能不通外网；字体用 `system-ui`/`ui-monospace` 兜底 |
| 中文优先，`lang="zh-CN"` | 读者是中方客户 |
| 响应式（≥1280 主视口，1024 可用） | 演示常在笔记本/投屏 |
| **无真实后端**：交互全部用内置假数据 | demo 不得发网络请求（避免内网报错、避免泄露真实数据） |

## 四、UI demo 的信息架构（**必须按这个做**，这是本轮诊断的成果）

### 4.1 顶层：4 个一级入口（L2 每入口 ≤4 项，硬约束）

| L1 | 含义 | 收纳原「13 页签」中的 |
|---|---|---|
| **今天** | 我这一轮要用的 | `overview` / `logs` / `reflections` |
| **项目** | 这个项目沉淀了什么 | `notes`(项目笔记) / `plan`(白板) / `hub`(知识库) |
| **团队** | 全团队共享什么 ★新 | 团队记忆 / 成员 / 审计 / 冲突 |
| **检索** | 我要找东西 | `search` / `stats` / `connect` / `calendar` / `workspaces` |

- 原 `storage` 降入**设置**（它是配置不是内容）
- **13 个页签必须全部有归属，零功能丢失**（proposal 里要能回答「我的功能去哪了」）

### 4.2 三个作用域必须视觉可分（诊断 R4 的正解）

每一屏都要能看出「这是**我的** / **这个项目的** / **全团队的**」——用色 + 徽标 + 分区标题三重表达，不得只靠文字。

### 4.3 设置页：9 分区 → **4 组**

| 组 | 收纳原 9 分区 |
|---|---|
| **引擎** | `engine` / `window` / `capacity` |
| **内容** | `skills` / `handoff` / `store` |
| **偏好** | `look` / `auto` |
| **关于** | `about`（+ 诊断，默认折叠） |

**关键手法（demo 里要体现）**：`field()` 加 `{advanced:true}` 默认折叠 ⇒ **首屏控件 80 → 约 15**。

### 4.4 交互原语：收敛为 **3 套**（现有 9 套并存）

1. **导航**：左侧一级 + 顶部二级（**真页签，不是滚动**）
2. **详情**：右侧抽屉（统一一个）
3. **确认**：居中模态（统一一个）

⚠️ **不得**引入「更多」折叠菜单（诊断列为必须拒绝的诱惑之一）。

### 4.5 UI demo 必须覆盖的屏幕（至少 8 屏）

1. 今天（首页，含唤回卡片 + 水位）
2. 项目 · 白板（看板泳道，含 **`失败与弯路`** 泳道）
3. 项目 · 交接账本（四段式）
4. **团队 · 团队记忆**（新，含「我的/项目的/团队的」三分区）
5. **团队 · 成员与登录**（新，展示「复用 DSH 宿主身份」的登录入口）
6. **团队 · 审计与追溯**（新，actor 时间线）
7. 检索（搜索 + 统计）
8. 设置（4 组，advanced 折叠已生效）

## 五、proposal 的结构（一页式 HTML）

| 节 | 内容 | 关键要求 |
|---|---|---|
| Hero | 一句话价值 + 版本 v3.1.7 | 不堆功能 |
| 现状诊断 | **承认客户说的「杂乱/晕」**，给出根因（**没有层级**，非信息太多） | 诚实 → 建立信任；**这是本 proposal 的杀手锏** |
| 我们要做什么 | 三块：团队记忆 / 企业登录 / 前端重构 | 每块给「客户得到什么」 |
| 怎么做 | 7 批迁移顺序（A 结构 → B 导航 → **C 设置页（契约变更）** → D 引擎块 → E token → F 降噪 → G 团队） | 让客户看到**有序** |
| 什么时候能看到 | **4 个里程碑**（demo 已就绪 → S1 单人登录 → S3 hub 分片 → S4 权威服务端） | demo 已就绪是**已完成项**，要显眼 |
| 我们凭什么 | 人无我有四条 + 177 项回归 + 开源可审计 | 引用具体数字 |
| 诚实边界 | 明文存储 / 审计级非防篡改 / 阿里云标准版才支持标准应用且日志 7 天 | **主动写缺点**，反而加分 |
| 下一步 | 3 个待确认问题 | 让客户有参与感 |

**语气**：专业、克制、有底气。**不吹**、不写「行业领先/革命性」。用数字和事实说话。
