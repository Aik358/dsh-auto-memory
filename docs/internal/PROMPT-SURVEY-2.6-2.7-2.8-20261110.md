# 五、⭐ 借鉴 prototype 的「模块化 / 系统化 / API 化」思路（用户明确要求）


**注意边界**：`prototypes/sidecar-store/` 管的是 `handoff/index.json`（白板索引），**不是**事件库；
原型代码里 `event-store` / `eventStore` / `resolveActiveEvent` / `appendCheckpoint` **全部 0 次命中**。
⇒ **不要试图把原型代码搬过来**，但**要借鉴它的架构思路**。

## 5.1 可借鉴的三个思路（请逐条评估「能不能用、怎么用」）


**① 模块化**：原型把「存储 / 状态 / 编解码 / 适配器」拆成 5 个文件，每个只做一件事；
   而现在的 WAL 逻辑挤在 `event-write.js` + `index.js` 两处巨型文件里（866 行 / 29,263 行）。
   ⇒ 评估：2.6-2.8 的改动是否值得抽出独立模块？抽哪几块？**不抽的理由是什么？**

**② 系统化**：原型有「一次事务可替换一个或多个 source」「同 ID 更新保留原位置」「删除保留墓碑」这类**成文协议**；
   而 WAL 的协议散在注释里。
   ⇒ 评估：2.6-2.8 需要先成文哪些协议？（如「什么算可预期失败」「降级后如何回读」）

**③ API 化**：原型对外只暴露 `replaceSources` / `loadView` / `findByTag` 等少量语义化 API，**调用方不碰磁盘格式**；
   而现在的写入口是「各调用方自己拼检查点字段再写」。
   ⇒ 评估：能否给事件写入口定义一层 API（如 `appendEventNote({kind, content, eventId?})`）？
     调用方不再关心 WAL 分几阶段、字段叫什么。**这是 2.6/2.7/2.8 的共同解法吗？**

## 5.2 明确不可借用（写上以免误导后面的人）


| 原型有的 | 为什么这里用不上 |
|---|---|
| `expectedState` CAS | 2.6 要解决「归属判错」，不是「并发写冲突」 |
