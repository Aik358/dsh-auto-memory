## §0 总判定：任务书的诊断方向对，但事实基础有三处偏了

用户的**设计直觉是完全正确的** —— 用「拒绝 + 回执指导」替代「长提示词」。但任务书基于的事实有一条关键失真，导致它把问题定位到了错误的层面：

| # | 任务书的说法 | 我的实测 | 判定 |
|---|---|---|---|
| **A** | §2.1「账本写得再烂也会被接受，四段全空也照样落盘」 | **不成立**。存在真实判据门 `checkHandoffCriteriaPre`（H1-H4 硬判据），7 个坏账本用例中 **6 个被拒绝且不落盘** | ❌ **事实错误** |
| **B** | §2.2「全仓 0 处回执引导文案」 | **成立**。`nextStepHint`/`followUpHint`/`suggestPre`/`receiptHint` 全部 0 处；「猜你想用」0 处 | ✅ 成立 |
| **C** | §2.3「现有返回文案纯报文，零指导」 | **部分成立**：`memory_event(create)` 已有 `下一步: 用 action=append 加检查点`；`memory_note` 成功回执有「请转述」；但 `append`/`close`/`memory_log` 确实无任何指导 | ⚠️ 需修正 |
| **D** | §2.4「校验能力存在，只是没用在内容质量上」 | **不成立**。`writeHandoffLedger`/`writePlanSnapshot` 都过判据门；`memory_user` 的复读防护/预算拒绝只是**入口级**卫生门，账本侧同等能力更强（H1-H4） | ❌ 归因错误 |
| **E** | §2.5「不对称：memory_user 有真质量校验，账本/事件只有技术校验」 | **部分成立但对象错**：账本**有**质量门（比 memory_user 更严）；真正裸奔的是**检查点**（`memory_event append`）与 `memory_log` | ⚠️ 需重定向 |
| **F** | §5 缺陷 4「`members` 恒空」 | **已被近期数据推翻**：实测 53 事件中 **50 个非空（94%）** | ❌ 事实错误 |

### 0.1 一句话结论

> **判据门只覆盖了「账本 .md」这一条写入路径，而且它排在 WAL 之后 —— 坏账本虽然被拒绝写文件，却已经作为检查点进了事件库（唯一真相源）。真正完全无校验的是检查点与日志。所以用户要的「拒绝 + 回执指导」不是从零新建能力，而是把已经存在的 `ledger-criteria` / `wb-contract` 判据延伸到事件侧，并把回执引导挂到 4 个成功路径上。**

### 0.2 我独立复现出的**新缺陷**（任务书未提，严重度最高）

**★WAL 半渡态：被拒绝的坏账本仍然进了事件库。**

`memory_note(kind=handoff)` 的执行顺序是（`lib/index.js` L21935-22010）：

```
Phase 1  appendHandoffCheckpointPre(...)   ← 先写事件，零内容校验
Phase 2  engine.writeHandoffLedger(...)    ← 再过判据门，不合格 → ok:false
Phase 3  失败 → 补一条 kind='handoff-write-failed' 检查点
```

**实测**（`artifacts/_probe-v2-wal.mjs`，真调工具）：

```
handoff/*.md 文件数 = 1
事件 evt_5112759b checkpoints=5：
  · kind=handoff               四段[g/s/d/n]=---- len=22   ← 被拒绝的坏账本，进了事件库
  · kind=handoff-write-failed  四段[g/s/d/n]=---- len=144  ← 补偿标记
  · kind=handoff               四段[g/s/d/n]=---- len=47   ← 第二份坏账本，也进了
  · kind=handoff-write-failed  四段[g/s/d/n]=---- len=131
  · kind=handoff               四段[g/s/d/n]=YYYY len=197  ← 唯一合格的那份
⇒ 半渡态（事件有、文件无）= 2 条
```

**为什么这比任务书说的「静默接受」更严重**：账本文件被拒了（用户看不到坏数据，很好），但**坏内容作为不可撤销的检查点永久留在事件库里**，而且每失败一次就多两条（坏账本 + 补偿标记）。事件库是「唯一真相源」，会被它污染，且 append-only 无法删除。

**负路径（证明不这么做会错）**：把 Phase 1/Phase 2 顺序对调（先判据门、后写事件）⇒ 坏账本零写入，事件库零污染。代价是「事件优先」语义需要重新表述 —— 但「事件优先」本意是**保证事件不丢**，不是「允许坏数据先入库」。

**★这不是隔离环境的推测 —— 真实历史数据里已经发生了。** 扫描本机 13 个真实工作区（553 个检查点）：

```
write-failed 补偿标记 = 3 条（= 3 次写入被门拦下，内容已进事件库）
  aik_auto_memory_use  evt_605d3053  plan-write-failed  2026-10-27T05:29:21
  dsh-auto-memory      evt_89786878  plan-write-failed  2026-10-25T12:48:53
  dsh-auto-memory      evt_89786878  plan-write-failed  2026-10-27T08:12:09

四段全空的 handoff 检查点 = 10 条（含长度 1,420 / 1,610 / 1,495 字符的大块内容）
  dsh-auto-memory      evt_761ad9ff  6 条，2026-10-28 07:27 — 16:18
  dsh-auto-memory      evt_89786878  1 条，2026-10-27
  aik_auto_memory_use  evt_2bd0662b  2 条，2026-10-28
```

⇒ **真实记忆库里已经有 10 条「四段全空但正文上千字符」的 handoff 检查点**。

**★归因（用 git 判定，不猜）**：`appendHandoffCheckpointPre` 的四段透传修复**尚未提交** —— `git diff HEAD -- lib/event-write.js` 显示工作区有 26 行未提交改动（注释日期 2026-10-28 的「用户实报检查点渲染不出来」修复）。而这 10 条里最新的一条是 2026-10-28 16:18。因此：

| 归因 | 判定 |
|---|---|
| 这 10 条是「判据门拒绝后的半渡态」？ | **不是**。只有 3 条 `plan-write-failed` 属于被拒场景，且都是 plan 不是 handoff |
| 这 10 条是「旧代码不写四段」？ | **是**。四段透传修复在工作区未提交 ⇒ 历史写入路径从不带四段 |
| WAL 半渡态在真实库发生过？ | **发生了 3 次**（3 条 `plan-write-failed`），规模远小于我最初的担心 |

⇒ **修正 §0.2 的严重度评估**：半渡态是**真缺陷且真实发生过**，但历史污染规模是 **3 条**（不是 10 条）。10 条四段全空是**另一个已修但未提交的缺陷**留下的存量。两者根因不同，不能合并归因。

**关键发现（每条都有实测支撑）**：

1. **`memory_note` 的 `required` 只有 `content`，但 `kind=handoff` 时 `content` 必须含四个逐字标题** —— 这个要求只写在 `description` 里（模型可忘）。而**判据门会强制它**，所以最终行为是对的。**这是全仓唯一「description 说 + 代码真拦」的闭环**，可作为其他工具的范本。

2. **`memory_event` 的 26 个字段里只有 `action` 是必需**。实测（`_probe-v2-receipts.mjs`）：
   ```
   append 只给 text、不给四段  →  接受 ✔  →  "已追加到 evt_xxx：本次 +1 条，现共 1 个检查点。"
   append 四段全空串          →  接受 ✔
   append 四段全空白符"  "     →  接受 ✔（落盘后四段=空白符，前端渲染出空白行）
   ```
   **负路径**：如果在这里加「四段全空 ⇒ 拒绝」，则本机存量 553 个检查点中 11% 的合格历史不受影响（它们四段齐全），而新的空检查点会被拦下。

3. **`memory_log` 结构上无法表达四段** —— 入参只有 `note/date/kind`。但它**会写事件检查点**（`kind='log'`），只是不带四段。所以「日志」这条路径的产物在事件库里必然是四段空的，这解释了存量四段缺失的主要来源。

4. **`calendar_add` 的校验是全部写入工具里最弱的**：仅 `title` 非空且不含换行。日期格式、时间格式、象限值都不校验（非法值回落「未分类」）。实测 `calendar_add({title:'x'})` 直接成功。

## §2 方向 2：四场景回执方案（可直接实施）

### 2.0 设计前提（先破一个误区）

任务书的 §1.1 把问题描述成「工具静默接受坏数据」。**实际不是**：账本已经被拦了。用户真正缺的是**两件不同的事**：

- **A 类（校验）**：不合格 ⇒ 拒绝 + 说清怎么改。**账本已实现；检查点/日志未实现。**
- **B 类（引导）**：合格 ⇒ 接受 + 提示下一步该考虑什么。**全区缺失。**

所以方案的形状应该是：**A 类只补 3 个缺口，B 类新建一套回执机制。**

### 2.1 统一回执框架（一次设计，四处复用）

```js
// 伪代码：lib/receipt-hint.js（新文件，纯函数零 IO）
export function buildReceiptHintPre(kind, ctx) → { text, chars } | null
```

**四条硬约束**（每条都来自实测的成本数据）：

| 约束 | 值 | 依据 |
|---|---|---|
| 单条回执上限 | **≤ 180 字符** | 实测现有回执 36-253 字符；注入面 23,562；回执 180 字 ≈ 注入的 0.76% |
| 触发条件 | 只在**状态发生变化**时给 | 同一建议重复给 = 噪声（用户明确担心） |
| 频率控制 | 同一 hint 每会话最多 1 次 | 用 `engine.state._receiptHintsSent = new Set()` |
| 可关闭 | `config.receiptHints !== false` | 沿用既有开关模式（`criteriaGate` 同款） |

### 2.2 场景 1：`memory_note(kind=handoff)` 之后

**现状回执**（实测）：
```
交接账本已写入: ...\handoff-20261029-002616.md
请在本轮回复正文向用户转述本次更新要点。
```
（174 字符，零下一步引导）

**建议回执**（成功路径，追加 1 句）：
```
交接账本已写入: <path>（revision: xxx）
请在本轮回复正文向用户转述本次更新要点。
关联事件: evt_5112759b「记忆工具校验姿态」有 5 个检查点，最后更新 3 分钟前 → 若本账本是该事件的延续，用 memory_event(action="append") 记一条；若是新方向，memory_event(action="create")。
```
（+128 字符，总约 300 字符）

**实现要点**：`engine.state` 里已有事件列表的缓存（`refreshEventStatePre` 会调 `eventStorePre.list()`），**不需要额外 IO**。取 `status==='active'` 且 `updatedAt` 最大的那一个即可（`resolveActiveEventPre` 已实现该逻辑，`lib/event-write.js:74`）。

**拒绝路径**（判据门）：保持现状。实测文案已经很好：
```
memory_note: 写入被判据门拦截（H1/H2），原文件未改动：
· [H1] 缺少或标题不逐字匹配的四段标题：...
· [H2] 这些段为空或少于 20 字符：...(无法解析出任何段)
请补齐后重试。
```
**唯一改进**：把「请补齐后重试」换成**可复制的模板**：
```
请按以下骨架补齐后重试（标题必须逐字一致）：
## 任务状态
<一句话 + 当前产物路径>
## 目标
<可验证的完成标准>
## 已试方案与失败原因
<方案 → 失败原因（保留报错词）>
## 进度与下一步
<可直接执行的第一步，带文件路径或命令>
```
（约 220 字符，只在拒绝时出现，可接受）

### 2.3 场景 2：`memory_event(create)` 之后

**现状回执**（实测 252 字符）：
```
事件已建立: evt_8d85a139
名称: 探针事件
状态: active
时间跨度: (未指定；append 检查点时会自动从 at 推导)
存储: C:\Users\...\event-store.json
下一步: 用 action=append 加检查点（记得带 idemKey）。
```

**问题**：①`存储:` 那行是**纯噪音**（路径 130 字符，模型永远不会用）②「下一步」只提 append，**没提「该写账本」**（用户场景 2 的原话）。

**建议**（**净减少**字符）：
```
事件已建立: evt_8d85a139 「探针事件」(active)
下一步: action=append 加检查点（带 idemKey；四段 goal/state/dead/next 必填）。
提示: 新事件通常需要一篇 memory_note(kind=handoff) 记录来龙去脉。若这是既有工作的延续，请确认是否该 append 到旧事件而不是新建（避免同一件事被拆成两个）。
```
（约 175 字符，**比现在少 77 字符**，且带完整引导）

### 2.4 场景 3：`memory_event(close)` 之后

**现状回执**（实测）：
```
事件已收口: evt_xxx
成果: <outcome 前 200 字符>
```
（零引导）

**建议**：
```
事件已收口: evt_xxx（5 个检查点，0 个感知）
成果: <outcome>
建议: 该事件还有 2 个感知项为空（userPercept/sharedGround）——若本次有用户裁定或双方共识，现在补进去还来得及吗？不可（已 closed）⇒ 下个事件记得写。
其余 active 事件: 3 个，其中 1 个超过 7 天未更新（evt_aaa「xxx」，11 天前）。
```
（约 210 字符）

**⚠️ 但要注意一个真问题**：`close` 之后事件是 append-only **不能补写感知**。所以「收口前检查」比「收口后提示」更有价值 —— **建议把提示移到 `close` 的拒绝路径**：当 `outcome` 为空或事件感知全空时，先返回：

```
memory_event: close 前请确认——该事件有 5 个检查点但 0 个感知项。
若本次有实质性进展，建议先用 action=append 补 userPercept/agentTrace；
若确实无需记录，重新调用 close 并带 confirmEmpty=true 即可收口。
```
（需新增 `confirmEmpty` 参数，否则会造成新的摩擦）

### 2.5 场景 4：`memory_log` 之后

**现状回执**（实测 95 字符）：
```
已更新记忆文档: <path>
- 00:26 探针：记录一条测试日志用于观察回执文案。
(日视图补写 1 行)
```

**建议**：
```
已更新记忆文档: <path>（+1 行）
- 00:26 探针：...
提示: 本篇日志落在事件 evt_xxx「记忆工具校验姿态」下（无四段）。若本轮有实质产出，建议同步 memory_note(kind=handoff) 写四段账本；若只是流水，忽略即可。
```
（约 165 字符）

**注意**：`memory_log` 的 `note` 只有一句话，**关键词匹配「是否该写账本」几乎必然误报**。所以这条 hint 应该用**启发式条件**：`note` 长度 > 60 字符 或 含「修/改/实现/完成/发布」等动词 ⇒ 才提示。

### 2.6 回执预算的定量依据

| 项 | 值 | 来源 |
|---|---|---|
| 一次完整注入 | 23,562 字符 | `_probe-v2-guidance.mjs` 实测 |

**⇒ 结论：回执不是成本增加，如果配合 §3 的提示词精简，总成本是下降的。**

### 3.5 迁移后模型「忘记写」的概率是升还是降？

**判定：升（短期），降（长期）。分三层论证**：

**① 为什么短期会升**
实测数据：`memory_event` 的 description 有 1,783 字符，`memory_note` 有 1,665 字符。当这些内容被删减后，模型在**首次调用**时缺少上下文 —— 而回执只在调用**之后**才给。存在「第一轮永远学不到」的窗口。

**② 为什么长期会降（三个机制）**
- **时机正确**：提示词在「轮次开始时」说，模型可能已经忘了上一句；回执在「刚做完这个动作」时说，是注意力的峰值。
- **可执行**：现在的提示词是「必须带溯源」；回执是「本次缺 quoteRef，源文件是 `lib/x.js:123`，补这一句即可」。后者有具体对象。
- **有反馈闭环**：提示词说错了没人知道；回执拒绝会让模型立刻看到「我错了」。

**③ 关键前提（负路径）**
**若只删提示词而不加回执，遗忘率必然上升**。实测证据：铭文段（1,510 字符）是「每轮提醒」，删掉它而靠回执补，就失去了「每轮都在场」的保险。**§5 的优先级必须保证：先加回执，后删提示词，中间隔一轮回归验证。**

## §4 方向 4：三个新功能的可行性

### 4.1 Timeline（大事件 → 小事件下钻）

**现状实测**（`lib/client.js`）：

| 检查项 | 结果 |
|---|---|
| 现有视图 | `renderStream`（时间流）/ `renderLanes`（泳道）/ `renderWorkflow`（工作流）——**三个都是平铺** |
| `parentId` 字段 | **0 处** |
| 「子事件」概念 | **0 处** |
| 「大事件」 | 4 处，但都是 demo fixture 的统计文案 |
| 详情下钻 | 有：`renderDetailPanePre` 展示单个事件的检查点/panel |
| `members` 填充率 | **94%**（50/53）—— 任务书说的「恒空」已被推翻 |

**⇒ 差距评估：用户要的能力 = 「选一个事件，看它内部的小事件」。现有的 `renderDetailPanePre` 已经是「事件 → 检查点列表」，**这就是一层下钻**。缺的是「大事件」这一层的聚合。**

**「大事件/小事件」怎么表达？三个候选**：

| 方案 | 数据基础 | 现成度 | 评价 |
|---|---|---|---|
| **A. 用 `members` 做归组**（账本文件 → 事件） | `members` 94% 非空 | ★★★★ | **推荐**。已有 `groupIntoCandidateEventsPre`（L7757）在做确定性聚类 |
| B. 新增 `parentId` | 需要 schema 改动（26 字段锁） | ★☆ | 不建议 —— 破坏契约且存量无法回填 |
| C. 用 `kind` 分组（ledger/planSnapshot/...） | 实测 `kind` 全是 `ledger`（53/53） | ★ | 不可行，无区分度 |

**结论**：Timeline 的**前置阻塞不是 `members`（94% 已填），而是缺少「事件之上的一层」**。建议用方案 A：把 `members` 指向同一批账本的事件聚成一个「大事件」视图。**P1 可做，约 150-200 行前端 + 1 个聚合 API**。

**负路径**：如果按任务书的假设（`members` 恒空是阻塞）去做，会先花时间修 `members` 写入 —— 而它已经 94% 非空了，白做。

### 4.2 智能提醒（实质性变化 → 提醒写四类感知）

**实测数据**（`_probe-v2-percept.mjs`，13 个真实工作区）：

```

userPercept  = 14  (每事件 0.26 条)
agentTrace   = 12  (每事件 0.23 条)
sharedGround =  6  (每事件 0.11 条)
commitments  =  6  (每事件 0.11 条)
四类感知全为 0 的工作区: 10 / 12
```

**★决定性发现**：`userPercept` 的 stage 分布是 `{accepted: 14}` —— **100% 用对了 stage**，kind 分布 `{preference: 13, state: 1}` 也全在枚举内。

**⇒ 这推翻了「模型判断不出」的假设。模型完全理解这些字段。真正的问题是「几乎从不触发」。**

三个假设的判定：

| 假设 | 判定 | 依据 |
|---|---|---|
| H1 提示词没说清 | ❌ 不成立 | 提示词里「实质性进展」出现 11 次（3 个面），比任何规则都多 |
| H2 工具没强制 | ✅ **成立** | 全部可选、零校验（实测四段全空也接受） |
| H3 模型判断不出「实质性变化」 | ❌ 不成立 | 写了的 14 条全部格式正确 → 能判断，只是不主动 |

**⇒ 根因是「触发时机」而非「表达能力」。** 这意味着回执提醒是对症的药：在**动作发生的瞬间**问「这次算不算实质性进展」。

**怎么避免变成噪音**（用户明确担心）：

- **条件化**：只在「本轮有新的用户发言」+「本轮写了检查点」时提示，且该组合每会话最多 2 次。
- **可判定的信号**（实测可得）：本回合的用户消息里含 `裁定/不要/必须/改成/同意/反对` 等词 ⇒ 提示写 `userPercept`；本回合调用了 `writeHandoffLedger` ⇒ 提示。
- **一句话形式**，不列举四类：`本次有用户裁定（"…"），建议补一条 userPercept(kind=authorResponse)；否则忽略。`

### 4.3 智能推荐（Calendar 猜你想用）

**现状实测**：`calendarAdd` 仅校验 `title` 非空且无换行（`lib/index.js:13857`）。

**判定「重要且可写 Calendar」的可行判据**（零 LLM）：

| 信号 | 可计算性 | 例 |
|---|---|---|
| 显式日期 | ★★★★★ | `2026-11-05`、`下周三`、`11月5号` |
| 显式时刻 | ★★★★★ | `14:00`、`下午三点` |
| deadline 词 | ★★★★★ | `截止`、`deadline`、`前交`、`到期` |
| 用户明确要求 | ★★★★★ | `提醒我`、`记一下日程` |

**推荐放在哪个工具的回执里？** 实测结论：**`memory_log` 是最佳落点**，因为：
- `memory_note(kind=handoff)` 已在写"当前进展"，再塞日程提示会让回执过长；
- `memory_log` 的 note 通常是"做完什么"，最可能含"下次什么时候"。

**可执行文案示例**（挂 `memory_log` 回执尾部，仅命中日期/deadline 词时出现）：
```
📅 本条提到「11月5日」「截止」——是否加入日历？
   calendar_add(date="2026-11-05", title="<事项>", quadrant="重要不紧急")
```

**风险（负路径）**：实测 `memory_log` 的平均 note 长度较短，关键词误报会很高。**必须限制为「同时命中日期 + deadline 词」**，否则每 3 条日志就会误报 1 条。

## §6 对任务书 §8 三个问题的直接回答

**Q1：`memory_user` 的复读防护/预算拒绝是什么时候加的？为什么没推广到账本/事件？**

- 复读防护 `tailHas` 是从 v0.1.x 就有的**入口级卫生门**（`lib/index.js:18079`），服务的是「追加式写入的重复内容」。
- 它**没有推广**是因为：账本走的是**整篇新文件**（`handoff-<ts>.md`），不存在"尾部重复"问题；而账本有**更强**的四段判据门。
- **所以「不对称」的真相是**：不是账本缺校验，而是**账本与笔记用了不同种类的校验**（结构判据 vs 复读防护），各自适配自己的写入形态。
- **真正没推广到的是检查点**：`memory_event(append)` 既没有复读防护（有 idemKey 但需模型手填），也没有结构判据。

**Q2：是否存在统一的「记忆写入质量基线」？建议设计一个。**

**不存在。但统一的基线不该是「一套规则」，而该是「每个写入工具至少声明自己的质量契约」**：

```js
// 建议形态：lib/write-baseline.js
export const WRITE_BASELINES = Object.freeze({
  handoff:      { hard: ['H1','H2','H3','H4'], soft: ['S1','S2','S3'], receipt: 'handoff-written' },
  plan:         { hard: ['P-H1','P-H2'],       soft: ['P-S1'],        receipt: 'plan-written' },
  checkpoint:   { hard: [],                    soft: ['四段完整性','溯源提示'], receipt: 'checkpoint-appended' },
  log:          { hard: ['非空','卫生'],        soft: ['是否该写账本'], receipt: 'log-written' },
  calendar:     { hard: ['title 非空','日期格式'], soft: [],           receipt: 'calendar-added' },
})
```

**关键设计**：`hard` 为空是**允许的**（检查点就是这种），但 `receipt` **必须存在** —— 这是「工具承担指导责任」的落点。

**Q3：`memory_note` 的 L21915「渲染结果为空 ⇒ 放行手写兜底」这个决策对不对？**

**对，而且不该改。** 理由：
- 该分支只在 `kind=plan && fromEvents=true` 时走到。
- 「事件渲染结果为空」意味着事件库有内容但四段全空 —— 此时**拒绝会让用户完全无法写白板**（必须先补事件，但模型可能正处在不知道该补什么的时刻）。
- 当前设计「退回手写 content」保证了**永远有出路**。
- **改进点不在这个分支**，而在于：渲染失败时应把「为什么空」告诉模型（当前只返回「事件渲染结果为空，未写入」，没说哪个事件缺四段）。
