## §4 必须改项逐条方案

> **前提：本报告为纯只读产出，未执行任何代码改动。** 以下均为方案，需用户拍板后另行实施。
> **纪律提醒（用户既有硬性规则）**：改 `lib/index.js` / `lib/*-pre.js` 后**必须由用户手动重启 dsh web 宿主**才生效；agent **绝不**执行 `Stop-Process` / `Start-Process`，绝不触碰 3080 端口进程。
> **本仓固有约束**：只改 `-pre` 模块（`tools/release.mjs` 生成去 `-pre` 的孪生体，漏登记 fail-closed）；仓内另有陈旧的同名非 `-pre` 孪生文件，**勿手改**。

### 4.1 M1a —— 会话文件名候选表去硬编码（**最高优先级，建议在升级宿主之前先行落地**）

**风险**：`resolveSessionFile()`（`lib/index.js:3231-3244`）用**固定候选名**查找会话日志。历史上该文件名已随宿主从 `session.jsonl.zstd` 变为 `session.v3.jsonl.zstd`（代码注释 `:3229` 自述），而插件是**靠人工追加候选名**跟上的 —— 这套机制在 V4 面前同样会失效，且**失效时静默**（返回 `''`，五条功能链同时退化，见 §3.2）。

**方案（首选：目录扫描通配，不再枚举名字）**：
1. 把 `:3233` 的固定候选表改为**目录扫描**：`readdir(dir)` 取所有匹配 `/^session(\.[A-Za-z0-9]+)*\.jsonl(\.zstd)?$/` 的**普通文件**，按 `mtimeMs` 取最新（保留现有「按 mtime 取最新」语义，避免改动行为）。
2. 同步改 `:4012`（sid 回退）与 `lib/subagent-gc-pre.js:204`（子代理清扫）两处同形候选表 —— **三处必须一次改全**。依据仓库既有教训：「同一语义若在多个函数里各写一份判据，改动必须一次改全；只改部分会进入『半修』状态，有的路径能解析、有的恒判失败，症状看起来像新 bug，实为同一根因未改完。」
3. **保留向后兼容**：`session.jsonl`（明文）与 `session.jsonl.zstd` 仍须命中；`.zstd` 与明文的分支判据已存在（`:3262` 用 `decodeZstdFramesHead`，`:3668` 用 `file.endsWith('.zstd')` 分流）—— 扫描后**沿用同一分流判据**，不要另写一套。
4. **补一条守卫（必需）**：新增 smoke 断言「给定一个临时目录 + 一个 `session.v4.jsonl.zstd` 文件 ⇒ `resolveSessionFile()` 必须返回该文件」。**这条守卫的价值在于：V4 变更时它必须变红，而不是静默退化。** 这正是仓库既有纪律要求的形态。

**验收标准**：① `session.v3.jsonl.zstd` / `session.jsonl.zstd` / `session.jsonl` 三种既有形态行为不变（可用现有会话目录做真行为探针）；② 人造 `session.v4.jsonl.zstd` 能被解析；③ 全量回归不新增红。

### 4.2 M1b —— V4 事件形状双版本兼容

**风险**：`foldSessionLogEvents()`（`:9425`）按 type 字面量分五支（`:9437` / `:9444` / `:9452` / `:9464` / `:9469`），解析失败**逐行 continue、整体 try/catch** ⇒ V4 改形状即**静默产空**。

**方案（分四步，与 4.1 同一手法：先取证、再兼容、后加锁）**：
1. **先取证，不改码**：升级宿主前，抽样 1–2 个真实会话 `.zstd`，用现有 `decodeZstdFramesHead` 解出事件，**落盘为基线快照**（记录事件 type 全集 + `request/header` / `request/context` 的字段形状）。
   - 实测可用样本：`C:\Users\JH Z\.dsh\sessions\--D-dsh-auto-memory--\<会话id>\session.v3.jsonl.zstd`。
   - **注意**：本报告实测最新的**明文** `.jsonl` 样本 `_debug_child.jsonl` 属 **2026/8/14 陈旧文件**、首行 `version=0`，**不代表当前格式**，不可作为 V4 基线。当前会话一律为 `.jsonl.zstd`。
2. **升级后立即复跑同一批样本**，对比 `foldSessionLogEvents()` 输出（`msgs.length`、`provider`、`model`、`attachments` 计数）与基线是否一致。
3. **若 V4 改了形状**：在 `foldSessionLogEvents` 内做**双版本兼容**（V4 分支优先、V3 分支回退），**不要直接替换** —— 与 v3.1.2 目录选择器「双路径兼容」同一手法，保证旧会话仍可读。
4. **补守卫**：把「给定样本 ⇒ 期望 `msgs.length` / `model`」做成 smoke 断言，V4 变更时必须变红。

**⚠️ 实施顺序建议**：**先做 4.1 与 4.2 第 1 步（取证），再升级宿主。** 因为升级后若两处同时失效，将难以区分「是文件名没匹配上」还是「是事件形状变了」—— 先把文件名这一层打通，才能把 V4 形状变化隔离成单一变量。

### 4.3 M4 —— settings.yaml 读取降级为末位兜底

**风险**：0.1.7 起 settings.yaml **仅导入一次**、不再是权威源 ⇒ 本插件的 `contextWindow` 推导会停在导入时快照，新模型/改窗口后查不到 ⇒ 退化 fallback `131072`，UI 显示「回退默认值」（`lib/client.js:429` `waterFallbackSrc`）。

**方案（按优先级）**：
1. **首选**：把窗口解析的**权威源**改为官方路由容量。本插件**已有该路径**（`lib/index.js:3283` 注释「窗口优先级=手动覆盖 > 官方 `request/context` 容量 > settings.yaml auto/fallback」）⇒ **只需把 settings.yaml 从「次优」明确降为「末位兜底」**，并在设置页文案里如实标注来源。现有四档文案（`waterAutoSrc` / `waterManualSrc` / `waterOfficialSrc` / `waterFallbackSrc`）**已具备表达能力**，关键是确保 settings.yaml 命中时不再冒充「自动检测」。
2. **次选**：改从 Profile 的插件配置读取当前模型列表（需先摸清 0.1.7 的实际存储位置与形状 —— **本报告未取证，见 §5.6**）。
3. **不改也可接受为优雅降级**（有 fallback、不报错），但应在 `docs/` 记录该已知边界。
