## 0. 一句话结论

**瓶颈不在模型，在「喂什么文本」。**

同一批数据、同一个模型 C2，只把文档表示从「整篇 `checkpoint.text`」换成「检查点的四段 `goal+state`」：

| 指标 | 换表示前 | 换表示后 | 变化 |
|---|---|---|---|
| 归属 top-1（63 查询 / 47 事件 / LOO） | 31.7% | **47.6%** | **+15.9pp** |
| 配对 AUC（同事件 vs 不同事件） | 0.556 | **0.754** | +0.198 |
| 块结构 AUC（651 检查点） | 0.645 | **0.717** | +0.072 |
| 聚类 ARI（全量 651，GT=事件 id） | 0.127 | **0.409** | **+0.282** |

而**换模型**（C2 → C3，5.4× 体积、6.9× 耗时）在同样的好表示下只带来：

| 指标 | C2 + fields | C3 + fields | 变化 |
|---|---|---|---|
| 归属 top-1 | 47.6% | 50.8% | +3.2pp |
| 聚类 ARI | 0.409 | 0.443 | +0.034 |

⇒ **先改表示（零成本、零下载），再谈换模型。** 这是本报告最该带走的一条。

**但也要说清边界**：即使最好的组合（C3 + fields），归属 top-1 = 50.8%、聚类 ARI = 0.443，
按任务书 §10.5 的门槛（top-1 ≥ 70%、ARI ≥ 60%）**都只落在「边缘」档，不能做自动判定**。
⇒ **2.3 应做「候选排序 + 模型裁决」，不得做成「阈值自动归属」**（下面 §7 给决策表）。

## 0.5 【直接可用】判断评分标准

> 这一节是全篇唯一需要落地的东西。数据来源 `scripts/13-operating-points.mjs`（`out/operating-points.json`）。

### 0.5.1 核心结论：**不要用绝对余弦，用 top1−top2 的 margin**

绝对分数在三个模型之间**完全不可迁移**：要拿到同一个覆盖率档，C2 需要 θ≈0.94、bge-small 需要 θ≈0.80、bge-m3 需要 θ≈0.80。
而 `margin = top1 − top2` 在同一模型内是稳定的，且精度高得多。

### 0.5.2 归属判定（这条新记忆该挂到哪个事件）

「只在满足条件时才自动挂，否则只给候选」：

| 模型 | 判据 | 覆盖率 | 精度 |
|---|---|---|---|
| **bge-small-zh（23 MiB）** | **margin ≥ 0.05** | **33.3%** | **85.7%** |
| | margin ≥ 0.03 | 42.9% | 77.8% |
| | top-1 余弦 ≥ 0.80 | 47.6% | 50.0% |
| bge-m3（557 MiB） | margin ≥ 0.05 | 39.7% | 76.0% |
| | margin ≥ 0.03 | 54.0% | 73.5% |
| C2 e5-small（129 MiB） | margin ≥ 0.02 | 19.0% | 83.3% |
| | margin ≥ 0.03 | 1.6% | 100%（样本仅 1 条） |
| | top-1 余弦 ≥ 0.94 | 34.9% | 54.5% |

**读法**：想要「误挂率 ≤ 15%」，用 bge-small 的 `margin ≥ 0.05`，能自动处理 1/3 的写入；
想要「覆盖 40% 以上」，改用 `margin ≥ 0.03`，误挂率升到约 22%。
C2 在任何阈值下都达不到同样的「覆盖率 × 精度」，bge-m3 覆盖更高但精度更低且体积 24×。

### 0.5.3 合并判定（这两条碎片该不该合）

| 模型 | 高精度阈值 | 精度 | 召回 | 误合率 |
|---|---|---|---|---|
| C2 | θ ≥ 0.94 | 0.548 | 0.192 | 8.6% |
| bge-small-zh | θ ≥ 0.85 | 0.606 | 0.167 | 5.9% |
| bge-m3 | θ ≥ 0.80 | 0.645 | 0.167 | 5.0% |

**读法**：想把误合率压到 5%，召回只剩 16.7%（即 6 对里才捞到 1 对）。
⇒ **自动合并不可行**，只能「高阈值自动 + 中区间出提案 + 人/模型确认」。
另有一条硬规则必须前置：**文本逐字节相同 ⇒ 视为同一件事的重复记录**（实测 100 个难点负样本里有 3 对完全相同，
且它们挂在 3 个不同事件下，任何余弦阈值都会把它们判成"该合"）。

### 0.5.4 落地写法（可直接抄）

```js
// 表示：name + summary + 最近 3 条检查点的 (goal + state)，截断 480
const rep = (ev) => `${ev.name} ${ev.summary} ${last3(ev).map(c => `${c.goal} ${c.state}`).join(' ')}`.slice(0, 480)

const scored = actives.map(e => ({ id: e.id, s: cos(embedQuery(text), embedPassage(rep(e))) }))
  .sort((a, b) => b.s - a.s)

const margin = scored[0].s - scored[1].s
if (margin >= 0.05) return { decision: 'attach', eventId: scored[0].id, confidence: 'high' }   // 精度 ~86%
if (margin >= 0.03) return { decision: 'propose', eventId: scored[0].id, confidence: 'medium' } // 精度 ~78%
return { decision: 'candidates', top3: scored.slice(0, 3) }                                    // 不判定
```

三条配套约束（都来自负结果，别省）：

1. **阈值必须按模型配置**，不能写全局常量（同一覆盖率档：C2 0.94 / bge 0.80）。
2. **L1 标识只做 tie-break，不覆盖语义排序**（实测覆盖时 C3 掉 8.0pp、C2 掉 3.1pp）。
3. **二分类/聚类分开配阈值**（实测最优值不同：0.584–0.899 vs 0.80–0.95）。

## 3. 实验 B · 分数矩阵诊断（决定性）

### 3.1 三套表示（同数据、同模型 C2、同查询）

| 表示 | 归属 top-1 | 配对 AUC | 块 AUC | 聚类 ARI |
|---|---|---|---|---|
| `raw-text`：`name + summary + 最近3条 checkpoint.text`（生产现状，480 字） | 31.7% | 0.556 | 0.645 | 0.127 |
| `strip`：同上，但先去掉 markdown 标题/表格/时间戳 | 38.1% | 0.552 | 0.654 | 0.134 |
| `fields`：`name + summary + 最近3条 (goal + state)` | **47.6%** | **0.754** | **0.717** | **0.409** |

⇒ **去 markdown 样板几乎没用（+6.4pp 归属，其余持平）；换字段有决定性作用（+15.9pp / +0.198 / +0.282）。**

### 3.2 为什么 raw 表示会废掉：语料形态

| 事实 | 数值 |
|---|---|
| 检查点文本长度 | min 10 / 中位 **780** / p95 **1200（已被截断）** |
| 以 `#` 开头的整篇 markdown 文档 | **159 / 644 = 24.7%** |
| 含表格 `\|…\|` | 54 / 644 = 8.4% |
| 开头就是「交接账本 / 项目白板」的整篇粘贴 | **118 / 644 = 18.3%** |

⇒ 一段 1200 字的账本里可能横跨 5 个任务，平均池化后主题被稀释；
而两段不同的账本共享同一套标题模板（`## 任务状态`、`| 事件 |`），向量被模板拉到一起。
这解释了 raw 表示下 47×47 矩阵**中位 0.9056、极差仅 0.1055**：所有事件看起来都像。

### 3.3 块结构判定（651 检查点，GT = 事件 id）

| 模型（raw） | 块 AUC | same 均值 | cross 均值 | same P5 | cross P95 |
|---|---|---|---|---|---|
| C2 e5-small | 0.645 | 0.9121 | 0.9030 | 0.8840 | 0.9283 |
| C3 bge-m3 | 0.623 | 0.6255 | 0.5958 | 0.5213 | 0.6900 |
| bge-small-zh | 0.639 | 0.7321 | 0.6941 | 0.5999 | 0.8010 |
| all-MiniLM | 0.652 | 0.6358 | 0.5485 | 0.3528 | 0.7808 |
| gte-small | 0.604 | 0.8688 | 0.8598 | 0.8316 | 0.8946 |

| 模型（fields） | 块 AUC | same 均值 | cross 均值 |
|---|---|---|---|
| C2 | **0.717** | 0.9177 | 0.8968 |
| C3 | **0.743** | 0.6697 | 0.5811 |
| bge-small-zh | 0.688 | 0.7461 | 0.6724 |

**判定**（按任务书 §10.4 ④）：
- raw 表示下 **AUC 0.60–0.65 + 分数全部挤在 0.86–0.93** ⇒ **既有块结构、也严重压缩** ⇒ 属「表示层问题，调阈值无救」；
- fields 表示下 **AUC 0.717–0.743**，same P5 / cross P95 仍然重叠（0.8759 vs 0.9208）⇒ **有块结构但分布重叠，固定阈值仍不可用，必须用相对排序**。

⇒ **实验 B 的结论：C2 这条路不是「容量到头」，是「表示喂错了」。** 换表示后同一模型立刻可用性大增。

### 4.4 JS 与 Python 的数值对账（回答「Node 跑的是不是同一个模型」）

做法：取 **JS tokenizer 产出的 `input_ids`**，连同 JS 侧向量一起落盘；
再用 **Python 原生 onnxruntime 1.28 喂同一批 ids**、跑同一份 `model_int8.onnx`，
按 `m7_embedding_v1.py` 同一套后处理（CLS + L2）算出向量，逐条比余弦。

| 项 | 实测（12 条真实文本，token 48–259） |
|---|---|
| min cos(JS, PY) | **0.9999996** |
| mean cos | 1.0000000 |
| max 逐元素差 | **1.64e-07** |
| 输入 | `input_ids` / `attention_mask` |
| 输出 | **单一** `last_hidden_state`（batch, seq, 1024） |

⇒ **权重、图、池化、归一化四件事完全一致**，残差来自 ORT 版本差（node 1.21 vs py 1.28）的浮点噪声。
⇒ 但本次也发现一个**行为差异**（容易造成「两边不一致」的错觉）：
`ext(text, {truncation:true, max_length:512})` 在 pipeline 调用里**不生效**
（`cos(max_length=128, max_length=512) = 1.000000`），实际按 `tokenizer.model_max_length = 8192` 编码；
而 Python 侧车 `m7_embedding_v1.py` 是**硬编码 512**。要截断必须显式走 `ext.tokenizer(text, {truncation:true, max_length})`。

### 5.5 补测 · 100 MB 档位：`bge-base-zh-v1.5` q8（98.5 MiB / 768 维）

> 起因：需求方提出「C2 也是 JS、BGE 也是 JS，价格一样，为什么不用 BGE 替换 C2，
> 体积控制在 100–200 MB，而且 BGE 还有 sparse / ColBERT 三件套」。
> 本节回答两件事：**① 100 MB 档能买到什么；② 多花 76 MB 值不值。**

**① 三件套只在 bge-m3 上存在（已核对仓库文件）**

| 仓库 | dense ONNX | `sparse_linear.pt` | `colbert_linear.pt` |
|---|---|---|---|
| `BAAI/bge-m3` | 542 MB（int8） | ✅ 3,516 B | ✅ 2.0 MB |
| `BAAI/bge-base-zh-v1.5` | — | ❌ 无 | ❌ 无 |
| `Xenova/bge-small-zh-v1.5` | 23 MB | ❌ 无 | ❌ 无 |

⇒ 200 MB 预算内**拿不到** sparse / ColBERT；bge-m3 的最小可用量化是 int8 **557.5 MiB**（q4f16 反而 667 MiB）。

**② 实测（同数据、同表示、同 LOO 口径；bge 系另测了官方检索指令前缀）**

| 模型 | 体积 | ms/条 | top1(raw) | top1(fields) | top5(fields) | MRR(fields) | margin(fields) | 块AUC(fields) | ARI(fields) |
|---|---|---|---|---|---|---|---|---|---|
| bge-small-zh q8 | **23.3 MiB** | **12.4** | 33.3% | 46.0% | 63.5% | 0.553 | 0.0211 | 0.688 | 0.424 |
| **bge-base-zh q8** | **98.5 MiB** | 34.6 | **30.2%** | **42.9%** | 55.6% | 0.493 | 0.0268 | 0.676 | 0.412 |
| C2 e5-small q8 | 129.1 MiB | 56.1 | 31.7% | 47.6% | 65.1% | 0.560 | 0.0103 | 0.717 | 0.409 |
| bge-m3 int8 | 557.5 MiB | 151.4 | 42.9% | 50.8% | 76.2% | 0.622 | 0.0342 | 0.743 | 0.443 |

**检索指令前缀（`为这个句子生成表示以用于检索相关文章：`，只加在 query 侧）实测效果**：

| 组合 | 无指令 | +指令 | 差 |
|---|---|---|---|
| bge-small-zh · raw | 33.3% | **36.5%** | +3.2pp |
| bge-small-zh · fields | 46.0% | 46.0% | 0 |
| bge-base-zh · raw | 30.2% | 31.7% | +1.5pp |
| bge-base-zh · fields | 42.9% | 41.3% | −1.6pp |

⇒ 指令前缀是**小且不稳定**的效应，不改变任何结论；此前「只给 e5 加前缀」的不公平已在本轮补齐。

**结论（可能是本轮最反直觉的一条）**：

1. **体积翻 4 倍（23 → 98 MiB）没有带来收益，反而更差**：fields 下 46.0% → 42.9%（−3.1pp），
   raw 下 33.3% → 30.2%（−3.1pp）。两套表示、两套样本同向 ⇒ 不是抽样噪声。
2. **在 100 MB 档，没有任何候选超过 129 MiB 的 C2**（fields 下 C2 47.6% > base 42.9% > small 46.0% 中最高者仍 ≤ C2）。
3. **只有 bge-m3（557 MiB）明确更好**（50.8% / top5 76.2%），且它是唯一带三件套的。
4. bge-small-zh 的真实优势不在精度，在 **1/5.5 体积、4.5× 速度、margin 翻倍（0.0211 vs 0.0103）**。

> 未解释的部分（如实登记）：bge-base 为何不如 bge-small，本轮**没有定位**。
> 候选原因（未验证）：q8 量化对 768 维 base 损失更大 / 训练分布与本项目开发日志语料不匹配 /
> base 对长文本更敏感。**在定位之前，不建议把这个结论外推成「BGE 越大越差」。**

## 6. 实验 E · 二分类 vs 聚类（必须分开看）

### 6.1 二分类：**不可用，且原因是根本性的**

| 模型（raw） | AUC(pos/neg) | best-F1 | 阈值 | P | R |
|---|---|---|---|---|---|
| C2 | 0.556 | 0.677 | 0.880 | 0.531 | 0.933 |
| C3 | 0.506 | 0.669 | 0.399 | 0.502 | 1.000 |
| bge-zh | 0.516 | 0.667 | 0.374 | 0.500 | 1.000 |

| 模型（fields） | AUC(pos/neg) | best-F1 | 阈值 | P | R |
|---|---|---|---|---|---|
| C2 | 0.754 | 0.700 | 0.899 | 0.650 | 0.758 |
| C3 | 0.729 | 0.677 | 0.584 | 0.622 | 0.742 |
| bge-zh | 0.724 | 0.683 | 0.595 | 0.533 | 0.950 |

**所有模型、所有表示，最优 F1 都卡在 0.68–0.70**，且 precision 只有 0.50–0.65 ——
原因不是模型，是数据里**存在文本完全相同的跨事件对**：

- 100 个难点负样本中 **3 对（3.0%）文本逐字节相同**，内容都是同一条系统消息
  「【账本写入被门拦下】原因: 写入被判据门拦截（H1）…」，
  分别挂在 `evt_882dee05` / `evt_4d65008f` / `evt_8180305e` 三个事件下；
- 因此 `maxHard = 1.000` 而 `minPos = 0.127–0.864` ⇒ **`可分离 = 否`（所有模型无一例外）**；
- 在最优阈值下 hard 组正确率 **0.0%** —— 100 个难点对全部被判成「同一件事」。

⇒ 结论：**「两条文本像不像」不足以判定「是不是同一件事」**。
文本相同的重复记录可以属于两个事件（这条拦门消息就是），
必须引入非文本判据（标识符、时间窗、来源目录）。

### 6.2 聚类：比二分类健康，但仍不够

| 模型（raw） | 全量 651 best ARI | 最佳阈值 | 聚出 k（真值 47） | 平衡集 oracle-k ARI |
|---|---|---|---|---|
| C2 | 0.127 | 0.94 | 140 | 0.111 |
| C3 | 0.122 | 0.76 | 173 | 0.072 |
| bge-zh | 0.154 | 0.84 | 186 | 0.034 |

| 模型（fields） | 全量 best ARI | 最佳阈值 | k | 平衡集 oracle-k ARI |
|---|---|---|---|---|
| C2 | 0.409 | 0.95 | 346 | 0.261 |
| C3 | **0.443** | 0.80 | 296 | **0.297** |
| bge-zh | 0.424 | 0.86 | 324 | 0.225 |

**NMI 与 ARI 严重背离**（fields·C3：ARI 0.297 / NMI 0.790）。
原因：该数据下模型倾向**过度切分**（k=296 vs 真值 47），
过切会让「每个预测簇都很纯」⇒ NMI 高，但 ARI 因为拆散了同事件而低。
⇒ **本任务必须用 ARI 判定，不能用 NMI**（这条要写进 2.3 的验收口径）。

**阈值一致性**：二分类最优阈值（0.584–0.899）与聚类最优阈值（0.80–0.95）**不等**，
且**跨模型不可迁移**（见 §8.3）。⇒ 阈值必须是模型配置的一部分，且二分类与聚类要各留一个参数。

## 7. 实验 F · 与现有规则对照

### 7.1 规则基线（L1 标识层 + 词袋 0.34，逐字复刻 `lib/index.js:24632-24737`）

| 数据集 | 组合 | P | R | F1 | 准确率 |
|---|---|---|---|---|---|
| raw | pos vs neg | 0.686 | 0.200 | 0.310 | 0.554 |
| raw | pos vs hard | 0.296 | 0.200 | 0.239 | 0.305 |
| fields | pos vs neg | **0.886** | 0.325 | 0.476 | 0.642 |
| fields | pos vs hard | 0.411 | 0.325 | 0.363 | 0.377 |

规则的特点很鲜明：**精度高（0.886）、召回极低（0.325）**。
它只在「有明确标识」时说话，这正是它作为**强证据**的价值。

### 7.2 L1 作为归属决策的真实表现（关键）

| 指标 | raw 数据集 | fields 数据集 |
|---|---|---|
| 查询里含标识的比例 | 47/63 = 74.6%（16 条完全无标识） | 44/63 = 69.8%（19 条无标识） |
| L1 实际触发（有 active 事件 name/summary 命中同一标识） | **30/63 = 47.6%** | **29/63 = 46.0%** |
| 触发时「正确事件在命中集合里」 | **66.7%**（20/30） | **65.5%**（19/29） |
| 触发时按生产规则（取 updatedAt 最新）选中正确 | **30.0%**（9/30） | **34.5%**（10/29） |
| L1 单独 top-1（含未触发即失败） | **14.3%**（9/63） | **15.9%**（10/63） |

⇒ **生产 L1 的短板在多命中消歧，不在标识提取**：命中集合约 2/3 含真值，
但「取 updatedAt 最新」只兑现了约一半（30.0% / 34.5%）。
这是 1.4 可以低成本改进的点（例如：多命中时取**语义最接近**的那个，而不是最新）。

### 7.3 「L1 优先 + 余弦兜底」vs 纯余弦（同一批查询）

| 数据集 × 模型 | 纯余弦 top-1 | L1+余弦 | 差 |
|---|---|---|---|
| raw · C2 | 31.7% | 28.6% | **−3.1pp** |
| raw · C3 | 42.9% | 34.9% | **−8.0pp** |
| raw · bge-zh | 33.3% | 33.3% | 0 |
| raw · MiniLM | 20.6% | 27.0% | +6.4pp |
| fields · C2 | 47.6% | 49.2% | +1.6pp |
| fields · bge-zh | 46.0% | 47.6% | +1.6pp |
| fields · C3 | 50.8% | 46.0% | **−4.8pp** |

⇒ **「L1 覆盖语义」在模型较强时是负收益**（C3 上 −8.0pp / −4.8pp）。
⇒ 2.3 的接线应改为：**语义排序为主，L1 只做「同票优先 / 强负证据排除」**，不做覆盖。

## 8. 三问结论

### Q1 · C3（bge-m3 1024 维）能否解决 C2 解决不了的区分度问题？

**🟡 部分能，但不足以改变方案形态。**

- 有明确增益：raw 表示下 top-1 31.7%→42.9%（+11.2pp）、配对 8:1 压倒 C2；
- 换好表示后增益收窄到 +3.2pp（47.6%→50.8%），说明**它补的是表示缺陷，不是判定能力**；
- 绝对水平仍不够：top-1 50.8% < 70% 门槛，聚类 ARI 0.443 < 0.60 门槛；
- 代价确定：磁盘 557.5 MiB（C2 的 4.3×）、单条 386.8 ms（C2 的 6.9×）。

**边界**：C3 适合做**候选排序**（top-5 76.2%，比 C2 高 11.1pp），不适合做**判定**。

### Q2 · 如果 C3 更好，它应该做成什么形态？

**结论变了：C3 不该绑 Python。** 本轮实测它可纯 JS 载入（2527 ms / 1024 维），
所以它的产品定位是「**可选下载的大模型**」，不是「可选安装的 Python 引擎」。

建议形态：

| 项 | 建议 |
|---|---|
| 开关名 | `semanticEmbedModel`（取值 `e5-small` \| `bge-small-zh` \| `bge-m3`），而不是三档 tier 开关 |
| 触发条件 | 默认 `bge-small-zh`（23.3 MiB 随包）；`bge-m3` 仅当用户显式下载后自动启用 |
| 降级链 | `bge-m3 → bge-small-zh → e5-small → C1 词法`；任一档资产校验失败即降一档并记一条 `degraded` |
| 用户可见文案 | 「已启用增强语义模型（bge-m3，542 MB）。未安装时使用内置轻量模型（23 MB），效果相差约 3 个百分点。」 |
| 何时不用语义 | 归属判定一律不自动落盘；语义只出 top-3 候选，由模型裁决 |

（原任务书的「C3 优先、C2 降级」**不成立**：C3 与 C2 的差别是磁盘与下载，不是 Python。）

### Q3 · 有没有体积更小、JS 原生可用、能胜任的模型？

**✅ 有：`Xenova/bge-small-zh-v1.5`（q8，单文件）。**

| 项 | 实测 |
|---|---|
| 磁盘 | **24,451,050 B / 23.3 MiB**（C2 的 1/5.5） |
| 维度 | **512**（→ 必须改 H1 的 384 硬校验） |
| pooling / 前缀 | `cls` / 无前缀（官方 `1_Pooling` 已核对） |
| 载入 | 首次 1755 ms（含首次推理）/ 复载 **144 ms** |
| 速度 | **12.4 ms/条**（C2 56.1 ms 的 1/4.5） |
| top-1 | raw **33.3%**（C2 31.7%）/ fields **46.0%**（C2 47.6%） |
| 块 AUC | raw 0.639 / fields 0.688 |
| 聚类 ARI | raw **0.154**（C2 0.127）/ fields 0.424 |
| ONNX sha256 | `15b717c382bcb518ba457b93ea6850ede7f4f1cd8937454aa06972366cd19bcc` |

**判定：等价质量 + 1/5 体积 + 4.5× 速度 ⇒ 推荐作为默认内置模型。**
代价是维度 384→512，需改 H1/H4（但 H1 本来就得为 C3 参数化，边际成本≈0）。

被淘汰的候选（均为实测，非推断）：

| 候选 | 体积 | 淘汰理由 |
|---|---|---|
| bge-base-zh-v1.5 q8 | 98.5 MiB | fields top-1 **42.9%**（比 23 MiB 的 bge-small 还低 3.1pp）、top5 55.6%；见 §5.5 |
| all-MiniLM-L6-v2 q8 | 22.6 MiB | 中文 top-1 **20.6%**（比 C2 低 11.1pp） |
| gte-small q8 | 33.1 MiB | top-1 **28.6%**，体积还大 1.4× |

未测：jina-v2-small、nomic-embed-text-v1.5、e5-large、Qwen3-Embedding（safetensors 无 torch，见 §14）。

### Q4 · Python sidecar 剩下的必要性

本轮唯一能确认的是：**就「1024 维 bge-m3 embedding」这一件事，Python 不再必要**（JS 直载已实测）。
Python 侧车剩下的价值只剩：fp32 provider（`BgeM3Embedder`）、以及其它 python 工具链的复用。
⇒ 建议**不要**为了 embedding 让用户装 Python，把它降级为「已有 python 环境的用户可获得 fp32 精度」。

## 9. 决策表：什么场景用哪个方法

| 场景 | 推荐做法 | 实测依据 |
|---|---|---|
| 新记忆归属（1 条 → 已有事件） | **表示先用 `goal+state`**；语义出 top-3 候选；L1 标识作**并列优先**，不作覆盖 | L1 覆盖 C3 时 −8.0pp；fields 表示 top-5 76.2% |

| 绝大多数用户（无 C3） | `bge-small-zh q8` + `fields` 表示 | 23.3 MiB / 12.4 ms / top-1 46.0% |
| 已有 C3 的用户 | 保持 C3，但只做排序与 top-5 召回 | top-5 76.2% |

| **H5** | `embedding-config.js` | 固定 `onnxFile` 字符串 | 取配置 |
| **H6（新）** | `semantic-js-worker.js:58` | 硬编码 `pooling: 'mean'` | 从配置取（bge 系必须 `cls`；实测误用 mean −7.9pp） |

⇒ 任何写成 `0.86` 的全局阈值，在 C2 下会把**全部**碎片合并，在 C3 下**一个都不动**。

## 12. 补测 · bge-m3 三件套：JS 到底能不能做 sparse / ColBERT

> 起因：被问到「是不是 JS 只能输出三者之一」+「Python 侧应保留做扩展与 GPU」。
> 这一节把前提先钉死，再给实测，因为**前提错了会做错架构决定**。

### 12.1 机制澄清：三件套不是三条通路，是**同一个张量的三种用法**

本机取 ONNX 输出：`outputs = [('last_hidden_state', [batch, seq, 1024])]` —— **只有一个输出**。

| 模式 | 算法（官方 FlagEmbedding 口径） | 用到的量 |
|---|---|---|
| dense | `L2(hidden[CLS])` | 1 个向量（1024） |
| sparse | `w_t = relu(hidden_t · W + b)`，再对非 padding token 取 **max** → `token_id → weight` | 每 token 1 个标量 |
| ColBERT | 每 token 各自 L2 归一化；打分 `Σ_{q_tok} max_{d_tok} cos`（MaxSim） | 每 token 1 个向量 |

⇒ **三者都从 `last_hidden_state` 派生**。所以「JS 只能拿到三者之一」不成立——
障碍不是 JS 语言，而是 **sparse 需要一个 1024×1 的线性头**（默认在 `sparse_linear.pt` 里，需 torch 才能读）。

**本轮实测把那个头取出来了**（脚本 `10-extract-sparse-head.py`，纯 zipfile+struct，不需要 torch）：

```
sparse_linear.pt = 3,516 B，内含 weight(1024×fp16) + bias(1×fp16)
weight bytes = 2048 | bias bytes = 2
len(w) = 1024 | bias = 0.045196533203125
w: min=-0.019363 max=0.022202 mean=-0.001243
```

⇒ **1025 个数就能复现 sparse 模式**，JS 侧 30 行即可（`11-multivector.mjs` 已实现并跑通）。

### 12.2 实测：同一批查询，三种打分（表示 = fields，模型 = bge-m3 int8）

配置 A：63 查询 / 47 候选，query 截 96 token、doc 截 128 token（为控时间）

| 方法 | top-1 | top-5 | MRR | 中位排名 |
|---|---|---|---|---|
| dense（CLS） | 50.8% | 76.2% | 0.622 | 1 |
| sparse（抽出线性头） | 44.4% | **77.8%** | 0.596 | 2 |
| ColBERT MaxSim | 44.4% | 65.1% | 0.536 | 2 |
| **dense + sparse（min-max 融合）** | **55.6%** | **77.8%** | **0.663** | 1 |
| dense + ColBERT | 47.6% | 66.7% | 0.573 | 2 |
| 三者全上 | 50.8% | 73.0% | 0.607 | 1 |

配置 B：**只在 20 条查询上放开截断**（query 256 / doc 384，接近全长），以排除截断这个混淆

| 方法 | top-1 | top-5 | MRR |
|---|---|---|---|
| dense | 60.0% | **85.0%** | 0.684 |
| sparse | 50.0% | 80.0% | 0.643 |
| **ColBERT MaxSim** | **65.0%** | 80.0% | **0.695** |
| **dense + sparse** | **70.0%** | 80.0% | **0.761** |
| dense + ColBERT | 60.0% | 80.0% | 0.691 |

**读法（避免过度解读）**：

1. **sparse 有真实互补性**：配置 A 里 dense+sparse 把 top-1 从 50.8% 拉到 55.6%（+4.8pp，+5 条查询）、
   配置 B 里从 60.0% 拉到 70.0%（+10pp）。两套样本同向 ⇒ 这个增益大概率是真的。
2. **ColBERT 对截断极其敏感**：96/128 截断时 44.4%（比 dense 低 6.4pp），放开到 256/384 后 65.0%（比 dense 高 5pp）。
   ⇒ 它的价值依赖**长序列 + 逐 token 存储**，属于「要么全量、要么掉质」的形态。
3. **配置 B 只有 20 条查询**：65% vs 60% 只差 1 条，**不构成显著差异**，不能据此说 ColBERT 更强。

### 12.3 真正的限制不是 JS，是**存储与延迟**

| 项 | 实测/推算 |
|---|---|
| dense 存储 | 每事件 1 条 × 1024 float = **4 KB** |
| ColBERT 存储 | 每文档 `seq × 1024 float`；644 条检查点按均值 ~350 token ≈ **923 MB**；按 512 上限 ≈ **1.35 GB** |
| ColBERT 打分成本 | 全长 MaxSim 是 `q_len × d_len` 次 1024 维点积：940 对耗时 **28.7 s**；短截断时 2961 对耗时 27.5 s ⇒ **全长每对约 3.3×** |
| sparse 存储 | 每文档 一个 `token→weight` 稀疏表（非零项通常几十~几百） |
| 三路嵌入的额外成本 | 同一 forward 已产出全部信息，**无需二次推理**（本轮 144 条 token 级向量 = 15.7–19.5 s） |

⇒ 结论：**JS 在能力上三者都能做**（已跑通稀疏头抽取与 MaxSim）；
**不建议**在插件运行时上 ColBERT，理由是 `~1 GB 索引 + 每对 3.3× 打分`，不是「JS 做不到」。

## 13. 对主线的三条可执行建议

1. **2.3 的接线先改表示，不要先换模型**：`createEventForWorkPre` / 归并提案取文本时，
   优先用 `checkpoint.goal + checkpoint.state`（缺则回退 `text`），实测归属 +15.9pp、ARI +0.282。
   这个改动的风险级别是「纯函数级」，与 2.1（填 goal）天然互补 —— 2.1 做得越好，这条收益越大。
2. **1.4 的 L2 升级**：把「L1 覆盖语义」改成「语义排序 + L1 作 tie-break」，
   并修多命中消歧（当前「取 updatedAt 最新」只兑现 34.5%，而命中集合含真值 66.7%）。
3. **2.4 的自动化程度**：ARI 0.443 不支持「自动合并」；只能做「高阈值自动 + 中区间人工确认」。
   另外必须先加一条**「文本完全相同 ⇒ 同一件事的重复记录」判定**，
   否则那 3 个挂着同一条拦门消息的事件会被反复误合/误拆。
