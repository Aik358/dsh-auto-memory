# 前缀缓存异常调查报告 · DeepSeek V4.1 Flash

**报告日期**：2026-10-05
**数据来源**：中转站用量账单 `billing-usage-2026-10-05.csv`（847 条请求 / 325,243,165 tokens / ¥9.69）
**统计区间**：2026-10-05 14:54 – 21:37（本地时间，UTC+8）
**报告目的**：请运营方协助核查 DeepSeek V4.1 Flash 通道的前缀缓存（prompt cache）行为

---

## 一、结论摘要

在同一中转站、同一客户端、同一时段内，两个模型的缓存表现出现**数量级差异**：

| 指标 | DeepSeek V4.1 Flash | GLM 5.3 Flash | 差异 |
|---|---:|---:|---|
| 请求数 | 173 | 674 | — |
| 整体缓存命中率 | **60.4%** | **87.2%** | −26.8pt |
| 严重未命中率（命中 <20%） | **38.2%** | 12.9% | 2.96× |
| 命中时的命中深度 | 91.6% | 99.6% | −8.0pt |
| 命中时平均漏算 token | **31,568 / 请求** | 1,511 / 请求 | 20.9× |
| 未命中后下一条即恢复 | 52% | 93% | — |
| **0–10 秒间隔内的命中率** | **84.8%** | **99.5%** | **−14.7pt** |
| 单位成本（每百万 token） | ¥0.041 | ¥0.027 | **+52%** |

**核心结论**：这不是缓存过期（TTL）问题，也不是客户端前缀改写问题。证据指向**上游实例侧的缓存可见性缺失**——同一份上下文，在 DeepSeek 通道上会被间歇性地当作全新请求处理。

---

## 二、关键证据（按强度排序）

### 证据 1（决定性）：5 秒内的请求也会失效

若失原因是缓存过期，则间隔越短命中率应越高。实测：

| 同模型相邻请求间隔 | DeepSeek 命中率 | GLM 命中率 |
|---|---:|---:|
| 0–10 秒 | 84.8%（n=24） | **99.5%**（n=158） |
| 10–20 秒 | 60.4%（n=62） | **99.0%**（n=325） |
| 20–30 秒 | 43.5%（n=25） | 82.8%（n=95） |
| 30–60 秒 | 66.6%（n=38） | 34.6%（n=79） |

GLM 在 0–20 秒窗口内稳定保持 99%+，而 DeepSeek 在 **10–20 秒**这一档就掉到 60.4%。**任何 TTL 都无法解释 5–20 秒内的缓存失效。**

### 证据 2（决定性）：失效后 5–14 秒，同一条内容又能命中

排查中发现一个高度一致的模式：**某条请求完全未命中（read≈0），但它之后 5–14 秒内的下一条请求却完整读到了几乎相同的上下文（94–99%）**。

真实时序样例（15:46–16:04 窗口）：

```
15:57:21  prompt=176,576  命中 99.8%   ← 正常
15:57:40  prompt=177,245  命中  2.2%   ← 同一上下文，缓存整个消失
15:57:49  prompt=177,623  命中 99.8%   ← 9 秒后自动恢复

16:02:20  prompt=182,000  命中 99.5%   ← 正常
16:02:29  prompt=186,233  命中  0.0%   ← 完全未命中
16:02:37  prompt=189,000  命中 98.6%   ← 8 秒后恢复

15:49:10  prompt=109,000  命中 99.4%
15:49:28  prompt=109,155  命中  3.6%   ← 中间这条失效
15:49:35  prompt=115,000  命中 94.9%
```

**含义**：缓存内容客观存在且可用，只是**中间那一条请求没有落到持有缓存的实例上**。若缓存真被清除，下一条不可能在 5–14 秒内读回。

统计口径：153 条全未命中请求中，**116 条（75.8%）**在下一条同内容请求上恢复。

### 证据 3：一个只出现在 DeepSeek 通道的常量 `36186`

DeepSeek 通道有 8 条请求的 `cache_read` **恰好等于 36186**，且它们自身的 prompt 大小天差地别：

```
prompt = 105,139  → read = 36,186
prompt = 159,651  → read = 36,186
prompt = 172,593  → read = 36,186
prompt = 264,428  → read = 36,186
prompt = 426,912  → read = 36,186
prompt = 661,222  → read = 36,186
prompt = 662,203  → read = 36,186
prompt = 660,181  → read = 36,186
```

**GLM 通道 674 条请求中出现该值的次数为 0。**

这强烈提示：DeepSeek 通道侧存在一个**固定约 36k token 的可缓存前缀上限**（例如系统提示与工具定义部分），超出部分（整个对话历史）在某些请求上完全无法命中。

### 证据 4：失效时缓存里只剩零星碎片

DeepSeek 未命中请求的 `cache_read` 取值分布：

```
256×13   1024×12   36186×5   2176×3   14876×3   17280×3   17536×3
0×2      1408×2    13516×2   14293×2  14487×2   17024×2   18048×2
19072×2  896×1     2793×1    13710×1  13904×1   14099×1   16768×1
17792×1  18304×1
```

全部落在 **0 – 36k** 区间，而对应 prompt 普遍在 300k–660k。**缓存里只剩下不足 5% 的内容**。

### 证据 5：命中时的深度也不完整

即使算作「命中」的请求，DeepSeek 的平均漏算量也远高于 GLM：

- DeepSeek 命中行：平均漏 **31,568** tokens/请求（p10=529，p90=**121,586**）
- GLM 命中行：平均漏 **1,511** tokens/请求（p10=143，p90=1,801）

DeepSeek 的 p90 达到 121,586，说明相当一部分「命中」请求实际只读到了一半缓存。

### 证据 6：与客户端行为无关

命中请求的 `read` 值**恰好等于 prompt 减去本轮新增的少量 token**（GLM 命中行中位仅漏 421 tokens）——这正是「前缀不变、只在尾部追加」的标准形态。若客户端每轮改写前缀，命中行的 read 会接近 0，而不是 200k–420k。

同一份客户端代码、同一条网络出口（账单中 `来源IP` 全部为同一地址），只有 DeepSeek 通道异常，可排除客户端侧因素。

## 三、根因假设与证据强度

### 假设 A：DeepSeek 通道存在多上游实例/多账号，请求被分散，各自维护独立缓存

**证据强度：高（主因）**

支持：
1. 5–20 秒内即失效，TTL 无法解释（证据 1）
2. 失效后 5–14 秒又能读回，说明是「落到别的实例」而非「缓存被删」（证据 2）
3. 38.2% 的严重失效率，与 2–3 个实例轮询的理论值吻合
4. 失效与恢复交替出现的间隔不规律，符合负载均衡调度的特征

### 假设 B：该通道的上游前缀缓存容量上限显著低于 GLM

**证据强度：中高（并存因素）**

支持：
1. `36186` 常量在不同 prompt 下恒定（证据 3）
2. 命中请求的 `cache_read` 上限约 420k，而 GLM 可达同量级但更稳定
3. 命中深度仅 91.6% 且 p90 漏 121k（证据 5）

### 假设 C：缓存过期 TTL

**证据强度：排除**

0–10 秒窗口内 DeepSeek 仍有 15.2% 失效率。若为 TTL，不可能在 10 秒内失效。

### 假设 D：客户端前缀改写 / 中转站上下文改写

**证据强度：排除**

命中行形态完全符合「前缀稳定 + 尾部追加」（证据 6）。若前缀被改写，命中行的 read 不会达到 200k–420k。

## 四、请运营方协助核查的事项

按优先级排列，前两项最关键：

### ★ 1. DeepSeek 通道是否为多账号 / 多上游轮询？

- 该通道配置了几个上游 Key 或几个上游实例？
- 调度策略是什么（轮询 / 随机 / 按负载）？
- **能否对同一 API Key（或同一会话）做粘性路由，固定到同一上游实例？**

> 这是本次调查指向的首要原因。若确为多实例轮询，启用会话粘性应能立刻改善。

### ★ 2. DeepSeek 通道的上游来源是什么？

- 是 DeepSeek 官方 API，还是其他渠道？
- 若是官方，是否有多个账号池？
- 上游是否对 DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens` 做了转换或丢弃？

### 3. 能否提供该时段 DeepSeek 通道的上游侧请求日志？

需要**上游返回的**（非中转站计算的）缓存字段，例如：

```json
"usage": {
  "prompt_tokens": 661222,
  "prompt_cache_hit_tokens": 36186,      // 上游实际报告的命中量
  "prompt_cache_miss_tokens": 625036
}
```

若可能，请一并提供该时段的路由记录（每个请求发往哪个上游账号/实例）。

### 4. `36186` 这个值在贵方系统中是否有特殊含义？

- 是否为某个固定前缀（系统提示 + 工具定义）的缓存块大小？
- 是否与贵方对请求做的预处理（消息裁剪、去重、重排、注入）有关？

### 5. 中转站是否对 DeepSeek 请求做过额外处理？

- 是否有上下文裁剪、历史消息压缩、消息去重？
- 是否注入了额外的前置内容（时间戳、审计头、系统提示）？
- 若注入了**变化的内容**（如每轮不同的时间戳），会直接击穿前缀缓存——建议改为固定值或后置。

## 五、影响评估

**本次账单（1 个时段，173 条 DeepSeek 请求）**：

- 严重未命中的 66 条请求吃掉 **21,084,222** 个未命中 token，占 DeepSeek 全部未命中 token 的 **86.2%**
- 按该通道实际资费折算，这部分多支出约 **¥1.325**，相当于 **DeepSeek 通道花费的 52%**
- 若缓存表现达到 GLM 的水平（87.2%），单位成本可从 **¥0.041/百万 token 降至 ¥0.027 左右**

**按当前使用强度外推**：若每日 DeepSeek 用量与今日相当，该问题造成的额外开销约在**每日 ¥1.3 量级**，且随用量线性放大。

**用户体验层面的影响同样明显**：未命中意味着上游需要重新预填充 20 万–60 万 token，直接抬高了首字节延迟（实测未命中请求的 TTFB 中位数为命中请求的 1.6–2.7 倍）。

## 六、附录：复算方法

数据取自账单 CSV，逐行计算：

```
命中率        = cache_read_tokens / (cache_read_tokens + input_tokens)
严重未命中    = 命中率 < 20%
单位成本      = 实际扣除 / (input + output + cache_read) × 1,000,000
同模型间隔    = 该行时间 − 前一条同模型请求时间
```

**核心复算数字（可直接核对）**：

| 项目 | 数值 |
|---|---|
| DeepSeek 请求数 / 总 token / 花费 | 173 / 62,515,815 / ¥2.570 |
| GLM 请求数 / 总 token / 花费 | 674 / 262,727,350 / ¥7.121 |
| DeepSeek 严重未命中条数 | 66（38.2%） |
| 其未命中 token | 21,084,222（占 DeepSeek 未命中的 86.2%） |
| `36186` 出现次数 | DeepSeek 8 次 / GLM **0 次** |
| 全未命中后下一条恢复率 | 116/153 = 75.8% |
