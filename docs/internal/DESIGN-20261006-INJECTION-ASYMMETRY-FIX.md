## 2. 关键澄清：唤回块本身**不带快照**

你以为的现象是「每次唤回都裹着一遍完整前缀」。

**实际机制**：唤回块与快照是**两个独立的面**，各自内容互不包含。但宿主把它们**拼成一个字符串**再整体去重。

所以看起来像「唤回带了快照」，真相是：**唤回块一变，整串就变，把 38 KB 快照一起拖着重投**。

这个区别决定修法方向：**不是「把快照从唤回里去掉」（本来就没在里面），而是「让唤回的变化不再污染整串」。**

---

## 3. 不对称的物理定义与实测

| | 插件侧 _snapFp === snap | 宿主 project() |
|---|---|---|
| 判据粒度 | **快照级** | **拼接串级** |
| 单 context 面时 | 等价 | 等价 |
| 加唤回面后 | **不等价** | **不等价** |

两边都以为对方会去重 ⇒ 谁都没去重。

实测（最大会话 45.5 MB，1,758 次记忆类投递）：

| 判据 | 实测 |
|---|---|
| 完整档 / 精简档 | **1,731 / 21**（98.5% 完整版） |
| 相邻两次**整串**相同 | **0 / 1757** |
| 相邻两次**快照**相同 | **480 / 1757** |
| 完整版去重后唯一版本 | **481 / 1751** |

相邻变化分类（决定性证据）：

| 类型 | 次数 | 性质 |
|---|---|---|
| 快照也变了 | 1,277 | 该投（但应投精简版） |
| **唤回换包 · 快照未变** | **480** | **纯浪费约 17.1 MB** |
| 唤回消失/新增 · 快照未变 | 0 | — |
| 两者都没变 | 0 | — |

唤回是一次性通道（渲染即 markDelivered 且 st.claimed=null），它不重复；它是**高频变化源**。

## 5. 方案（分层，按依赖顺序）

### 第 1 层 · 消除不对称（必须最先做）

目标：**让唤回块的变化不再污染快照的去重**。

| 选项 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **1A** | 唤回块内容与上次相同时返回空串 | 低 | 只救「同包重复渲染」；实测唤回 851/1063 都在变 ⇒ 效果有限 |
| **1B** | **唤回块脱离 context 面**，改为独立消息投递 | 中 | 需查宿主是否支持独立投递；**最干净** |
| **1C** | 唤回块并入快照面，由插件统一决定重投 | 中高 | **推翻 2026-09-15「唤回是独立面」的既有裁定** |
| **1D** | 插件侧不再依赖宿主去重（删 15209 分支） | 低 | 与既有机制冲突，非治本 |

**建议：1B 优先调查，1A 作兜底。** 理由是只有 1B 能在宿主侧真正解耦唤回与快照；1A 只在唤回内容重复时有救，而数据显示它几乎每次都变。

### 第 2 层 · 修分级判定（病灶 B）

`lib/index.js:15209` 的快照未变分支返回完整版且**不调 countTieredSlim()**。

**注意**：若第 1 层做成（唤回不再污染整串），这条分支的前提「交宿主去重」**重新成立**，它就**变回无害**。
所以第 2 层的正确动作**不是「删掉它」**，而是「第 1 层做完后**验证它是否还有害**」，并确认各返回路径的精简计数语义一致。

### 第 3 层 · 体积与节奏（你真正想要的效果）

**3a · 完整版瘦身**（目标 38 KB → 约 20 KB）
- 规则段 18.8 KB 是最大项，三个选项：①保留但仅真人在场时给；②压缩措辞；③移出注入、改 memory_read(kind=user) 按需取
- `[降级]` 段每步 100% 变 ⇒ 应改为稳定文本或移出快照
- 铭文 62% 变化率 ⇒ 检查是否含时间性文本

**3b · 节奏改成你要的语义**
当前实测配置：真人在场 → 该 turn 首次即给完整版（不受门槛限制）；无人在场 → 攒够 fullEverySlims = 3 次精简版就放行完整版；snapshotMinGapRounds = 5。
你期望的是「自己跑的时候每隔 10 轮一次完整版」—— 当前是「攒 3 次精简就给」，**比 10 轮激进得多**。
需你明确：**「10 轮」以什么为计数单位**（step / turn / 精简版次数）？

**3c · 精简版比例**
实测已是完整版的 **4.8%**（1,850 / 38,312），**优于你期望的 1/10**。若完整版瘦身到 20 KB，比例为 9.3%，仍达标。
⇒ **精简版本身不用再瘦。**

## A.1 用户拍板（四项全定）

| 问题 | 用户裁定 |
|---|---|
| 整体思路（解耦唤回／快照） | **认可，按此方向查** |

| 「10 轮」计数单位 | **投递精简版的次数**（既能省上下文，又保证语义不漂移） |
| `[降级]` 段每步必变 | **先不管**（属完整版容量问题，动它会牵扯更多面） |
| 完整版新语义 | **人发消息投一遍完整版；其余每隔 10 次精简版投一次完整版** |

## A.2 ★1B 可行性技术判定：**不可行**

用户思路是「把唤回单独作为一项放在下面」。技术判定如下：

### 证据 1 · `dsh-system-prompt` 只提供两个注册 API
从 asar 解出的 `dsh-system-prompt/lib/index.js`（17,387 B）实测导出面：
```
section(section)   // 静态段 → 进 system prompt
context(context)   // 动态面 → 进 runtime-context 快照
```
**没有第三个「独立投递」注册口。**

### 证据 2 · 所有 context 面被拼成【一条】消息
```js
// joinContextSections(sections)
const body = sections.map(s => s.text).join('\n\n');
if (body.length === 0) return '';
return 'Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n' + body;
```
```js
// RuntimeContextProjection.project(current, sections)
if (this.retained?.text === snapshot) return;      // ← 整串比较
return createUserMessage({ content: [{ type:'text', text: snapshot }], ... });  // ← 只创建一条
```
⇒ **context 面在宿主侧没有「各自独立成消息」的路径**。

### 证据 3 · 插件没有独立投递通道
实测插件的 API 面：
- `ctx.get(...)` 拿到的服务：workspaceRegistry / agent / agents / llm / sessionController / sessionQuery / sessions / subagents / tokenMeter
- `ctx.systemPrompt` 只有 `section()` 与 `context()`
- 无 `session.append`（该方法是宿主内部 `this.session.append`，未暴露给插件）
- 插件对 `inbox`（`agent/inbox/spliced`）**零使用**，那是宿主内部的 next-turn / next-step 队列

### 结论
**1B「唤回脱离 context 面、独立投递」在现有宿主 API 下做不到。** 若要实现，必须改宿主（`dsh-agent-loop` / `dsh-system-prompt`），超出插件改动范围。

## A.3 因此的可行收敛（1A + 1C 组合）

| 层 | 动作 | 依据 |
|---|---|---|
| **1C** | 把唤回块**并入快照面**（同一个 context 面内渲染），由插件统一决定该面是否变化 | 推翻 2026-09-15「唤回是独立面」的裁定，需用户在 A.1 之外**追加确认** |
| **1A** | 若保留独立面：唤回内容与上次相同时返回空串 | 只救重复渲染，实测唤回 851/1063 都在变 ⇒ 收益有限 |

**1C 的实质**：唤回不再作为独立面参与拼接，而是被插进快照文本内部。这样「唤回变了」只影响快照面自身，而该面是否重投由插件按新语义（10 次精简 / 真人在场）决定 ⇒ **不对称被彻底消除**。

代价：唤回从「每包必达」变成「受快照注入节奏控制」。需用户确认这是否可接受 —— 因为它改变的是**唤回时效性**，不只是省 token。

## A.4 完整版新语义（待施工）

```
真人在场（人按发送键）  → 完整版（不受门槛限制）
其余所有轮次            → 精简版
累计每满 10 次精简版    → 放行一次完整版
```

对应改动：`fullEverySlims` 3 → 10（或新增键），并确保：
1. 精简计数在**所有返回路径**上语义一致（含 `lib/index.js:15209` 快照未变分支 —— 它当前不调用 `countTieredSlim()`）
2. 末尾兜底不再无条件返回完整版

## A.5 待追加确认（唯一一项）

**是否接受 1C**：把唤回并入快照面，代价是唤回不再「每包必达」，改为受注入节奏控制。

| **1B** | **唤回块脱离 context 面**，改为独立消息投递 | 中 | 需查宿主是否支持独立投递；**最干净** |
| **1C** | 唤回块并入快照面，由插件统一决定重投 | 中高 | **推翻 2026-09-15「唤回是独立面」的既有裁定** |
| **1D** | 插件侧不再依赖宿主去重（删 15209 分支） | 低 | 与既有机制冲突，非治本 |

**建议：1B 优先调查，1A 作兜底。** 理由是只有 1B 能在宿主侧真正解耦唤回与快照；1A 只在唤回内容重复时有救，而数据显示它几乎每次都变。

### 第 2 层 · 修分级判定（病灶 B）

`lib/index.js:15209` 的快照未变分支返回完整版且**不调 countTieredSlim()**。

**注意**：若第 1 层做成（唤回不再污染整串），这条分支的前提「交宿主去重」**重新成立**，它就**变回无害**。
所以第 2 层的正确动作**不是「删掉它」**，而是「第 1 层做完后**验证它是否还有害**」，并确认各返回路径的精简计数语义一致。

### 第 3 层 · 体积与节奏（你真正想要的效果）

- `[降级]` 段每步 100% 变 ⇒ 应改为稳定文本或移出快照
- 铭文 62% 变化率 ⇒ 检查是否含时间性文本

**3b · 节奏改成你要的语义**
当前实测配置：真人在场 → 该 turn 首次即给完整版（不受门槛限制）；无人在场 → 攒够 fullEverySlims = 3 次精简版就放行完整版；snapshotMinGapRounds = 5。
你期望的是「自己跑的时候每隔 10 轮一次完整版」—— 当前是「攒 3 次精简就给」，**比 10 轮激进得多**。

**3c · 精简版比例**

# 附录 B · 最终结论（2026-10-06，用户四项拍板后）

## B.0 一句话结论

**思路方向对，但「唤回独立投递」在现有宿主 API 下做不到；而你的目标并不需要它。**
真正的主因是另一个 bug（`lib/index.js:15209`），修掉它 + 你要的 10 次节奏，即可拿到约 7 倍降幅。

## B.1 为什么「唤回独立投递」做不到（三项硬证据）

**证据 1 · 宿主只提供两个注册口**（从 asar 解出的 `dsh-system-prompt/lib/index.js`，17,387 B）：
```
section(section)   // 静态段 → system prompt
context(context)   // 动态面 → runtime-context 快照
```
没有第三个「独立投递」注册口。

**证据 2 · 所有 context 面被拼成【一条】消息**：
```js
function joinContextSections(sections) {
  const body = sections.map(s => s.text).join('\n\n');
  if (body.length === 0) return '';
  return 'Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n' + body;
}
project(current, sections) {
  if (this.retained?.text === snapshot) return;      // 整串比较
  return createUserMessage({ content: [{ type:'text', text: snapshot }] });   // 只创建一条
}
```
⇒ context 面在宿主侧**没有「各自独立成消息」的路径**。

**证据 3 · 插件没有私有投递通道**：
实际 API 面 = `ctx.systemPrompt.{section,context}` + `ctx.get(...)`（workspaceRegistry/agent/agents/llm/sessionController/sessionQuery/sessions/subagents/tokenMeter）。
`session.append` 是宿主内部方法（`this.session.append`），未暴露；`agent/inbox/spliced` 是宿主内部 next-turn 队列，插件零使用。

**并且**：你要的「唤回单独作为一项放在下面」，**在渲染上已经是这样了** —— 唤回面 order = SECTION_ORDER+1，渲染时排在快照之后，用 `\n\n` 拼接。问题不在「它是不是单独一项」，而在**宿主去重的粒度是「拼接后的整串」**。

## B.2 好消息：你的目标不需要解耦（这才是主因）

`lib/index.js:15209`：
```js
if (stT && stT._snapFp === snap) {
  diag('tiered inject: → 完整版（快照未变·交宿主去重）')
  return snap + engine.renderReflectionRequest()   // 返回【完整版】，且不调 countTieredSlim()
}
```
该分支的**前提**是「返回全文，宿主会去重，零额外投递」——**该前提在唤回面存在时不成立**。后果双重：
1. 返回 38 KB 完整版，但唤回变化 ⇒ 宿主照样投递（本意只想投 3.9 KB 唤回）
2. **不调用 `countTieredSlim()`** ⇒ 精简计数不涨 ⇒ `fullEverySlims` 门槛永不满足 ⇒ 该分支越长越强

**诊断日志实测分支分布**（284 条 verdict）：

| 分支 | 次数 | 占比 |
|---|---|---|
| 完整版（**快照未变·交宿主去重**）← 病灶 | **140** | **50%** |
| 精简版（未获授） | 81 | 29% |
| 精简版（节流） | 15 | 5% |
| 完整版（兜底） | 12 | 4% |
| 完整版（真人在场/攒够精简） | 12 | 4% |

| 精简版（冷启动） | 8 | 3% |
| 完整版（间距已满足/暂缓放行） | 4 | 1% |

**投放端实测**：1,758 次记忆类投递中 **1,731 次是完整版（98.5%）**，精简版仅 21 次。

## B.3 修完后的收益测算（可复算）

| 项 | 当前 | 修复后 |
|---|---|---|
| 完整版投递次数 | 1,731 | ≈ 人发消息轮 149 + 每 10 次精简 ≈ 50 ⇒ **≈ 200** |
| 完整版字节 | 1,731 × 38 KB ≈ 64 MB | 200 × 38 KB ≈ **7.6 MB** |
| 其余投递 | — | ≈ 430 × (1.85 + 3.87) KB ≈ **2.5 MB** |
| **合计** | **≈ 70 MB** | **≈ 10 MB（约 7 倍降幅）** |

※ 精简版与唤回合计 5.7 KB，相对 38 KB 完整版可忽略 ⇒ **不解耦也不亏**。

## B.4 最终施工方案（三项，无需 1C）

**S1 · 修 15209（主因）**
该分支不再返回完整版；改为与其它未获授路径一致：`countTieredSlim()` + 返回精简版。
保留「快照未变」这一事实用于诊断留痕，但不再据此返回完整版。

**S2 · 按用户语义改节奏**
```
真人在场（人按发送键那一轮） → 完整版（不受门槛限制）
其余所有轮次               → 精简版
累计每满 10 次【精简版投递】→ 放行一次完整版
```
- `fullEverySlims`: 3 → **10**
- ★计数口径必须与用户语义一致：**统计「精简版实际投递次数」**，而非当前的 `_slimStep/slimEveryRounds` 二级计数（现口径 10 次 = 30 步，语义不符）
- 末尾兜底（`lib/index.js:15214`）不得再无条件返回完整版

**S3 · 一致性校验（防半修）**
所有返回路径统一收口：任何返回完整版的分支都不得跳过计数；任何返回精简版的分支都必须计数。
（同一语义多处各写一份判据 ⇒ 必须一次改全，本仓踩过该坑）

## B.5 不做的事（用户已裁定）

| 项 | 裁定 | 理由 |
|---|---|---|
| 规则段 18.8 KB 瘦身 | **不做** | 完整版改 10 轮一次后占比不再是问题 |
| `[降级]` 段每步必变 | **不做** | 属完整版容量问题，动它会牵扯更多面 |
| 唤回并入快照面（原 1C） | **不做** | 不解决浪费（合并后投递字节不变），且推翻 2026-09-15 既有裁定 |
