## 一、结论：现版六步计划不能直接开工

用户怀疑成立：此前测绘没有覆盖关键业务状态耦合面，且 R4 中若干「已有能力」实际上没有接线。

最大的三个阻塞风险：

1. **就地更新后，接续完成判定可能永远不变。**
   `handoffMaterialStamp()` 只拼接 PLAN mtime、最新旧账本文件名和事件指纹，不包含账本内容或 revision。原地编辑稳定文件名时，旧会话刷新后可被判为「没有新材料」。
   证据：`lib/index.js:7950-7970`；调用点 `:8034`、`:8068`、`:8078`。

2. **稳定路径不是历史副本。**
   检查点 `sourceRef + revision/digest` 只能发现指针漂移，无法从可变文档恢复旧版本；旧账本的四段也不等于全文。若按现计划清理，会把未证明覆盖的历史变成不可恢复数据。
   当前真实库中，687 篇严格时间戳账本只有 **151 篇**找到规范化全文匹配，**536 篇**没有；151 篇里还有额外节、声明身份不一致、检查点缺失等需要逐条判定的情况。

3. **R4 把跨状态写入、读侧失效和 UI 留在不同阶段，但接续依赖它们同时成立。**
   文档锁只保护 Markdown，共享 `index.json`、事件库、会话内 `latestHandoffText`、面板列表、跨工作区根解析都有独立状态。当前六步没有完整定义事务与失效协议。

## 二、缓存与耦合面：关键遗漏清单

| 耦合点 | 实测结论 | R4 遗漏/风险 |
|---|---|---|
| `state.latestHandoffText` | 水位写入后更新；装配时按 15 秒 TTL 读盘刷新；跨进程写入没有主动失效通道 | 不是永久陈旧，但存在刷新窗口；新文档写入后必须刷新同一状态，不能只改文件 |
| 跨工作区接续 | `buildContinueCarry()`、`handoffMaterialStamp()` 使用 `resolvePathsForSession()`；另有全局账本路径缓存 10 分钟 | 新 `documents/` 路径必须沿被接续会话解析，不能回落到引擎当前工作区 |
| `index.json` | 写入有同 source 替换与 revision 记录；常规 `_loadSidecarIndexPre()` 只用 PLAN revision 判重建 | 新文档若在独立目录，须定义是否入共享索引；不能靠「文件名不变」检测内容变化 |
| 共享 sidecar 锁 | `writeSidecarEntryPre()` 的读—改—写没有与文档更新共用同一事务锁 | 两文档分别更新时，可能互相覆盖索引条目；必须有跨进程负路径 |
| `handoffMaterialStamp()` | 使用 `latestLedgerNamePre()`，该函数只看旧 `handoff-*.md` 文件名 | 原地更新必须改用内容 revision/digest；这是 R4 漏掉的关键耦合 |
| `scanUnarchivedLedgersPre()` | `lib/event-plan.js:65-93` 只扫顶层，不递归；真实调用在 `lib/index.js:8587`、`:8641`、`:10339` | `handoff/documents/` 默认不会进入存量计数与归并；真实扫描器已执行，返回 `total=698 / examined=776 / skippedNonLedger=78` |
| 事件四段 | `event-write.js:696-737` 已解析四段，但检查点正文仍是全文 | 四段非空率不能当全文覆盖证明；R4 必须保留这一区别 |
| 检查点身份 | 生产库没有 `checkpointId`；`event-store.js:976-997` 的载荷白名单也没有该字段 | R4 要求 `eventId + checkpointId` 覆盖证明，必须先定义身份，不可直接复用 |
| `opId` 幂等 | 事件库支持 `opId`，但 `appendHandoffCheckpointPre()` 不向 `eventStorePre.append()` 透传 | 「一次文档更新关联多个事件」需要跨事件幂等协议，否则部分成功与重试不可控 |
| 注入 | `_snapFp/_snapLogFp` 仅做节流；`state.latestHandoffText` 才是账本正文来源 | 新文档进入注入时须同时定义选择、预算、失效与节流，不能只加 RAG chunk |
| 外部变更简报 | `lib/global-brief.js:76-83` 只枚举 handoff 顶层；自写豁免在 `lib/index.js:13564`、`:21563-21589` | 新目录默认不可见；新写入器必须登记自写，避免把本机写入误报为外部变更 |
| 面板列表 | `handoffPanelData()` 只枚举旧文件；`file` 白名单在 `lib/index.js:8892` 只允许旧命名 | 新文档不会出现在现有列表，也不能被打开；legacy 模式在 `lib/index.js:8834-8888` 提前返回 |
| 面板刷新 | 经典 PlanTab 在挂载、`reloadKey`、会话变化时取列表；已打开文件内容没有持续失效 | 「侧边栏入口」不是只写 lister；还需已打开文档的更新契约 |
| 团队基线打包 | `lib/index.js:11810-11842` 只收事件库、PLAN 等既有对象，不递归新目录 | 新维护文档若应随基线迁移，必须显式纳入；否则跨设备接续缺材料 |
| 水位自动账本 | `lib/index.js:6939-6987` 有事件优先、账本兜底与 criteria 降级写入 | R4 的严格缺段拒绝不能直接套到这里，否则紧急接续可能失去最后材料 |
| 既有提示词 | `lib/index.js:447`、`:13524`、`:24490` 明确要求「新开一篇、append-only、不追改」 | 第 1 步必须同步改写，否则实现改完后模型仍被旧指令驱动新建快照 |

另：跨工作区归并扫描模块 `lib/event-regroup-scan.js:33-70` 也只看顶层；但该模块目前没有生产调用，不应把「模块未接线」与「生产已漏读」混报。

## 三、数字复核

### 1. 账本数量与 A 类绑定率

实测：`handoff-*.md` **688 篇 / 2,098,241 B**；严格时间戳名 **687 篇 / 2,095,611 B**；无后缀 686；`-b` 后缀 1；带 `eventId` **21 篇 = 3.0568%**。

结论：688、687、3.06% 可复现；686 是旧的无后缀清单，不能与 688 的字节数混用。

### 2. pre-WAL 523：不成立为覆盖证据

按文件名日期 `< 2026-10-25`：严格时间戳全量 **533 篇**，无后缀旧清单 532 篇。

第一条 handoff 检查点在本地 **2026-10-25 09:51:38**，说明 WAL 不是当天零点启用。其 `sourceRef` 指向秒级文件名 `handoff-20261025-095138.md`，该文件存在 `sourceRef` 但无规范化全文匹配。

因此：523 不是当前严格集合的日界计数；日界也不是精确 WAL 上线时刻；「523 + 163 = 686」只是旧分母恒等式，不能证明任何一篇的内容覆盖。

**最终应使用逐篇规范化全文匹配：687 篇中 151 篇匹配，536 篇不匹配。536 应表述为「无规范化全文匹配，禁止自动删除」，不能夸大为「完全没有任何事件记录」。**

### 3. handoff 四段 92.6%

实测 handoff 检查点 164 条：`goal` 非空 152/164 = **92.68%**；四段全非空 91/164 = **55.49%**；`sourceRef` 为空 141/164 = **85.98%**。

结论：92.6% 的 goal 覆盖率成立，但不能外推为四段齐全率或全文覆盖率。92.6% 也不能支撑 R4-3 的删除条件。

### 4. 相邻账本复用率：原报告口径混杂

本轮统一口径：687 篇严格文件按文件名时间排序，比较相邻两篇，剔除生成 H1、二级标题、注释、空行。

| 口径 | 值 |
|---|---|
| 当前行在前一篇出现的多重集复用率 | **6.557%**（686 对）|
| 唯一行集合 Jaccard 逐对均值 | 3.617% |
| 多重集 bigram Jaccard 逐对均值 | 24.305% |
| 10 分钟相邻对行复用率 | 9.563% |
| 30 分钟 | 7.883% |
| 60 分钟 | 6.829% |

**17.02%、27.59% 未能从被引用脚本按同口径复现**，不能继续与 6.56% 混称同一个「行级 Jaccard」。规划收益只能按文件数、派生索引、重复全文拷贝和稳定骨架计算，不能宣称正文可省 90%。

### 5. 2.6 的 60.1% 零交集

固定快照上复现：200 条 plan/handoff；37 条无 L1 标识；163 条有标识；98/163 = **60.12%** 零交集；31/200 = 15.5% 多事件命中，最大 fanout 24。

**但生产 L1 已有 `evt_xxx` 目标直查**：`lib/event-write.js:206-213`。200 条中 **29 条**包含可直达 active 事件的 `evt` 引用，纯正则集合比较把这些也算成零交集。

结论：60.1% 是该测绘算法的真实输出，但不是「98 条必然新建率」，更不能作为把 0.34 话题门搬到 memory_note 的决策证据。

## 四、六步计划的可执行性

| 步骤 | 判定 | 必须补的内容 |
|---|---|---|
| 1. 协议与写入门 | **需补** | 先定义文档/事件身份、revision 来源、prepared/committed 语义、紧急保底、严格门与警示边界；同步改旧提示词 |
| 2. 显式身份 | **需补** | `documentId/eventIds` 不仅是新参数，还需首建返回身份、跨窗口恢复身份、非法关联拒绝、多事件幂等与部分成功协议 |
| 3. 文档 upsert | **需补** | 锁/CAS/原子写之外，补物理路径白名单、角色门、自写登记、共享索引事务、跨进程真实负路径 |

| 5. RAG/UI 解耦 | **需补** | 覆盖接续、检索、语义下钻、面板 legacy 与 iter5、跨工作区路径、团队基线；维护文档按节入 RAG，旧快照不重复入 |

## 五、发现的缺陷，按严重度排序

1. **接续完成指纹不含原地更新内容**：`lib/index.js:7950-7970`。
2. **稳定 sourceRef 不能恢复被覆盖历史**：`lib/event-write.js:696-737`；R4 §2.2/§3.2 必须补版本恢复语义。
3. **新文档读侧默认不可见**：`lib/index.js:5957-5963`、`:8892`、`:8919-8925`；`lib/event-plan.js:65-93`。
4. **跨进程索引与文档更新不是一个事务**：`lib/index.js:5439-5459`；`lib/shared-state-lock.js:90-137`。
5. **提示词仍强制新建快照**：`lib/index.js:447`、`:13524`、`:24490`。
6. **R4 所需 checkpoint 身份与跨事件幂等未接线**：`lib/event-store.js:976-997`；`lib/event-write.js:696-750`。
7. **新文档不会自动进入现有跨工作区/备份通道**：`lib/index.js:11810-11842`；`lib/global-brief.js:76-83`。
8. **用户可见性只写了目标，没有覆盖 legacy 与打开文档的更新**：`lib/index.js:8834-8888`；`lib/client.js:13940-13971`、`:14118`。

## 六、开工前必须补的清单

1. 先修订 R4 第 1 步，落一份字段级协议：`documentId`、`eventIds`、`revision`、`opId`、检查点身份、prepared/committed、失败补偿。
2. 把 `handoffMaterialStamp()` 改为包含文档 revision/digest，并做「同文件内容更新必须触发完成」的负路径。
3. 明确跨进程锁的粒度：文档、共享索引、事件库的顺序与失败回滚；两文档并发与一事件部分成功都要测。
4. 补齐读侧矩阵：动态注入、scope=all、scope=handoff、语义检索、下钻、legacy/iter5 面板、跨工作区接续、基线打包。
5. 先恢复「上次做了什么」的查询链，再讨论删除；账本只留当前态后，历史回答必须继续由检查点与日志提供。
6. 存量只读审计优先于迁移：151 篇匹配不等于全部可删，536 篇无匹配一律保留。
7. 第 6 步若要物理删除，须先明确恢复来源与真实恢复演练；若环境不允许额外副本，则只停新增、移出普通视图，不删。
8. 以上协议修订完成后，才进入隔离实现；不直接按现六步接管真实数据。
