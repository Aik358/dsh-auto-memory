# 零、用户的核心裁定（**先读这条，它决定了本任务的前提**）


> **交接账本（handoff）应当「仅限于接续使用」，不应该参与 RAG 召回。**
> **它和「项目白板」不应该混为一谈。**
> **交接账本需要单独排期**：减少重写量，**大多数时间应当是「编辑更新」而不是「重写新建」**。

**这是一条设计意图裁定，不是现状描述。**
现状与它相反：实测交接账本的全文**确实进了 RAG 召回语料**（2.7 测绘已量化）。
⇒ 本任务的第一个动作就是**把这处偏差查清**，而不是当成「本来就这样」。

## 1.2 单份账本的结构（四段式）


```
L1   # 交接账本 · 2026-11-09 20:22
L5   ## 任务状态
L12  ## 目标
L17  ## 已试方案与失败原因
L25  ## 进度与下一步
```

**关键观察**：四段的**骨架和大部分内容基本不变**，每次真正变化的往往是「进度与下一步」或「失败原因」的一两条。
**但现在每次 `memory_note(kind=handoff)` 都新建一个完整 33 行文件。**

## 1.3 交接账本确实进了 RAG 召回（与用户裁定相反）


`lib/event-recall.js:45` 的 `textOfEventPre(ev)` **遍历事件全部 checkpoints 并把 `c.text` 原样拼入**：

```js
if (ev && Array.isArray(ev.checkpoints)) {
  for (const c of ev.checkpoints) {
    const t = String((c && c.text) || '').trim()
    if (t) L.push('- [' + String((c && c.kind) || 'log') + '] ' + t)   // ← kind=handoff 的全文也进这里
  }
}
```

2.7 测绘实测：召回语料 1,077,256 字符中，`kind∈{plan,handoff}` 全文贡献 **62.35%**。
⇒ **交接账本（本该只用于接续）被当成了 RAG 语料** —— 这正是需要单独处理的偏差。

## 1.4 相关约束（不要违反）


- PLAN.md 是「事件渲染的投影」，用户面板可见；交接账本**不是**，两者定位不同。
- 白板与账本各有判据门（M1 丢卡门、P-H1 判据、锚点门），改动前必须查清会被波及哪几个门。
- `memory_note(kind=handoff)` 每次写都会走 Phase 1 WAL → Phase 3 补偿（2.6/2.7/2.8 正在处理这一段）。
- 本任务**只出方案，不动代码**。

## 2.1 问题①：能否减少重写新建次数，改为**编辑更新为主**？


必须回答：

1. **现在为什么是新建？** 技术上是因为 append-only 契约，还是仅仅因为实现简单？给代码证据。
2. **改成编辑更新会破坏什么？** 逐个列：
   - append-only 契约（检查点只增不改）—— 账本文件的 append-only 与事件检查点的 append-only **是不是同一个契约**？
   - 锚点（`<!-- memory:mem_* -->`）会不会因编辑而失效/重复？
   - 判据门（M1 / P-H1 / 锚点门）会不会误判？
   - 并发写会不会冲突？（可复用 `lib/shared-state-lock.js` 的 `withSharedStateLock`）
3. **编辑什么、新建什么？** 给出具体建议。
   例如：
   - 同一工作会话内**复用同一份账本**（按「会话」或「工作段」而非「每次写」切分）
   - 只更新「进度与下一步」小节，其余三段保持不变
   - 什么时候**必须**新建（如重大阶段切换、跨天、用户显式要求）
4. **量化收益**：按你的方案，686 份能降到多少？总字节能降多少？**给可复算的估算**。

## 2.2 问题②：能否**以白板中的事件为单位**？

必须回答：

1. **白板与账本现在是什么关系？** 白板是事件渲染的投影（`fromEvents`），账本是独立文件。

2. **具体形态建议**（给 2-3 种，含取舍）：

   - 形态 C：账本不再是文件，改为事件库的一个视图（完全派生）

3. **每种形态**：

   - 与现有的「接续」用法（`memory_recall(scope=handoff)` 读什么？）的关系

4. **关键追问**：如果账本按事件组织，那**「跨事件的接续信息」放哪**？
