## §1 用户的完整设计意图（逐字，这是需求原文）

### 1.1 核心机制：**用「拒绝 + 回执指导」替代「长提示词」**

```
现状（用户不满）：  长提示词 → 模型读 → 模型可能忘/可能不做 → 工具静默接受 → 数据是坏的
用户要的：          工具校验 → 不合格就【拒绝 + 告诉模型该做什么】 → 模型改正
                    合格就【接受 + 提示下一步该考虑什么】
```

**用户的理由**：过多提示词会导致**效率下降 + 上下文占用提升**。所以正确做法是：
> 「如果要保持提示词比较简练，应当在**调用工具之后**进行返回」

### 1.2 用户给的四个具体回执场景（**逐字**）

| # | 用户原话 | 场景 |
|---|---|---|
| 1 | 「我写完了账本，是不是应该考虑一下相关的事件？」 | `memory_note(kind=handoff)` 之后 |
| 2 | 「或者我加了事件，是不是应该考虑加账本？」 | `memory_event(create)` 之后 |
| 3 | 「我事件结束之后，是不是应该再过一遍其他的事件？」 | `memory_event(close)` 之后 |
| 4 | 「我写了 memory log，是不是应当考虑一下交接白板和最近的事件？」 | `memory_log` 之后 |

### 1.3 用户要开始做的三个功能（这是产品需求，不是 bug 修复）

**功能 1：事件展示与下钻（Timeline）**
> 「MemoryGuard 可以直接列出模型最近做的事情（包括大事件和小事件）。主要是可以先选大事件，比如用 **Memory Timeline 列出最近时间线的大事件**，然后可以再通过 Memory Timeline、Blackboard 等相关内容，**查看每个大事件里的小事件**。」

**功能 2：智能提醒与写入**
> 「如果某个事情记了有实质性变化，系统可以提醒模型看看有没有**共同记忆、共同共识或者作者情感**，评估是否可以写入。」

**功能 3：智能推荐（猜你想用）**
> 「对于比较重要、可以写入 **Calendar** 的事情，系统不仅要在提示词里提醒我，还要**在调用完工具以后，智能推荐『猜你想用』**。」

### 2.5 事实 E：**校验强度存在严重「不对称」——这是最有力的证据**

**但 `memory_note(kind=handoff)` / `memory_event(append)` 的 8 个拒绝分支全是技术性的**：

#### 为什么这个不对称是决定性的

```

```

**同一个代码库里，有的工具会拒绝坏数据，有的不会 —— 这不是能力问题，是「没有统一设计」。**

**请调查**：
1. `memory_user` 的复读防护/预算拒绝是什么时候加的？为什么没推广到账本/事件？
2. 是否存在统一的「记忆写入质量基线」（所有写入工具都该满足的最小标准）？如果没有，请设计一个。
