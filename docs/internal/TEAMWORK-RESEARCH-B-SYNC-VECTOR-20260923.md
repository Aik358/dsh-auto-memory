## 0. 结论速览（TL;DR）

**一句话回答产品负责人：实时同步对向量编码不难，难的是冲突与一致性；而"实时"这个词对向量本身也不必要求到实时。**

四条主结论：

1. **嵌入计算的成本在本项目的真实数据规模上可以忽略。** 按本仓实测吞吐外推，10 万条记忆本地全量重编码约 **37 分钟**（一次性、可后台）；走云 API 约 **0.4 美元**（详见 §1.1）。"重编码贵"在本项目量级上**不成立**。
2. **真正的瓶颈是冲突与一致性，不是嵌入计算。** 嵌入是无状态纯函数（可重放、可幂等、可并行）；而"谁赢、怎么合并、删除算什么"是有状态分布式问题（不可重放、有顺序依赖）。见 §1.6 判据。
3. **业界事实标准已经是"两阶段"：写立即可见（词法）+ 秒~分钟级向量补齐。** 本仓自己就已经是这个形态（JS 档语义不可用时退化为词法兜底）。见 §2.6 判据。
4. **本仓已有的两个语义可以直接升格为同步原语**：`status ∈ {current, superseded, retracted}` 的**单调性**（§3.2.1），以及 `migrate()` 的**两阶段提交 + fail toward duplication**（§3.2.2）。这是本项目做团队版最大的现成资产。

**对 Q4 的推荐**：**候选 B（权威服务端 + 事件日志）为主线**，候选 A（对象存储快照）作为落地第一步与降级路径，候选 C（CRDT 本地优先）**暂不采用**——原因见 §4.4。

**"实时同步"在架构里应落到这些具体指标**（§4.5）：

| 环节 | 目标 | 是否可异步 |
| --- | --- | --- |
| 记忆文本 + 状态标记可见 | **≤ 5 秒**（p95） | 否（这是"实时"的真正含义） |
| 词法（倒排）检索可用 | **≤ 5 秒**，与文本同时 | 否 |
| 向量检索可用 | **≤ 5 分钟**（p95） | **是**（可异步补齐） |
| 换嵌入模型/维度 | **小时级**，计划内窗口 | 是 |
| 跨端全量重建 | 小时级 | 是 |

## 1. Q1：实时同步对向量编码到底难在哪？

### 1.1 嵌入是文本的函数 ⇒ 增量 embedding 与全量重建的成本模型

**基本关系**：`vector = f(text, model, chunker)`。文本、模型、切块策略三者任一变化，该向量即失效。

**成本公式**：

```
增量重算成本   C_inc  = N_dirty × k̄ × L̄ × c
全量重建成本   C_full = N_total × k̄ × L̄ × c  +  I_rebuild
写入放大系数   A      = C_inc / C_写一条
```

其中 `N_dirty` = 脏条目数，`k̄` = 平均 chunk 数/条，`L̄` = 平均 token 数/chunk，`c` = 单位 token 的编码成本（本地为时延，云为费用），`I_rebuild` = 索引重建开销。

**本仓实测基线**（`docs/M7-EMBEDDING-BENCHMARK.md`）：

| 实测项 | 数值 | 来源 |
| --- | --- | --- |
| 语料编码吞吐（bge-m3，CPU 16 线程） | **41–48 chunks/s** | `docs/M7-EMBEDDING-BENCHMARK.md:66` |
| 全量 163 chunk 耗时 | ≈ 4 s | 同上 |
| 模型加载时间 | bge-m3 **2.8 s** / qwen3 1.1 s / e5 3.2 s | `docs/M7-EMBEDDING-BENCHMARK.md:65` |
| 峰值内存 RSS | bge-m3 **2.05–2.21 GB** | `docs/M7-EMBEDDING-BENCHMARK.md:58-60` |
| 索引体积 | **4.0–4.2 MB / 千 chunk** | `docs/M7-EMBEDDING-BENCHMARK.md:58-63` |
| 1 万 chunk 索引 ≈ 40 MB；10 万 chunk ≈ 400 MB | float32 × 1024d | `docs/M7-EMBEDDING-BENCHMARK.md:140` |

**代入推算**（假设 `k̄ = 1`，即一条记忆 ≈ 一个 chunk；再假设 `L̄ = 200` tokens/条）：

| 规模 | 本地全量重编码 | 索引体积 | 云 API 全量重编码（3-small @ $0.02/1M tokens） |
| --- | --- | --- | --- |
| 1 万条 | 10 000 ÷ 45 ≈ **222 s ≈ 3.7 分钟** | ≈ 40 MB | 2 M tokens ≈ **$0.04** |
| 10 万条 | 100 000 ÷ 45 ≈ **2 222 s ≈ 37 分钟** | ≈ 400 MB | 20 M tokens ≈ **$0.40** |

> 【推断】上表按 `41–48 chunks/s` 线性外推。**该基准只实测了 163 个 chunk**（`docs/M7-EMBEDDING-BENCHMARK.md:66`），外推到 10 万 chunk 未经验证。真实曲线受内存带宽、批大小、模型加载摊销影响，可能偏离。**在上团队版之前应先做一次 10 万条规模的实测**。
>
> 【推断】`L̄ = 200 tokens/条` 为估算值（中文约 1 token ≈ 1.5 汉字，加元数据），**非实测**。
>
> 【待核实】`$0.02 / 1M tokens` 是 OpenAI `text-embedding-3-small` 的公开标价，本次调研**未能打开官方定价页**（`https://developers.openai.com/api/docs/models/text-embedding-3-small` 返回 **HTTP 403**）。价格请以 [官方定价页](https://developers.openai.com/api/docs/models/text-embedding-3-small) 或 [OpenRouter 条目](https://openrouter.ai/openai/text-embedding-3-small) 二次核实后再用于预算。

**这一节的关键判断**：全量重建在本项目量级上是 **分钟级 × 角元级**，不是"很贵"。所以"实时同步会不会让向量编码变得困难"——**在成本维度上不成立**。

### 1.2 模型版本漂移：新旧向量不可比

**机制**：不同嵌入模型把文本映到**不同的向量空间**。跨空间的 cosine 相似度**没有语义**——不是"精度下降"，是"数值无意义"。维度不同（1024 vs 768 vs 1536）时，连放进同一个集合都不可能。

**结论**：
- **必须整库重建**，没有"部分迁移"这种选项。
- **双写过渡可行，但要付代价**，工程手段有两种：
  1. **多向量字段（named vectors）**：同一 point 存 `v1`（旧模型）与 `v2`（新模型），检索按字段选。代价：存储 + 编码成本翻倍。
  2. **集合版本 + 别名切换**：新建 `mem_v2` 集合灌满后再把读写别名切过去，旧集合保留一个回滚窗口。这是业界常见做法。代价：切换期需要双写或短暂停写。
- 【待拍板】本项目选哪种，取决于能否接受一个"检索质量可能短暂回退"的窗口。

**本仓的实证支持——换模型是真实会发生的**：M7 基准中 `multilingual-e5-large` 被**淘汰**：修正 doc 前缀 bug 后 R@5 仍只有 0.727、跨语言仅 0.60（20 条 zh↔en 查询错 8 条），而同场的 bge-m3 是 R@5=0.989、跨语 20/20 全中（`docs/M7-EMBEDDING-BENCHMARK.md:70-78`）。**一次选型淘汰 = 一次整库重建**。团队版若各成员模型版本不一致，检索结果会不可比。

**建议**：向量条目必须自带 `{ model, modelRevision, dim, chunkerVersion }` 四个 provenance 字段，**服务端在检索时强制按这四项过滤**，而非假设"大家的向量都一样"。本仓 M7 基线的做法可参照：模型 pin 到 revision 前 12 位（`docs/M7-EMBEDDING-BENCHMARK.md:20-22`）。

### 1.3 分块（chunking）策略变更 ⇒ 向量 id 全变

**机制**：chunk 边界一变，切出来的**文本片段就变了**，于是以内容哈希为 id 的向量 **id 全部失效**——即使原始记忆一个字都没改。

**本仓实证**：M7 基准比较了三种策略（`docs/M7-EMBEDDING-BENCHMARK.md:56-63, 79-82`）：

| 策略 | R@5（bge-m3） | chunk 数 |
| --- | --- | --- |
| fixed-256 | **0.989** | 163 |
| para-512 | 0.966 | 154 |
| fixed-1024 | 0.955 | 154 |

结论是"小 chunk 稳定占优，1024 最差"（`:79`）。**若日后从 fixed-512 切到 fixed-256，chunk 数从 154 变 163、且每个 chunk 的边界几乎全变** ⇒ 全部向量 id 失效。

**连锁影响的完整链条**（这是本节要强调的部分）：

```
chunker 版本变更
  → chunk 边界变
  → 向量 id 全变（若 id = hash(chunkText)）
  → 旧 id 必须全删、新 id 全量 upsert（一次全量写，不是增量）
  → 指向 chunk 的所有外部引用同时失效：
       · 倒排索引里的 chunk 位置
       · 图关系（本仓白板/锚点 handoff-anchor.js）里的锚点
       · 证据链（本仓 evidence-store.js）里的引用
  → 检索质量短暂不可用（新老混杂期）
```

**规避设计（建议，属【推断】的工程做法）**：向量 id **不要**只用 `hash(chunkText)`，改为：

```
vectorId = hash(memoryId + "|" + chunkerVersion + "|" + chunkIndex)
```

并把 `chunkerVersion` 同时写进 payload。这样：
- 换 chunker 时新老向量**可以共存**（id 空间不撞），支持灰度与别名切换；
- 需要清理时按 payload 过滤删除（Qdrant / Milvus / pgvector 都支持按 filter 删）。

代价：同一记忆的同一段文字会在不同版本下重复存储，**存储放大 ~2×**（仅切换期）。【待拍板】

### 1.4 写入放大：一条记忆改动触发多少下游重算

**量化模型**：

```
A = 1（向量） + 1（倒排） + K（图边） + 1（摘要） + 1（miv 级联）
```

**本仓已经踩过这个坑，并且已经修过——这是最有价值的现成证据**：

`lib/hub-io.js:98-106` 的注释原文：

> ★#110（2026-09-22）：**批内合并落盘**（消除写放大）。
> 背景：hub 一次喂数会连续写**同一份快照 N 次**（每行判据 upsert 一次 ⇒ 一次整份写盘）。
> 做法：批内只记「最后一次的整份数据」，批末统一原子落盘。

**即：一次喂数产生 N 次整份写盘**——这就是写入放大的真实案例。本仓的解法是**批内合并（micro-batch）**，机制实现在 `lib/hub-io.js:114-122`（`flushPendingPre`）与 `:171-179`（`beginBatch` / `endBatch` / `flushBatch`）。

**更强的一处级联：miv**。`lib/state-commit.js:104-126` 的 `memoryIndexVersionPre()`：

- 输入是**全部** records + boardCards 的 `(id, status, contentDigest)` 元组列表（`:109-122`）；
- 按 id 排序后拼成 canonical 串再 sha256（`:123-125`）；
- 输出 `idx_pre_ + 32 hex`（`:125`）。

**含义：任意一条记忆的内容变化，miv 必变。** miv 是"同一份快照"的**身份判定**（`:80-89` 注释），所以 miv 一变，**所有以 miv 为键的缓存/去重/跳过逻辑全部失效**，下一轮走冷路径。这是一个**单条改动 → 整库级影响面**的级联。

> 【推断】团队版里 miv 的级联效应会被放大：N 个成员各自的写入都会推高全库 miv 变更频率，若检索缓存以 miv 为键，命中率会随团队规模下降。**建议在团队版把 miv 的粒度从"全库"下沉到"分片"（按 workspaceRef 或成员分片各算一个 miv）**——但这需要改 `memoryIndexVersionPre` 的语义，属设计变更，**未经拍板不要动**。

**写入放大的抑制手段（按性价比排序）**：

1. **micro-batch 合并**（本仓已有，`lib/hub-io.js:98-122`）—— 把同一批内的 N 次写压成 1 次。
2. **脏标记 + 队列重算** —— 只重算真正变了的条目（§2.1）。
3. **语义去重**（§2.2）—— 从源头减少"需要编码的新文本"。
4. **内容哈希短路** —— `contentDigest` 未变则跳过重编码。本仓已具备该字段（`lib/state-commit.js:114`）。

### 1.5 设备侧算力：本地小模型 vs 云 API

| 维度 | 本地（bge-m3，本仓实测） | 云 API（如 DashScope / OpenAI） |
| --- | --- | --- |
| 单次编码时延 | 吞吐 41–48 chunks/s ⇒ 单 chunk ≈ **21–24 ms** | 单次调用 **~100 ms–2 s**（含网络 RTT，与批量大小相关） |
| 模型冷启动 | **2.8 s** 加载 + **2.2 GB** RSS 常驻 | 无（服务端） |
| 边际成本 | **0**（只用本机 CPU/GPU） | 按 token 计费（10 万条 ≈ $0.4，见 §1.1） |
| 隐私 | **数据不出本机** | 记忆内容出本机 ⇒ 团队敏感信息风险 |
| 失败模式 | 内存不足、模型文件损坏 | 限流、网络抖动、密钥失效 |
| 离线可用 | **是** | 否 |

**关键判断**：本地模型的痛点**不是单 chunk 时延**（21–24 ms 很快），而是 **2.2 GB 常驻内存 + 2.8 s 冷启动**。对交互式场景，这个内存代价比时延更痛。云 API 的痛点则是**隐私与可用性**，不是钱。

**对本仓的直接含义**：本仓 JS 档已经承认了这条退化路径——语义检索生效需同时满足模型资产与 peer 依赖两项，**缺任一即退化为词法兜底**（用户级规则，对应 `lib/*` 的语义引擎开关语义）。团队版应把"词法兜底"从**异常路径**提升为**设计内的一等公民**（§2.5）。

### 1.6 ★ 判据：实时同步的真实瓶颈是"嵌入计算"还是"冲突与一致性"？

**判据：瓶颈是「冲突与一致性」，不是「嵌入计算」。** 三条理由：

1. **嵌入计算是无状态纯函数**：`f(text, model, chunker)` 不依赖任何其他条目的状态 ⇒ 可重放、可幂等、可并行、可任意重试。这类计算**天生适合异步与批处理**。
2. **成本量级不构成约束**：10 万条 ≈ 37 分钟（本地一次性）或 ≈ $0.4（云）——见 §1.1。这是**后台任务**的成本，不是用户可感知的延迟。
3. **而"谁赢"是有状态问题**：并发写入的合并顺序、删除语义、成员权限、离线重连——这些**不可重放、有顺序依赖、且错了会静默丢数据**。§3 的冲突表显示，真正的风险全在这里。

**推论（对产品负责人疑问的直接回答）**：
- "实时同步会不会对向量编码有点困难？" → **不会**。向量编码可以完全异步化，不影响"实时"。
- 真正需要"实时"的是**文本与状态标记的可见性**；向量可以**秒~分钟级**补齐（§2.6）。

## 2. Q2：业界怎么做增量/近实时向量同步

### 2.1 工程模式一览

| 模式 | 做法 | 代价 | 适用 |
| --- | --- | --- | --- |
| **脏标记（dirty flag）** | 条目落盘时打 `needsEmbed=true`，后台扫描重算 | 需要一个可靠的扫描触发器 | 单机、小规模 |
| **队列重算** | 写入事件进队列，worker 消费后编码 | 需要队列基础设施 | 团队版 |
| **micro-batch 合并** | 攒 N 条 / T 毫秒后一次批量编码 | 引入延迟（可调） | **推荐**，与队列天然搭配 |
| **内容哈希短路** | `contentDigest` 未变则跳过 | 无 | **必做**，本仓已有该字段 |

**micro-batch 的必要性有本仓实证**：`lib/hub-io.js:99` 明确记录"一次喂数会连续写同一份快照 N 次"，解法就是批内合并（`:98-122`）。同一逻辑平移到编码侧即"批内只编码一次"。

**CDC → 嵌入管线的通用形态**（外部来源）：
- [Streaming CDC Events to Vector Databases for Real-Time AI](https://streamkap.com/resources-and-guides/streaming-to-vector-databases)
- [Building a Real-Time Embedding Pipeline with CDC and Vector Stores](https://streamkap.com/resources-and-guides/streaming-embeddings-pipeline)

两条来源描述的是同一套主流架构：**源库变更 → CDC 捕获 → 消息队列 → 嵌入 worker → 向量库 upsert**。这与本仓"文件为真源"的形态不同，本仓需要的等价物是**文件 mtime/内容哈希 → 事件化 → 队列 → 编码**（属【推断】的移植方案）。

### 2.2 语义去重与合并：从源头避免重复编码

三个层次的去重手段，成本递增：

| 层次 | 手段 | 成本 | 效果 |
| --- | --- | --- | --- |
| 精确 | **内容哈希**（本仓 `contentDigest`，`lib/state-commit.js:114`） | ~0 | 完全相同才命中 |
| 近似-文本 | **simhash / MinHash** | 低（纯 CPU） | 近重复文本 |
| 近似-语义 | **向量近邻 + cosine 阈值** | 需先编码（但不需再编码第二条） | 语义重复 |

**向量近邻去重的正确做法**（关键是"先查后写"，而不是"写完再删"）：

```
新记忆到达
  → query 向量库 top-1（用临时向量或已缓存向量）
  → 若 cosine ≥ θ  → 判定为重复：只更新元数据/证据计数，不新增向量
  → 若 cosine < θ  → 编码并 upsert
```

**阈值 θ 怎么定**：这是一个**需要标定的参数，不能拍脑袋**。可参考向量库厂商给出的近重复判定阈值指引（[Zilliz Cloud · 向量近似去重](https://docs.zilliz.com.cn/docs/vector-similarity-dedup)），以及文本去重的学术综述（[A Survey of Text Deduplication: From Syntactic Matching to Semantic Understanding](https://ieeexplore.ieee.org/abstract/document/11366861)）。

> 【推断】团队版场景下 θ 的建议起点是 **0.90–0.95**，但必须用本仓真实记忆语料标定：过高会漏合并、过低会把"同主题不同结论"的记忆错误合并——**后者是数据损坏，比漏合并危险得多**。本仓已有 hard-negative 判别基准可复用（`docs/M7-EMBEDDING-BENCHMARK.md:56-63` 的 `hard-neg err` 列，bge-m3 0.111 / qwen3 0.074）。**建议：θ 的确定必须先跑一次本仓语料标定实验，不得直接采用外部默认值。**

**用 LLM 判断是否合并**：成本最高（一次 LLM 调用/候选对），只在"向量判定为灰区"时使用（θ 下界 < cosine < θ 上界）——这是【推断】的两段式做法，业界常见但本次未找到权威来源直接背书。

### 2.3 向量库的 upsert/delete 与一致性语义

**核心事实：主流向量库默认都是"最终一致"，写入返回成功 ≠ 立即可检索。**

| 向量库 | upsert 语义 | 一致性模型 | 关键点 |
| --- | --- | --- | --- |
| **Qdrant** | `PUT /collections/{c}/points`（按 id upsert，覆盖语义） | **默认异步索引**；写入返回时可能尚未建入 HNSW | 支持 `wait=true` 等待可检索；官方 Points 文档：[qdrant/docs · points.md](https://github.com/qdrant/docs/blob/master/qdrant/v0.3.x/points.md)、[Updating Data](https://qdrant.tech/documentation/edge/edge-api/updating-data/) |
| **Milvus** | `upsert` = delete + insert（**不是原地更新**） | 提供 4 档：Strong / Bounded Staleness / Session / Eventually（默认 Bounded Staleness） | 官方：[Milvus 一致性级别](https://milvus.io/docs/zh/v2.6.x/consistency.md)、[ConsistencyLevel API](https://milvus.io/api-reference/cpp/v2.6.x/Collections/ConsistencyLevel.md) |
| **Weaviate** | PUT/PATCH 对象，HNSW 异步建索引 | 支持**异步复制**（async replication），副本间最终一致 | 官方：[Async Replication](https://docs.weaviate.io/deploy/configuration/async-rep) |
| **pgvector** | 标准 SQL `INSERT ... ON CONFLICT DO UPDATE` | **强一致**（事务） | 但 HNSW 索引维护是插入路径的一部分：需要足够的 `maintenance_work_mem`（默认 64MB 对大索引不足），且需 `VACUUM`/索引重建处理更新残留 |
| **LanceDB** | Lance 列式格式上的 upsert/delete | 基于对象存储，写后需 compaction | 本次未获取到权威一致性文档，**标注为未验证** |

**pgvector 的索引细节来源**：[pgvector 生产实践参考](https://github.com/damusix/skills/blob/main/postgres/references/94-pgvector.md)、[pgvector vs VectorChord 基准](https://edb.prod.acquia-sites.com/sites/default/files/2026-06/pgvector_vs_VectorChord_benchmarks.pdf)

**Qdrant 删除注意**：按 filter 删除是**延迟执行**的（[qdrant PR #8389 · Delete points by filter with deferred](https://github.com/qdrant/qdrant/pull/8389)）；基于 filter 的 update 需要先解析成 point ids 再写 WAL（[qdrant PR #9678](https://github.com/qdrant/qdrant/pull/9678)）。**含义：删除/批量更新的可见性有额外延迟，架构上不能假设"删了就查不到"。**

**对本仓的直接含义**：既然连专业向量库都不保证"写即可见"，那么在团队版里要求"向量检索实时"**在工程上是逆流的**——正确的做法是承认 eventual consistency 并设计降级（§2.5）。

### 2.4 CDC（变更数据捕获）→ 嵌入管线

标准形态（见 §2.1 两条来源）：`源变更 → CDC → 队列 → worker → 向量库`。

**对本仓的映射**（【推断】，因为本仓真源是文件而非数据库）：

| CDC 概念 | 本仓对应物 | 证据 |
| --- | --- | --- |
| 变更日志 | hub 的事件日志 / 每日日志 append-only 文件 | 本仓日志为 append-only 语义 |
| 变更记录 | `contentDigest` 变化 | `lib/state-commit.js:114` |
| 提交边界 | `buildStateCommitPre` 的 txId / actor / writes | `lib/state-commit.js:153-196` |
| 幂等键 | `txId` | `lib/state-commit.js:163` |

**关键洞察**：本仓的 `state-commit.js` 已经定义了**提交单据**的完整形状——`{workspaceKey, boardId, txId, actor, writes, stateChanges}`（`:179-191`）。这就是一个**现成的变更事件结构**，可以直接作为 CDC 事件的载荷。**这是本仓做团队版最大的结构性红利之一**。

### 2.5 ★ 两阶段模式：先写文本（立即可见）→ 后台补向量（延迟可见）

**业界谁这么做**（外部来源）：
- 代码搜索领域是典型：Sourcegraph 明确区分**词法/符号搜索**与**语义搜索**两条路径（[Sourcegraph symbol search](https://sourcegraph.com/docs/code-search/types/symbol)）。代码检索的语义索引天然滞后于词法索引。
- 索引增量更新：GitHub Copilot 的代码索引采用**自适应/增量索引**策略（[Adaptive indexing · Copilot Workspace 分析](https://qu3ry.net/articles/adaptive-indexing-github-copilot-workspace.pdf)），而非每次全量重建。
- 向量库侧的一致性问题正是这一模式存在的理由（§2.3 的表）。

> 【推断】本次调研**未能找到**一篇明确写出"text-first, embed-later"这一命名的权威厂商文档。上述证据表明该形态在工程实践中普遍存在（词法/语义双路径、异步索引），但"业界事实标准"这一措辞属**基于多方证据的归纳**，而非某份文档的原话。

**本仓其实已经是这个形态**——这是本节最重要的本仓证据：

- JS 档语义检索生效需**同时**满足两项条件（模型资产落于 `~/.dsh/models/js-semantic`，且 peer 依赖装在 dsh profile 目录），**缺任一即退化为词法兜底**（用户级规则，对应本仓语义引擎的开关语义）。
- 即：**本仓早已实现了"语义不可用时退到词法"的降级路径**，只是当前把它当作**异常兜底**，而非**设计内的正常运行态**。

**架构上要做的改动（很小）**：把"词法兜底"从异常路径改为一等公民的**首屏路径**——写入后先让词法索引立即可查，向量由后台补齐。本仓 `lib/degrade.js`（18 336 B）已有降级机制的骨架。

### 2.6 ★ 判据：是不是根本不必"实时"？

**判据：不必。业界事实上就是「写立即可见（词法）+ 秒~分钟级向量补齐」。**

三条支撑：

1. **向量库自己都不保证写即可见**（§2.3）：Qdrant 默认异步索引、Milvus 默认 Bounded Staleness、Weaviate HNSW 异步。**要"向量实时"就得主动开 `wait=true` / `Strong`**，那是用写入吞吐换一致性——团队版多成员并发写时这个交换不划算。
2. **降级路径已经存在且可用**：本仓词法兜底是成熟实现（§2.5）。
3. **用户体验上，语义检索的延迟不可感知**：用户问"我之前存的关于 X 的记录"，词法先给出结果已满足 80% 需求；向量补上后检索质量提升，但**没有用户会盯着秒表等向量索引**。

**因此，"实时同步"的合理定义应重写为**（§4.5 会给出具体指标）：

> **实时 = 记忆文本与状态标记的跨端可见延迟 ≤ 5 秒；向量检索为尽力而为的最终一致，目标 ≤ 5 分钟。**

## 3. Q3：多端记忆同步的冲突与一致性

### 3.1 CRDT vs OT vs 服务端权威：本数据模型该选哪个

**先明确数据模型**（这是选型的前提）：

```
记忆条目 = {
  文本内容（append-only 的日志行 / 备注段）
  元数据（tags, importance, 时间戳, addedBy, scope, workspaceRef）
  状态标记（status ∈ {current, superseded, retracted}，单调追加）
}
```

**三方案对比**：

| 方案 | 适合的数据 | 对本模型的问题 |
| --- | --- | --- |
| **OT**（Operational Transform） | 字符级并发的**单篇长文档**协同编辑（Google Docs 类） | **不适合**。OT 需要一个中心的、有顺序的转换服务器；且本模型是"多条目集合"而非"单篇文档"，条目间无字符级交错。引入 OT 属于用重武器打小目标。 |
| **CRDT** | 无中心、需离线、并发写同一结构的场景 | **部分适用**，但**不能无脑用**（见下） |
| **服务端权威** | 成员数中等、可接受联网、需强审计 | **适合**，且与 §4 的候选 B 天然吻合 |

**CRDT 在本模型下的具体用法、代价与坑**（按要求，不讲空话）：

**该用哪些 CRDT 构件**：

| 字段 | 合适的 CRDT | 理由 |
| --- | --- | --- |
| `status ∈ {current, superseded, retracted}` | **单调集合 / grow-only set**（或 LWW-Register 但**优先级固定**） | 状态**只追加不回退**，天然单调 |
| `addedBy`、创建时间 | **不可变字段**（写入即定） | 无冲突可能 |
| `tags`、`importance` | **LWW-Register（每字段一个时间戳）** | 简单，但**会静默丢并发写** |
| 文本正文 | **不建议用 CRDT 文本（RGA/YATA）** | 见下"坑"第 1 条 |

**三个必须知道的坑**：

1. **LWW 会静默丢弃并发写** —— 这是 CRDT 最常见的误用后果。业界手册明确记录：[Last-writer-wins silently drops concurrent writes](https://raw.githubusercontent.com/handbook-academy/engineering-handbook/refs/heads/main/hld/part-3-distributed-systems-theory/05-crdts.md)。对记忆系统而言，**静默丢一条记忆是不可接受的**——这正好与本仓"fail toward duplication, never toward loss"的原则（`lib/hub-io.js:395`）冲突。若用 LWW，必须**同时保留被丢弃的版本**（即 LWW 选择"显示哪个"，但不删另一个）。
2. **文本 CRDT（RGA/YATA）的元数据开销**：每个字符带一个唯一 id，内存与存储放大**数倍**。对本仓这种"条目级追加"的模型，用字符级 CRDT 是**严重的过度设计**。
3. **CRDT 不解决权限与审计**：CRDT 让所有副本收敛，但"谁能写哪条"是**授权问题**，CRDT 层管不了，必须另做。

**本仓的实证支持——用户已经做过一次相关裁定了**：本仓 procedure 双库的存储方案在 2026-09-23 由用户改判为**物理分文件**，理由是"**单文件在团队同步时整个文件都落在冲突面上**"（既往会话记忆，对应本仓 `lib/hub-io.js:220-245` 的双库设计）。这条裁定本身就是**冲突面最小化**的设计原则——**团队版应沿用这个原则：按归属分片，让冲突面尽可能小，而不是靠 CRDT 去自动化解大规模冲突**。

> 【待拍板】最终选型建议见 §4.4。本节的结论是：**CRDT 的"收敛能力"对本模型是过剩的，真正需要的是"冲突面分片 + 单调状态 + 两阶段提交"**（后两者本仓已有）。

### 3.2 ★ 本仓已有的两个语义能不能直接当同步原语？

**答案：能，而且是本仓最有价值的现成资产。**以下逐条读代码求证。

#### 3.2.1 `status ∈ {current, superseded, retracted}`：只追加状态、不物理删除

**代码证据**：

- 定义：`lib/state-commit.js:38`
  ```js
  export const MEMORY_STATUS_PRE = Object.freeze(['current', 'superseded', 'retracted'])
  ```
- 同处还有另两套状态的定义，且**注释明确要求三者不得互转**（`lib/state-commit.js:33-40`）：`TASK_STATE_PRE = ['open','done','passed']`、`ARCHIVE_STATE_PRE = ['active','archived']`。
- 该状态**进入 miv 摘要**：`lib/state-commit.js:113` 取 `status` 参与 canonical 串构造，因此"状态变了 miv 必变"（`:84-85` 注释）。

**为什么这是同步原语**：

1. **单调性 ⇒ 天然可交换、可重放、幂等。** `current → superseded` 是单向的；两个成员并发地把同一条标为 `superseded`，结果**相同**（幂等）。这消除了绝大多数合并冲突。
2. **不物理删除 ⇒ 不会出现"丢了就找不回"。** 冲突的后果退化为"状态标记取哪个值"，而不是"数据没了"。
3. **与 `supersedes` / `retract` 的既有语义对齐**：本仓规定 `superseded` 的可见后果是**「返回但标记」**（不剔除、不降权），且必须指出最新结论在哪（`supersededBy` 指针）——这是**用户明确裁定**过的（用户级规则）。**团队版应原样继承**：这正是分布式系统里"保留冲突痕迹、由消费者裁决"的正确做法。
4. **「标错即回退」有现成通道**：本仓 `memory_note` 提供 `restore=` 用于把标错的 `superseded`/`retracted` 状态改回 `current`（即**移除状态行**）。团队版需要一个等价的成员级 restore，且**必须留痕**（谁在何时撤销了什么）。

> 【推断】把该状态用于跨端同步时，需要一个**状态变更的偏序**（谁先谁后）。`lib/state-commit.js:242` 的 `at: Date.now()` 是**本地时钟**，在跨设备场景下**不可靠**（时钟漂移）。团队版建议引入**逻辑时钟（Lamport / 版本向量）**替代或补充 `at`——但注意本仓 `at` 的既有语义不要改动（`:242` 属回执字段，未参与 miv 构造），可以在其上**新增**字段而非替换。

#### 3.2.2 两阶段迁移：先写接收库 → 读回校验 → 写捐赠库 → 读回校验，失败两库整体回滚

**代码证据**（`lib/hub-io.js`，实现体 `migrate()` 在 `:403-535`）：

- **设计动机（原文注释）**，`lib/hub-io.js:390-398`：
  > 为什么必须两阶段：跨文件移动**不是原子的**。写目标成功、删源失败 ⇒ 条目复制成两份；
  > 反序则更糟——删源成功、写目标失败 ⇒ **条目直接消失**。故这里定死两条：
  > ① **先写接收库、后写捐赠库**——失败时最坏是「多留一份」而非「丢一份」，
  > 即 **fail toward duplication, never toward loss**（可见、可重试、可人工清理）。
  > ② 每写一步就**读回校验**，不是写完就当成功（写盘函数的返回不等于内容真落对）。
  > 任一步校验不过：把两库恢复到**迁移前快照**，并如实返回 rolledBack。
- **回滚凭据**：迁移前对两库各取一份解析快照（`lib/hub-io.js:412-418`）。
- **两阶段提交序列**（`lib/hub-io.js:493-509`）：`write-receiving` → `verify-receiving`（`:498-501`，读回并断言目标条目**带着正确 scope** 已落地）→ `write-donating`（`:504`）→ `verify-donating`（`:506-508`，读回并断言源库**已不含**该条目）。
- **回滚实现**：`rollbackBoth()`（`:420-429`）把两库写回迁移前快照；同时**复位内存副本**（`:515-516`）——注释说明这是为了"避免下一条基于坏状态继续"。
- **进度可见化**：`onProgress` 回调（`:400`，注释称"进度是两阶段提交的**可见化**"）。

**为什么这是同步原语**：这段逻辑解决的是**与跨端同步完全相同的问题**——"跨两个不可原子提交的存储移动一条数据"。三条可直接继承：

1. **fail toward duplication, never toward loss** —— 跨端同步的第一原则。
2. **每写必读回校验** —— "写函数返回成功 ≠ 内容真落对"，这在网络传输场景下更成立。
3. **回滚凭据必须在操作前取** —— 事后取不到干净快照。

**团队版需要补的部分**（【推断】）：
- 现实现是**单机双文件**、回滚靠**本地快照**。跨端场景下接收方是**远端**，回滚需要远端配合，且网络分区时可能**双向都不可达**。
- 因此需要**补偿事务（saga）**而非本地回滚：把"迁移"拆成可重试的幂等步骤，失败时进入**待人工裁决队列**而非静默回滚。
- **幂等是前提**：重试不能产生第二份。本仓 `migrate()` 已有幂等分支（`:469-479`，`src === targetScope` 时只校正 `workspaceRef` 并返回 `{ok:true, noop:true}`）——这个模式可原样复用。

| --- | --- |
| **成员身份** | `addedBy` 目前是**自由字符串**（只校验 `typeof === 'string'`，`:140`），不是受验证的身份。团队版需要它绑定到**可信成员标识**（如邮箱/SSO subject），否则可伪造。 |
| **`addedBy` ≠ 权限** | 它记录"谁加的"，不表达"谁能改"。需要独立的**权限模型**（如：作者可改自己的、管理员可改全部）。 |
| **`authorizedBy` 的远程语义** | 该字段当前是**本机**的模型/用户授权痕迹。跨端时必须区分"远端成员授权"与"本地模型授权"，否则审计链断掉。 |

> 【推断】建议的权限最小集：`{memberId, role: owner|member|reader, scopes: [workspaceRef...]}`，并在服务端**强制**校验——不要依赖客户端自报的 `addedBy`。

### 3.4 删除语义：只标状态不删，对同步是优势还是负担？

**结论：净优势，但有一个必须补的缺口。**

**算优势的部分**：

| 维度 | 理由 |
| --- | --- |
| 冲突后果降级 | 冲突结果从"数据丢了"变成"标记取哪个值"——**可逆** |
| 幂等/可重放 | 状态标记是单调的，重复应用无副作用（§3.2.1） |
| 审计完整 | 保留历史 ⇒ 满足团队场景的合规与追溯需求 |
| 误删可恢复 | 本仓已有 `restore=` 通道可撤销误标 |
| 与 CRDT 天然契合 | 单调集合是最简单、最无争议的 CRDT 类型 |

**算负担的部分（要正视）**：

| 负担 | 影响 | 缓解 |
| --- | --- | --- |
| **存储/索引只增不减** | 向量与倒排索引持续膨胀，检索池被作废条目污染 | 检索侧按 `status` 过滤；物化视图只含 `current` |
| **"删除"无法真正满足合规要求** | 若成员要求"删除我的数据"（GDPR 类），状态标记不构成删除 | 需要独立的**物理清除流程**（带审计留痕），与日常语义分离 |
| **作废条目仍占检索预算** | 本仓规定 `superseded` 是"返回但标记"（不剔除、不降权）⇒ 团队规模变大后噪声线性增长 | 【待拍板】团队版可能需要引入**降权**（当前规则禁止降权，这是用户裁定，改动需重新拍板） |

> 【待拍板】上面第三行是一个**真实的架构张力**：本仓现行规则（`superseded` 返回但不降权）是**单用户**场景下的正确选择（用户自己知道哪条过时了），但在**团队 + 时间累积**场景下，不降权意味着检索结果会越来越吵。**建议：把"是否引入降权"作为一个显式决策项交给用户，并在团队版用"默认降权 + 可关闭"的形式实现开关解耦（用户已有"功能开关必须解耦"的硬性要求）。**

### 3.5 ★ 冲突场景表

| 场景 | 冲突本质 | 收敛方案（建议） | 依据 |
| --- | --- | --- | --- |
| **两人同时改同一条** | 两个内容版本同时存在 | **不覆盖**：保留两个版本，把后者标为 `superseded` 并指向先者（或反向，按确定性规则），**由消费者看到两条**。绝不静默 LWW。 | 本仓 `:395` "fail toward duplication, never toward loss"；LWW 静默丢写的实证见 §3.1 坑 1 |
| **一人删除、一人修改** | 删除与修改的因果歧义 | **修改胜出、删除降级为状态标记**。因为本仓不物理删除，"删除"本身就是 `retracted` 状态；若同时有修改到达，则**两个状态都保留**（`retracted` + 新版本 `current`），并把冲突呈现给用户裁决。 | 本仓不删语义（§3.2.1）；`status` 单调可并存 |
| **离线后重连** | 两端各自累积了若干变更，需批量合并 | **事件日志重放 + 幂等键**。每条变更是 `{txId, actor, writes, stateChanges}`（本仓 `lib/state-commit.js:179-191` 的现成形状）；重连后按 txId 去重、按逻辑时钟排序重放。**幂等是前提**，重复投递不得产生第二份。 | 提交单据形状 `lib/state-commit.js:179-191`；幂等分支范例 `lib/hub-io.js:469-479` |
| **两人同时改同一条的不同字段** | 字段级并发 | 若采用**每字段 LWW**，可无冲突收敛，但需接受"看不见对方那一半改动"；建议改为**字段级合并 + 冲突字段可见**。 | 每字段时间戳是 CRDT 常规做法，但需注意 §3.1 的静默丢写 |
| **同一记忆被两端同时新建成"新条目"（语义重复）** | 条目 id 不同但内容相同 | 这正是**语义去重**（§2.2）的用武之地：收端 ingest 时先查近邻，命中则合并证据计数而非新建 | 向量近邻去重，阈值需标定（§2.2） |

**表中所有方案都依赖同一个前提：变更必须能表达为幂等事件。** 本仓 `state-commit.js` 已经提供了这个形状（`txId` + `actor` + `writes` + `stateChanges`），**这是团队版可以直接复用的第三个现成资产**。

## 4. Q4：落地架构选型建议（阿里云为主、多云端兼容）

### 4.1 候选架构 A：对象存储 + 快照同步（最简）

**形态**：成员本地继续以文件为真源；定期把记忆库快照（或 append-only 日志增量）推到**对象存储**（OSS）；其他成员拉取。

| 维度 | 评估 |
| --- | --- |
| **延迟** | 分钟级（受快照周期控制），**无法做到秒级** |
| **成本** | 极低（OSS 存储 + 请求费；10 万条记忆文本量级 ≈ 数十 MB） |
| **复杂度** | **最低**（无服务端、无数据库） |
| **离线能力** | **最强**（本地文件为准，联网只是同步时机） |
| **向量处理** | **本地各自编码**。各端独立建向量索引 ⇒ 模型版本可能不一致 ⇒ 检索结果不可比（§1.2） |
| **失败模式** | 并发写同一快照 ⇒ **必须做冲突检测**（本仓已有 `expectedDigest` / `expectedStateVersion` 机制，`lib/state-commit.js:193-194`）；快照整体覆盖会**静默丢数据**（本仓 `lib/hub-io.js:237-239` 的"读坏过的文件不覆盖"约束③正是为防这个） |

**适用**：2–3 人小团队、对实时性无要求、想先验证协作流程。

### 4.2 候选架构 B：权威服务端 + 事件日志/CDC（推荐主线）

**形态**：引入**权威服务端**（阿里云 RDS PostgreSQL + pgvector，或 Tablestore）；所有写入先提交为**事件**（复用本仓 `state-commit.js` 的提交单据形状）落库；服务端按事件顺序应用并维护权威状态；成员端本地缓存 + 增量拉取；向量由服务端后台 worker 统一编码。

| 维度 | 评估 |
| --- | --- |
| **延迟** | **秒级可达**（文本/状态走同步提交）；向量**分钟级**（worker 异步） |
| **成本** | 中等（RDS 实例 + 向量索引存储；10 万条 × 1024d float32 ≈ 400 MB，pgvector 完全放得下） |
| **复杂度** | 中（需要服务端、迁移、权限） |
| **离线能力** | **中等**（本地缓存可读可写，联网后重放事件；需幂等） |
| **向量处理** | **统一模型版本**（服务端一份），彻底消除 §1.2 的不可比问题；换模型时服务端做**别名/双写切换**（§1.2 手段 2） |
| **失败模式** | 服务端不可用 ⇒ 成员端退化为**本地词法模式**（本仓已有该降级路径，§2.5）；网络分区时事件积压，恢复后重放（需幂等 + 逻辑时钟） |

**为什么推荐 B**：本仓的三个现成资产（提交单据 `state-commit.js:179-191`、单调状态 `:38`、两阶段校验 `hub-io.js:493-509`）**全部指向"有权威端的提交-应用模型"**。选 B 意味着**最大化复用已有设计**，而不是另起一套 CRDT。

### 4.3 候选架构 C：CRDT 本地优先

**形态**：无中心；每个成员是独立副本，通过 CRDT 自动收敛；向量各端自建。

| 维度 | 评估 |
| --- | --- |
| **延迟** | **本地 0 延迟**；跨端收敛是异步的（秒~分钟，取决于同步频率） |
| **成本** | 低（可无服务端；但需要同步通道，如 RocketMQ / 或 P2P） |
| **复杂度** | **最高**（CRDT 库选型、墓碑清理、逻辑时钟、调试困难） |
| **离线能力** | **最强**（这是 CRDT 的核心优势） |
| **向量处理** | 与 A 同病：各端独立编码 ⇒ 模型/维度可能不一致；且**向量本身不是 CRDT**（无法自动合并两个向量）⇒ 向量必须由一端权威生成或全端重算 |
| **失败模式** | 墓碑永久累积（存储与检索污染）；语义重复条目无法自动合并（不同 id）；权限/审计需要另做（§3.1 坑 3） |

**关键反对理由**（针对本模型的）：**向量不是 CRDT**。CRDT 能收敛"状态标记"和"元数据"，但**无法收敛"向量"**——两个端对同一条记忆算了两个略有差异的向量，CRDT 没有语义去合并它们（取哪个？平均？都留？都留则检索重复）。**这是 CRDT 路线在本场景的结构性短板**，也是不建议选 C 的主要理由。

### 4.4 选型结论

| 候选 | 延迟 | 成本 | 复杂度 | 离线 | 向量 | 建议 |
| --- | --- | --- | --- | --- | --- | --- |
| A 对象存储快照 | 分钟级 | 最低 | 最低 | 最强 | 各端独立（不可比） | **作为第一步与降级路径** |
| **B 权威服务端 + 事件日志** | **秒级** | 中 | 中 | 中 | **统一版本（最佳）** | **★ 主线** |
| C CRDT 本地优先 | 本地 0 / 跨端异步 | 低 | 最高 | 最强 | **无法收敛（结构短板）** | 暂不采用 |

**推荐：B 为主线，A 作为落地第一步。** 理由汇总：本仓三个现成资产均指向 B；C 在向量维度上有结构性短板；A 的实现成本最低，可作为 B 的过渡形态（先跑通"谁写了什么"的协作流程，再引入服务端）。

> 【待拍板】上表是技术评估，**最终选型需要产品负责人确认**——尤其是"是否愿意引入服务端"这一项，它决定了产品形态（是否需要运维、是否有中心化信任问题）。

### 4.6 分阶段推荐路线

**阶段 0：验证冲突面（1–2 周，无服务端）**
1. 把本仓提交单据（`lib/state-commit.js:179-191`）序列化为**可交换的变更事件**。
2. 用架构 A（OSS 快照 + 增量日志）跑通两人协作，**专测 §3.5 的五个冲突场景**。
3. 目的一：验证"事件形状"是否够用；目的二：**在引入服务端之前先量化真实冲突率**（若冲突极少，架构选型可以更保守）。

**阶段 1：引入权威服务端 + 词法实时（2–4 周）**
4. RDS PostgreSQL 承载权威状态；**先只做文本与状态同步**，向量仍各端本地。
5. 达成"文本 ≤ 5 秒可见"（架构里的"实时"）。
6. 权限最小集随此阶段落地（§3.3 的缺口表）。

**阶段 2：服务端统一向量 + 语义去重（2–4 周）**
7. 向量编码上移到服务端 worker（FC + 队列），模型版本统一。
8. 落地"两阶段"：写入立即返回（文本已可见）→ 后台补齐向量 → 前端如实显示"语义检索补齐中"。
9. 用本仓 M7 基准语料**标定去重阈值 θ**（§2.2），不得使用外部默认值。

**阶段 3：模型升级能力（按需）**
10. 实现集合别名切换 / 双写过渡（§1.2），使换模型成为**计划内操作**而非事故。
11. 补齐"物理清除流程"以满足合规（§3.4 的负担表）。

**明确的非目标（本阶段不做）**：
- 不引入 CRDT 文本（§3.1 坑 2）。
- 不追求"向量实时"（§2.6 判据）。
- 不把云效 Codeup 用于记忆同步（层级不同，§4.5）。

### 4.7 ★「实时同步」在架构里对应到什么具体指标

| 环节 | 指标 | 同步/异步 | 依据 |
| --- | --- | --- | --- |
| 记忆文本 + 状态标记跨端可见 | **≤ 5 s（p95）** | **同步**（这是"实时"的真正含义） | §2.6 |
| 词法（倒排）检索可用 | **≤ 5 s**，与文本同时 | **同步** | §2.5 |
| 向量检索可用 | **≤ 5 min（p95）** | **异步**（可后台补齐） | §2.3 各向量库默认即最终一致 |
| 语义去重判定 | 随向量补齐（≤ 5 min） | 异步 | §2.2 |
| 换嵌入模型 / 维度 | **小时级**，计划内窗口 | 异步 + 灰度 | §1.2 |
| 跨端全量重建 | 小时级 | 异步 | §1.1（10 万条本地 ≈ 37 分钟） |
| 冲突呈现给用户裁决 | **≤ 5 s**（与文本同步可见） | 同步 | §3.5 不允许静默 LWW |

**哪个环节可以异步**：**只有向量相关的环节可以异步**（编码、索引、去重判定、模型升级）。**文本、状态标记、冲突提示必须同步**——因为它们是"用户能直接感知到的记忆本身"，而向量只是"检索质量的增强"。

## 7. 一句话总结

**"实时同步会不会让向量编码变困难"——不会。** 向量编码在本项目的量级上是"分钟级 × 角元级"的后台任务，完全可以异步化；真正需要实时的是**文本与状态标记的可见性**。而多端同步的真实难点在冲突与一致性——对此本仓已经有**三个可直接升格的现成原语**（单调状态、两阶段提交、幂等的提交单据），架构主线应选**权威服务端 + 事件日志**，让"实时"落到 **文本 ≤ 5 秒、向量 ≤ 5 分钟** 这两个可验收的指标上。
