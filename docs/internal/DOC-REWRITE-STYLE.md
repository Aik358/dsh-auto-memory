# 文档改写规范 · 从「施工计划」到「完工报告」

> 本文是**改写作业的唯一判据**。适用对象：`docs/` 下所有标题或首段仍呈**计划态**的文档
> （标题含「计划 / 规划 / 方案 / 施工单 / 待办 / 候选 / 前瞻 / 蓝图 / 排期 / 作战 / TODO / PLAN」等，
> 或正文含「待批准 / 未开工 / 计划中 / 下一步做 / 待办」等未完成语）。
>
> **改写目标**：施工已完毕，文档要从「我们打算怎么做」变成「我们做了什么、结论是什么、证据在哪」。

---

## 一、四条硬纪律

1. **只改框架与语态，不得增删事实。** 原文的每一个数字、路径、commit、断言结果都必须原样保留。
   改写不是重写，是把时态与人称从「将要做」掰成「已做完」。
2. **不得编造结论。** 若原文未记录结果，写「本阶段结束时未单独留档，结论见 <相关文档>」，
   严禁自行填空。宁可留空，不可虚构。
3. **不改文件名与路径。** 若干文档被回归套件与工具在运行期真读（见 §四），改名即打红。
4. **保留原文的取证部分。** 「实测 / 取证 / 断言 / 复算」是这类文档最值钱的部分，一字不删。

---

## 二、统一头部模板

每篇改写后的文档，**首部**替换为下列四段（其余正文保持不变，仅做语态矫正）：

```markdown
# <标题去掉「计划 / 方案 / 规划」等词，改为陈述式>

> **状态**：已完工 · <完工日期 YYYY-MM-DD>
> **性质**：<施工记录 / 设计定稿 / 验收报告 / 研究结论> —— 本文为**完成后的技术记录**，不再作为待执行计划。
> **落点**：<本文件所述变更实际落在哪些文件 / 哪次发布 / 哪个 commit>
> **验收**：<套件名 + PASS 数，或「已并入全量回归」>

## 摘要

<3–6 句。必须回答四个问题：当初要解决什么问题 → 采用了什么方案 → 实际结果如何 → 留下了什么>
```

## 三、语态对照表（逐条替换）

| 计划态（改写前） | 报告态（改写后） |
|---|---|
| 待批准 / 待用户拍板 | 已批准（<日期>）· 已落地 |
| 未开工 / 计划中 | 已完工（<日期>） |
| 下一步要做 / 后续补 | 已完成；遗留项见 <路径> |
| 本方案提出 / 建议采用 | 本方案已实施 |
| 预计 / 预期收益 | 实测结果（若无实测：预期收益，尚未单独实测） |
| 目标：… | 达成：…（或：部分达成，差距为…） |
| ⚠️ 风险 | 风险处置：<实际怎么处理的> |
| TODO / 待办清单 | 已办结清单（逐条标注结论） |
| 「本次不执行」 | 「本次未执行（原因：…）；<后续是否执行>」 |

**人称纪律**：主语用「本项目 / 该批次 / 本方案」，**禁止**第一人称叙述（「我做了 / 我们决定 / 我排查」）。
**语气纪律**：陈述事实，不写夸饰。参照 DeepSeek 官方技术报告的克制度——结论用事实口吻说出，不用信念口吻。

## 五、归档判据

满足以下**全部**三条 → 移入 `docs/archive/`（保持相对层级）：
1. 内容是**过程留痕**（AUDIT / HANDOFF / ISSUE 派工 / 进度台账 / R 轮记录 / 事故取证）；
2. **没有**被回归套件、工具或公开发布文档引用（`grep` 验证）；
3. 结论**已被**其他文档吸收。

反之，只要**结论仍有独立价值**（研究定稿、架构契约、验收报告、方法论）→ **原位改写**，不归档。

## 六、完工日期取值规则

按优先级取用，**不得编造**：
1. 原文中记录的最后一次执行/验收日期；
2. 该批次对应的 `CHANGELOG.md` 条目日期；
3. 用 `git log -1 --format=%ad --date=short -- <落点文件>` 取实际提交日；
4. 三者皆无 → 写「完工日期未单独留档」，不写具体日期。
