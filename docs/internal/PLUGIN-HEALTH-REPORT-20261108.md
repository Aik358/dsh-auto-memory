# 第一部分：那个 84 MB 的东西是什么

## 一句话答案

**它是一个「争吵记录本」。记的是：AI 从对话里提取的事实，跟之前记下的事实，说法不一样的地方。**

问题有三层：

1. 它把「说法不一样」判得太宽 —— 同一样东西换个措辞就算「吵架」
2. 记下来的吵架**从来没人处理**（处理代码写了，但没人调用）
3. **模型一条都看不到** —— 既不在注入里，也不在检索里

**所以它是一本只进不出、还没人读的账。**

## 数字（2026-11-08 06:54 实测）

文件位置：

```
C:/Users/JH Z/.dsh/memory/hub/facts.json
```

| 项目 | 数字 |
|---|---|
| 文件大小 | 87,927,583 B = 83.85 MB |
| 真正有用的事实 | 约 1,000 条，占 0.42 MB |
| 「争吵记录」 | 64,644 条，占 70.89 MB |
| 已处理过的争吵 | 0 条 |
| 未处理的争吵 | 64,644 条（100%） |
| 平均每条争吵占 | 1,083 B |

**84 份体积里 83 份是争吵记录，1 份是真正的事实。**

## 涨得有多快（实测，不是估算）

盯了 65 秒：

```
起始    87,884,253 B
65 秒后  87,927,583 B
增量        43,330 B
```

| 周期 | 增量 |
|---|---|
| 每小时 | 约 2.3 MB |
| 每天 | 约 55 MB |
| 每月 | 约 1.6 GB |

**注意：这是在你没在干活的时候测的** —— 只要后台 worker 还在喂数，它就一直在涨。

## 它是怎么长出 64,644 条争吵的

### 第一步：往里面喂事实

后台有个 worker（语义候选提取器）持续从对话里提取这种结构化事实：

```
主体(subject) + 属性(predicate) + 值(object)
```

你项目里的真实例子：

```
主体 = 项目
属性 = 构建工具
值   = esbuild
```

喂进来的入口是 HTTP 路由（`lib/index.js:27030` 的 `action: 'feed'`）。

### 第二步：跟已有的比，看是不是「打架」

判定代码在 `lib/fact-store.js:131-137`，全文只有 7 行：

```js
export function isFactConflict(a, b) {
  if (a.scope !== b.scope || a.subject !== b.subject || a.predicate !== b.predicate) return false
  const ao = a.object ?? ''
  const bo = b.object ?? ''
  return ao !== bo          // ← 就这一行决定「算不算打架」
}
```

翻成人话：

> **主体同名 + 属性同名，但值只要文字不完全一样 → 就算打架。**

**这是第一个病根：判得太宽。**

`object` 是一句自然语言。同一个意思换个说法，字符串就不一样：

```
第一次提取：「shadow 只记录 / canary 显式注入 / active 全量注入」
第二次提取：「shadow 只记录、canary 需要显式、active 全部生效」
```

人看是同一件事，**代码看是两个不同的值 → 记一次打架**。

### 第三步：把双方完整存下来

看 `lib/fact-store.js:478-486`：

```js
conflicts.push({
  conflictId: ...
  left:  { ...existing, provenance: [...] },   // 完整存一份「旧的」
  right: { ...c, provenance: [...] },          // 完整存一份「新的」
  resolved: false,                             // ← 永远写 false
})
void persist()                                  // ← 立刻存盘
```

三个要点：

**① 每条记录存两份完整快照**（`left` + `right`），都带 `provenance` 溯源数组。
这就是为什么平均一条 1,083 B —— 它其实存了两条事实的全套信息。

**② `resolved` 永远写 `false`。** 代码里没有任何地方把它改成 `true`。

**③ `void persist()` 每次打架立刻存盘。**
而存盘的实现是**把整份 84 MB 重写一遍**。

### 第四步：没人处理，于是只进不出

`lib/fact-store.js:640-648` 其实**写了处理函数**：

- `conflictsList()` —— 列出所有争吵
- `pendingConflicts()` —— 列出没处理的
- `resolve()` —— 标记某条已处理

**但全仓搜索这三个函数，除了定义处，零调用。**

```
能记下争吵    ✅
能处理争吵    ✅ 代码写好了
有没有人处理  ❌ 没人调用
```

**这是个只开了一半的阀门：进水口开满，出水口焊死了。**

### 第五步：它长大了会怎样

**对模型：零影响，因为模型根本看不到它。**

| 通道 | 有没有读它 |
|---|---|
| 注入面（28 个 `pushPart` 段落） | 没有 |
| 检索面（`memory_recall` 的 5 个 scope） | 没有 |
| 面板 overview | 有（只显示个计数） |

**这 64,644 条争吵，对记忆系统来说：零价值、纯负担、还在涨。**

**对磁盘和性能：实实在在的负担。** 每次存盘 = 重写 84 MB。哪怕只加一条 1 KB 的记录，也要把 84 MB 全写一遍。

## 小结：三层问题与修复顺序

| 层 | 问题 | 严重度 |
|---|---|---|
| ① 判定 | 同主体同属性、值措辞不同就判打架，必然大量误报 | 高（源头） |
| ② 存储 | 一条存两份完整快照；每次打架立刻重写整份文件 | 中（放大器） |
| ③ 出口 | 处理函数零调用；模型读不到 | **最高（价值为零）** |

**修的顺序应该是 ③ → ① → ②**：

- 先给它出口（能处置 / 能读），那 64,644 条才有意义
- 再收紧判定（减少新误报）
- 最后优化存储（不用每条都重写整份）

**只修 ①：存量 64,644 条还在。只修 ③：每天还在新增 55 MB。**

# 第二部分：事件为什么碎成一地

## 先纠正我上一轮的一个说法

你对 `groupIntoCandidateEventsPre` 的判断**是对的**。我查清了：

```
curateUnarchivedPre 全仓只有 2 处：
  L8581   函数定义
  L27868  HTTP 路由（前端点「审理」按钮才触发）
```

**它只在人工点「审理存量账本」时跑，日常完全不跑。**

所以它跟日常碎片化**没有因果关系**。我上一轮把它算成「第二条碎片路径」是过度推断。

（它仍然是个问题 —— 一个写好了没接线的能力 —— 但那是另一回事，见第三部分。）

## 真正的元凶：一行除法

### 插件本来想做的事

你每干完一段活，模型调 `memory_log` 写一条日志。
写的时候，插件会试着把它**挂到已有事件上**，而不是每次新建一个事件。

「挂哪个事件」的判断在 `lib/index.js:24470-24507`。

### 它怎么判断「是不是同一件事」

用词汇重合度。注意分子分母取的是什么：

```js
// 分母：这次日志【全文】切出来的词
const _noteTok = [...]        // 可能有几十上百个词

// 分子来源：已有事件的【名字（40 字）+ 摘要】
const _evTok = new Set(tok(_best.name) + tok(_best.summary))

let _hit = 0
for (const _t of _noteTok) if (_evTok.has(_t)) _hit += 1
const _ratio = _hit / _noteTok.length;   // ← 分母是日志全文的词数
return _ratio >= 0.34 ? 挂上去 : 新建一个
```

### 为什么这是数学上不可能通过的

```
分子最多 = 事件名里的词数（几十个）
分母     = 日志全文的词数（几十上百个）
```

**比值上限 = 事件名词数 / 日志词数。**

而事件名只有 40 个字（下面会讲），能有多少词？

A 线实测 26 个事件，用「事件自己的名字 vs 事件自己的正文」算这个比值的理论上限：

| 指标 | 实测值 |
|---|---|
| 中位数 | 0.081 |
| 最大值 | 0.320 |
| 达到 0.34 阈值的 | **0 / 26** |

**即使用「这条日志和它自己的事件」这种最理想情况，也过不去。**

所以每次 `memory_log` 的结局必然是：

```
算出来 < 0.34
   ↓
判定「找不到同主题事件」
   ↓
新建一个事件
```

**每写一次日志 = 多一个碎片。这是必然，不是偶发。**

### 这个错是什么时候进去的

`git log` 搜 `0.34` 只命中一个提交：**`e338473f`（2026-11-05 17:20）**。

那次改动把旧逻辑换成新的主题门。旧逻辑是：

```js
const active = evId ? { id: evId } : resolveActiveEventPre(store0)
//                             ↑ 旧：挂到「最近更新的 active 事件」
```

**旧逻辑虽然粗（总是挂到最近那个事件），但至少不会产生碎片。**
新逻辑想聪明点（找到真正对的事件），但判据算错，退化成「永远新建」。

实测印证：11-05 15:30 出现第一个碎片事件，之前一个都没有。

## 雪上加霜：三件事让碎片无法补救

### ① 模型看不到 eventId，只能新建

铭文（每轮提醒）里写着：

```
有新进展 ⇒ memory_event(action=append, eventId, checkpoint)
```

**但要 append，模型得知道 `eventId`。**

而注入面（模型唯一的信息来源）**从来不输出 eventId**。

查渲染层 `lib/event-render.js`：

| 搜索项 | 出现次数 |
|---|---|
| `id` | **1 次**（而且只是用来过滤，不是输出） |
| `evt_`（事件 ID 前缀） | **0 次** |

**结果：模型看不见 eventId → 无法 append → 只能 create（create 不需要 eventId）。**

这跟主题门恒失败**指向同一个动作**：新建。

### ② 归组能力写好了，但没接线

`lib/` 下有 4 个文件，共 **42,839 B**，专门做「把碎片重组成事件」：

```
event-regroup.js            11,486 B
event-regroup-scan.js       11,745 B   ← 里面有 7 条「什么算一件事」的判据
event-regroup-propose.js     9,274 B
event-regroup-apply.js      10,334 B
```

配套 **4 个测试套件全部存在且通过**。

**但主引擎 `lib/index.js` 对它们引用 0 次。**

而且 `event-regroup.js:8-13` 的模块头注释，逐字写着：

> 旧版「把账本变成事件」用的是**纯确定性聚类**，**实测产出垃圾：一篇账本 = 一个事件，事件名直接取「目标段首行」**，而那行往往是 `<!--type=goal-->` 这种未清理的 HTML 注释。
>
> 用户裁定（逐字）：「可以先用这个机械的分类器来提供借鉴，但是**不能全量相信**，只能作为**加速器**。**具体事件的分类还是得 AI 来解决**。」

**你自己早就裁定过这件事，代码里也批判过，替代实现写完、测试通过 —— 就是没接上。**

### ③ 事后也没有合并能力

`memory_event` 有 5 个动作：create / set / append / close / rename。

**没有 merge。** 而且检查点是 append-only，不能搬到另一个事件上去。

所以即使你想手动收拾，也没有工具。

## 碎片化的完整因果链

```
① 主题门取错分子分母（数学不可能通过）
        ↓
② 每次 memory_log 判定「找不到同主题」→ 新建事件
        ↓
③ 新建时 kind 走默认值 unknown（全仓没有推断逻辑）
        ↓
④ 新建时不填四段（goal/doing/deadend/next）
        ↓
⑤ 事件名被写死截到 40 字（切在句子中间）
        ↓
⑥ 注入面不输出 eventId → 模型想 append 也做不到
        ↓
⑦ kind=unknown 让卡片退化成「只有标题行的窄卡」
        ↓
⑧ 归组模块零调用 → 事后也合并不了

结果：事件库只增不减，越堆越多。
```

实测：45 个事件里 **27 个是碎片**；27 个碎片里 **14 个建完之后从来没被写过一笔**（`updatedAt - createdAt = 0 秒`）。

# 第三部分：其他值得知道的问题

下面这些不是「致命」，但都是真实缺口。

## 3.1 铭文其实已经是清单了，但缺最关键的东西

你说「应该给指令性清单而不是自然语言」—— 实测发现**它已经是清单了**：

| 指标 | 实测 |
|---|---|

| 给「做到什么程度算完」的段 | **0 段** |
| 缺前置数据（模型没材料做）的条目 | **23.7%** |

**所以你问「consolidate 能不能达成优质记忆库」—— 现在不能。它连系统里最主要的记忆形态都看不到。**

## 3.8 两处方法论上的坑（值得写进纪律）

**① 「导出零引用」不等于死代码**

1,163 个导出里：

- 42 个真死（全仓零引用）
- **173 个仍被自己模块内部调用**（如 `event-store.js:41` 的 `EVENT_STATUSES` 在 `:211` 自用）
- 347 个只被测试引用

按「零引用就删」的朴素口径去删，会删掉正在跑的代码。

**② 同名旧文件名会制造假「误报」**

`docs/internal/ISSUE117-TRIAGE-20260922.md:39` 曾以「该文件在 pre 线不存在」把 `acceptance.js` 判为误报。

但现树上的 `acceptance.js` 就是 pre 线改名后的同一模块（`tools/release.mjs:398` 登记了旧名）。

**孤儿条件从未消失，是被改名骗过去了。**

# 第四部分：该怎么办

## 4.1 按「有没有增长性」排序，不是按严重度

| 优先级 | 问题 | 为什么是这个顺序 |
|---|---|---|
| **第 1** | facts.json 84 MB | **有增长性**：每天 +55 MB，不修会涨到 GB。而且出口是零 |
| **第 2** | 事件碎片化 | **有增长性**：每写一次日志多一个碎片 |
| 第 3 | 铭文 eventId / 四段 | 稳态缺陷，但现在就在影响每轮质量 |
| 第 4 | consolidate 视野 | 稳态缺陷 |
| 第 5 | 平行形态联动 | 稳态缺陷 |
| 第 6 | 13 个孤儿模块 / 死控件 | 不增长，清理项 |

## 4.4 一个判断顺序上的建议

如果你想先看到「肉眼可见的改善」，建议顺序是：
