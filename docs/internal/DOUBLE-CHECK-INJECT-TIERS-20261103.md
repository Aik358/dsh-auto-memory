## 1. Q1 —— 档位枚举：8 个值，不是 4 个

提示词背景把模型描述为「四档」（human_full / human_slim / run_full / run_slim）。实测 `lib/index.js:1790-1815`：

```
const INJECT_TIERS = {
  LEGACY: "legacy",              // 档位缺失/非法时的 fail-open 回退值
  HUMAN_FULL, HUMAN_SLIM,        // F1 F2 —— 真人发声
  RUN_FULL, RUN_SLIM,            // F3 F4 —— 运行中
  POST_COMPACT,                  // F5 —— 压缩后重建
  HANDOFF_CARRY,                 // F6 —— 交接接续
  HANG_COMPENSATE,               // F7 —— 挂机代位补偿
}
```

**这意味着任务书预设的「四档矩阵」不足以覆盖实现。** 我按 8 档全量实测（§3），并把「四档」理解为四个**主档**（`*_full` / `*_slim` × 人/无人），另 4 个是**时机档**（LEGACY 是回退、POST_COMPACT / HANDOFF_CARRY / HANG_COMPENSATE 是触发时机覆盖）。

### 1.1 判定函数与调用链（实测行号）

| 环节 | 位置 | 说明 |
|---|---|---|
| 枚举 | `lib/index.js:1790` | 8 值 |
| 判定 | `:1975` `decideInjectTierPre(p)` | 优先级：isCarry > postCompact > hangComp > human/run |
| 白板规格 | `:1994` `planSpecForTierPre` | 全文 / 核心 7 节 / 不投 |
| 谓词 4 个 | `:1818 / :1837 / :1840 / :1863` | isHuman / isPlanFull / shouldInjectPlan / isRulesFull |
| **生产消费点** | `:21833` → `:21882` → `:21885` → `:21907` → `:21918` | 见 §2 时序 |

### 1.2 「一处定义、多处手抄」—— 实测确认 4 组重复判据

| 语义 | 模块级（**生产 0 消费**） | 生产真正在用的内联副本 |
|---|---|---|
| 档位枚举 | `INJECT_TIERS` `:1790` | 函数内 `_T` `:11093` |
| 规则全文 | `isRulesFullTierPre` `:1863` | `_rulesFullTierInline` `:11203` |
| 白板全文 | `isPlanFullTierPre` `:1837` + `planSpecForTierPre` `:1994` | `_planSpec` `:11109` **+** `_planCapFullIdx` `:11867`（第三份） |
| 画像/语义唤回 | `isHumanTierPre` `:1818` | `:11498` 与 `:11547` **两份手写名单** |

**为什么必须内联**：`renderMemoryDynamic` 被 20+ 套件用 `new Function` 抽取执行，沙箱里没有模块级 const。这是仓内已固化的纪律，**内联本身合理**；但代价是「模块级那份无人消费 ⇒ 套件守护的是死代码」。我已实测验证：模块级 4 个谓词在生产路径确实零调用。

## 2. Q2 —— 生产路径可达性

### 2.1 实际写入的档位只有 5 种（由生产调用点直出）

`lib/index.js:21833`：

```js
let _tierGuess = decideInjectTierPre({ isHuman: _isHumanNow, isFull: true })
//                                                              ^^^^^^^^^^^^^ 硬编码
```

因为 `isFull: true` 写死，该调用**只能**产出 `human_full` / `run_full`，再叠加三个时机覆盖（`post_compact` / `handoff_carry` / `hang_compensate`）。
**`*_slim` 不经此产生** —— 它们只来自 `:21907-21915` 的降级块。

### 2.2 时序实测（图 4）

```
① decideInjectTierPre(isFull:true)     L21833  → 只能 *_full
② 写 state                              L21882
③ renderMemoryDynamic(完整帧)          L21885  ← 此处只可能读到 *_full
④ 降级为 *_slim                        L21907-21915
⑤ renderSlimSnapshotPre(精简帧)        L21918  ← 此处才读到 *_slim
```

源码偏移实测：`renderMemoryDynamic` 起始偏移 `1150153` < 降级块 `1152002` < `renderSlimSnapshotPre` `1152132`。**顺序确凿**。

### 2.3 ★ 裁定：这不是缺陷 —— 但用户要的「user slim」确实不存在

我一度把「完整帧永远看不到 `*_slim`」当缺陷，**复核后修正判断**：

- 「完整帧拿 `*_full`」在语义上是**对的**：完整帧就该给全量档。
- `renderMemoryDynamic` 里那套 `*_slim` 裁剪分支在完整帧上确实是死代码，但它不影响正确性 —— 因为精简帧走的是**另一个函数** `renderSlimSnapshotPre`。

**真正的缺口在这里**（与既有报告一致，我独立验证）：

`renderSlimSnapshotPre` 的函数体里**只有 6 处 `out.push`**，且**完全不读** `planText` / `latestHandoffText` / `rulesSection` / `tier0LayerText`（逐项 grep 实测 = false/false/false/false）。

⇒ 生产里实际只有两态：

| 形态 | 字符 | 内容 |
|---|---|---|
| 完整帧 | ~13,005（本装置）/ 报告 24,393（含真实事件库） | 全量 |
| 精简帧 | ~2,219（含真实唤回/事件） | **只有**状态行 + 检索指引 + 唤回声明 + 一条事件 + 画像摘要 |

**中间那一档（`human_slim` = 规则摘要 + 核心 7 节白板 = 9,965）在生产没有入口。** 用户 2026-10-27 纲要里定义的 "slim = 核心节、不投规则全文" 形态，代码写了、测试测了、生产不生效。

### 2.4 ★★ P0 缺陷：水位与挂机两条钩子 100% 失效

这是本次复核**最重的发现**，三重独立证据：

**证据 1 — 静态作用域证明**

```
lib/index.js:22110  try {
lib/index.js:22111    const _rqK = String(engine.requestIdPre(agent) || '')   ← 块级 const
lib/index.js:22137  } catch (_) {}                                          ← try 块在此关闭
lib/index.js:22387    if (stH._reqHumanFullKey !== _rqK) {  ← 块外引用 ⇒ ReferenceError
lib/index.js:22388    stH._reqHumanFullKey = _rqK
lib/index.js:22392    stH._humanConsumedKey = _rqK
lib/index.js:22408    stH._reqHumanFullKey = _rqK
```

**证据 2 — 动态实跑**（按真实作用域形状复现）：

```
修复前（当前生产形态）  水位钩子生效 = false   ⇒ 恒 false = 死代码
修复后（_rqK 提到 try 外）水位钩子生效 = true    ⇒ 恢复
```

异常被 `catch (_eWf)` / `catch (_eHg)` **静默吞掉** —— 与仓内已固化的「门控类判定禁止空 catch 兜底」纪律同型。

**证据 3 — 生产日志独立佐证**（`~/.dsh/dsh-auto-memory-diagnose.log`，15,013 行，5 天）：

| 诊断标签 | 命中次数 |
|---|---|
| `水位阈值命中` | **0** |
| `挂机代位补偿` | **0** |
| `真人在场` | 216 |
| `精简版被节流` | 3,427 |

⇒ 用户最在意的「25% / 50% 时人说话的下一轮投完整版」，**从实现至今一次都没执行过**。

**修法**：把 `const _rqK` 的声明移到 `try` 之外（一行移位），其余逻辑不动。功能即可恢复。**未改动代码**（调查阶段纪律）。

### 2.5 吞异常清单（实测计数）

| 函数 | 总 catch | 空 `catch(e){}` |
|---|---|---|
| `renderMemoryDynamic` | 17 | 7 |
| `renderSlimSnapshotPre` | 7 | 2 |
| 档位判定块 `:21818-21884` | — | fail-open 且**不写 diag**（异常不可见） |

档位判定块的 fail-open 方向是对的（不炸宿主），但**不留日志** ⇒ 一旦出问题无法从现场还原。建议改为 `diag()` 留痕。

## 4. Q4 —— 与用户意图的逐条符合度

> 用户 2026-11-03 三条意图：① full 不每轮注入，只在首轮 / 压缩后 / 25%·50% 人说话的下一轮；② full 不设上限或上限极大；③ 其他时候给 user slim。

### 4.1 「不每轮注入」——⚠️ 部分满足

- `snapshotMinGapRounds` 默认 **20**（每次完整版之间至少 20 个模型请求）✅
- `slimEveryRounds` 默认 **8**（精简帧自身再节流）✅
- **但**：`_grantByHuman` 使**每个带真人消息的请求都无条件授予完整版**，与水位、turn 序号无关。
- 生产日志：完整版 216（真人在场）+ 223（非门槛触发）+ 87（达门槛）+ 1（保真）= 527 次；其中真人触发占 41%–84%。

⇒ **用户要的「三种时机」实际只有「首轮」在按设计工作**；「压缩后」日志 0 次；「25%/50%」是 §2.4 的死代码。

### 4.2 「25% / 50% 水位」——❌ P0 失效

判据函数本身**完全正确**，我实测 8 条断言全绿：

| 场景 | 结果 |
|---|---|
| 26.3% 首次跨 25 | fire, fireAt=25 ✅ |
| 已投 25，28% 再说话 | 不重复投 ✅ |
| 跨 50 | fire, fireAt=50 ✅ |
| 一跳跨两档（20%→55%） | 只投一次，取最高 ✅ |
| 水位未知 | fail-closed 不投 ✅ |
| 生产接线条件 | `_waterFire.fire && isHuman`（两条件 AND）✅ |

**问题不在判据，在接线**：`_waterFire` 算对了，但一进授予分支就 `ReferenceError`（§2.4）。

### 4.3 「4000 预算」——✅ 是告警线，用户的归因有偏差

源码 `lib/rules-layer.js:437-441` 逐字：

> 「这两个数字是**警戒线**，不是**截断线**……超预算 ⇒ **全量注入**（一个字都不砍）+ 注入强提示要求整理」

告警文案本身也写明：「注意：**超预算不会截断**（全文照常注入）」。

实测佐证：真实 49 条规则 = 6,083 字符，用户预算线 1,500 / 项目 4,000，**超限 4 倍仍全量注入**，且规则段内**无任何截断标记**（`envelope.truncated = []`，且 `rules` 分项在 envelope 里明确豁免裁剪）。

**所以用户看到的「用户规约超预算线 4000 / 当前 5347」这条提示，不是「被 4000 卡住」的证据，而是「规则确实很长」的告警。** 真正被小预算砍掉的是 **`user-memory` 与 `project-notes`（每段 sub≈1,473）**，那两段与 4000 无关。

**这是一处需要向用户讲清的归因偏差**（既有报告 §2 差距 2 已识别，我用独立实测确认）。

### 4.4 白板 / 账本截断比

| 项 | 值 |
|---|---|
| PLAN.md 源 | 11,134 字符 |
| 完整档白板注入 | **1,941**（17.4%） |
| 瘦档白板注入 | 1,884（16.9%） |
| 瘦/完整 | **97.1% —— 几乎没裁** |
| 账本源 | 1,807 → 注入 812（44.9%） |

完整档白板预算 8,000 但**只用 1,941** ⇒ 不是预算不够，是**按节优先级截断**只留下核心节。白板源 4 节里有 3 节是高优先 ⇒ 可裁空间天然很小（与既有报告 D-2 判据修正同因）。

## 8. 复核方法学说明（便于他人复验）

1. **先实证后读结论**：我在读完 `INVESTIGATE-USER-TIERS-20261103.md` 之前已独立跑出全部数字。白板 1,941 与报告精确对上是「独立复现」而非「抄袭」。
2. **装置踩过的 3 个自造陷阱（已排除）**：
   - ① 初次用 `injectBudgetChars=2400`（非生产默认 8000）⇒ 体积偏小；
   - ② 规则抽取传错键名（`userMemory` 应为 `userText`，且缺 `rulesLayeringMode:'self'`）⇒ `rules=0` 假象；
   - ③ `truncatePlanBySections(plan, null, …)` 返回 `null` 是**契约**（非数组 ⇒ 调用方回落 `truncatePlanByPriority`），我一度误判为"白板为空"。
   三者都在报告正文中留痕，因为「误判如何被排除」本身是可复算证据。
3. **软模块注入**：`rules-layer.js` 与其它模块有同名顶层符号（`clean`），必须用独立 IIFE 作用域包裹注入，否则 `SyntaxError`（这也是套件维护者的真实坑）。
