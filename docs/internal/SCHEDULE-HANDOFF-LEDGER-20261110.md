## 三、依赖图与并行策略

```
2.6 memory_note+eventId ──┐
                          ├──> L1 ──> L2
L0 协议成文（只读） ──────┘    │
                              ├──> L3 (=2.7 合并) ──> L4 (=D4 合并)
                              └──> L5（前端/看板，可并行）
                                        │
                                        └──> L6（条件触发：L1 稳定 ≥14 天）
```

**三条硬约束**：
1. **同一文件不得并行**：L1/L2/L3/L4 都动 `lib/index.js` 与 `lib/event-write.js` ⇒ 严格串行；只有 L5 的前端部分（`lib/client.js`/`skins`）可与后端并行，但**必须同批回归**。
2. **L3 不能拆开做**：2.7 与 L3 改同一个 `ckPayload` 的四个字段（`text/sourceRef/idemKey/panels`），拆开=同一处改两遍、两套验收、两遍回归。
3. **L4 必须在 L3 之后**：`kind∈{plan,handoff}` 的语义在 L3 后被改写（全文→增量/摘要），过滤口径必须按新语义定；否则 D4 的跳过清单立刻过期（用户 2026-11-10 已裁定 D4 后置，与此一致）。

**每项收工的固定动作**（照抄施工总表纪律）：
- 真执行验收（禁止「源码含某字符串」充当证据）+ 每条判据带负路径 + 变异反向验证（变异必红、还原复绿）。
- `git status` 无 M lib/ 之外的本批残留；`node --check` 目标文件；真 import 一次。
- 记 (行数, 字节数, 导出符号数) 三元组基线；>500 行文件只用定点 edit。
- 提示词与注释**同批改**（`index.js:447,1526,1583,7919,24975` + client i18n）：代码改成编辑、提示词仍说「新开一篇」= 模型继续新建（反向误导）。

## 四、与 2.6 / 2.7 / 2.8 的合并裁决（一句话版）

- **2.6 → L1/L2 →（2.7+L3）→（D4+L4）→ L5 → L6**。

## 五、验收总判据（独立线 L 收口时必须同时满足）

1. **用户三条裁定逐条可判**：
   - 「仅限接续」：`scope=handoff` 不再把账本当 RAG 语料；`scope=all` 语料中 handoff 贡献 0%。
   - 「与白板不是一回事」：看板/索引不再混编（卡片数 ≤740、`index.json` ≤1.9 MB）；前端两个页签职责分离。
   - 「编辑更新为主」：新增写入中「编辑已有批次」占比 ≥80%（连续 7 天审计），「新建」只能由 L0 的三条新建时机触发。
2. **物理量**：文件增长速率从 12.27 篇/天 → ≤1 篇/天（按批次日均 ≤1.5 批次）；每写一次磁盘写放大 ≤5.2 MB；handoff 检查点 ≤500 字符/条。
3. **不回归**：存量 687 篇逐字节不变；`event-store.json` 检查点总数守恒（除新写入）；`smoke-test-handoff` 等 21 个核心套件按新判据更新后全绿。
