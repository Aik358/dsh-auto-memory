## 一、结论先行（三句话）

1. **前端「晕」的根因不是信息太多，是零层级**：13 个页签 + 9 个设置分区 + 80 个控件 + 135 个 `data-dam-*` 全部平铺在同一层，代码里**没有任何一处**表达「一级/二级」「日常/高级」「我的/项目的/团队的」。
2. **身份接入的拦路虎不是 OAuth 本身，是本仓自己的回环守卫**：我实测 10 例确认，**跨站回跳（Google 回跳的实际形态）与内网 IP/域名访问一律 403**——这决定了登录方案必须绕开"回调到现有路由"。
3. **重构必须先看守卫，因为 UI 结构是被 177 项回归里的一部分字符串锚定锁死的**：设置页 9 分区 key 与顺序被硬锁 ⇒ 分组改动是**契约变更**，必须单独成批。

## 二、问题 ①：前后端如何适配

### 2.1 身份层：协议与登录方式

| 项 | 结论 | 依据 |
|---|---|---|
| 协议 | **OIDC**（不做纯 OAuth2；SAML2 不在插件内实现） | 本仓零依赖无 XML 栈，自研 XML-DSig 与「未通过产物校验不得部署」纪律冲突；阿里云 IDaaS 的 SAML 入方向**仅企业版**，OIDC 免费版即支持 |
| Google | Authorization Code + PKCE（`openid email profile`） | A 卷 §1 |
| 阿里云 | IDaaS / EIAM 标准协议应用 | 免费版仅 10 账户 / 3 应用、**不支持标准应用** ⇒ 企业采购必须**标准版起**；且**标准版日志仅 7 天 ⇒ 审计必须自建** |
| 自建账号 | 保留，与 SSO 账号**归并到同一 `identity` 表** | 用户原话「除去自建身份账户系统之外尝试接入 Google，阿里云等等」 |
| 账号归并 | `identity(provider, subject)` 唯一键；邮箱验证后才允许自动关联 | 防「同一人用两个 IdP 登录变成两个用户」 |

### 2.2 ★ 回调怎么落地（本轮最硬的发现）

**实测事实**（`artifacts/_r2-guard-proof.mjs`，10 例真机）：

| 请求 | 结果 |
|---|---|
| `Host: 127.0.0.1` | 200 ✓ |
| `Host: 192.168.1.50` / `example.com` | **403** |
| `Sec-Fetch-Site: cross-site` | **403** |
| `Origin: https://accounts.google.com` | **403** |

⇒ **「把回调地址指向现有插件路由」被实测否掉**（不是理论风险，是 `lib/index.js:9048` 的硬判据）。

三条路线的**优先级（结合用户"远程操控"这条新信息后调整）**：

| 优先级 | 路线 | 为什么 | 风险 |
|---|---|---|---|
| **1** | **设备码（RFC 8628）** | 无回调 ⇒ 不受 `Sec-Fetch-Site` / 内网拓扑影响；且 A 卷发现**宿主自带 `ctx.authorization.registerFlow` + `session.notify({url})`，正是设备码的宿主原生形态** | Google 需为"有限输入设备"类型申请；阿里云需核实支持 |
| 2 | 企业内网 Web 应用客户端 | `https://<内网域名>/api/dsh-auto-memory/identity/callback` | 需**替换**（非放宽）回环守卫为「同源 + 会话」，**必须与 cookie 会话同批上线** |
| 3 | 本机临时回环监听 | CLI 惯例（`gh`/`gcloud`） | ⚠️ **用户的远程操控场景下，`127.0.0.1:<port>` 指向用户那台机器而非宿主** ⇒ 只在「浏览器与宿主同机」时成立。**且插件能否 `listen` 额外端口未验证**（宿主契约只给 `register*`） |

**⚠️ 必须先确认的一件事**：用户说「我这是用的远程操控插件，本来应该是 127.0.0.1:3080」。
- 若是**端口转发/隧道**（远端 3080 映射到本地）⇒ 浏览器 Host 仍是 `127.0.0.1`，现有 54 条路由**恰好还能工作**；
- 若是**直连宿主内网 IP/域名** ⇒ 按实测 ③/④，**54 条路由全部 403、界面整体不可用**。
⇒ **这是团队版的前置问题，不只是登录问题。**

### 2.3 ★ DSH 新版「DeepSeek 账号登录」可能改变整个方案

- 本机实测 dsh 版本 = **`0.1.6-alpha.2`**，包内**未检到** account/login 实现（`auth` 命中的是 ACP 协议桩与 `authMethods: []`）⇒ **本机这个版本还没有**。
- 若新版**向插件暴露身份**（如 `ctx.identity`）⇒ 插件只需「把宿主身份映射为成员 + 写入 `actor`」，**Google/阿里云大量工作可省**，且身份贯穿宿主与插件更一致。
- 若新版只是**登录 DSH 客户端**而不暴露给插件 ⇒ 插件仍须自建。
- ⇒ **建议把这条列为最高优先级的前置确认项，不要先动手写 SSO。**

### 2.4 前后端职责分工（用户点名要的）

| 环节 | 前端 | 后端（插件宿主侧） |
|---|---|---|
| 登录入口 | 登录页 / 「用 Google 登录」按钮 | 生成 `state`+PKCE，发起授权 |
| 回调落地 | **不参与**（用设备码则展示 code+短链） | 受控回调路由 或 轮询取令牌 |
| 会话 | 携带 cookie（同源，无需额外头） | **新增**：cookie 校验、会话表、CSRF |
| 令牌续期 | 无需感知 | refresh + 吊销 |
| 身份展示 | 「谁写的」徽标 / 头像 / 在线状态 | 提供 `identity` 只读端点 |
| 权限可见性 | 按角色隐藏/禁用控件 | **每个写路由都要校验**（当前 54 条只有回环判据） |
| `actor` 注入 | — | 提交单据 `actor` 由**服务端**填，不信客户端 |

**改动性质说明（重要）**：本仓现约定「新开路由搭 `/config` 便车」，但**身份不能塞进 `/config`**（那是配置读写语义，POST 会落盘）⇒ 身份需要 **2 个只读端点**，这是对该约定的**受控例外**（A 卷 §0.4）。

### 2.5 迁移六步（A 卷口径，逐条可执行）

`S0 基线冻结 → S1 单人登录最小可用（2 路由 + 1 IdP + 默认关闭开关）→ S2 actor 升级 → S3 hub 分片 → S4 权威服务端 → S5 多 IdP + 自建 → S6 企业交付项`

## 三、问题 ②：前端重构 + 大厂取经

### 3.1 「晕」的诊断（三重取证一致）

**主代理实测** + **B 卷穷举**，结论一致且互补：

| 层级 | 事实 | 证据 |
|---|---|---|
| 设置页 | 1 个 `slots.register` 装下 **735 行**，内分 9 分区 / **80 个 `field()`** / 28 checkbox / 30 number / 13 select，**全部同时挂载** | `client.js:7667` / `:6989-6999` / `:7009` |
| 左侧 nav | **「假页签」**：`jumpToSection()` 只做 `scrollIntoView` ⇒ 用户以为在切 Tab，实际在滚动 | `:7003` |
| 视图页签 | **13 个**平铺（`overview/logs/refine/hub/storage/notes/plan/reflections/connect/calendar/search/workspaces/stats`） | `:5621-5623`（我已复核 = 13 ✓） |
| 交互范式 | **9 套并存**；「切换分区」3 种、「展开」4 种 | `:5555`/`:5678`/`:7006`、`:3115`/`:2304`/`:2305`/`:3361` |
| 术语 | **8 组冲突**；「工作区」×102 vs「项目」×31；`handoff` 一名三用 | `:331-333`、`:436`/`:7260`/`:5622` |
| 设计 token | 唯一 hex **56**、唯一 rgba **107**；**18 个 `--dam-*` 无一个是颜色**；状态色**三套并存** | `:2054`/`:2164`/`:7091` |

**线性膨胀的机械物证**：设置页 5 处注释**自述是「补接线」**（`:7204`/`:7227`/`:7247`/`:7264`/`:7324`）——一次审计又加了 5 个控件；`MemoryTabBody` 的 `stats` 分支缩进异常（`:5618`）+ `search` 裸兜底（`:5619`）= 两次追加的痕迹。

**一句话根因**（B 卷）：**「晕」不是信息太多，而是没有层级。** 唯一的层级信号是 `<h3>` 和提示文字。

> **主代理的补充**：`WorkspaceTab` 是 **2608 行单函数**（`L5128–7735`），内部**零子渲染函数** ⇒ 这是"没有层级的代码级成因"，也解释了重构必须**分批**。

### 3.2 ★ 重构的硬约束（本轮最有价值的发现）

**`lib/client.js` 的 UI 结构已被 177 项回归中一部分「字符串锚定守卫」固化。** 43 个套件读该文件，其中是结构硬锁的关键几条：

| 守卫 | 锁的内容 | 含义 |
|---|---|---|
| `smoke-test-s2-settings-panels.mjs:102` | 9 分区 key **与顺序**逐字相等 | ⚠️ 分组改动 = **契约变更**，不是纯 UI |
| 同上 `:145` | `scrollIntoView({behavior:'smooth'})` 必须存在 | 设置页导航被锁为**滚动式**，改真分页会红 |
| 同上 `:117`/`:152` | 面板块行数 100~130、必须**紧贴** semMode（行号差=1） | 搬块约束极密 |
| `smoke-test-panel-position.mjs:42/44` | `eq(bodyReuse,2)`、`eq(tabsReuse,2)` | `MEMORY_TABS()`/`MemoryTabBody()` 调用次数**恰好 2** |
| 同上 `:32-35`/`:60` | `panelTab` 三条逐字正则；不得往 `shell.overlay` 注册带 label 的第二页面 | 状态层不得重构为 `useState` |
| `smoke-test-v314-gate-scope-j.mjs:74`/`:79` | `--dam-accent` 必须在；`data-dam-tour-link` 计数 === 3 | 颜色 token 化必须继续用该变量 |
| `smoke-test-graph-mode.mjs:276/463/471` | `data-dam-key:boardMode`、看板三键、`data-dam-lane` 等必须在 | 看板 DOM 标记不得改名 |

**该守卫文件头部 `:1-18` 记录了真实事故**（改设置页前必读）：B1 分区重构把「⟳ 检测」「🧩 安装向导」按钮留在 engine、面板搬到 store；导航是滚动式 ⇒ 面板渲染了但落在**视口下方 6 个分区处**，用户报障原话**「引导页和检测页弹不出来」**。

### 3.3 不破锁的收敛路径（B 卷手法，我已理解其成立理由）

| 手法 | 为什么不撞锁 |
|---|---|
| `MEMORY_TABS()` 改为**派生函数**（`return MEMORY_NAV[activeGroup].tabs`） | 函数名/签名/**调用次数**全不变 ⇒ `eq(tabsReuse,2)` 仍绿，而 UI 收敛为 4 组 |
| `MemoryTabBody` 改**表驱动** | 不影响 `eq(bodyReuse,2)` |
| **最高杠杆单笔**：`field()` 加 `{advanced:true}` 默认折叠 | 首屏控件 **80 → 约 15**；且 `:102` 只看 `section('key', sectionLabels.key,[` 的**调用形态**，不看块内容 |

### 3.4 重构骨架与批次

- **L1 收敛为 4 入口**：今天 / 项目 / 团队 / 检索；L2 每入口 ≤4 项（硬约束）
- 13 个页签**全部有归属、零功能丢失**（`storage` 降入设置）
- **单机 / 团队按作用域三分法**：我的 / 这个项目的 / 这个团队的
- **7 批顺序**：A 结构就位（零感知）→ B 导航收敛 → **C 设置页分组（唯一需改守卫，必须独立成批）** → D 引擎块搬移 → E token 化 → F 降噪 → G 团队增量，**每批带验收判据**
- 设计系统：动效/间距**已有 12 个 token**，颜色**完全没有** ⇒ 追加 12 个语义色 + 6 个尺寸 token 进现有 `CSS` 数组（`:1576-2019`），零构建可落地
- ⚠️ **字号必须保留 `* var(--dam-scale)`**——用户 4 档缩放是已上线特性，直接替换 = 回归

### 3.5 团队维度落在哪

- 新增**独立 L1「团队」**（首版可用 `EmptyState` 上线 IA，**零后端依赖**）
- **不新增 `slots.register`**（规避 `:44` 计数锁与 `:60` 限制）

### 3.6 大厂取经（B 卷第 2 部分，17 条映射）

**最有价值一条**：**GitHub 的「谁负责」（CODEOWNERS，声明式配置）与「谁写的」（blame，追溯视图）必须分成两个机制** ⇒ 直接决定团队版「冲突提示」（需路由支撑）与「作者徽标」（只需展示）落点不同。

**「必须拒绝的 3 条诱惑」**：
1. 团队设置**只要在设置页再加一个 section** —— 会复制 R1 膨胀路径，且**会复现 s2 守卫记录的那次事故形态**；
2. 页签太多**加个「更多」折叠** —— 已是第 10 套交互范式，且把「可发现性问题」换成「不可发现问题」；
3. **先做一次全局配色统一** —— 方向对但**顺序错**：主因是层级问题，先统一颜色不会让人「不晕」，且违反「无确凿证据不得删除既有视觉表现」纪律。

## 四、用户裁定（2026-09-23 晚更新，**已解除两条阻塞/决策**）

> 用户原话：「放心，0.1.7alpha2 就可以登录了，别的不着急，我觉得开源系统不需要加密，客户可以自己加密，本地只留接口就行，现在可以派专家组的 agent 先用 HTML 做一份新版 UI 的 demo（teamwork 也要有），并写一个 HTML 的 proposal 给客户哄好了」

### 裁定 1（★ 架构级）：**登录由宿主提供，插件不自建账号体系**

- 依据：DSH `0.1.7-alpha.2` **已具备登录能力**（用户确认）。
- ⇒ **自建 IdP 集成方案作废**。插件侧只做：**成员映射**（宿主身份 → `memberRef`）、`actor` 注入、审计留痕。
- ⇒ 「Google / 阿里云登录」的实现位置从**插件**上移到**宿主**；插件**本地只留接口**。
- ⇒ 本卷 §2.2 的「回调怎么落地」三条路线（设备码 / 内网 Web 客户端 / 回环监听）**降级为背景资料**——若宿主代为完成登录，插件无需实现回调，`isLoopbackRequest` 与 `Sec-Fetch-Site` 的冲突**不再阻塞登录**。
- ⚠️ 但**回环守卫冲突本身仍然存在**（实测 10 例），它继续影响的是：**团队版能否经内网 IP/域名访问**。这条仍需确认（见下）。

### 裁定 2（架构级）：**开源不加密，加密交给客户，本地只留接口**

- 依据：用户原话「开源系统不需要加密，客户可以自己加密，本地只留接口就行」。
- ⇒ 记忆数据**本地明文存储**（开源可审计），**不做端到端加密**。
- ⇒ 企业若需加密，由客户在**存储层**自行施加；插件**预留加解密接口**。
- ⇒ 约束：**必须向甲方披露「当前为明文」**，不得暗示已加密。

### 裁定 3：本条工作线推进方式

- 派专家组做两件交付物：**新版 UI 的 HTML demo（必须含团队/teamwork 维度）** + **面向客户的 HTML proposal**。
- ⇒ 已产出共享契约 `docs/internal/TEAMWORK-R2-UI-CONTRACT-20260923.md`（色板/字体/IA/8 屏/禁用词），两件产物同源。
- 其余待决事项（S1 落点、viewer 可见性、embedding 统一）用户明确「别的不着急」。
