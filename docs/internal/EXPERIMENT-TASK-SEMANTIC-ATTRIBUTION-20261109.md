# 任务书 · 语义归属实验 v3（验证 1.4 的 L2 排序 + L3 模型裁决）

> 2026-11-09 · 关联：施工总表 1.4 / §15 候选排序器 / 批次 5.1 铭文
> 本文件只出实验方案与数据包说明，不含产品代码改动。
> **v1 / v2 数据包已作废**（原因见 §10），现行数据包是 **v3**。

## 0. 为什么做这个实验

1.4 要解决的是「未传 eventId 时这条日志挂哪个事件」。现行判据（词袋重合率 ≥0.34）在 211 条真实日志上实测：

| 事实 | 实测值 |
|---|---|
| 按现行判据（只比「最近更新」事件）通过 | **0 / 211 = 0%** |
| 扫全部 47 个 active 取最高分 | 12 / 211 = 5.7% |
| 理论最高命中率（事件词集 ÷ 日志词数）中位 | 0.351；另有 45.9% 条目数学上不可能过线 |

⇒ 不是「阈值太严」，是**口径错配 + 候选集只有 1 个**，等于每条日志都新建事件。

语义模型（C2 e5-small q8，384 维）实测（金标=独占标识，n=37）：name+summary top-1 48.6%；+四段 32.4%；
**+最近 3 检查点 top-1 54.1% / top-3 75.7%**；全体 top-1 余弦挤在 0.905–0.928、top1−top2 分差中位 0.006–0.012。

⇒ **语义能排序、不能靠阈值判定**。1.4 因此定为四层：L1 标识硬判 → L2 向量排序 → L3 模型裁决 → L4 词法兜底。
本实验只验证 **L3**：给定 L2 候选（及 L1 信号），模型能不能判对。

### 2.1 案例从哪来、金标怎么定（**这是 v3 与 v1/v2 的关键差别**）

- 案例：2026-11-04 起的真实日志条目 92 条（`WS/*.md` 的 `- HH:MM [kind:…] 正文` 行）。
- **金标 = 检查点溯源（provenance）**，不用规则猜：每条日志都能在事件库里唯一定位到「它当时被写进的那个事件」。
  - `kind=attach`（77 条）：该事件在本条之前已有检查点 ⇒ 决策时它**已存在**，正确动作是挂它。
  - `kind=new`（15 条）：本条就是该事件的**第一个检查点** ⇒ 决策时该事件**尚不存在**，正确动作是新建。
  - 其中 5 条 attach 在遮蔽后「无可辨识材料」⇒ `answerable:false`，**不进准确率分母**（否则不可答）。
- 只取 2026-11-04 起，因为此前的归属由旧逻辑「无脑挂最近更新的事件」决定（#543 之前的缺陷），**其归属不可信**。

### 2.2 遮蔽（防泄漏）—— v1/v2 就是死在这里

因为案例是**已经写进库的历史条目**，事件材料里天然含「本条日志原文」，模型可直接字符串匹配得答案（v1 试点 c001 就是这么「对」的）。v3 做了三件事：

1. 候选事件材料里**剔除与本条日志相同（或为其前缀）的检查点**；
2. 若事件名与本条日志高度重合（事件由该条日志创建），该候选的 `name` 置 `null` + `nameMasked:true`；
3. `kind=new` 的 case，把「由本条创建的那个事件」**从候选池里整体移除**（决策时它不存在）。

体检：v3 cases 里目标日志原文出现次数 = **0**；含 `goldSource` = false。

## 3. 两轮独立判定

| 轮次 | 允许看 | 可挂集合 | 输出 |
|---|---|---|---|

### 3.1 口径裁定（2026-11-09，试点后由用户侧裁定）

**问题**：「修复批次执行日志（W1-TOOLS / W1-TEAM 这类）算伞状编排事件的执行阶段，还是算独立工作线？」

**裁定**：**算伞事件的执行阶段 ⇒ attach 伞事件**（置信 medium，不给 high）。规则：

1. 日志是**某批次的进度 / 子项 / 收口**，且候选伞事件的 name/summary/checkpoints 描述的正是该批次 ⇒ `attach`；
2. 日志**开启新的独立工作线**（新主题 / 新范围 / 新 agent，不属于任何在跑批次）⇒ `new`；
3. 分不清时才用「宁拆勿并」作 tie-breaker；但「L1 唯一命中 + 时间线自洽 + 全库扫描无 founding 事件」属于**分得清**，不是分不清。

理由：本项目的主导惯例是「一次批量施工 = 一个事件，各子项落地日志 = 该事件的检查点」——金标分布里两个批次伞事件占 attach 金标约六成（具体数字不写进执行方可见材料，避免泄漏）。

**另两处口径纠正**：

- A 轮口径中「候选检查点含本条日志原文 ⇒ high」**必须删除**：v3 已遮蔽（剔除同文检查点 / 派生事件名置 null），看不到原文属正常；若仍看到高度重合文本，应作可疑信号上报。
- A 轮按盲态证据**如实记录**，判 `new` 就写 `new`，不得回改；A/B 差异本身就是实验要量的量（A 的候选覆盖能力有限）。

1. **覆盖是硬上限**：语义 top-5 只覆盖 33/72（45.8%）的正确答案；加上 L1 才 53/72（73.6%）。
   ⇒ attach 准确率必须与覆盖一起看，否则分母里混进了「候选里根本没有正确答案」的 case。
2. **纯 L1 会误并**：15 条新事里它判挂 4 条；纯语义第一名更糟，15 条全挂（误并 15/15）。
   ⇒ L3 的价值 = 在 L1 点不中的地方补判 + 在 L1 指错时否决。

## 11. 实验结果与判定（v3，2026-11-09）

### 11.1 两轮实测（执行方：另一对话；A 轮 1,563s / B 轮 300s）

**A→B 翻转 13 条，13 条全部判对**（A 判 new ⇒ B 判 attach 且命中金标），**0 次翻转变错**。这是 L1 信号价值最直接的证据。

### 11.2 预注册判据核对

| 判据 | 结果 | 结论 |

### 11.3 数据包缺陷（已定位，不是模型问题）

v3 的 nameMasked 规则**过宽**：只要「事件名 ≈ 日志开头」就遮蔽，但这在本项目是常态（日志常以事件名开头复述），并不等于「该事件由本条日志创建」。结果 6 条（c176/c180/c190/c191/c192/c194）的金标事件名被误遮蔽，模型据「名遮蔽 ⇒ 派生自本日志 ⇒ 自成事件」判 new —— 判定逻辑正确，输入被破坏。

**已生成修复包**：artifacts/_ranker-fix-20261109/cases6.jsonl（6 条，金标事件名恢复可见、仅剥本条检查点、候选与 identifier 重算）。剔除这 6 条后的指标：A 23/27 = 85.2%，B 36/47 = 76.6%。

### 11.4 B 轮剩余 11 条错误的性质

| 类别 | 条数 | 性质 |
|---|---|---|
| 批次执行日志被判为「独立工作线」（fe-wizard 批 0–4 / P6，c130–c139） | 7 | **违反已裁定口径**（批次执行子项应 attach 伞事件），模型据「独立工作线」自行改判 |
| alpha.7 战役批次内部子事件辨识（c157/c168/c169/c170） | 4 | 把战役日志挂到战役内某个子事件或判 new，未挂到战役事件本体 |

⇒ 两类都是**判定口径 / 战役事件辨识**问题，不是覆盖率或遮蔽问题。

### 11.5 判定（按预注册规则，不做事后放宽）

**未达 H2 ⇒ 不接入自动 attach。**

但三项硬证据支持「提示模式」而非「放弃 L2/L3」：
1. 安全维度完胜：A/B 误并均 **0/15**，而 ruleL1 是 4、embTop1 是 15 —— 这正是 #543 最痛的点；
2. A→B 13 次翻转全对，说明 L1 信号 + 模型判断的组合是有效的；
3. 覆盖是硬上限（A 45.8% / B 73.6%），未命中的大部分根本不是判断问题。

**建议的接线形态**（待用户裁定）：

| 层 | 动作 |
|---|---|
| L1 独占标识命中 | **自动 attach**（已有 92.9% 精度的实测支撑） |
| L2 语义 top-3 + L1 候选 | 写进**工具回执**作提示，不自动挂 |
| L3 模型判断 | 由模型在下一轮带 eventId 重调（一次性提示，不重复打扰） |
| 兜底 | 无信号 ⇒ 新建 + 回执注明「未自动归属」 |

**下一步（成本很低）**：修复包 6 条重判（A/B 各一次，约 5 分钟）；合并后重算 H1/H2，再定最终形态。
