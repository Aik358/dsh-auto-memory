## 六、问题 3：归属判据为什么没拦住无关内容？

### 6.1 词袋 0.34 门的确切实现（问题 3.1）

`lib/index.js:24709-24737`（孪生实现 `lib/event-write.js:240-264`）：

```js
// 分词：单个汉字 / 或 [a-z0-9_]{2,} 连续串；去 40 个中文停用词
noteTok = 去重( log 正文的 token )         // ← 只有日志一侧进集合
evTok   = 去重( _latest.name + _latest.summary 的 token )
ratio   = |noteTok ∩ evTok| / |noteTok|     // ← 分母恒为「日志 token 数」
attach  ⇔ ratio >= 0.34
```

**分子分母怎么算**：
- 分子 = 日志 token 里出现在「**最近更新的那一个** active 事件」的 name ∪ summary 里的个数；
- 分母 = **日志自身**的 token 数（去重后）。

**为什么大量无关内容能过门 —— 三个可证的机制**：

1. **分母与被比较的事件无关**。事件侧只影响分子，所以「事件 name+summary 越长 ⇒ 分子越大 ⇒ 越容易过门，而分母不变」。这是单调的「富者愈富」：
   - 实测事件侧词集规模：big5 = 65 / 57 / 90 / 103 / 50，**小事件（≤3 条）中位 = 19** ⇒ 大事件的词集是它的 **2.6–5.4 倍**。
   - 也就是说：**同一个事件越被写、summary 越被写长，它吸住下一条无关内容的能力就越强**，而它每吸收一条又会 `updatedAt = now`（`event-store.js:1032`）⇒ 永远是 `_latest` ⇒ 正反馈闭环。
   - 这个闭环在源码注释里被承认过（`index.js:24590-24593` 讲 `#543` 的「正反馈污染」），但**只对 memory_log 修了**。

2. **只在「最近更新的一条事件」上比**（`_latest`，`:24622-24629`）。不与其他 46 个 active 事件比 ⇒ 只要比值恰好对上一个，就挂；其它候选根本不参与。

3. **两个「无证据即挂」兜底**（`:24726`、`:24731`）：
   ```js
   if (!_noteTok.length) return { decision:'attach', reason:'legacy', event:_latest }
   if (!_evTok.size)     return { decision:'attach', reason:'legacy', event:_latest }
   ```
   语义是「没证据 ⇒ 挂最近的」——这与 `#543` 的「**宁拆勿并**（误拆可逆、误并不可逆）」方向相反。实测这两个分支在真实数据上几乎不会触发（停用词清空后词集不可能为空），所以它是**代码气味，不是本次主因**。

**实测：这门在真实数据上的通过率**

| 输入 | 条数 | 过 0.34 门 |
|---|---|---|
| 全库检查点 vs 当前 `_latest`（`evt_23e2976e`） | 763 | **2.1%**（16 条） |
| 全库检查点 vs **自己所属事件** | 763 | **4.8%**（37 条） |
| 其中 `memory_log` 的、落在 big5 的 | 217 | **0.9%**（2 条） |

⇒ **门其实是「很严」的，它不是把无关内容放进来的那道闸。** 这一条推翻了任务书的问题设定（「门失效或压根没走」）——**答案是「压根没走」**，见 6.2。

**门的区分力（AUC 式，n=534）**：拿每条 big5 检查点对「自己所属事件」的比值 vs 对「其它 4 个 big5」的比值中位：

```
同事件更近 = 244 (45.7%)   相同 = 24   同事件更远 = 266 (49.8%)
```

**「同事件更远」比「更近」还多** —— 这个口径在本数据上**没有区分力**（还不如抛硬币）。原因是 6.1-1：大事件的 summary 词集很大，而检查点大多是短日志，落在谁身上都差不多。

### 6.2 有没有兜底路径绕过这门（问题 3.2）—— 有五条，其中一条是主因

### 6.3 `appendHandoffCheckpointPre` vs `appendCheckpointPre`（问题 3.3）—— 是，前者完全不做归属判断

```js
// lib/event-write.js:701-711  ★ appendHandoffCheckpointPre
let evId = String(opts.eventId || '')
if (!evId) {
  const store0 = await readStorePre(storePath)
  const active = resolveActiveEventPre(store0)     // ← 只按 updatedAt 取最大
  if (active) evId = active.id
  else { /* 建新事件，名字取 sections.goal 或「交接账本」 */ }
}
// 然后直接 eventStorePre.append(storePath, evId, { checkpoint: ckPayload })
```

对比 `appendCheckpointPre`（`event-write.js:384-431`）：

| | `appendCheckpointPre` | `appendHandoffCheckpointPre` |
|---|---|---|
| 归属 | **无**（要求调用方给 `eventId`，`:386` 缺则抛错） | **无**（自己用 `resolveActiveEventPre` 猜） |
| 输入校验 | `text` 非空（`:388`） | `ledgerText` 非空（`:699`） |
| 额外产出 | — | 解析四段 + 写 `goal/state/dead/next` + 可带四类感知（`:731-750`） |
| 幂等 | idemKey 由调用方给 | idemKey = `kind:<sha12(路径+全文)>`（`:737`） |

**结论：两者都零归属判断；区别只是 `appendCheckpointPre` 把「选谁」的责任推给调用方（因此调用方可以做出正确选择，也可能做错），而 `appendHandoffCheckpointPre` 自己拍一个「最近更新」的默认值。**
真正**有**归属判断的是 `pickActiveEventByTopicPre`（`event-write.js:197-265`）—— 而它**在这条链路上没有任何调用点**（全库 3 个调用点：`:198` 自引用、`:704`、`:800`，后两者都是 `resolveActiveEventPre`）。

### 6.4 有没有「最近事件优先」把新内容吸进大事件（问题 3.4）—— 有，而且源码明写了「故意不改」

- 定义：`lib/event-write.js:110-131`
  > `① resolveActiveEventPre —— 找当前活跃事件。判据：status === 'active' 且 updatedAt 最大。`
- 使用点：`event-write.js:704`（`appendHandoffCheckpointPre`）、`event-write.js:800`（`mirrorPlanSectionsPre`）。
- **正向反馈的机械保证**：`event-store.js:1032` `if (appended) ev.updatedAt = now0()` —— 每收一条检查点就刷新自己，于是**永远是 `_latest`**。
- **为什么没修（原文引用，这是最关键的一段）** —— `lib/index.js:24595-24596`：
  > `★为什么不动 resolveActiveEventPre 本体：它还被 handoff(:536) 与 plan(:630) 复用，改它等于顺手改账本与白板的归属语义，超出本 issue 范围。`

⇒ **`#543`（2026-11-04）的修复被明确限定在 memory_log 一条路上，`memory_note` 那条被刻意留在了旧语义。** 这就是「判据没拦住」的直接答案：**不是门失效，是门根本没装在那条路上。**
