## 一、一个需要澄清的口径：「输入tokens」不是 prompt 大小

账单的列恒等式是这样的（847 行全部吻合，可复算）：

```
输入tokens + 输出tokens + 缓存写入tokens + 缓存读取tokens = 总tokens
```

所以「输入tokens」是**本次未被缓存覆盖的部分**，真实 prompt 应该是：

```
真实 prompt = 输入tokens + 缓存读取tokens
```

您举的那条例子正好能说明这一点：

| 您的记录 | 账单实际值 |
|---|---|
| `prompt=3,531  read=238,080` | 输入=3,531，**缓存读=238,080**，真实 prompt = **241,611** |

一条 3.5k 的请求不可能读出 23.8 万的缓存，所以这里应该是把「输入tokens」当成了 prompt 长度。这个列名确实容易误读，我们一开始也核对了一遍才确认。

## 二、由此两处论据需要修正

**1）关于「71 条小切片」**

按您的口径（输入 < 5000 且缓存读 > 20 万）筛出来是 **577 条**，而这些行的真实 prompt 是 **203k–660k**、命中率 **99.8%**——它们其实是缓存工作得**最好**的那一批，不是切片。

**2）关于「GLM 大 prompt 同样 99% miss」**

用「输入tokens ≥ 5万」筛选，本质上是在挑未命中的行（输入大 ⟺ 没命中），会得到循环结果。改用真实 prompt 筛选：

| 筛法 | GLM 结果 |
|---|---|
| 输入tokens ≥ 5万 | 85 条，未命中 84 条 = 99% |
| **真实 prompt ≥ 5万** | **668 条，命中 87.2%**，未命中 84 条 = 13% |

而且 **GLM 的真实 prompt 中位数是 410k，比 DeepSeek 的 330k 还大**；GLM 在 prompt ≥ 300k 的 518 条请求上命中率仍有 **87.5%**。所以「GLM 只是请求小」这个前提可能不成立。

## 三、我们这边的观察：更像是多账号路由，各账号缓存独立

补充一点可能对您有用的现象——**恢复是「阶跃」而不是「缓慢回升」**：

```
21:30  命中 67%
21:40  命中 54%
21:50  命中 93%   ← 单桶跳 39 个百分点
22:00  命中 90%
```

缓存自然回温应该是缓坡，一刀切上去更像**路由发生了切换**。三条旁证：

**① 固定前缀读值随时段漂移**（不同账号的系统提示长度不同）：

```
20 时段：1024 / 2176 / 13516 ~ 18304（13–18k 一族）
21 时段：1408 / 19072 / 36186 / 39040 / 39168 / 45312 / 56960 / 62208 / 71168
22 时段：16768 / 19072 / 36186 / 39040 / 39168（收敛）
```

**② 同一分钟内两个上下文并存、且各自都命中**：

```
21:44  679k → read=675072  命中 99.4%  ✓
21:44  503k → read=36186   命中  7.2%  ✗
21:44  229k → read=229248  命中 99.7%  ✓
21:45  233k → read=36186   命中  7.2%  ✗
21:45  233k → read=233088  命中 99.9%  ✓
```

同一时刻，A 会话和 B 会话的缓存都完好在，偏偏 C 会话只读到系统提示——单实例似乎解释不了，更像请求落到了不同实例、各自持有独立的缓存池。

**③ `36186` 更像账号指纹，而不是容量上限**：它只在部分请求上出现，且 20/21/22 三个时段能读到的固定前缀数值并不相同。所以确切说它是「某个账号的系统提示长度」，而不是一个统一的上限。

## 四、想请您协助确认的几点

1. **DeepSeek 通道是否配置了多个上游 Key / 多个实例？调度策略是轮询、随机还是按负载？**
2. **能否提供该时段的路由记录**（每个请求落到哪个账号/实例）？有这张表基本就能完全闭合。
3. **是否可以考虑对同一会话做粘性路由**（固定到同一实例）？如果缓存池确实按实例隔离，这一项应该能直接改善。
4. **上游返回的 `prompt_cache_hit_tokens` 是否有做转换或丢弃**？如果能给出上游原始字段，我们可以交叉验证。

另外说明一下：我方客户端这边没有做拆分会话、改写历史或重排消息的动作——173 条请求的真实 prompt 最小 20k，全程只有 1 次回落，是从 22k 单调增长到 672k 的**单会话连续轮**。这一点也可以排除掉。
