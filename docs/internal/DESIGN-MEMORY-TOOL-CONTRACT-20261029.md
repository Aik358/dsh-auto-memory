## §1 设计原则与成本账

### 1.1 三条不可让渡的原则

| # | 原则 | 依据（实测） |
|---|---|---|
| **P1** | **已有强判据的地方不重复建** | `checkHandoffCriteriaPre` 的 H1-H4 实测拒绝 6/7 个坏账本，且不落盘 |
| **P2** | **回执必须有硬预算** | 注入面 23,562 字符；单次回执若失控会直接吃掉注入预算 |

### 1.3 ★对任务书 §3 的三处事实纠正（本轮最重要）

任务书 §3 的数字来自前序调查，我复核时发现**三处口径错误**，且**根因都是「迁移数据混入运行时统计」**：

| # | 任务书说 | 实测真相 | 根因 |
|---|---|---|---|
| **C1** | 「553 检查点里四段齐全的只有 **11%**」 | **口径错误**。11% 是「goal+state+**next** 全非空」，而提示词明说「dead 无则空串」，`next` 也允许空。正确口径「四段全空率」= **6%**（运行时 8%） | 判据选错了字段组合 |
| **C2** | 「模型会用感知，只是不触发」（据 14 条 userPercept 全 stage 正确） | **部分成立但归因错**。76% 的感知集中在**单个事件**（`evt_89786878`「项目白板」），且**79% 来自 `memory_note(handoff/plan)` 路径**，来自 `memory_event(append)` 的独立写入仅 7/38 | 未区分写入路径 |
| **C3** | 「members 填充 94%，不是阻塞」 | **成立但含义反了**。36 个迁移事件 **members 100% 填充；四类感知 0 条**。94% 是**迁移子代理按提示词强制产出**的，不代表模型日常行为 | 未区分迁移 vs 运行时 |

**⇒ 关键修正：存量 53 个事件中，36 个（68%）是 `memory_upgrade` 迁移产出，17 个（32%）是运行时自发。**

```
迁移产出（2026-10-27T03:12 同一分钟建 36 个）      36 事件 / 141 检查点
  检查点四段齐全率  99%      四类感知 0 条      quoteRef 0 条
运行时自发                                        17 事件 / 412 检查点
  检查点四段齐全率  92%      四类感知 38 条     quoteRef 10 条
```

**这条纠正直接改变方案形状**：不能说「模型不会写四段/不会写感知」（迁移数据把这两项统计都拉高了或拉偏了），而要说「**运行时路径里 `memory_event(append)` 是感知写入的荒地**」。

### 2.2 P0-1：WAL 半渡态（真缺陷，必须前置）

**现状**（`lib/index.js` L21953-22010）：

```
Phase 1  appendHandoffCheckpointPre(...)   ← 先写事件，零内容校验
Phase 2  writeHandoffLedger(...)           ← 再过判据门，不合格 ok:false
Phase 3  失败 → 追加 kind='handoff-write-failed' 补偿检查点
```

**实测后果**：坏账本进事件库（唯一真相源），每失败一次多两条。真实库已发生 **3 次**（3 条 `plan-write-failed`）。

**方案：Phase 0 前置预检（纯函数，零 IO）**

```js
// lib/index.js  memory_note 的 kind=handoff|plan 分支，Phase 1 之前插入

// Phase 0：判据门预检 —— 不合格直接拒绝，Phase 1/2/3 全不执行
if (engine.config.criteriaGate !== false) {
  const probe = args.kind === 'handoff'
    ? checkHandoffCriteriaPre('# 交接账本 · ' + engine.memToday() + ' ' + nowHm() + '\n\n'
        + writeH.split(/\r?\n/).filter((l) => !/^#\s*交接账本/.test(l)).join('\n').replace(/^\n+/, ''))
    : checkPlanCriteriaPre(writeH)
  if (probe && !probe.ok) return 'memory_note: ' + criteriaRefusalTextPre(probe) + HANDOFF_SKELETON_HINT
}
```

**三个必须满足的实现约束（已逐个实测验证）**：

| 约束 | 实测结论 | 证据 |
|---|---|---|
| ① 判据门是纯函数（可安全前置） | ✅ `wb-contract.js` 只 import `node:crypto` 与 `./handoff-anchor.js`，后者零 import，无 `await` | `_probe-design-wal.mjs` §② |
| ② 前置判定与 Phase 2 判定一致 | ✅ 7 个用例**零翻转**（用 `fullText` 口径构造时） | 同上 §③ |
| ③ 成本可忽略 | ✅ 平均 **0.221 ms**（对照：读 1.5 MB store = 9 ms） | 同上 §① |

**★负路径（不这么做会错）**：若沿用现在的顺序，每一次「判据门拒绝」都会在事件库留下 2 条不可撤销的脏检查点。实测已发生 3 次；按用户当前的账本产出频率（603 篇），拒绝发生率哪怕 1% 也会持续累积。

**语义重新表述（回答 §8 问题 5）**：

> 原文：「事件优先（WAL）」= 先写事件再写文件，保证事件不丢。
>
> 新表述：**「校验优先，事件其次」** —— 校验（纯函数、零副作用）前置于所有写入；通过后才按 WAL 顺序写事件与文件。理由：WAL 的目的是「保证事件不丢」，而**脏数据进事件库不是「不丢」，是「丢不掉」** —— append-only 下它永远无法删除。⇒ 语义从「先写事件」修正为「**只允许合格内容进事件**」。

### 2.3 P0-2：检查点软校验（**不做硬拒**）

**判据**（在 `memory_event` 的 `append` 分支计算，零额外 IO）：

```js
const ck = args.checkpoint || {}
const quad = { goal: String(ck.goal||'').trim(), state: String(ck.state||'').trim(),
               dead: String(ck.dead||'').trim(), next: String(ck.next||'').trim() }
const quadEmpty = !quad.goal && !quad.state && !quad.dead && !quad.next
const textHas = String(ck.text||'').trim().length > 0
const kind = String(ck.kind || 'progress')

// 不算硬伤：log/state 类检查点天然是流水
const QUAD_EXEMPT_KINDS = new Set(['log', 'state', 'plan-write-failed', 'handoff-write-failed'])
```

**分级（回答 §8 问题 2）**：

| 情形 | 判定 | 行为 |
|---|---|---|
| `kind ∈ {log,state}` 且四段全空 | **正常** | 静默接受（实测这类占 274/553） |
| `kind ∉ 豁免集` 且四段全空 且 `text` 非空 | **软警示** | 接受 + 回执提示（不拒绝） |
| 四段全空 且 `text` 也空 | **硬拒** | 拒绝（`appendCheckpointPre` 已有该判据，`eventStorePre.append` 层缺失，需对齐） |
| 四段全空白符 `" "` | **按空处理** | 实测空白符会**原样落盘**，判据必须 `trim()` |

**为什么不做硬拒（负路径）**：实测 `handoff` 类检查点四段全空率 **14%**（71 个里 10 个），`log` 类 8%。硬拒会让这部分正常节奏断裂，而其中 10 条是**存量**（append-only 无法补），硬拒只会让模型面对无法修复的历史。

### 2.4 P1-1：`calendar_add` 格式校验

**现状**：`lib/index.js:13857` 仅校验 `title` 非空且无换行。

**补三条（都是确定性校验，零误判）**：

```js
if (!/^\d{4}-\d{2}-\d{2}$/.test(String(item.date || ''))) throw ... '日历日期必须是 YYYY-MM-DD，收到：' + item.date
if (!/^(\d{1,2}:\d{2}|--:--)$/.test(String(item.time || '--:--'))) throw ... '日历时间必须是 HH:MM 或 --:--'
if (/^(00|2[4-9]|[3-9]\d):/.test(String(item.time||''))) ... // 小时越界
```

**负路径**：现在 `calendar_add({title:'x', date:'下周三'})` 会**接受**并把 `下周三` 原样写进 CALENDAR.md，之后 `calendar_list` 按 `date` 排序时该条落在字符串序的错误位置。

## §3 B 类：回执引导框架

### 3.1 框架形态（新建 `lib/receipt-hints.js`，纯函数零 IO）

```js
/**
 * buildReceiptHintPre(kind, ctx) → string（''=不提示）
 *
 * 五条硬约束（全部来自实测）：
 *   ① 单条 ≤ 180 字符（现有回执 36-253；注入面 23,562；180 ≈ 0.76%）
 *   ② 静默优先：拿不到数据就返回 ''（绝不输出「不确定」的猜测）

 *   ④ 可关：config.receiptHints !== false

 */
```

### 3.2 触发条件与频率控制（可判定判据）

### 3.3 §8 问题 3 的答案：**零额外 IO（有硬证据）**

**实测结论**（`_probe-design-io.mjs` / `_probe-design-io2.mjs`）：

```
真实最大 store = 1,500.1 KB（11 事件 / 412 检查点）
  readStorePre 单次        = 8.0 – 9.0 ms   ← 读盘 + JSON.parse
  从已解析 store 取回执字段  = 0.0015 ms     ← 占解析成本的 0.02%
```

⇒ **判据：能在已读的 store 上算，就绝不另起一次读盘。**

**三处「数据已经在手里」的确证**：

| 位置 | 已经持有的数据 | 现在丢掉了什么 |
|---|---|---|
| `appendHandoffCheckpointPre`（无 eventId 时） | `resolveActiveEventPre(store0)` 返回完整 `active.event` | 只回传 `{eventId}`，丢掉 `name`/`checkpoints.length`/`updatedAt` |
| `eventStorePre.close` | `mutatePre` 内已找到 `ev` 全对象 | 只回传 `{ok, alreadyClosed, event}`；**注意 event 是全对象，其实够用** |
| `eventStorePre.append` | 返回 `checkpointCount` | 缺 `name`（但调用方可用 `args` 判） |
| `refreshEventStatePre` | 已算 `pickT2EventsPre(events, 2)`（= filter active + sort updatedAt desc） | 只落地 `slimEventT1`；**首项与 activeCount 都算过** |

**方案**：`refreshEventStatePre` 里追加一行投影（**无新增 IO**）：

```js
// 已有：this.state.slimEventT1 = events.filter(active).sort(updatedAt desc).map(...)
// 追加（同一份 events，零额外 IO）：
this.state.receiptCtx = {
  activeTop: picks[0] ? { id: picks[0].id, name: picks[0].name,
                          cps: (picks[0].checkpoints||[]).length,
                          updatedAt: Number(picks[0].updatedAt)||0 } : null,
  activeCount: events.filter((e) => e && e.status === 'active').length,
}
```

**★负路径**：若每个工具都自己 `readStorePre` 一次，在真实最大工作区（1.5 MB）上每次多 **9 ms**，且 `memory_event` 的五个 action 都会各多一次 —— 全部是纯浪费。

**缓存失效**：`refreshEventStatePre` 已在每个 action 之后调用（`memory_event` 五个分支 + `memory_note` 事件侧），所以 `receiptCtx` 天然是最新的。**无需另设失效逻辑**。

## §4 四场景逐条设计（全文案 + 字符数）

### 场景 1 · `memory_note(kind=handoff)` 之后

**现状回执**（实测 174 字符）：

**方案 · 成功路径**（追加 ≤180）：

**方案 · 拒绝路径**（替换现有「请补齐后重试。」8 字）：

```
<可验证的完成标准>

<可直接执行的第一步，带文件路径或命令>
```
（约 **210 字符**；替换后净增约 200，但**只在被拒时出现**）

**★关键补充（必须做）**：现有拒绝文案有个实测缺陷 —— 判据门报的是 `H2: 任务状态(0 字符)`，但**没有告诉模型「20 字符」这个阈值**（阈值在代码里，`CRITERIA_LIMITS_PRE_V1.sectionMinChars = 20`）。⇒ 骨架模板必须显式带上阈值说明，否则模型会反复写 5-10 字然后被连拒。

### 场景 2 · `memory_event(create)` 之后

（实测 7/12 个工作区 active > 2，**这条提醒有真实价值**）

### 场景 3 · `memory_event(close)` 之前/之后

**⚠️ 关键设计约束（回答 §8 问题 3 的收口部分）**：`close` 之后 append-only **不能再补感知**。所以：

**方案 · 收口前检查（推荐，价值高于收口后）**

```js
// memory_event 的 close 分支，调 eventStorePre.close 之前
if (!args.confirmEmpty) {
  const ev = await eventStorePre.detail(storePath, id)   // ★已有 API，无新增实现
  const c = ev && ev.ok ? ev.event : null
  if (c) {
    const perceptEmpty = !(c.userPercept||[]).length && !(c.sharedGround||[]).length
    const cps = (c.checkpoints||[]).length
    if (perceptEmpty && cps >= 3) {
      return 'memory_event: close 前请确认——该事件有 ' + cps + ' 个检查点但 0 条感知。\n'
        + '若本次有实质性进展，建议先用 action=append 补 userPercept/sharedGround；\n'
        + '若确实无需记录，重新调用 close 并带 confirmEmpty=true 即可收口。'
    }
  }
}
```

（约 **150 字符**；新增参数 `confirmEmpty: { type: 'boolean' }`）

- **为什么不造成死锁**：模型总能带 `confirmEmpty=true` 强制收口
- **为什么不破坏幂等**：第一次调用**根本没写盘**（直接 return），事件状态未变
- **实测依据**：`eventStorePre.close` 已 closed 返回 `{alreadyClosed:true}` 不抛错（`lib/event-store.js:628`）

**方案 · 收口后提示其他事件（用户场景 3 原话）**：
```

```
（约 **75 字符**）

- **触发**：`state.receiptCtx.activeCount >= 2`
- **★注意**：实测 `close` 用得极少（**2/53 = 4%**）⇒ 这条 hint 的**实际触发频率极低**，优先级可降（见 §8）

### 场景 4 · `memory_log` 之后

**★这是本方案里最需要纠正的一条 —— 任务书假设的前提被实测推翻。**

任务书说「`memory_log` 的 note 只有一句话 ⇒ 关键词匹配几乎必然误报」。**实测反过来**：

```
真实日志条目 1,235 条：
  平均长度 = 680 字符
  长度 > 300 字符 = 973 条（79%）
  最长达 2,000 字符（撞上 sanitizeForWrite 上限）
⇒ 这个插件的 memory_log 不是「一句话概括」，是「长篇报告」
```

**五种启发式的命中率实测**：

| 启发式 | 命中率 | 判定 |
|---|---|---|
| 长度 > 60 | 95.8% | ❌ 噪音 |
| 长度 > 60 且含动词 | 86.3% | ❌ 噪音 |
| 长度 > 80 且含动词 | 85.4% | ❌ 噪音 |
| 长度 > 100 | 93.7% | ❌ 噪音 |
| 含动词且长度 > 40 | 88.2% | ❌ 噪音 |

**⇒ 全部不可用。** 换一个完全不同的判据：

**方案 · 用「该日是否已有 handoff 落盘」做判据（零 LLM、零误报）**

```
实测（dsh-auto-memory 工作区 50 天）：
  同一天既有日志又有账本 = 27 天
  只有日志              =  2 天   ← 真正需要提醒的场景
  只有账本              = 21 天
⇒ 「写了日志但那一天没账本」= 4%
```

```js
// memory_log 写入成功后
// 判据：当日 handoff 目录里是否已有 handoff-YYYYMMDD-*.md
const dayPrefix = 'handoff-' + date.replace(/-/g, '')
const hasTodayLedger = engine._handoffNamesToday   // 由 refresh 预计算（复用 readdir 结果）
if (!hasTodayLedger && hintBudget) {
  return base + '\n提示: 今日还没有交接账本。若本轮有实质产出，建议 memory_note(kind=handoff)。'
}
```
（约 **65 字符**；触发率约 **4%**）

**★负路径**：
- 若用「长度 > N」判据 ⇒ 96% 的调用都触发 ⇒ 每条日志后面都挂一句提示，实测会造成**上下文污染**（1,235 条 × 65 字符 = 80 KB 历史累积）
- 若用「note 含关键词」⇒ 实测 0/1235 条日志含四段标题、0/1235 含文件路径（正则用了全角/半角两种都 0 命中），说明模型写日志时**不带结构化标记**，关键词无从匹配

**附带结论（重要，回答 §8 问题 1）**：既然日志平均 680 字符，那它**事实上已经在充当账本**了。⇒ `memory_log` **不该加四段入参**（会让它更臃肿），正确的处置是：
1. 保持 `memory_log` 为「流水/日记」定位
2. 在回执里**明确它的定位**：`（本条为流水，四段账本请用 memory_note(kind=handoff)）`—— 仅在首次时给一次

## §6 三个新功能方案

### 6.1 功能 1 · Memory Timeline（大事件 → 小事件下钻）

**现状实测**：
- 三视图（`renderStream` / `renderLanes` / `renderWorkflow`）**全是平铺**
- `parentId` 字段全仓 **0 处**
- `renderDetailPanePre` 已是「事件 → 检查点列表」= **一层下钻**
- `members` 填充率 **94%**（但 **100% 来自迁移**，见 §1.3-C3）

**⇒ 缺的只有「事件之上的一层」聚合。**

**方案（推荐）：用 `members` 的文件归组关系聚出「大事件」，不新增 `parentId`**

判据（全部可计算，零 LLM）：两个事件属于同一「大事件」当且仅当
1. 它们的 `members` 有**交集**（同一篇日志/账本被归入两个事件），或
2. `startMs`/`endMs` 区间**重叠**，且 `sections.goal` 首行相似度 ≥ 0.6

```
大事件（聚合视图）
  ├─ evt_a「v4 底层改造」   members=[2026-10-24.md, PLAN.md]
  ├─ evt_b「v5 串行化」     members=[2026-10-24.md]        ← 与 a 交集
  └─ evt_c「v6 事件对齐」   members=[PLAN.md]              ← 与 a 交集
```

- **改动面**：新增 1 个聚合 API（`/event-timeline`，复用 `eventStorePre.list({all:true, withTime:true, withMembers:true})`）+ 前端 1 个视图
- **为什么不用 `parentId`（负路径）**：`validateEventPre` 用 `EVENT_TOP_FIELDS` 做 fail-closed 校验（26 字段，多一个 `unknown:` 就抛错）；且 53 个存量无法回填 ⇒ 加了也全是 null

**⚠️ 关键提醒**：`members` 现在 100% 来自迁移（运行时自发的 17 个事件里只有 14 个填了）。所以 **Timeline 的聚合质量取决于「运行时是否写 members」** —— 这需要 §4 场景 1/2 的回执里补一句「请填 members」。**这是 Timeline 真正的前置**，不是任务书说的「members 恒空」。

### 6.2 功能 2 · 智能提醒（实质性变化 → 提示写四类感知）

**★复核结论：这个功能的落点必须改。**

实测发现：
- 38 条感知里，**30 条（79%）落在 `handoff`/`plan` 检查点附近**（Δ=0 秒）
- **0 条**落在 `memory_log` 附近
- 只有 7 条落在 `progress` 检查点附近

**⇒ 感知本来就在 handoff 路径上被写了 —— 不需要「新建一个提醒」来提醒这件事。**

**真正的问题在别处**：38 条感知集中在 **7 个事件**（13%），且 **76% 集中在 1 个事件**。

**方案：把提醒挂在 `memory_event(append)`，用「本事件已有感知」做判据**

```js
// append 成功后的回执
if (evHadNoPerceptBefore && args.checkpoint?.kind === 'progress') {
  hint = '\n提示: 本事件此前没有任何感知记录。若这次是实质性进展（新结论/验收结果/用户裁定），' +
         '建议补一条: userPercept={stage:"accepted",kind:"preference",text:"…"} 或 agentTrace={action,result}。' +
         '纯读取/纯等待可忽略。'
}
```
（约 **130 字符**）

**判据（零 LLM，可判定）**：

| 信号 | 可判定性 | 用不用 |
|---|---|---|
| 本事件已有 `userPercept/agentTrace` 计数 = 0 | ★★★★★ | ✅ **主判据** |
| 检查点 `kind === 'progress'` | ★★★★★ | ✅ 排除 `log` 流水 |
| **本轮**用户消息含裁定词（`裁定/不要/必须/改成/同意/反对`） | ★★★☆ | ✅ 副判据（提高准确度） |
| 「实质性变化」本身 | ★ | ❌ 需要 LLM 判断，不做 |

**避免噪音**：三重限制 —— ①每会话最多 2 次 ②只在 `progress`+本事件零感知时 ③同一事件只提醒一次（`_receiptHintsSent` 记 `evt:xxx`）。

**负路径**：若改成「每次 append 都提醒写感知」⇒ 实测 553 个检查点会产生 553 次提醒 ⇒ 必然被模型忽略（噪音适应）。

### 6.3 功能 3 · Calendar「猜你想用」

**判据（零 LLM，全部可计算）**：

| 信号 | 正则 | 精度 |
|---|---|---|
| 显式日期 | `\d{4}-\d{2}-\d{2}` / `\d{1,2}\s*月\s*\d{1,2}\s*[日号]` | 极高 |
| 显式时刻 | `\d{1,2}:\d{2}` / `(上午\|下午\|晚上)\s*[一二三四五六七八九十\d]+点` | 极高 |
| deadline 词 | `截止\|deadline\|到期\|前交\|DDL` | 高 |
| 用户明确要求 | `提醒我\|记一下日程\|加到日历` | 极高 |

**推荐落点：`memory_log` 的回执（但用「双命中」防噪音）**

```js
// 必须「日期/时刻」与「deadline 词或用户明确要求」同时命中
const hasTime = DATE_RE.test(note) || CLOCK_RE.test(note)
const hasIntent = DEADLINE_RE.test(note) || EXPLICIT_RE.test(note)
if (hasTime && hasIntent) { /* 给推荐 */ }
```

**文案**：
```
📅 本条提到「<匹配到的片段>」——是否加入日历？
   calendar_add(date="<抽取日期>", title="<事项>", quadrant="重要不紧急")
```
（约 **95 字符**）

**误报控制（实测依据）**：单条件（只有日期）在真实日志上会误报大量「记录于 2026-10-28」这类日期；**双命中**把误报压到接近 0，代价是召回率下降（可接受：Calendar 本来就该由用户明确要求时写）。

**负路径**：若挂在 `memory_note(kind=handoff)` 回执上 ⇒ 那条回执已经有「关联事件」提示（168 字符），再塞日历推荐会超过 §3.1 的 180 字符上限。

## §9bis 用户质询：「提高合规率」这一半没验证 —— 更稳的替代方案

> 用户原话：「整个方案的价值主张是『省 1,498 字符 + 提高合规率』，但提高合规率这一半完全没验证。评估一下有什么更加稳一点的方案」

**这个质询是对的，而且比我原本以为的更严重 —— 因为它不是「未验证」，而是「已经验证并指向相反结论」。**

### 9bis.1 我补做的验证：一个 50 天 / 695 篇的自然实验

判据门（H1-H4）于 **2026-09-14** 上线（`checkMutationPre` 的 P0 写入门）。账本是 append-only 且文件名带时间戳 ⇒ **可按日期精确回测**。用生产判据函数（`checkHandoffCriteriaPre`）跑全部 695 篇真实账本：

| 时段 | 篇数 | 合规率（H1-H4 全过） |
|---|---|---|
| 判据门**上线前**（< 2026-09-14） | 58 | **77.6%** |
| 判据门**上线后**（≥ 2026-09-14） | 637 | **99.1%** |
| 10 月以来（≥ 2026-10-01） | 317 | **100.0%** |
| 最近 7 天（≥ 2026-10-23） | 94 | **100.0%** |

失败判据构成：全部 19 篇不合格中，`H2`（段太短）13 篇、`H1`（缺段）6 篇，**H3/H4 零次**。

**⇒ 三条硬结论**：

1. **「校验类干预有效」这一点不需要再验证** —— 判据门上线带来 **+21.5 个百分点**（77.6% → 99.1%），这是本仓历史上最强的合规提升证据。
2. **但这份收益已经在 9-14 落袋了** —— 我方案里的 A 类（回执引导）**不可能再复现这个提升**，因为天花板只剩 **0.9 个百分点**（99.1% → 100%）。
3. **10 月以来 317/317 全过** —— 说明模型现在**已经会写合规账本**。任何「再提升合规率」的主张，在数据上都缺乏空间。

### 9bis.2 更要紧的发现：「提高合规率」抓错了对象

合规率只能从**已落盘的账本**观测。而被判据门拒绝的写入**不产生文件**，是统计盲区。我量化了这个盲区，并发现**真正的漏在哪里**：

```
「有日志」的工作区-天 = 102
  其中也有账本        = 44（43%）
  只有日志、没有账本  = 58（57%）   ← 这才是最大的洞
```

**57% 的「工作-天」写了日志但没写账本。** 这不是「写了但不合规」，是**根本没写**。

| 问题形态 | 规模 | 回执能治吗 | 判据门能治吗 |
|---|---|---|---|
| 写了但格式错 | **0.9%**（6/695） | 边际收益趋 0 | ✅ 已治（99.1%） |
| **完全没写账本** | **57%**（58/102 工作日） | ✅ 能（但需正确判据） | ❌ 治不了（没有东西可校验） |
| 检查点缺四段 | 8%（运行时） | 软提示 | 软校验 |

**⇒ 结论：用户真正需要的是「提醒该写」，不是「校验写得对不对」。** 而这一点，恰好是**唯一无法靠静态代码验证的那一半**（因为它的收益取决于模型看到提醒后是否改变行为）。

### 9bis.3 因此：把方案改成「可验证收益优先」的三层结构

**核心思路：把「靠模型自觉」的部分降到最少，把「工具确定性完成」的部分提到最多。** 每一层都有独立的、无需跑模型就能验证的判据。

#### L0 · 确定性修复（收益 100% 可验证，不依赖模型）

| 项 | 收益形态 | 可验证判据 | 收益量级 |
|---|---|---|---|
| **WAL Phase 0 前置预检** | 事件库不再被脏数据污染 | 坏账本 ⇒ `checkpoints.length` 增量 = **0**（负路径：注释掉 ⇒ +2） | 已发生 3 次，实测可复算 |
| **`eventStorePre.append` 补 text 非空** | 两处口径一致 | 空白 text 抛错 | 确定性 |
| **`idemKey` 自动生成** | 重试不再产生重复检查点 | 实测有 **10 条**同事件内 kind+text 完全重复；缺失 idemKey 24 条 | 消除 **10 条**已实测脏数据 |
| **`sha256` 从 rel 文件自动算** | 溯源字段从 0% → 可覆盖 | 实测缺失率 **100%**（553/553） | 一次性补齐，零模型依赖 |
| **`calendar_add` 格式校验** | 不接受 `date:'下周三'` | 负路径：非法日期抛错 | 确定性 |

**这一层的意义**：`idemKey` 与 `sha256` 是**唯一两个「工具能替模型做、且模型做不好」的字段**（实测 idemKey 缺 4%、sha256 缺 100%）。**把它们自动化，是「提高数据质量」里唯一不依赖模型的路径。**

> ⚠️ 但必须诚实标注：**`quoteRef` 自动化实测不可行** —— 202 个有 `sourceRef` 的检查点里，文件 100% 存在，但 `quoteLine` **全部为 0**，无法定位原文行。所以溯源只能做到「文件指纹」级，做不到「原文摘录」级。

#### L1 · 回执提醒（收益 4% 可验证，但触发率本身可精确测量）

**改法：把「4 个场景全上」收缩为「1 个场景，且判据正确」。**

- **保留**：场景 4（`memory_log` 之后提醒写账本）—— 因为 57% 的洞在这里
- **判据改为**：「当日该工作区是否已有 handoff 落盘」⇒ 触发率实测 **4%**（2/50 天），噪音可控
- **砍掉**：场景 1/2/3（合规率已 100%，且场景 1 的「关联事件」提示在 99% 情况下是多余的）

**可验证判据（不需要跑模型）**：埋点统计「hint 触发次数 / 总调用次数」。若触发率落在预期的 4-10% 区间，说明判据正确；若 >30%，说明判据失效（噪音）。

**唯一无法静态验证的**：模型看到提示后是否真的去写账本。**这一项必须 A/B 实测，且我建议把它做成「可开关 + 可观测」，而不是默认开启。**

#### L2 · 提示词精简（收益可验证，但**必须最后做**）

保持不变（−2,218 字符可精确测量），但**做法的稳定性要改**：

**原方案**：删提示词 → 靠回执补 → 期望合规率不降（**不可验证**）

**更稳的做法：删之前先测「模型在无提示词下能否产出合规账本」**

```
步骤 1  保留全部提示词，跑 baseline：连续 10 轮真实任务，记录账本合规率（预期 100%，与自然实验一致）
步骤 2  删掉一组提示词（如 D1 四段纪律），再跑 10 轮，记录合规率
步骤 3  若合规率下降 > 5 个百分点 ⇒ 回滚该组；否则保留
```

**这套流程的稳定性来自**：①有 baseline 对照 ②按组灰度（不是一次删 2,218）③有明确的回滚判据（5 个百分点）④每组的收益（字符数）与风险（合规率）可分别量化。

### 9bis.4 三档方案的稳定性对比

| 维度 | 原方案（A 类全上 + 4 场景） | **保守方案（推荐）** | 激进方案 |
|---|---|---|---|
| 价值主张 | 省字符 + 提高合规率 | **修确定性缺陷 + 省字符** | 全面重写提示词体系 |
| 「提高合规率」可验证吗 | ❌ 不可验（天花板仅 0.9%） | ✅ 不作为主张（改说「防污染」） | ❌ |
| 最大收益项 | 回执引导 | **WAL 前置 + idemKey/sha256 自动化** | 提示词重构 |
| 收益可复算 | 部分 | ✅ 全部（增量=0 / 缺失率 100%→可覆盖） | 部分 |
| 失败风险 | 中（提示词删过头，模型漏写） | **低**（只删可灰度验证的部分） | 高 |
| 需要跑模型验证 | 整个价值主张 | **仅 L1 的 4% 触发率** | 整个价值主张 |
| 工作量 | 4 批 | **2 批（L0 + L1 精简版）** | 6 批 |

### 9bis.5 修正后的优先级（替代 §8）

| 优先级 | 项 | 为什么稳 | 判据 |
|---|---|---|---|
| **P0** | WAL Phase 0 前置预检 | 收益 = 事件库零污染，**可复算** | 坏账本 ⇒ 检查点增量 = 0 |
| **P0** | `idemKey` 自动生成 | 消除已实测的 **10 条**重复检查点 | 重复数从 10 → 0 |
| **P0** | `sha256` 自动计算 | 缺失率 100% → 可覆盖 | 新检查点 100% 带 sha256 |
| **P0** | `eventStorePre.append` 补 text 判据 | 口径一致 | 空白 text 抛错 |
| **P1** | 场景 4 回执（唯一保留的场景） | 对应 57% 的真实洞；触发率 4% | 触发率落 4-10% |
| **P1** | `calendar_add` 格式校验 | 确定性 | 非法日期抛错 |
| **P1** | 提示词分批删 + A/B 灰度 | 有 baseline 与回滚判据 | 每组合规率下降 ≤5 个百分点 |

### 9bis.6 一句话回答用户的质询

> **更稳的方案 = 砍掉「提高合规率」这个价值主张（实测天花板只剩 0.9%，且已由 9-14 的判据门实现），改成「修 4 个确定性缺陷 + 只保留 1 个回执场景 + 提示词灰度删减」。这样方案的每一条收益都能在不跑模型的前提下复算，唯一需要实测的只有「回执触发率」这一个数字。**
