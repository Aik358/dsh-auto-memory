**答：至少 6 套并存，且存在 3 组「同一件事、不同交互」的重复实现。**

| # | 交互范式 | 用在哪 | 行号证据 |
|---|---|---|---|
| 1 | **横向滚动页签**（TabScroller，带 ‹ › 箭头） | 浮层面板 | `:5555-5599`，使用点 `:5788` |
| 2 | **左侧竖向 nav**（固定侧栏） | 会话页「记忆」 | `:5678-5681`（`:5674-5676` 注释自述「顶部横向滚动页签 → 左侧固定侧栏」） |

**三组「同事实、异交互」的实证**：

1. **「切换分区」这件事有 3 种交互** —— 浮层用横滚页签（`:5555`）、会话页用左侧竖 nav（`:5678`）、设置页用左侧锚点滚动（`:7006`）。三者**视觉与手势完全不同**，但用户在脑子里做的是同一个动作。尤其第 3 种：点设置页左侧 nav **不切页**，只是 `scrollIntoView`（`:7003`）—— 用户以为在切 Tab，实际在滚动，**这是「晕」的直接来源之一**。

2. **「展开看更多」有 4 种交互** —— `AnimatedDisclosure`（`:3115`，带高度动画）、`folded`（`:2304`，泳道）、`expanded`（`:2305`，卡片）、`showDetail`（`:3361-3363`，概览技术细节）。四种视觉语言、四种动画曲线。

3. **「白板」有两个载体、两套形态** —— 「白板看板」KanbanView（`:7688`）与「白板画布」WhiteboardGraphView（`:7708`，默认关）；同时 `boardMode` 配置（`legacy` / `graph`）在设置页切换（`:7361-7379`）**会 reload 整页**。也就是说：**用户要切换「白板长什么样」，得去「设置 → 关于与诊断」里点一个会刷新整个页面的按钮** —— 这是 IA 错位的最典型样本（详见 0.5 根因 R2）。

**看板自身的过度配置**：单一个看板视图就带 **7 个独立 state**（`:2285-2293`：zoom / colW / layout / folded / expanded / view / q），全部持久化到 localStorage（`:2070-2072` 三个 key + `writeLs`），工具条上排 **7 个控件**（`:2321-2334`）。用户打开「白板看板」第一眼看到的是一排 `A- 100% A+ W- 320px W+ 纵向 泳道 搜索…` —— **这是给作者自己用的调参面板，不是给读者的视图**。

### 0.5 「晕」的根因清单（5 条，每条指向代码）

#### R1 · 线性膨胀：每个新功能 = 一个新页签 / 一个新 `field()`，从无删除机制

**分类：历史堆积（主因） + 缺信息架构（次因）**

**证据**：
- `MEMORY_TABS()`（`:5621-5623`）13 个页签挤在一行数组字面量里，且 `MemoryTabBody`（`:5606-5620`）13 路 `if` 串联；`stats` 分支（`:5618`）**缩进比相邻行少 2 空格**，`search` 是**裸兜底 return**（`:5619`）—— 两次追加的物证。
- 设置页：`:994` 的 CHANGELOG 文案自述「**设置页按用途重排为 9 个分区**」，而 `:961` 的自述是同一件事 —— 说明「9 分区」本身就是**一次为了治理膨胀而做的重排**，它把膨胀从「一列长列表」变成「9 个分区」，但**并没有减少项数**。
- 设置页 80 个 `field()` 里，**多条注释自述是"补接线"**：`:7204`「补接线(设置页缺口审计 P0-3/P0-4/P0-6)」、`:7227`「补接线(P0-4)」、`:7247`「补接线(设置页缺口审计 P0-1)」、`:7264`「补接线(设置页缺口审计 P0-5)」、`:7324`「补接线(设置页缺口审计 P1/P2)」—— **5 处**。即：一次审计又往设置页**加了 5 个控件**。**这就是线性膨胀的机械证据。**

**⇒ 判定：这个代码库的"功能交付"定义包含"在设置页加一个开关"和"在面板加一个页签"，但从不包含"合并/下沉/移除"。** 面板页签与设置开关是**单调递增**的。

#### R2 · IA 错位：功能被放在与其语义无关的位置

**分类：缺信息架构**

**证据（三个样本）**：

1. **白板形态切换在「关于与诊断」里**（`:7358` 分区 → `:7361-7379`）—— 「白板模式（旧版白板 / 新版看板）」这个**内容层**的选择，被放进了**元信息层**（版本号、更新日志、QQ 群）的分区。而且它**会 `window.location.reload()`**（`:7371`）。
2. **安装向导在「语义记忆总开关」里**（`:7010` 分区 → `:7034-7035` 向导按钮 → `:7076-7151` 向导卡 → `:7075` `PySetupWizard`）—— 一个 130MB/563MB 的下载安装流程，内联在设置页第一个分区，与「是否启用记忆」的开关相邻。
3. **调试中心挂在设置页最底部**（`:7401-7403` → `DebugCenter` `:5801`，210 行、含文件扫描/诊断日志/落盘动作）—— 「为提 issue 提供诊断」（`:5800` 注释自述），却占着普通用户必然滚过的位置。

#### R3 · 无设计 token：颜色与状态语义靠现场硬编码，同一语义在不同页面颜色不同

**分类：缺设计 token**

**证据**：
- 56 个唯一 hex + 107 个唯一 rgba（0.4.2 实测）。
- **同一语义两套色**：看板 `KANBAN_TONES`（`:2054-2058`，3 档：`ok #3fa96a` / `warn #d4a94f` / `unknown currentColor`）vs 设置页 `stateBg`（`:7091-7101`，5 档：就绪 `rgba(47,164,106,.24)` / 错误 `rgba(196,74,74,.22)` / 取消或未下载 `rgba(196,138,42,.2)` / 进行中 `rgba(36,86,196,.2)` / 检测中 `rgba(128,128,128,.16)`）。**「成功」在看板是 `#3fa96a`、在设置页是 `rgb(47,164,106)`——两个不同色值，但**用户认为是同一件事**。
- `--dam-accent` 5 种 fallback（0.4.2 表）。
- 面板背景兜底直接写魔法数（`:5727`：alpha `< 0.65` → 提到 `0.96`），无 token。
- 18 个 `--dam-*` token 里**零个是颜色**。

#### R4 · 状态语义缺失：哪一级是"我"，哪一级是"项目"，哪一级是"团队"在 UI 上没有表达

**分类：缺信息架构（本轮 teamwork 化的**前置阻塞**）**

**证据**：
- 全文 `工作区`×102 / `项目`×31 混用（0.3 表），且 `:331-333` 同一组提示里出现「本工作区库」+「所有项目都能用」+「跨工作区共享」三种表述。
- 双库视图（`hubScopeWorkspace` `:331` / `hubScopeGlobal` 相关）已上线，但**只是文案层**——IA 上没有「我的 / 这个项目的 / 全团队共享」的三段分区。
- 设置页把「我的偏好」（`look` 分区：字号/强调色/面板位置，`:7327-7339`）与「项目数据」（`store` 分区：用户记忆目录/项目笔记目录/memoryRoot，`:7302-7307`）与「引擎行为」（`engine`/`window`/`capacity`）**三类作用域完全不同的东西混在一条滚动流里**。

#### R5 · 交互范式未收敛：同类动作多套手势，且无统一"返回/层级"心智模型

**分类：设计问题 + 历史堆积**

**证据**：0.2 节的 9 套交互范式；「切换分区」3 种（`:5555` / `:5678` / `:7006`）；「展开」4 种（`:3115` / `:2304` / `:2305` / `:3361`）。特别地，**设置页的左侧 nav 是"假页签"**（`:7003` 只做 `scrollIntoView`），这是最容易被用户误读为「点了没反应 / 页面在跳」的一处。

#### R6（附加）· 单写者文件的规模已经逼近人类可维护边界

**分类：工程约束（非设计问题，但决定重构手法）**

`lib/client.js` **7,734 行 / 600,159 字符**，其中：

### 1.1 信息架构（IA）重构

#### 1.1.1 新的顶层结构：4 个一级入口

**判据（L1 准入条件，三条同时成立才可进一级）**：

1. **时间性正交** —— 「什么时候用它」与其他入口不重叠（今天 / 做这个项目时 / 协作时 / 找东西时）
2. **作用域唯一** —— 一个入口只服务一个作用域（我 / 这个项目 / 这个团队 / 全部档案），**不同作用域不得混入同一入口**
3. **日常可及** —— 至少每周会主动打开一次（否则降入二级或设置）

| L1 入口 | 作用域 | 什么时候用 | 承载（L2） | 来源页签（行号） |
|---|---|---|---|---|
| **① 今天** | 我 · 当下 | 每次打开，看一眼就够 | 概览 / 日志 / 反思 / 上下文状态 | `overview` `:5607`、`logs` `:5608`、`reflections` `:5614`、`connect` `:5615` |
| **② 项目** | 这个工作区 | 干这个项目时 | 白板 / 笔记 / 记忆中枢 / 日历 | `plan` `:5613`、`notes` `:5612`、`hub` `:5610`、`calendar` `:5616` |
| **③ 团队**（新增） | 这个团队 | 协作、看谁在、看冲突 | 成员 / 共享库 / 改动与冲突 | **全新**（见 1.5） |
| **④ 检索** | 全部档案 | 找东西、看质量 | 搜索 / 统计 / 来源与质量 / 工作区 | `search` `:5619`、`stats` `:5618`、`refine` `:5609`、`workspaces` `:5617` |

**13 个现有页签全部有归属，零功能丢失**：

- 12 个进上表
- `storage`（存储，`:5611`）→ **降入设置**「协作与存储」组 —— 它是纯配置（记忆根目录/用户记忆目录/项目笔记目录 `:7302-7307`），不是"看内容"的地方

#### 1.1.2 单机功能 vs 团队功能怎么分

**三分法（按数据归属，不按功能）**：

| 归属 | 定义 | 落在哪 | 当前对应 |
|---|---|---|---|
| **我的**（跟人走，跨项目） | 换了仓库也还在的东西 | 「今天」+ 设置「外观」组 | 用户级记忆、反思、偏好（字号/强调色/面板位置 `:7327-7339`） |
| **这个项目的**（跟工作区走） | 换仓库就换一套 | 「项目」 | 工作区记忆、PLAN.md、账本、项目笔记、日志、日历 |
| **这个团队的**（跟团队走） | 成员间共享 | 「团队」 | **当前不存在**——这是 teamwork 版要补的唯一新维度 |

**为什么必须这样分**：当前 IA 把三类作用域**混在同一条滚动流里**（0.5 R4）。设置页 `store` 分区（`:7302`，项目数据路径）紧挨 `look` 分区（`:7327`，我的外观偏好）紧挨 `about` 分区（`:7358`，版本/QQ 群）—— 三类的**变更频率、影响范围、回滚代价完全不同**，却共享同一视觉权重。团队维度若直接插进这个流里，会立刻变成第 10 个分区（0.5 R1 的线性膨胀），且因为**作用域词本身还没统一**（0.3 术语表：「工作区」102 次 vs「项目」31 次），用户无法判断"这个开关影响的是我还是大家"。

#### 1.1.3 导航模型：从「5 挂载点 + 13 页签」收敛到「2 级 + 4 入口」

**现状**：5 个挂载点 → 13 页签 → 若干内部二级页（设置页 4 处条件渲染二级页：`:7038` `detOpen` / `:7169` `psecOpen` / `:7213` `promptEditOpen` / `:7076` `guide`）+ 2 类抽屉（`:3176` / `:3187`）+ 7 种模态（`:1314-1320`）。**层级实际是 3~4 层，但没有一层在视觉上被表达为"层"。**

**目标**：**两级，硬上限**。

```
L0 · 宿主 GUI
 └─ sidebar 按钮「记忆」                      ← 唯一入口，不动（:7655）
     │
     └─ 承载面（用户可切，不动状态层）          ← :5658 浮层 / :7677 会话页
         │
         ├─ L1 一级导航【固定 4 项，永不增长】
         │   今天 │ 项目 │ 团队 │ 检索
         │
         └─ L2 入口内二级【每入口 ≤ 4 项，硬约束】
              ├─ 今天：概览 · 日志 · 反思 · 上下文状态
              ├─ 项目：白板 · 笔记 · 记忆中枢 · 日历
              ├─ 团队：成员 · 共享库 · 改动与冲突        ← 新增
              └─ 检索：搜索 · 统计 · 来源与质量 · 工作区
```

**「什么进二级、什么留一级」的判据（可机械执行）**：

| 情形 | 判定 | 理由 |
|---|---|---|
| 与同入口其它项**作用域相同、只是视角不同**（列表 vs 图 vs 统计） | 留 L2，用**页内 segmented control** 承载而非并列页签 | 例：白板的「泳道 / 最近」「纵向 / 横向」——这是 7 个 state（`:2285-2293`）干的事，不该是页签 |
| 与该入口**作用域相同但时间性不同**（"现在"vs"历史"） | 留 L2 | 例：今天 › 概览 vs 日志 |
| **作用域不同** | 必须升 L1 或换入口 | 例：`workspaces`（跨工作区）不能留在「项目」里 |
| **只有配置项、没有内容展示** | 一律进设置，不进 L1/L2 | 例：`storage` |
| **一个入口的 L2 超过 4 个** | 必须合并（≤4）或提升为 L1 | **硬约束**——这是防止 13 页签复现的唯一机制 |

**关键设计取舍**：

- **`search` 不该是页签，应该是常驻动作**。当前 `SearchTab` 只有 **13 行**（`:4759`），且它同时是 `MemoryTabBody` 的**兜底 return**（`:5619`）—— 意味着任何未知 tab key 都会静默落到搜索页。**目标形态**：顶部常驻搜索框（输入即搜，无需切页），L1「检索」入口保留为「结果与质量」的综合页。**抄 Linear 的做法**（见 2.2）。

- **白板三形态合一**。当前「白板」以三种形态存在：旧白板 `PlanTab`（`:4442`，260 行）、白板看板 `KanbanView`（`:2487`）、白板画布 `WhiteboardGraphView`（`:2867`，默认关 `:7702-7704`），且形态切换藏在设置页 `about` 分区（`:7361-7379`）**并会 `window.location.reload()`**（`:7371`）。**目标**：「项目 › 白板」一个入口，形态是**页内 segmented control**（旧白板 / 看板 / 画布），切换即时生效不 reload。

#### 1.1.4 迁移期：13 → 4 怎么做到「不改代码也能先看到效果」

`MemoryTabBody` 是**表驱动改造的最佳切入点**（`:5606-5620` 已经是 13 路 `if`，结构上就是一张表）。迁移分三态：

**阶段 A（零风险，先做）**：在 `MEMORY_TABS()`（`:5621`）旁新增 `MEMORY_NAV` 常量，**保留原有 13 项**，但用分组元数据标注归属（`{key, label, group}`）。此时 UI **完全不变**，只是数据结构就位。

**阶段 B（可回滚）**：L1 导航渲染 `MEMORY_NAV` 的 4 个 group；点 group 后 L2 渲染其成员。此时**行为等价**（同样的页签，只是多了一层选择），但已能实测「4 入口是否够用」。

**阶段 C（收口）**：把 `MEMORY_TABS()` 改为 `MEMORY_NAV` 的派生函数：

```js
function MEMORY_TABS() { return MEMORY_NAV[activeGroup].tabs }   // 签名不变 ⇒ 守卫 :39 通过
```

**这样 `eq(tabsReuse, 2)`（`:44`）与 `eq(bodyReuse, 2)`（`:42`）都不受影响**——函数名、签名、调用次数全不变，只是返回值从"13 项平铺"变成"当前组 ≤4 项"。**这是在不破 177 项回归前提下完成 IA 收敛的关键手法。**

### 1.3 设计系统最小集（零构建前提下的可落地做法）

#### 1.3.1 现状盘点：已经有了什么

#### 1.3.2 CSS token 最小集（全部加在现有 `CSS` 数组里，`:1576-2019`）

**语义色（12 个，一次性）**：

'  --dam-err:#c44a4a;     --dam-err-bg:color-mix(in srgb,#c44a4a 20%,transparent);',
'  --dam-info:#2456c4;    --dam-info-bg:color-mix(in srgb,#2456c4 18%,transparent);',
'  --dam-neutral:#8b949e; --dam-neutral-bg:color-mix(in srgb,#8b949e 16%,transparent);',

#### 1.3.4 如何在不破 177 项回归的前提下渐进替换

**四条硬规矩**：

1. **只增不改签名**。新组件一律新增函数；被守卫锚定的既有函数（`MEMORY_TABS` / `MemoryTabBody` / `MemoryPageView` / `SettingsPage` / `KanbanView`）**签名与调用次数一字不改**。
2. **DOM 标记只增不减**。守卫锁定的 135 个 `data-dam-*` 中，被显式断言的约 **15 个**（见 C2 表）**永不改名**；要废弃的标记先保留一版，下一版再删。
3. **颜色替换走脚本 + 守恒断言**。`--dam-accent` fallback 统一（47 处）与 hex→token 替换（~120 处）必须用补丁脚本，脚本须含：内容锚定、命中数 == 预期、**EOL 性质守卫**（原纯 CRLF ⇒ 改后无裸 LF；⚠️ **不得写成「CRLF 计数不变」**——多行块替换必然改变行数，该判据恒假会误拒写盘）、前后 SHA256 记录。
4. **每批结束必须 `node --check lib/client.js` + 跑对应子集回归**（`node tools/run-smoke.mjs --filter=<关键词>`），**全量 177 项只在批次收口时跑**（`tools/run-smoke.mjs` 支持 `--filter`，见其用法注释 `:6`）。

#### 1.4.1 分组方案

| **A · 记忆内容** | `window`（注入什么）`:7165` + `capacity`（容量与归档）`:7224` | 普通用户 | 偶尔 |

#### 1.4.2 ⚠️ 设置页分组是**契约变更**，不是纯 UI 改动（必读）

`smoke-test-s2-settings-panels.mjs:102` 硬锁：

```js
eq(bounds.map((b) => b.key).join(','), 'engine,window,capacity,skills,handoff,auto,store,look,about', 'G1a 九个分区头齐备且顺序不变')
```

**⇒ 任何分组方案都会让这一行变红。** 这不是阻碍，而是**必须显式规划的动作**。该守卫文件头部（`:1-18`）记录的真实事故值得逐字重读：

> 背景（真实事故，2026-09-22）：B1 分区重构把两个面板留在 store 分区，而触发它们的「⟳ 检测」「🧩 安装向导」按钮在 engine 分区。分区导航是**滚动式**（jumpToSection 只 scrollIntoView，全部 section(…) 顺序平铺渲染）⇒ 状态正确置位、面板也确实渲染了，但渲染在当前视口下方 6 个分区处 ⇒ 用户看到「点了毫无反应」，报障为「引导页和检测页弹不出来」。

**同批必须做的三件事**：

1. **改 `G1a` 的期望字符串**为新分组顺序（`K1a` 式：把分组写进 `section()` 的 key 或新增 `group` 维度）
2. **保留 G1b（触发点↔渲染点同区）这个不变量本身** —— 它是治那次事故的，只能**改写判据**（从"9 个 key"改为"4 组 × 组内分区"），不能删除
3. **同步更新守卫头部注释**说明为何改（否则下一个读到的 agent 会以为 G1a 是被绕过而不是被演进）

**同时注意守卫 `:145`**：`el.scrollIntoView({ behavior: 'smooth', block: 'start' })` **必须存在**。若把设置页改为真分页，这一行会消失 ⇒ 该断言红。**两条路**：

- **路 A（推荐，低风险）**：保留滚动式，但**新增 `IntersectionObserver` 做 nav 高亮同步**（解决「假页签」问题 #4），`scrollIntoView` 保留 ⇒ **`:145` 不变红**
- **路 B（高风险）**：改真分页，同步把 `:145` 改为断言"分页渲染 + 当前组唯一挂载"，并重写 `:148`（engine 之后仍渲染 window 的平铺证明）

**⇒ 建议走路 A**：它用 ~35 行解决了用户感知问题（#4），且**完全不触碰最硬的三条锁**（`:145` `:148` `:152`）。

#### 1.5.2 为什么**不能**直接往现有设置页再塞一节（三条理由，全部有代码证据）

**理由 1 · 设置页的膨胀已经是可测量的病，不是感觉**

0.5 R1 的物证：设置页已有 **9 分区 / 80 控件**，且 `:7204` `:7227` `:7247` `:7264` `:7324` **五处注释自述是"补接线"**——即**一次审计又加了 5 个控件**。再加「团队」一节会变成第 10 个分区，且它会带进**账号、团队 ID、同步策略、权限默认值**至少 4-6 个控件。**⇒ 线性膨胀会被机械地复制一次。**

**理由 2 · 设置页的导航模型承载不了"账号"这类需要上下文的状态**

设置页 nav 是 `scrollIntoView`（`:7003`），**所有分区始终挂载**。而账号/在线状态是**强时效信息**（登录是否过期、团队是否可达、有多少人在线）——把它放在一个"滚过去就看一眼"的静态锚点区里，用户看不到状态变化。**在线状态需要"常驻可见"，设置页的语义是"改完就走"。**

**理由 3 · 设置页在宿主 GUI 里是「宿主拥有的页面」，插件只是租客**

`settings.section` 是宿主提供的槽位（`:7667`），label 是 `t('autoMemory')`。**团队的成员/协作是产品级一等实体，不是"某插件的一个设置项"** —— 放在这里会让用户以为「退出团队 = 关掉这个插件的某个开关」。

#### 1.5.3 团队入口的最小落地形态（不破回归）

**新增 L1 入口「团队」的实现路径**：

1. `MEMORY_NAV` 增加第 3 组 `team`（1.1.4 阶段 A 就已支持任意组数）
2. 「团队」的 L2 三项里，**成员 / 共享库 / 改动与冲突** 首版可以是 `EmptyState`（未登录时提示"登录后可见"）⇒ **零后端依赖即可上线 IA**
3. 登录成功后填充数据
4. **不新增 `slots.register`** —— 团队入口作为「记忆」承载面内的 L1 项存在（避免触碰守卫 `:60`「不得往 shell.overlay 注册带 label 的第二页面」与 `:44` 的调用次数锁）

**为什么团队成员徽标可以立刻做**：看板**已有** `data-dam-kx-badge` 标记与 `kxBadge` 渲染函数（`:2` 标记清单），加"谁写的"角标是**在该标记内增加内容**，不改标记本身 ⇒ 不破坏 `smoke-test-graph-mode.mjs:491-496`。

- **我们能直接抄的一条**（**本节最有价值的一条**）：**把「谁负责」与「谁写的」分成两个机制，不要合并成一个"作者"字段。**
  - 「**谁写的**」（追溯）= 卡片角标 + 点击溯源 → 直接映射到我们**已有**的 `memory_trace`（按 id 回溯版本链，`:6650` 附近工具）+ `prev_version` 版本链
  - 「**谁负责**」（声明）= 团队设置里的**声明式规则**（类似 CODEOWNERS：`handoff/` 归谁、白板某泳道归谁）→ 用于**冲突/评审路由**
  - **⇒ 这解释了我们团队版一个关键设计取舍**：B 卷（同步与向量）讨论的"冲突提示"属于**「谁负责」**机制（需要路由），而"谁写的徽标"属于**「谁写的」**机制（只需展示）。**两者数据源与 UI 落点都不同**（前者在「团队 › 改动与冲突」，后者在卡片角标）。
- **抄的成本**：中（需要成员身份 + 声明式规则存储）。
- ⚠️ **未验证**：blame 的具体 hover 交互未逐屏核对；CODEOWNERS 的语义已由官方文档确认存在。

#### Slack workspace 切换（[slack.com/help/articles/1500002200741](https://slack.com/intl/ko-kr/help/articles/1500002200741-%EC%9B%8C%ED%81%AC%EC%8A%A4%ED%8E%98%EC%9D%B4%EC%8A%A4-%EA%B0%84-%EC%A0%84%ED%99%98)）

- **做对了什么**：**workspace 是顶层容器，切换是"换整个上下文"而不是"加一个筛选器"。**
- **具体手法**：左侧最窄栏是 workspace 列表，切换后整个界面的内容、成员、设置全部跟着换。
- **我们能直接抄的一条**：**「我的 / 项目的 / 团队的」应该表现为"切换容器"而非"筛选标签"。**⇒ 这**恰好反驳**了"在现有页面加一个 scope 筛选器"的轻量做法：作用域切换应该是**L1 级**的。⇒ 支持 1.1.1 把「团队」设为独立 L1 入口，而不是在「项目」页里加一栏。
- **抄的成本**：低（是 IA 决策）。
- ⚠️ **未验证原文**：Slack 帮助页返回的是韩语版目录，**具体切换交互未核对**；「workspace 是顶层容器」为通用产品事实。

### 3.2 「这 3 条诱惑必须拒绝」清单

> 判据：每条都**对应第 0 部分的一个已证实根因**，且都是**在 teamwork 压力下最容易被选中的捷径**。

#### ❌ 诱惑 1 · 「团队设置只要在设置页再加一个 section 就行」

**诱惑描述**：teamwork 版要引入成员身份、登录、团队 ID、同步策略、权限默认值。最省事的做法是 `section('team', '团队', [...])`，接到现有 9 分区后面。

**为什么必须拒绝**（对应根因 **R1 线性膨胀** + **R4 状态语义缺失**）：

1. **R1 的物证**：设置页已有 9 分区 / 80 控件，且 `:7204` `:7227` `:7247` `:7264` `:7324` **五处注释自述是"补接线"** —— 这个代码库的"功能交付"定义包含"加一个开关"，从不包含"合并/下沉/移除"。**加第 10 个分区会把这条路径再走一遍。**
2. **R4 的物证**：作用域词本身还没统一（「工作区」×102 / 「项目」×31，`:331-333` 同一组提示里三个词）。**在作用域语言未统一前加"团队"作用域，用户无法判断这个开关影响的是我还是大家。**
3. **技术约束**：设置页导航是**滚动式**（`:7003`），全部 section 平铺渲染（守卫 `:148` 锁定了这个事实）。**新分区会落在视口下方更远处** —— 而这**正是 `s2-settings-panels.mjs` 记录的那次真实事故的形态**（面板渲染了但落在视口下 6 个分区处，用户报障"弹不出来"）。

**应该怎么做**：团队是**独立 L1 入口**（1.5.1），设置页只留「协作与存储」组里的**账号与同步开关**（3-5 个控件），且归入 C 组。

#### ❌ 诱惑 2 · 「页签太多了，加个"更多"折叠起来」

**诱惑描述**：13 个页签太挤，加一个 `▾ 更多` 把后 6 个折进去。

**为什么必须拒绝**（对应根因 **R5 交互范式未收敛** + **R1**）：

1. **R5 的物证**：我们已经**有 9 套交互范式**（0.2 节）：横滚页签 `:5555`、左侧竖 nav `:5678`、锚点滚动 `:7006`、抽屉 `:3176`、折叠 `:3115`、模态 `:6011`、内联面板 `:7038`、卡片展开 `:2305`、泳道折叠 `:2304`。**再加"更多"折叠 = 第 10 套。**
2. **它不解决根因**：13 个页签的问题是**没有分组（缺层级）**，不是**显示不下（缺空间）**。"更多"把问题从"看得见但乱"变成"看不见且乱" —— **这是把可发现性问题换成不可发现性问题**。
3. **守卫风险**：`eq(tabsReuse, 2)`（`:44`）与 `eq(bodyReuse, 2)`（`:42`）锁死了 `MEMORY_TABS()` / `MemoryTabBody()` 的调用次数。任何"再多渲染一处页签"的实现都会撞锁。

**应该怎么做**：**分组**（1.1.4 的 `MEMORY_NAV` 三阶段迁移），并把低频项目**移出页签**到搜索/命令入口（映射表 #3），把 13 项降到 4 组 × ≤4 项。

#### ❌ 诱惑 3 · 「视觉太乱，先做一次全局配色/圆角统一（顺手把硬编码色都换成变量）」

**诱惑描述**：既然有 56 个 hex + 107 个 rgba、`--dam-accent` 有 5 种 fallback，那就全库替换成 token。

**为什么必须拒绝**（对应根因 **R3 无设计 token**，但**拒绝的是"顺序"不是"目标"**）：

1. **§1.6 批次 E 的设计已经说明它该做**——但**必须排在 B/C 之后，且必须分批**。一次性全库换色会：
   - 产生**数百处**改动，与批次 B/C 的**结构性改动混在同一 diff 里** ⇒ 一旦回归红，**无法判断是"换了色"还是"动了结构"**
   - 撞上 `smoke-test-v314-gate-scope-j.mjs:74`（`--dam-accent` 必须存在）——若替换手法把变量名也换了，守卫直接红
   - 违反"不得大段重写"约束（C3）：**7,734 行里每行都可能被某个守卫的字符串锚点引用**
2. **R3 不是"晕"的主因**：主因是 **R1（无层级）** 与 **R5（交互不收敛）**。**先统一颜色不会让用户觉得"不晕了"** —— 用户的原始反馈是"杂乱、看着晕晕的"，这是**层级问题**的语言，不是配色问题。
3. **用户硬性纪律**：**无确凿证据不得删除既有动画或视觉表现**："动画对美学观感是硬需求，怀疑方向未证实前必须先取证定位真因，不得用减法改动兜底未验证的猜测。" ⇒ 全局换色若顺手改了任何视觉表现，**属于用未验证的猜测做减法**。

**应该怎么做**：**先结构、后视觉**。批次 B/C 建立层级 → 批次 E 才做 token 化，且 E 分三小步（E1 新增 token 不动旧值 → E2 替换 accent fallback → E3 合并两套状态色），每步独立回归。
