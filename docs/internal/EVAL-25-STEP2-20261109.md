### 1.2 参数级不匹配（致命）

细则给的是：

```
const w = await this.writePlanSnapshot(p.projectDir, rendered, {})
```

而 `preparePlanPre` 的 CAS 判据是（lib/plan-store.js:247-249，逐字）：

```js
if ((current || opts.expectedRevision !== undefined) && opts.expectedRevision !== planRevisionPre(current)) {
  return conflictPlanPre(file, current, incoming, opts, 'plan-version-conflict: memory_read(kind=plan) before rewriting; retain both candidates')
}
```

`opts = {}` ⇒ `expectedRevision === undefined`；真实工作区 `current` = 27,397 B 的白板（非空）⇒ `(current || false)` 为真、且 `undefined !== planRevisionPre(current)` ⇒ 恒进 `conflictPlanPre`。

后果有三层：
1. 返回值 `{ok:false, error:'plan-version-conflict…'}` ⇒ 细则的 P-1（`r1.wrote === true`）**必红**；
2. `conflictPlanPre` 每次都会**再写一个冲突副本**（plan-store.js:203-210，`flag:'wx'` 写 `handoff/conflicts/PLAN-<uuid>.json`）⇒ 每次事件写都留一个垃圾文件（本机该目录现存 **9 个 / 208,958 B**）；
3. 永远不写白板 ⇒ 「自动重绘」实际零效果，只剩日志噪声。

**正确写法**（二选一，推荐 a）：
- **(a) 让写盘口自己算版本**：新增内部选项（如 `{ redraw: true }`），在 `writePlanSnapshot` 读完 `existing`（含 :5258-5264 的自愈）之后、:5266 调 `preparePlanPre` 之前，令 `opts.expectedRevision = planRevisionPre(existing)`。语义正确：重绘内容来自事件、不来自旧白板正文，且整个读-改-写在 calendar lock 内（:5248），不存在外部竞态。
- **(b) 在方法里传** `expectedRevision: planRevisionPre(existing)`——注意必须用 `writePlanSnapshot` 内部**自愈后**的文本口径，否则 healed 与原始文本 revision 不等 ⇒ 存量重复锚点白板会**永久冲突**（:5260-5264 只 heal 内存态、不落盘）。

### 1.3 附带发现：重绘的输入是「精简投影」，不含检查点正文

`eventStorePre.list(..., {all:true})` 走 `projectEventForListPre`（event-store.js:708-717），base 只有 7 键：`id/name/summary/status/sections/updatedAt/checkpointCount`。**没有 checkpoints 数组**（:1079 注释明写）。
⇒ 自动重绘与手动 fromEvents 的**渲染保真度完全相同**（都是投影级），不会因为「自动」而更差；但这也意味着细则设想的「事件写完 ⇒ 白板反映新检查点」**做不到**：新检查点只改 checkpointCount，不进「近期进展」列。这不是本方案的错，是 fromEvents 通路既有口径——但**必须写进验收判据**，否则会拿「检查点文本没出现在白板」当回归。

|---|---|---|---|---|

### 2.3 但有三个结构性问题，细则没写

1. **必须自带 try/catch**。分支都在 :25676 的 try 内，任何冒泡异常都会被 :25784 变成 `memory_event 失败: …`——事件已写成功却报失败（用户会重试 ⇒ 重复写入）。细则片段里的内层 `try { if (…) await engine.redrawPlanFromEventsPre(p, exec.agent) } catch (_) {}` 是**必需**，不是可选。
2. **测试抽取壳只注入 5 个形参**：tests/smoke/smoke-test-v4-memory-event-tool.mjs:47 为 `new Function('defineTool','eventStorePre','V4_EVENT_STORE_FILENAME','path','engine', …)`。挂点里只能引用 engine / p / args / exec（及 path、eventStorePre），**不能引用模块级常量**。该壳的 engine 只有 resolvePaths 与 refreshEventStatePre（:41-44）⇒ 若挂点用 `(engine.config || {}).boardMode` 做门，engine.config 为 undefined 时门为假、不会调用；**但如果写成 `engine.config.boardMode` 就会 TypeError**（虽被内层 catch 吞掉，仍会污染断言）。必须保留 `(engine.config || {})` 的兜底。
3. **memory_log 完全不在覆盖范围**（细则最大的前提错误）。memory_log 的执行体（`defineTool('memory_log'… )` @ :24490，执行体到 :24972 return）**直接**调 `createEventForWorkPre`（:24848）与 `appendCheckpointPre`（:24878），**没有任何一处 refreshEventStatePre**（全文件 18 处命中里没有 memory_log 区段）。它只更新 `engine.state.logText`（:24917-24925）。
   ⇒ 若只在 memory_event 四分支接线，**最频繁的写者（今日 9 条 memory_log）一条都不会触发重绘**。要覆盖它必须加**第 5、6 个挂点**（建议在 :24884 之后，或并入 :24895-24910 的派生块），该抽取壳的形参表见 smoke-test-v4-h1b-memory-log.mjs:104-115（17 个，**含 engine，不含 eventStorePre**）⇒ 挂点同样只能走 `engine.redrawPlanFromEventsPre`。

### 3.3 一轮对话多写多少（按本机真实调用量）

今日（记忆日 2026-11-09）实测：memory_log 调用 **9** 次（当日日志 9 条 `- HH:MM [kind:…]` 行）；检查点 **23** 条（kind: log 9 / progress 9 / handoff 4 / handoff-write-failed 1）；新建事件 **2** 个。

- 只挂 memory_event 四分支：≈ progress 9 + create 2 ≈ **11 次/日** ⇒ **11 × 7.43 MB ≈ 81.7 MB/日**
- 只挂 memory_log：9 次/日 ⇒ **66.9 MB/日**
- 两处都挂（细则的完整意图）：≈ 20 次/日 ⇒ **≈ 148.6 MB/日**
- 换算到「一轮对话」（本机习惯：1 次 memory_log + 1 次 memory_event）⇒ **≈ 14.9 MB/轮**，其中正文只有 19.7 KB

CPU 代价：只在**内容真的变了**时才付 243 ms（sidecar）+ 约 10 ms（读 store + 渲染 + 锚点）；不变时应短路在写盘之前（前提是短路判据修对，见 §4.3）。

> 说明：`index.json` 体量与工作区历史成正比。本工作区 329 篇归档 ⇒ 2,848 entries / 7.38 MB；新用户的小工作区会小很多（仍按同比例放大）。**但「重绘 26 KB」这个量级在任何工作区都不成立**——真正的量级是 index.json 的整份尺寸。

## 4. M1 保护门与 CAS 会怎样

### 4.1 expectedRevision 传空 ⇒ 必撞 #164 CAS

见 §1.2，plan-store.js:247。补充：`writePlanSnapshot:5350-5351` 还有第二道 CAS（`latest !== existing` ⇒ `conflictPlanPre(...'plan-external-edit-conflict')`），这条在锁内、正常不会命中，但同样会写冲突副本。

### 4.2 M1 会怎样——取决于传不传 archivedIds

M1 实现：`checkMutationPre`（index.js:5853）→ :5881-5898 解析前后 cardIds → `validateMutationBoundaryPre`；**只有 M1 不合格时降级为警示**（:5909-5919）：

```js
if (!res.ok && target === 'plan' && res.hard.every((h) => h.pass || h.id === 'M1')) {
  planDowngradeWarn = '⚠ 【白板丢卡警示 · 已照写】本次重写丢了 ' + unarch.length + ' 张卡片且未显式归档：'
  ...
  res.m1Downgraded = true
}
```

细则的调用**不传 archivedIds** ⇒ 每次都会命中。实测口径（不是细则写的「34→0」）：

```
disk cardIds        = 34
anchored(render)    = 34 cards
两者交集            = 4          ← 所以丢的是 30 张，不是 34 张
```

⇒ **每轮都会吐「⚠ 白板丢卡警示 · 已照写」，且 warn 会一路透传到 memory_event 回执**（如果回执拼接了 w 的返回值）。细则 §2.5.4 的 F2 断言「result.m1 === false」在它自己给的代码下**恒为 false**。

### 4.3 细则的 no-change 短路恒不成立

```js
if (String(rendered) === String(existing)) return { ok: true, skipped: 'no-change', ... }
```

实测：`rendered` = 17,914 B / **0 颗锚点**；`existing`（磁盘 PLAN）= 27,397 B / **34 颗锚点**。二者**永不相等**（连长度都不同）。
⇒ 即使事件一字未改，也会走完整写盘：归档 27,397 B + 重写正文 19,716 B + 重写 index 7,382,763 B。细则的 N-1a/N-1b/N-1c 三条负路径**必红**。

**正确比法**：拿**锚点化之后**的渲染结果与磁盘比——

```js
const anchored = anchoredPlanPre(this.wbWsKeyPre(p.projectDir), rendered)
if (anchored === existing) return { ok: true, skipped: 'no-change', bytes: Buffer.byteLength(existing, 'utf8') }
```

可复算支持：`anchoredPlanPre`（plan-store.js:85-130）按「标题 + 同名出现序号」算 id（:101-116），**无时间戳、无随机**；实测把同一份事件按 id 正序 / 倒序喂入，渲染结果逐字节相同，锚点结果也相同 ⇒ 修好比法后短路是真的会命中。注意：修好后**首次仍然会写**（磁盘 34 个 id 与渲染出的 34 个 id 只有 4 个相同），第二次才短路。

### 4.4 fromEvents 是怎么绕过 M1 的——可以复用，但要明白代价

代码（index.js:25082-25095，逐字注释）：

```js
// ★★2026-11-09（用户实报「fromEvents 每次触发 M1 丢卡 34 张」）：**语义错配，不是丢卡**。
//   渲染器（plan-render.js）输出「事件 → 四节 markdown」的**整体重建**，它不产出也不搬运任何
//   memory 锚点（全文件 0 处生成）。而 M1 门的判据是「before 侧 cardIds 是否全在 after」⇒
//   每次 fromEvents 重写都天然满足「before 34 张 / after 0 张」⇒ 每条白板都被判丢卡并吐警示。
//   正确处置：fromEvents 是**显式重建**，旧卡是被事件数据**替代**（有留痕、可从 archive 取回）⇒
//   把 before 侧全部卡片作为 archivedIds 传下去（v3.1.4 批 J 为「有意消失」设计的通道）。
```

实现：读旧 PLAN → `parseWhiteboardPre(_oldPlan, {kind:'plan'}).cardIds` → `fromEventsArchivedIds`（:25089-25095）→ 在 :25111-25114 并入 `archIds` → :25164 传给 `writePlanSnapshot`。

**可以复用同一手法**（且口径必须用 `parseWhiteboardPre(…).cardIds`，不能用 `planCardsPre(…).id`——两套 id 不同源）。但必须知道它的真实语义：archivedIds = 「旧卡全部有意归档」 ⇒ **M1 在这条路径上被完全旁路**，渲染器回归（少渲染事件、标题被截断、四段全空）时**不会再有警示**。它换来的是「不刷屏」，不是「有保护」。
⇒ 建议：自动重绘这条路径接受这一点，但**必须同时**加一条独立的渲染健全性判据（例如「渲染出的卡片数 ≥ 事件数」或「当前状态表格行数 = active 事件数」），否则等于把唯一的护栏拆掉。

## 5. 默认开关形态

### 5.1 默认值：**false**，且建议把语义收窄（见 §6/§7）

判据（三条，都是实测/结构性的）：

1. **写放大**：开 = 每次事件写 7.43 MB（99.4% 是 index.json），CPU 243 ms；按今日调用量 20 次/日 = 148.6 MB/日。这不是「26 KB × N」的量级，默认开等于给每个用户加一个**每天几百 MB 的静默写盘**。
2. **失败姿态**：按细则原样开 ⇒ 100% CAS 冲突 + 100% M1 警示 + 短路失效；用户看到的是「白板没变 + 每次事件写都带一条丢卡警示」，且 conflicts/ 目录每写一次多一个 JSON。默认开 = 把这三个缺陷直接推给用户。
3. **用户可感知度**：第一次成功重绘会把磁盘 34 张手写卡的 id 换成渲染 id（交集仅 4 张）⇒ 前端选中态、用户手写的卡结构、以及「我上次写的那节」全部错位。这必须是**用户显式同意的动作**，不能是默认行为。

## 6. 只做「手动触发 + 定时」可行吗——四个形态比较

先明确一条**既有事实**：手动通路**已经存在且不需要改代码**——`memory_note({kind:'plan', fromEvents:true, expectedRevision:<memory_read 的 revision>})`（index.js:25058-25099；CAS 见 :25164）。它今天就能用，代价同样是一次 7.43 MB 写（因为它同样走 writePlanSnapshot）。所以「手动」不是「省掉写放大」，只是「写放大由人控制频次」。

| 形态 | 触发频率（本机实测口径） | 写放大 | 新鲜度 | 实现面 | 主要风险 |
|---|---|---|---|---|---|
| **A. 纯手动**（零代码，现状） | 由模型/用户决定 | 7.43 MB/次 | 按需 | **0 行** | 模型不记得调 ⇒ 白板长期不更新（现状即如此：磁盘 PLAN 与事件渲染第 6 行就分叉） |
| **B. 脏标记 + 心跳合并**（15 s tick index.js:29194 已有） | 1 次 / N 分钟；N=60 ⇒ 24 次/日 | 24 × 7.43 MB = **178 MB/日** | ≤N 分钟 | 中等：脏标记（内存+落盘，进程重启不丢）+ 合并器 + 与写盘锁的并发 | 定时器里做重活（心跳本身已有 6 个 bgGuard 任务）；N 小则写放大比 A 还高 |
| **C. 语义时刻触发**（handoff 写成功 / close） | 今日 handoff 4 + close 少 ⇒ **4–6 次/日** | 4–6 × 7.43 MB = **30–45 MB/日** | 阶段级（账本/收口时） | 小：2 个挂点（memory_note 的 plan/handoff 分支 :25225 之后；memory_event close :25771 之后） | 仍要修 CAS / archivedIds / 短路三处；close 幂等调用也会触发（靠短路挡） |
| **D. 手动 + 宿主定时任务**（schedule_* 或外部 cron 调一个 HTTP 路由） | 用户设定（日/周） | 每次 7.43 MB | 天级 | 大：要新增路由或工具（工具数 22 是硬锁，路由 86 也有文档锁） | 为一个低频动作扩工具/路由面，收益比最低 |

**结论**：B 的「合并」并不能把写放大降下来（它只是把 N 次并成 1 次，单次仍是 7.43 MB）；真正决定总量的是**触发频次 × index.json 体积**。因此**频次应尽量低、语义尽量明确** ⇒ C 是自动化里性价比最高的一档；A 是零成本兜底；D 不建议。

## 8. 建议：**不做「每次写都重绘」**，改成 C 形态 + 先修三处

### 8.1 明确建议

1. **不要按细则落地第二步**（CAS/短路/M1 三处缺陷任一都会让功能在真实工作区里失效或伤人）。
2. **不要默认开启**；`planAutoRedraw` 若保留，默认 `false`，并把语义写成「在**事件收口/账本写入**后重绘」，而不是「每次事件写」。
3. **本批的最小可交付**：把「手动 fromEvents + expectedRevision」写进提示词/文档（A 形态，零代码、零风险），把「每次写都重绘」降级为**待 sidecar 写放大治理之后再评估**的独立项。
4. 若必须现在就要自动化：只做 **C**（close + handoff 两个语义时刻），并把 §8.2 的五步全部做完再开开关。

### 8.2 最小落地步骤（C 形态，按顺序）

**S1（前置，必做）修 `redrawPlanFromEventsPre` 的三个判据**
- 版本：内部选项让 writePlanSnapshot 在 :5266 前令 `opts.expectedRevision = planRevisionPre(existing)`（existing 取 :5258-5264 自愈后的文本）；**不要**把空 `{}` 传进去。
- 归档集合：`archivedIds = parseWhiteboardPre(existing, {kind:'plan'}).cardIds`（与 M1 同源；**不用** planCardsPre）。
- 短路：`anchored === existing` 才 `skipped:'no-change'`（anchored 用 `anchoredPlanPre(this.wbWsKeyPre(p.projectDir), rendered)`）。
- 另加一条**渲染健全性**判据（卡片数 ≥ 事件数 / 表格行数 = active 数），补上 M1 被旁路后缺失的保护。

**S2 挂点只加两处**：memory_event 的 close（:25771 之后）、memory_note 的 `kind==='handoff'` 成功分支（:25225 之后）。create/append/set/rename 不挂。memory_log 不挂（等 sidecar 治理后再议）。

**S3 开关**：`DEFAULT_CONFIG.planAutoRedraw = false`（:766 区内，2 空格缩进）；门 = `(engine.config || {}).planAutoRedraw === true && String((engine.config||{}).boardMode||'') === 'graph'`；**不加 UI**。

**S4 文档计数**：verify-docs 期望值由文档侧提供，故同批改 WHITEPAPER.md:99、HOMEPAGE-CONTENT-FOR-GM53.md:279、FRONTEND-CO-CREATION.md:93、README.md、README.zh-CN.md 的 179 → 180，再跑 `node tools/verify-docs.mjs` 收 EXIT=0。

**S5 验收（真执行 + 负路径 + 变异）**
- P：改一条事件 ⇒ `wrote===true` 且 PLAN 字节变化、含新文本；
- N-1：同一状态连调两次 ⇒ 第二次 `skipped==='no-change'`，PLAN **字节与 mtime 均不变**；
- N-2：注入会抛的 writePlanSnapshot 桩 ⇒ 工具本身仍返回成功（事件写入不被拖垮），redraw 返回 `ok:false`；
- N-3：`m1Downgraded===false`（要真跑，不能静态断言）；
- 变异：删短路行 / 去掉 archivedIds / 把 expectedRevision 改回 undefined ⇒ 对应断言必红。

### 8.3 若用户坚持「每次写都重绘」

必须同批附三件事，否则不建议上线：
1. 先治理 `index.json` 全量重写（7.38 MB/次）——这是 99.4% 的成本，也是本项真正的瓶颈；
2. 强制节流（例如同一工作区 ≥10 分钟才重绘一次），把 148.6 MB/日压到可接受量级；
3. 在回执里显式回吐「本次未重绘 / 已重绘 / 被门拦下」，禁止静默（否则用户无法判断白板是否过期）。
