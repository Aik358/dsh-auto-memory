## 一、实测结果（10 例，全部真机验证）

用 node 原生 `http` 精确控制请求头，对 `GET /api/dsh-auto-memory/config` 发 10 次探测：

| # | 请求头 | 结果 |
|---|---|---|
| ① | `Host: 127.0.0.1:3080` | **200 ✓** |
| ② | `Host: localhost:3080` | **200 ✓** |
| ③ | `Host: 192.168.1.50:3080` | **403 ✗** `forbidden: loopback-only` |
| ④ | `Host: example.com:3080` | **403 ✗** `forbidden: loopback-only` |
| ⑤ | `Host: 回环` + `Sec-Fetch-Site: cross-site` | **403 ✗** |
| ⑥ | `Host: 回环` + `Sec-Fetch-Site: same-origin` | 200 ✓ |
| ⑦ | `Host: 回环` + `Sec-Fetch-Site: none` | 200 ✓ |
| ⑧ | `Host: 回环` + `Origin: http://evil.com` | **403 ✗** |
| ⑨ | `Host: 回环` + `Origin: http://127.0.0.1:3080` | 200 ✓ |
| ⑩ | `Host: 回环` + `Origin: https://accounts.google.com` | **403 ✗** |

**通过 5 / 10。**

### 结论（把 A 卷的推断升级为已证实）

1. **闸门②（Host）已证实**：Host 不是 `127.0.0.1` / `localhost` / `[::1]` ⇒ **一律 403**。
   ⇒ A 卷「经内网 IP 或域名访问时 54 条路由会全部 403」是**真事实，非推断**。
2. **闸门③（Sec-Fetch-Site）已证实**：`cross-site` ⇒ **403**。
   ⇒ **Google OAuth 授权码流的标准回跳（从 accounts.google.com 跳回本机）会被直接挡死**。
   ⇒ 我先前那份约束文档（`TEAMWORK-R2-CONSTRAINT-OAUTH-20260923.md`）的判断**成立**。
3. **Origin 也参与判定**：外部 Origin（含 `accounts.google.com`）⇒ 403；只有同源或无 Origin 才放行。

### 这对方案的直接后果

- **「把回调地址指向现有插件路由」这条路被实测否掉**（不是理论风险）。
- 路线优先级调整为（我此前倾向 B，现在仍维持但理由更硬）：
  - **B（本机临时回环监听）** —— 唯一不触碰现有安全模型的路线。但**仍未验证插件能否 `listen` 额外端口**（宿主 `webServer` 契约只暴露 `register/registerUpgrade/registerFallback/tapIndex/port`）。
  - **C（设备码，RFC 8628）** —— 天然无回调，且 **A 卷发现宿主自带 `ctx.authorization.registerFlow`（含 `session.notify({url})`），正是设备码的宿主原生形态**。这是本项目**最被低估的一条路**。
  - **A（为回调开一条受控例外路由）** —— 会削弱现有 54 条路由共享的安全模型，**必须同时补 state+PKCE 绑定**，风险最高，作退路。

## 二、用户本轮补充的两条关键信息

### 信息 1：「我这是用的远程操控插件，本来应该是 127.0.0.1:3080」

**含义**：用户当前**不是**在宿主本机的浏览器上操作，而是通过**远程操控**（远程桌面/远程 Web 之类）在使用 GUI。

这与实测 ③/④ 撞在一起：
- 若远程操控是通过 **端口转发/隧道**（把远端 3080 映射到本地），浏览器看到的 Host 仍是 `127.0.0.1` ⇒ 现有守卫**恰好还能工作**。
- 若远程操控是**直接访问宿主内网 IP 或域名**，则按实测 ③/④，**54 条路由全部 403、界面整体不可用**。
- ⇒ **必须先确认用户实际用的是哪种**（这是团队版的前置问题，不只是登录问题）。

**对身份架构的连带影响**：远程场景下浏览器不跑在宿主机器上，**「本机回环临时监听」这条路线的可用性依赖网络拓扑**——若浏览器在远端，`127.0.0.1:<随机端口>` 指向的是**用户那台机器**而非宿主，回调收不到。
> 这一点**推翻了我先前对路线 B 的乐观判断的一半**：B 只在「浏览器与宿主同机」时成立。
⇒ 综合看，**设备码（路线 C）在远程场景下反而是唯一稳的**，因为它不依赖任何回调拓扑。

### 信息 2：「后面的 dsh 版本还可以使用 DeepSeek 账号登陆」

**含义**：DSH 宿主**自身**在更新的版本里会提供账号登录能力。

我实测本机环境：
- 已装 dsh 版本 = **`0.1.6-alpha.2`**。
- 在本机 `@deepseek-ai/*` 包内**未检到** account/login/signIn 的实现（`auth` 命中的是 ACP 协议的 `authenticate` 桩与 `authMethods: []`，**不是账号体系**）。
- ⇒ **本机这个版本还没有账号登录**；用户说的「后面的版本」= 尚未安装的新版。

**对架构的影响（这是本轮最重要的一条）**：

| 分支 | 含义 | 对插件的要求 |
|---|---|---|
| 若新版 DSH 提供**宿主级账号身份**（如 `ctx.identity` / `ctx.account`） | 插件可**直接复用宿主身份**，无需自建 IdP 集成 | 插件只做「把宿主身份映射为成员 + 注入 `actor`」，**Google/阿里云接入交给宿主** |
| 若新版只是**登录 DSH 客户端**而不暴露给插件 | 插件仍需**自己**做 IdP 集成 | 走本文档第一节的三条路线 |

⇒ **这是必须先向 DSH 官方/新版确认的问题，不能猜。** 若宿主会暴露身份，本轮「自建 Google/阿里云 SSO」的**大量工作可省**，且一致性更好（同一个身份贯穿宿主与插件）。

**另：`~/.dsh/remote-web-ui-registry/web.json` 实测密钥结构**
- 文件 90 B，键为 `id`(len=16) 与 `secret`(len=43)（值已隐藏，未读取明文）。
- A 卷把它标为【未验证】用途。结合用户说的「远程操控插件」，**高度怀疑这就是远程 Web UI 的访问凭据**（推断，未验证）——若成立，它正是**远程访问身份**的现成入口，团队版应优先核清它，而不是另起一套。

## 四、诚实边界
