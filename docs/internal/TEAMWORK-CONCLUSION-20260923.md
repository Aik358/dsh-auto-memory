## 一、直接回答你提的三个问题

### 问 1：teamwork 要强调「人无我有」的能力 —— 找到没有？

**找到了，但只有 4 条，且都不是「更多记忆」而是「更可信的记忆」。**

大厂的统一解法是「**中心化知识库 + 连接器 + ACL 继承 + 用户级私有记忆**」（A 卷 §1.6）。它们能回答"公司里有什么"，**回答不了"这条结论当时是错的、错在哪、后来被谁推翻了"**。

更关键的一层（A 卷 §1.7 的地基）：**企业知识检索那一整类（Glean / Notion AI / Rovo / Dust / Slack AI）本质是「只读检索系统」——记忆的写入者是"人"，AI 只是读者。** 所以"记忆过时""记忆冲突"在它们的数据模型里**根本不存在**，它们不需要解决。而本项目的记忆是 **AI 自己写的**，这两个问题就是天生的。

经减法后剩下的 4 条卖点：

| # | 亮点 | 竞品等价物 | 为什么大厂做不了（真实原因，非"没想到"） |
|---|---|---|---|
| 1 | **记忆生命周期治理**（`superseded` / `retracted`，「返回但标记」） | 未找到 | ① 权限边界：标记意味着"错的东西还在库里"，与合规取向（要删）相反；② **技术硬障碍：派生数据无稳定 ID**——他们的向量/索引/图谱从数据模型上就没有"这条结论的身份证" |
| 2 | **防记忆劫持**（无模型参与的记忆写入结构性不可能） | 未找到 | 他们靠**模型对齐**兜；我们改不了别人的模型，只能在数据层解。且他们**规模大到无法逐条审校**，只能接受概率性污染 |
| 3 | **「失败与弯路」是一等公民**（跨人接续继承的是**排除项**，不只是结论） | 未找到 | ① **输入不存在**：失败从来没被落纸；② 知识管理传统把失败当负资产；③ 缺「项目交接」这个实体 |
| 4 | **可信度可量化**（技能晋升要跨会话证据，证据量公开） | 未找到 | ① "给人写的规则加验证门槛"在它们的产品形态里是侮辱性的；② **跨用户证据聚合的实体不存在** |

**最好的宣传语（A 卷 §3.1）**：新人接手一个当事人不在的项目时，能继承的不只是结论，还有**「哪些路走过是死的、为什么死」**。

**被降级为"技术底座、不作卖点"的 6 条**：写入侧锚点保护、Tier-0 预算裁剪、上下文水位、证据链三店、双库作用域、技能导出约束。理由：要么用户感知不到（预算裁剪/水位），要么是**必备品而非卖点**（写入保护）——用户不会为"你不会把我的数据写坏"额外付费，但没有它就不敢让人多写。

### 问 2：commit / 工作流 / RAG 这些「大厂做得很好」的 —— 做不做？

**做，但都只做最小形态，且明确列出「不做」清单。** 优先级与边界（A 卷 §3.2）：

| 对标项 | 最小可用形态 | 明确不做 |
|---|---|---|
| **RAG** | **只接一个来源：共享记忆库本身** | 不做连接器生态（Glean/Slack/Notion 那些我们拼不过，也不该拼） |
| **commit / 版本** | 复用已有字段 `expectedDigest` / `expectedStateVersion`（**已存在，见 `lib/state-commit.js:179-191`**） | **不做 diff**——记忆条目的 diff 语义不清，做出来没人看 |
| **工作流** | **只做「交接五步链」** | 不做通用工作流引擎（那是另一个产品） |

### 问 3：「实时同步会不会对向量编码有点困难？」——**不会，瓶颈不在这里**

**这是本次调研最值钱的一条结论（B 卷 §0）：**

> **实时同步对向量编码不难，难的是冲突与一致性；而"实时"这个词对向量本身也不必要求到实时。**

三条支撑：

1. **成本量级不构成约束**【实证 + 推断】。本仓实测吞吐 **41–48 chunks/s**（`docs/M7-EMBEDDING-BENCHMARK.md:66`）⇒ 10 万条**全量**重编码本地约 **37 分钟**（一次性、可后台跑），云 API 约 **$0.4**。"重编码贵"在本项目量级不成立。
2. **本仓已有两道现成防线**（我亲自实测）：
   - **向量复用已是内容寻址**：`sha256Hex(it.l0)` 命中即复用，**跨 id 复用**且**批内同 hash 只嵌入一次**（`lib/l0-index.js:154-177`，注释原话「不变更新的真实输入数 = 0」）⇒ **同一段文本永远不重算**。
   - **向量工件自带"向量空间身份"**：实测 `~/.dsh/memory/semantic/vectors-*.json` 内含 `identity{provider, model, modelRevision, dimension:1024, normalization, dtype, chunkPolicyVersion, configHash}` + `workspaceRef` + `scope` ⇒ **换模型/换维度/换切块策略会造成身份不匹配，天然隔离，不会静默混用**。
3. **真正的瓶颈是冲突与一致性**【实证 + 推断】。嵌入是**无状态纯函数**（可重放、幂等、可并行）；冲突是**有状态分布式问题**（不可重放、有顺序依赖、错了静默丢数据）。

**因此「实时同步」应该落到这些可验收指标（B 卷 §0）：**

| 环节 | 目标 | 能否异步 |
|---|---|---|
| 记忆文本 + 状态标记可见 | **≤ 5 秒**（p95） | **否** ← 这才是"实时"的真实含义 |
| 词法（倒排）检索可用 | **≤ 5 秒**，与文本同时 | 否 |
| **向量检索可用** | **≤ 5 分钟**（p95） | **是**（可后台补齐） |
| 换嵌入模型 / 维度 | 小时级，计划内窗口 | 是 |

**业界本来就是这么做的**【实证】：主流向量库**默认即最终一致**——[Milvus 的 ConsistencyLevel](https://milvus.io/api-reference/cpp/v2.6.x/Collections/ConsistencyLevel.md) 提供 Bounded Staleness 等多档、[Weaviate 有 `HNSWWaitForCachePrefill` 这类异步预填开关](https://github.com/weaviate/weaviate/blob/89814a74/adapters/repos/db/repo.go)、[Qdrant 批量上传走异步索引](https://qdrant.org.cn/documentation/tutorials-develop/bulk-upload/index.md)。而**本仓的词法兜底（语义双条件门缺一即降级）早已是这个形态的实现**——建议从"异常降级路径"升格为**设计内的一等公民**。

## 二、同步架构选型（B 卷 §4 结论）

**推荐主线：候选 B（权威服务端 + 事件日志 / CDC）**，候选 A（对象存储快照）作为落地第一步与降级路径，候选 C（CRDT 本地优先）**暂不采用**。

**暂不采用 CRDT 的两个原因**：
- **向量本身不是 CRDT** ⇒ 两端各自算出的向量无法收敛（结构性短板，不是调优能解决）
- **CRDT 承诺"不漏任何写入"，与"让错误失效"直接冲突**（A 卷独立得出同一结论）；且 agent 是**整篇重写**而非局部编辑，CRDT 挡不住推平

**可直接升格为同步原语的三个本仓资产**【实证，我已逐条核验行号】：
1. **单调状态** `['current','superseded','retracted']`（`lib/state-commit.js:38`）——只追加不回退 ⇒ **可交换、可幂等**
2. **两阶段提交 + fail toward duplication, never toward loss + 每写必读回校验**（`lib/hub-io.js:390-398` 注释、`:493-509` 实现、`:420-429` 回滚）——**直接是同步搬运原语**
3. **幂等提交单据** `{workspaceKey, boardId, txId, actor, writes, stateChanges}`（`lib/state-commit.js:179-191`）——**即现成的 CDC 事件载荷**

阿里云为主的产品对比（DashVector / Tablestore 向量 / RDS PostgreSQL + pgvector / Milvus / OSS / SLS / FC / RocketMQ / 云效 Codeup）与四阶段路线见 B 卷 §4。

## 三、必须由你拍板的三件事（其余都可以我来定）

| # | 待拍板项 | 为什么必须你定 | 我的建议 |
|---|---|---|---|
| 1 | **团队版是否引入成员身份**（"谁写的"） | **这是所有亮点的共同前置**：当前系统是**单人设计**，没有 `addedBy` 之外的作者概念（`lib/procedure-store.js:140/176/272/757` 只有这个字段）。不引入，亮点 1/3/4 只能做半截 | **要引入**，且最小形态就是扩用 `addedBy` + 成员表，不必上完整 RBAC |
| 2 | **通用库写入是否需审批** | 涉及团队信任模型 | **只留痕不审批**（同 A 卷建议）——否则 RBAC 审批流会吃掉整个版本周期 |
| 3 | **「失败与弯路」的书写摩擦是否强制** | 涉及用户会不会真的写 | 建议**强制**（否则这条最好的亮点会因为"没人写"而空转） |

另有两项技术取舍（可随第 1 项一起定）：`superseded` 在团队版是否引入**降权**（当前用户裁定是"返回但标记、不降权"）；换模型时用**多向量字段**还是**集合别名切换**。
