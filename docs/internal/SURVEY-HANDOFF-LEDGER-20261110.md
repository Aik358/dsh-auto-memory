### 0.2 任务书 §1.2「四段骨架和大部分内容基本不变」——**这条前提不成立**

原文断言「每次真正变化的往往是『进度与下一步』或『失败原因』的一两条」。实测（`scripts/05-similarity-clusters.cjs`）：

|---|---|---|---|---|

| ≤30 min | 399 | 7.88% | 0.2777 | 31/399 |
| ≤60 min | 514 | 6.83% | 0.2634 | 32/514 |
| 全量相邻 | 686 | **6.56%** | **0.2431**（中位 0.2064） | **34/686（5.0%）** |

## 1. TL;DR（≤10 行）

1. 「每次新建」**不是实现惰性，是 M-CM1 的原始设计**：`handoff-<ts>.md append-only` 从提交 `1578f98d`（2026-09-06）起就是「append-only 语料」，紧接着 `9a7b5e35` 又把它接进 `memory_recall(scope=handoff)` 当检索语料。**用户今天的裁定是推翻这套原始定位，不是修一个 bug**。
2. 「四段骨架和大部分内容基本不变」**不成立**（相邻篇行级复用率 6.56%、bigram Jaccard 0.24）。编辑化的收益不在正文，在**骨架 16.39% + 文件数 + 派生索引 + 重复全文拷贝**。
3. 账本与事件 sections **格式同构但语义层级不同**（代码自己写明了：事件头=整件事低频当前态，账本=本次会话高频快照，`event-write.js:752-760`）。照搬事件 sections 会复现当年被修掉的缺陷（事件卡「目标」变成流水）。
4. 但**「同一份三写」是真的**：刷新仪式提示词 `index.js:7917-7919` 明令「先写事件四段 → 再渲染白板 → 再写一篇账本」，同一组四段在同一仪式里落三处；注入面再分两段各投一次。这是 4.5「跨形态去重」登记项，不是新发现。
5. A/B 两类成立，但比例要收窄：**A 类（绑事件）= 21/687 = 3.06%**（最近 60 篇 13 篇），**B 类里只有约 1/3 是跨事件/批次级路线图**，56% 仍是单工作单元快照，14% 是自动骨架。
6. 账本确实提供事件库没有的东西，但**只剩 4 类**：①pre-WAL 的 523 篇历史（不可重建）②降级/跨工作区兜底（事件写失败、无工作区绑定）③给人看的带时间戳文件列表（面板「交接账本」页签）④本轮四段的「最新态」（事件头 sections 实测 29/53 事件为空、与最新账本 20/20 不一致）。
7. 推荐路线：**改造（B+），不是保留原状、也不是整类取消**——写成「每个工作段/批次一份、按 eventId 或项目级容器事件归并、按节 upsert 编辑、不进 RAG、注入面只留一段」，存量 687 篇**只归档不合并**。
8. 与 2.7 **必须合并做**，且顺序固定：**2.6（memory_note 加 eventId）→ L1/L2（稳定路径+upsert）→ 2.7+L3（WAL 只记增量/摘要+指针）→ D4/L4（读侧隔离）**。先做 2.7 会白做一次文件名契约（见 §7.3）。
9. 波及面比任务书列的多 6 处：`_collectWhiteboardDocsPre` 看板全量读盘、`index.json` 全量重写、`event-store.json` 全量重写、`handoff-state` 路由、刷新仪式提示词、全局兜底指针。
10. 实测写放大：**每写一篇账本 ≈ 10.6 MB 磁盘写**（3 KB .md + 3.24 MB event-store 全量重写 + 7.38 MB index.json 全量重写）。这是编辑化最硬的收益点。

### 2.4 为什么当年选择「每次新建」而不是「编辑更新」？（给证据，不猜）

**有证据的四条理由（按证据强度排序）：**

1. **文件名就是时间线，是产品契约**（`1578f98d` 注释 + `handoffStamp()` `:1639` + `listHandoffLedgers` 按字典序倒序取最新 `:5959` + 同秒 `-b/-c` 后缀保序 `:5396`）。编辑会破坏「文件名时间戳 = 这一篇的写时刻」这条读取契约。
2. **它是「append-only 语料」，与日志同构**（`:5373` 注释逐字）。M-CM2 再把它接进检索 ⇒ 追加式语料才符合「语料」语义；可编辑的文档不适合当检索语料（同一路径内容漂移，召回结果不可复现）。
3. **新建使写入路径无需防覆盖**：`beforeText:''` ⇒ 保护门显式不适用（`:5872-5879`），只需过判据门 H1–H4；不用 CAS、不用锁、不用处理并发读改写。**这是省掉一整套一致性机制的最省事形态**。
4. **判据门要求每次写「完整四段」**（H1 标题齐、H2 每段非空 ≥20 字，`ledger-criteria.js:65-81`；上限 8,000 字 `index.js:25105`）⇒ 天然是「写整篇」，没有为「写单节」设计过入口。

**没有找到的证据（必须说明）：**
- 全仓、git log 里**没有任何「评估过编辑更新并否决」的记录**。`git log -S"不追改旧账本"` 命中的是提示词改写（`7d4f409c`/`53d20e7a`/`8e76cc88`），不是设计评审。
- `writeHandoffLedger` 自 `1578f98d` 起就是「新文件」，之后只加过判据门（`P0 2026-09-14`）、锚点（`L5 2026-09-17`）、sidecar（`P2 2026-09-16`）、WAL（`v4-C1 2026-10-25`），**没有一次改动讨论过「改成编辑」**。
- ⇒ **「每次新建」是形态选择的自然结果（省事 + 文件名即时间线 + 当语料用），不是权衡后的裁决。** 这正是用户的新裁定可以推翻它的依据。

**「为什么把账本和白板绑在同一配置项」**（Lead 追加问题）：因为 `1578f98d` 一次提交同时交付了 `PLAN.md` 快照、四段式账本、白板页签、水位触发——在 M-CM1 里它们是**同一件能力（交接白板）的三个部件**。`handoffEnabled` 是**总开关**语义（`:970` 「false=完全不读写」），不是说两者概念相同。此后没有做解耦，是因为**没有需求**，不是因为认定它们该在一起。

## 3. 问题①：能否减少重写新建，改为编辑更新为主？

### 3.1 现在为什么是新建？（技术原因是 append-only 契约，还是实现简单？）

**两者都不是「不可改的契约」，是「两条独立契约被混在一起当成一条」：**

| 契约 | 位置 | 强度 | 改编辑会不会破 |
|---|---|---|---|
| **事件检查点 append-only** | `event-store.js:914` 注释「append：仅允许追加 checkpoints…」；全库唯一整体替换点是迁移专用（`upgrade-apply.js:368`） | **真契约（硬）** | **不会破**。编辑的是 .md 文件，与检查点存储无关 |
| **账本文件 append-only** | 只存在于注释（`:5373`）与提示词（`:447`）里；**没有任何代码强制**（`writeHandoffLedger` 用 `writeFullRaw` 写任意路径，没有「同名文件已存在则拒绝」的判据） | **软约定（可改）** | 会被破，但破的是「文件历史序列」这条**读侧契约**，不是存储契约 |

⇒ 回答任务书 2.1.1 的追问：**技术上可以改编辑**，前提是同时改读侧（最新篇判定、列表、归档、检索）与提示词。**真正的拦路虎不是 append-only，是「文件名=时间戳=历史版本链」这个读侧契约。**

### 3.2 改成编辑更新会破坏什么？（逐个列，含实测结论）

| 风险 | 结论 | 证据/对策 |
|---|---|---|
| **事件检查点 append-only** | **不破** | 见上表；两者不是同一契约 |
| **锚点 `<!-- memory:mem_*`** | **风险低，且编辑反而更稳**。锚点 id = hash(ws, relPath, title, ordinal)（`wb-sidecar.js` `computeWhiteboardCardIdPre`/`applyAnchorsPre`）；relPath 稳定 ⇒ id 稳定。**现状每篇新文件 ⇒ relPath 每次都变 ⇒ 每次重算新 id**（实测 618 篇 / 2,489 个锚点，全是一次性的） | 需注意：编辑时改小节标题会改 id ⇒ sidecar 条目 id 变（会触发 `writeSidecarEntryPre` 的「同 source 清理陈旧条目」逻辑，行为上等价「换卡」）。**账本 target 不跑保护门**（`:5879`），所以锚点变化不会触发丢卡拒绝 |
| **判据门（H1–H4 / S1–S4）** | **需要改喂法**：现在判据跑在「写盘全文」上（`:5387-5395`）。若只传增量节，H1/H2 必失败。对策：先读旧文 → 合并出**新全文** → 再把新全文送判据门 → 通过后落盘（判据语义不变，只是输入换成「合并后全文」） | `ledger-criteria.js:59-101`；`checkMutationPre:5853-5935` |
| **M1 / P-H1 / 锚点门** | **不受影响**：三者都是 **plan 专属**（M1 在 `:5909` 硬编码 `target==='plan'`；P-H1 是 `checkPlanCriteriaPre`；锚点/用户区保护在 `:5878-5880` 提前返回）。账本唯一相关的门是 H1–H4/S1–S4 | 已核：`checkMutationPre:5879`「ledger-append-only-no-before-side」 |
| **并发写冲突** | **新增风险（现在没有）**。现状：文件名唯一 ⇒ 并发写只是多两篇文件，最终一致。编辑后：读改写必须串行。**现成解法：`withSharedStateLock(file)`（`lib/shared-state-lock.js`，`journal-storage.js` 已这样用）** | 需补：锁内 read→merge→write 全程；锁粒度 = 单账本文件 |
| **「最新一篇」判定** | **要改一处**：`readLatestHandoff`（`:5028-5046`）用 **mtime** + 文件名决胜 ⇒ 编辑会更新 mtime，**行为正确**；但 `listHandoffLedgers`（`:5959`）**按名字排序取最新 12 篇** ⇒ 编辑后的旧文件会排在很后面，被检索漏掉 | 改：listHandoffLedgers 排序键由「名」改「mtime」 |
| **sidecar 索引 / 看板** | **要改**：同一篇文件被编辑后，`writeSidecarEntryPre` 会按 source 清旧条目再 upsert（`:5454-5464`），逻辑本身兼容；但账本不再每篇一文件 ⇒ 卡片数骤降（见 §3.4） | —— |
| **事件检查点 idemKey** | **要改**：`idemKey = kind + sha1(ledgerPath + 全文)`（`event-write.js:713,737`）。编辑后同一 path 不同全文 ⇒ 不同 key ⇒ 不会误去重（正确）；但若改成「只记增量」，idemKey 需基于 eventId+节+内容重算 | 与 2.7 合并处理 |
| **历史可追溯性** | **要转移载体**：账本不再保留历史版本 ⇒ 历史必须由事件检查点承担。实测：WAL 时代（2026-10-25 起）154 篇有检查点（164 条，含重试）；**pre-WAL 的 523 篇没有**任何事件侧副本 | ⇒ 存量不迁移（见 §3.5） |

### 3.3 编辑什么、新建什么（具体建议）

**写入单位（这是关键，见 §4 的 A/B 分析）：不是「每个事件」，而是「每个工作段/批次」。**

- **默认：一个「账本单位」= 一个批次/工作段**，用 `batchId` 标识（A 类 = `eventId`；B 类 = 项目级容器事件 id，如 `evt_project_<ws>` 或显式传入的 batch 名）。
- **每次 `memory_note(kind=handoff)` = 对该文件做「按节 upsert」**：
  - 默认只更新 `进度与下一步` + `任务状态`（实测这两段占 54.4% 字符，且是每次必变的）；
  - 允许一次传多节（`sections:{goal,deadend,...}`）；
  - 未传的节**原样保留**（不重写、不丢）。
- **必须新建的时机（四条）**：
  1. 该 `batchId` 首次写账本；
  2. 上一份已 `closed`（事件收口/批次交付）后进入新阶段；
  3. 跨自然日且提示词要求「每日交接」（可选，建议默认不新建，因为账本是「这件事」而不是「这一天」）；
  4. 用户显式要求 `newLedger:true`（逃生门）。
- **落盘路径（稳定，不带时间戳）**：`handoff/ledger-<batchId>.md`（例如 `handoff/ledger-evt_23e2976e.md`、`handoff/ledger-project--D--dsh-auto-memory--.md`）；文件内部首行保留 `# 交接账本 · <创建时间>`，另加 `lastUpdated=<时间>` 与 `revision=<n>` 供「最新篇」判定与 CAS。
- **什么时候**保留时间戳命名的旧账本：存量 687 篇**一律不动**（见 §3.5）。

### 3.4 量化收益（可复算，脚本 `scripts/05`、`scripts/04`）

**先给不成立的估算，避免误导**：「按只改一条估算省 90% 正文」是错的（相邻篇正文行级复用仅 6.56%）。**能拿到的是下面四项：**

| 收益项 | 现状实测 | 改造后（按 60 min 工作段归并） | 降幅 |
|---|---|---|---|
| 账本文件数 | 687 | **173**（保留每段最后一篇的投影） | **−74.8%** |
| 账本字节总量 | 2,095,611 B | **507,483 B**（同投影） | **−75.8%** |
| 小节卡片数（喂看板/索引） | 2,848 张（去重 301） | **730 张** | **−74.4%** |
| `index.json` 体积（每次写全量重写） | **7,321,380 B**（实测重建） | **1,888,669 B** | **−74.2%** |
| 看板单次读盘 | **2,123,008 B / 328.2 ms** | 554,482 B（−73.9%） | —— |
| 每篇骨架重写量 | 211,286 B 合计 / 308 B 每篇（16.39%） | ≈0（编辑不重写骨架） | −16.4% |
| 每写一次的磁盘写放大 | **≈10.63 MB**（3 KB .md + 3.24 MB event-store 全量重写 + 7.38 MB index 全量重写） | **≈5.13 MB**（index 降至 1.89 MB） | **−51.7%** |

**说明与口径**：
- 「保留每段最后一篇」是**理论上限投影**，前提是中间篇的内容已被事件检查点接住。**pre-WAL 的 523 篇不满足这个前提**（无事件副本）⇒ 该投影**只能用于新增写入，不能用于存量合并**（§3.5）。
- 归并粒度选择依据（`scripts/05`）：10 min 段 498 个（几乎不省）；30 min 288 个（−58.1%）；**60 min 173 个（−74.8%，且单篇段只有 70 个、最大段 51 篇）**；120 min 104 个；按自然日 56 个（−91.8%，但一天一账本会把不同批次混在一起，不推荐）。
- **建议取 60 min 作为默认「工作段」口径的可配置值**（`ledgerSegmentMinutes: 60`），不写死。

### 3.5 存量 687 篇怎么处置？

**结论：不合并、不改写、只归档；存量是历史，不是技术债。**

| 处置 | 做法 | 理由 |
|---|---|---|
| 保持原样 | 687 篇留在 `WS/handoff/`，不改内容 | append-only 与可追溯性；pre-WAL 523 篇无事件副本，改写=销毁唯一记录 |
| 停止增长 | 新书写路径不再产生时间戳新文件 | 新形态用稳定路径 |
| 归档 | 达到阈值（如新形态稳定运行 14 天后）整体移入 `WS/handoff/archive/`（该目录已有 329 篇 PLAN 归档先例，4,097,500 B） | 归档后必须**同时**把它移出召回面（见 §5 RAG 行），否则 `searchHandoffCorpus` 仍全量扫 329+687 篇（实测单次 **4,643,008 B / 389.8 ms**） |
| 不合并 | 不做「多篇合成一篇」 | 合并=重写=丢内容（相邻篇复用率仅 6.56%，合并必丢 90%+）；且 2.4 归并教训（`applyRegroupPre` 不判对象归属会全量归档） |
| 索引清理 | 归档时用 `(_writeSidecarIndexPre)` 的 source 清理逻辑重建一次 index | 否则 2,843 条 ledger 小节条目永久留在 7.38 MB 索引里 |

### 3.6 若最终「取消账本」，问题①是否自动消解？

**部分消解，但有两个副作用要接住**：
1. 「编辑 vs 新建」问题消失（不再有账本文件）；**但「历史承载」问题转移到事件检查点**——如果 2.7 又把检查点改成摘要，则**账本取消 + 2.7 摘要化 = 全文历史无处存放**。这是三线合并时最容易踩的坑（见 §7.3）。
2. 存量 523 篇 pre-WAL 账本仍是唯一记录 ⇒ **取消只能是「停止新增」，不能是「删除文件」**。

- B 类占比高的**原因之一**是时代：`eventId` 约定 2026-10-24 才出现，且**只有刷新仪式提示词**要求写（`index.js:7919`「账本首行必须写 eventId=…」），普通 `memory_note(kind=handoff)` 的提示词/工具描述**从不要求**。⇒ **86% 的 WAL 时代账本也没绑事件，是设计缺口（2.6 要补的 `eventId` 参数），不是用户偏好。**

### 4.3 如果账本改为「项目级视图」：三种形态对比

| 维度 | **形态 A**：单文件、内部按 eventId 分节 | **形态 B（推荐）**：每工作段/批次一文件，A 类绑 eventId，B 类绑项目容器事件 | **形态 C**：账本不再是文件，纯事件库视图（与白板同构） |
|---|---|---|---|
| 文件形态 | `handoff/ledger.md`（唯一） | `handoff/ledger-<batchId>.md`（稳定路径，少而长） | 无文件（或只有一份渲染快照） |
| 与 append-only | 破 .md append-only，**不破**检查点 | 同 A | 完全不需要 .md |
| 接续用法 | 注入「当前 `##` 节」，需按 batchId 选节 | 注入**该批次的当前态**，路径稳定、CAS 可做 | 注入事件卡片段（已有） |
| 与 RAG 隔离 | 容易（一个文件加白名单） | 容易（目录白名单 + kind 过滤） | 天然隔离（不进语料即可） |
| 迁移代价 | 高（687 篇要「拆节合并」= 重写） | **低**（存量不动，新增走新路径） | 中（要把 A 类 21 篇内容回灌事件？不必要——它们已在检查点里） |
| 并发 | 单文件全工作区串行（争用最大） | **按文件锁**（争用小） | 走事件库既有 `mutatePre` |
| 用户可见性 | 一个文件，翻起来最长 | **按批次分文件，最接近用户说的「每个事件一个/多个事件共享一个」** | 面板只能看事件卡，丢失「时间线文件列表」 |
| 跨事件信息 | 需要额外一层「跨事件节」 | **天然：项目级容器事件的一份账本** | 需要项目级容器事件（2.6 已提出该协议） |
| 主要风险 | 单文件无限膨胀、并发争用 | 需要 `batchId` 归属判定（复用 2.6 的归属门） | 丢失人读文件与兜底能力 |

**推荐：形态 B（改造），并把形态 C 作为**长期收敛方向**（等 2.6 的项目级容器事件协议落地、且事件 sections 能被可靠更新之后再谈）。**

### 4.4 三种形态都要回答的两个问题

**Q：与「事件卡片注入段」的分工是什么？**
- **事件卡片段 = 明细**（T2，≤2,400）：只展开当前 1–2 个 active 事件的**四段当前态**，告诉模型「这件事到哪了」。
- **账本段 = 批次总览**（走 `handoffLedgerChars`，建议 400–800）：告诉模型「**这一批/这一阶段**整体到哪了、下一批做什么、哪些坑已经踩过」——**跨事件的那一层**。
- 两者**必须做内容指纹去重（4.5）**：账本段里如果只是重复事件卡的四段，就不该再投一次。实测：账本段 800 字符 + 事件卡 ≤2,400 字符，两段独立预算，**同义内容最多可重复投 3,200 字符**。
- 分工的**判据**：账本段只保留「事件卡里没有的」= 跨事件下一步 / 批次路线 / 已放弃方案（死路）；单事件的四段由事件卡承载。

**Q：「跨事件的接续信息」放哪？**
- **放「项目级容器事件」的账本 + 事件 sections.next**。2.6 已提出「项目级容器事件」协议（`SURVEY-2.6-2.7-2.8-20261110.md` §2.3），本任务与它直接对接：
  - 一个工作区一个项目级容器事件（`kind=project`，名称=项目名）；
  - 它的 sections.next = 「下一批做 X」这类跨事件结论；
  - 它的账本文件（形态 B 的 B 类） = 批次级路线图（就是 `20261012-161009` 那种）。
- **白板 PLAN 的 `待办` 节**已经渲染 `sections.next`（`plan-render.js`），所以「跨事件下一步」在白板上已有投影 —— **账本不应该再写一份第三份**（这是 D-6 的修法）。

### 4.5 与白板 PLAN.md 的边界（若账本也变成投影，两者还分得开吗？）

**能分开，但必须用「内容职责」而不是「文档类型」来分：**

| 文档 | 职责 | 更新时机 | 数据来源 | 用户可见位置 |
|---|---|---|---|---|
| **PLAN.md** | **项目全貌**（当前状态表/近期进展/关键约束/待办） | 方向变化、阶段收口 | **事件库渲染**（`fromEvents`，`plan-render.js`） | 面板「白板」页签 |
| **账本（改造后）** | **批次交接单**（这一批做什么、做到哪、下一批第一步） | 每个工作段收尾 / 接续前 | **模型手写**（含跨事件结论），单事件部分可从事件四段预填 | 面板「交接账本」页签（保留） |
| **事件卡片** | 单事件明细四段 | 每次变动 | 事件库 | 注入段 |

⇒ 判据：**「项目级 → 白板」「批次级/交接级 → 账本」「事件级 → 事件卡」**。三者若都变成事件的投影，就退化成「同一数据的三个渲染器」，那才是用户反对的「混为一谈」。**账本就是唯一允许「模型手写的跨事件叙述」的载体**，这是它改造后的身份。

### 4.6 三条路线对比与推荐

| 路线 | 做法 | 收益 | 代价 | 判定 |
|---|---|---|---|---|
| **R1 保留原状** | 继续每篇新建、继续进 RAG、继续喂看板 | 零改动、零迁移风险 | 用户三条裁定全部不落地；写放大 10.6 MB/次、看板 2.8k 卡、召回 61.28% 被快照占据 | **否决**（与用户裁定正面冲突） |

### 6.3 建议 API（伪代码，不落地）

```js
// ── 写入（memory_note(kind=handoff) 内部调用这一层，调用方不碰磁盘）──
ledgerStore.upsertSection({
  projectDir,
  batchId,                    // A类=eventId / B类=项目容器事件 id；缺省 => 归属门推导

ledgerStore.read({ projectDir, batchId })            -> { ok, text, revision, path, sections }
ledgerStore.list({ projectDir, limit, includeArchived }) -> [{ batchId, path, revisedAt, title, status }]
ledgerStore.archive({ projectDir, batchId, reason })  -> { ok, archivedPath }
ledgerStore.latest({ projectDir })                    -> { batchId, path, text, revisedAt }  // 兼容 readLatestHandoff

ledgerWal.replay({ projectDir, eventId }) -> { applied:boolean, sections:string[] }   // Phase2 失败恢复

// ── 召回闸门（D4 用；单一真源）──
ledgerRecall.inCorpus({ kind, sourceRef }) -> false
ledgerRecall.search({ terms, limit }) -> [{ where, matches }]      // 改造后的 scope=handoff

// ── 系统化协议（成文，写进 docs）──
// P1 单位协议：一个 batchId 一份账本；batchId 来源优先级 = 显式参数 > L1 标识命中 > 项目容器事件 > 新建
// P2 更新协议：默认只 upsert「进度与下一步」+「任务状态」；未传的节不重写；revision +1
// P3 新建协议：仅 batchId 首见 / 上一份 closed / 用户显式 newLedger
// P4 隔离协议：账本永不进 RAG 语料；注入面只投「跨事件层」；看板不喂账本卡片
```

**与 sidecar-store 原型的对应**：store↔`ledger-store`、codec↔`ledger-format`、journal↔`ledger-wal`、state↔revision/CAS、adapter↔`ledger-index`。**唯一不照抄的**：原型「Markdown remains the source，从不编辑源文件」（`markdown-adapter.js:7-10`）——账本改造**恰恰要编辑源文件**，所以 adapter 层必须新增 `upsert` 语义（这是与白板索引层的最小哲学冲突，需要在协议里显式写出来）。

### 7.3 与 2.6/2.7/2.8 的冲突裁决（**任务书要求的「谁先做」**）

**冲突本体（同一行代码）**：`lib/index.js:25139-25161` 的 Phase 1 把 `ledgerText: writeH` 传给 `appendHandoffCheckpointPre`，`event-write.js:737` 把它塞进 `ckPayload.text`。**2.7 要改这里（全文→摘要+指针），本任务 R2 也要改这里（全文→增量+稳定路径指针）。**

**结论：合并做，不分开做。顺序固定为：2.6 → L1/L2 → （2.7 + L3 合并为一项）→ D4/L4。理由三条（按强度）：**

1. **2.7 的指针方案依赖本任务提供的「稳定文件名」。** 2.7 测绘报告 §3.2.2 明确：handoff 的指针「Phase 1 在 Phase 2 之前，拿不到最终文件名」，只能提两个 hack（H1 预生成时间戳占位传给 Phase 2；H2 事后补一条 pointer 检查点）。**如果先做 2.7，这两个 hack 都要先实现一遍，R2 落地后再推翻重做。** 而 R2 的稳定路径（`handoff/ledger-<batchId>.md`）让 Phase 1 **天然知道**文件路径 ⇒ 2.7 的 H1/H2 直接不需要了。
2. **R2 单独上线会让检查点体积不降反升。** 编辑化减少的是**文件**，不减少**写入次数**（每次 `memory_note` 仍是一次写）。若 L3 不做，每次编辑仍往检查点塞一份全文（1,689 字符均值）⇒ 事件库/RAG 语料继续按写入次数增长，**只是 .md 不再长**。用户「减少重写量」的意图只能在一半上落地。
3. **D4（读侧跳过 handoff）的过滤口径必须在 2.7/L3 之后定。** 现在 `kind∈{plan,handoff}` 的语义是「全文快照」；改完后 handoff 检查点的语义变成「增量/摘要」，两者不再同质。**先做 D4 会按旧口径写死过滤清单，改完语义后口径又对不上。** 用户 2026-11-10 已裁定 D4 后置到「2.6/2.7/2.8 测绘完成之后」（`CONSTRUCTION-PLAN:233-236`）——本报告的 7.3 与那条裁定一致，并进一步指出「测绘之后还要等 L3 落地」。

**为什么不「先 L3 再 2.7」分两步**：两者改的是同一个 `ckPayload` 对象（`text/sourceRef/idemKey/panels` 四个字段），分两步会各改一次、各写一套验收、各跑一遍回归。**合并后一次改完，验收判据取两者交集**（见 L3 行）。

**与 2.6 的关系**：2.6 是硬前置（`memory_note` 无 `eventId` 参数 ⇒ 无法按事件归并账本；实测 96.9% 账本无绑定）。
**与 2.8 的关系**：2.8（失败标记 Phase 0 前置拦截）与 L3 的 Phase 3 补偿相邻但**不冲突**——2.8 只改「失败时是否入库」，L3 改「成功时存什么」。建议 2.8 在 L3 之后做（因为 L3 会改补偿文案与 idemKey 口径，2.8 的拦截清单要基于新口径）。
