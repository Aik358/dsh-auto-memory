## 1. TL;DR

八项协议已经可以闭合到**隔离实现入口**：

1. `documentId` 是稳定文档身份，`revision` 是规范化内容摘要，二者不得由 mtime 或最近 active 事件代替。
2. 检查点必须新增并持久化 `checkpointId`；多事件更新共享同一个业务 `opId`，但每个事件、每个 WAL 阶段使用独立的存储操作键。
3. 最终目标 revision 必须在 Phase 0 构造完整候选文档时算出；Phase 1 写 prepared，Phase 2 后追加 committed，不修改旧检查点。
4. `handoffMaterialStamp` 必须包含新文档目录中每份文档的内容 revision；同名、同 mtime 的内容更新必须改变指纹。
5. 跨进程锁只提供互斥，不提供 CAS、原子写或业务回滚。文档、共享索引、事件库不得靠一把大锁伪造成跨资源事务。
6. 当前 11 个读侧均不能凭既有实现自动支持 `handoff/documents/`；必须逐项接线、逐项实测。
7. 「上周我做了什么」必须由事件检查点、日志及历史会话的时间线查询回答，不能依赖当前维护文档。
8. 存量审计先于迁移，迁移先于任何删除；没有独立恢复来源时，只允许停新增、移出普通视图，不删除。

**允许开工的范围：默认开关关闭的隔离实现和合成夹具测试。**
**仍不允许的范围：真实存量迁移、接管唯一接续来源、物理删除。** 后三者还要求读侧实现、历史链验收、恢复演练及用户单独授权。

本机独立实测：

- 严格时间戳账本 **687 篇 / 2,095,611 B**；规范化全文匹配 **151**，无匹配 **536**。
- 同名且恢复原 mtime 后更新正文，现行 `handoffMaterialStamp()` 前后均为 `0|handoff-20261110-120000.md`。
- 两进程各执行 25 次锁内读改写，最终计数 **50**；竞争超时为 `state-lock-timeout`；锁内写失败后正文保持失败写入值，证明锁**不提供回滚**。
- `checkpointId:'cp_probe'` 真写入后落盘为 `undefined`；`appendHandoffCheckpointPre` 不透传 `opId`；相同 `opId` 携带不同载荷时会被当作重放，没有比载荷的判据。
- 新目录中的文档不会进入存量扫描，也不会进入团队基线。

## 2. 字段级协议表

### 2.1 文档与操作字段

以下字段均为 **R4 待实现协议**，不是当前代码已有能力。

| 字段 | 语义与来源 | 校验与失败行为 | 机械验收 |
|---|---|---|---|
| `documentId` | 等于 `handoff/documents/<documentId>.md` 的去扩展名 basename。首建由文档存储层根据显式 slug 与首建时间生成；更新只能由调用方提供既有 ID。跨窗口从接续材料、文档清单或用户选择恢复，不得猜最近文档。 | 匹配 `^[a-z0-9][a-z0-9-]{0,63}-[0-9]{6}-[0-9]{4}$`；路径解析后必须仍位于本工作区 `handoff/documents/` 内。非法 ID、绝对路径、`..`、符号链接越界均返回 `document-id-invalid`，事件和文档增量均为 0。 | 真创建后返回值与文件名一致；重启进程按 ID 读到同一文档；同名更新文件数不变；非法 ID、跨目录、越界 symlink 全部拒绝。 |
| `eventIds` | 文档显式关联的事件集合；首建和更新都必须携带。单事件是长度为 1 的数组；多事件是同一维护单元的显式关联，不靠正文关键词猜测。兼容参数 `eventId` 只能归一为单元素数组，与 `eventIds` 同时出现且不一致时拒绝。 | 去空、去重、排序后至少 1 项，每项匹配 `evt_[0-9a-f]{8}` 且真实存在、非 closed。缺 ID 返回 `event-ids-required`；未知/关闭事件返回 `event-id-unavailable`；不得退化为最新 active。 | 无 ID、重复 ID、未知 ID、closed 事件均事件 +0、文档不变；两事件文档必须得到两份独立结果。 |
| `revision` | 文档当前内容身份。先构造完整候选文档，再计算 revision。候选统一 UTF-8、无 BOM、CRLF/CR→LF；仅把元数据行中的 revision 值置空后计算 `SHA-256`，输出 `sha256:<64 hex>`。标题、事件关联、正文、链接及保护区都参与计算。 | 更新必须携带 `expectedRevision`；只有磁盘当前 revision 完全相等才能提交。首建使用显式 create-only，不接受伪造的空 revision。相同内容的重复更新返回 `noop:true`，不新增 WAL。 | 同内容跨进程算出同值；任一字节语义内容变化都变值；错误 expectedRevision 返回 `document-version-conflict`；旧 revision 在新提交后不能再写。 |
| `opId` | 一次文档 upsert 的业务操作身份，由调用方在首次尝试时生成，格式 `r4op_<32 hex>`。同一操作关联的所有事件共享该值；修改意图后重试必须生成新 opId。 | 必须同时绑定 `operationDigest=SHA-256(canonical({schema,documentId,expectedRevision,eventIds,candidateRevision,changeSetDigest}))`。同 opId、同摘要才可重放；同 opId、不同摘要返回 `op-payload-mismatch`。 | 同一操作在两个事件重放，每事件每阶段最多一条检查点；同 opId 改一个字节的意图必须拒绝而非静默去重。 |
| `checkpointId` | 新增的真实持久化字段，格式 `ckpt_<16 hex>`，由事件存储在 append 时生成，事件内唯一并随结果返回。不能用数组下标、时间戳或 `idemKey` 冒充。 | 加入 `lib/event-store.js:976-997` 的持久化白名单和校验；重复 ID 返回 `checkpoint-id-conflict`。旧检查点不原地回填。 | 真 append 后读回同一 ID；列表、详情和恢复 API 均返回该 ID；重复写入由幂等键去重，不能产生第二个 ID。 |
| `legacyCheckpointKey` | 只用于存量审计的确定性身份：`sha256(canonical({eventId,checkpointIndex,at,kind,text,sourceRef,idemKey,quad}))`。它不是新生成的 `checkpointId`。 | 报告必须标 `identityMode:'legacy-derived'`；不得声称旧记录已有持久化 ID。 | 同一快照重复计算相同；任一参与字段变化即变化；事件库重排时报告必须重新审计，不沿用旧结果。 |
| `changeSet` | prepared 的可恢复载荷。按固定文档区域保存 `{regionId,beforeText,afterText}`，覆盖所有发生变化的区域，包括元数据、链接区、删除区和用户区。首建保存完整初始文档；更新不另存整份未变化文档。 | `baseRevision + changeSet` 必须能构造 `candidateRevision`；缺任一变化区域即拒绝进入 Phase 1。不能只存四段摘要。 | 在隔离夹具中，从基线文档重放得到逐字节等价的目标规范化文档；删除一个变化区域后校验必须失败。 |
| `prepared` | Phase 1 持久化「准备执行什么」：文档 ID、基线/目标 revision、事件集合、opId、operationDigest、changeSet、规范四段及当前摘要。 | 任一关联事件没有 prepared，不得开始文档更新。部分事件 prepared 成功时，文档不得写，结果必须逐事件报告。 | 杀死进程后可凭 prepared 重建操作；同 opId/phase 重放不重复；缺恢复材料不能进入文档写。 |
| `committed` | 文档原子写并读回一致后追加的终态记录：目标 revision、preparedCheckpointId、实际写盘结果。committed 仍是 append-only 新检查点。 | 文档已是目标但 committed 写入失败时，返回 `documentCommitted:true,eventComplete:false`，不得回滚正文或重写旧 prepared。 | 成功操作每个关联事件各有一条 committed；其 revision 等于磁盘实际 revision；重放 committed 不新增检查点。 |
### 2.2 WAL 与失败补偿状态机

现有 Phase 1→2→3 位于 `lib/index.js:25138-25197`；旧实现把全文放进检查点，见 `lib/event-write.js:696-750`。R4 改为：

```text
Phase 0  读取并构造候选文档
         校验 documentId/eventIds/expectedRevision/固定结构/保护区
         生成 candidateRevision、opId、operationDigest、完整 changeSet
         可预期失败：返回错误，文档 +0、事件 +0

Phase 1  对 eventIds 逐个追加 prepared
         checkpoint.opId = 业务 opId
         存储层操作键 = opId + ':prepared'
         任一失败：停止，绝不写文档；报告逐事件 prepared 状态

Phase 2  重新取得文档锁
         重读并复核 expectedRevision
         原子写候选文档，读回并复核 candidateRevision
         冲突：返回 conflict；意外异常：进入 Phase 3

Phase 3  文档成功后逐事件追加 committed
         存储层操作键 = opId + ':committed'
         文档意外失败则追加 failed
         存储层操作键 = opId + ':failed'
         failed 引用 preparedCheckpointId，记录实际残留 revision 和错误码
```

同一个业务 `opId` 不能直接作为同一事件多次 append 的存储操作键，否则现有 `eventStorePre.append()` 的重放早退会把 committed 吞掉。源码依据：`lib/event-store.js:915-969`。

现有 `appliedOps` 只存时间戳且容量为 500，见 `lib/event-store.js:370-420`。R4 必须扩展为同时保存 `operationDigest`，并能在台账淘汰后从带 `opId` 的检查点恢复重放证据。旧数字型台账记录遇到新 R4 重放时返回 `op-payload-unverifiable`，不得默认同载荷。

### 2.3 失败矩阵

| 失败点 | 文档 | 事件 | 必须返回/补偿 |
|---|---|---|---|
| 非法 ID、结构错误、可预期 CAS 错误 | 不变 | +0 | 明确错误码；不得先写失败检查点 |
| 第一个事件 prepared 失败 | 不变 | 可能 0 | `aborted-before-document` |
| 多事件 prepared 部分成功 | 不变 | 部分 prepared | 逐事件状态；可凭 changeSet 恢复或放弃 |
| Phase 2 CAS 竞争 | 旧版不变 | prepared 已有 | `document-version-conflict`，不得自动覆盖 |
| 原子写异常 | 旧版或目标版，必须读回判断 | prepared 已有 | failed 记录实际 revision；保留 changeSet |
| committed 部分失败 | 目标版已存在 | 部分 committed | `documentCommitted:true,eventComplete:false` |
| 索引更新失败 | 已成功正文不回滚 | committed 不变 | `indexStale:true`；索引按当前正文重建 |
| 本进程缓存刷新失败 | 正文不变 | committed 不变 | 明确 stale；下一读侧刷新按 revision 读盘 |
| 进程被杀 | 由原子写决定旧/新，不得出现半文件 | 可只剩 prepared | 启动时按 opId 对账，缺终态且磁盘为目标时补 committed |

## 3. handoffMaterialStamp 改造方案与负路径断言

### 3.1 新指纹定义

现行实现只拼接 PLAN mtime、最新旧账本名和事件计数，见 `lib/index.js:7950-7970`；`latestLedgerNamePre` 只识别旧文件名，见 `lib/index.js:20709-20719`。

R4 使用结构化指纹再求 SHA-256：

```json
{
  "schema": "r4-material-stamp-v2",
  "plan": {"present": true, "revision": "sha256:..."},
  "legacyLatest": {"name": "handoff-....md", "revision": "sha256:..."},
  "documents": [
    {"documentId": "construction-plan-261110-1223", "revision": "sha256:..."}
  ],
  "events": {
    "digest": "sha256(canonical event identity/state projection)"
  },
  "readErrors": []
}
```

规则：

- `documents` 对 `handoff/documents/` 中全部合法文档按 `documentId` 排序，逐份从**正文真源**计算 revision；不能只读一个可能陈旧的 manifest。
- 旧账本与新文档并存时，两类来源都参与，不能因存在新文档就丢掉旧账本维度。
- 事件投影至少包含每个事件的 `id/name/summary/status/sections/updatedAt/checkpointCount/outcome`，防止同毫秒 set 且检查点数不变时漏检。
- 缺失、空目录和读取失败是三种不同状态；读取失败必须进入 `readErrors`，不得静默退回一个看似稳定的旧指纹。
- 返回值仍可为字符串，保持现有调用方接口；格式变更只影响一次新基线，不得要求跨版本比较旧字符串。

### 3.2 三个调用点的语义

| 调用点 | 语义 | 改造要求 |
|---|---|---|
| `lib/index.js:8034` | 每次接续尝试前记录 before | 必须按被接续会话解析路径；不得读当前引擎另一工作区 |
| `lib/index.js:8068` | 读不到会话事件尾时的材料变化兜底 | 同名内容更新也必须使 `cur!==before` |
| `lib/index.js:8078` | turn completed 后验证是否真有材料变化 | 不能只凭 turn 结束报成功；新文档正文变化必须通过 |

`_snapFp/_snapLogFp` 不是这一问题的替代品；当前 `_snapLogFp` 只取日志段，见 `lib/index.js:23716-23720`。

### 3.3 实现后的必过断言

| 编号 | 操作 | 断言 |
|---|---|---|
| F-1 | 同一 documentId、同 mtime，正文 A→B | `after!==before` |
| F-2 | 不修改任何内容再读一次 | `after===before` |
| F-3 | 只更新文档的 `updatedAt` 元数据 | revision 与 stamp 均变化 |
| F-4 | 新增、删除、重命名新文档 | stamp 均变化 |
| F-5 | 旧账本和新文档并存，只改旧账本 | stamp 变化 |
| F-6 | A 工作区文档改变，B 不变 | `stamp(A)` 变化、`stamp(B)` 不变 |
| F-7 | 文档读取从成功变成 EACCES/损坏 | stamp 含错误变化，不得静默等于旧值 |
| F-8 | 在隔离副本中移除文档 revision 维度 | F-1/F-5 必须变红；恢复后复绿 |

现行实现的负对照已实测：同名、同 mtime 更新后 `unchanged:true`，见 `artifacts/_protocol-r4-20261110/data/fingerprint.json`。

## 4. 跨进程锁粒度与测试设计

### 4.1 真实作用域

`lib/shared-state-lock.js` 全文结论：

- 锁以规范化后的资源路径为键；锁文件为 `<canonical>.lock`，获取门为 `<canonical>.lock.acquire`，见 `:90-95`。
- `openSync(...,'wx')` 提供同一路径的互斥，见 `:85-89`。
- 可跨同机进程；同一规范化路径跨工作区也会互斥；**不是全局锁，也不保证网络文件系统或跨主机互斥**。
- 死主回收仅对同 hostname、正整数 PID 且 `process.kill(pid,0)` 报 ESRCH 的记录生效，见 `:23-35`。
- 损坏获取门默认有 30 秒宽限，见 `:38-83`；实测新鲜损坏门不回收，超过宽限才回收。
- 超时抛 `state-lock-timeout`，见 `:123-129`；`withSharedStateLock` 只在 finally 中释放锁，见 `:134-137`，不会撤销 job 已产生的写入。
- 同步版与异步版使用同一锁文件协议，见 `:139-214`。不得把 async 锁插进依赖同步起手的既有队列。

### 4.2 R4 资源与锁名

| 资源 | 锁粒度 | 必须覆盖的临界区 |
|---|---|---|
| 单个维护文档 | `withSharedStateLock(documentPath)`，形成 `.md.lock` | 读当前版→结构/CAS 校验→原子写→读回 |
| 共享 `handoff/index.json` | `withSharedStateLock(indexPath)`，形成 `index.json.lock` | 读最新索引→合并全部条目→原子写→读回 |
| `event-store.json` | 保留现有 `acquireSharedStateLock(storePath+'.lock')`，形成 `.json.lock.lock` | 沿用 `event-store.js:504-510`，不另造不同名锁 |
| 会话内状态与 UI | 不伪装成跨进程文件锁 | 以 committed revision 为失效信号，必要时重新读盘 |

注意：既有 MemoryDocumentStore 传入的是 `filePath+'.lock'`，见 `lib/memory-writer.js:503-521`。新文档若需与该写入器互斥，必须使用完全相同的最终锁路径，不能一个传文档路径、另一个传 `.lock` 后还假定二者互斥。

### 4.3 锁顺序与死锁规避

**R4 默认禁止同时持有文档锁、索引锁和事件锁。**

逻辑顺序为：

```text
D-read/prepare → 释放 D
E-prepared     → 释放 E
D-CAS/write    → 释放 D
E-committed    → 释放 E
I-reindex      → 释放 I
C-invalidate
```

理由：事件 append 内部会自行取锁；外部再持事件锁包裹 append 会形成自等。文档更新与多事件 prepared 本来就不是一个可原子覆盖的临界区，应通过 WAL 和 CAS 表达，而非制造跨资源大锁。

一次 `opId` 只允许更新一个文档；多文档操作拆成多个业务操作，避免多文档锁顺序问题。

### 4.4 失败回滚边界

- 锁获取失败：不执行写入，返回 `lock-unavailable`。
- 文档写失败：临时文件清理；不得靠 unlink 目标文件实现所谓原子回滚。
- 索引写失败：正文是赢家，索引标 stale 并可重建；不回滚正文。
- committed 写失败：正文是赢家，保留 prepared；不得修改 append-only 历史。
- `catch` 不得吞掉原异常后返回成功；所有部分成功必须逐资源列出状态。

### 4.5 跨进程负路径测试

实现后使用两个真实 Node 子进程，夹具只放工作区内，不使用 `os.tmpdir()`：

| 用例 | 断言 |
|---|---|
| 两进程同文档、同 expectedRevision 更新 | 至多一个提交成功，另一个为 conflict；最终 revision 属于赢家，无静默覆盖 |
| 两进程分别更新不同文档并更新共享索引 | 两文档均成功；索引同时含两组条目，不能后写抹掉先写 |
| 两进程对同一事件库 append | 检查点总数精确等于成功 append 数，无丢写 |
| 一事件 prepared 成功、另一事件失败 | 文档不变；结果逐事件可见；重放不重复 |
| 持锁期间 kill 子进程 | 新进程最终按死主协议恢复，不出现半截文档；有界等待 |
| 活主持锁 | 竞争者超时且文档不变 |
| 索引写故障注入 | 正文保留、`indexStale:true`、重建后索引与正文一致 |
| 隔离变异：去掉共享索引锁 | 并发丢条目用例必须能区分实现，不得恒绿 |

## 6. 历史查询链

### 6.1 当前能回答什么

当前存在三条可用但有限的通道：

1. `memory_recall(scope=events)` 通过 `textOfEventPre` 检索 name/summary/sections/checkpoint.text，见 `lib/event-recall.js:45-61`。
2. `memory_recall(scope=all)` 检索本地日志，但默认只取最近 40 份，并明确提示窗口限制，见 `lib/index.js:14168-14177`；其他工作区每区只扫 15 份日志，见 `:14483-14495`。
3. `expandEventRecordPre` 只展开最近 5 条检查点，见 `lib/index.js:14707-14712`。

因此现行可以回答部分历史，但**没有完整的「指定时间区间 + 指定事件 + 全部检查点」查询协议**。不能把窗口内未命中写成「当时什么都没做」。

### 6.2 R4 后的权威回答链

「上周我做了什么」按以下顺序回答：

```text
解析为明确的本地时间区间 [from,to)
        ↓
事件检查点时间线：eventId / at / kind / 四段 / checkpointId / opId
        ↓
按日读取日志与 archive 冷存储，补充事件之外的证据
        ↓
必要时查询历史 DSH 会话
        ↓
汇总完成事项、失败、当前后续，并列出来源与覆盖缺口
```

维护文档只回答「现在是什么状态」，不是历史来源。

### 6.3 必须新增的只读查询契约

在事件检索通道增加结构化过滤参数，而不是让模型反复猜关键词：

| 参数 | 规则 |
|---|---|
| `from` / `to` | 显式日期或带时区的 ISO 时间；`from` 含、`to` 不含 |
| `eventId` | 可选；给出时必须精确匹配 |
| `kinds` | 可选检查点类型过滤 |
| `cursor` / `limit` | 分页；不得用最近 5 条截断冒充完整时间线 |
| `includeQuad` | 返回持久化四段，不使用渲染截断文本 |

输出至少含 `eventId/checkpointId/at/kind/text/goal/state/dead/next/sourceRef/opId`，并附 `range/coveredSources/readErrors/truncated/nextCursor`。

新增工具参数或 action 后必须先重启宿主再真机验证，避免旧 enum 静默降级。

### 6.4 机械验收

| 编号 | 夹具 | 断言 |
|---|---|---|
| H-1 | 事件内有周初、周中、周末三条检查点 | 指定上周区间返回三条且按 at 正序 |
| H-2 | 区间前后各有边界检查点 | 只返回 `[from,to)` 内记录 |
| H-3 | 当前维护文档含新词，但无对应检查点 | 历史查询不得把当前态冒充上周事实 |
| H-4 | 区间超过 5 条检查点 | 分页后全集完整，不受现有最近 5 条限制 |
| H-5 | 检查点全文改为摘要/指针 | 仍能返回该次写入的四段、目标 revision 和恢复指针 |
| H-6 | 事件库损坏或读取失败 | 返回 `readErrors`，不得返回「无记录」 |
| H-7 | 所有账本文件从夹具移除 | H-1 仍通过，证明不依赖账本历史文件 |
| H-8 | 固定本地时钟和时区 | 日期边界三次运行结果一致 |

| 判据 | 实现 | fail-closed 条件 |

## 8. 物理删除前置条件

### 8.1 恢复来源是什么

分两层，不得混用：

1. **历史内容证据**：事件检查点可以证明某些历史正文存在；规范化全文匹配不等于原始字节备份。
2. **物理删除恢复来源**：独立于待删目录的受控备份，含原文件字节、相对路径、SHA-256 manifest、生成时间、恢复工具和恢复演练报告。

当前团队基线上传也不包含维护文档，见 `lib/index.js:11358-11378`，不能把它当作现成备份。

### 8.2 恢复演练

在任何真实删除前，在隔离目录执行：

1. 从备份恢复一篇候选旧账本，断言恢复文件 `Buffer.equals()` 原备份，SHA-256 一致。
2. 对一个最小批次全部恢复，断言文件数、每篇 SHA、相对路径完全一致。
3. 重启读取方，验证旧账本检索、面板、跨工作区接续重新可见。
4. 删除/重建派生索引，断言索引可由 Markdown 真源重建，事件检查点总数不变。
5. 注入损坏备份、缺文件、部分恢复、进程中断，断言均 fail-closed，不得把半次恢复报为成功。
6. 再执行一次恢复，证明操作幂等，不生成 `-b/-c` 伪身份。

恢复演练失败即停止整个删除批次，不得只删掉已恢复的一篇后继续。

### 8.3 给用户的明确选择题

**A（推荐，环境不允许额外副本时唯一可选）：保留原件。**

- 停止新增旧格式快照；
- 从普通维护视图和默认 RAG 中移出；
- 保留按路径读取与专门历史查询；
- 不做任何物理删除。

**B：另行授权最小批次物理删除。**

仅当同时满足才可选择：

- 用户看到具体文件清单、字节数和 coverageReport 摘要；
- 每条五判据通过；
- 独立备份存在且 SHA 清单吻合；
- 隔离恢复演练通过；
- 用户为该批次给出明确授权。

**未选择视为 A；不得默认执行 B。**

### 8.4 「不归档」与「禁止自动删除」的边界

- R4-3「旧版不归档」约束的是**新维护文档的正常就地更新**：成功 committed 后不创建历史 Markdown 副本。
- 「禁止自动删除」约束的是**存量旧账本清理**：任何不确定项都保留。
- 新文档正常更新不需要生成永久归档；存量物理删除永远是独立、显式、可恢复的批次。
- 普通 R4 写入器不得携带删除能力；删除工具若未来存在，必须要求备份 ID、报告摘要、候选 SHA 清单和用户授权令牌四者同源。

### 9.4 隔离实现要求

- 使用合成文档、合成事件和合成会话；不复制真实记忆正文进测试夹具。
- 根目录固定为 `artifacts` 或未来测试专用工作区目录下的绝对路径；不使用 `os.tmpdir()`。
- 每个测试使用独立目录；清理只删除本测试创建的目录。
- 变异实现必须位于隔离副本，不得在共享 `lib/` 上就地改后还原。
- 新模块验收必须真 import→真构造→真调用→断言返回/副作用；源码含字符串只能作守卫。
- 子进程输出管道采用测试环境允许的方式；探针自身失败不得归因为产品锁失败。
- 新字段/新枚举/新 action 需重启宿主后再做真机验证。
- 本任务没有运行全仓回归，未来实现批次必须按影响套件与里程碑要求另行执行。
