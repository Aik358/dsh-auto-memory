## §0 一句话任务

**用可复现的方法，测出「哪种提示词 / 哪种工具反馈」能让模型写出最合规的记忆数据 —— 然后把最优配置写成实验报告。**

---

## §1 为什么做这个实验（背景，必须先读）

### 1.1 已发生的三件事

**① 一个真实缺陷暴露了「提示词 vs 工具」的分工问题**

用户实报：白板检查点全渲染成空白行。根因是 `appendHandoffCheckpointPre` 解析出四段（goal/state/dead/next）却只构造 5 个字段，四段全丢。已修。

**② 一份设计方案给出量化结论**（`docs/internal/DESIGN-MEMORY-TOOL-CONTRACT-20261029.md`）

- 固定成本合计 **47,778 字符/每次请求**（注入面 23,562 + 工具 description 8,035 + schema 12,869 + GUIDANCE 3,312）
- 12 条核心规则中 **10 条在 ≥2 个提示面重复**，「四段必填」在 5 个面出现 **39 次**
- 建议：把指导从提示词搬到**工具回执**，净减 1,498 字符

**③ 我已做过一次小规模控制变量实验（4 臂），结果推翻了上面第 ② 条的乐观假设**

```
臂 | 提示强度                        | H1四段标题 | hardPass
---|--------------------------------|-----------|---------
A  | 完整 7 条硬性要求（现状）        |    PASS   | PASS
B  | 只说「需要包含四段」             |    FAIL   | FAIL
C  | 只说「结构化」                  |    FAIL   | FAIL
D  | 完全不提格式                    |    FAIL   | FAIL
```

**关键发现**：删到只剩「需要包含四段」这句，就 **0% 通过**。不是降 5 个百分点，是**从 100% 掉到 0%**。

**失败原因高度一致**：B/C/D 三臂**全都在标题上加了 `（type:xxx）` 后缀**，例如：

```
模型写的：  ## 任务状态（type:state）
判据门要求：## 任务状态
```

为什么？因为这个仓库的真实约定里**到处都是 `type:goal` / `type:state` 这种 tag**，模型看见了就往标题上贴。

### 1.2 所以真正要回答的问题

```
Q1  提示词里哪些内容是「不可删的最小集」？（删了就 0% 通过）
Q2  工具 description / schema 加内容，会提升还是降低合规率？
Q3  工具回执里加建议，能替代提示词里的说明吗？
Q4  human_slim / run_slim 两个档位的提示词，哪个版本效果更好？
```

## §2 实验必须知道的机器事实（避免踩坑）

### 2.1 被测系统的结构

```
模型（被测）
  ↓ 看到
  ├─ 注入的提示词  ← renderMemoryDynamic() 产出，按 INJECT_TIERS 分档
  │                   档位：human_full / human_slim / run_full / run_slim /
  │                        post_compact / handoff_carry / hang_compensate / legacy
  ├─ 工具 description + schema  ← lib/index.js 里 21 个工具的注册定义
  ↓ 调用
  └─ memory_* / calendar_* 工具
       ↓ 返回回执
       └─ 回执文本（当前：只报成功，零指导）
```

### 2.2 三个关键事实

**事实 1：提示词可以「只换文字、不改代码」**

存在 `promptLayerOverrides` 机制（`lib/index.js` L1096 / L1386 `DEFAULT_PROMPT_LAYERS`）：

```js
promptLayerOverrides: {},   // key=层名, value=覆盖文本
// 空字符串覆盖 = 使用默认（想恢复默认就把该层设为 空串）
```

⇒ **实验可以用它做变量，不必改代码、不必重编译。**

**事实 2：判据门是纯函数，可离线评判**

```js
import { checkHandoffCriteriaPre } from 'lib/wb-contract.js'
const r = checkHandoffCriteriaPre(账本文本)
// r.hardPass  = H1-H4 是否全过
// r.hard[]    = 逐条判据（H1 四段标题逐字 / H2 段≥20字符 / H3 无占位 / H4 ≤8000）
// r.soft[]    = S1-S4（各段≤5行 / 有「方案→失败原因」箭头 / 下一步可执行 / 无临时信息）
```

⇒ **不用真的落盘就能评判**（这很关键，见事实 3）。

**事实 3：真调工具会污染真实记忆库 —— 必须避开**

```
resolvePaths 按 cwd 派生工作区目录，DSH_HOME 与配置都拦不住。
当前真实库：1210 个工作区 / 696 篇账本 / 553 个检查点。
⇒ 实验若真调 memory_note，会在 ~/.dsh/memory/workspaces/ 下新建脏工作区。
```

**⇒ 强制纪律：实验只让模型「输出账本文本」，由脚本离线评判，不落盘。**

## §3 实验总体设计（四个子实验，按依赖顺序）

```
子实验 1  控制变量：工具 description / 回执 的增量效果
          自变量 = 工具描述长度 / 回执内容
          因变量 = 模型调用行为 + 输出合规性
              ↓
子实验 2  提示词注入：human_slim / run_slim 各版本对比
          自变量 = 提示词版本（现款 vs 目标款 vs 中间态）
          因变量 = 合规率 + 字符成本
              ↓
子实验 3  迭代收敛：根据 1/2 的结果，迭代出最优提示词
          产出 = 最终选定的提示词 + 实验报告
              ↓
子实验 4  接续前刷新仪式提示词（§13，优先级最高）
          自变量 = 仪式提示词的 4 个版本（含已发现的死锁修复）
          因变量 = 完成率 / 死锁触发率 / 事件归属正确率 / 耗时
          ★ 与前三个不同：这个必须真调工具，不能只离线评判
```

**★ 执行层（§14，决定上面四个怎么跑）**：

```
外部 harness（zcode / workbuddy / 终端）
  ↓ spawn
dsh --profile <memexp> --json "<任务>"   ← 插件真加载，memory_* 工具真存在
  ↓ NDJSON
离线评判（checkHandoffCriteriaPre）+ 汇总
```

> **不能用 DSH 内部子代理做 —— 会被宿主注入污染（§14.1）。**

## §4 子实验 1 · 控制变量（工具侧）

### 4.1 设计

**目的**：回答 Q2 / Q3 —— 工具描述加内容、工具回执加建议，各自的效果。

**方法**：**同一个任务 + 同一模型 + 只有工具描述/回执不同**。

```
组别   工具 description          工具回执              预期观察
----  -------------------------  -------------------  ------------------
D0    现状（原样）                现状（只报成功）      基线
D1    现状 + 补充四段格式说明      现状                合规率是否上升
D2    现状                        现状 + 拒绝时给骨架   合规率是否上升（靠拒绝教学）
D3    现状 + 补充                  现状 + 给骨架        两者叠加
```

### 4.2 关键约束（必须遵守，否则实验无效）

**① 不能让真模型真的调用 `memory_note`**

因为会写真实记忆库。做法：**用一个桩（stub）伪装成 memory_note 的返回**。

```js
// 实验脚手架伪代码（不需要改产品代码）
const stubReceipts = {
  D0: '交接账本已写入: <path>',                       // 现状回执
  D2: '判据门拦截：缺少 ## 目标。请按以下骨架补齐：...',  // 拒绝 + 骨架
};
```

**② 工具 description 的变量怎么注入？**

两种做法，按可执行性选：

```
做法 A（推荐，零侵入）：把工具描述当作【提示词的一部分】直接拼进被测模型的 prompt
   —— 因为模型看到的确实就是这段文字，只是它来自 schema 而非注入面。
   ⇒ 用 subagent 时，把 description 文本写进它的初始 prompt 即可。

做法 B（更真但更重）：真改 lib/index.js 的工具定义 + 重启 DSH
   —— 只有做法 A 无法回答某问题时才用。需要用户批准。
```

### 4.3 判定指标（必须全部可复算）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **合规率** | `checkHandoffCriteriaPre(txt).hardPass === true` 的比例 | 生产判据函数，非自评 |
| **H1 通过率** | 四段标题逐字匹配 | 同上 `r.hard` 中 H1 |
| **S2/S3 通过率** | 软判据 | 同上 `r.soft` |
| **格式污染率** | 标题带 `（type:xxx）` 等后缀的比例 | 正则 `^##\s*.+?[（(]` |
| **字符成本** | 提示词 + 工具描述的字符数 | `length` |
| **调用正确率** | 是否调对了工具（该用 memory_note 却用 memory_log 等） | 人工/脚本判 |

**样本量**：每组 ≥ 5 个不同任务（不能同一个任务跑 5 次，会因记忆而趋同）。

## §5 子实验 2 · 提示词注入（human_slim / run_slim 对比）

### 5.1 为什么要专门测这两个档位

`INJECT_TIERS` 有 8 个档位，其中：

```
human_full   用户说话 → 完整注入
human_slim   用户说话 → 精简注入   ← 高频，最值得优化
run_full     运行中   → 完整
run_slim     运行中   → 最克制     ← 最高频，最值得优化
```

**这两个档位占实际注入的绝大多数轮次**，但目前的精简版内容是「从完整版删减」得来的，**从未独立验证过效果**。

### 5.2 设计：现款 vs 目标款

**先取现款原文**（实验执行者必须自己取，不能凭本文档转述）：

```bash
cd /d/dsh-auto-memory
node -e "import('./lib/index.js').then(m=>{const L=m.DEFAULT_PROMPT_LAYERS;console.log(L.snapshotSlimMaintain);console.log('====');console.log(L.snapshotSlimGuide)})"
```

**变量设计**：

| 版本 | 内容 | 字符数 |
|---|---|---|
| **V0 现款** | 原样 | 实测 |
| **V1 目标款** | 只保留「不可删最小集」（见 §6.1 的方法测出） | 实测 |
| **V2 加回执指引** | V1 + 「详细要求见工具回执」 | 实测 |
| **V3 极简** | 一句话：「记忆用 memory_* 工具，格式见 schema」 | 实测 |

### 5.3 真实语料（关键：不能用人造任务）

**必须用真实历史任务**，否则测不出真实分布。语料来源：

```
1. 真实账本 696 篇  → 每个任务描述可反推出「当时在做什么」
   位置：~/.dsh/memory/workspaces/*/handoff/handoff-YYYYMMDD-*.md
2. 真实事件 53 个 + 553 个检查点
   位置：~/.dsh/memory/workspaces/*/handoff/event-store.json
3. 真实日志
   位置：各工作区 .dsh-memory/
```

**采样要求**：
- 从**运行时自发**的 17 个事件 / 412 个检查点里抽（**不要用迁移产出的 36 个**，那些是 `memory_upgrade` 子代理按提示词强制生成的，不代表模型日常行为）
- 覆盖不同类型：缺陷修复 / 新功能 / 调研 / 发布
- 每类 ≥ 3 个

## §6 子实验 3 · 迭代收敛

### 6.1 第一轮：找出「不可删最小集」

**方法：逐条删除法（ablation）**

```
起点 = 完整提示词（已知 100% 通过）
步骤：
  1. 每次只删一条规则
  2. 跑 5 个样本
  3. 若合规率下降 → 该条【不可删】，加回
  4. 若合规率不变 → 尝试永久删除
  5. 重复直到没有可删项
```

**必须逐条测的候选删除项**（来自设计方案 §5.1 的可删清单）：

| # | 候选删除项 | 现状字符 | 我的预判（待实验推翻） |
|---|---|---|---|
| D1 | 「四段重写纪律」 | 258 | **不可删**（小实验已证：删了 0% 通过） |
| D2 | 「检查点必带溯源」 | 114 | 可删？实测仅 10/412 有溯源 ⇒ 说了也没用 |
| D3 | 「感知填写时机」 | 317 | 可删？79% 感知来自 handoff 路径 |
| D4 | 「name/summary 维护时机」 | 216 | 可删（close 时可代码检查） |
| D5 | 「白板纪律」 | 812 | 部分可删（保留「不要手写」一句） |
| D6 | 「事件记忆（v4）」 | 239 | 可删（schema 已表达） |

**特别注意 `type:xxx` 污染**：

小实验发现 B/C/D 三臂**全部**在标题后加了 `（type:state）` 后缀。请专门测：

```
对比  提示词中明确写「标题后不要加任何后缀」 vs 不写
观察  格式污染率变化
```

这可能是一个**独立于提示词长度的、成本极低收益极高**的改动。

### 6.2 第二轮：工具回执能否替代提示词

**核心问题**：如果工具回执足够好，提示词能删到多短？

```
组别  提示词        工具回执                    预期
----  ------------  --------------------------  ------------------
R0    V1（最短）     无                         基线
R1    V1            拒绝时给骨架模板            合规率上升？
R2    V1            拒绝时给骨架 + 对比实际值     合规率大幅上升？
R3    极简 V3       拒绝时给骨架 + 对比实际值     极限测试
```

**R2 是重点**：当前判据门的拒绝文案只列**期望值**（「缺少或标题不逐字匹配的四段标题：任务状态」），不列**实际值**。小实验里 B 臂被拒时的原文就是这个 —— 模型看到「缺少任务状态」，但它明明写了 `## 任务状态（type:state）`，**不知道自己错在哪**。

⇒ 假设：**「对比实际 vs 期望」能让模型 1 次就改对，从而允许提示词大幅精简。** 这是本实验最有价值的假设。

### 6.3 收敛判据

```
停止迭代的条件（满足任一）：
  1 连续 2 轮迭代，合规率提升 < 2 个百分点
  2 已无单条可删项（ablation 全部尝试完）
  3 达到目标：合规率 ≥ 95% 且 提示词字符数 < 现款的 50%
```

## §7 实验执行方式（⚠️ 已被 §14 取代，保留作历史对照）

### 7.1 零成本方案：用子代理当被测模型

> ⚠️ **本方案已作废 —— 存在观察者污染（子代理本身就跑在被注入记忆提示词的环境里）。**
> **请直接看 §14 的外部驱动方案。** 下面内容保留，仅供对照。

**这是本机唯一可行且无 API 成本的方式。**

```
每个实验组 = 起 N 个 subagent
  每个 subagent 的 prompt = 【实验提示词（变量）】+【任务描述】+【输出格式要求】
  subagent 只输出文本，不调用工具
  → Lead/脚本用 checkHandoffCriteriaPre 离线评判
```

**优点**：零 API 成本、可重复、天然隔离（子代理不知道实验设计）、可并行。

**缺点（必须写进报告）**：子代理与真实宿主模型不完全等同（上下文构造方式不同）。**结论的适用范围要如实标注。**

### 7.2 若要更真：用真实任务回放

```
从真实账本反推 20 个任务描述 → 每个任务起一个子代理真做（限只读任务）
  → 让它自然产出账本 → 离线评判
代价：慢（每个任务需真执行），但最接近生产。
建议：只在最终验收时用这条路，迭代阶段用 7.1。
```

## §9 纪律要求（本仓硬规约，违反会被打回）

### 9.1 数据纪律

| # | 要求 |
|---|---|
| 1 | **禁止自评冒充判据** —— 合规率必须用生产函数 `checkHandoffCriteriaPre` 算，不许人工目测 |
| 2 | **每条结论给可复算物理量** —— 字符数 / 百分比 / PASS 数，不接受「效果更好」 |
| 3 | **样本量必须披露** —— 每组 N，以及置信区间（若 N<10 要标注） |
| 4 | **区分「迁移产出」与「运行时自发」** —— 迁移数据是被提示词强制生成的，会污染统计 |
| 5 | **不要用「源码含某字符串」当验收** |

### 9.2 安全纪律

| # | 要求 |
|---|---|
| 1 | **实验绝不真调 memory_note / memory_event / memory_log** —— 会污染真实记忆库（1210 工作区 / 696 账本） |
| 2 | 若必须真调，**先起独立 cwd + 事后核对工作区清单，只删本次新增且名字含特定前缀的目录**，并在报告里声明残留 = 0 |
| 3 | **不改 lib/ 下任何产品代码**（本阶段只做实验、出报告） |
| 4 | 不提交、不改版本号、不发布 |

### 9.3 实验有效性纪律

| # | 要求 |
|---|---|
| 1 | **控制变量要真的控制** —— 同一任务、同一模型、只有自变量不同 |
| 2 | **每组 ≥ 5 个不同任务**（同一任务重复跑会趋同） |
| 3 | **必须做负路径** —— 证明「不这么做会错」，例如：还原被删的规则 ⇒ 合规率必须回升 |
| 4 | **报告必须如实写「没验证的部分」** |

## §10 我已知的风险（执行者必须复核）

| # | 风险 | 说明 |
|---|---|---|
| **R1** | **子代理 ≠ 真实宿主模型** | 子代理的 system prompt 是宿主另建的，与真实 DSH 会话的注入面不同。**结论只能在「子代理环境」内成立，向真实生产外推需谨慎标注** |
| **R2** | 小实验样本量只有 4 臂 × 1 任务 | 我那个 4 臂实验 **N=4**，不足以支撑强结论。**必须重做并加大样本** |
| **R3** | `type:xxx` 污染可能是「子代理特有」 | 因为我给子代理的任务描述里提到了 `type:goal` 等词。真实场景是否也会污染，需单独验证 |

| **R6** | **在 DSH 内部起子代理做实验 = 观察者污染** | 子代理本身受宿主注入影响 ⇒ 自变量被污染。**已改为外部驱动（§14）** |

## §13 子实验 4 · 接续前刷新仪式提示词（**新增，优先级最高**）

### 13.1 为什么这个必须单独测

「接续前刷新仪式」是 `lib/index.js:7103 refreshRitualPrompt()` 返回的一段提示词，在**每次会话接续前**发给旧 Agent，让它刷白板 + 写账本，然后新会话拿这些材料接续。

**它是本插件里唯一「一次性让模型连做 3-5 个记忆操作」的提示词**，所以：

```
① 它同时承担：事件归属 + 白板重写 + 账本撰写 三件事
② 它有时间预算：默认 120 秒（client.js fAutoContinueRefreshTimeout）
③ 它决定新会话能不能「认领同一件事」→ 直接决定事件是否会被重复创建
```

**而且它已经暴露了真实缺陷。** 下面是本次会话实际收到该提示词后，逐条核出的 6 处：

### 13.2 已确认的 6 处缺陷（实测，非推测）

| # | 缺陷 | 证据 | 严重度 |
|---|---|---|---|
| **F1** | **顺序死锁**：第 0 步说「查不到事件就在**第 2 步之后**补 create，并把新 eventId 写进账本」；但第 2 步要求「账本首行必须写 eventId=<第 0 步拿到的 id>」⇒ 查不到时第 0 步拿不到 id，账本无从写，而 create 却被排在账本**之后** | `lib/index.js:7111` vs `:7113` 原文对读 | **P0 · 逻辑不可执行** |
| **F2** | **与末句自相矛盾**：末句「完成后只回复一句已刷新，**不要再调用其他工具**」，但 F1 要求在账本之后补一次 create = 额外工具调用 | `:7114` vs `:7111` | **P0** |
| **F3** | **revision 字段歧义**：第 1 步要求 `expectedRevision=所读revision`，但 `memory_read(kind=plan)` 实际返回 **19,324 字符 / 含多个 revision 字段**（实测：plan 本体 + 每张卡片各有 revision）⇒ 模型不知道该填哪个 | 实测 `memory_read(kind=plan)` 返回含 3+ 个 `revision` 键 | **P1** |
| **F4** | **第 0 步无法唯一命中**：实测 `memory_recall(scope=events, query=...)` 返回 **6/11 个事件命中**，其中 2 个已是 [完成] 状态；提示词**没有任何判据**告诉模型该选哪个 ⇒ 选错就把账本挂到错误事件 | 实测（本次会话第 0 步） | **P1 · 污染数据** |
| **F5** | **超时预算不足**：正常路径最少 4 次工具调用（recall / read plan / note plan / note handoff），查不到事件 +1 = 5 次；默认超时 120 秒。在 PLAN 长 + event-store 1.5 MB 的大工作区极易超时 | `client.js:343 fAutoContinueRefreshTimeout` 默认 120s | **P1** |
| **F6** | **plan 重写易冲突**：第 1 步带 `expectedRevision`，期间若 PLAN 被改 ⇒ `plan-version-conflict` ⇒ 白板刷新失败（历史已出现该失败记录） | event-store 中存在 `plan-write-failed` 检查点 | **P2** |

### 13.3 实验设计

**自变量**：仪式提示词的 4 个版本

| 版本 | 关键改动 |
|---|---|
| **R0 现款** | 原样（`lib/index.js:7110-7114`） |
| **R1 修死锁** | 把 create 挪到第 2 步**之前**；或明确「查不到 ⇒ 直接建新事件，其 id 用于账本」 |
| **R2 R1 + 给判据** | 追加「选事件判据」：优先选 `status=active` 且 `updatedAt` 最近的；若有多个候选，逐一列出让模型选 |
| **R3 R2 + 给字段** | 明确 `expectedRevision` 取**哪一个** revision（建议：只取 PLAN 本体那一层，并给出截取示例） |

**因变量（全部可复算）**：

| 指标 | 定义 |
|---|---|
| **完成率** | 4 步全做完的比例（recall 成功 / PLAN 刷成功 / 账本写入成功 / eventId 写入正确） |
| **死锁触发率** | 因 F1 导致「账本无 eventId 或 create 排在账本后」的比例 |
| **事件归属正确率** | 账本里写的 eventId 与「真实对应事件」一致的比例（需人工标注 ground truth） |
| **耗时** | 从收到仪式到回「已刷新」的墙钟秒数（对照 120s 超时） |
| **白板冲突率** | 出现 `plan-version-conflict` 的比例 |
| **新会话认领成功率** | **关键终局指标**：新会话第一次 `memory_event(append)` 是否带上了旧 eventId |

### 13.4 测试方法（注意：这个不能只用离线评判）

前三个子实验可以「只让模型输出文本」，但仪式提示词**必须真调工具**才能测，因为它测的就是「多步工具编排」。

**安全做法：隔离工作区**

```bash
# 1. 记录基线
ls ~/.dsh/memory/workspaces/ > artifacts/_exp-ritual/before.txt

# 2. 在专用 cwd 下跑（resolvePaths 会派生出新工作区）
mkdir -p artifacts/_exp-ritual/ws-r0 && cd artifacts/_exp-ritual/ws-r0

# 3. 起子代理，把仪式提示词原文发给它，让它真执行

# 4. 事后核对，只删本次新增且含 exp-ritual 的目录
ls ~/.dsh/memory/workspaces/ > artifacts/_exp-ritual/after.txt
diff before.txt after.txt   # 只允许出现预期的新目录
```

**验收纪律**：报告里必须声明「实验工作区残留 = 0」。

### 13.5 我建议的修法（供实验验证，不是结论）

```
现款（死锁）：
  0. recall 查事件 → 有则记 eventId；无则【第2步之后】create
  1. read plan → note plan
  2. note handoff（首行写 eventId）
  3. 只回复已刷新

建议（无死锁）：
  0. recall(scope=events) 查事件
     ├─ 命中 1 个 active  → 用它，继续第 1 步
     ├─ 命中多个         → 只列出「id + name + 状态 + 最后更新」，问用户或选 updatedAt 最新的
     └─ 一个都没有       → 先 memory_event(create)，拿到 id，再继续
  1. read plan（记下 PLAN 本体那一个 revision）→ note plan
  2. note handoff（首行 eventId=<上面确定的 id>）
  3. 只回复已刷新

★ 关键变化：create 从「账本之后」挪到「第 2 步之前」，死锁消失；
  且第 0 步变成「三路分支」，每路都保证有 eventId 可用。
```

### 13.6 优先级

**这是本实验计划里优先级最高的一项**，因为：

```
① F1/F2 是【逻辑不可执行】，不是效果好坏 —— 现行提示词在「查不到事件」这条路径上是坏的
② 它导致的是【数据污染】（账本挂错事件），比「格式不合规」严重
③ 它的修复成本极低（改 5 行字符串），收益确定
④ 它不需要等实验结论 —— 但修复后【必须】实验验证新版本确实更好
```

**建议顺序**：先做 13.4 的基线测试（R0），确认 F1 能被复现；再测 R1/R2/R3。

## §14 ★执行方式修订：必须由外部 harness 驱动（解决「观察者污染」）

> 本节由用户质询后补做实测得出。**它推翻 §7.1 的「用子代理当被测模型」方案。**

### 14.1 为什么要改：观察者污染

**用户质询（原话）**：「在这个 DeepSeek harness 里自己操作，**可能会受到提示词本来的影响**。」

**这个质询是对的，而且是致命的**：

```
若在 DSH 内部起子代理做实验：
  ① 子代理本身就跑在【被注入记忆提示词】的环境里
  ② 它看到的是【真实的注入内容】—— 这恰好是自变量
  ③ 它还会继承当前会话的部分上下文与行为倾向
  ⇒ 自变量被污染：你无法区分「是实验提示词起作用」还是「宿主注入起作用」
  ⇒ 这是教科书级的观察者效应（observer effect），实验结论不可信
```

### 14.2 实测：外部驱动完全可行（已真跑通）

**DSH 原生提供 headless 模式**：

```bash
dsh --profile headless --json "<任务文本>"
```

**实测输出（本次真跑，exit=0）**：

```json
{"type":"session","sessionId":"session-44698ff3-20b1-4590-802a-7fa475a2e74f","cwd":"D:\\dam-exp-probe"}
{"type":"status","phase":"turn_start","turn":1}
{"type":"status","phase":"step_start","turn":1,"step":1}
{"type":"thinking","text":""}
{"type":"text","text":"OK"}
{"type":"status","phase":"step_end","usage":{"inputTokens":8010,"outputTokens":2,"cacheReadTokens":0,"totalTokens":8012}}
{"type":"status","phase":"turn_end","reason":{"kind":"completed"}}
{"type":"final","text":"OK"}
```

**这份输出提供了实验要的全部测量量**：

| 字段 | 用途 |
|---|---|
| `sessionId` | 每轮独立；配合 `--session-id` 可续跑同一会话 |
| `cwd` | **确认工作区隔离是否生效**（我指定 `D:\dam-exp-probe`，它就是它） |
| **`usage.inputTokens`** | **提示词体积的直接测量值**（本次 8,010） |
| `thinking` / `text` / `final` | 模型输出，供离线评判 |
| `turn_start` / `step_end` | **步数统计**（判断模型是否「一轮就做完」） |

**⇒ 关键结论：外部进程可以调起 DSH 的真实会话，拿到完整 NDJSON 事件流。观察者污染问题被彻底解决。**

### 14.3 已发现的阻塞：插件没装在 headless profile

**实测**：上面那次 headless 跑完后检查工作区列表 —— **没有新增 `dam-exp` 工作区** ⇒ 插件未加载。

**根因**（查 profile 配置确认）：

```
~/.dsh/profiles/headless/package.json
  dependencies: {}                                    ← 空
  bundles: [dsh-base, dsh-headless]                   ← 只有两个基础包

~/.dsh/profiles/desktop/package.json
  "@a9i5k4/dsh-auto-memory": "link:D:/dsh-auto-memory"   ← 插件只装在这里
  bundles: [..., "@a9i5k4/dsh-auto-memory", ...]
```

**⇒ 必须先解决：让 headless profile 也加载本插件。**

### 14.4 解决方案（两选一，优先 A）

#### 方案 A：派生一个专用实验 profile（**推荐**）

```bash
# 1. 从 desktop 模板派生（这样自动带上全部插件，含 dsh-auto-memory）
dsh rescue --from-default-profile desktop

# 2. 或手工建 profile：复制 desktop 的 package.json，改 name，保留插件依赖
#    注意：profile 名会决定 ~/.dsh/profiles/<name>/ 目录
```

**⚠️ 但要注意**：派生 profile 会继承 desktop 的**全部**插件（几十个），启动慢且引入新的干扰变量。

**更干净的做法**：手工新建最小 profile，只装 `dsh-base` + `dsh-headless` + `dsh-auto-memory`：

```json
// ~/.dsh/profiles/memexp/package.json
{
  "name": "dsh-profile-memexp",
  "private": true,
  "dependencies": {
    "@a9i5k4/dsh-auto-memory": "link:D:/dsh-auto-memory"
  },
  "dsh": { "profile": { "bundles": [
    "@deepseek-ai/dsh-base",
    "@deepseek-ai/dsh-headless",
    "@a9i5k4/dsh-auto-memory"
  ] } }
}
```

然后：

```bash
cd ~/.dsh/profiles/memexp && pnpm install
dsh --profile headless --json "..."   # 或 dsh --profile memexp
```

#### 方案 B：把插件临时加进 headless profile

```
直接编辑 ~/.dsh/profiles/headless/package.json，加上 link 依赖与 bundle。
⚠️ 缺点：会改动你日常用的 headless profile，实验完后要还原。
```

### 14.5 修订后的执行架构

```
【外部驱动层】任意 harness（zcode / workbuddy / 你自己的终端）
    │  职责：写 harness.mjs、起进程、收集 NDJSON、离线评判、写报告
    │  它不需要有 memory_* 工具，也不需要懂 DSH
    ↓  execSync / spawn
【被测层】dsh --profile <memexp> --json "<任务>"
    │  职责：真实执行一轮 DSH 会话（含真注入 + 真工具）
    │        cwd 由外部指定（隔离工作区）
    ↓  NDJSON stdout
【评判层】checkHandoffCriteriaPre（纯 JS，可独立 import）
    │  职责：对输出做合规判定，给出可复算数字
    ↓
【产物】results.json + 原始 NDJSON + 实验报告
```

**这样设计的好处**：

| 优点 | 说明 |
|---|---|
| **消除观察者污染** | 被测模型只看到实验设定的提示词，不受当前会话影响 |
| **可自动化** | 外部脚本循环跑 N 组，零人工 |
| **可复现** | 同一条命令重跑即得同组数据（模型随机性需多次取均值） |
| **隔离彻底** | `cwd` 由脚本指定到临时目录，工作区自动派生 |
| **能测子实验 4** | 因为插件真加载了，`memory_*` 工具真存在 |

### 14.6 关键实现细节（踩坑预警）

**① Windows 上 `timeout` 命令冲突**

```bash
# ✗ 错：Windows 的 timeout.exe 会抢走这个命令（实测报「无效语法」）
timeout 120 dsh --profile headless ...

# ✓ 对：用 Node 的 spawn 超时，或 Git Bash 的 --foreground
```

**② 工作区隔离的验证方法（每次必做）**

```bash

ls ~/.dsh/memory/workspaces/ > after.txt
diff before.txt after.txt
# 只允许出现「本次实验预期新建」的目录，且必须含实验代号（如 dam-exp）
```

**③ 提示词变量的注入方式（重要）**

子实验 2 要比较 human_slim / run_slim 的不同版本。有两种注入路径：

```
路径 A：改配置 promptLayerOverrides（不改代码，推荐）
  ~/.dsh/.../config.json: { promptLayerOverrides: { snapshotSlimMaintain: '<新文本>' } }
  ⚠️ 但每个 profile 的配置位置不同，实验前必须先确认

路径 B：用 --patch 叠加一个配置层
  dsh --profile memexp --patch ./exp-v1.yml --json "..."
  ⚠️ 需先确认 --patch 能覆盖到 promptLayerOverrides（本仓未验证）

路径 C：直接改 lib/index.js 的 DEFAULT_PROMPT_LAYERS（最脏，最后手段）
  ⚠️ 会污染产品代码，实验后必须还原并校验 sha256
```

**⇒ 实验第一步必须先验证「哪条注入路径真的生效」**：用一个可观测标记（如在提示词里加 `[EXP-MARKER-V1]`），跑一次 headless，grep 输出里有没有这个标记。没有就说明路径不通。

**④ 模型随机性**

```
同一配置跑 3 次，合规率可能不同（温度/采样）。
⇒ 每组至少要 N=5 个不同任务 × 1 次，或 1 个任务 × 3 次取均值。
⇒ 报告里必须标注「每格样本量」与「是否取均值」。
```

```text
- 每次实验前后必须 diff 工作区列表，报告里声明残留 = 0
- 合规率必须用 checkHandoffCriteriaPre 算，禁止目测
- 不改 D:\dsh-auto-memory\lib\ 下任何产品代码（改配置/建 profile 可以）
- 不提交、不改版本号、不发布
- 若必须改产品代码做实验，先备份 + 事后还原 + 校验 sha256，并在报告里声明
```

### 14.8 这个方案仍然存在的局限（诚实标注）

| # | 局限 | 影响 |
|---|---|---|
| **L1** | headless 的 system prompt 与真实 desktop 会话不完全相同 | 绝对数值可能有偏差，但**相对比较（A vs B）仍然有效** |
| **L2** | headless 每轮都是新会话，测不出「多轮累积效果」 | 子实验 2 的「首轮学不到」问题测不了，需另设多轮实验（用 `--session-id` 续跑） |
| **L3** | 建 profile 会引入配置差异 | 必须保证所有实验组用**同一个** profile，只改提示词 |
| **L4** | 模型采样随机性 | 每格需多次取均值，成本上升 |

## §12 一句话提醒

**这份计划最大的风险是：把「子代理实验」的结论直接当成「真实生产结论」。**

小实验已经出现过一次这种情况 —— 我们以为「删提示词只会小幅降合规率」，实测是 **从 100% 掉到 0%**。

**请对每一个结论都问一句：这个数字是在什么环境下测的？能不能外推？**
