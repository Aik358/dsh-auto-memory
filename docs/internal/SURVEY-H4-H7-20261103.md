## 二 · H6 的根因不是「腰斩」，是一整套预算推导

`lib/index.js:11744`
```js
const sub = Math.max(0, Math.floor((budget - 500 - catalogCost) / 4))
```

四个证据段（recent-logs / reflection / user-memory / project-notes）**平分**剩余预算，各拿 `sub`。`injectBudgetChars` 默认 **8000** ⇒ sub ≈ 1,564。

随后 `lib/index.js:11897`：
```js
const memRefLimit = sub * 4 + catalogCost + planCap + ledgerCap + 400
```
分项限额**由 sub 反推**，保证桶装得下四段。

⇒ 三种改法，代价完全不同：

| 改法 | 做法 | 代价 |
|---|---|---|
| A | 调 `injectBudgetChars`（8000 → 40000） | 一行配置，但**同时**放大白板/账本预算（`planCap` 也吃它）⇒ 全帧可能从 24k 涨到 60k+ |
| B | 把 user-memory / project-notes 移出 `sub` 平分，单独给预算 | 定点，只影响两段；但 `memRefLimit` 推导要跟着改，否则桶超限被 drop |
| C | 只对**全帧档**放宽这两段上限（slim 档不变） | 符合「full 不设上限」的用户意图，但需新增「全帧专用证据段预算」概念 |

**这是需要拍板的地方。**
