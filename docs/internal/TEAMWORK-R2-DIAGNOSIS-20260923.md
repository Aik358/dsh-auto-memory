## 二、「晕」的根因（每条都指向代码）

### 根因 1：设置页是「一个 section 装下 9 个不相关主题」

`function section(key, title, content)` 定义在 `client.js:7000`，被调用 **9 次**：

```
L7010 engine   ｜ L7165 window  ｜ L7224 capacity
L7239 skills   ｜ L7260 handoff ｜ L7276 auto
L7302 store    ｜ L7327 look    ｜ L7358 about
```

- `engine`（引擎/语义模型）、`window`（上下文水位）、`capacity`（容量）、`skills`（技能库）、`handoff`（接续）、`auto`（自动化）、`store`（存储）、`look`（外观）、`about`（关于）
- **这 9 个主题分属 4 类完全不同的心理模型**：配置（engine/store/look）、监控（window/capacity）、内容治理（skills/handoff）、元信息（about）。
- 但它们**在同一个滚动页里平铺、同一视觉权重**（`settings.section` 只有 1 个挂载点，order 25）。
- ⇒ **这正是用户说"杂乱"的结构性原因**：没有一级/二级之分，所有东西同级。

### 根因 2：没有统一的交互原语，每个功能自己造一套

| 交互范式 | 出现次数 | 判读 |
|---|---|---|
| `kanban/lane` 泳道 | **54** | 主要视图 |
| `drawer` 抽屉 | **34** | 大量使用 |
| `badge` 徽标 | **20** | 状态表达 |
| `zoom/colW/toggleLayout/toggleFold/toggleCard` | **17** | 自建布局控制 |
| `switch/Checkbox` 开关 | **14** | 配置项 |
| `Details/Accordion` 折叠 | **1** | 仅 1 处 |
| **`Tabs` 页签** | **0** | **无** |
| **`Dialog` 弹窗** | **0** | **无** |
| **`Overlay` 弹层** | **0**（走宿主 `shell.overlay`） | 借用宿主 |

- 关键判读：**页面内部没有 Tabs / Dialog 原语**，但有 34 处 drawer 与 17 处自建缩放/列宽/折叠控制 ⇒ 「同类信息用不同交互」是**代码事实**，不是观感。
- `Details/Accordion` 只有 1 处 ⇒ 折叠不是体系化的，是偶发的。

### 根因 3：★ 同一概念 3–5 种叫法（**这是最直接的"晕"源**）

| 概念 | 实测的各种叫法（出现次数） | 叫法数 |
|---|---|---|
| **工作区 / 项目** | `workspace`=146 · `workspaces`=41 · 工作区=102 · 项目=31 · `project`=28 | **5** |
| **水位 / 上下文窗口** | 水位=49 · `water`=31 · `contextWindow`=6 · 上下文窗口=3 | **4** |
| **账本 / 交接** | 接续=107 · `handoff`=71 · 账本=57 | **3** |
| **技能库 / procedure** | `procedure`=48 · `skill`=33 · 技能库=**仅 2** | **3**（且中文几乎不用！） |
| **白板 / PLAN** | 白板=136 · `PLAN.md`=9 | 2 |
| **索引层 / L0 / 指引层** | `L0`=2 · `l0`=1 · 指引层=1 · 索引层=0 | 4（且都极少） |

**判读**：`技能库` 只出现 2 次而 `procedure` 出现 48 次 ⇒ **界面基本在对用户说英文内部术语**；`工作区/项目` 5 种叫法意味着**同一屏里可能同时出现三种称呼**。

### 根因 4：线性膨胀模式——每个功能加一个 section/徽标/开关

- 设置页 9 个 section、20 处 badge、14 处 switch、59 个 API 路径 —— 这是一个**只增不减**的累积曲线。
- `conversation.view` 有 3 个（order 78/80/81），全部挤在同一优先级带内 ⇒ **没有主次**。

## 三、对重构的硬约束（本文件确立，子代理报告必须遵守）

1. **不得引入构建链**：`client.js` 是零构建手写模块加载器（`var h = React.createElement`，`client.js:17`）。
2. **`lib/client.js` 是单写者文件**，且有 **177 项 smoke 回归**（`node tools/run-smoke.mjs`）⇒ 必须分批改、每批可独立验证。
3. **新增身份相关 UI 不得再往现有设置页塞第 10 个 section**（根因 4 的教训）——必须借 IA 重构一起落位。
4. **术语必须先统一再改 UI**（根因 3）：术语不统一时做任何布局调整，用户仍会晕。

## 四、第二轮实测：**主因不在设置页，而在 `WorkspaceTab` 与样式层**

> ⚠️ **本节修正前面的判断。** 第一轮我把「设置页 9 个 section 平铺」列为根因 1；第二轮取到标题原文与分区体量后，判定需要**下调设置页的嫌疑、上调下面两条**。修正依据如实列出。

### 修正依据 1：设置页的标题其实是**好的中文**，且已有页内跳转

`client.js` 里 `sectionLabels` 的真实内容（zh）：

```
engine   → '语义记忆总开关'      window  → '记忆窗口（注入什么）'
capacity → '记忆容量与归档'      skills  → '自动沉淀成技能'
handoff  → '长会话接续'          auto    → '自动化与免打扰'
store    → '存储与外部记忆'      look    → '外观与交互'
about    → '关于与诊断'
```

- **9 个标题全部是面向用户的中文短语，不是英文内部术语** ⇒ 「标签看不懂」**不成立**。
- 且代码里**已有** `function jumpToSection(key)`（`client.js:7000` 之后）做页内跳转 ⇒ 设置页**不是"没有导航"，而是"有导航但未显性化"**。

### 修正依据 2：设置页的问题不是"9 个平铺"，而是**极度不均衡**

| 分区 | 起始行 | 体量 |
|---|---|---|
| `engine` 语义记忆总开关 | L7010 | **155 行** |
| `window` 记忆窗口 | L7165 | 59 行 |
| `capacity` 容量与归档 | L7224 | **15 行** |
| `skills` 自动沉淀成技能 | L7239 | 21 行 |
| `handoff` 长会话接续 | L7260 | 16 行 |
| `auto` 自动化与免打扰 | L7276 | 26 行 |
| `store` 存储与外部记忆 | L7302 | 25 行 |
| `look` 外观与交互 | L7327 | 31 行 |
| `about` 关于与诊断 | L7358 | 40 行 |

- 设置页总跨度 **349 行**（L7010–L7358）。
- **`engine` 一项占 155 行 = 全页 44%**；而 `capacity`(15) / `handoff`(16) / `skills`(21) 三个"真正的治理功能"加起来才 52 行。
- 判读：这**不是均匀的"9 个主题平铺"**，而是「**一个巨型主题 + 八个薄壳**」。用户向下滚动时，前 44% 都在一个主题里 ⇒ 观感是"这页好长"，而非"东西好多"。

### ★ 主因 1：`WorkspaceTab` 是一个 **2608 行的单函数**

全文件顶层定义只有 **8 个**，其中两个是巨型块：

| 位置 | 体量 | 说明 |
|---|---|---|
| L1453–4905 | **3453 行** | 从 `var ROUTE_PREFIX = '/api/dsh-auto-memory'` 开始的一整块 |
| **L5128–7735** | **2608 行** | **`function WorkspaceTab()`** —— 承载整个可见 UI |

- `WorkspaceTab` 内部**没有任何 `var Xxx = function` 形式的子渲染函数**（实测计数 = 0）⇒ **没有组件边界**，所有视图/页签/抽屉/看板都在这一个函数体里内联展开。
- 三个 `conversation.view`（在 L7677/7688/7708 注册）与整个 `settings.section`（L7010–7358）**都在这同一个函数体内**。
- ⇒ **这是"晕"的结构性根源**：不是信息架构错了，而是**没有模块边界**，任何局部调整都要在一个 2608 行的函数里做（也解释了为什么重构必须分批、且必须有回归兜底）。

### ★ 主因 2：没有样式层 —— **430 处内联 style，仅 7 处 className**

| 写法 | 实测次数 |
|---|---|
| `style: { ... }`（内联样式对象） | **430** |
| `className: '...'` | **7** |
| `<style>` 注入块 | 1 |
| CSS 变量 `--dam-*` 使用 | **284** |

- **73 种**不同的 CSS 属性被内联使用（`WebkitLineClamp`、`backdropFilter`、`willChange` …）。
- **51 种硬编码颜色值**（`#c44a4a`、`#2fa46a`、`#e0a53a`、`rgba(76,141,255,.18)`、`color-mix(...)` …），其中还混着宿主变量 `--dsw-alias-*`（说明既想复用宿主主题、又在自己硬编码）。
- **93 种硬编码尺寸值**（`440px`/`560px`/`900px`/`1400px`/`1800px`/`170px`/`420px`/`520px`/`220px`/`96px` …）。
- 判读：**284 处 `--dam-*` 说明作者有 token 意识**，但没有把它当唯一来源 ⇒ 视觉一致性靠"每次手抄同一个数字"。这是"看着晕"的**第二根因**：同一类控件在不同页面长得不一样。

### 主因 3（补充）：语义色命名不统一

| 关键词 | 次数 |
|---|---|
| `error` | **97** |
| `ok` | 47 |
| `success` | 22 |
| `warn` | 20 |
| `tone` | 14 |
| `muted` | 7 |
| **`danger`** | **0** |
| **`variant`** | **0** |

- 状态语义有 **4 套并行词汇**（`ok`/`success`/`error`/`warn` + `tone`）且 `danger` 完全未用 ⇒ 徽标/提示的红黄绿**不是从一个语义表来的**。

### 修正后的根因排序（供重构方案采纳）

| 优先级 | 根因 | 证据 | 类型 |
|---|---|---|---|
| **P0** | `WorkspaceTab` 2608 行无组件边界 | L5128–7735；内部子函数 = 0 | 架构 / 历史堆积 |
| **P0** | 无样式层：430 内联 vs 7 className | 73 属性 / 51 色 / 93 尺寸 | 缺设计系统 |
| **P1** | 术语 3–5 种叫法（工作区/项目、接续/账本/handoff…） | 见 §二·根因 3 计数表 | 缺术语表 |
| **P1** | 语义色 4 套并行、`danger` 未用 | `error`97 / `ok`47 / `success`22 | 缺设计 token |
| **P2** | 设置页 engine 一项占 44%，其余为薄壳 | 155 行 vs 15–31 行 | 布局不均衡 |
| **P2** | 页面内无 Tabs / Dialog 原语（各 0） | 靠 34 抽屉 + 17 自建缩放代替 | 缺交互原语 |

**给重构方案的硬结论**：**不要先动信息架构**（设置页标题与跳转其实合格）。第一刀应切在
① **`WorkspaceTab` 拆出组件边界**（纯移动，不改行为，可回归验证）；
② **建样式层**（把 430 内联收敛到 CSS 变量 + 少量可复用组件）。
这两条做完，「晕」会显著下降，且之后才谈得上把「团队维度」插进合理位置。
