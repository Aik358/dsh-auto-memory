# 一、为什么必须重跑（上一轮实验的三个出题缺陷）


## 1.1 缺陷一（致命）：`fields` 表示在归属时刻**不可得**

上一轮最好的变体是 `fields` = 每个检查点的 `goal` + `state`（四段中的两段）。实测填充率：

| 项 | 真实快照实测 |
|---|---|
| 检查点总数 | 770 |
| `goal` 非空 | 524（**68.1%**）|
| `state` 非空 | 542（70.4%）|
| `goal`+`state` 都非空 | 524（**68.1%**）|
| **事件级** `sections.goal` 非空 | **23 / 52（44.2%）** |

**真正的问题是时机**：归属发生在「一条新日志刚写进来」的那一刻。此刻事件的可得表示只有
`name` + `summary` + **已有检查点原文**。`sections.goal/state` 是**事后**才由 Agent 主动 `memory_event(action=set)` 补写的，
**归属时刻大概率还没有**。
⇒ 用 `goal+state` 当文档表示 = **先把答案整理成结构化要点，再考模型能不能匹配上**。
⇒ 这个 +15.9pp 在真实场景拿不到。**本实验的第一目标就是量化这个损失。**

## 1.2 缺陷二：语料 100% 中文为主，纯英文 **0 条**

Lead 已实测（剥掉代码标识符/路径/camelCase 之后统计 725 条文本）：

| CJK 比例 | 条数 |
|---|---|
| = 0（纯英文） | **0** |
| < 0.15 | **0** |
| < 0.5 | 42（5.8%）|
| > 0.85（中文为主） | **725（100%）** |

⇒ 上一轮所有指标只在「中文为主」分布上成立。用户指出的真实场景（模型输出英文、GitHub issue 全英文）**完全未覆盖**。

## 1.3 缺陷三：查询形态可能与真实不符

上一轮查询是「检查点文本」，真实查询是**新写的一条日志**。形态、长度、括号/编号习惯可能不同。

# 三、方法论（这是本任务的核心，请严格按此出题）


## 3.1 「符合实际的出题」定义


```
对于每个待测目标检查点 C（属于事件 E）：

  查询 Q = C.text                          ← 一条真实的检查点原文（模拟「新写的一条日志」）

  候选文档 = 除 E 之外所有 active 事件 + E 自己，共 47 个；每个事件的表示按下面 A/B 两种口径：
    A『冷启动口径』= name + summary + 该事件**第 1 条**检查点原文
    B『成熟口径』  = name + summary + 该事件**最近 N 条**检查点原文（N=5）

  注意：**两种口径都不使用 sections.goal / sections.state**（那正是要证伪的东西）

  打分 = cos(embed(Q), embed(事件表示))
  判据 = 正确事件 E 在 47 个候选里的排名
```

**关键要求**：
- 查询 C 在算「事件 E 的表示」时必须被**剔除**（LOO，留一法），否则就是拿答案当输入
  若 E 的表示在剔除 C 后为空（例如 E 只有 1 条检查点且 C 就是它）⇒ 该样本标记 `degenerate` 并**单独统计**，不得混入主指标
- 所有事件表示与查询必须用**同一模型、同一前缀口径**

## 3.2 必须跑的三组对照


| 组 | 文档表示 | 目的 |
|---|---|---|
| **G1** | `fields`（goal+state，上一轮口径） | **复现基线**，确认本实验与上轮可对齐 |
| **G2** | `A 冷启动口径` | 真实场景下限 |
| **G3** | `B 成熟口径` | 真实场景常态 |

⇒ **G1 → G3 的落差 = 「上一轮提升」中有多少是出题方式带来的假象**。这是本实验最想拿到的数字。

## 3.3 语言分桶（第二目标）

对每个目标检查点按语言打标，**分桶报告**，不许只给总分：

```
langOf(text):
  先剥离：行内代码 `...`、camelCase 标识符、全大写缩写、路径、长 hash、HTML 注释
  cjk = 汉字数, lat = 字母数
  cjk+lat == 0        -> 'none'   （纯符号/数字，单独统计）
  cjk == 0            -> 'en'
  lat == 0            -> 'zh'
  cjk/(cjk+lat) > 0.85 -> 'zh-mostly'
  cjk/(cjk+lat) < 0.15 -> 'en-mostly'
  否则                 -> 'mixed'
```

**注意**：现有语料里 `en` 与 `en-mostly` 预期为 **0 条**（Lead 已实测）。
⇒ 若确实为 0，**如实报告「本机真实语料中不存在纯英文样本」**，不要伪造英文样本凑数。
⇒ 但要求额外做一个**受控英文探针**（见 3.4）。

## 3.4 英文与跨语言：受控探针（第二目标的核心）

不要编造「看起来像真实记忆」的英文语料。改用**受控探针**，只回答能力问题，不冒充真实分布：

**探针 P1 · 同语言英文（英→英）**
  取 15 个事件，用其 `name` + `summary` 的**人工英译**作为英文查询，匹配英文事件表示。
  ⇒ 回答「纯英文场景下模型还能不能分开」。
  若人工英译成本高，退而求其次：用**现有语料里 CJK 比例最低的 15 条**（Lead 实测最低 ratio=0.238）。
  但必须标注「这不是纯英文」，不得当成纯英文结论。

**探针 P2 · 跨语言（中→英 / 英→中）**
  构造 15 对「中文查询 ↔ 英文文档」与 15 对「英文查询 ↔ 中文文档」，
  测 cos 分布 vs 同语言对的 cos 分布，报告 **跨语言掉多少**。
  同样：人工翻译若成本高，允许用**受控模板**（例如把中文事件名翻成英文），但必须标注构造方式。

> ⚠ 探针结论只能写成「在受控探针上，跨语言相对同语言的相对损失是 X%」，
> **不得**写成「真实场景跨语言准确率是 X%」。

## 3.5 语言路由的可行性评估（顺带回答）
