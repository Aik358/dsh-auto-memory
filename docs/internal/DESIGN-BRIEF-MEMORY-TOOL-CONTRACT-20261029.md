## §1 这个产品是什么（先建立心智模型，否则方案会跑偏）

`dsh-auto-memory` 是 DSH（DeepSeek Harness）的**自动记忆插件**。它给模型提供一组 `memory_*` / `calendar_*` 工具，让模型在对话过程中沉淀长期记忆。

**核心架构（这是设计的地基，不可动摇）**：

```
事件（Event）            = 记忆的第一等单元。一件事 = 一个事件容器，可中断再捡起，跨天也算同一件
  ├─ name / summary      = L0 总览（模型写）
  ├─ sections{goal,doing,deadend,next}  = 四段，反映「当前」状态（不是历史累积）
  └─ checkpoints[]       = 检查点。每次进展一条 = 一个证据点
        └─ goal/state/dead/next  = 检查点级四段（白板「近期进展」的数据源）

白板 PLAN.md    = 事件的【投影视图】，不手写
交接账本 .md    = 动态状态的权威原文载体（append-only）
每日日志        = 日记类，独立，不事件化
每日反思        = 日记类的蒸馏产物，独立

★ 真相源只有一个：事件。白板/账本/笔记都是投影。
```

**关键文件**：

| 文件 | 作用 |
|---|---|
| `lib/index.js` | 主引擎（1.35 MB）：21 个工具的 schema 与执行分支、注入渲染、pre-step |
| `lib/event-store.js` | 事件存储与投影（`append` L555+ / `list` L650 / `checkpointQuad` L478） |
| `lib/event-write.js` | 事件写入（`appendCheckpointPre` L170 / `appendHandoffCheckpointPre` L401 / `parseLedgerSectionsPre` L357） |
| `lib/wb-contract.js` | 白板/账本判据门（`checkHandoffCriteriaPre` H1-H4 / `checkPlanCriteriaPre` P-H1/P-H2） |
| `lib/ev4-adapter.js` | 前端适配（`adaptCheckpointPre` L126） |

## §2 为什么要做这件事（用户原话，需求原文）

### 2.1 用户的判断

> 「提示词可能是有问题的，它**没有正确地指导模型正确的记忆写入流程**。」
>
> 「如果，如果要保持提示词比较简练，**应当在调用工具之后进行返回：不是一味地接受，而是如果不符合相关格式，就返回相关指导并拒绝接受**，并提示我执行相关的操作。」
>
> 「过多的指示提示词可能会导致效率下降和上下文占用提升。」

**三条约束同时成立**：
1. 提示词必须**变短**（效率 + 上下文成本）
2. 指导不能丢 —— 搬到**工具回执**里
3. 不合格就**拒绝**，并告诉模型怎么改

### 2.2 用户明确点名的四个回执场景（逐字）

| # | 用户原话 | 触发工具 |
|---|---|---|
| 1 | 「我写完了账本，是不是应该考虑一下相关的事件？」 | `memory_note(kind=handoff)` 之后 |
| 2 | 「或者我加了事件，是不是应该考虑加账本？」 | `memory_event(create)` 之后 |
| 3 | 「我事件结束之后，是不是应该再过一遍其他的事件？」 | `memory_event(close)` 之后 |
| 4 | 「我写了 memory log，是不是应当考虑一下交接白板和最近的事件？」 | `memory_log` 之后 |

### 2.3 用户要做三个新功能（逐字，产品需求）

**功能 1 · Memory Timeline（事件展示与下钻）**
> 「可以直接列出模型最近做的事情（包括大事件和小事件）。主要是可以先选大事件，比如用 **Memory Timeline 列出最近时间线的大事件**，然后可以再通过 Memory Timeline、Blackboard 等相关内容，**查看每个大事件里的小事件**。」

**功能 2 · 智能提醒与写入**
> 「如果某个事情记了有实质性变化，系统可以提醒模型看看有没有**共同记忆、共同共识或者作者情感**，评估是否可以写入。」

**功能 3 · 智能推荐（猜你想用）**
> 「对于比较重要、可以写入 **Calendar** 的事情，系统不仅要在提示词里提醒我，还要**在调用完工具以后，智能推荐『猜你想用』**。」

## §3 已确认的事实基线（前序调查已实测，可直接采信但建议复核关键项）

### 3.1 提示词重复度 —— 这是「必须精简」的量化依据

```
GUIDANCE 常量（system prompt）        3,312 字符
21 个工具 description 合计            8,035 字符
21 个工具 schema 合计                12,869 字符
注入面（完整版渲染结果）              23,562 字符
────────────────────────────────────────────
固定成本合计                         47,778 字符 / 每次请求
```

**⚠️ 关键口径**：工具 description + schema = **20,904 字符**，比注入面还大。**「工具定义本身就是最大的提示词」** —— 精简的主战场在这里，不在注入面。

**同一条规则跨提示面重复（实测）**：

| 规则 | 出现在几个面 | 总命中次数 |
|---|---|---|
| R1 四段必填 goal/state/dead/next | **5 面** | **39 次** |
| R2 检查点必带溯源 | 4 面 | — |
| R3 每次变动重写四段 | 3 面 | — |
| R5 close 前先 set summary | 3 面 | — |
| R10 白板由事件渲染不要手写 | 3 面 | — |

⇒ **12 条核心规则中 10 条在 ≥2 个面重复。可删约 2,100 字符。**

### 3.2 当前「校验姿态」的真相（⚠️ 与直觉不同，务必读完）

**账本已经有很强的质量校验，不需要新建**：

```js
// lib/wb-contract.js —— checkHandoffCriteriaPre() 真实判据
H1  四段标题齐全且逐字匹配（缺一个就拒）
H2  每段不得少于 20 字符（实测：18 字符的「下一步」会被拒）
H3  不得是纯占位符段
H4  总长 ≤ 8000 字符
S1-S4 软判据（各段 ≤5 行 / 有「方案→失败原因」箭头 / 下一步可执行 / 无临时信息）
```

**真正没有校验的是这几处**：

| 工具 | 现状 | 危害 |
|---|---|---|
| `memory_event(append)` | 检查点四段全空也**接受**；无溯源也接受 | 白板/详情页出现空白行（用户已实报） |
| `memory_log` | 结构上**无法**提供四段（入参只有 note/date/kind） | 它写的 log 检查点四段恒空 |
| `calendar_add` | **仅校验 title 非空且无换行**；日期/时间/象限都不校验 | 日历可能带坏日期 |
| `memory_event(set)` | 可把 sections 写成空串 | 四段被清空 |

**「语义必填但标成 optional」**：`memory_note` 的 `expectedRevision` 描述里写「plan 整篇重写必填」但 `required=false`（CAS 会因此走 no-CAS 路径）。

### 3.3 回执引导：完全空白

```

grep -nE 'nextStepHint|followUpHint|suggestPre|receiptHint'        => 空（基础设施不存在）
```

**现有回执实测**（真实调用取到的原文）：

| 工具 | 当前回执 | 字符数 | 有无下一步指导 |
|---|---|---|---|
| `memory_event(append)` | `已追加到 evt_xxx：本次 +1 条，现共 1 个检查点。` | ~40 | ❌ 零 |
| `memory_event(create)` | `事件已建立: evt_xxx / 名称: ... / 状态: active / 存储: <130字符路径> / 下一步: 用 action=append 加检查点（记得带 idemKey）。` | 252 | ⚠️ 只有 append，**没提该写账本**；且「存储」那行是纯噪音 |
| `memory_event(close)` | `事件已收口: evt_xxx / 成果: <前200字符>` | — | ❌ 零 |
| `memory_note(handoff)` | `交接账本已写入: <path> / 请在本轮回复正文向用户转述本次更新要点。` | 174 | ⚠️ 只有「请转述」 |
| `memory_log` | `已更新记忆文档: <path> / - 00:26 ... / (日视图补写 1 行)` | 95 | ❌ 零 |

### 3.4 一个已确认的真缺陷（P0，方案里必须覆盖）

**WAL 半渡态：被判据门拒绝的坏账本，仍然进了事件库**

```
lib/index.js  memory_note(kind=handoff) 的执行顺序：
  Phase 1  appendHandoffCheckpointPre(...)   ← L21953-21959，先写事件，零内容校验
  Phase 2  writeHandoffLedger(...)           ← L21977-21980，再过判据门，不合格 ok:false
  Phase 3  失败 → 追加 kind='handoff-write-failed' 补偿检查点  ← L21983+
```

**实测后果**：账本 `.md` 被拒（好），但坏内容已作为**不可撤销的检查点**留在事件库；每失败一次多两条（坏内容 + 补偿标记）。

**真实数据**（13 个工作区 / 553 检查点）：
```
write-failed 补偿标记 = 3 条  ⇒ 半渡态真实发生过 3 次
```

**Phase 3 的文案自己就承认了**：「原内容已作为前一检查点记入事件（可经 memory_recall(scope="events") 取回）。」

## §6 工作纪律（本仓硬规约，违反会被打回）

### 6.1 证据纪律

- **禁止静态断言冒充验收** —— 「源码里存在某字符串」不算证据。必须真 import → 真构造 → 真调用 → 断言返回值或副作用
- **每条关键结论必须带负路径** —— 证明「不这么做就会错」
- **必须给可复算物理量** —— 字符数 / 字节数 / sha / PASS 数，不接受「大约」「估计」
- **不采信本任务书的结论** —— §3 的事实基线是前序调查实测的，但请**抽查复核**关键数字（尤其 47,778 与 553 检查点这两处）

### 6.2 安全纪律

- **本阶段只出方案，不改 `lib/` 下任何产品代码**（用户要求「先出方案」）
- **探针脚本会真调工具，而 `resolvePaths` 按 cwd 派生工作区** —— 配置与 DSH_HOME 都拦不住。若写探针，**必须在运行前后对比工作区清单，只删本次新增且名字含特定前缀的目录**，并在报告里声明残留 = 0
