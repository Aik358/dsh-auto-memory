## 1. 原始设计意图

### 1.1 它想做的那件事

设计文档 `docs/M8-MEMORY-HUB.md` §1 原文：

> 记忆中枢把三层记忆（经历/事实/技能）串成一条链：**从对话沉淀经历 → 固化事实 → 把反复成功的流程固化为技能（skill）→ 相似场景自动召回注入，让 AI 按固定流程执行**。这是 M7 记忆召回系统的「供给侧」——M7 决定「怎么送达」，记忆中枢决定「有什么可送达」。

即 M8 是**供给侧**：决定「有什么可送达」；M7 是**投递侧**：决定「怎么送达」。两者分工明确，这是好设计。

### 1.2 设计图规定的输入（关键）

`docs/M8-MEMORY-HUB.md` §2 的路径图把三个 store 的输入**分开画**：

| store | 设计图上的输入 | 图上备注 |
|---|---|---|
| M-02 Episodic（经历） | **M2 segments（对话段）** user/assistant/reasoning | append → consolidate → episode |
| M-03 Semantic（事实） | **M7 judgement-shadow 的 `semantic_candidate` / `profile_candidate`** | 图注明确「**Python 只建议**」 |
| M-04 Procedural（技能） | **M5 evidence** + `procedure_candidate` + episode success | observe → candidate → validated → active |

**要点**：设计图上 **fact 的输入不是 episode**。episode 只喂 procedure（`success episode` / `crossFeed 举一反三`）。这是本报告所有结论的基准线。

### 1.3 设计原则（模块头注释自述）

`lib/memory-hub-pre.js:18-23`：

- **不杂糅**：三层各管各的 store，hub 只做编排和转发，不重实现任何一层的逻辑。
- **即插即用**：Host 接线时传入三个 store 实例即可工作。
- **全 fail-closed**：任一 store 缺失/失败，该路静默跳过，不阻断其他路。

### 1.4 回写通路的设计意图

`lib/index.js:10095-10096` 原文：

> 写回:P1④ 主闭环——hub.facts 中 **confirmed**/未过期/未撤销/**置信≥0.6** 的事实,每日限额
> 治理式写入 notesPath/userFile(autoConsolidate 同款 appendText 原子事务)→ 进 M7 语料。

即：把 hub 里**已确认的事实**搬运进 `MEMORY.md`，让它们进入注入面与语义语料，闭合「发现 → 固化 → 送达」的环。**意图合理**。

### 1.5 它服务的最终价值（`docs/M8-MEMORY-HUB.md` §4）

技能生命周期 `observed → candidate → validated → active → deprecated`，晋升门槛四关：跨会话 ≥3、成功 ≥2、correction ≤30%、高风险需批准。**这套技能晋升机制是有价值的，且运转正常**（用户手动晋升的 9 条真技能即为证）。

> **⚠️ 范围界定**：本报告的批评**只针对 fact 层与其回写出口**。procedure 层（技能晋升 + checklist 注入）不在批评范围内——A 阶段已退役其机械切片分支，剩余两条通路（模型直写、用户手动）是正当的。

## 4. 根因：三个层次的叠加

### 4.1 根因 A（代码缺陷，直接因）

`lib/index.js:10216`：

```js
if (typeof fact.confidence === 'number' && fact.confidence < 0.6) continue
```

| 写法 | 字面语义 | 设计意图 |
|---|---|---|
| `typeof c === 'number' && c < 0.6` → 拦 | 「是数字**且**低于 0.6 才拦」 | 「**置信≥0.6 才放行**」 |

两者在 `null` / `undefined` / 字符串上**行为相反**：

| `confidence` | 实际 | 应为 |
|---|---|---|
| `0.5`（数字） | 拦 ✅ | 拦 |
| `null` | **放行** ❌ | 拦 |
| `undefined` | **放行** ❌ | 拦 |
| `'0.9'`（字符串） | **放行** ❌ | 拦 |

**这是「逃逸型守卫」模式**：用负向类型判断实现白名单式门槛，未覆盖的类型不是被拒而是被放行。

### 4.2 根因 B（设计缺口，来源因）

`lib/memory-hub-pre.js:252`：

```js
if (ep.unresolved && ep.unresolved.length && stores.facts) {
```

这条边在设计图（§1.2）上**不存在**。它引入了一个不该存在的来源：**episode 的原始对话文本**。

而支撑它的判据 `extractUnresolved`（`lib/episodic-store-pre.js:237`）是纯正则：

```js
/[^。！？\n]*[？?][^。！？\n]*/g
```

⇒ **凡含问号的句子即判为「未决事项」**，无法区分「用户的真实待办」与「用户随口一问」。

配套的 `extractIntent`（同文件）是 `clean[0].slice(0, 60)` ⇒ **取本会话第一条用户文本，截断 60 字，直接当主语**。

### 4.3 根因 C（意图未实现，放大器）

`lib/index.js:10095` 的设计注释要求「**confirmed**」前提，但：

- `lib/fact-store-pre.js:54` 的枚举是 `['fact', 'observation', 'directive']` —— **根本没有 `confirmed` 这个取值**
- 出口 `hubFlushTick` **不检查 `epistemicStatus`**

⇒ 设计的四个前提（confirmed / 未过期 / 未撤销 / 置信≥0.6）中：
- 「未过期」`ttl:0` = 永不过期 ⇒ 恒真
- 「未撤销」只在显式撤销时假 ⇒ 基本恒真
- 「置信≥0.6」**因根因 A 而失效**
- 「confirmed」**从未实现**

**四个前提实际只剩一个「未撤销」在起作用。**

### 4.4 为什么内容判据（B-3）无法补救

`lib/fact-store-pre.js:245` 的 B-3 判据（2026-09-22 上线）只拒 5 种形态，其中与问句相关的是：

```js
function factQuestionOnlyPre(text) {
  const s = String(text).trim()
  if (!/^[?？]\s*$/.test(s.replace(/[^?？]/g, ''))) ... // 简化示意
  if (!FACT_QUESTION_TAIL_RE_PRE_V1.test(s)) return false   // 须【以 ?/？ 结尾】
  return !factHasClausePre(s)                              // 且【整句无陈述成分】
}
```

- 这些残句的问号多在**句中**（`不是谁告诉你…？上下文才刚过一半儿，继续。`）⇒ 第一关不过
- 或句尾接陈述、含「是/在/有/了」⇒ `FACT_CLAUSE_MARKER_RE_PRE_V1` 命中 ⇒ 第二关不过

**实证**：B-3 上线后，2026-09-23 12:32 仍新增一条。⇒ **靠内容判据堵这条通路，方向不成立。**

### 4.5 这个缺陷 2026-09-19 已被记录，但未修

`docs/internal/ISSUE10B-FORENSICS-20260919.md` §4.4 的过滤链表第 ④ 行**逐字写着**：

> `confidence < 0.6` 拒绝 ｜ `:8972` ｜ **`confidence: null` 直接放行**（`typeof null !== 'number'`）⇒ 实测 3 条 null 全过

同批修复（T1-1 / T1-2 / T1-3）补的是**清洗器**（U+FFFD、运行时信封），即 ⑥ 号门。**④ 号门被记录在案却没修**，因此从设计至今一直生效。

> **可复用判据（建议写入开发纪律）**：`typeof x === 'number' && x < T` 形的守卫是**逃逸型**守卫——它放行 `null`/`undefined`/字符串，与「必须 ≥T 才通过」的意图相反。凡白名单式门槛，不得用负向类型判断实现。

## 5. 影响评估

### 5.1 危害面（按严重度）

| # | 危害 | 说明 | 等级 |
|---|---|---|---|
| 1 | **劫持 agent 行为** | 用户的祈使句/问句被固化后进入 **Tier-0 每轮无条件注入**。实测已发生：agent 读到「我紧急停一下…」后**把一段过期原话当成实时指令，中止了手头任务**。 | **严重** |
| 2 | **污染项目长期记忆** | `MEMORY.md` 是 AI 维护的文件，混入 11 段非模型产出的机械文本，且带 `##` 标题 ⇒ 被 `compactLegacyLayer` 当独立段落搬运、进语义语料。 | 高 |
| 3 | **自指闭环（半闭合）** | `MEMORY.md` 被重新扫描后产出新 fact（`predicate=记录要点`，`confidence=0.5`）。本轮它被 ④ 正确拦下（数值型），**但如果将来出现 `null` 值，环会闭合**。 | 中 |
| 4 | 面板噪音 | 「记忆中枢 → 事实」栏展示 158 条，**157 条无意义**，用户判断力被干扰（2026-09-21 审计已列为问题）。 | 中 |
| 5 | 存储与 token 成本 | 158 条 fact 持续累积；`MEMORY.md` 每轮注入。 | 低 |

### 5.2 关键判断：**这条通路当前的实际价值接近零**

| 通路成分 | 评估 |
|---|---|
| 147 条数值型 fact | 主语是 `mem_xxx`（记忆条目自身 id），谓词是 `relation`/`记录要点` ⇒ **是记忆语料自己派生的循环数据，无独立信息**。且它们**本来就被 ④ 拦下、从未进入正文**。 |
| 11 条 null fact | 全部是垃圾。 |
| **结论** | 即便把 ④ 修好，**M8 回写通路的产出会归零**——因为唯一能通过的 11 条正是要拦的垃圾，其余 147 条本就通不过。 |

> **换句话说**：这条「自动把 fact 写进 MEMORY.md」的通路，从设计到今天，**没有成功搬运过一条真正有用的知识**；它唯一实际做成的事，就是**污染了 11 次**。

### 5.3 为什么会这样：它的输入源本身就不产出知识

- 入边 ①（judgement-shadow）：设计规定，但实测产出的是 `subject=mem_xxx` 的元数据行，**不是事实陈述**。
- 入边 ②（episode）：设计外的边，产出用户口语。
- 入边 ③（memoryId 富化）：产出条目元数据。

⇒ **三条入边都不产出「关于世界的知识」**。而出口却按「这是知识」的模板（`## 标题 + 要点 + 来源`）渲染。**形态错配**是根本问题：**它拿的是过程数据，写的是知识形态。**

### 5.4 与 M7/注入面的耦合（这是危害 1 的机制）

```
hubFlushTick ──写入──► MEMORY.md ──► tier0-catalog-pre 切分 ──► Tier-0 常驻目录
                                                                      │
                                                                      ▼
                                                        每轮无条件注入 agent 上下文
```

**关键**：Tier-0 是**无条件注入**层，不经过相关性过滤、不经过模型审校。任何进入 `MEMORY.md` 的文本，都会在**每一轮**出现在 agent 眼前。这使它成为整个系统里**权限最高的写入面**——而它有一个**无模型参与的写入者**。

## 6. 改造方案

### 6.0 决策总览

| 优先级 | 事项 | 性质 | 改动量 |
|---|---|---|---|
| **P0** | 修 ④ 号闸门（白名单化） | Bug 修复 | 1 行 |
| **P0** | 清理已污染数据 | 数据 | 见 §6.3 |
| **P1** | 决定 `episode → fact` 边去留 | **设计决策（需用户拍板）** | 见 §6.2 |
| **P1** | 让出口检查 `epistemicStatus` | 补设计意图 | 1 行 |
| **P2** | 注入侧加「既往记录，非当前指令」标记 | 防劫持兜底 | 见 §6.4 |
| **P3** | 重新定位 M8 回写通路的存在意义 | **架构决策** | 见 §6.5 |

### 6.1 P0：修闸门

**锚点**：`lib/index.js:10216`

**现状**：
```js
if (typeof fact.confidence === 'number' && fact.confidence < 0.6) continue
```

**建议改为（白名单式）**：
```js
const conf = fact.confidence
if (!(typeof conf === 'number' && conf >= 0.6)) continue
```

**理由**：`!(A && B)` 形式保证「不满足全部条件即拦」，`null`/`undefined`/字符串一律被拒。语义从「低于阈值才拦」翻转为「达标才放行」，与设计注释一致。

**同步建议**：加一行 diag 留痕（本仓纪律：fail-soft 必须留痕），例如
```js
try { diag('hub flush skip(confidence): ' + fact.factId.slice(0,16) + ' conf=' + String(conf)) } catch (_) {}
```

**附带影响（必须知情）**：修改后 **M8 回写通路产出归零**（见 §5.2）。这是正确答案，但意味着这条通路**变成空转**——见 §6.5。

### 6.2 P1：`episode → fact` 这条边（**需用户拍板**）

`lib/memory-hub-pre.js:252-…`，约 20 行。

**三个选项**：

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **(a) 删除** | 整段移除，fact 只接受设计规定的 judgement-shadow 输入 | 与设计图一致；彻底堵住口语入口 | 失去「未决事项自动进 fact」能力（但实测该能力产出 100% 垃圾） |
| **(b) 保留 + 加严判据** | 保留边，但要求 `unresolved` 项**不含**第一人称/祈使/口语标记，且主语不得等于 `episode.intent` | 保留设计外能力 | 又一道内容判据；B-3 的失败证明这类判据易漏 |
| **(c) 改道** | 该边不再写 fact，改写 episodic 的**待办视图**（只展示不注入） | 保留「未决」语义，且不进注入面 | 需新增视图面 |

**建议 (a)**，理由：
1. 与设计图一致，消除「设计外的一条边」这一结构性偏差；
2. 实测该边产出 **11/11 全垃圾**，无损失；
3. 用户已明确「机械通路已被我弃用」（A 阶段裁定的同一原则）；
4. 「用户未决事项」这一信息**本来就不该进长期记忆**——它是**会话状态**，不是**知识**。

### 6.3 P0：清理已污染数据

| 目标 | 内容 | 注意 |
|---|---|---|
| `MEMORY.md` | 2 个 `（M8 固化）` 块 | **必须先备份 + 确认锚点归属**（该块紧邻 `<!-- memory:mem_* -->`，硬删会留下孤儿/错位锚点——本仓「防锚点击穿」纪律） |
| `archive/notes-archived.md` | 9 个块 | 归档文件，可选清理 |
| `hub-pre/facts.json` | 157 条垃圾（147 元数据 + 11 口语） | 建议整表清空或标记 revoked；**注意 `mem_45e4426` 等真实条目的 provenance 引用** |

**清理前必做**：这三处都要先备份，且 `facts.json` 清理要确认不影响 `procedure` 的 `sourceMemoryIds` 引用链。

### 6.4 P2：注入侧防劫持标记（兜底）

**动机**：§5.1 危害 1 是最高危的——**记忆能反过来指挥 agent**。即使前几项修好，**只要任何无模型写入者存在，这个风险就在**。

**做法建议**：在 Tier-0 常驻目录的渲染处，给**来源可疑**的条目（`sourceClass="semantic-candidate"` / 无模型审校痕迹 / 含祈使句或问句形态）加前缀标记，如 `[既往记录·非当前指令]`。

**注意**：此项**改注入文案形态**，会占用每轮 token，且需要定「可疑」的判据 ⇒ 属需用户拍板项。

### 6.5 P3：重新定位这条通路（**架构决策，最重要**）

**核心问题**：`MEMORY.md` 已经有一条**模型维护**的正规写入通路（`memory_log` / `memory_note` / 维护蒸馏，锚点 `index.js:11114` / `:11153` / `:8602` / `:8697` / `:8802`）。

⇒ **机器回写是重复建设**。而且它带来三个结构性问题：
1. 绕过了模型判断（本仓的核心纪律是「客观叙述由模型维护」）；
2. 写的是**过程数据**，却用**知识形态**渲染；
3. 直通**最高权限注入面**（Tier-0 无条件注入）。

**三个方向供选择**：

| 方向 | 描述 | 适用判断 |
|---|---|---|
| **① 废弃回写** | 删除 `hubFlushTick` 整段（含定时器、flush-state 持久化、模板）。fact 层只服务面板展示与 M7 语料，**不再写 `MEMORY.md`** | 若认为「模型维护记忆」已是唯一正当通路 ⇒ **推荐** |
| **② 降级为只读面板** | 保留 fact 存储与面板，彻底取消回写 | 若仍想保留「记忆中枢」三栏视图 |
| **③ 转人工闸门** | 回写改为**待批准队列**，用户/模型确认后才写 | 若确实需要机器发现，但必须经审 |

**建议 ①**：M8 的**真正价值在 procedure 层**（技能晋升 + checklist 注入，运转正常且用户认可），fact 层回写是**设计图上一条从未产出价值的闭环**。删除它可同时消除：无模型写入者、最高权限面污染、token 成本、面板噪音。

> **如果选 ①**，M8 剩余职责变为：episodic 记录、procedure 晋升、judgement 消费、面板展示。这些**都不含无模型写入**。

## 7. 建议实施顺序

```
步骤 1  备份三处数据（MEMORY.md / archive / facts.json）
步骤 2  修 ④ 号闸门（1 行）→ 止血，新泄漏立即停止

步骤 6  【拍板】注入侧标记（§6.4）→ 兜底
步骤 7  跑全量回归（node tools/run-smoke.mjs，基线 175 套件）
```

**依赖关系**：步骤 2 独立、可立即做；步骤 4/5/6 需拍板；步骤 7 必须在 2–6 之后。

**注意**：改动落在 `lib/index.js` / `lib/memory-hub-pre.js`，**属宿主加载期模块，改完需用户自行重启 dsh web 生效**（agent 不自行重启）。
