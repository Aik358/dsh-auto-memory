# R4 交接账本改造方案：实时维护文档

> 日期：2026-11-10 · 范围：方案，不实施 · 输入裁定：R4-1～R4-6
> 调查方式：只读源码与真实记忆数据；未改 `lib/`、`tests/`、`tools/` 或真实记忆数据。
> 行号以本轮工作树为准，实施时须按函数名重新定位。

## TL;DR

**把工作区当前维护主题的交接账本改成一份可就地更新的 Markdown 项目/批次维护文档：稳定语义文件名含首次创建时间，文档关联一个或多个事件，只保留当前事实；事件检查点仍 append-only，保存本次规范四段及文档指针，不复制文档全文。**

默认一个**维护单元**（项目或独立工作流）一份；一个批次不自动生成新文档。只有并发维护需要不同入口、主题确实独立且有不同的完成标准时才新建。一个项目可有少量文档，但不能由“最近活跃事件”决定文件名或覆盖目标。

分六步：①成文协议与写入侧四段门；②显式归属及稳定文档 ID；③可编辑文档 + 锁/CAS/原子写；④与 2.7 合并为“结构化四段 + 指针 + 可恢复摘要”，并接入 2.8 Phase 0；⑤按节 RAG 与白板/面板解耦；⑥先审计存量、证明覆盖，再做可回滚的清理。

| 维度 | 当前 | R4 |
|---|---|---|
| 定位 | 每次会话的四段快照、append-only 语料 | 当前项目/批次事实、路线和接续入口 |
| 文件 | 每次 `handoff-<时间>.md` | `<语义文档名>-<首次创建时间>.md`，就地更新 |
| 历史 | 文件与检查点双份全文 | 文档只留当前；历史只在事件检查点，不另存归档 |
| 绑定 | 多数无 `eventId`，否则选最新 active | 显式文档 ID，关联一个或多个事件；不猜归属 |
| 正文 | 检查点 `text` 存全文 | 四段 + 当前源指针/指纹 + 短变更摘要；不存全文 |
| RAG | 检查点全文与账本文件重复 | 当前文档按选定节建独立来源，事件只供其自有信息 |
| 白板 | 同一采集/索引/开关混管 | 白板是事件投影；维护文档是人工/模型维护的跨事件叙述 |

### 0.2 关键事实纠正：log 与 handoff 不是同一条写入链

`appendHandoffCheckpointPre` 在 `lib/event-write.js:696-737` **已经解析账本四段并落 `goal/state/dead/next`**，`:722-737` 还记录了 2026-10-28 的修复。它不是“只存 memory_log 正文”。`event-store.json` 里 handoff 的 goal/state 约 93% 非空就是对应证据。

因此不能从 `log` 的四段低填充率直接推出“R4 的 handoff 检查点历史普遍不等价”。**log 规范化是 R4 依赖写入协议时的相邻改进，不是 handoff 改造的硬前置。** 也不能反过来说 handoff 已满足等价：四段缺项、额外章节、锚点/标题差异和 141 个空指针仍需处理。

## Q1：R4 的具体形态

### 1.1 从 CONSTRUCTION-PLAN 提炼什么

范本是 892 行的持续维护入口，而不是历史流水：前置“接续须知/一句话现状/环境快照/立即行动”；中间按批次列任务、落点、判据、依赖和状态；后接细节、文档索引与启动提示；末尾“维护约定”明确每完成一项、每批收工、判据变化、新增任务、裁定落定时该改哪里。历史内容只在其影响当前状态时保留，并明确指向替代它的当前表/提交；旧 BASELINE 标为历史快照，不混成当前事实。

R4 应复用这些**结构特征**，而不是复制 892 行的体量或把所有事件卡再展示一遍。

### 1.2 文档单位：维护单元，而非会话或自动批次

**建议默认每个工作区一个主维护文档，必要时每个独立维护主题一份。** 一个文档可挂多个 `eventIds`；批次是文档内可编辑的分节，不自动成为文件名或容器事件。

取舍：
- 每事件一份会让跨事件主线重新碎成大量小文档，违背 R4-5；
- 每批次一份仍会按批次反复新建，且“批次边界”没有可靠自动判据；
- 永远全工作区一份则并发争用、篇幅和无关主题混杂；
- 因而用调用方显式 `documentId` + 有明确完成标准的维护主题作为边界。项目主文档优先，独立主题按需建。

“依附事件”是关联与回链，不是按事件自动投影，也不要求虚构 `kind=project` 容器事件。若 2.6 后续提供项目容器事件，可作为其中一个关联，但不是本文档存在的前提。

### 1.3 文件路径、名称、冲突与排序

路径：`WS/handoff/documents/<slug>-<YYMMDD-HHMM>.md`。沿用记忆根，保证接续/面板可读；新目录使旧 lister 不意外吸收新文件。

> **★ 2026-11-10 用户裁定（命名简化，取代精确到秒）**：
> · 「精确到秒会让文件非常冗长」；「对于这种比较稳定的文件来说，有点不必要了」
> · 直接用 `20261110` 即可；**或去掉年份前两位 → `261110`**，再加「-多少时多少分」
> · **本文采用 `<slug>-<YYMMDD-HHMM>.md`**（例：`CONSTRUCTION-PLAN-261110-1223.md`）
> · 语义：时间戳只代表**首次创建**，永不因更新改名。这是稳定 sourceRef / RAG 来源 ID / 接续指针的前提。
>
> **分钟粒度的唯一性**：同一 slug + 同一分钟的**真正首建冲突**由 `create-only + 原子创建` 拒绝，返回现有文档让调用方确认；
> 不用 `-b/-c` 猜测是否同主题（旧 `-b` 是防覆盖，不是身份协议）。

- **时间戳只代表首次创建，永不因更新改名。** 这是稳定 sourceRef、RAG 来源 ID 与接续指针的前提。
- `title` 由调用方显式提供；无标题时优先用用户/维护主题名，不用 `kind` 自动生成，不把事件名当成充分依据；最后才允许 `HANDOFF-NOTES`。中文标题保留用于 H1，文件名 ASCII slug 默认从标题翻译/音译；无法确定语义 slug 时使用 `handoff-notes`，由调用方补名称。
- 同一工作区同名且同维护主题：`documentId` 指向同一份，不新建；同分钟不同主题由 slug 区分。真正相同 slug+分钟的首建由 `create-only + 原子创建` 判冲突，返回现有文档让调用方确认，**不以 `-b/-c` 猜测是否同主题**。旧 `-b` 是防覆盖，不是身份协议。
- 文档内保存 `documentId`（可为文件名去扩展名）、`createdAt`、`updatedAt`、`revision`；列表按 `updatedAt` 或目录 manifest 排序，绝不按字典序。
- 受影响不止 `listHandoffLedgers`：`findLatestGlobalHandoff`（5008-5024）、`readLatestHandoff`（5027-5045）、`_collectWhiteboardDocsPre`（5778-5802，含从固定列切日期）、`listHandoffLedgers`（5957-5960）、`handoffPanelData` 文件白名单/枚举（8892/8920-8926）、`searchHandoffCorpus` 调用、sidecar 标题/索引、一键接续和前端名称展示。新文档必须有独立 lister/索引，不通过放宽旧正则混进旧时间线。

### 1.3b 用户可见性（2026-11-10 用户追加诉求）

用户原话：「这个主要也是让用户可以看到的。比如咱们可以在侧边栏里留一个地方，让用户随时看到现在做这个事所维护的这一套内容。用户可以随时提问，比如我现在侧边栏开着相关的报告，然后向你实时回复。」

⇒ 维护文档**必须有面板/侧边栏入口**，不是只落盘：
- 入口展示「当前正在维护的这一套文档」（按维护单元分组，不按时间线罗列）
- 用户可**边看边提问**，模型实时回复当前文档内容
- 这与 §Q5「与 PLAN.md 的边界」一致：维护文档用独立页签/分组，不混进旧账本时间线
- **命名简化（上文 `<slug>-<YYMMDD-HHMM>.md`）正是为这个可见性服务**：文件名要让人一眼认出是哪份文档

### 1.5 相关文档与事件 members 的边界

链接区服务于**人/模型接续时的确定性下钻，以及 RAG 的来源关联**；事件 `members` 是“该事件使用了哪些来源”的结构化索引，二者互补。文档链接可指向多个事件共享的总表、设计、审计、代码、issue/PR；不要求为每个事件复制其 `members`，也不自动把所有 members 拼进文档。

格式为固定 `## 相关文档` + `ledger-links:v1` 标记；每项 Markdown 链接 + 简短关系说明。仓内文件用仓库相对 POSIX 路径；记忆文件用明确的 `handoff/...` 相对引用；外部 issue/PR 用 HTTPS；不允许 `file://` 和任意绝对路径被当成通用读权限。模型显式维护，工具校验路径格式/存在性并提示失效；可建议从事件 `members` 去重补候选，但不静默写入。RAG 仅把链接当来源元数据/可选扩展，不能未授权抓任意 URL。

## Q2：实时更新的技术实现

### 2.1 两种 append-only 必须分开

`lib/index.js:5373` 的“账本 append-only 语料”是旧产品/文件策略；`lib/event-store.js:10` 的检查点/约束只能追加是事件存储契约。`DESIGN-MEMORY-TOOL-CONTRACT-20261029.md` §2.2 约束的是 WAL 顺序和防污染，不要求 `.md` 永不编辑。故**文档可编辑、检查点保持 append-only**，不违反 P0-1 的意图；相反要避免坏内容先永久入事件。

### 2.2 新文档存储与保护

新增独立 `ledger-document-store`（名称建议）负责路径白名单、解析、首建、读取、更新、原子替换和目录 manifest。复用 `withSharedStateLock(documentPath, async ...)` 覆盖**整个读→CAS→校验→写→读回**临界区。它已有同主机死进程回收和超时，能用于跨进程互斥；但不能单独提供 CAS 或原子性。

当前 `writeHandoffLedger` 用 `writeFullRaw`，后者对非 CALENDAR 文件是普通 `writeFile`（13691-13700），不可沿用为就地覆盖实现。改为临时文件 + fsync/关闭 + rename 的 `writeTextAtomicPre`，并在锁内核对 revision。

- `memory_note(kind=handoff)` 新增 `documentId`、`title`、`eventId/eventIds`、`expectedRevision`；未给 documentId 的更新不得落到最近文档，返回候选或要求显式首建。
- 已存在文档必须携带 `expectedRevision`；首建必须 create-only。revision 取完整最终文档规范化 SHA-256，不复用会改变内容的旧文件名时间戳。
- H1-H4 质量门改为对**合并后的新文档**检查；增加固定节、唯一 documentId、事件 ID、链接格式校验。旧的 memory 锚点仅保留为 sidecar 兼容性元数据，不是文档历史。
- M1/P-H1/用户区门当前因 `target=handoff` 在 `lib/index.js:5872-5879` 显式不适用，而 PLAN 才有 M1 降级逻辑。**就地更新会消除这个前提**：需新增“用户保护区逐字保持、固定节不得丢、关联事件不得无意被清空、无新文档不得覆盖”的保护；不要直接套用 PLAN 卡片 M1。用户区若未提供则默认无，一旦标记存在即不可由普通模型更新删除。
- 工具读回成功后才更新 `state.latestHandoffText` 和索引；索引失败可重建但必须显式警示，不得回滚已成功正文。

### 2.3 WAL 三段的新职责

| 阶段 | R4 内容 |
|---|---|
| Phase 0 | 读取现有文档；验证归属/固定结构/四段/保护/CAS 可行性；2.8 的可预期错误在此拒绝，事件 +0 |
| Phase 1 | 向显式选定的一个或多个事件追加**规范四段 + sourceRef + 本次源指纹（若已有）+ 变更载荷（完整更新意图与规范四段）/幂等键**；不追加全文。每个关联事件同一 opId，不能猜最近 active |
| Phase 2 | 锁内复核 expectedRevision，原子写当前文档；记录最终 `revision/contentDigest`，读回一致 |
| Phase 3 | 意外 Phase 2 失败：追加紧凑失败标记 + **本次完整变更材料（结构化四段、被替换节的原文或全文，按恢复所需选择）**，sourceRef/attemptId 相同；可预期门拒绝不再入事件。恢复程序按 attemptId 幂等重放并验证目标 revision |

“摘要+指针”不是自动恢复：当前指针在更新前指向旧版本。故 Phase 1 必须包含足以完成本次变更的规范四段/变更载荷；短摘要不能冒充完整恢复材料。多事件写入须由同一 attemptId 记录部分成功并补偿，不能宣称多事件具有原子性，也不是复制全文。

## Q3：只保留最新与存量删除边界

### 3.1 新文档的正常更新

每次成功就地更新可覆盖旧版，不创建 `archive/`、备份文件或历史章节。安全来自 Phase 1 已落规范变更、Phase 2 CAS/原子写和 Phase 3 可恢复材料，而非保留旧 Markdown。崩溃时恢复工具只回放到当前文档，不形成长期归档。

### 3.2 “可删除”必须是逐条证明，不是统计推断

对每篇候选旧账本生成 `coverageReport`，只有全部满足才具备删除资格：

1. **身份**：确定映射到 `eventId + checkpointId`；不能只凭标题或日期。检查点 `at` 在文件创建窗口内，eventId（若有）相同，sourceRef（若有）规范化为该文件。
2. **规范等价**：以统一的“去除仅生成标题、`memory`/`type` 锚点、CRLF 归一化”后的文本为比较单位。优先检查点 text 与源文件规范化全文一致；若四段之外有额外章节，检查点必须也有这些节，不能只比四段。
3. **四段语义**：逐段比较非空事实。无失败必须区分“源明确无失败”和“缺字段”；goal/state/next 空白、正文有内容、额外节丢失均判不覆盖。不得用 1800 字渲染结果或截断后的注入文本作证明。
4. **绑定/时间线**：凡文档声称 eventId，检查点必须在同一事件；多事件引用必须分别存在。缺绑定不能自动认为最近 active 覆盖。
5. **报告持久化**：报告记录源 sha、检查点 id、规范化 sha、差异、判据版本；报告本身是审计元数据，不是旧正文归档。未通过或无法判定一律保留并人工分流。

现有 handoff 检查点含全文时，规范化全文是主要判据；未来只有指针/摘要的检查点**不能反向证明旧版正文已覆盖**。strict gate 遇到 hash 不一致、路径缺失或四段缺项即 fail-closed。

### 3.3 不能自动删的内容

- **523 篇 pre-WAL**（调查报告口径）：没有对应事件记录，禁止自动删；
- 检查点不存在、无可靠身份映射、正文/四段不一致、含未覆盖额外节的任何文件；
- 141 个无 sourceRef 的 handoff 检查点不能仅因数量相近就与文件配对；
- 降级/跨工作区兜底仍依赖的唯一文件、用户区/用户手工材料；
- PLAN、PLAN 归档、会话转写、sidecar 审计记录不属于本任务可删对象。

`log` 类只证明该日志正文存在，不证明账本被覆盖；330 条 log 的四段补齐也不能替代上述证明。事件头 sections 只有当前态，不能作为历史覆盖证明。

### 3.4 存量与恢复

建议分三组：A 类先跑严格覆盖证明；B 类中路线图由人/模型**显式选择并合并**到当前维护文档，其余按快照处理；水位垃圾若只是空骨架也仍需满足无独有正文才可清理。不要自动把 688 篇合成一份。

“不可归档”针对新版本历史；存量清理需一个**迁移期可逆保护**，与实时文档的永久归档不同。建议每次迁移前有工作区外/受控备份（默认文件系统快照或仓库备份），报告 sha 清单，先以只读 dry-run 和隔离副本完整验证；只有用户明确授权真实清理才删。恢复失败或报告不吻合即停止，原文件与索引原子恢复，事件 append-only 不篡改。若环境禁止任何额外历史副本，则本方案建议**不做存量物理删除**，只停止新增和移出普通视图/RAG。

## Q4：RAG 与 2.7 的统一方案

### 4.1 独立按节索引当前文档

把 `handoff/documents/*.md` 注册为 `kind=maintenance-doc` 的独立来源，每节一个 chunk：`documentId + sectionId + revision` 为身份；默认索引“接续须知/当前状态、立即行动、当前风险与未决、维护计划、相关文档”。四段中只选含跨事件路线、有效失败经验的段落；单事件重复四段不进入文档 chunk。全文可按需读取，**不把全文原样拼进每个事件语料**。

`textOfEventPre`（`lib/event-recall.js:45-61`）及 `index.js` 的对称实现仍消费事件自己的 name/summary/sections/规范检查点；不再把 handoff/plan 旧全文当成事件默认召回语料。它可返回 `sourceRefs` 让检索层关联当前文档，但不能递归重复展开同一文档。移除 `scope=all` 的最新账本重复 L0 项，保留维护文档作为单一来源命中；`scope=handoff` 增加 `maintenance` 语义而不是继续扫全部旧快照。

### 4.2 61.28% 应变成什么

该比例是当前**事件召回拼接字符**中 plan+handoff 全文占比，不是价值或质量指标。R4 的目标不是拍一个新百分比，而是：新文档 chunk 不重复入多个事件；同一正文在一份召回结果最多出现一次；总字符随当前文档数而非历史写入数增长；在冻结真实 query 集上 A/B，事件命中率不低于基线的 95% 且关键接续事实/失败原因召回不下降。

为预算规划可设**事件默认拼接语料中维护文档引用/摘要 0～5%**，独立文档库按 query 单独取 top-k，不受 61% 继承。全文 0 份进事件，指针只有几十字符；文档自身在独立 RAG 中的占比不设硬目标。5% 是初始预算而非实测最优，必须经 2.7 的 A/B 校准。

### 4.3 与 2.7 不打架

事件检查点是“当时规范写了什么/何时发生”的紧凑可恢复记录；文档 RAG 是“现在维护的结论是什么”。两者不是同一读取方向。旧全文检查点不篡改、可标 legacy；新 handoff 不再全文进事件，由独立文档来源提供当前摘要。Phase 1 不含全文时仍可恢复本次变更，RAG 质量由按节索引而不是复制历史全文维持。

## Q5：与 PLAN.md 的边界

| 对象 | 真源/维护者 | 内容 | 更新 |
|---|---|---|---|
| PLAN.md | 事件库投影（fromEvents） | 多事件并列的当前全貌，sections 等 | 事件变化后自动重绘 |
| 维护文档 | 模型/用户通过文档 API | 跨事件决策、路线、执行顺序、相关文档与接续第一步 | 实质变化时编辑当前文档 |
| 事件/检查点 | append-only 事件库 | 单事件四段当前态与规范历史 | append/set 按既有权限 |

依附不等于投影：文档带 `eventIds` 供归属、反链、RAG 关联，但不能由这些事件自动重新生成。事件卡不自动复制到维护计划；白板不读维护文档作为真源。若一条“下一步”纯属单事件，应该只写事件 sections；跨事件的排序/依赖/取舍才进文档。重复检测以段落 fingerprint + eventId 提示维护者删减，不靠相同内容再次生成。

读侧与 UI 也应分开：`_collectWhiteboardDocsPre` 不读新文档；新文档用独立索引、页签/分组。`handoffEnabled` 目前同时控制 PLAN 与账本读写（970-986），保留为兼容总开关，但新增内部 `maintenanceDocsEnabled` 读路径/回退前须明确配置迁移，不能静默把关闭白板变成删除文档。可在过渡期共用总开关，长期以两个能力开关明确边界。

## Q6：排期、2.6/2.7/2.8 与落地

### 6.1 对已有排期逐项表态

- **1a：拆分并提前“维护文档四段规范”，不直接把所有 log 强套四段。** 同一文案可以共享写作规范，但代码与提示必须分对象：`maintenance-doc/handoff` 要有 goal/state/dead/next（dead 可显式“无已确认失败”，其余不允许空泛占位），`log` 仍是正文原料；需要结构化事实时走 progress/state/deadend 或 memory_event append。log 若需要四段，必须新增显式 `sections/quad` 参数，不可从散文猜。历史 log 不应自动回填；266/330 等存量数字也不应成为猜测来源。
- **1b：不提前，保持渲染侧工作。** 它不能解决写入缺失；可与统一接口并行，但 R4 验收用持久化检查点，不用渲染输出。
- **1c：不提前为 R4 前置，按计划做注入闭环。** 它解决注入保真，不是写入完整性；文档按节注入后应复用其总量计费/不丢尾部的成果。
- **5.1：拆分。** `5.1-W`（写入侧结构规范、显式空值、文档/检查点职责、回执验证）前置到第 1 步；`5.1-P`（跳过条件、终止位、合并条目、总长、过期注释、真实执行顺序）留在批次 5。后者仍必要，因为写作内容合格不等于提示词调度正确。必须新增实际写入适配器/校验作为 **R4-W0**，不能声称仅靠提前一条铭文就完成。

### 6.2 与 2.6/2.7/2.8 的合并与顺序

不建议照搬旧 R2 的 L 线，但“2.7 与文档 WAL 同一事务合并”仍成立，理由是新稳定路径消除时间戳占位 hack，且全文→指针会影响 Phase 1/3 和 RAG。

1. **R4-W0 + 2.6 协议/API**：显式 documentId/eventIds、归属不猜测、四段写入与恢复协议、共享 API 骨架。2.6 是接口前置，但不是自动主题门。
2. **文档 upsert**：稳定路径、锁/CAS/原子写/保护和清单；可在真实开关默认关闭的隔离夹具实现。
3. **2.7 + R4 WAL 同批**：规范四段、sourceRef/digest、恢复载荷，按节 RAG 回读。旧全文不动。
4. **2.8 Phase 0 同批联验**：必须在首次启用新 WAL 前，对新 CAS/结构/归属失败 +0 检查点；意外错误仍留可恢复记录。2.8 的通用失败清单可随后扩展，不阻塞文档特有预检。
5. **RAG/白板/UI 解耦**：新 kind 语义稳定后再切换，保留旧 legacy 可读；A/B 验收。
6. **存量审计与可逆清理**：不与新写入口同时盲迁；只有覆盖报告全部通过、备份/回滚演练成功才执行。

## 7. 分步实施计划（供实施者执行，不是本轮已做）

| 步 | 改什么 | 验收判据（含负路径） | 回滚点 | 主要风险 |
|---|---|---|---|---|
| 1. 协议与写入门 | 文档 v1 schema、固定节/链接区、事件关联、检查点 payload 规范、恢复协议；拆 5.1-W | 四段实际落盘并可读回；缺 goal/state/next 或非法关联拒绝；log 不被强改；渲染文本不参与验收 | 仅文档/接口与 flag，无生产写入 | 把 prompt 当成写入保证；把 log 当 handoff |
| 2. 2.6 显式身份 | memory_note 增 documentId/title/eventIds/expectedRevision；统一归属 API | 指定多事件均收到同一 opId 引用；无 ID 不自动选最新 active；旧调用在 legacy flag 下不变 | 关闭新入口 | 自动错误关联；事件/文档 ID 混淆 |
| 3. 文档 upsert | 新存储、锁内 CAS、原子写、读回、固定结构/用户区保护、manifest/新 lister | 连续 100 次更新文件数不变；两写者一成功一 conflict，无静默覆盖；kill/写失败无半截文件；首建同秒冲突不覆盖；路径白名单抗越界 | 关闭 upsert，旧文件 untouched | 锁不足、非原子 writeFile、 revision 口径漂移 |
| 4. 2.7+2.8 WAL | Phase 0/1/2/3 紧凑 payload、恢复材料、摘要+指针和回读 | 成功检查点无文档全文；指针/指纹读回当前版本；CAS/结构错事件 +0；意外失败能从变更材料恢复到精确 revision，重放不重复 | 关闭新 WAL，恢复旧实现仅用于新数据须保留兼容 | 指针指向旧版、摘要不足以恢复、多事件部分成功 |
| 5. RAG/白板/UI | maintenance-doc 按节索引；事件语料去全文；去 L0 重复；独立面板/lister；新预算联验 | 相同正文单次出现；冻结 query 集 ≥95% 事件命中基线且关键事实无退化；全文可按需读；PLAN 不读维护文档；新旧文件排序正确 | 切回 legacy 只读索引，不恢复双写全文 | 召回质量下降、链接扩展重复、前端漏新文件名 |
| 6. 存量审计/清理 | 只读报告→隔离迁移演练→明确授权的最小批次清理 | 688 个全量盘点；每删 1 个有 coverage 证明；sha/索引/回滚演练通过；任何不确定即保留 | 受控备份 + manifest + 原子恢复；事件不改历史 | pre-WAL 唯一记录、规范化误删、额外章节丢失 |

迁移期间默认双读、不双写全文：新维护文档优先；旧账本作为 legacy 只读兜底。切换时先冻结旧写入、取快照、完成审计，再让新写入单独接管；回滚不得重新把新文档每次更新复制成快照。

## 8. 诚实边界

- **本轮实测**：688/687 文件及字节；事件/检查点数量和 kind 分布；handoff 四段填充与 sourceRef；active sections；index/event-store 文件大小；源码中的写入、渲染、注入、锁、正则和 append-only 差异。
- **复核历史脚本结果，未逐一重跑所有统计**：56 天、相邻复用率、25 份 B 类抽样、523 篇 pre-WAL、2,848 卡片、61.28% 语料占比。它们来自 2026-11-10 调查脚本/数据，本方案保留其原始口径，不当作今日以后固定值。
- **设计推理**：维护单元默认值、目录和 schema、RAG 0～5% 初始事件引用预算、恢复协议、多事件引用策略、迁移顺序。均需实现后真跑验收。
- **未验证**：真实模型是否会按新提示维护而非新建；真实 query A/B；跨进程故障注入下新存储；多事件部分 append 的最优事务补偿；存量 688 篇逐篇覆盖映射。因此没有授权任何自动删除。
- **数据时点**：本轮真实 store 已比任务书多 10 条检查点；所有数量应随实施重新冻结，不以旧文档中的固定值作为删除依据。
