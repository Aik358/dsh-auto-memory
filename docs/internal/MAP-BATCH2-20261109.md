## 3. 【重点】2.4 的实际危险度：细则低估了

### 3.1 细则已发现的三处越界写（**全部属实**）

| # | 缺陷 | 后果 |
|---|---|---|
| D-1 | 新事件被塞 `memberLedgers` / `origin` / `createdBy` 三个非法顶层键 | `validateEventPre` 判 `unknown:*` ⇒ **写前校验抛错** |
| D-2 | 旧事件被改成 `status:'archived'`（**不在枚举** `active/paused/closed`）+ `archivedAt` / `archivedBy` | `bad-status` + `unknown:*` ⇒ **抛出** |
| D-3 | 新事件 `checkpoints` 恒为 0，旧检查点不迁移 | 归并后碎片原有检查点**无处可去** |

### 3.2 细则**没写到的第四处**：归档范围失控

`event-regroup-apply.js:191-198` 逐字：

```js
for (const ev of next.events) {
  if (ev && String(ev.status) === 'active') {   // ← 只判 active，不判「是否本次归并对象」
    ev.status = 'archived'
    ...
  }
}
```

**它遍历的是全库 `next.events`，条件只有「status === 'active'」** —— 没有任何「只处理提案里点名的碎片」的过滤。

⇒ 实测后果：**47 个 active 全部被归档**，其中
- 只有 **23 个**是应该归并的碎片（共 31 条检查点）
- 另外 **24 个**是本项目的主力事件（共 **615 条检查点**，含「记忆系统大修施工总表」「注入层审计」等），**会被一并归档**

**这比细则写的「46 个 active 全部不可再写」还要严重一层**：细则把它归因为「坏状态值导致校验失败」，
实际是**范围本身就不对** —— 即使 D-2 的枚举问题修好、改成合法值 `closed`，这 24 个非碎片事件**照样会被错误归档**。

### 3.3 修复这处需要的额外判据

`applyRegroupPre` 必须**只归档提案里点名的成员**，判据应是：

```
归档范围 = proposal.proposedGroups[*].members 里出现的 sourceRef（账本文件名）
          ∪  显式传入的 archiveIds（如有）
而不是「全库 active」
```

并且要加一条**守恒断言**：`归档数 === 提案覆盖的碎片数`，不等即中止（不落盘）。

## 10. 【续研】批次 2 到底是干什么的，以及它的真实地位

> 用户追问：「这个第二项到底是用来干什么的？在这个修复之间占什么地位？为什么你说现在会有很多风险？」
> 本节是对该追问的回答，全部数据本机实测。

### 10.1 它解决的是什么问题：一件事被拆成 N 个事件

这个插件的记忆模型是：**事件 = 一件事，跨天可中断再捡起**。白板、事件卡、注入面都按事件组织。
所以「同一个任务产生 20 个事件」不是整洁度问题，是**功能性损坏**：

| 受损面 | 具体后果 |
|---|---|
| 白板 | 51 行「当前状态」里 20 行是同一件事的不同片段，真正的主线（如施工总表）被挤到看不见 |
| 事件卡 | 注入面只能显示 2 张卡，而其中一张可能是「task-38 完成并提交 f1c46a31」这种**一句话流水** |
| 检索 | 搜「#557」会命中 3 个不同事件，模型无法判断哪条是主线 |
| 四段 | 碎片事件的 sections 全空 ⇒ 渲染出来是空壳 |

**批次 2 的 5 项，其实是同一条链的 5 段**：

```
① 新事件别再空着（2.1 填 goal、2.2 判 kind）   ← 治「产生」
② 让工具能看出哪些该合并（2.3 只读提案）        ← 治「识别」
③ 把该合的合掉（2.4 落盘归并）                  ← 治「存量」
④ 让白板跟上事件（2.5 自动重绘）                ← 治「呈现」
```

缺任何一段，链条都断：只做 2.1/2.2 → 存量碎片永远躺在那；只做 2.4 → 新碎片继续产生，白改。

### 10.2 【关键新发现】碎片化**已经停止了** —— 1.4 把它治住了

我按 `createdAt` 统计了全部 52 个事件：

| 日期 | 新建事件数 |
|---|---|
| 2026-10-27 | 9 |
| 2026-11-05 | 3 |
| 2026-11-06 | 7 |
| **2026-11-07** | **23** ← 碎片大爆发日 |
| 2026-11-08 | 3 |
| **2026-11-09** | **1**（还是我自己的测试事件 `evt_7bf3ec29`，已 close） |

23 个碎片的创建日分布：**11-05 两个 / 11-07 十九个 / 11-08 两个 / 11-09 零个**。

再往前一步看**写入有没有散开**：11-09 当天全库新增 51 条检查点，**全部落在 1 个事件上**（`evt_23e2976e`，施工总表）。

> 这一条很重要：批次 1B 的 **1.4（L1 标识层 + 强负证据 + 词袋兜底）就是专门治碎片化的**。

> 换句话说：**「产生碎片」这个源头已经被批次 1 关掉了。**

### 10.3 那么 2.1 / 2.2 还有用吗？有，但性质变了

它们不再是「止血」，而是**质量提升**：

| 项 | 治什么 | 与碎片化的关系 |
|---|---|---|
| 2.1 填 goal | 新建事件的**四段首段为空**（现 29/52 个事件四段全空） | 不治碎片，治「事件建出来了但没内容」 |
| 2.2 判 kind | 全部落在 `unknown`（现 32/52 个） | 不治碎片，治「事件卡上的徽章全是未知」 |

**它们对存量 47 个 active 事件零作用**（只影响新建），这一点我在上一版报告里说过，需要再强调一次：
**修完 2.1/2.2，你打开面板看到的仍然是 32 个 unknown、29 个四段全空。**

### 10.4 2.4 的风险到底是哪些（逐条量化）

上一版说「比细则更危险」，这里给出**完整的三层风险**：

**第一层：范围失控（我新发现的第四处缺陷，细则没有）**

`event-regroup-apply.js:191-198` 只判 `status === 'active'`，不判「是不是本次归并对象」。
实测后果：**47 个 active 全被归档**，而真正该合并的碎片只有 23 个、只承载 **31 条检查点**。

**第二层：数据集中度极高 ⇒ 误伤代价不对称**

| 排名 | 事件 | 检查点 |
|---|---|---|
| 1 | GitHub issue 三录/修复编排 | **199** |
| 2 | 项目白板 | **160** |
| 3 | alpha.7 施工批次 | **61** |
| 4 | 记忆系统大修施工总表 | 59 |
| 5 | 白板前端映射层修复 | 57 |

**前 3 个事件承载 64.9% 的检查点，前 8 个承载 88.6%。**

⇒ 风险不对称到什么程度：**为了归并 31 条检查点（碎片），可能毁掉 647 条里的大部分**。
这两个数字差 **20 倍**。这就是我说「有很多风险」的核心量化依据。

**第三层：不可逆 + 静默**

- `applyRegroupPre` 会先做快照（`snapshotStorePre`），回滚函数也有 —— 但**回滚需要人手动调用**，不是自动的；
- D-2 的坏状态值会让后续 `memory_log` **直接抛错**（不是静默丢数据），这一点反而算安全网；
- 真正危险的是 D-3：**检查点不迁移**。碎片那 31 条检查点在归并后会留在旧事件里（旧事件只是被标坏状态），
  看起来「数据还在」，但新事件是空的 ⇒ **归并了个寂寞**。

### 10.5 它在整个大修里占什么地位

```
批次 1（止血）        ✅ 已完成 —— 把「产生碎片」的源头关了（1.4）
   ↓
批次 2（碎片完整修复） ← 现在这里。**唯一目的是收拾批次 1 之前留下的烂账**
   ↓
批次 3（投递预算）     依赖 2.5 的白板投影才能谈「投递什么」
   ↓
批次 5（铭文重写）     依赖 2.x 让事件本身有内容可写
```

**一句话定位**：批次 2 是**清历史欠账**，不是解决当下问题。
当下的问题（碎片继续产生）已经被批次 1 解决了。

⇒ 这直接导出一个我之前没说清的判断：

> **2.1 / 2.2 / 2.3 值得做**（提升质量、零风险、能立刻看到效果）；
> **2.4 是一个「可做可不做」的清账动作**，收益是 23 个碎片变少、面板更清爽，
> 代价是一次不可逆的批量写。**当前 47 个事件的面板并没有因为碎片而瘫痪**，
> 所以 2.4 的紧迫性远低于细则给的排序。

### 10.6 修正上一版报告的一处判断

上一版 §5 把 2.4 排在 2.3 之后、2.5 之前，默认它是必须做的。
**基于 §10.2 的新数据，这个排序需要修正**：2.4 应该改成「条件触发」——
只有当 ①面板确实被碎片淹没，或 ②用户希望面板只显示少数主线事件 时才做。
否则可以先做 2.1/2.2/2.3/2.5，把 2.4 挂起。
