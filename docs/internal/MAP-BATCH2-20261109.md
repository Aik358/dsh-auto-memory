## 3. 【重点】2.4 的实际危险度：细则低估了

### 3.1 细则已发现的三处越界写（**全部属实**）

| # | 缺陷 | 后果 |
|---|---|---|
| D-1 | 新事件被塞 `memberLedgers` / `origin` / `createdBy` 三个非法顶层键 | `validateEventPre` 判 `unknown:*` ⇒ **写前校验抛错** |
| D-2 | 旧事件被改成 `status:'archived'`（**不在枚举** `active/paused/closed`）+ `archivedAt` / `archivedBy` | `bad-status` + `unknown:*` ⇒ **抛出** |
| D-3 | 新事件 `checkpoints` 恒为 0，旧检查点不迁移 | 归并后碎片原有检查点**无处可去** |

### 3.2 细则**没写到的第四处**：归档范围失控

`event-regroup-apply.js:191-198` 逐字：

```js
for (const ev of next.events) {
  if (ev && String(ev.status) === 'active') {   // ← 只判 active，不判「是否本次归并对象」
    ev.status = 'archived'
    ...
  }
}
```

**它遍历的是全库 `next.events`，条件只有「status === 'active'」** —— 没有任何「只处理提案里点名的碎片」的过滤。

⇒ 实测后果：**47 个 active 全部被归档**，其中
- 只有 **23 个**是应该归并的碎片（共 31 条检查点）
- 另外 **24 个**是本项目的主力事件（共 **615 条检查点**，含「记忆系统大修施工总表」「注入层审计」等），**会被一并归档**

**这比细则写的「46 个 active 全部不可再写」还要严重一层**：细则把它归因为「坏状态值导致校验失败」，
实际是**范围本身就不对** —— 即使 D-2 的枚举问题修好、改成合法值 `closed`，这 24 个非碎片事件**照样会被错误归档**。

### 3.3 修复这处需要的额外判据

`applyRegroupPre` 必须**只归档提案里点名的成员**，判据应是：

```
归档范围 = proposal.proposedGroups[*].members 里出现的 sourceRef（账本文件名）
          ∪  显式传入的 archiveIds（如有）
而不是「全库 active」
```

并且要加一条**守恒断言**：`归档数 === 提案覆盖的碎片数`，不等即中止（不落盘）。

**这说明什么（关键的坏消息）**：

`smoke-test-v5-p6-r6-regroup-apply` 有 40 条断言、全部通过，**却完全没抓到 §3 那四处缺陷**。
这属于项目规约里明确列过的「覆盖假象」第 ③ 类 —— **缺陷会被现有套件钉成绿**。

具体可能是：
- 套件用的是**自造的 store 夹具**（事件少、字段全），而不是真实形态的库；
- 断言停在「函数返回 ok」层，没有对**落盘后的事件**跑 `validateEventPre`；
- 没有一条断言检查「归档范围是否 == 提案成员」。

⇒ **2.4-前置的验收不能靠这 4 个套件**，必须新写「落盘后再校验 + 范围守恒」的断言，
并且**用真实 store 的副本**做夹具（而不是理想化小样本）。
