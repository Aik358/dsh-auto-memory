## 0 · 用户的设计意图（判据基准）

1. **user full 不该每轮注入**。只在三时机注入：①会话首轮 ②上下文压缩后 ③压缩水位到 **25%** 与 **50%** 时「人说话的下一轮次」。
2. **full 档不设注入量上限，或上限极大**。
3. **其他时候注入的都是 user slim**（精简、可裁剪）。

### 1.1 我原定的判据被证伪

我曾要求「full/slim 重叠率 > 80% 即区分度不足」。实测：全帧 24,393 字符 vs 精简帧 2,219，**行重叠 2.68% / 字符 1.67%** ⇒ 帧级不成立。

真正重复的是**档内**：`human_full` vs `handoff_carry` **sha256 完全一致**；`human_full` vs `post_compact` 100% 行 / 98.01% 字符；两档精简帧 90% 字符。
⇒ 判据应改为「**同档不同来源**之间不得逐字节相同」，而不是「全帧 vs 精简帧」。

## 3 · 每批的验收判据（CR-10）

- **H1**：真跑注入装配套件，断言水位命中分支**不再抛 ReferenceError**；负路径：把声明改回 try 内 ⇒ 断言必红。
- **H4**：构造「刚压缩完」的会话状态，断言下一轮拿到全帧；负路径：未压缩时不得给全帧。
- **H2+H3**：模拟 10 个连续真人 turn，断言 FULL 只出现在首轮与水位命中轮，其余为 SLIM（当前实测是 FULL=10）。
- **H5**：断言精简帧里 user 侧字符数 **> 0** 且含规则摘要（当前为 0）。
- **H6**：断言 user-memory 注入长度 ≈ 源长度（当前 5.64%）。
- **H7**：断言帧内不含「超预算线」字样。
- **H8**：删掉任一模块级判据 ⇒ 注入行为必须改变（证明它真被消费）。
- **H9**：断言 `human_full` / `post_compact` / `handoff_carry` 三者 sha256 **两两不同**。

## 4 · 风险

- H1 是「一行修复改变全局行为」的典型：修好后水位钩子立刻开始工作 ⇒ 用户会**突然**在 25%/50% 收到全帧。需先确认这是期望行为（按用户意图是）。
- H6 解除腰斩会让单轮注入体积显著上升（user-memory 从 1,529 → 最高 27,102 字符），需评估对上下文预算与费用的影响。
- H2+H3 改动注入节奏，属高风险区（本仓历史上多次因注入时序出事故），必须逐条变异验证。

## 5 · 四档扩展调查（2026-11-03 第二轮，依据 `INVESTIGATE-TIERS-FULL-20261103.md`）

### 5.1 事实修正（推翻本文 §1 的过宽表述）

- 原表述「`human_slim`/`run_slim` 在帧渲染器不可达」**范围过宽**。实测：四档在生产**全部可达**，但分两种形态 ——
  `user_full`/`run_full` 由全帧渲染器 `renderMemoryDynamic` 产出；`user_slim`/`run_slim` **只以「精简帧」形态可达**（`renderSlimSnapshotPre`，2,219 / 1,999 字符）。
- 具体不可达的只是「`*_slim` 作为**全帧内容档**」：降级发生在全帧渲染**之后** ⇒ 规则摘要 4,189 / 白板核心节 1,884 / 不投画像这一整套在 `renderMemoryDynamic` 内是死代码（仅测试态可强制）。
- 方向结论不变，但**归因口径已订正**：不是「档位不可达」，而是「档位到不了全帧渲染器」。

### 5.2 枚举与消费（实际 8 个键，不是 4 档）

- 档位键：LEGACY + 7 个功能档。判定函数 5 个，其中 **3 个生产消费为 0**（`isRulesFullTierPre`/`planSpecForTierPre`/`isHumanTierPre`），生产用的是函数体内的**内联副本**（L11129 / L11217 / L11176 / L11561）⇒ 与 §H8「判据收敛」同一根因，**改一处必须同批改内联副本**。
- `renderRulesSlimPre`（模块级）生产消费同样为 0，生产走 `_renderRulesSlimInline`（L11176）。

### 5.3 两两区分度（生产形态，6 对全部 sha 不同 ⇒ 判据 PASS）
