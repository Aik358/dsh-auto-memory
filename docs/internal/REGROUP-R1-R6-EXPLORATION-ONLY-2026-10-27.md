## 为什么这条路没走通（实测数据）

### 决定性证据：机械分组在真实数据上**零覆盖**

```
本工作区 587 篇账本：
  目标段非空        572 篇
  目标段去重后      565 种写法（平均每种 1.0 篇）
  机械判据「目标段首行完全相同」 ⇒  0 命中
  机械覆盖率        0 / 587 = **0.0%**
```

根因：每篇账本的目标段都是**独立撰写的自然语言**，措辞各不相同。
（实测原型 `event-plan.tsv` 是**人工逐条写的 127 行清单**，不是机械算出来的。）

### 次生问题

1. **上下文装不下**：587 篇全文 ≈ 124 万字符 ≈ 100 万 token，单个子代理读不完。
2. **人审环节不可接受**：用户裁定「老用户升级不想费心订正记忆」⇒ 不能要求人读 TSV。
3. **AI 直接产 JSON 事件难审计**：185 个 JSON 事件人不愿意逐条读，TSV 清单反而好审。

## 后来怎么解决的

改**提示词**（`lib/migration-prompt.js` v3 → v4），而不是加模块：

| v4 提示词补的 | 对应本批的哪个能力 |
|---|---|
| 三类产物分开处理（机械产物按日期归桶） | 替代了 R1 的「机械分组建议」 |
| 精读 + 跳读三步法（单次 read ≤8,000 字符） | 替代了 R2 的「分批 + prompt 构造」 |
| 事件名质量闸门（写进提示词） | 复用 R1 的闸门**规则**（但用提示词实现） |
| 阶段 5 自检 9「账本守恒」 | 等价于 R1 的 `validateRegroupConservationPre` |
| 子代理自己 `memory_event(action:create)` | 替代了 R3 + R6 的解析与落盘 |

★ 结论：**能力需求是真的，但实现方式选错了。**
  提示词路线更简单（0 新模块）、更可审计（人能读）、更符合「全自动」要求。
