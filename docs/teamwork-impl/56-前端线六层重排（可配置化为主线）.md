# 56 · 前端线六层重排（★可配置化是主线，不是末节）

> 生成 2026-09-27 ｜ 依据：用户口头澄清 + 23 卷 L21/L112 原文 + 28 卷 §3 schema 草案
> **本卷修正 55 卷的根本错误**：把「客户可配置化」当成收尾工作，实际它是**主线**。

---

## 〇、我错在哪（附原文，不是辩解）

我把「取值层」理解成「把 223 个颜色换成变量」——机械活，所以给了 15%。
但用户原话（23 卷 L21 逐字）是：

> 「用户要『**更换所有元素的位置、设置哪个页面出现哪些内容**、背景图、banner』⇒ 这是**布局可配置化**，不是皮肤换色」

同卷 L112 进一步定义：

> 「用户要的『换元素位置 / 某页出现哪些内容』＝ **区域顺序 ＋ 插槽开关的数据驱动**」

⇒ 这块的目标**不是「我们好改」，是「客户能改」**。验收尺也不一样：

| 我上一版以为的尺 | 真正的尺 |
|---|---|
| 改了颜色后视觉不变 | **客户改一个配置文件，界面按他的意思重排** |
| 代码里颜色都走变量 | **客户不必看代码、不必找我们，自己就能换** |

## 一、★现状实测（这块从零开始）

| 项 | 实测 | 含义 |
|---|---|---|
| 内部页签（＝客户说的「屏」） | **13 个** | `MEMORY_TABS()`：overview / logs / refine / hub / storage / notes / plan / reflections / connect / calendar / search / workspaces / stats |
| `data-dam-page` | 62 次 | 只有「页」级锚点 |
| `data-dam-region` | **0 次** | ❌ 区域层不存在 |
| `data-dam-slot` | **0 次** | ❌ 插槽层不存在 |
| `data-dam-block` | **0 次** | ❌ 块层不存在 |
| 布局配置键 | 仅 3 处痕迹 | ❌ 无客户可改的配置系统 |
| `assetOf` / `SKIN_ASSETS` | 0 / 0 | ❌ 素材通路未接 |

**⇒ 结论：客户可配置化的三层锚点全部为 0，整套配置系统不存在。**

## 二、★28 卷已有 schema 草案（不是新设计，是既有资产）

28 卷 §3 已给出**完整可用的草案**，我上一版没把它当主线：

| 项 | 规模 |
|---|---|
| region（区域） | **7 个** |
| slot（插槽） | **18 个** |
| blockKind（块类型） | **10 种** |
| authorSurface（客户操作面） | **5 项** |

**客户能做的 5 件事**（全部是 CSS/属性层面，不需要 JS）：

| # | 能做什么 | 怎么做 |
|---|---|---|
| 1 | 改区域**排版顺序** | 覆写 `order` |
| 2 | 改区域**尺寸** | 覆写 `--dam-region-w/h/min` |
| 3 | **隐藏/显示**某个区域或插槽 | `display:none` |
| 4 | 改块**外观/图片** | 覆写 token + 背景图 |
| 5 | 换**背景图 / banner** | 素材槽位 |

**客户不能做**（业务逻辑，永不由客户承担）：改数据来源、改交互行为、改 API 路径、改渲染分支。

## 三、★配置形态：配置文件（用户裁定 B）

用户裁定：**「给个配置文件让客户自己编辑」**（不做设置界面）。

这决定了工作量分布：**重在 schema 设计 + 校验 + 容错，不在界面**。

| 要做 | 为什么 |
|---|---|
| schema 定义（region/slot/block 清单） | 客户要知道能改什么、名字叫什么 |
| 读取 + 校验 + 默认值合并 | **客户改错了不能崩** |
| 容错：未知键 / 缺键 / 类型错 | fail-safe，不是 fail-closed |
| 示例配置 + 注释 | 客户得看得懂 |
| 文档：每个键管什么 | 客户得查得到 |

**验收判据（可复算）**：
- 正路径：删掉配置文件 ⇒ 界面与默认完全一致
- 正路径：改一个 region 的 order ⇒ 该区域换位置，其余不动
- 负路径：配置写了不存在的 region 名 ⇒ **不崩**，忽略该项并留一行告警
- 负路径：配置文件 JSON 语法错误 ⇒ **不崩**，回落默认布局

## 四、★六层重排（客户可配置化升为主线）

| 序 | 层名 | 做什么 | 权重 |
|---|---|---|---|
| 一 | **配置层** | 配置文件 schema + 读取 + 校验 + 容错 + 示例 | 10% |
| 二 | **结构层** | 13 屏 × 区域/插槽/块**三层锚点**（region 7 / slot 18 / block 10） | **25%** |
| 三 | **外观层** | 颜色/字体/圆角 token 化 + 素材槽位（客户换 logo 色、换图） | 20% |
| 四 | **看板层** | 按 v4 图重做时间轴界面（含去重与分组） | 20% |
| 五 | **团队层** | 团队页签 + 归属徽标 + 10 条 team 路由接线 | 15% |
| 六 | **皮肤层** | 6 图槽位 + 占位样式 | 10% |

**为什么这样排**：
- **结构层 25%**：13 个屏要逐个打三层锚点，从 0 到 13×N；这是客户排序/显隐的前提
- **外观层 20%**：含 token 化（223 色值）+ 素材通路，是客户换 logo 色的前提
- **配置层 10%**：是前两层的入口，但**必须在结构层之前定 schema**（否则锚点白打）
- 看板层从 30% 降到 20%：它仍是重头，但不再是唯一大头

**依赖方向（不可颠倒）**：

```
配置层（schema 定义）
    ↓ 必须先定
结构层（打锚点）+ 外观层（token 化）
    ↓ 客户才能改
配置层（读取/校验/容错落地）
    ↓
看板层 / 团队层 / 皮肤层（在结构上渲染）
```
