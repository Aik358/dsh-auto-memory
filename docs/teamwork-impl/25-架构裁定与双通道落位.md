## 2. ★Lead 补充的三点

（用户说「有想补充的意见也可以随时打断」，故据实写出三条，其中第一条可能让方案更省事。）

### 补充一：三档不是两档 —— 大部分「涉密客户」其实还是 S3

这是**最省事的一点**。很多人以为「涉密 = 得自己写服务端」，其实内网自建的对象存储（**MinIO**、Ceph RGW、华为云 Stack 的 OBS）**也是 S3 兼容的**。

| 档 | 场景 | 用什么 | 代码要改吗 |
|---|---|---|---|
| **T0 默认** | 一般企业 | 公有云 S3（阿里云 OSS / 腾讯云 COS / 华为云 OBS / AWS / GCS） | — |
| **T1 涉密常见** | 内网部署、不上公网 | **内网自建 MinIO / Ceph**（仍是 S3） | ✅ **零改动**，只换 endpoint |
| **T2 极端** | 客户要求「必须有服务端做审计/审批」，或连对象存储都不给开 | 自建 HTTP 服务端（transport=http） | ❌ 需要额外工作 |

> **⇒ 建议：把「自建服务端」的定位收紧为「T2 极端场景的兜底」，而不是「涉密客户的默认选择」。**
> 因为 T1（内网 MinIO）已覆盖绝大多数涉密场景，而它**不需要任何额外代码**。
> 收益：T2 的工程量**不需要现在投入**，只保留接口位即可。

### 补充二：双通道**绝不能写成两套代码**

白皮书既有判据：**「凡有两个可独立影响同一行为的输入，即未真正合并。」**
> 反过来同样成立：**同一条同步语义，不得有两份实现。**

**正确做法：一个传输接缝（transport seam），两个后端。**

```
   同步语义层（队列 / 冲突判定 / 日历双轨 / 注入仲裁）  ← 全部与通道无关，一行不改
                        ↓  只依赖这一份接口
   ┌──────────────────────────────────────────────┐
   │  transport 接缝： put(key,val) / get(key) / list()  │
   └──────────────────────────────────────────────┘
        ↓ 后端 A                      ↓ 后端 B
   S3 兼容（含 MinIO）          自建 HTTP 服务端
```

**纪律（可断言）**：
1. 同步语义层（`team-outbox` / `team-merge` / `team-calendar` / `team-inject` / `team-board` / `team-derived`）**不得**出现任何通道判断分支（形如 `if transport === ...`）。
2. 通道差异**只允许**存在于接缝实现内部。
3. **必须有一致性测试**：同一组操作分别跑两个后端，断言产出**相同**。否则两条通道就是两套系统。

### 补充三：T2 通道必须**显式标注「未验证」**，不许当第二真源

> ⚠️ **CR-9 追加**：T2 的**安全红线不因「测试用途」而放松** —— 涉密场景下「以为走内网、实际走公网」是安全事故级。若要测试，测的是 **S3 通道**（见 [26 卷](26-测试方案与三处混淆纠正.md)），**不是 T2**。

这是工程诚实问题。T2（HTTP 自建服务端）若**只留接口不实现/不验证**，那它就是一个**没跑通的承诺**。两条纪律：
1. **UI 上直说**：`transport=http` 未实装/未验证时，设置页该选项必须显示「未验证通道（企业内网专用，需联调）」，而不是静默可选。
2. **不许静默降级**：若选了 http 但没配服务端，必须**明确报「未配置」**，不得悄悄回落到 S3。

> ★**第 2 条是安全红线**：涉密场景下「以为走内网、实际走公网」的后果不可接受。
> ⇒ 该条必须成为**测试用例（负路径）**：`transport=http` 且 endpoint 未配置 ⇒ 断言**不发起任何公网请求**。
