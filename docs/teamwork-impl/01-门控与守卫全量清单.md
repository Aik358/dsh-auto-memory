## 二、回环守卫的真实实现（逐行）

```js
// lib/index.js:10727-10739  —— 原文照抄
function isLoopbackRequest(req) {
  const address = req.socket && req.socket.remoteAddress
  if (address !== '127.0.0.1' && address !== '::1' && address !== '::ffff:127.0.0.1') return false
  const host = req.headers.host
  if (typeof host !== 'string') return false
  let hostUrl
  try { hostUrl = new URL('http://' + host) } catch { return false }
  if (hostUrl.hostname !== '127.0.0.1' && hostUrl.hostname !== 'localhost' && hostUrl.hostname !== '[::1]') return false
  if (req.headers['sec-fetch-site'] === 'cross-site') return false
  const origin = req.headers.origin
  if (origin === undefined) return true
  try { return new URL(origin).host === hostUrl.host } catch { return false }
}
```

**它实际挡了 5 类东西**（逐条）：
1. 非回环源 IP（`remoteAddress`）；
2. 缺失/畸形 `Host` 头；
3. Host 不是 `127.0.0.1`/`localhost`/`[::1]`（**挡住内网 IP 与域名访问**）；
4. `Sec-Fetch-Site: cross-site`（**挡住跨站发起**）；
5. 有 `Origin` 且与 Host 不同源。

**★ 对 Teamwork 的直接影响（关键结论）**：
- 这条守卫**只在"浏览器/外部客户端"这条路上有意义**；**插件→团队服务端的出站请求不受它约束**。
- 因此 Teamwork 的**入站**不需要动它（保持本机语义），**出站**是全新路径，必须自己建鉴权（Bearer token / mTLS）。
- 旧调研实测过的"OAuth 回调用宿主接缝"结论**再次被证实必要**：任何"团队服务端回调到插件路由"的方案都会撞死在这 5 条上。

## 七、Teamwork 化：守卫层的改法（可直接落地）

### 7.1 保持入站不变，新增"出站鉴权"层

**不建议**改 `isLoopbackRequest`（56 处调用，改动面极大且守卫被 smoke 覆盖）。正确做法是**新增并列的一层**：

```js
// 新增文件：lib/team-auth.js（未来实施时）
// 职责：团队出站请求的鉴权与租户隔离；与 isLoopbackRequest 完全正交。

/** 团队请求的统一出口：所有出站都经此，禁止各处裸 fetch。 */
export function createTeamFetch({ getToken, serverUrl, teamId, timeoutMs = 8000 }) {
  return async function teamFetch(path, { method = 'GET', body, signal } = {}) {
    if (!serverUrl || !teamId) return { ok: false, error: 'team-not-configured' }
    const token = await getToken()               // 由 team-identity 提供（宿主 credentials seam）
    if (!token) return { ok: false, error: 'not-authenticated' }
    const ctl = new AbortController()
    const timer = setTimeout(() => ctl.abort(), timeoutMs)
    try {
      const res = await fetch(new URL(path, serverUrl), {
        method,
        headers: {
          'content-type': 'application/json',
          // ★ 三件套：成员身份 + 租户 + 客户端版本（服务端据此做隔离与兼容）
          'authorization': 'Bearer ' + token,
          'x-dam-team': teamId,
          'x-dam-client': 'dsh-auto-memory/' + PKG_VERSION,
        },
        body: body === undefined ? undefined : JSON.stringify(body),
        signal: signal || ctl.signal,
      })
      if (!res.ok) return { ok: false, status: res.status, error: await safeText(res) }
      return { ok: true, data: await res.json() }
    } catch (e) {
      return { ok: false, error: String((e && e.message) || e) }   // 永不抛：出站失败不得影响本机
    } finally { clearTimeout(timer) }
  }
}
```

**为什么这样设计**：
- 出站失败**永不抛**（返回 `{ok:false}`）⇒ 满足"本地优先"硬约束（判据 4），网络挂掉不影响本机任何功能；
- `x-dam-team` **每个请求都带**（满足"跨团队零可见"必须在服务端 where 条件里、不能客户端过滤"的判据）；
- token 从宿主 credentials seam 取，**插件不落明文**。

### 7.2 给路由加"团队读写"的第二种鉴权（不改既有 56 条）

未来若需要**让团队服务端反向读取本机**（例如拉取本机待推送队列），**不要新增对外路由**（会撞回环守卫 5 条），而是：

```js
// 复用既有出口：本机主动推（outbox pull 模型），服务端不反向连本机。
// 若确有反向需求，唯一可行通道是 host 的 remote/RPC seam，而非 webServer 路由。
```

**判据**：**任何"服务端 → 插件"的连接都必须先证明它不经过 `isLoopbackRequest`**，否则方案作废。

## 八、门控清单对 Teamwork 的三条硬约束（结论）

1. **入站零改动**：56 条路由与回环守卫**全部保持原样**，Teamwork 只加出站。
2. **不存在"服务端调插件"的路**：所有团队交互必须是**插件主动出站拉取**（pull/outbox 模型）—— 这条直接决定了同步架构只能是"客户端拉 + 客户端推"，不能是"服务端推送"。
3. **身份必须由宿主提供**：因为 56 条路由没有一条能承载登录态，且回环守卫不允许外部回调。
