## 一、★★★ 第 1 条必做项：**下行接住 member（旁挂索引）**

> **用户逐字裁定（2026-09-27）**：「你要放到 B12。然后用**旁挂索引方案**，你首先落盘，**做前端的时候不要忘了这个事儿**。」

### 1.1 问题是什么（**这是用户提问挖出来的真实缺口，不是补锅**）

用户问：「如果没有这个健全的记号，那现在在 Teamwork 里怎么能看到是谁同步的东西、谁上传的东西呢？如果在前端里展示的话，也展示不出来啊。」
⇒ 排查结果：

| 位置 | 「谁改的」有没有 | 代码证据 |
|---|---|---|
| **上传信封** | ✅ **有** | `team-sync.js:126-132` `member: { id, role }` |
| **未登记身份 ⇒ 拒绝上传** | ✅ | `team-sync.js:122-124` `throw new Error('identity-not-registered')` |
| **冲突中心** | ✅ **有，且落盘** | `team-merge.js:125` `byMember`；`:171` `resolvedBy`；`:193-200` `toJSON/load` |
| **归属徽标路由** | ✅ 有（但只返回**当前登录者**） | `index.js:13719` `actor: member ? {...} : null` |
| **本地 Markdown 文件** | ❌ **没有** | 设计如此（见 1.3） |
| **★ 下行拉回本地后** | ❌ **member 丢了** | **← 这就是缺口** |

**⇒ 缺口精确定位**：
`
上传带 member ✅ → 云端存 ✅ → 下行拉回时 member 未按条目落盘 ⚠️ → 前端无法按条展示作者
`

### 1.2 要做什么（旁挂索引方案，用户已批准）

**新增一个旁挂索引文件**（不碰任何 Markdown）：

| 项 | 建议值 |
|---|---|
| 文件名 | `team-attribution.json`（放数据目录，与 `team-conflicts` 同级） |
| 结构 | `{ schema: 1, items: { '<key>': { memberId, memberName, at, op } } }` |
| 写入时机 | **下行合并时**，按条目 key 记录 `member` |
| 读取者 | 前端「归属徽标」+ 「谁写的」列表；**「记忆」页签与左下角浮窗读同一份** |

### 1.3 为什么不用「把作者写进 Markdown」（**用户已批准此判断**）

| 方案 | 判决 |
|---|---|
| **A 旁挂索引（★采用）** | ✅ 保住 G-E5「磁盘仍是人类可读 Markdown」；✅ **旧数据零影响**（不改任何既有文件格式） |
| B 写进 frontmatter | ❌ 破坏 G-E5；❌ **会让 1 万旧用户升级真的出问题** |
| C 只存内存 | ❌ 前端展示不稳定，刷新即丢 |

### 1.4 验收判据（**不许用"源码里有某字符串"结案**，遵 CR-10）

- [ ] **正路径**：真构造 merge → 下行含 member 的条目 → 断言 `team-attribution.json` 里该 key 的作者 = 上传者 id
- [ ] **负路径**：下行条目**缺 member** ⇒ 断言**不写入**（不得留空占位行）
- [ ] **隔离路径**：`teamEnabled=false` ⇒ 该文件**不该被创建**（老用户零新增文件）
- [ ] **可复算物理量**：文件字节数 + 条目数 + sha
