# 24 · 架构科普与选型（写给非技术背景的读者）

> 生成 2026-09-26 ｜ 起因：用户在拍板前问「团队服务端架构」到底是什么。
> 本文**不含代码**，用比喻讲清两件事：①为什么会有「服务端」这个岔路 ②为什么你的业务目标已经替你选好了。
> 附：本文可直接作为**给客户 IT 的说明材料**（§5 那张表就是你要向客户索要的信息）。

---

## 1. 问题的本质：两台电脑怎么交换记忆？

团队里 A 和 B 两台电脑，要把各自的「记忆」给对方用。**只有两种根本做法**：

### 做法一 · 设一个「收发室」（= 团队服务端）

公司里开一间收发室。A 把东西送到收发室，收发室再分给 B。

| 需要什么 | 说明 |
|---|---|
| 一台**一直开着的机器** | 不能关机，一关大家就收不到东西 |
| **有人负责它** | 装、升级、备份、坏了要知道 |
| **一笔持续的钱** | 云主机是按月付费的 |
| **你要额外写一套软件** | 收发室本身 —— 这就是「服务端」。要处理登录、权限、谁发给谁、坏了怎么办 |

**风险**：收发室一停，**所有**人在**所有**设备上都不再同步。它变成一个「单点」。

### 做法二 · 用一个「共享柜子」（= 云存储）

公司本来就有一个共享柜（比如云盘）。A 把自己的东西放进柜子，B 自己去柜子里拿。

| 需要什么 | 说明 |
|---|---|
| **柜子** | 由云厂商提供，**本来就是 24 小时在线**、本来就有备份 |
| **一把钥匙** | 云厂商给你的账号密钥（一串字符） |
| **你要额外写一套软件** | 只有三件事：**怎么放、怎么拿、两个人放冲突了怎么办** —— 全在你自己的插件里 |

**关键**：柜子是「哑巴」的。它只负责存东西，不会替你管事。所以「谁放的、什么时候放的」要**你自己写在纸条上**（写在文件里），「两个人同时改了同一份怎么办」也要**你自己的规则**来判。
> 好消息：这三件事**在本项目里已经全部写完了**（后面 §6 会讲清楚到哪一步）。

## 2. 两条路的正面对比（这才是你真正要拍的板）

| 对比项 | 做法一 · 自建服务端 | 做法二 · 共享柜子 |
|---|---|---|
| **客户要提供什么** | 一台机器 + 一个会运维的人 | **4 个字段**（见 §5），通常找 IT 开个「存储桶」就行 |
| **客户要额外花钱吗** | 要（云主机月费） | **基本不用** —— 客户本来就在用阿里云/华为云，存储费极低 |
| **你要多写多少代码** | 一整套服务端（登录/权限/接口/部署/升级/安全补丁） | **只写存储读写**（已写完大半） |
| **出事谁负责** | **你**（服务端是你写的，停了是你的锅） | **云厂商**（存储是它的服务，SLA 由它背） |
| **能不能卖给多家云** | 要重写适配（每家的机器、网络、认证都不同） | **同一套代码通吃五家云**（§3 说明为什么） |
| **客户 IT 的阻力** | 大（「我们凭什么给你开一台服务器？」） | **小**（「开个存储桶给个密钥」是标准操作） |
| **能不能过合规** | 要单独做安全评估 | 走客户已有的存储合规体系 |

## 3. 为什么「换一家云」不用重写代码 —— S3 兼容

打个比方：**USB-C**。

不同牌子的手机、电脑、充电宝，插口长得一样，所以一根线通吃。**不是**因为大家商量好了，而是因为 USB-C 成了事实标准，谁不跟进谁就卖不动。

云存储也有这么一个事实标准，叫 **S3**（亚马逊 2006 年推出的存储服务）。它定的「怎么放、怎么拿」这套说法太通用了，于是**其他家都做了一个一模一样的接口**：

| 云厂商 | 产品名 | 服务地址长什么样 |
|---|---|---|
| 阿里云 | OSS | `https://oss-cn-hangzhou.aliyuncs.com` |
| 腾讯云 | COS | `https://cos.ap-guangzhou.myqcloud.com` |
| 华为云 | OBS | `https://obs.cn-north-4.myhuaweicloud.com` |
| AWS | S3 | `https://s3.us-east-1.amazonaws.com` |
| Google Cloud | GCS | `https://storage.googleapis.com`（互操作模式） |

> **⇒ 你写一套代码，讲「S3 的话」，五家云都能听懂。**
> 客户说「我们用阿里云」，你就把地址填成阿里云那一行；客户说「我们用华为云」，换一行。**代码一个字不用改。**

**这正是你说的「只做兼容性工作」的技术含义。** 它不是「给五家各写一个版本」，而是「写一个通用版本，换四个字段」。

> ★**还有一件对涉密客户很重要的事**：内网自建的对象存储（**MinIO**、Ceph、华为云 Stack 的 OBS）**也是 S3 兼容的**。
> ⇒ 也就是说，**大部分「涉密/内网」客户，走的仍然是这条路，代码零改动，只换地址**。
> 真正需要自建服务端的，是极少数「必须有服务端做审计审批」或「连对象存储都不给开」的场景（T2）。详见 [25 卷](25-架构裁定与双通道落位.md) §2。

## 4. 为什么这条路线还有个隐性好处：你本人不需要运维

自建服务端 = 你要对**客户的生产环境**负责。半夜服务端挂了，客户找的是**你**。
你要处理：机器到期、系统升级、证书过期、安全漏洞、被扫描、被封、被 DDoS……这些都是**持续**的责任。

走共享柜子 = 你只交付一个**插件**。柜子是客户自己的，坏了也是客户自己的云在坏。
你要负责的范围从「一台机器的运行」缩小到「我的插件读写有没有写错」。

> 对一个**要卖给多家公司**的产品，这个差别是决定性的：
> 前者每多一个客户就多一份运维债；后者多一个客户只多一次配置。

## 5. 客户要提供什么（一页纸，可直接发客户 IT）

走「共享柜子」路线，客户 IT 只需要填满**下面这张表**。填完就能开工。

| # | 你要什么 | 大白话 | 客户 IT 怎么给 |
|---|---|---|---|
| 1 | **存储服务地址** | 「柜子在哪」 | 云控制台建一个「存储桶（Bucket）」，把访问地址复制给你 |
| 2 | **区域** | 「柜子在哪个城市」 | 建桶时选的地域，如 `cn-hangzhou` / `us-east-1` |
| 3 | **访问密钥 ID** | 「钥匙的编号」 | 控制台 → 访问密钥（AccessKey）→ 新建，**只授权这一个桶** |
| 4 | **访问密钥密码** | 「钥匙本身」 | 同上，只显示一次，务必存好 |
| 5 | **路径风格开关** | 「地址写法用哪种」 | 开 / 关二选一，多数国内云需要**开**；不确定就试两次 |

> ★**务必对客户说的一句**：密钥请**只授权这一个桶**，不要给整个账号的管理员密钥。
> 这是标准做法，客户 IT 听到这句反而更放心。

**客户不需要提供**：不用开服务器、不用装软件、不用开放端口、不用配防火墙。

## 6. 当前代码走到哪一步了（诚实进度）

两条路各自的完成度实测如下。**结论是「两条路都只写了一半」**——但这是**好消息**，因为没有需要推倒的东西。

| | 做法一 · 服务端路线 | 做法二 · 共享柜子路线 |
|---|---|---|
| **设计定了吗** | ✅ 契约 02 定了 | ✅ 13 卷定了，五家云地址都查过官方文档 |
| **配置项建了吗** | ❌ **没有** —— 代码要读 `teamServerUrl` / `teamId` / `teamToken`，**这三个键从未注册过** | ✅ **建好了** —— `teamEndpoint` / `teamBucket` / `teamRegion` / `teamPathStyle` / 密钥 ×2，共 6 个 |
| **代码写了吗** | ✅ 写了（网络出口 + 定时推送 + 失败重试队列） | ❌ **没写** —— 全 lib 扫描：**没有一个 S3 客户端**、没有签名算法，装不进去也取不出来 |
| **现在能跑吗** | ❌ 不能 —— 恒返回「未配置」 | ❌ 不能 |
| **CR-8 裁定后** | 保留为 **T2 兜底**（涉密内网专用），补三个键即可复活 | **主线**，默认通道 |

**大白话总结**：
- 服务端路线：**写好了发动机，但没给油箱** —— 代码在等三个从没填过的配置，所以永远是「未配置」。
- 共享柜子路线：**画好了柜子的图纸、量好了钥匙孔的尺寸，但还没做那把钥匙** —— 六项配置都在，就差读写柜子的那段代码。

两条路**都不需要推倒**：服务端路线的那些代码里，「失败重试队列」「网络超时处理」**换到柜子路线照样能用**（只是把「发给服务端」改成「放进柜子」）。

## 7. 为什么你的业务目标已经替你拍完了这个板

你说：**「客户只说他们公司用阿里云，但我想卖给其他公司，有用的 Google 的、有用的 AWS 的、有用的华为云的，所以我只是想做一些兼容性的工作。」**

这句话把答案说完了。逐条对照：

| 你说的 | 对应的技术选择 |
|---|---|
| 「客户环境不统一，有五家云」 | → **必须走 S3 兼容**（只有这一条路能一套代码通吃五家） |
| 「我只想做兼容性工作」 | → **不自建服务端**（自建的话每家客户都要单独适配机器/网络/认证，恰恰是最不兼容的做法） |
| 「客户只说他们用阿里云」（不想配合你搞复杂东西） | → **只需 4–5 个字段**（§5 那张表），客户 IT 五分钟能填完 |
| 「要卖给多家公司」 | → **你承担的责任越小越好**（共享柜子路线的运维是云厂商的，服务端路线的运维是你的） |

> ⇒ **结论：走「共享柜子」（S3 兼容直连），不自建团队服务端。**
> 这不是我替你做决定，而是**你的四句话推出的唯一结论**。

**唯一的代价（要诚实说）**：柜子是「哑巴」，不会替你管事。所以「谁放的、什么时候放的、两个人改冲突了怎么办」——**这三件事必须你自己的代码来做**。好消息：**这三件事在本项目里已经全部写完了**（见 §8）。

## 8. 换路线要保留什么、补什么（给施工用，一句话一条）

**保留（不浪费，换路线照样用）**：
1. 出站队列与重试（`lib/team-outbox.js`）—— 本来就是「消息排队 + 失败重试」，与发给谁无关。
2. 冲突判定与合并（`lib/team-merge.js`）—— 三方比对（我的旧值 / 我的新值 / 对方的值），与存哪无关。
3. 日历双轨（`lib/team-calendar.js`）—— 本机轨 / 团队轨分离。
4. 注入仲裁（`lib/team-inject.js`）—— 「团队来的记忆怎么在有限预算里插进去」。
5. 白板两阶段（`lib/team-board.js`）、派生重算节流（`lib/team-derived.js`）、身份登记（`lib/team-identity.js`）。
6. 六项配置键本身（`teamEndpoint` 等）—— 直接就是柜子路线要的东西。

**补（这才是真正要新写的）**：
1. **一个 S3 客户端**：会用 4 把钥匙去读/写柜子（含请求签名）。这是整条路线里**唯一**的新技术件。
2. **同步路径改向**：把「POST 到 `api/team/sync/push`」改成「PUT 一个对象到柜子里」。
3. **成员名册**：柜子里放一张「成员表」，谁都可以读；在场状态按「最后更新时间」推算。
4. **契约 02 重写**：把里面「团队服务端」的假设，改成「本机算 + 柜子读」（§1.2 的 20 个配置键对照表就是重写依据）。

**不做（省掉整整一大块）**：登录鉴权服务、权限管理后台、服务器部署与升级、证书与端口、独立的安全评估。

## 10. 术语对照（以后听到这些词不再懵）

| 你会听到的词 | 大白话 |
|---|---|
| **服务端 / 后端服务** | 一台一直开着、替你管事的机器（本文的「收发室」） |
| **对象存储 / OSS / COS / OBS / Bucket** | 云上的「共享柜子」（本文的做法二） |
| **S3 兼容** | 柜子的「USB-C 标准」，五家云都做了同一个插口 |
| **Endpoint（端点）** | 柜子的地址 |
| **AccessKey / 密钥** | 开柜子的钥匙（编号 + 密码两件套） |
| **pathStyle** | 地址的两种写法，国内云多数要用另一种 |
| **CDC / 增量同步** | 只传「变了的部分」，不传整本（省流量、快） |
| **冲突** | 两个人同时改了同一条，谁说了算的问题 |
| **ETag** | 柜子给每份文件算的「指纹」，用来判断文件变没变 |
