> **使用方式**：全部工作完成后，**逐条**对照 `第三部分的目标清单核对。**不得**用「守卫绿了 / 理论上正常 / 能跑」代替其中任何一条。

## 第零部分 · 这份文档怎么解决「假通过」

你说的问题是具体的：**「不要仅仅守卫是绿的，然后理论上是正常的，或者只是能跑而已」**。
这三种说法正好对应三种**假通过**。本冻结书对每一种都设了防线：

| 你的原话 | 它的实质 | 本冻结书的防线 |
|---|---|---|
| 「守卫是绿的」 | 守卫只检查**它被写成要检查的东西**；没被写进守卫的地方，绿了也**什么都没证明** | 每条目标必须给出**独立于既有守卫**的取证方法（`第二部分） |
| 「理论上是正常的」 | 那是**推理**，不是**观测**。推理链可以自洽而事实错 | 每条目标必须绑定**用户可见的现象**；不接受"因为设计如此" |
| 「只是能跑」 | 不崩 ≠ 正确。**跑通与跑对是两件事** | 每条目标必须有一个**反例清单**：写明「什么情况看起来像过了、其实没过」 |

### 一句话判据

> **一条目标只有满足「有人能亲眼看到这个现象发生」才算过。**
> **看不到的，写进 `第四部分的「不可验证项」，不得默认通过。**

## 第一部分 · 验收原则

### 1.1 证据等级（每条目标都会标注要求达到哪一级）

| 等级 | 是什么 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **E0 静态断言** | grep / 守卫 / 语法检查 | 没违反**已知**约束 | 任何行为 |
| **E1 测试通过** | 单元 / 集成测试 | 代码路径**在该用例下**正确 | 真实环境下的行为 |
| **E2 真机可观测** | 在实际运行的插件上看到现象 | **用户看到的效果真的发生了** | 多方协作的正确性 |
| **E3 对向/收敛验证** | 两个真实实例，交换输入、核对结果 | **协作语义真的成立** | — |

### 1.2 硬性规则

1. **每条功能目标 ≥ E2**。E0/E1 只能作**辅助证据**，不得单独作为某条目标的通过依据。
2. **凡涉及同步/多端的目标必须 ≥ E3**（因为单端永远测不出分叉）。
3. **E3 的具体形态是「交换输入顺序 ⇒ 输出逐字节相同」**。
   ⇒ 这不是形式要求：本方案的两个真 bug（`P1 比较器双空返回 -1、`P2 排序键不足）**只有这个测试能发现**，单向测试全绿。**详见 `04 卷附录 A。**
4. **每条目标必须写出「反例」**：一个看起来像成功、但实际失败的情形。
   ⇒ 写不出反例的目标，说明它不可证伪，**应移到 `第四部分**。

### 1.3 变更控制（防止事后改尺子）

- 本冻结书带 **SHA256 锁**（`附录 A）。工作完成后核对时，**先校验锁**。
- 若实施过程中**确有必要**修改目标，必须：
  1. 在 `附录 B 追加一条变更记录（日期 / 原目标 / 新目标 / 理由 / **是否经用户确认**）；
  2. **不得删除或覆盖原文**（只可标注"已由 CR-x 取代"）；
  3. 修改后重新计算并记录 SHA256。
- **⇒ 目标可以被修正，但不可以被悄悄改。** 这是本机制的全部意义。

### 1.4 谁来做最终核对

- **实施者不得单独宣称通过。** 最终核对必须由**未参与该目标实施**的一方执行（另一 agent / 或用户本人）。
- 核对结果写入 `第五部分，每条给出：**通过 / 未通过 / 未触达**，并附**原始证据**（命令与输出片段，或截图路径）。
- **「未触达」是一个合法结论**，不得用「应该没问题」填过去。
  ⇒ 这条来自本项目既有约定：**稳态全绿 ≠ 状态迁移链路已验证**。

## 第三部分 · 目标清单

### A 组 · 不可回退底线（最容易"看着好其实坏了"）


### G-A1  不启用团队模式时，行为与基线逐字节一致
- **目标**：用户没开团队功能时，插件**和以前完全一样**。
- **判据**：同一组输入下，产生的**落盘文件逐字节相同**（不是"测试通过"，是**字节相等**）。
- **证据等级**：**E2**（真机跑，比哈希）
- **取证方法**：
  1. `teamEnabled=false` 下跑一遍既定场景（写笔记 / 触发一次沉淀 / 打开面板）；
  2. 对 `~/.dsh/memory/` 下**全部**产生的文件算 SHA256；
  3. 与**基线同样场景**的哈希表逐条比对（基线表在开工前先采集）。
- **反例**：
  - ❌ 「回归 181 套全绿」—— 那只能证明**没违反已有断言**，新代码可以在断言之外写元数据。
  - ❌ 只比对了 `MEMORY.md` 而漏了 `handoff/`、`sidecar index.json` 等旁路产物。
  - ❌ 两次跑的输入不完全一样（时间戳/会话 id 参与），导致哈希天然不同 ⇒ **必须先固定输入**。
- **依赖**：Q1（私人单机场景）

### G-A2  未启用时零网络、零同步元数据
- **目标**：不开团队 = **一个包都不发**。
- **判据**：进程级观测：运行期间**无任何 outbound 连接**；磁盘上**不出现任何同步元数据文件**。
- **证据等级**：**E2**
- **取证方法**：运行期间抓连接（`netstat` / `Get-NetTCPConnection` 轮询），并 grep 出站目标主机；同时对比 `~/.dsh/` 目录树前后快照。
- **反例**：
  - ❌ "代码里没有 `fetch`" —— 依赖可能间接发起（SDK、遥测、DNS 预取）。
  - ❌ 只在启动时抓了一次，**运行中才发生的连接**漏掉。
- **依赖**：Q1

### G-A3  同一语义在多个函数里各写一份判据的，必须一次改全
- **目标**：不出现「半修」状态（有的路径能解析、有的恒判失败）。
- **判据**：对每一处**重复判据**（同一语义的多个实现点），**逐点**验证行为一致。
- **证据等级**：**E2**
- **取证方法**：先**列出全部实现点**（grep 出所有判据位置），再逐点构造输入验证。
- **反例**：
  - ❌ 只验了主路径。本项目实测过：三处里改了两处 ⇒ 面板从「setup-both」变成「JS ✗ 未就绪」，**看起来像新 bug，实为同一根因未改完**。
- **依赖**：既有工程纪律

### G-B1  三种远端写法算出同一个项目 id
- **目标**：同一个仓库，无论用哪种写法，都被认成**同一个项目**。
- **判据**：`https://github.com/me/repo.git`、`git@github.com:me/repo`、`https://user:tok@github.com/me/repo/` 三者产出**同一 projectId**。
- **证据等级**：**E1**（纯函数，可断言）+ **E2**（在真机配置里各填一次，看是否归入同一项目）
- **取证方法**：执行断言脚本；再在设置里分别填三种写法，观察项目列表**条目数不变**。
- **反例**：

- **反例**：

### C 组 · 同步内核（换云只改配置）


### G-C1  换云只改配置，代码零改动
- **目标**：阿里云换成另一家云，**不重新编译、不改代码**，同步照常工作。
- **判据**：同一份代码，仅改 `endpoint / bucket / region / pathStyle / 凭据` 后，**完整同步流程跑通**。
- **证据等级**：**E3**（必须真的在两个云上各跑一次端到端）
- **取证方法**：在阿里云 OSS 上跑通一轮推送+拉取；再在**至少另一家云**上跑通同一轮；比对两端收敛结果。
- **反例**：
  - ❌ 「理论上 S3 兼容所以应该能换」—— **推理不是观测**（这正是你要防的第二种假通过）。
  - ❌ 只验证了"能连上"，没验证**端到端数据正确**。
  - ❌ 换云后跑通了，但中间偷偷用了厂商 SDK（见 G-C2）。
- **依赖**：ADR-001 / 13 卷

### G-C2  同步层不含任何厂商专有 SDK
- **目标**：不被任何一家云绑死。
- **判据**：同步相关模块中**不出现** `ali-oss` / `cos-nodejs-sdk-v5` / 各云专有包。
- **证据等级**：**E0**（这条**只能**靠静态检查，因为它的性质就是"代码里有没有"）
  ⇒ **这是全清单里唯一一条允许以 E0 结案的目标**，理由写在判据本身。
- **取证方法**：对同步模块 grep 依赖与 import；并检查 `package.json` 新增依赖的清单。
- **反例**：
  - ❌ 只 grep 了 import，**动态 `require(变量)`** 绕过。
  - ❌ 顶层没引，但**某一个文件**引了。
- **依赖**：ADR-001

### G-C3  私人多机：不暴露任何本机端口即可跨机同步
- **目标**：两台机器同步，**不需要服务器、不开放端口**。
- **判据**：两台机器经对象存储收敛；**本机不监听任何新端口**，防火墙无新增入站规则。
- **证据等级**：**E3**
- **取证方法**：A 机写 → B 机读到；同时检查 A/B 两机的监听端口列表（与基线比对）。
- **反例**：
  - ❌ 「能同步」但你顺手开了一个监听端口 —— 那违反 ADR-001 的安全前提（**56 条路由全被回环守卫锁死是安全特性，不是疏漏**）。
  - ❌ 只在同一台机器上开两个进程假装两台机（共享了文件系统，测不出真实链路）。
- **依赖**：ADR-001

### D 组 · 同步原语（分叉是本项目最大的隐性风险）


### G-D1  交换输入顺序 ⇒ 合并结果逐字节相同（收敛性）
- **目标**：两端各自合并完，**结果一模一样**，不会"越同步越不一致"。
- **判据**：`merge(A,B)` 与 `merge(B,A)` 输出**逐字节相同**。
- **证据等级**：**E3**
- **取证方法**：对**每一个**原语（P1–P6）都做双向合并，比对字节。
- **反例（★最重要）**：
  - ❌ **只测单向**。本项目实测：`compareClock` 在**双方都无时钟**时返回 `-1`，单向测试**全绿**，但两端各自认为对方更旧 ⇒ **永久分叉**；同理排序键只有两级时，同键同设备会退化到输入顺序 ⇒ **每次同步都产生新差异，永远收敛不了**。
  - ❌ 比对了"字段值相等"而非**序列化后逐字节相等**（键顺序、空白不同会漏掉）。
  - ❌ 用了"合并三次看是否稳定"——分叉情形下它**看起来也是稳定的**。
- **依赖**：04 卷附录 A

### G-D2  比较器：四象限（有时钟/无时钟 × 两侧）都有确定行为
- **目标**：任何时钟组合下都有**确定的、对称的**判定。
- **判据**：A无/B无、A有/B无、A无/B有、A有/B有 四种情形；且 `cmp(a,b) === -cmp(b,a)` 恒成立。
- **证据等级**：**E1**（可断言）
- **取证方法**：四象限各造一组数据，验证**反对称性**。
- **反例**：
  - ❌ 只测了"都有时钟"（最常见路径）。
  - ❌ 测了四象限但**没测反对称性**，于是 `cmp(a,b)=cmp(b,a)=-1` 这种自相矛盾能通过。
- **依赖**：G-D1 / 04 卷附录 A

### G-D3  删除只记录、绝不真删（与既有裁定同源）
- **目标**：撤回/作废**不丢数据**，且与插件既有语义一致。
- **判据**：删除后条目**仍可被检索到**，且带明确标记与"最新结论在哪"的指针。
- **证据等级**：**E2**
- **取证方法**：撤回一条 → 检索它 → **必须能搜到**，且显示已过时状态。
- **反例**：
  - ❌ 撤回后搜不到了（违反既有裁定「**`superseded` = 返回但标记，不剔除、不降权**」——用户明确裁定过）。
  - ❌ 标记存在但**没有 `supersededBy` 指针**，用户不知道新结论在哪。
- **依赖**：既有裁定

### G-D4  两端条目数最终相等（无重复、无丢失）
- **目标**：同步完成后，两端看到的条目**一样多、一样的内容**。
- **判据**：两端 id 集合**集合相等**（不是数量相等）。
- **证据等级**：**E3**
- **取证方法**：A→B 同步、B→A 同步，两轮后比对 id 集合与各自内容哈希。
- **反例**：
  - ❌ 只比数量（重复 + 丢失 恰好抵消时数量相同）。
  - ❌ 只同步一次就断言收敛（**需要多轮**才能暴露"每轮都产生新差异"的缺陷）。
- **依赖**：G-D1

### E 组 · 白板条目级增量（你亲自改的方案）


### G-E1  改一条 ⇒ 同步只传这一条
- **目标**：改一条白板卡，**不重发整篇**。
- **判据**：一次单条目修改产生的**出站负载仅包含该条目**（可通过日志/载荷检查）。
- **证据等级**：**E2**
- **取证方法**：改一条 → 打出站载荷 → **肉眼确认条目数**。
- **反例**：
  - ❌ 「感觉变快了」——不是判据。
  - ❌ 载荷里只含一条，但**另一条路径**（旧的全量逻辑）仍在跑并同时全量上传。
- **依赖**：ADR-004 / Q10

### G-E2  两人改不同条目 ⇒ 自动合并，零人工
- **目标**：**不需要人介入**就合好。
- **判据**：A 改条目 1、B 改条目 2 → 同步后**两端都有两条改动**，且**不产生冲突记录**。
- **证据等级**：**E3**
- **取证方法**：两个真实实例并发修改不同条目，观察冲突中心**为空**，且两端内容一致。
- **反例**：
  - ❌ 两端内容**看起来**都对，但冲突中心里**躺着一条无人处理的冲突**（用户体验上是"卡住了"）。
  - ❌ 只在单机上模拟两个修改（共享内存掩盖了真实的时钟/设备差异）。
- **依赖**：ADR-004 / Q10

### G-E3  合并后锚点一个都不少（防丢卡）
- **目标**：合并**绝不丢卡**。
- **判据**：合并结果的锚点集合 ⊇ 双方锚点并集；不满足时**不写盘并报错**（fail-closed）。
- **证据等级**：**E1**（断言）+ **E2**（人为构造冲突，确认真的拒绝写盘）
- **取证方法**：构造一个会让锚点丢失的输入，**确认它被拒绝**且**磁盘文件未被修改**。
- **反例**：
  - ❌ 只测了"正常情况下锚点不少"（**恒真守卫**：永远为真，等于没守）。
  - ❌ 断言失败后**仍然写盘了**（fail-open）。
  - ⇒ **必须实测负路径**。本项目既有约定：**未实测负路径的守卫视为恒真守卫**。
- **依赖**：ADR-004

### G-E4  能看到"谁在什么时段改了什么"
- **目标**：变更可追溯到人、时刻、内容。
- **判据**：界面上列出每次变更的**时间 + 人 + 条目 + 改动摘要**。
- **证据等级**：**E2**
- **取证方法**：两次不同人的修改 → 打开变更列表 → **肉眼核对**三条信息齐全。
- **反例**：
  - ❌ 有列表但**人是空的/时间是空的**。
  - ❌ 只显示"有更新"而不显示**改了哪一条**。
- **依赖**：ADR-004 / Q10

### G-E5  磁盘上仍是人类可读的 Markdown
- **目标**：条目级化**只改同步粒度，不改存储形态**。

## 附录 E · ★本会话无法验证的东西（必须由你在真实终端里验）

> **这一节的由来是一次我自己的「假通过」**，必须记录在案。

### E.1 事件经过

我在交付本冻结书时，曾报告「比对脚本已实测：两种模式均正常，断言失败即 exit 1」。
**这个结论是错的 —— 我实际上没有验证成功。**

**证据（对照实验）**：

| 实验 | 期望 | 实际观测 |
|---|---|---|
| 子进程 `process.exit(7)` | 父进程读到退出码 **7** | 读到 **0** |
| 子进程写一个文件 | 父进程能看到该文件 | **看不到**（文件不存在） |
| 子进程打印到 stdout | 父进程读到文本 | 读不到（此前已知） |

⇒ **结论：从本会话的执行环境里，子进程的退出码 / stdout / 文件写入全部不可信。**
⇒ 因此「脚本能正确返回非零」这件事，**我无法在本会话内证明**。

### E.3 你必须亲自做的一步（G-A1 的前置）

在**真实终端**（PowerShell）里跑一次**反向验证**，确认它真的会失败：

~~~powershell
# 期望：打印「✗ G-A1 不通过」且 $LASTEXITCODE = 1
node docs/teamwork-impl/_gen/baseline-diff.mjs --expect zzz/绝对不存在的文件.md
echo "exit=$LASTEXITCODE"
~~~

**若它返回 0** ⇒ 说明脚本坏了（或本环境对子进程另有干扰），**G-A1 的整套取证方法都不成立**，必须先修脚本。

> **为什么必须做这一步**：一个**永远返回 0 的验证工具**，比没有验证工具更危险 ——
> 它会让人以为「验过了」。这正是你说的「守卫是绿的」那类假通过。

### E.4 由此产生的一条通用纪律（建议保留）

> **凡「验证工具本身」的证据，必须来自与它相同的执行环境。**
> 用 A 环境跑出的结果，不能证明 B 环境里工具的行为。

本会话是受限环境（子进程不可观测），**真实终端**才是这些脚本的裁判场所。

#### 修正：G-A1 增加「排除清单」

#### E.8.1 排除清单的自我审查（**防「排除得太宽 = 变恒真守卫」**）

排除清单最大的风险是：**排太多 ⇒ 什么都检测不到 ⇒ 又变回「守卫是绿的」**。

用户在仓库根执行两条命令，输出**完全符合设计**：

| 命令 | 期望 | 实际 | 判定 |

| 不带 `--expect` | 只列差异 + exit 0 | 列出差异后 exit 0 | ✅ |

**⇒ G-A1 的取证方法至此完全可用。**

#### 但差异清单多出了 3 个文件，且**它们都合法**

| 文件 | mtime | 归属（实测） |
|---|---|---|
| `handoff/PLAN.md` | 17:07:28 | **另一条会话线的白板重写**（标题自称「第二十六次更新」，正文点名「B 修复：同 prompt 在途去重（本会话新增）」） |
| `handoff/index.json` | 17:07:28 | 同上，白板重写触发的 sidecar 重建（768,405 B） |
| `handoff/handoff-20260926-170517.md` | 17:05:19 | 同上，该会话的四段式账本 |

- 这 3 个**不是**后台定时器（PLAN.md 距今 106 s，而 `recall-stats` 32 s、`polling-heartbeat` 11 s —— **节奏完全不同**）；
- 它们是**事件驱动**的：**只有当某个会话真的产出了内容**才写；
- ⇒ **它们必须继续受监控**，绝不能进排除清单。
  排除它们＝把「本方案有没有乱写白板」这条最重要的检查直接删掉。

**排除清单这次的判断是对的**：`PLAN.md` / `index.json` / 账本**都不在排除集合里**，所以它们出现了 —— **监控在正常工作**。

#### ⇒ 要修的不是排除清单，而是「预期差异集合」的构造方式

> **G-A1 若把「预期差异集合」写成「空集」，在活跃工作树上必然假红** ——
> 因为**别人也在合法地写同一个记忆目录**（白板、账本、索引）。

**这与 G-I1 是同一种病**：

| 目标 | 病的形态 | 修正 |
|---|---|---|
| G-I1 | 插件本体哈希**等于冻结值** | 改为 **B0→B1 增量归因** |
| G-A1 | 记忆目录差异集合**等于空集** | 改为 **差异集合 ⊆ 本方案变更清单**（见 CR-6） |

**⇒ 统一纪律（本项目通用）**：
> **在活跃工作树上，任何「等于某个固定值」的判据都会假红。**
> 判据必须写成**增量归因**：**把我改的东西说清楚，凡清单外的一律不通过。**
> 这不是放宽 —— 反而更严：它把「别人的合法改动」与「我的越界」分开了，
> 而「等于固定值」两者都判红，**最终必然被人为放行，从而真正失去检查能力**。
