## 八、★重大修正（2026-09-27 · 由用户提问触发）

### 8.1 本文档原来的错误表述

本文档第六节原写：「**用户担心的「鉴权标」：目前不存在于写入路径**」。
**这句话是错的、且会误导**。根因：Lead 只搜了「本地写入路径」，**没搜上传信封与内存状态**就下了"不存在"的结论。

### 8.2 准确事实（三条落点，全部有代码证据）

| 落点 | 内容 | 代码位置 |
|---|---|---|
| **① 上传信封** | `member: { id, role }` —— **谁上传的** | `team-sync.js:126-132` |
| **② 未登记身份 ⇒ 拒绝上传** | `throw new Error('identity-not-registered')` | `team-sync.js:122-124` |
| **③ 冲突中心（且落盘）** | `byMember`（谁引起的冲突）/ `resolvedBy`（谁裁决的）；`toJSON()` / `load()` 持久化 | `team-merge.js:125` / `:171` / `:193-200` |
| **④ 归属徽标路由** | `actor: member ? { id, role } : null`（**只返回当前登录者**） | `index.js:13719` |
| **⑤ 本地 Markdown** | **没有** —— 设计如此 | 见 8.3 |

### 8.3 为什么 Markdown 里没有（这是**设计**，不是遗漏）

- **G-E5**「磁盘上仍是人类可读的 Markdown」—— 塞进作者标会污染文件
- **旧数据没有该字段** —— 强行补写会**真的搞坏 1 万旧用户的数据**（这正是用户担心的场景，设计上已避开）
- ⇒ **本条对"旧用户升级安全"的结论不变**（反而更强：正是因为不写 Markdown，升级才安全）

### 8.4 ★但暴露了一个真实缺口（已记入 B12，见 37 卷）

```
上传带 member ✅ → 云端存 ✅ → 下行拉回时 member 未按条目落盘 ⚠️ → 前端无法按条展示"谁写的"
```

**用户已裁定**：
1. **放到 B12 做**（不单独消耗一次重启）
2. **用旁挂索引方案**（`team-attribution.json`，不碰 Markdown）
3. **要求写进规划文件专门一块，B12 时不许跳过** ⇒ 已落 `37-B12开工必读清单.md`

### 8.5 教训（写入本卷以警后来者）

**判据**：**「某功能不存在」这类否定结论，必须覆盖「本地文件 / 上传载荷 / 内存状态 / 数据库」全部落点**，只搜一处就下结论会误报。
