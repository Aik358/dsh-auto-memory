## §0.5 ★工作重心与调查顺序（用户 2026-09-27 明确）

> **用户原话要点**：「**后端我这跑得还是比较严谨的，主要是前端发现没什么变化。所以你还是重这个前端的截图、代码判断，以及前后接线一类的内容；如果我发现前端错位了，后端也找不到相应的接口的话，再去调查后端的缺口。**」

### ★调查顺序（按此执行，不要倒过来）

| 步 | 查什么 | 手段 | 判据 |
|---:|---|---|---|
| **1** | **前端界面到底变了没有** | **截图（computer use，见 §8）** | 对照 49 卷 §四 规格 + v4 基准图 `77bebc7c` |
| **2** | **前端代码是否真有那个实现** | 读 `lib/client.js`（**纯 CRLF / ES5**） | **文件 + 行号 + 代码原文** |
| **3** | **前后接线是否走通**（★重点） | 沿**消费链**走：配置/数据 → 侧车/宿主 → 前端取值 → 渲染分支 | 每一跳都要有**调用点**；断在哪跳就记在哪 |
| **4** | **只有 3 断掉、且宿主侧确实找不到对应接口时** | 才下探 `lib/index.js` / `lib/wb-sidecar.js` | 记「前端错位 + 后端无接口」 |

### 三档结论（★不要越档下结论）

| 档 | 现象 | 结论措辞 |
|---|---|---|
| **A** | 截图看到**错位/缺失**，且源码里**能找到实现** | 「**前端实现有问题**」+ 行号 |
| **B** | 截图看到**错位**，源码里**找不到实现 / 找不到消费点** | 「**前端未接线**」+ 断点位置 |
| **C** | 前端错位 **且** 宿主侧**也没有对应接口/字段** | 「**后端缺口**」← **只有这一档才去查后端** |

> **⇒ 后端默认视为「已通过」**（用户自己已跑得较严谨）。**你只需在 C 档回溯**。
> **⇒ 不要因为「某个套件/验收器红了」就去翻后端** —— 那属 L4（见 §4.5）。

### 为什么重点压在前端（本项目自己的证据）

| 事实 | 含义 |
|---|---|
| **R29–R37 连续九轮 `lib/` 零改动** | 后端物理量长期未变，而前端仍在改 |
| **用户观感「一天基本没变化」** | 前端改动的**可见效果**是薄弱环节 |
| **已知「存在但没消费」先例**（锚点挂满 1,871 次却零消费方；`includeArchive` 宿主有、前端从未传） | **前后接线断点**是最可能的失效位置 |
| **静态守卫全绿而屏幕无变化**（8 个 `--dam-*` token 有消费无定义） | 守卫绿 ≠ 看得见 |

### 4.5 ★★判据层级：事实 > 代码 > 程序（**本节优先级高于 §4.1–§4.4**）

> **用户 2026-09-27 原话**：「**我不太相信你这些配套的断言插件（也就是程序）。你这些断言可能只是你认为的正确，并不是实际上的正确。还是要面向事实，面向代码是否有这样的实现、这样的实现是否正常，以及前端是否以这样的实现为主。**」

**⇒ 可信度四级（高者可推翻低者）**：

| 级 | 名称 | 是什么 | 可否成结论 |
|---|---|---|---|
| **L1** | **事实** | 界面上真实发生的事：**截图 / 点击 / 真机 HTTP 响应 / 落盘文件字节** | ✅ **唯一可直接成结论的层级** |
| **L2** | **代码** | 源码里**真存在**这样的实现，且**实现本身正常**（读得通、边界合理、不是静默失效） | ✅ 强证据（须附**文件 + 行号 + 代码原文**） |
| **L3** | **消费** | **前端 / 宿主确实以这个实现为主**（有真实消费方，不是写了没人用） | ✅ **必查** |
| **L4** | **程序** | 我方自己的断言脚本 / 验收器 / 套件 | ⚠️ **只能作线索，不得作结论** |

#### 为什么 L4 必须降级 —— 本项目自己的 8 条实证（全部真实发生过）

| # | 假绿 / 假红 | 教训 |
|---:|---|---|
| 1 | **套件全绿 ≠ 功能通过**：R33 之前看板层四项**只有源码字符串守卫**，套件一直绿，功能从未真执行验证 | 断言对象若是「源码里有没有某字符串」= **恒真守卫** |
