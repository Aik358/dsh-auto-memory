### 1.2 逐文件要点（原文摘录）

#### (1) `skin-manifest-v2.schema.json`

`required` 七项（原文）：

> `["skinManifestVersion", "id", "name", "nameEn", "version", "author", "contributes"]`

关键约束（原文摘录）：

- `skinManifestVersion`：`"const": 2`，描述为 **「Manifest file-structure version only; NOT a compatibility negotiation axis」**。
- `id`：`^[a-z][a-z0-9-]{0,31}$`；「The skin-center owns scoping under `html[data-dsh-skin="<id>"]`」。
- `contributes.required = ["stylesheet"]`；另有 `patches`（L3 自由选择器，高敏感）与 `backgroundMedia.{light,dark}`。
- `facets.client.required = ["entry", "apiVersion"]`。
- v1 弃用字段三枚：`package` / `wiring` / `bodyAttr`，均为「Ignored with a migration warning; **never triggers fail-closed**」。
- `$defs.relPath`：`^(?!/)(?!.*(?:^|/)\.\.(?:/|$))(?!.*://)[A-Za-z0-9._\-/]+$` —— 禁止前导斜杠、`..`、协议 URL。

#### (2) `semantic-attrs-v1.md`（★与我们最相关的文件）

**纪律原话（决定我们要不要主动输出属性）**：

> 每个枚举值必须有明确 **owner、版本、含义与锚定方式**，不能只堆字符串——防止语义层退化成另一套隐式 DOM API。
> 不输出语义属性的插件**只享受 L1 token 基础覆盖，不承诺完整换肤覆盖**。

**两条产出通道**（原文）：

> **compat adapter**（皮肤中心的合并 MutationObserver，为官方 DOM 与未 opt-in 插件补打属性；非永久公共契约，官方区域在上游主题缝落地后进入删除评估，第三方插件区域长期保留）与**组件主动输出**（仓内插件按 packages/AGENTS.md 约定自行输出，更准更快）。

**bare value 规则**（原文）：

> part 用**裸值**、归属交给 `data-dsh-plugin`（如 `column` 而非 `task-board-column`）；选择器写法 `[data-dsh-plugin="ssh"] [data-dsh-part="terminal"]`。
> **不复用官方 `data-plugin`**：官方用它标注 style 标签的插件归属（dsh-client-modules / dsh-client-hmr），语义不同。

**实测计数 vs 文档自述（重要）**：

|---|---:|---:|---:|---|
| surface | 8 个 | **8** | **8** | 一致 |
| part | 79 行 | **79** | **96** | 行数一致；因 14 行为「`a` / `b`」多值行，展开后 **96** 个值 |

#### (3) `hooks-api.d.ts`

定位原文（关键，决定我们**不该**去用 hooks）：

> hooks are a **TRUSTED escape hatch**, reviewed and released with this repository, reserved for extreme cases of built-in skins. They are not — and will not evolve into — the default entry for out-of-repo executable extensions; those belong to the Phase 2+ browser facet.

约束原文：

> - default-export the contract function below;
> - **no top-level side effects**（loading the module must not execute anything）;
> - **no module-level mutable state**: every skin switch is a NEW activation identity, and dispose/cleanup is idempotent (may run 0, 1 or N times).

`SkinHooksContext` 的六层固定装饰层（原文 `layers`）：`background` / `ambient` / `top` / `bottom` / `sidebar` / `foreground`；**「All layers are pointer-events: none; interactive content must go through official slots/ui-primitives instead.」**

#### (4) `official-tokens-v1.json`

- `contractVersion`: 1；`excludedPrefix`: `--dsw-static-`；`count`: **299**（实测数组长度 299，与声明一致）。
- `source`: `official surfaces: @deepseek-ai/dsh-client-ui-theme@0.1.7-rc.1 lib + @deepseek-ai/dsh-web-frontend@0.1.7-rc.1 dist/assets`。
- 命名分布（实测）：`--dsw-font-*` 最多，其余为 `--dsw-alias-*`、`--dsw-shadow-*`、`--dsw-specific-*`、`--dsw-elevation-*` 等。

#### (5) `primary-action-tokens-v1.md`

四元组（原文表格）：

| Token | Role |
|---|---|
| `--dsw-alias-button-primary-fill` | Button background |
| `--dsw-alias-button-primary-hover` | Button background while hovered |
| `--dsw-alias-button-primary-dimmed` | Disabled-button tint |
| `--dsw-alias-label-primary-foreground` | Text on the fill |

**★ 对我们是直接命中的一条禁令（原文）**：

> `--dsw-alias-brand-primary` and `--dsw-alias-brand-primary-invert` are **accent and foreground tokens, not a button pair**: in the current official theme both resolve to the same theme-neutral, so using them as fill + text renders black-on-black (light) or white-on-white (dark). **Never consume them as a button fill.**

消费者规则（原文）：

> A filled primary button uses the set — fill / hover / foreground — **verbatim** … Do not use `brand-primary` as a button background, **do not introduce per-plugin hardcoded accents**, and do not pair the tokens across families.

#### (6) `performance-guidelines-v1.md`

六条规则（原文标题）：

- **R1** — DOM observation must be scoped and short-circuited（禁止从 MutationObserver 回调广播全树扫描；必须缓存 anchor；高churn 区域先 `closest()` 短路）。
- **R2** — Host-glyph fingerprint matching must be one regex pre-scan。
- **R3** — Frame loops and infinite animations must pause when hidden（`visibilitychange` + `animation-play-state: paused`；「Do not write CSS custom properties that nothing consumes」）。
- **R4** — `will-change` must not be parked on full-screen or idle layers（「A static 0px filter (`blur()`) is a no-op; the layer cost is not.」）。
- **R5** — Never interleave layout reads and writes in mutation callbacks。
- **R6** — Delegation of cleanup（每个 observer/listener/timer 必须经 `ctx.onCleanup`，**逆序**拆除，含新增的 global-body 属性）。

验收口径（原文）：

> Long tasks with an aggregate **> 100ms**, or frames on the main busied line during those operations, indicate a violation of the rules above.

### 1.3 契约自述里的「已知脆弱点」（官方自己列的，共 4 条）

原文（`semantic-attrs-v1.md` §已知脆弱点 · 上游主题缝 PR 诉求）：

1. AppFrame 三列容器本体只有 hash 类，列级钩子缺失 → 诉求：三列自带稳定 data 钩子。

**同时实测确认**：主按钮四元组 `button-primary-fill` / `button-primary-hover` / `button-primary-dimmed` / `label-primary-foreground` 与 `brand-primary-invert` —— **我方使用次数均为 0**。

⇒ 若皮肤按契约重映射四元组，我方的实心按钮**完全不跟随**（既不用四元组，也不用 invert）。这才是比「2 处灰区用法」更实质的缺口：**§2.5.4**。

#### 2.5.4 主按钮 token 四元组：完整缺失

| 官方 token | 我方使用次数 | 判定 | 后果（实测推断依据） |
|---|---:|---|---|
| `--dsw-alias-button-primary-fill` | **0** | 缺失 | 皮肤为该 token 设定的主色**不会**作用到我方任何按钮 |

**我方按钮实际靠什么上色**（实测）：`data-dam-btn`（**143 次**出现 / **111 个渲染点**）与 `data-dam-tab` 走的是——

⇒ 结论：**我方按钮的视觉主要由内联样式 + 硬编码色决定，官方 token 只覆盖底色/边框/文字的老三样**。这是 §3-O7 的根。

#### 2.5.5 token 层小结

- 完整缺失的 token 家族：**主按钮四元组（5 个 token 全部 0 次）**。

### 3.1 ★ 过时点 O1（A 级）：契约把「插件」当**被动被标注者**，而非**主动声明者**

**官方原文**（`semantic-attrs-v1.md` · 纪律节）：

> 两个产出通道：**compat adapter**（皮肤中心的合并 MutationObserver，为官方 DOM 与未 opt-in 插件补打属性）与**组件主动输出**（**仓内插件**按 packages/AGENTS.md 约定自行输出，更准更快）。

**我方实测**：

- 我方**不是**「仓内插件」——我方是第三方包 `@a9i5k4/dsh-auto-memory`（`package.json` 实测），与 skin-center 仓库无任何收录关系。
- 官方全库扫描（6 契约文件 + 2 README + `lib/client.js` + `lib/index.js`）**不含** `auto-memory` / `a9i5k4` / `data-dam-` / `data-skin-slot`（实测命中 **0**）。
- 官方 compat adapter 的「补打范围」原文限定为「官方 DOM 与未 opt-in 插件」，而 adapter 是否认得**第三方插件的 DOM**——契约**未作任何说明**。
- 我方**没有** adapter 所依赖的锚点：实测 `data-slot=` 在 `lib/client.js` 中出现 **0 次**（原文说 adapter「从稳定锚点（`data-slot` 出口、`data-chat-flow-kind` 等）」打标）。

**⇒ 过时点**：契约的「两通道」设计假设了「插件源码在官方仓内」这一前提。对**外部分发的插件**，两个通道**都不可达**。这是最根本的一条。

【推断】第三方插件既不在「仓内主动输出」名单，其 DOM 结构对 adapter 又是未知的，故 adapter 大概率**不会**为我方打标——依据是 adapter 补打所依赖的锚点我方一个都不具备（实测 0）。

- **为什么不能由我定**：这决定 §4.5 的 S1/S7 两个施工步骤，且涉及**跨仓库协作**（需向上游提 I6）。任何自declare 都会让契约的「每个枚举值必须有明确 owner、版本、含义」纪律在我方这一侧破口。
- **需要谁定**：**用户**（决定是否向上游提 issue / 是否接受自declare）＋ skin-center 维护者（决定是否开通道）。
- **最小补充信息**：官方是否有「第三方 plugin id 白名单/命名空间」的未公开约定（本机只读无法确认；需问维护者或看其仓库 issue 区）。

### U2 — B 组 4 个泛义 part 的**复用边界**在哪？

- **问题**：`row` / `card` / `header` / `panel` 在官方由 2–3 个 owner 复用。我方能否也复用？复用到什么颗粒度？
- **为什么不能由我定**：「能否被多方复用」是**契约设计决策**，不是实现细节。我方若自行复用，皮肤作者写 `[data-dsh-part="card"]`（不带 plugin 限定）时会**同时命中多方**，造成意料之外的样式。
- **需要谁定**：**用户**（是否接受「必须带 `[data-dsh-plugin]` 限定才生效」的用法约束）。
- **最小补充信息**：插件方的 selector 惯例（我方在 §4.1 已给建议：一律 `[data-dsh-plugin="auto-memory"]` 前缀）。

### U3 — 我方面板缩放手柄能否复用 `resize-handle`？

- **问题**：官方 `resize-handle` 的锚定方式是 `[data-side]`，语义是**列宽手柄**（AppFrame 三列）；我方 `data-dam-resize` 是**面板内缩放**（拖动改变面板尺寸，非列宽）。
- **为什么不能由我定**：语义是否「足够接近」需契约 owner 判断；【推断】若复用，皮肤若按「列宽手柄」写样式（如 `cursor: col-resize`、细长条），会与我方面板的**角落缩放手柄**（`se-resize` 类）冲突。
- **需要谁定**：**用户**（可否接受语义近似）。
- **最小补充信息**：我方手柄的完整交互（是否只右下角、是否双向）。

### U4 — 2 处 `brand-primary` 作按钮底色是否要改？主按钮四元组是否要补？

- **问题**：契约原文「**Never consume them as a button fill**」；我方 **L1930**（侧栏按钮激活背景）与 **L6377**（关闭按钮背景）用了 `color-mix(brand-primary …)`。同时我方对四元组消费率为 **0%**。
- **为什么不能由我定**：① 这两处**都不是契约定义的「filled primary button」**（一处是导航激活态、一处是次要按钮），字面上不违规；② 补四元组会**改变现有视觉**，而项目既有硬约束是「**无确凿证据不得删除/改动既有视觉表现**」。
- **需要谁定**：**用户**（视觉决策）。
- **最小补充信息**：我方是否**存在**真正的「实心主按钮」；在哪个界面（若存在，四元组必须补）。

### U5 — 设置卡外壳（`settings.section`）到底谁渲染？

- **问题**：官方 `plugin-item` 的锚定原文是「`[data-slot="web-ui.plugin.item"]` **内 entry**」——即**卡片外壳属官方**、只有 entry 内容属插件。我方 `settings.section` 卡的外壳是官方渲染还是我方渲染？
- **为什么不能由我定**：**只读代码无法确认**——需要真机 DOM 快照（我方文件里既无 `[data-slot=` 也无卡片外壳 HTML，说明外壳很可能由官方渲染；但这属【推断】）。
- **需要谁定**：需**真机取证**（打开设置页看 DOM），再由用户决定是否向上游要 part。
- **最小补充信息**：一次设置页 DOM 快照（属宿主运行时，本任务为只读调研，未做）。

### U6 — 141 个缺口锚点的**策略**：保留私有名还是全量改名？

- **问题**：是保留 `data-dam-*` 私有属性 + 只加 `data-dsh-plugin` 归属声明（**新增式**），还是把 141 个锚点改名进 `data-dsh-part`（**替换式**）？
- **为什么不能由我定**：① 契约纪律明确要求 part「不能只堆字符串」「防止语义层退化成另一套隐式 DOM API」——把 141 个私有词汇塞进 `data-dsh-part` **正是它要防的**；② 项目既有用户偏好是「对旧版难看的实现做**替换式重写**而非追加式覆盖」，与契约纪律在此**冲突**，需用户裁定优先级。
- **需要谁定**：**用户**。
- **最小补充信息**：用户对「语义属性接入」的期望范围（全覆盖 vs 关键路径）。

### U7 — 12 号文档的 6 图插口协议 vs 官方 manifest，走哪条？

- **问题**：12 号文档设计了 `SKIN_ASSETS` + `data-skin-slot` 的**平行协议**（且运行时零实现，O10）；官方 manifest 的 `contributes` 只有 3 个字段，其中只有 `backgroundMedia` 能装下 6 张图里的 1 张（§4.4）。
