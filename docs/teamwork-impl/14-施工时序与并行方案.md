# 14 · 施工时序与并行方案（可直接排期）

> 用途：把 `06-实施批次与验收.md` 的 11 个批次排成**带并行与依赖的施工时序**，
> 明确「哪些派子智能体 / 哪些 Lead 亲自做 / 哪些必须用户在场」。
> 判据一律回溯 `00-目标冻结书.md`（G-A1…G-I2），**不以"跑通了"结案**。

---

## 一、先说结论：这不是能「挂机跑完」的工程

三条硬约束决定了**人必须在环**，任何调度都绕不过：

| # | 约束 | 后果 |
|---:|---|---|
| 1 | **宿主只能由用户重启**（AI 绝不执行 Stop/Start-Process） | 凡需要"插件以 `teamEnabled=true` 真的跑起来"才能取的证据（G-C3 / G-D1 / G-F2 / G-H1…），**每一轮都必须你重启一次** |
| 2 | **`lib/index.js` 是单写者文件**（962,241 B 现状） | 8 个批次都要改它 ⇒ **索引文件上的改动必须串行**，并行度天然受限 |
| 3 | **G 级验收要求 E2/E3 证据** | **E2 = 真机可观察、E3 = 双向收敛**。E3 的判据是"交换输入顺序 ⇒ 逐字节相同"，**需要两台机器**；单机跑不出来 |

**⇒ 结论：挂机能产出的是"代码 + 单机测试绿"（E0/E1 级），
真正的验收（E2/E3）必须你回来操作。** 这不是组织问题，是证据等级的硬要求。

## 三、并行方案（4 个波次）

### 波次 0 · 无依赖，立刻开工

| 任务 | 执行者 | 触碰文件 | 说明 |
|---|---|---|---|
| B0 基线冻结 | **Lead** | 只读 | 采 B0（开工基线），写进 `_gen/B0.txt` |
| B1-1 技能 id 内容寻址 | 子代理 A | `lib/procedure-store.js` | **不碰 index.js** ⇒ 真并行 |
| B2 的 `team-identity.js` + `team-auth.js` | 子代理 B | 两个新文件 | 纯新文件 ⇒ 真并行 |

**这一切的并行是"真"的**：三个执行者写的文件集合**两两不交**。

### 波次 1 · 装配阶段（Lead 独占 index.js）

| 任务 | 执行者 | 说明 |
|---|---|---|
| B1-2 团队项目 id 接入 | **Lead** | index.js 只改 1 处读取点 |
| B2 index.js 装配 + 14 个配置键 | **Lead** | **必须与 B1-2 同一编辑窗口**，避免两次改同一文件 |
| B3 `team-outbox.js` | 子代理 A | 只依赖 B2 已冻结的**键名**，不需要 index.js |

### 波次 2 · 关键路径

| 任务 | 执行者 | 说明 |
|---|---|---|
| B4 `index.js` 挂心跳 + `team-sync.js` | **Lead**（index.js 部分）+ 子代理 A（新文件） | ★ pre-step 耗时必须**实测** |
| B5 日历双轨 | **Lead** | index.js 四个函数 |

### 波次 3 · 分叉（这里并行度最高）

| 任务 | 执行者 | 触碰文件 |
|---|---|---|
| B6 `team-pull.js` + `team-conflict.js` | 子代理 A | 两个新文件（最大块） |
| **B10 前端团队 UI** | 子代理 B | `lib/client.js` ← **与 index.js 完全不冲突** |
| B9 派生重算调度 | 子代理 B（B10 之后） | 新文件 |

**⇒ B6 与 B10 是本项目唯一的两条"大块真并行"**：
一个改后端单写者，一个改前端单写者，**零重叠**。

### 波次 4 · 收口

| 任务 | 执行者 | 说明 |
|---|---|---|
| B7 注入层合并 | **Lead** | ★最高风险（前缀缓存），必须实测 |
| B8 白板冲突 + 看板两阶段 | **Lead** | index.js |

## 六、建议的最小挂机方案

如果你确定要挂机，**我建议这样切**，让一夜产出最大化且不产生废码：

1. **只跑到 B5 为止**，别碰 B6 之后
   理由：B5 是**首个可演示闭环**，你回来只需重启一次就能拿到 E2 证据。
   B6/B7 涉及合并与注入，**没有真机验证就只能算"写了代码"，风险反而是负的**（未验证的合并逻辑比没有更危险）。
2. **并行只开 2 个子代理**（波次 0 的 A/B），遵守既有并行上限。
3. **每批结束立刻跑全量回归**（181 套件，约 1 分钟），把红绿归属当场判掉。
4. **绝不 commit / push / publish**（沿用既有纪律，等你指令）。

**你回来的验收动作**（约 15 分钟）：
```powershell
node --check lib/index.js
node --check lib/client.js
node tests/smoke/smoke-test.mjs          # 期望 181 PASS / 0 FAIL
Get-FileHash lib\index.js, lib\client.js, package.json -Algorithm SHA256
node docs/teamwork-impl/_gen/baseline-diff.mjs   # G-A1
```
然后**你重启宿主**，我接着取 E2 证据。

## 八、★补漏：皮肤线（ADR-002 的并行轨道）**本卷第一版漏了**

> **自纠**：本卷第一版只排了 B0–B10（后端 + 前端功能），**把 ADR-002 明确要「并行推进」的皮肤线漏掉了**。
> 皮肤线在 `12-皮肤资源插口清单.md` 与 `11-架构决策记录.md` 的 ADR-002 里有完整定义，但**没有进入施工时序**。此处补齐。

### 8.1 皮肤线现在有什么（已存在，不是待建）

| 资产 | 路径 | 规模 |
|---|---|---|
| 皮肤原型 | `docs/teamwork-research/skin/index.html` | **190,355 B / 10 个具名页面 / 4 主题 / 92 token** |

**实测前提**：现有原型是 **0 个 `<img>`、1 个 `<svg>`** —— **100% CSS/SVG 实现**。
⇒ 插口不是「在既有图上改造」，而是**新增一组约定槽位**。

### 8.2 ADR-002 的裁定（用户原话已记录）

> 用户问：皮肤线**是否需要等 GPT-image 画完**才能做？
> 裁定：**先做完、留插口。等图会把并行变成串行。**

**三条理由**：
1. **等图 = 皮肤线被阻塞**，并行名存实亡；
2. 本仓已验证「**追加式覆盖**」手法，插口与之同源；
3. **图片是资源，不是结构** —— 结构定稿后换图是**一行替换**；结构没定就画图，**图会白画**。

### 8.3 皮肤线的 4 个任务（含依赖）

| 任务 | 交付物 | 依赖 | 执行者 | 说明 |
|---|---|---|---|---|
| **S1** | `lib/skin-assets.js`（**新增，纯数据**） | **无** | 子代理 | 与任何批次都不冲突；可**立刻**做 |
| **S2** | 6 个 `data-skin-slot` + 占位样式 | **B10 之后** | 子代理 | 与 B10 同改 `client.js` ⇒ **必须串行** |
| **S3** | 6 张图（**用户用 GPT-image 生成**） | 无（**不阻塞代码**） | **用户** | 随时可做；prompt 须带尺寸+构图+「不要文字」 |
| **S4** | 换图（改 `SKIN_ASSETS` 6 个 `file` 字段） | S1+S2+S3 | 任一方 | **一行替换，结构代码零改动** |

**★ 关键判据（ADR-002 纪律一）**：**代码只认 key，不认文件** ——
代码里**不得出现任何图片路径字面量**。

### 8.4 它挂在哪一波

```
波次 0 ─┬─ S1 skin-assets.js        ← 与 B1-1 / B2 新文件同批，三个新文件并行
        ├─ B1-1 procedure-store.js
```

### 8.5 为什么 S1 能真并行、S2 不能

| | 触碰文件 | 与谁冲突 | 能否并行 |
|---|---|---|---|
| **S1** | `lib/skin-assets.js`（全新） | **无** | ✅ 真并行 |
| **S2** | `lib/client.js`（既有） | **B10** | ❌ 必须串行 |

**⇒ 这正是本卷的主结论在皮肤线上的复现**：
> **能并行的只有「新文件」；碰到单写者文件的一律串行。**

### 8.6 皮肤线的验收（并入 G-H2 / G-H3）

| 目标 | 判据 | 证据等级 |
|---|---|---|
