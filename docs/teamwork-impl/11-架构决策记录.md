## ADR-001（Q1 拍板）· 服务端以阿里云为基准，兼容多云，并覆盖私人用户场景

**用户原话**：
> 这个客户用的是阿里云，所以要以阿里云为基准，兼容 Google Cloud、Amazon Web Service、腾讯云、华为云等平台的内容。
> 同时，也要兼容私人用户。例如：1. 单人多机：看看能不能使用公网暴露同步。2. 单人单机：可以选择关闭 teamwork。

### 这条推翻了 03/04 卷的一个隐含前提

03 卷 `fetchJson` 与 04 卷服务端契约原先**默认「我们提供一个 HTTP 端点」**。
按本条裁定，正确形态是 **「端点位置可换、协议不变」** —— 即**多云可移植层**。

### 决策：把「存储/通道」抽象成 S3 兼容 + HTTP 两档

| 云 | 对象存储 | S3 兼容？ |
|---|---|---|
| **阿里云（基准）** | OSS | ✅ 支持 S3 兼容 API |
| AWS | S3 | ✅ 原生 |
| Google Cloud | GCS | ✅ 有 S3 兼容 XML API（互操作模式） |
| 腾讯云 | COS | ✅ 支持 S3 兼容 API |
| 华为云 | OBS | ✅ 支持 S3 兼容 API |

⇒ **实现上只写一套「S3 兼容客户端」，阿里云是默认配置项** —— 这样「以阿里云为基准」是**默认值**，而「兼容多云」是**架构性质**，不是五套适配器。
⇒ **严禁**在同步层出现任何云厂商专有 SDK 调用（如 `ali-oss`）—— 唯一例外是可选的自建服务端部署模板。

### 私人用户两条场景的处理

**① 单人多机 —— 用对象存储当会合点，不需要服务端**

**用户原话「公网暴露同步」有两种读法，必须分清**：

| 读法 | 做法 | 我的判断 |
|---|---|---|
| **A. 暴露插件宿主端口到公网** | 让另一台机器直连本机 19387 | ❌ **不可行、也不该做** —— 01 卷实测 **56 条路由全部被回环守卫锁死**，这是**安全特性**；为单人多机去破它，等于把整个插件暴露在公网 |
| **B. 用公网上的对象存储当会合点** | 两台机器各自推拉同一个 bucket 前缀 | ✅ **推荐**：零服务端、零端口暴露、复用 ADR 的 S3 兼容层 |

⇒ **采纳 B。** 「公网暴露」的对象是**存储桶**，不是**你的机器**。
⇒ 这也让**私人版与企业版共用同一套同步内核**，只是 endpoint / 凭据不同 —— 实现成本几乎为零。

**② 单人单机 —— 关掉 teamwork**

⇒ 这正是既有设计里的 `teamEnabled = false`（03 卷）。
**本轮确认该开关存在且语义正确**：
- `teamEnabled = false` 时**不注册**任何同步监听器、不建任何网络连接、不写任何同步元数据；
- 行为与**未装团队版**逐字节一致（这条已写进每一批的验收门槛）。

### 对实施的影响

| 批次 | 影响 |
|---|---|
| B1 | 同步层**唯一新增长点**：一个 S3 兼容客户端 + 一个 HTTP 回退。**不引入任何厂商 SDK。** |
| B2 | 配置项里 `endpoint` / `bucket` / `region` / `pathStyle` 四件套；阿里云为默认样板 |
| B4+ | 私人多机 = 同一内核算不同配置；**不新增代码路径**（只新增默认值） |
| 全部 | `teamEnabled=false` 的零副作用门槛照旧 |

## ADR-002（Q2 拍板）· 并行推进，皮肤先做完并留出插口

**用户原话**：
> 我同意并行去做，但是皮肤线会有一些美学的资源，是不是需要通过 GPTimage2，等他画完这些以后才能做，还是可以先做完，留出插口，然后我去生成完以后再插入

### 答复：**先做完、留插口。等图会把并行变成串行。**

**理由（三条，按重要性）**：

1. **等图 = 皮肤线被阻塞，并行就名存实亡。** 皮肤线当前的价值恰恰是「不依赖任何未完成的外部产物」——它能先用占位资源把结构、交互、主题全跑通。
2. **本仓已验证「追加式覆盖」手法**：视觉升级通过**追加一层**实现，既有行零改动、守卫零破坏。插口方式与之同源。
3. **图片是资源，不是结构。** 结构定稿后再换图是**一行替换**；结构没定就画图，图会白画。

### 插口的具体做法（三条纪律）

**纪律一：所有图片只经一个清单引用，代码里不出现任何图片路径字面量。**

~~~js
// lib/skin-assets.js（新增，纯数据）
/**
 * 皮肤资源清单 —— 代码只认 key，不认文件。
 * 换图 = 改本文件一行；结构代码零改动。
 * ★ 缺失时的降级：assetOf() 返回占位符，页面必须看起来仍然是「完整的」。
 */
export const SKIN_ASSETS = Object.freeze({
  'hero.bg':      { file: '', alt: '首页背景', size: '2000x1200', status: 'pending' },
  'empty.state':  { file: '', alt: '空状态插画', size: '600x400',  status: 'pending' },
  'sync.icon':    { file: '', alt: '同步状态图标', size: '96x96',   status: 'pending' },
  // ...（按 10 屏逐屏列全，见 `皮肤资源插口清单.md）
})

/** 取资源：未就绪时返回一个确定性占位（不抛错、不留白）。 */
export function assetOf(key) {
  const a = SKIN_ASSETS[key]
  if (!a || !a.file) return { placeholder: true, key, alt: (a && a.alt) || key }
  return { placeholder: false, url: a.file, alt: a.alt }
}
~~~

**纪律二：占位符必须是「能被误认为成品」的观感，不能是灰色方块。**
⇒ 用**同尺寸、同构图、同色调的 CSS 渐变 + 文字标签**兜底。这样图到位前后，**布局与观感都不塌**，演示随时可做。

**纪律三：每张图必须带尺寸与构图说明。** 否则你生成时只能凭感觉，回来还要我改裁剪。
⇒ 见 `皮肤资源插口清单.md`（本轮产出，可直接拿着去生图）。

### 并行时间线

| 时间 | 皮肤线 | 你（生图） |
|---|---|---|
| 第 1 周 | 结构 + 交互 + 4 套主题 + 占位资源**全部跑通**，可演示 | 按清单产图 |
| 第 2 周 | 图到位，**按清单逐条替换**（每条一行） | 审阅 |
| 之后 | 视觉打磨（不影响功能） | — |

⇒ **你的生图不阻塞任何东西**；图什么时候回，皮肤就在当天变好。

## ADR-003（Q1 补充）· 私人版与企业版共用内核

由 ADR-001 直接推出，但值得单列，因为它**削减了大量实施量**：

| | 企业版 | 私人多机 | 私人单机 |
|---|---|---|---|
| 同步内核 | 同一套 | **同一套** | 不启用 |
| 差异 | endpoint/bucket/凭据 + 审批与角色 | **仅配置** | `teamEnabled=false` |
| 新增代码路径 | — | **0** | **0** |

⇒ **不做两套实现。** 企业版多出来的只是**治理层**（角色、审批、审计），不是**同步层**。
