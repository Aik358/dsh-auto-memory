# ADR-004（Q10 修正）· PLAN 白板改为「条目级增量」，不做整篇重写

> **用户原话**：
> 「哎，能否做成增量加修改的形式呢？其实整篇重写好像并不是我的本意的，有增量和修改的情况，就方便在各个成员之间同步了，这样也可以明确显示是什么时段，谁在修改什么」

---

## 一、你的直觉是对的，而且比你想象的更可行

**先澄清一个事实**：你说的「有增量和修改」**在白板的存储层已经存在了** —— 我上一轮没说清楚。

**实测 `PLAN.md` 现状**：

| 事实 | 数值 |
|---|---|
| 全文大小 | 19,270 B |
| `## ` 级条目数 | **14 个** |
| 卡锚点 `<!--memory:mem_...-->` | **12 个** |
| 其中带锚点的条目 | 7 个 / 14 |

**每个条目长这样**（真实片段）：

~~~markdown
## ★E3-FIX-3：两个周期二合一（2026-09-26 · 用户指令「...」）
<!-- memory:mem_7410069339a7b896e293644e40b17866 -->
type:progress
**用户判断成立**：设置页原先有「工作台轮换周期（天）」...
~~~

⇒ **条目是天然独立单元、且已有稳定 id**。
⇒ **「条目级增量」不是要新建体系，而是要停止把整篇当成一个 blob。**

---

## 二、为什么会「整篇重写」—— 根因

**不是设计选择，是一个具体的实现缺陷**：

`memory_note(kind=plan)` 走的是**整篇覆盖**语义：
- 调用方**必须提供完整新全貌**（不能只给一条）
- 插件**保护门**逐条比对前后卡片集合（缺锚点会被拒 → 这正是「防锚点击穿」那条规则）

⇒ 结果：**改一条 = 重发 14 条**。同步时这 14 条**全部**被当成变更。所以：
- 两个成员各改一条 ⇒ 两份「整篇」冲突 ⇒ **必须人工裁决**
- 也无法回答「**谁在什么时间改了什么**」——因为每次都是全量

**你感到别扭的正是这个：一次意图上只改一条的操作，在数据层表现为全篇改写。**

---

## 三、改造方案：条目级 CRDT-lite

**核心思路**：把 `## ` 级条目当**独立实体**，各有自己的时钟。

~~~js
// lib/plan-entry.js（新增，纯函数）
import { createHash } from 'node:crypto'

/**
 * 条目 id：内容寻址但**不含正文**（正文会变，id 不能变）。
 * 依据：wb-sidecar.js:78 wbEntryIdPre 的同一思路 —— sha256(作用域 \0 定位符)。
 * 为什么用标题+锚点而非序号：序号会因插入/删除而漂移，导致 id 复用错对象。
 */
export function planEntryIdOf(projectId, heading, anchor) {
  const basis = String(projectId) + '\0' +
                (anchor || normalizeHeading(heading))       // 锚点优先，无锚点退化到标题
  return 'pe_' + createHash('sha256').update(basis, 'utf8').digest('hex').slice(0, 32)
}

/** 标题归一：去装饰符、压缩空白 —— 保证两端算出同一 id。 */
export function normalizeHeading(h) {
  return String(h || '').replace(/^#+\s*/, '').replace(/[★☆\s]+/g, '').trim().toLowerCase()
}

/** 把整篇 PLAN.md 解析成条目数组（纯函数，无 IO）。 */
export function parsePlanEntries(projectId, markdown) {
  const parts = String(markdown || '').split(/^(?=## )/m).filter((s) => s.startsWith('## '))
  return parts.map((raw) => {
    const firstLine = raw.split(/\r?\n/, 1)[0] || ''
    const heading = firstLine.replace(/^##\s*/, '')
    const m = /<!--\s*memory:(mem_[0-9a-f]{32})\s*-->/.exec(raw)
    const anchor = m ? m[1] : ''
    return {
      id: planEntryIdOf(projectId, heading, anchor),
      anchor,
      heading,
      body: raw.slice(firstLine.length).replace(/^\r?\n/, ''),
    }
  })
}
~~~

### 合并规则：**条目级 LWW + 粒度访问控制**

| 情形 | 处理 |
|---|---|
| **两条改的是不同条目** | ✅ **自动合并，无需人工** —— 各自独立，互不冲突 |
| 两条改的是**同一条目** | 走 **P1 字段级 LWW**：比时钟 → 新者胜 |
| 同一条目 + **时钟也一样** | 比内容哈希（**三级排序键**，04 卷附录 A 的教训）⇒ 确定性，两端一致 |
| 一方**新增**条目 | ✅ 直接并入（P2 append-only） |
| 一方**删除**条目 | 走 **P5 墓碑**：只记录不真删（与既有裁定「superseded = 返回但标记」一致） |

**★ 关键收益**：原本「4 处需要人工裁决」里的**白板这一处，降级为只在「同一人同一条目同时改」时才需要**。
⇒ **冲突面大幅收窄。**

## 四、你要的「谁在什么时段改了什么」—— 直接可得

条目级化之后，审计信息**自然产生**：

~~~js
// 每条变更都带时钟与来源
const change = {
  entryId: 'pe_...',              // 哪一条
  op: 'upsert',
  clock: { wall: 1758800000000, seq: 42, device: 'desktop-jhz' },
  actor: 'zhangsan',              // 谁（来自团队身份）
  at: '2026-09-26T16:52:00+08:00',
  diffSummary: '标题未变，正文 +312 字',   // 可直接渲染
}
~~~

**前端可显示**（这就是你在 Q5 里选的「同步状态条」里的内容）：

~~~
┌─ 白板变更 ────────────────────────────┐
│ 16:52  张三   修改「E3-FIX-3」+312 字   │
│ 15:04  李四   新增「F 线收尾」           │
│ 昨天   张三   撤回「旧 GC 设计」          │
└───────────────────────────────────────┘
~~~

**注意**：这一段**不需要额外开发** —— `lib/wb-sidecar.js` 的 `buildVersionsPre`（L453）**已经在建版本链**，`traceByIdPre`（L551）**已经能按 id 回溯**。
⇒ **改造量远小于新建一套。**

## 五、但必须守住两条底线（否则会退化）

**底线一：Markdown 永远是唯一真源。**
条目级化只改**同步粒度**，**不改存储形态** —— 磁盘上仍然是一个 `PLAN.md`，仍然是人类可读的 Markdown。
⇒ 绝不允许为同步另建一个「真源文件」。

**底线二：保护门不能失效。**
`memory_note(kind=plan)` 的锚点比对保护门是**为防止丢卡**而存在的（「防锚点击穿」）。
条目级合并**必须**在合并后**重新校验全量锚点集合** —— 否则合并可能静默丢卡。

~~~js
/**
 * 合并后守卫：合并结果必须包含双方锚点的并集。
 * 依据：既有的「防锚点击穿」纪律 —— 丢卡是静默的、事后难查，必须前置断言。
 */
export function assertNoAnchorLoss(before, after) {
  const want = new Set([...before.mine, ...before.theirs])
  for (const a of want) {
    if (!after.anchors.has(a)) {
      throw new Error('合并丢卡：锚点 ' + a + ' 在合并结果中消失（fail-closed）')
    }
  }
  return true
}
~~~

**★ fail-closed**：断言失败时**不写盘**，报错给人看。丢一条白板卡比报一次错严重得多。
