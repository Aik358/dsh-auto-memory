# 13 · 同步协议到底是什么？阿里云 / 腾讯云 / 其它云怎么落地

> **本卷专为回答一个被问了两次的问题**：「如果我用阿里云或者腾讯云的话，这个协议的同步该怎么做呢？」
> 上一轮我没讲清楚，责任在我。本卷用**一张表 + 一段可跑代码**把它钉死。

---

## 一、先破除一个误解：**「同步协议」不是某家云的协议**

**关键区分**：

| 层 | 是什么 | 会不会因云而异 |
|---|---|---|
| **① 同步语义层**（我们的协议） | 谁赢、怎么合并、冲突怎么办 | ❌ **完全不变** |
| **② 传输层**（搬字节） | HTTP PUT / GET / LIST | ⚠️ **换 endpoint 与签名** |
| **③ 存储实现** | 阿里云 OSS / 腾讯云 COS / S3 … | ✅ 各家不同，但被 ② 抹平 |

⇒ **换云 = 只换第 ② 层的一行配置。第 ① 层（也就是「同步协议」本身）一个字都不改。**

**这就是为什么我建议「S3 兼容」而不是「写五个适配器」**：
阿里云 OSS、AWS S3、腾讯云 COS、华为云 OBS、GCS **全部提供 S3 兼容 API**（已核官方文档，见 `五）。

## 二、一张表：同步到底在同步什么

**同步面只有 4 类数据**（这是 01 卷的实测结论，不是设计偏好）：

| 类别 | 内容 | 同步吗 | 怎么同步 |
|---|---|---|---|
| **S0 本机私有** | 会话原文、绝对路径、本机时钟 | ❌ **绝不出站** | — |
| **S1 个人云** | 私人用户的跨机记忆 | ✅ 可选 | 同一套通道 |
| **S2 团队共享** | 白板 / 账本 / 规则 / 技能 / 事实库 | ✅ **核心** | 对象存储 PUT/GET |
| **S3 派生重算** | `index.json` / 向量 / 摘要缓存 | ❌ **不同步** | 各端本地重建 |

**为什么 S3 不同步**：它是**可重建的投影**。同步它 = 制造第二真源 = 两端不一致的新来源。
（依据：`lib/wb-sidecar.js:9-10` 明文「index.json 完全可重建」）

## 三、协议本体：一次同步到底发生什么

**六个原语**（04 卷详述），云无关：

| 原语 | 含义 | 用在 |
|---|---|---|
| **P1 字段级 LWW** | 同字段比时钟，新者胜 | 事实库字段 |
| **P2 append-only log** | 只追加，不改旧行 | 日历 / 审计 |
| **P3 OR-Set** | 增删并存，删带标记 | 标签 / 成员 |
| **P4 两阶段移动** | 先占位再落位 | 归档 / 迁移 |
| **P5 墓碑** | 删除只记录不真删 | 撤回 / 作废 |
| **P6 重算** | 不传结果，传输入 | 索引 / 向量 |

**一次 push 的完整流程**（以改了一条白板卡为例）：

~~~js
// lib/teamwork-sync.js（新增，示意）
async function pushOnce(client, projectId, localChanges, clock) {
  for (const ch of localChanges) {
    // ① 组装信封：只含可共享字段（白名单，绝不含绝对路径）
    const env = {
      projectId,                    // 内容寻址 id（见 ADR-001）
      entityId: ch.id,              // 内容寻址：sha256(ws\0relPath\0title)
      entityKind: ch.kind,          // 'plan-card' | 'handoff' | 'rule' | 'skill' | 'fact'
      op: ch.op,                    // 'upsert' | 'tombstone'
      payload: ch.payload,          // 白名单字段
      clock: { wall: clock.wall, seq: clock.seq, device: clock.device },
      hash: sha256Of(ch.payload),   // 内容哈希：用于三级排序（P2 必需）
    }
    // ② 写进「变更日志」路径：append-only，不覆盖
    const key = `${projectId}/log/${clock.wall}-${clock.device}-${clock.seq}.json`
    await client.put(key, JSON.stringify(env))
  }
}

async function pullOnce(client, projectId, since) {
  // ③ 列出变更日志（S3 的 LIST 就是"拉"）
  const keys = await client.list(`${projectId}/log/`, { since })
  // ④ 逐条取出 → 按原语合并 → 本地写盘
  for (const k of keys) {
    const env = JSON.parse(await client.get(k))
    await mergeByPrimitive(env)   // ← 协议语义全在这一步，与云无关
  }
}
~~~

**注意**：`client.put` / `client.get` / `client.list` 是**唯一的云相关接口** —— 就是这三个。
换云只改它们的实现（其实连实现都不用改，只改 endpoint 与凭据）。

## 四、多云落地：**endpoint 配置表**（你要的答案）

**同一个 S3 兼容客户端**，只换下面四件套：

| 云 | 服务 | endpoint 形态 | 签名 | path-style |
|---|---|---|---|---|
| **阿里云（基准）** | OSS | `https://oss-cn-hangzhou.aliyuncs.com` | S3 兼容（V4 或 V2） | 需确认，通常开 |
| AWS | S3 | `https://s3.us-east-1.amazonaws.com` | V4 | 可选 |
| **腾讯云** | COS | `https://cos.ap-guangzhou.myqcloud.com` | S3 兼容 V4 | 需开 |
| 华为云 | OBS | `https://obs.cn-north-4.myhuaweicloud.com` | S3 兼容 | 需开 |
| Google Cloud | GCS | `https://storage.googleapis.com`（互操作模式） | 需用 HMAC 密钥 | 视配置 |

**配置项（只这四个 + 两个开关）**：

~~~js
// config.json 里的 team 段（示意）
{
  "teamEnabled": true,
  "syncTransport": "s3",              // 's3' | 'http'（自建服务端）
  "endpoint": "https://oss-cn-hangzhou.aliyuncs.com",
  "bucket": "my-team-memory",
  "region": "cn-hangzhou",
  "pathStyle": true,                  // 多数国内云需要开
  "accessKeyId": "***",               // 凭据走系统密钥环，不写进配置
  "prefix": "dsh-auto-memory/"
}
~~~

**★ 关键纪律：严禁在同步层出现任何厂商专有 SDK。**

~~~js
// ❌ 禁止
import OSS from 'ali-oss'             // 绑死阿里云
import COS from 'cos-nodejs-sdk-v5'   // 绑死腾讯云

// ✅ 正确：只用 S3 兼容协议（可以用 @aws-sdk/client-s3，它讲的是协议不是厂商）
// 或者干脆手写：三个动词就够 —— PUT / GET / LIST
~~~

⇒ **这条纪律（`modules/99-后端改造汇总.md` 的 WS1）就是「以阿里云为基准、兼容多云」的实现方式。**

## 五、官方依据（已核实）

四个云均有官方 S3 兼容文档：

- 阿里云 OSS：[Compatibility with Amazon S3](https://help.aliyun.com/en/oss/developer-reference/compatibility-with-amazon-s3) —— 明写支持 S3 协议，且区分 virtual-hosted / path-style 两种寻址
- 腾讯云 COS：[通过 S3 兼容方式访问 COS](https://www.tencentcloud.com/document/product/436/32537)
- Google Cloud：[Interoperability with other storage providers](https://docs.cloud.google.com/storage/docs/interoperability)
- 华为云 OBS：支持 S3 API（[相关实践](https://developer.huawei.com/consumer/cn/forum/topic/0203171281845200560)）

**★ 但有一个必须实测的差异点**：各家对 S3 的**实现程度不同**。已知差异：
- 阿里云 OSS：`x-oss-process` 参数在 S3 协议下语义不同（我们用不到）
- **ETag 算法不同**：分片上传时 OSS 与 S3 的 ETag 计算方式**不一样**
- ACL 定义有差异

⇒ **我们不用 ETag 做一致性判定**（改用自己算的内容 sha256），这条差异**自动免疫**。
**这是「自算哈希」这个设计的意外红利** —— 04 卷附录 A 里 P2 的三级排序键已经用了它。

## 六、私人用户两条场景（你 Q1 里点名的）

### 场景 1：单人多机

**⭐ 你原话说的「公网暴露同步」，必须先纠正一个理解**：

| 读法 | 判断 |
|---|---|
| **把插件宿主端口暴露到公网**，让另一台机器直连本机 | ❌ **不可行、也不该做** |
| **用公网上的对象存储当会合点** | ✅ **推荐** |

**为什么第一种不行**：01 卷实测，**56 条路由全部被回环守卫锁死** —— 这是**安全特性**，不是疏漏。
为「单人多机」去破它，等于把这个插件挂到公网给任何人调。**代价与收益完全不成比例。**

**正确做法（零服务端）**：

~~~js
// 私人多机：两端各自推拉同一个 bucket 前缀
// A 机（办公室）  → PUT  →  oss://my-bucket/dsh-personal/{projectId}/log/...
// B 机（家里）    → GET  ←  同一个前缀
//
// 不需要任何服务器、不需要开放任何端口、不需要固定公网 IP。
// 「公网」暴露的是【你的存储桶】，不是【你的机器】。
~~~

**附带好处**：这与企业版**共用同一套同步内核** —— 只是 endpoint 与 bucket 不同。
⇒ **私人多机的新增代码量 = 0**（只需一份配置）。

### 场景 2：单人单机

⇒ `teamEnabled: false`

**语义（03 卷已定义，本轮确认）**：
- 不注册任何同步监听器
- 不建立任何网络连接
- 不写任何同步元数据
- **行为与未装团队版逐字节一致**（这是每批验收的门槛）

## 七、一句话回答你的问题

> **「这个协议的同步」= 六个同步原语 + 三个对象存储动词（PUT/GET/LIST）。**
> **换云只改 endpoint 与签名，协议本身不变。**
> **阿里云是默认样板，腾讯云/华为云/AWS/GCS 填不同的四个字段即可。**

**禁止做法**：为每家云写一个 SDK 适配器 —— 那是**五套代码、五个 bug 面、五次回归**，而它们的差异**只需要四个配置字段**就能覆盖。
