## ★ 1. 团队服务端由谁部署？（阻塞全体）

**背景**：01 卷实测证明 —— **插件不能接收服务端入站连接**（56 条路由全被回环守卫锁死）。⇒ 架构上只能是"**客户端推 + 客户端拉**"，服务端必须是一个**可由客户端主动访问的 HTTP 端点**。

**选项**：

| 选项 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 我们自建 SaaS** | 我们运营服务端 | 客户零运维；升级统一 | 需我们承担数据合规责任；客户可能不接受数据出内网 |
| **B. 客户自建** | 交付 Docker 镜像，客户部署在自己内网 | 数据不出内网（**企业最爱**）；合规简单 | 客户需要运维能力；版本碎片化 |
| **C. 局域网过渡** | 暂不做服务端，先做"共享目录同步"（复用 migrate-pack 通道） | **零服务端即可演示**；风险最低 | 无实时性；适合 ≤5 人小团队 |

**我的建议**：**C 先行做演示，B 作为正式交付形态，A 作为可选托管**。
理由：C 能在**本轮之后立刻做出可演示的东西**（不依赖任何服务端开发），先用它向客户证明"团队记忆"的体验；B 是最符合企业采购习惯的形态。

**影响面**：决定了 03 卷 `2.3 `fetchJson` 的实现目标（SaaS 端点 vs 客户内网端点 vs 无端点）。

## ★ 2. 先起皮肤线吗？（不依赖同步，最快见效）

**背景**：皮肤（`docs/teamwork-research/skin/` 已有 10 屏原型）与同步**完全解耦** —— 它只改 `client.js` 的追加段与 CSS 变量。

**选项**：
- **A. 先做皮肤** —— 1–2 周可见效果，客户能立刻看到"我们定制的样子"；
- **B. 先做同步** —— 能力先行，但客户看不到视觉变化；
- **C. 并行** —— 两条线互不冲突（皮肤改 `client.js` 追加段，同步改 `index.js` + 新增文件）。

**我的建议**：**C 并行**，但**皮肤优先入演示**。
理由：皮肤工作量小（追加式覆盖，本仓已验证手法）、客户感知强、且**零风险**（不动 `index.js`）。

## 3. 团队项目 ID 怎么生成？（B1-2 的输入）

**背景**：`wsKey` 按本机路径派生 ⇒ 跨机不汇合（**身份级缺陷**）。需要与路径无关的团队项目 ID。

**选项**：
| 选项 | 生成方式 | 风险 |
|---|---|---|
| **A. 管理员登记** | 客户在团队设置里手填 | 需要人工；但最可控 |
| **B. git remote 派生** | 从 `remote.origin.url` 规范化哈希 | **有 git 的团队零配置**；无 git 则退化 |
| **C. 服务端分配** | 首次连接时服务端给 ID | 需要服务端；离线不可用 |

**我的建议**：**B 优先、A 兜底、C 可选**（就是 03 卷 `2.5 已实现的优先级）。
**需你确认**：无 git 且未登记时的降级行为 —— **是否接受"仅本机共享"并在 UI 明确提示**？（我的实现是接受 + 提示，因为静默失败更糟。）

## 4. 加密策略？

**背景**：你此前的裁定是"**开源不加密 + 企业自持密钥 + 必须明示明文**"。团队版引入服务端后，这条需要再确认。

**选项**：
- **A. 完全沿用既有裁定**：明文存服务端，靠传输层 TLS + 访问控制；
- **B. 传输加密 + 落库明文**（同 A，但明确写进合同）；
- **C. 端到端加密**：插件侧加密后上行，服务端只见密文 —— **代价**：服务端无法做冲突检测与检索，**会推翻 04 卷的服务端设计**。

**我的建议**：**A/B**（即沿用你的既有裁定）。
**理由**：选 C 会让"服务端自动冲突检测"完全失效，且团队检索无法工作 —— 与产品目标冲突。**必须主动向客户披露明文存储**（这是既有要求）。

## 5. 冲突中心要不要做成默认页签？

**背景**：04 卷设计里，只有 **4 处**需要人工裁决（用户规则整篇 / 项目笔记 / PLAN 白板 / 通用库技能晋升）。其余全部自动解。

**选项**：
- **A. 独立页签**（第 14 个 tab）；
- **B. 嵌在同步状态条里**（有冲突才展开）；
- **C. 只在设置页**。

**我的建议**：**B**。理由：4 处冲突是低频事件，做成常驻页签会占位置且在"零冲突"时显得空洞；但**必须显眼**（有冲突时状态条变色 + 数字徽标）。

## 6. 影子检索的匿名上报默认开还是关？

**背景**：`shadow-retrieval` 记录"召回了但没被用"的记忆。团队版若汇总这些数据，能改进共享库质量 —— 但这是**行为数据**。

**我的建议**：**默认关闭**，在团队设置里显式开启并说明收集什么。理由：默认收集行为数据在企业采购里是红线。

## 7. 团队收件箱需要几人确认？

**背景**：团队记忆入库若需审批，需要定"几个人同意才算通过"。

**选项**：1 人（任一管理员）/ 2 人（双人复核）/ 按条目风险分级。

**我的建议**：**默认 1 人（管理员）**，高风险条目（如用户级规则、通用库技能晋升）可配置为 **2 人**。

## 8. 证据链原文是否上云？

**背景**：`evidence-store` 保存证据原文。它可能包含**会话片段**（含敏感内容）。

**选项**：
- **A. 只上云"摘要 + 哈希"**，原文留本机；
- **B. 原文上云**（团队可查完整证据）；
- **C. 按条目可选**。

**我的建议**：**A 为默认，C 为可选**。理由：证据原文是隐私风险最高的一类数据；只传哈希仍能验证一致性（这也正是哈希的用途）。

## 9. 高风险技能的审批人是谁？

**背景**：`memory_procedure` 的 `riskLevel: 'high'` 条目（本仓定义：high 需人工批准后才可激活）。

**我的建议**：**团队管理员 + 至少一位该领域成员**（双签）。需你确认角色命名（见第 11 条）。

## 10. 白板冲突默认策略？

**背景**：PLAN 白板是"整篇重写"语义（`memory_note(kind=plan)` 整体覆盖），字段级合并无意义。

**选项**：保留双方 / 保留较新 / 逐区块合并。

**我的建议**：**保留双方**（都存，人工裁决），**默认不自动合并**。
**理由**：白板是全项目的心智地图，自动合并会产生"四不像"的第三版，比两个人各自的版本都差。**这也是 05 卷 `3.8 已实现的行为。**

## 11. 访客角色与命名？

**背景**：需要定义角色体系。

**我的建议（三人最小集）**：

| 角色 | 权限 |
|---|---|
| **owner（所有者）** | 全部：成员管理、策略下发、删除团队库 |
| **admin（管理员）** | 审批、冲突裁决、策略配置（不能删团队） |
| **member（成员）** | 读写团队库、提审、看冲突（不能裁决他人的） |
| **guest（访客）**（可选） | **只读**团队库，不写入 |

**需你确认**：是否需要 `guest`？以及中文叫什么（"访客"/"只读成员"）。
