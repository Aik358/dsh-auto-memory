## 0. 本契约的地位与边界

| 层 | 谁负责 | 本契约是否可改 |
|---|---|---|
| 既有结构层（13 页签 / 9 分区 / 163 锚点） | 产品方 | **不可动**，§7 给出兼容证明 |
| **团队版新增结构层**（8 个屏幕的 DOM / 交互 / 路由） | 产品方 | **本契约即规格** |
| 皮肤层（颜色/字体/圆角/间距/动效/插槽） | 皮肤作者 / 企业 IT | **不在本契约重定义** —— 一律引用 `skin-token-contract.md` 的 `--skin-*` 与 `12-前端皮肤接口契约.md` 的 token 名与 7 个插槽，见 §6 |
| 行为层（记忆读写 / 召回 / 同步算法） | 产品方后端 | 本契约只引用其 HTTP 契约，不定义算法 |

**三条不变量**（贯穿全文）：

1. **零新增全局状态源**：团队版所有跨屏状态挂到既有模块级 `controller`（`lib/client.js:145-199`）+ `emit()`（:134）+ `useTick`（:2287）。
2. **零新增请求通道**：所有请求经 `apiGet`/`apiPost`（:1652/:1658），所有配置写经 `saveConfigPatch`（:1670），所有配置读经 `configOf`（:1695）。
3. **零裸色值**：新增组件一律 `var(--skin-*)`；本机沿用 `--dam-*` 的 23 个变量做尺度/动效。

## 2. 屏幕① 同步状态条（Sync Status Bar）

**位置**：记忆会话页顶栏（`data-dam-page-head`，:5940）下方新增一行；浮层形态下压缩成图标 + 数字（不展开）。

**DOM 契约**（全部新锚点，前缀 `data-dam-team-`）：

| 锚点 | 角色 | 含义 | 数据字段 |
|---|---|---|---|
| `data-dam-team-statusbar` | 容器 | 整条状态条 | — |
| `data-dam-team-state` | 控件（按钮） | 状态胶囊，点击展开详情 | `state.phase` ∈ `synced \| syncing \| offline \| conflict \| paused` |
| `data-dam-team-queue` | 容器 | 待同步队列计数 | `queue.pending`、`queue.inflight`、`queue.failed` |
| `data-dam-team-lastsync` | 容器 | 最后同步时间（相对时间） | `state.lastSyncAt`（ISO8601）、`state.lastSyncBy`（成员 id） |
| `data-dam-team-conflict-badge` | 控件（按钮） | 冲突计数徽标 | `conflicts.open` |
| `data-dam-team-pause` | 控件（开关） | 暂停/恢复同步 | 写 `config.team.syncPaused`（**本机开关，不广播**） |

**五种状态与配色**（只引用皮肤 token，不写字面色值）：

| phase | 文案键 | 颜色 token | 图标语义 |
|---|---|---|---|
| `synced` | `teamSyncSynced` | `--skin-color-ok` | 对勾 |
| `syncing` | `teamSyncSyncing` | `--skin-color-brand` | 旋转 |
| `offline` | `teamSyncOffline` | `--skin-color-text-tertiary` | 断线 |
| `conflict` | `teamSyncConflict` | `--skin-color-warn` | 警示 |
| `paused` | `teamSyncPaused` | `--skin-color-text-secondary` | 暂停 |

**路由**：

```
GET  /api/dsh-auto-memory/team-state            → { state:{phase,lastSyncAt,lastSyncBy,serverSeq,localSeq}, queue:{pending,inflight,failed}, conflicts:{open} }
POST /api/dsh-auto-memory/team-sync-now         → { ok:true, requestId }         # 手动触发一次同步
POST /api/dsh-auto-memory/team-sync-pause       → { ok:true, paused:boolean }    # 本机暂停开关
```

**刷新策略**：进入屏①拉一次；之后只由**两条通道**驱动——① 手动 ⟳（复用面板既有 nonce，:5973/:6065）；② 同步事件推送（若企业版有 SSE/WebSocket 通道，否则退化为 30s 轮询，与 `OverviewTab` 的 30s 自动重拉同范式，:3632-3652）。**不得**新增第三个定时器源。

**降级**：`GET /team-state` 失败 ⇒ 状态条整体折叠成一行 `data-dam-team-state="offline"`，**不阻塞**其余 13 个页签（调用点必须 `.catch`，与 :3861 等处同范式）。

## 3. 屏幕② 团队成员与在场（Members & Presence）

**位置**：屏①下方或独立分段；浮层形态只显示头像行（最多 5 个 + `+N`）。

| 锚点 | 角色 | 含义 | 数据字段 |
|---|---|---|---|
| `data-dam-team-members` | 容器 | 成员列表 | — |
| `data-dam-team-member` | 容器 | 单个成员卡 | `member.id / name / avatarUrl / role / joinedAt` |
| `data-dam-team-member-self` | 容器（属性） | 标记「我」的那一个 | `member.isSelf === true` |
| `data-dam-team-presence` | 容器（属性） | 在场状态 | `presence.state` ∈ `online \| idle \| offline` |
| `data-dam-team-presence-dot` | 容器 | 状态点（复用皮肤 `radius.pill`） | 同 `presence.state` |
| `data-dam-team-member-filter` | 控件（select） | 按成员筛选记忆 | 写 `view.filterActor`（**本机视图状态**，不上传） |

**在场判据（前端只做显示，不做判定）**：`presence.state` 与 `presence.lastSeenAt` 全部由后端给；前端**不得**用本地时间自行推算在线（避免多机时钟差误判）。前端唯一的本地派生是「最后活跃 ≤ 90s 视为 online」的**展示兜底**，且必须在 `data-dam-hint` 里标注「本地估算」。

**路由**：

```
GET /api/dsh-auto-memory/team-members    → { members:[{id,name,avatarUrl,role,joinedAt,isSelf}], me:{id} }
GET /api/dsh-auto-memory/team-presence   → { presence:{ [memberId]: {state,lastSeenAt,client} } }
```

**空态**：未加入团队 ⇒ `members.length === 0` 时渲染 `data-dam-team-members` 内一段说明（文案键 `teamNotJoined`）+ 一个「加入团队」按钮（跳团队设置分区 ⑦）。

## 5. 屏幕④⑤⑥（冲突中心 / 技能审批 / 交接账本）

### 5.1 屏幕④ 冲突中心（双栏差异 + 裁决）

**布局**：左栏「本机版本」/ 右栏「团队版本」，中间裁决动作区；移动端（容器 < 720px，判据用既有的 `--dam-measure` 断点思路）退化为上下堆叠 + 顶部切换。

| 锚点 | 角色 | 含义 | 数据字段 |
|---|---|---|---|
| `data-dam-team-conflicts` | 容器 | 冲突列表 | — |
| `data-dam-team-conflict` | 控件（行，可选中） | 单条冲突行 | `conflict.id`、`conflict.memoryId`、`conflict.kind` |
| `data-dam-team-conflict-head` | 容器 | 冲突头（标题 + 时间 + 双方） | `conflict.title`、`conflict.detectedAt` |
| `data-dam-team-diff` | 容器 | 双栏差异容器 | — |
| `data-dam-team-diff-local` | 容器 | 本机侧（`conflict.base`） | `conflict.local` |
| `data-dam-team-diff-remote` | 容器 | 团队侧（`conflict.remote`） | `conflict.remote` |
| `data-dam-team-diff-line` | 容器（属性 `data-op`） | 差异行，`data-op` ∈ `same \| add \| del` | 由 `conflict.diff[]` 渲染 |
| `data-dam-team-verdict` | 容器 | 裁决动作区（**同时是皮肤插槽 `conflict.actions` 的挂载点**） | — |
| `data-dam-team-verdict-keep-local` | 控件（按钮） | 采用本机 | POST `team-conflicts/resolve` `{id,choice:'local'}` |
| `data-dam-team-verdict-keep-remote` | 控件（按钮） | 采用团队 | `{choice:'remote'}` |
| `data-dam-team-verdict-merge` | 控件（按钮） | 手工合并（进入编辑态） | `{choice:'merge',content}` |
| `data-dam-team-verdict-ask` | 控件（按钮） | 交由他人裁决（指派） | `{choice:'delegate',assignee}` |

**路由**：

```
GET  /api/dsh-auto-memory/team-conflicts               → { items:[{id,memoryId,kind,title,detectedAt,local,remote,diff:[{op,text,aLine,bLine}]}], open:N }
POST /api/dsh-auto-memory/team-conflicts/resolve       → { ok:true, applied, newSeq }   # body: {id,choice,content?,assignee?}
POST /api/dsh-auto-memory/team-conflicts/delegate      → { ok:true, assignee }
```

**裁决的不可逆提示（硬要求）**：`choice` 为 `local`/`remote` 时，按钮文案必须带损失说明（文案键 `teamVerdictLocalWarn` / `teamVerdictRemoteWarn`），且**首次点击只进入确认态**（第二次点击才提交）—— 与 `ConnectTab` 的 `removeArm` 二次确认同范式（:5734）。

**与皮肤的关系**：`data-dam-team-verdict` 同时暴露给插槽 `conflict.actions`（`skin-token-contract.md` §五 第 7 项，**只允许追加按钮，不允许覆盖**）。插槽按钮若调用 `ctx` 未提供的后端动作，必须自己 `fetch`（契约允许），但**失败必须在自己按钮旁提示**，不得影响裁决区默认按钮。

### 5.2 屏幕⑤ 团队技能审批（Team Skills Approval）

**基线**：复用既有 `skills` 设置分区（:7655–7675）的统计闸门口径（`procedureMinSessions`/`procedureMinSuccess`/`procedureCorrectionCap`）与 `memoryHub` 的晋升理由文案（`hubWhy*` 系列，:621–629）。

| 锚点 | 角色 | 含义 | 数据字段 |
|---|---|---|---|
| `data-dam-team-skills` | 容器 | 待审批列表 | — |
| `data-dam-team-skill` | 容器 | 单条候选技能 | `skill.id`、`skill.title`、`skill.riskLevel` |
| `data-dam-team-skill-owner` | 容器 | 提交人（成员标识） | `skill.ownerId` → 成员名 |
| `data-dam-team-skill-evidence` | 容器 | 证据（复用 `hubEvLine` 文案格式） | `skill.evidence{seen,success,sessions,reused,corrections}` |
| `data-dam-team-skill-steps` | 容器 | 步骤预览 | `skill.steps[]` |
| `data-dam-team-skill-approve` | 控件（按钮） | 批准（晋升为团队技能） | POST `team-skills/approve` |
| `data-dam-team-skill-reject` | 控件（按钮） | 拒绝（须填原因） | `{action:'reject',reason}` |
| `data-dam-team-skill-edit` | 控件（按钮） | 修改后批准 | `{action:'edit',steps,criteria}` |

**审批权判据（前端只显示，不判定）**：后端返回 `skill.canApprove`（boolean）+ `skill.approveBlockedReason`（字符串键）。前端**不得**用本地角色推断能否审批（多团队场景下本地 role 不可靠）。

**路由**：

```
GET  /api/dsh-auto-memory/team-skills                  → { items:[{id,title,ownerId,riskLevel,steps,criteria,evidence,canApprove,approveBlockedReason}], pending:N }
POST /api/dsh-auto-memory/team-skills/approve          → { ok:true, action:'approve'|'reject'|'edit', promoted?:boolean }
```

**风险分级呈现**：`riskLevel === 'high'` 必须显式二次确认（沿用 `procedureHighRiskApproval` 的语义）；`medium`/`low` 直接提交。

### 5.3 屏幕⑥ 交接账本（按人分色 + 接续链）

**基线**：复用既有 `PlanTab`（:4698–4980）与 `API.handoffState`（:4578/:4616/:4780/:4805）。团队版**只加两件事**：① 每段账本按作者着色；② 把「谁接了谁的班」画成链。

| 锚点 | 角色 | 含义 | 数据字段 |
|---|---|---|---|
| `data-dam-team-ledger` | 容器 | 账本时间线 | — |
| `data-dam-team-ledger-seg` | 容器（属性 `data-actor`） | 单段，`data-actor` 用于取色 | `seg.actorId` |
| `data-dam-team-ledger-chain` | 容器 | 接续链视图 | `chain[]` |
| `data-dam-team-chain-node` | 控件（节点） | 链上一个节点（一次交接） | `node.from`、`node.to`、`node.at`、`node.sessionId` |
| `data-dam-team-chain-link` | 容器 | 节点间连线 | — |
| `data-dam-team-takeover` | 控件（按钮） | 「我来接」 | POST `team-handoffs/takeover` |

**分色实现（不许硬编码）**：每人颜色 = `--skin-color-team` 的 HSL 色相旋转，**在前端按 `actorId` 稳定哈希**得到 0–360 的增量，写成行内 CSS 变量 `--dam-team-actor-hue`，再由新增规则 `[data-dam-team-ledger-seg][data-actor] { border-left-color: hsl(var(--dam-team-actor-hue) 62% 52%) }` 消费。**不得**给每个成员写死一个色值（成员数不定）。

**路由**：

```
GET  /api/dsh-auto-memory/team-handoffs                 → { segments:[{id,actorId,at,title,body,sessionId}], chain:[{from,to,at,sessionId}], open:boolean }
POST /api/dsh-auto-memory/team-handoffs/takeover        → { ok:true, sessionId }   # 创建接续会话，复用既有 handoff-continue 的回程通道
```

**接续的宿主回程**：`takeover` 成功后必须走既有两条既有通道（**不许另开**）：
1. 新会话由后端创建，前端用 `sessions.open(sessionId)` 打开（`lib/client.js:4645` 既有写法）；
2. 交接提示词用 `ctx.remote.session.prompt({mode:'queue',...})` 送入（`:4584` 能力探测 + `:4591` 调用）。

## 11. demo 自检与「零硬编码色」的真实口径（2026-09-25 追加）

### 11.1 一次被 Lead 判红的口径修正（必须记录，避免复现）

初版 demo 把 4 套主题的色值直接写在 `[data-theme="…"]` 里，Lead 用统一判据扫出 **84 处 `#hex`**：

```js
const total = (s.match(/#[0-9a-fA-F]{3,6}\b/g)||[]).length;
const inFallback = (s.match(/var\([^)]*#[0-9a-fA-F]{3,6}[^)]*\)/g)||[]).length;
// 目标：total − inFallback === 0
```

- **判据本身是对的，但直接照字面执行会踩坑**：把 token 的默认色值藏进别处（JS 常量、外部文件）只是「把字面量搬家」，既不满足「双击即开、零依赖」，也让企业 IT 无法在 CSS 里覆盖。
- **正解**：把每个 token 声明改成 **企业覆盖钩子 + 默认兜底** 的写法，字面量落在 `var()` 的口袋里：

```css
[data-theme="light"] {
  --skin-color-brand: var(--skin-ent-color-brand, #4f5bd5);
}
```

这样一次性满足四件事：
1. Lead 判据 `total − inFallback === 0` 成立（84 处全部落在兜底位）；
2. 与皮肤契约 `skin-token-contract.md` §2 「**企业自定义 token 必须使用 `--skin-ent-*` 前缀**」完全一致 —— 不再是我另创一套；
3. 企业 IT 只要在自己的 CSS 里写 `--skin-ent-color-brand: #1E3A8A` 就能换主色，**不需要改 demo 一行代码**（12 卷 §五「方式①：直接覆盖 CSS 变量」）；
4. 组件区仍然 100% `var(--skin-*)`（实测 `[TOKENS-END]` 之后 hex=0 / rgb=0）。

### 11.3 接口对照抽屉（Lead 问的两件事之一）
