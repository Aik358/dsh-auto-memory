# 15 · 重启批次与交接方案（回答「能否集中重启」与「是否交给 ZCode」）

> 用途：把「需要重启宿主」这件事**从按批次逐次，改成按轮次集中**，
> 并给出「什么时候才真的需要把工作交给另一个 agent」的判据。
> 判据仍回溯 `00-目标冻结书.md`（30 条目标 / E0–E3 证据分级）。

---

## 一、先说三个实测事实（都影响结论）

| # | 事实 | 取证 |
|---:|---|---|
| 1 | 桌面端宿主是 **Electron 应用** `DeepSeek Harness.exe`，监听 19387 | 进程树：`pid=10496 → ppid=32552 → explorer.exe` |
| 2 | **我的 shell 不是宿主的子进程** | 我的工具链父进程是 `pwsh`，与 10496 无父子关系 |
| 3 | **desktop profile 用的是 `link:D:/dsh-auto-memory`** | `profiles/desktop/package.json` 依赖项 + node_modules 里是真符号链接 |

**事实 2 的准确含义（不要误读）**：

- **不会**出现「杀宿主连带杀掉我的 shell」这种进程级事故；
- **但是**：本轮对话的**运行上下文活在宿主进程里** —— 宿主一停，**本轮 turn 立刻终止**。
- ⇒ 所以「自己重启」的风险**不是自杀**，而是**中断本轮**：写一半的 turn 会断，
  未落盘的思路会丢。**这是可控的**（只要先把状态写进文档），但**不能边写边重启**。

**事实 3 的准确含义（这条最有价值）**：

> **开发树就是运行源。** 改 `lib/*.js` **不需要构建、不需要复制** ——
> 宿主下次启动时直接从 `D:\dsh-auto-memory\lib\` 读。
> ⇒ **重启 = 重读源码**，这也正是「改完要重启」的全部原因。

## 二、核心结论：**重启次数与「批次数」无关，与「修错轮数」有关**

这是本方案最重要的一句话。

**为什么**：

| 活动 | 是否需要宿主重启 |
|---|---|
| 写代码 | ❌ 不需要 |
| 跑单元测试（`node` 直接 require 新模块） | ❌ 不需要 |
| 跑全量回归（181 套件，纯 node） | ❌ 不需要 |
| `node --check` 语法检查 | ❌ 不需要 |
| **在真机上「看到」功能生效（E2 证据）** | ✅ **需要** |

⇒ **重启只挡「E2 取证」这一件事，完全不挡编码与 E0/E1 取证。**

**因此正确做法是**：

```
把所有代码写完 → 把所有单测/回归跑绿 → ★重启一次 → 一次性取完所有 E2 证据
                                                  ↓
                                      若有失败 → 修 → ★再重启一次
```

**⇒ 重启次数 ≈ 修错轮数 + 1，而不是批次数（10 批 → 不是重启 10 次，而是约 2 次）。**

## 三、最小重启方案（推荐）

| 阶段 | 内容 | 重启 | 可取证等级 |
|---|---|---|---|
| **R0** | 采开工基线 B0；写全部代码（B1–B10 + S1–S2） | ❌ | — |
| **R1** | 全量回归 181 套件 + 所有新模块单测 | ❌ | **E0 / E1** |
| **R2** | ★**重启第 1 次** → 一次性取全部 E2 证据 | ✅ **1** | **E2** |
| **R3** | 按 R2 结果修错 + 回归 | ❌ | E0/E1 |
| **R4** | ★**重启第 2 次** → 复验 E2 | ✅ **2** | E2 |
| **R5** | 你重启第 3 次（若仍有失败） | ✅ 3 | — |

**⇒ 单机项目的期望重启次数：2 次（顺利）/ 3 次（有修错）。**
**不是 10 次。**

R2 那一次重启后，**可以连着把下面全部取完**（它们只需要「插件在跑」）：

### 3.2 一次重启**覆盖不了**的（必须两台实例）

**⇒ 7 条 E3 目标里，5 条需要第二台机器或第二套环境，1 条（G-C1）需要两个云账号。**

**这不是重启能解决的，是「环境」问题。** 见第五节。

## 四、哪些改动需要重启、哪些只需刷新

| 改动对象 | 生效方式 | 依据 |
|---|---|---|
| `lib/index.js`（宿主半） | **必须重启** | 它在宿主进程里 require |
| `lib/*.js` 新模块（宿主半） | **必须重启** | 同上 |
| `lib/client.js`（浏览器半） | **可能只需刷新页面** ⚠️待实测 | 它经 `/plugins/<id>/client.js` 由 HTTP 提供 |
| `docs/**`、`artifacts/**` | 无需重启 | 不参与运行 |

⚠️ **待实测项**：`client.js` 是否每次 HTTP 请求都读盘。
- 若**是** ⇒ **B10 / S2（前端两项）完全不消耗重启次数**，你的负担进一步下降；
- 若**否**（启动时缓存）⇒ 与 index.js 同等对待。

**这一条必须在 R2 那一次重启时顺便测掉**（改一行注释 → 刷新页面 → 看是否生效）。
**在测出来之前，按「需要重启」保守排期。**

## 五、关于 E3（两台机器）—— 这才是真正的阻塞

冻结书 1.2 硬性规则第 2 条：**凡涉及同步/多端的目标必须 ≥ E3**。

**E3 的形态**：两个真实实例，交换输入顺序 ⇒ 输出**逐字节相同**。

### 可用的三条路（按成本排序）

| 方案 | 成本 | 能覆盖 |
|---|---|---|
| **A. 本机跑第二个 DSH 实例**（不同 profile / 不同 memoryRoot） | 中；需确认能否隔离 memory root | G-C3 / G-D1 / G-D4 / G-E2 |
| **B. WSL**（本机已检测到 `wsl` 可执行，但**发行版列表为空**） | 低～中；需先装一个发行版 | **G-B3**（路径分隔符）+ 可做第二个实例 |
| **C. 真第二台机器 / 云主机** | 高 | 全部 E3 |

**★ 待你决定的一步**：是否允许我**装一个 WSL 发行版**。
- 装 WSL 只影响本机，不碰 DSH、不碰插件；
- 装了之后 **G-B3（唯一要求「真 Linux」的目标）可本地闭环**；
- 不装则 G-B3 必须留到你有第二台机器。

**在你决定前，E3 的 7 条一律记为「未触达」** —— 按冻结书的规矩，
**看不到的写「未触达」，不许写成「通过」**。

## 六、是否把「反复重启的部分」交给 ZCode？

### 6.1 先厘清：**那段「反复重启的部分」其实不存在**

上面的分析已经证明：
- 重启**不按批次累积**，而是**按修错轮次**；
- 单机部分期望 **2 次**重启；
- 不涉及「几十次重启」这种规模。

**⇒ 没有值得专门外包的「高频重启段」。** 这是结论的前提，不成立就没有外包的必要。

### 6.2 交给 ZCode 会引入什么

| 项 | 说明 |
|---|---|
| **它不懂上下文** | 它不知道这次改了什么、为什么改，**重启时机judge不了** |
| **权限面扩大** | 要给它 computer use 才能操作桌面 → 等于把桌面控制权交出去 |
| **无法驱动我的会话** | 它重启完 DSH 后，面对的是一个**空白新会话**；它没法「让我继续」 |
| **故障归因更难** | 出问题时无法判断是代码问题还是编排问题 |

### 6.3 推荐方案：**交接文档 + 你做「一键触发器」**

**不外包重启权**，而是把「重启后如何继续」写成文档：

```
我：写完代码 → 跑绿回归 → 更新交接单 → 告诉你「可以重启了」
你：点一下重启（30 秒，不需要理解代码）
新会话：读交接单 → 继续下一轮
```

**你的动作被压缩成「点一下」，且权限零扩大。**

### 6.4 什么情况下**才**值得交给 ZCode

只有当出现下面这种组合时：

> **需要「无人值守 + 多次重启 + 每次重启后自动推进」**，
> 即你真的要**睡觉期间让它自己迭代**。

但即便如此，也**不推荐** —— 因为：
1. 单机部分期望 2 次重启，**挂机收益极小**；
2. E3 那 7 条**挂机也做不了**（需要第二环境）；
3. 未验证的合并逻辑（B6/B7）**自动迭代风险为负** —— 它会悄悄写坏记忆数据。

## 八、一句话

> **重启不是按批次累积的，是按修错轮次累积的 —— 单机部分期望 2 次。**
> **挂机能跑完 R0+R1（全部代码 + E0/E1 证据）；E2 需要你点两次重启；E3 需要第二台环境。**
> **不要交给 ZCode：没有值得外包的高频重启段，而且它无法驱动我的会话。**
