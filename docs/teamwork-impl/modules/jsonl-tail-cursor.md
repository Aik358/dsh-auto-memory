### 职责

**环形 JSONL 的增量游标**（issue #103）。`judgement-shadow.jsonl` 由 Python 侧按"保尾丢弃"维护（`SHADOW_LOG_MAX=256`）⇒ 用行数当游标在写满后必然失效（`lines.length` 恒等于上次 count ⇒ 增量区间恒空 ⇒ 消费端**永久停摆且无痕迹**）。本模块把游标改成**行内容指纹**。


### 内部关键实现

**1. 为什么行数当游标必然失效（issue #103 的完整推导）**

文件写满 256 行后，每次重写仍是 256 行 ⇒ 消费端读到的行数**恒等于**上次记录的 count ⇒ **增量区间恒为空** ⇒ 消费端永久停摆。
**而且**："没有新行"本身是**合法状态** ⇒ 这个停摆**不会留下任何痕迹**（不报错、不告警）。

**2. 处方：内容指纹**

改用行内容指纹后，环内每一行只被交付一次，**与文件是否被截断无关**。这是"环形缓冲 + 增量消费"这一组合的正确解法。

**3. 纯函数、零依赖、不碰文件系统**

便于用**假环**直接单测（不需要真实文件），也让该逻辑能被复用到任何环形 JSONL 场景。

```js
/**
 * 团队变更流水的增量游标 —— **复用内容指纹，不用行号**。
 *
 * 为什么不能自己写一个"读到第 N 行"的游标：本模块的存在理由正是该写法必然失效 ——

    },
    reset: () => { if (inner && typeof inner.reset === 'function') inner.reset() },
  }
}
```

### 与团队化的关系

**判定：派生重算（Derived）· 纯函数。**

游标是"我读到哪了"的**本地进度**，跨端毫无意义（A 的读取进度不能给 B 用）。团队化后每端各持自己的游标即可。

### Teamwork 改造要点

1. **团队同步日志（增量流）需要同型游标**：若要同步"团队变更流水"（append-only），消费端同样需要**内容指纹游标**而不是行号/偏移——本模块可直接复用其设计。
2. **环内每行只交付一次**：这是本模块的核心不变式。团队流水若用环形保尾存储，必须沿用同一语义，否则会出现"重复应用补丁"。
3. **"没有新行"是合法状态**：必须与"读取失败"区分开——本模块的设计动机正是"永久停摆却无痕迹"，团队同步不得重蹈。

### 风险与回归

- 回归：单测用**假环**直接验证（不碰文件系统），改造时不要引入真实 fs 依赖。
- 游标判定必须是内容指纹，不得退化为行数或字节偏移。
