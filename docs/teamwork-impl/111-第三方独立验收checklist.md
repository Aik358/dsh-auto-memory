### 0.6b ★判据层级：事实 > 代码 > 程序（用户裁定，**优先级高于本节其余各条**）

> 用户原话：「**我不太相信你这些配套的断言插件（也就是程序）……还是要面向事实，面向代码是否有这样的实现、这样的实现是否正常，以及前端是否以这样的实现为主。**」

| 级 | 名称 | 可否成结论 |
|---|---|---|
| **L1** | **事实**（截图 / 点击 / 真机响应 / 落盘字节） | ✅ **唯一可直接成结论** |
| **L2** | **代码**（真存在 + 实现本身正常，附文件+行号+原文） | ✅ 强证据 |
| **L3** | **消费**（前端/宿主确实以此为主，有真实消费方） | ✅ **必查** |
| **L4** | **程序**（我方断言脚本 / 套件 / 验收器） | ⚠️ **只能作线索，不得作结论** |

**⇒ 本清单里所有「取证命令」都属 L4。它们只用来定位与生成候选证据；「通过」必须由 L1 或 L2+L3 支撑。**
**⇒ 只有 L4 时，结论写「有程序证据但未取得事实证据」——这不是「通过」。**
（完整 8 条实证与「三问」见 [112 §4.5](112-第三方独立判定任务书.md)、[113 §4](113-文档全量索引与交接包.md)）

### 0.6c ★调查顺序：前端优先，后端只在 C 档回溯（用户 2026-09-27 裁定）

> 用户原话要点：「**后端我这跑得还是比较严谨的，主要是前端发现没什么变化。……如果我发现前端错位了，后端也找不到相应的接口的话，再去调查后端的缺口。**」

| 档 | 现象 | 结论 |
|---|---|---|
| **A** | 截图看到错位/缺失，且源码里**能找到实现** | 「前端实现有问题」+ 行号 |
| **B** | 截图看到错位，源码里**找不到实现或消费点** | 「前端未接线」+ 断点 |
| **C** | 前端错位 **且** 宿主侧**也无对应接口/字段** | 「后端缺口」← **只有这一档才查后端** |

**⇒ 后端默认视为「已通过」**（用户已自行跑得较严谨），本清单 §3.1 的后端核对表**只在出现 C 档时才逐条走**。
**⇒ 不要让「某个验收器红了」触发后端调查** —— 那是 L4 证据（见 §0.6b）。

### 0.7 证据分级（00 卷 §1.1，逐字）

| 等级 | 是什么 | 能证明 | **不能证明** |
|---|---|---|---|
| **E0** 静态断言 | grep / 守卫 / 语法检查 | 没违反**已知**约束 | 任何行为 |
| **E1** 测试通过 | 单元 / 集成测试 | 代码路径**在该用例下**正确 | 真实环境下的行为 |
| **E2** 真机可观测 | 在实际运行的插件上看到现象 | **用户看到的效果真的发生了** | 多方协作的正确性 |
| **E3** 对向 / 收敛验证 | 两个真实实例，交换输入、核对结果 | **协作语义真的成立** | — |

**硬性规则**：① 每条功能目标 **≥ E2**；② 凡涉及同步 / 多端 **≥ E3**；③ E3 的形态 = **交换输入顺序 ⇒ 输出逐字节相同**；④ 每条目标必须写出**反例**（写不出的应移入「不可验证项」）。

### A 组 · 不可回退底线

#### G-A1 不启用团队模式时，行为与基线一致
- **目标**：用户没开团队功能时，插件**和以前完全一样**。

- **排除清单覆盖率下限**：**≥ 83.3%**（855/1026 仍在监控）。低于此值须重跑覆盖度核查，否则本判据退化为恒真守卫。

#### G-A2 未启用时零网络、零同步元数据

- **反例**：❌ 只 grep import，**动态 `require(变量)`** 绕过；❌ 顶层没引但某一个文件引了。

#### G-C3 私人多机：不暴露任何本机端口即可跨机同步
- **判据**：两机经对象存储收敛；**本机不监听任何新端口**，防火墙无新增入站规则。
- **E3。取证**：A 机写 → B 机读；同时比对 A/B 监听端口列表（与基线比）。

### D 组 · 同步原语（★分叉是本项目最大的隐性风险）

#### G-D1 交换输入顺序 ⇒ 合并结果逐字节相同（收敛性）
- **判据**：`merge(A,B)` 与 `merge(B,A)` 输出**逐字节相同**。
- **E3。取证**：对**每一个**原语都做双向合并，比对**序列化后的字节**。
- **反例（★最重要）**：❌ **只测单向** —— 本项目实测 `compareClock` 在双方都无时钟时返回 `-1`，单向测试**全绿**，但两端各自认为对方更旧 ⇒ **永久分叉**；排序键只有两级时，同键同设备会退化到输入顺序 ⇒ 每次同步都产生新差异，永远收敛不了。❌ 比对「字段值相等」而非序列化字节（键顺序/空白不同会漏掉）。❌ 用「合并三次看是否稳定」—— **分叉情形下它看起来也是稳定的**。

#### G-D2 比较器：四象限都有确定行为
- **判据**：A无/B无、A有/B无、A无/B有、A有/B有 四情形；且 **`cmp(a,b) === -cmp(b,a)` 恒成立（反对称）**。
- **E1。取证**：四象限各造一组数据。
- **反例**：❌ 只测「都有时钟」（最常见路径）；❌ 测了四象限但**没测反对称性** ⇒ `cmp(a,b)=cmp(b,a)=-1` 这种自相矛盾能通过。
- **★探针纪律**：`decideKeyPre` 的签名是 **`(base, local, remote)`**（3 参）；本项目曾因为**少传第 3 参**而误报「不对称」。报红前先读 `export function` 行。

#### G-D3 删除只记录、绝不真删
- **判据**：撤回后条目**仍可被检索到**，且带明确标记与「最新结论在哪」的指针（`supersededBy`）。
- **E2。取证**：撤回一条 → 检索它 → **必须能搜到**且显示已过时状态。
- **反例**：❌ 撤回后搜不到（违反用户明确裁定：**「superseded = 返回但标记，不剔除、不降权」**）；❌ 标记存在但**没有指针**，用户不知道新结论在哪。

#### G-D4 两端条目数最终相等（无重复、无丢失）
- **判据**：两端 **id 集合相等**（不是数量相等）。
- **E3。取证**：A→B、B→A 各同步一轮，**多轮**后比对 id 集合与各自内容哈希。
- **反例**：❌ 只比数量（重复 + 丢失恰好抵消时数量相同）；❌ 只同步一次就断言收敛。

### E 组 · 白板条目级增量

#### G-E1 改一条 ⇒ 同步只传这一条
- **判据**：一次单条目修改产生的**出站负载仅包含该条目**。
- **E2。取证**：改一条 → 打出站载荷 → 确认**条目数**。

#### G-E2 两人改不同条目 ⇒ 自动合并，零人工
- **判据**：A 改条目 1、B 改条目 2 → 同步后两端都有两条改动，且**冲突中心为空**。

#### G-E3 合并后锚点一个都不少（防丢卡）
- **判据**：合并结果的锚点集合 ⊇ 双方锚点并集；**不满足时不写盘并报错（fail-closed）**。
- **E1（断言）+ E2（人为构造冲突，确认真的拒绝写盘）**。
- **取证（必须实测负路径）**：构造一个会让锚点丢失的输入 ⇒ 确认**被拒绝**且**磁盘文件未被修改**。
- **反例**：❌ 只测「正常情况下锚点不少」（恒真守卫）；❌ 断言失败后**仍然写盘了**（fail-open）。

#### G-E4 能看到「谁在什么时段改了什么」
- **判据**：界面列出每次变更的**时间 + 人 + 条目 + 改动摘要**。
- **E2。取证**：两次不同人的修改 → 打开变更列表 → 核对**三条信息齐全**。
- **反例**：❌ 有列表但人是空的/时间是空的；❌ 只显示「有更新」而不显示改了哪一条。

#### G-E5 磁盘上仍是人类可读的 Markdown
- **判据**：`PLAN.md` 仍是标准 Markdown，编辑器打开可读，**无二进制/私有格式混入**。
- **E2。取证**：同步若干轮后直接打开文件**肉眼读**；可辅助统计控制字符数与标题/锚点数。
- **反例**：❌「结构上还是 md」但**塞满了同步元数据**，人已经读不下去 —— 这违背「真源是人类可读文件」的根本前提。

**「客户能改」才是真尺**（56 卷 §〇）：判据不是「代码里都走变量了」，而是 **「客户改一个配置文件 / 换一行 file 字段，界面按他的意思变」**。

**客户不能做的（业务逻辑，永不由客户承担）**：改数据来源 / 改交互行为 / 改 API 路径 / 改渲染分支。

### 3.3 ★六层核对时最容易犯的两个口径错

1. **「锚点挂上了」≠「锚点被消费」**：`data-dam-* ` 存在只证明标记在，不证明任何渲染分支读了配置。必须另有「改配置 ⇒ 界面变」的 E2 证据，否则该层只能记 **部分**。
2. **「静态守卫绿」≠「该层通过」**：凡断言对象是源码字符串/计数，一律降级为**守卫，非功能证据**（CR-10）。本项目 R33–R36 正是把看板层四项从「只有源码字符串守卫」改为「真执行验收」才收口的 —— **判定人对看板层必须用真执行口径复核，不得采信守卫数量**。

## §6 反向验证（验证「验证工具本身」）

> **凡「验证工具本身」的证据，必须来自与它相同的执行环境。**
> 一个**永远返回 0 的验证工具**比没有更危险 —— 它会让人以为「验过了」。

| 工具 | 反向验证方法 | 期望 |
|---|---|---|
| `baseline-diff.mjs` | 加 `--expect` 指向不存在的文件 | exit 1 **且** 输出含 `✗ G-A1 不通过`；且须同时报「预期内但未发生」 |
| `verify-layout-schema.mjs` | 已内建 §5.2 / §6.3 / §6.4 三条负路径 | 变异 region 名 / 伪造锚点 → 必红 |
| `verify-skin-assets.mjs` | 已内建 §3.3（未知 key ⇒ 确定性占位）与 §3.4（断言器自身可被证伪：哨兵路径必须不存在） | 未知 key 不抛、返回 `placeholder:true` 且**不带 url** |
| 任一「只报结论」的脚本 | 人为破坏被测文件后重跑 | **必须变红**；不变红即为恒真守卫 |
| 全量回归 | 临时把一个套件的断言取反 | 该套件必须 FAIL，且 **FAIL 数 = 1** |

**覆盖度自审**：若某判据是「排除某些文件后再比对」，必须同时给出**监控覆盖率**并设下限，否则排除清单会**静默退化为恒真守卫**（00 卷 E.8.1）。
