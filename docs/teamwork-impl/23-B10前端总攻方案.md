## 1. 契约漂移实测（本轮最重发现）

### 1.1 结论先说

> **frontend/02-团队版前端契约.md §6.1 承诺的 20 个 team* 配置键里，只有 2 个在代码中真实存在。**
> 反向另有 **13 个键是代码有、契约没写**。
> ⇒ 前端若照契约写控件，**17/20 个控件会静默失效**（配置键名写错与字符串枚举写错一样不报错）。

### 1.2 逐键对照（实测）

| 契约 §6.1 的键 | 代码实装？ | 代码里的实际键 / 差异性质 |
|---|---|---|
| teamEnabled | 有 | 一致 |
| teamConflictPolicy | 有 | 一致（但**值域不同**：契约写 ask/prefer-team/prefer-local，代码是 keep-both） |
| teamServer | 无 | 实际是 **teamEndpoint**，且**语义不同**：契约指「团队服务地址」，代码是 **S3 endpoint** |
| teamId | 无 | 实际是 **teamProjectId**，且**不由服务端下发**，由 git remote 推导 |
| teamMemberName | 无 | 实际是 **teamMemberId** ＋ **teamMemberRole**（两个键而非一个） |
| teamSyncMode | 无 | 实际是 **teamSyncIntervalMs**（数字，不是 off/manual/auto 三档枚举） |
| teamSyncIntervalSec | 无 | 实际是 teamSyncIntervalMs（**单位不同：秒 vs 毫秒**） |
| teamScopeDefault / teamShareExternal / teamShowAttribution / teamShowAudit / teamSkinId / teamSyncPaused | 无 | 全部未实装 |
| teamSyncSynced / Syncing / Offline / Conflict / Paused / NotJoined | 无 | **不是配置键，是 i18n 文案键**——被契约误列进配置键表 |
| teamVerdictLocalWarn / teamVerdictRemoteWarn | 无 | 同上，是文案键 |

**代码有、契约未载的 13 个**：teamEndpoint · teamBucket · teamRegion · teamPathStyle · teamAccessKeyId · teamSecretAccessKey · teamProjectId · teamOutboxMaxItems · teamMaxConflicts · teamInjectEnabled · teamDerivedDebounceMs · teamSyncIntervalMs · teamState（路由常量）。

### 1.3 ★根因（2026-09-26 二次实测，**修正了本文首版的一处错误判断**）

**首版错误**：本文第一稿写「实测架构是**多端直连 S3 + CDC**」。
**该判断是错的**（当时只有键名对照、没有走到网络层取证）。二次实测结果如下。

#### 实测事实（可复现）

| # | 测什么 | 命令/判据 | 结果 |
|---|---|---|---|
| 1 | S3 签名实现 | 扫全 `lib/*.js`：`AWS4-HMAC-SHA256` / `createHmac` / `x-amz-date` / `Signature=` | **全部 0 命中** |
| 2 | S3 键谁在读 | 扫 14 个 `team*` 键的引用点 | endpoint/bucket/region/AK/SK/pathStyle **只在 `index.js` 出现 1–2 次**（= 只在 DEFAULT_CONFIG 声明 + `/team-state` 回显），**无任何业务消费** |
| 3 | 网络层读什么键 | `lib/team-auth.js` 的 `serverUrlOf` / `teamIdOf` / `readToken` | 读 **`teamServerUrl`** / **`teamId`** / **`teamToken`** |
| 4 | 这三个键注册了吗 | 在 `DEFAULT_CONFIG` 块内检索 | **三个全都没有** ⇒ 该层**恒返回 `not-configured`** |
| 5 | 同步推给谁 | `lib/team-sync.js` 的 `PUSH_PATH` | `api/team/sync/push` ⇒ **推给一个 HTTP 服务端** |

#### 结论：两条路各写了一半

```
路线甲 · 团队服务端：
  契约 02 假设了它 ✅    代码也按它写了 ✅ (team-auth + team-sync push)
  ...但它的三个配置键从未注册 ❌  ⇒ 整层恒 not-configured，同步当前是空的

路线乙 · 直连对象存储：
  13 卷设计定案了它 ✅  (S3 兼容 / 四云通吃)
  ...六个配置键也注册了 ✅
  ...但没有任何代码消费它们 ❌  ⇒ 没有 S3 客户端、没有签名、没有 PUT/GET
```

> ★所以真实状态**不是**「架构已定、契约过时」，而是「**两条路都只写了一半，必须先选一条走完**」。
> ⇒ 契约 §2/§3 里 `POST /team-sync-now`、`GET /team-members`、`/team-presence` 这类**服务端**路由，
> 在选定的架构下都需要重新落位（选乙则改设计为「本机算 ＋ 存储读」）。

#### 附：B2 的验收口径本身偏弱（据实记录，非追责）

[16-进度台账.json](../teamwork-impl/16-进度台账.json) 里 B2 的验收子项写的是
「**teamFetch 四情形均 `{ok:false}`**」——这是一个**纯否定式**判据：
未配置 / 未登录 / 超时 / 非 2xx **四种全部失败**，与「这一层根本没接通」在观测上**不可区分**。
⇒ B2 四情形全绿**不能**证明鉴权层可用。
**可复用判据**：凡验收写成「N 种情形全部返回失败」，必须**同时**给出一条**肯定式**判据（至少一条返回成功），否则该验收对「功能是否接通」无鉴别力。

## 3. 前端全量改造的三层拆法（对 Q2「全量」的可执行解释）

「不在屎山上做增量」是对的，但 742 KB、223 个字面色值、14 套结构断言的文件**不能先拆后建**。正确顺序是**先立骨架，再搬家具**，每层都带可验证判据：

| 层 | 做什么 | 判据（可验证） | 风险 |
|---|---|---|---|
| **L1 取值层** | 223 个字面色值 ＋ 262 个 rgb() 抽成 token 表，全部改走 var(--dam-*, 原值) | **视觉零变化**（改的只是「值从哪来」）⇒ 改前/改后截图逐像素对比 | 低（机械替换） |
| **L2 布局层** | 版面抽成「区域 region ＋ 插槽 slot」；用户要的「换元素位置 / 某页出现哪些内容」＝ 区域顺序 ＋ 插槽开关的**数据驱动** | 默认布局渲染结果与 L1 完成态一致；改一个 JSON 就能换位置 | 中（需设计 schema） |
| **L3 团队层** | B10b 团队屏 ＋ 归属徽标 ＋ 筛选，**挂到 L2 的插槽上** | teamEnabled=false 时插槽全空 ⇒ 与 baseline 一致 | 中 |

> ★**L1 与 L2 不依赖任何 team 后端**，可在后端补齐期**并行开工**（与 21 卷「皮肤可并行因为只碰 DOM」同源）。
> 唯一前提是先做 22 卷的守卫锁测绘（已做），并明确 L1/L2 会触碰 14 套结构断言中的哪几套。
