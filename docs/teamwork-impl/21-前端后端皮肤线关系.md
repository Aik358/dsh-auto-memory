# 21 · 前端 · 后端 · 皮肤线 —— 三方关系与同步约束

> **为什么有这一卷**：用户明确要求「**这个一定要前后端同步，而且要理解清楚前后端的关系，以及和皮肤线的关系**」。
> 这一卷把三者的**依赖方向、改动顺序、耦合点、以及「一起改会撞车的地方」**讲清楚。
>
> 时间：2026-09-26 ｜ 状态：**权威**（后续施工以本卷的依赖方向为准）

---

## 一、先看一张图：三条线不是并列的，是**分层**的

```
┌──────────────────────────────────────────────────────────────┐
│ L4 皮肤层  skin-center 官方契约 + 我们的 6 个图片槽位 + data-dsh-part  │
│    ── 只依赖「DOM 上有没有稳定语义属性」，不依赖任何业务逻辑        │
├──────────────────────────────────────────────────────────────┤
│ L3 前端层  lib/client.js（单写者，742,031 B）                     │
│    ── 消费 L2 的接口；产出 DOM（供 L4 挂钩）                      │
├──────────────────────────────────────────────────────────────┤
│ L2 接口层  56 条路由 + 19 个工具 + 14 个 team.* 配置键            │
│    ── 唯一的「契约面」；**前端与后端只在这里相遇**                  │
├──────────────────────────────────────────────────────────────┤
│ L1 后端层  lib/index.js（单写者，963,818 B）+ 新增 5 个 team-*.js │
│    ── 产出数据；不知道前端长什么样                                │
└──────────────────────────────────────────────────────────────┘
```

**关键结论**：
1. **前后端之间只有一条通道：L2 接口层**。前端不读后端内部状态，后端不知道前端渲染。
2. **皮肤层只跟 DOM 有关，跟业务完全无关**。这是它能「并行」的**根本原因**。
3. ⇒ **皮肤线可以与后端同步开工**，只要不去动 `client.js` 的**结构**。

## 二、依赖方向（**改动的先后顺序**，不是重要性）

```
后端(B*)  ──先做──▶ 接口(L2)  ──必须稳定──▶ 前端(B10)  ──产出 DOM ──▶ 皮肤(S2/S3)
   │                                              │
   └────────── 配置键(team.*)两端都要读 ───────────┘
```

| 谁 | 依赖谁 | 能不能先做 |
|---|---|---|
| **后端 5 个新模块** | 无 | ✅ **可以最先做**（纯新增文件，零重叠） |
| **后端 index.js 装配** | 新模块 + 配置键 | ⚠️ 必须**串行**（单写者） |
| **前端 client.js** | **接口必须已定型** | ⚠️ 否则会「按想象写接口」⇒ 返工 |
| **皮肤（S1 数据表）** | 无 | ✅ **可以最先做** |
| **皮肤（S2 槽位）** | 前端 DOM **必须已存在** | ❌ 必须 **等 B10 落地**（同一文件） |
| **皮肤（S3 语义属性）** | 前端 DOM + 官方契约 | ❌ 等 B10 + S3 差异报告（已有） |

## 三、★三条「会撞车」的规则（这是最容易出事的地方）

### 规则 1：`lib/client.js` 是单写者 —— 全项目只有 4 处真并发

| 文件 | 谁能改 | 并发性 |
|---|---|---|
| `lib/index.js` | **只有 Lead** | ❌ 串行（11 批里有 8 批要碰它） |
| `lib/client.js` | **只有 Lead** | ❌ 串行（B10 / S2 / S3 都碰它） |
| **其余新增文件** | 可并行 | ✅ **只有新文件才真并行** |

⇒ **真并行的只有 4 个新文件**：`team-identity.js` / `team-auth.js` / `team-project-map.js` / `team-outbox.js`（+ `skin-assets.js`）。

### 规则 2：皮肤改 `client.js` 的**两种方式**，风险完全不同

| 方式 | 动到什么 | 风险 | 判据 |
|---|---|---|---|
| ✅ **追加式** | 只在文件**末尾**新增 CSS 段 + 组件 | 低 | 既有 163 个 `data-dam-*` 锚点**全部仍在** |
| ❌ **插入式** | 在既有组件中间插代码 | **高** | 会击穿字符串锚定守卫（本仓有守卫硬锁） |

⇒ **皮肤只允许追加式**。这条必须写进 S2/S3 的验收。

### 规则 3：总开关必须**只影响自己**

```js
teamEnabled = false   // ⇒ 后端零网络、前端零 UI 变化、皮肤零加载
```

⚠️ **反向违规**：`skinEnabled` 不得顺带改变团队功能的行为；
     `teamEnabled` 也不得顺带改变皮肤的行为。**两个开关正交。**

## 四、★真正的耦合点（只有 4 个）

三方之间**真正需要同时对齐**的只有这 4 处，其余都是独立的：

| # | 耦合点 | 后端做什么 | 前端做什么 | 皮肤关心什么 |
|---:|---|---|---|---|
| **C1** | **同步状态** | 产出 `{成员/最后同步/队列深度/冲突数}` | 渲染成状态条 | 给状态条一个 `data-dsh-part` 可改配色 |
| **C2** | **冲突中心** | 产出 4 类待裁决项 | 渲染列表 + 回传裁决 | 列表项的视觉 token |
| **C3** | **日历双轨** | 写行时带 `<!-- dam-track:team -->` | 显示轨道标记 | 团队标记的颜色 |
| **C4** | **配置键分区** | 读 `team.*` 14 键 | 渲染第 10 分区设置页 | 表单控件的 token |

⇒ **只有这 4 处需要「前后端 + 皮肤」三方同时看**。其余 47 项功能（51 − 4）不涉及三方耦合。

## 五、三条线的「完成」定义（**互相不能替代**）

| 线 | 完成的判据 | **不算完成**的情况 |
|---|---|---|
| 后端 | 接口能返回正确数据，且 `teamEnabled=false` 时**行为与基线逐字节一致** | 「代码写了但没接线」 |
| 前端 | 开关**即时回显**，且 163 个既有锚点全在 | 「写盘成功但界面没变」（用户明确视为「功能坏了」） |
| 皮肤 | 换图**只改 `SKIN_ASSETS` 一行**，结构代码零改动 | 「图能显示但排版写死了」 |

⚠️ **最危险的一种假完成**：后端改了、前端没改 ⇒ 用户**看不到任何东西**，但回报告诉他「做完了」。
⇒ **每个后端批次都必须配一个「前端可见性」检查**。

## 六、与「10 张概念图」的关系（用户特别问的）

那 10 张概念图是**客户给的企业交付目标形态**，它落在**L4 皮肤层 + L3 前端的排版骨架**上：

| 概念图表达了什么 | 谁负责实现 |
|---|---|
| 布局骨架（左栏 / 卡片网格 / 分栏比例） | **L3 前端**（结构性，改动大） |
| 配色 / 圆角 / 阴影 / 间距 | **L4 皮肤**（token，改动小） |
| 图片/插画位置 | **L4 皮肤**（6 个槽位） |
| 功能开关、数据展示 | **L1 后端**（数据从哪来） |

⇒ **概念图是「验收标准」，不是「实现手段」**：
> 原型 `skin/index.html` 是**照着概念图做的可交互样张**，
> 它是 L3+L4 的**共同目标**，但**本身不是插件的一部分**（它在 `docs/` 下，不参与运行时）。

⚠️ **一条尚未验证的风险（已在查）**：
> 10 卷 README 自述「给皮肤子代理的简报把 4 张路径标错了 3 个，子代理的更正也是错的」，
> 随后又自证「原型的 10 个页面与真实概念图一一对应，没有按错图去画」。
> **这句自证没有硬证据。** 已派专人逐张开图核对，产出见 `20-概念图与原型逐张核对.md`。
> **在该核对出结论前，不得宣称皮肤线「按概念图画对了」。**

## 七、施工顺序（把上面所有约束压成一条线）

```
波次 0 ✅  B1 身份缺陷 · B2 配置键+身份+鉴权 · S1 皮肤数据表 · S3 协议差异对比
波次 1     B3 出站队列（新文件，可并行） → B2 装配（index.js，串行）
波次 2     B4 同步心跳（关键路径） → B5 日历双轨（首个闭环）
波次 3     B6 下行合并 + 冲突中心  ‖  B10 前端 UI   ← 两条线可并行（不同单写者文件）
波次 3.5   S2 皮肤槽位 + S3 语义属性接入      ← 必须等 B10（同改 client.js）
波次 4     B7 注入层（最高风险） → B8 白板冲突 · 看板

★ 皮肤线可在波次 0–3 期间「做数据与设计」，但**碰 client.js 必须排在 B10 之后**。
```

## 八、一句话总结

> **后端先定接口，前端再消费接口，皮肤最后挂 DOM。**
> **三条线唯一的交汇点是 L2 接口层；皮肤之所以能并行，是因为它只碰 DOM、不碰业务。**
> **两个开关（`teamEnabled` / 皮肤）必须正交。**
