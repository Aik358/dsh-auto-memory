# ADR-005 · 其余拍板汇总（Q4–Q9、Q11）

> 本卷记录 Q4–Q11 的定案。**与我建议不同的三条已标 ⚠️**，并写明其连带影响。

---

## ⚠️ ADR-005-A（Q4）· 加密：**A 为主 + 可选 E2E 档位**

**用户选择**：A 为主 + 可选 E2E 档位（**非**我建议的纯 A）

**意味着什么**：
- **默认档**：明文存服务端 + TLS + 访问控制；**必须主动向客户披露明文存储**（沿用既有裁定）
- **可选档**：某些团队可为敏感库开启 E2E

**⚠️ 必须写清楚的代价（否则实施时会踩空）**：

**开了 E2E 的那个团队，以下功能会失效**——这不是 bug，是密码学必然：

| 功能 | 明文档 | E2E 档 |
|---|---|---|
| 服务端自动冲突检测 | ✅ | ❌ **失效** |
| 服务端团队检索 | ✅ | ❌ **失效** |
| 服务端去重 | ✅ | ❌ 只能按密文哈希（仅相同明文可去重） |
| 端到端同步 | ✅ | ✅ 仍可用（靠客户端合并） |

⇒ **E2E 档必须由客户端自己完成冲突检测** —— 也就是说 **04 卷的客户端合并逻辑必须完整实现**（不能依赖服务端兜底）。

**实施要点**：
- `cryptoMode: 'plain' | 'e2e'` **按团队（甚至按库）粒度**，不是全局开关
- **切换档位 = 数据迁移**（已存在的明文要加密上行，或反之）⇒ **必须做成一次性迁移任务，不可运行时热切**
- UI 必须**明确标注**「此库已启用端到端加密，团队检索不可用」——**不能让用户以为是坏了**

## ⚠️ ADR-005-B（Q7）· 入库审批：**一律 1 人**

**用户选择**：一律 1 人（任一管理员）（**非**我建议的「默认 1 人 + 高风险 2 人」）

**影响**：
- `procedure-store` 的高风险条目（`riskLevel: 'high'`）**审批人数从 2 降为 1**
- **但**：既有裁定「high 需人工批准后才可激活」**不变** —— 仍是**必须有人批**，只是不再要求两人
- ⇒ 减少一个状态字段，实施更简单

**⚠️ 需注意的一处冲突**：
Q9 你选了「高风险技能 = 管理员 + 领域成员**双签**」。
⇒ **Q7 与 Q9 在「高风险」上口径不同**：
- **Q7 管的是「团队库记忆入库」**（一般条目）
- **Q9 管的是「`memory_procedure` 的 high 技能激活」**（特殊条目）

**当前处理**：**两者并存，不冲突**——
- 团队库普通记忆入库：**1 人**
- 高风险技能激活：**双签**（管理员 + 领域成员）

但这**确实是一处需要你确认的语义重叠**：如果「高风险技能」也算「团队记忆入库」的一种，
那双签是**它的专属规则**（更严），应当**优先适用**。**我按「更严者优先」实现**：
> **一条变更只要命中「高风险技能」判定，就走双签；否则走 1 人。**

## ⚠️ ADR-005-C（Q8）· 证据链：**原文上云**

**用户选择**：原文上云（**非**我建议的「只传哈希」）

**这个选择改变了 04 卷的一条设计**：

| 原设计 | 现在 |
|---|---|
| 证据只存哈希，原文留本机 | **原文上云** |

**⚠️ 三条必须补的配套（否则是隐私事故）**：

**① 必须做**脱敏**再上行**（不是可选项）

~~~js
// lib/evidence-redact.js（新增）
/**
 * 证据上云前的脱敏 —— 白名单式。
 * 依据：用户选择「原文上云」，但 `S0 本机私有` 的边界仍必须守住。
 */
const REDACT_RULES = [
  // 1. 绝对路径 → 相对路径（各端根目录不同，且属隐私面）
  [/([A-Za-z]:\\[^\s"'\n]+|\/(?:Users|home)\/[^\s"'\n]+)/g, '<path>'],
  // 2. 会话 / 设备标识
  [/\bsession[-_]?[0-9a-f]{8,}\b/gi, '<session>'],
  // 3. 常见密钥形态（宁可误伤）
  [/\b(sk|ghp|gho|glpat|xox[baprs])[-_][A-Za-z0-9_-]{16,}\b/g, '<secret>'],
  [/\b[A-Za-z0-9+/]{40,}={0,2}\b/g, '<maybe-secret>'],
  // 4. 邮箱
  [/\b[\w.+-]+@[\w-]+\.[\w.]{2,}\b/g, '<email>'],
]

export function redactEvidence(text) {
  let s = String(text || '')
  for (const [re, rep] of REDACT_RULES) s = s.replace(re, rep)
  return s
}
~~~

**② 必须给用户一个「不上云」的出口**
即使默认上云，**必须**提供**逐条/逐项目**的「仅本机」标记 —— 否则用户遇到敏感内容时只能放弃使用证据功能。

**③ 披露要写进 UI，不只是合同**
在团队设置里**明确显示**：「证据原文会同步到团队服务端」。

## ✅ ADR-005-D（Q5）· 冲突中心：**嵌在同步状态条**

- 零冲突时不占位置
- 有冲突时状态条**变色 + 数字徽标**，点开侧滑
- **★ 与 ADR-004（Q10 条目级增量）联动**：白板冲突大幅减少后，冲突条**更少出现** ⇒ 这个选择更成立

---

## ✅ ADR-005-E（Q6）· 影子检索上报：**默认关闭**

- 设置里显式开启，并**说明收集什么**
- 理由（保留在案）：默认收集行为数据在企业采购里通常是红线

---

## ✅ ADR-005-F（Q9）· 高风险技能：**管理员 + 领域成员双签**

- 见 ADR-005-B 的语义重叠说明：**更严者优先**
- 需你确认的一点：**「领域成员」怎么定义？** 我按「与技能 `topic` 匹配的成员」实现，**若无匹配成员则退化为管理员单人 + 明确提示**（不能因为找不到人就卡死）

---

## ✅ ADR-005-G（Q11）· 角色：**owner / admin / member 三角色**

- 不含 `guest`
- 需要外部只读时：**临时成员 + 只读规则**（用规则而非新角色表达，避免权限模型膨胀）
- **★ 与 Q7「一律 1 人」一致性检查**：Q7 说「任一管理员」，即 `owner` 与 `admin` 都可审批 ✓
