# Issue #45：memory_recall 的本地召回覆盖修复

## 行为约定

本修复取消 `recall()` 内两处按追加顺序执行的 256 条记录截断：默认 L0 模式的候选数组，以及旧格式的独立语义检索候选数组。**在既有文件窗口内，所有被 `buildL0IndexPre` 解析出的条目均进入各自的排名输入**。来源顺序、排序算法、语义阈值和最终结果数量限制不变。

本地文件窗口仍为最近 40 份日志、最近 30 份反思，以及当前项目笔记和用户级 MEMORY.md。额外枚举第 41/31 个文件名只用于发现窗口外仍有文件，不读取该文件正文。发现超窗时，命中或未命中的最终响应都会附上 `[本地检索范围受限]` 提示，避免把“当前检索范围未命中”误作“从未记录”。`handoff`、`sessions` 和 `expand` 的早返回不受这一提示影响。

这不是“全历史全文搜索”：归档、文件窗口外的历史、没有记忆锚点的文本，以及未进入 L0 摘要的正文，仍受原有路径的限制。结果未进入 top-K 也不等于记录未进入候选集。保留按日期 `memory_read`、按锚点展开及磁盘原文检索作为不同用途的路径。

## 为什么不改成更大的数字或来源配额

把 256 改成 4096，只会把必现截断推迟；按日期排序也不能使预算外记录可达。按来源配额只能保护一部分笔记，仍会丢掉长 MEMORY.md 的尾部。因此本次将输出限制保留在排名之后，不再用查询前的记录配额决定一条已读取记录有没有资格参与检索。

不改自动注入预算、锚点/ID 生成、持久化索引格式、Python index-sync 协议、工具 schema 或配置。不修改其他 Issue 的实现。

## 受影响的既有测试：`smoke-test-p2-semantic-recall-pre.mjs`

该既有 smoke 有两条断言直接锁定了本次要移除的记录预算，属于被本修复取代的旧契约：

1. 源码守卫 `SRC.includes("maxRecords: 256")`——要求调用点继续传入记录预算。
2. 行为断言 `assert.equal(seen[0], 8, '语料截断到 maxRecords=8')`——要求语义臂按 `maxRecords` 截断语料。

两条改为：守卫改为 `!SRC.includes('env.maxRecords')`（语义臂不得再消费任何记录预算），行为断言改为 `seen[0] === perFile * 2`（窗口内全部已解析记录进入排名；`maxRecords: 8` 仍被显式传入，用于证明它已被忽略）。**`minScore` 阈值、`limit` 输出截断、确定性、fail-soft、miv 格式等其余 13 条断言原样保留。**

行为等价性说明：`minScore` 与 `limit` 均在排名之后生效，本次未改；唯一改变的是排名**之前**的候选集大小。适配后该文件在候选树 15/15 通过，在未修复的基线上为 13/15——失败的正是上述两条改点断言，其余 13 条在基线上依旧通过，因此适配没有削弱既有覆盖，也没有吞掉异常或删除断言。

## 语义后端与性能

移除记录截断后，首次冷缓存嵌入成本可能上升。当前 JS 引擎按条调用嵌入，不能用离线测试替身的耗时代表真实模型速度。用真实后端实测（真实 `multilingual-e5-small/q8` ONNX 模型，5/5 文件 SHA-256 命中 `semantic-js.js` 内冻结清单；真实 `python/worker_semantic_v1.py` + `bge-m3-onnx-int8-v1`）：

| 语料条数 | C2 冷嵌入（中位 / 区间） | C2 热查询 | C2 峰值 RSS |
|---:|---:|---:|---:|
| 256（旧行为口径） | 2.8 s / 1.6–5.5 s | 3–41 ms | 533–568 MB |
| 476（标准夹具） | 7.2 s / 3.6–9.5 s | 4–33 ms | 557–583 MB |
| 1024 | 17.4 s / 9.5–23.4 s | 7–33 ms | 568–580 MB |
| 2048 | 39.5 s / 21.7–46.9 s | 9–35 ms | 587–631 MB |
| 4097（单文件极值） | 57.3 s / 23.9–84.0 s | 5–30 ms | 614–640 MB |

绝对冷时间方差大（机器状态主导），**只有同进程配对测量可靠**：256→476 的增量为 +2.95/+2.97/+5.40 s，中位 **+2.97 s**（≈13.5 ms/条）；同进程冷嵌入由 1.6–4.7 s 升至 4.6–7.6 s（中位 2.8×）。ms/条 对条数的回归 R² 0.89–0.998，即成本对条数**近似线性**。两处截断都影响 C2：`l0Mode` 下语义臂同样活着（用 `l0Corpus` 构造 `rankSnap` 调 `_semanticRankBest`）。

热查询毫秒级，新增成本只出现在语料或其 `miv` 变化后的首次冷嵌入。注意缓存是**整个语料一个 `miv` 键**（`buildIndexIfStale`），语料任何变动都导致**整库重嵌、无增量嵌入**；本次改动把每次这类重嵌的规模从 256 条抬到全量。

**移除 cap 对 C3 没有任何影响**：`_pySemanticRank`（`lib/index.js:6792-6823`）接收 `corpusSnap` 但**从不读 `corpusSnap.records`**——它只用 `pyPaths` 取 `memoryIndexVersion`，再让 worker 在**自己已 `index_sync` 过的向量**上做 dense search，而那套语料来自 index-sync 的 M4 快照（另有 `SHADOW_LEXICAL_BUDGET_V1.corpusRecords = 512`、`sourceFiles = 3` 约束），与 `recall()` 的 L0 语料是两套东西。因此 C3 的 index-sync 成本（实测 476 条 18.5–40.5 s、4097 条 204.1 s；常驻内存约 1 GB）是它**自身的成本属性，不是本 PR 引入的**；C2 档直接承担上表成本，C3 档零成本，`auto` 档 C3 就绪走 C3、否则落回 C2。

**这是移除截断的真实代价，是否可接受需由维护者判断**；本修复不重新引入隐藏 cap，也不以文件重排掩盖不可达记录。若认为不可接受，方向应是持久化/增量嵌入缓存（`miv` 已具备可缓存语义、当前是整库粒度）或带明确覆盖协议的方案，而**不是**恢复查询前截断——该性能方案未在本 PR 实现。

需要特别说明的既有边界：C3 依赖 **index-sync** 子系统在 `<dsh-home>/memory/index/files` 下的同步快照（`workspaceKey` + `scope` + `miv` 三重对齐），该子系统有自己的分页预算（`INDEX_SYNC_PAGE_BUDGET_V1.maxRecordsPerPage = 64`）。本修复**不**重新设计 C3→C2→词法的降级链，也**不**宣称 C3 的召回覆盖已随本修复一起扩大；本修复只保证 `recall()` 自身不再在排名前丢掉候选。若出现不可接受的延迟，应继续评估持久化/增量缓存或有明确覆盖协议的检索方案，而不是重新引入不透明的查询前截断。
