# Memory recall 技术债清理方案（P1–P3，v4 之后的独立批次）

> 触发：用户 2026-10-24 原话「Memory recall 现在好像也是坨屎山，找时间修一下」
> 定位：**独立批次**，不并入 v4。原因见 §4。
> 状态：方案阶段，`lib/` 零改动。

---

# §0 · 一句话结论

> **它确实是屎山，但不是「算法烂」，是「结构烂 + 没有质量基准」。**
> 所以修法不是重写算法，而是先建**可测**（离线评测集）、再**可拆**（462 行函数 → 4 个模块）、再**可回退**（221.9 MB .bak 挪出 lib/）。
> 算法（语义臂 / RRF 融合）**不动** —— 那 1,420 行是活的，重写风险远大于收益。

## 1.2 真实效果（recall-stats.json，57,428 次注入记录）

| 通道 | events | hits | zeroHit | 零命中率 | 平均每次命中 |
|---|---:|---:|---:|---:|---:|
| **model**（工具调用） | 268 | 665 | **165** | **61.6%** | **2.5 条** |
| **inject**（注入侧） | 57,428 | 902,551 | 0 | 0.0% | 15.7 条 |
| **shadow**（影子校准） | 359 | 2,872 | 0 | 0.0% | **8.0 条** |

**三条通道互相矛盾**：model 只想起 2.5 条 / shadow 想起 8.0 条 / inject 想起 15.7 条。同一套语料、同一天，差 **6.3 倍**。这说明三条通道的「命中判据」不是同一套 —— 而没有任何文档说清它们应该相同还是不同。

## 1.3 命中分布（329 个被命中 id）

| 层 | ids | count | 占比 |
|---|---:|---:|---:|

**60 个 user 层 id 吃掉 42.7% 的命中量**；头部条目被反复召回（`mem_02d5bef3` 37 次、`mem_02855b71` 34 次），长尾几乎不动。

## 1.4 最关键的缺口：**没有召回质量基准**

28 个检索相关 smoke 套件，全部是「单点断言」（某个函数返回什么、某个字段存不存在）。**没有一条测「召回的到底对不对」**。

后果：
- 改判据不会红（只要函数签名不变）
- 改坏了会红（但红的是某个字段，不是「召回变差」）
- 无法回答「这次改动让召回变好了还是变差了」

# §2 · 三个阶段的方案

## P1 · 可测（1 天）—— 先建基准，不改任何代码

**目标**：产出一个离线评测集，能量化「召回质量」。

**做法**：
1. 从 `recall-stats.json` 的 57,428 次注入记录里抽样（按 layer 分层抽样，每层 200 条）
2. 反推每次的 query（注入记录里有 trigger + 上下文窗口）
3. 人工/半自动标注「应该命中哪些」（用当前实现的 top-10 做初筛，人工只做「是/否」）
4. 冻结成 `artifacts/recall-eval/dataset.jsonl`（约 400–600 条）
5. 写 `artifacts/recall-eval/run.mjs`：跑当前实现 → 输出 R@5 / R@10 / MRR / zeroHit 率

**验收**：
- 数据集 ≥400 条，覆盖 5 个 layer
- `run.mjs` 能跑出基线数字（**这就是「改造前」的对照值**）
- **负路径**：故意把 `recall()` 改成永远返回空 → zeroHit 率必须变成 100%（证明评测能测出退化）

**产出**：`artifacts/recall-eval/` + 一份 `BASELINE.md`（记录当前 R@5/MRR/zeroHit）

## P2 · 可拆（1 天）—— 462 行拆成 4 个模块

**目标**：改一处不用再读全 462 行。

**做法**：

| 现在 | 拆成 | 行数 |
|---|---|---|
| `recall()` 里的 handoff 分支 | `lib/recall-handoff.js` | ~40 |
| `recall()` 里的 archive 分支 | `lib/recall-archive.js` | ~50 |
| `recall()` 里的 sessions 分支 | `lib/recall-sessions.js` | ~30 |
| `recall()` 里的 all/current 主路 | `lib/recall-main.js` | ~200 |
| `recall()` 本体 | 只保留 scope 路由（~60 行） | 60 |

**同时做**：17 处 `await import()` 改成**顶部静态 import**。理由：运行期才知道依赖缺失是最难查的一类 bug（本仓历史踩过）。

**验收**：
- `recall()` 本体 ≤80 行
- 17 处动态 import → 0 处（除 `node:crypto` 这类可保留）
- **字节等价**：拆前后对同一输入返回**逐字节相同**的字符串（拿 P1 的评测集跑两遍比对）
- 负路径：任一子模块 import 失败 → 顶部就报错，而不是运行到一半才炸

## P3 · 可回退（0.5 天）—— 221.9 MB .bak 挪出 lib/

**目标**：不再在「5 个 l0-extract 版本」里猜哪个是真的。

**做法**：
1. `mkdir artifacts/_debt/lib-bak/`
2. 把 `lib/*.bak*` 全部 `git mv`（或 `mv`）进去
3. 写 `artifacts/_debt/README.md`：每个 .bak 的来源、日期、对应 commit（能从 git log 查到的写进去）
4. 检索所有代码/文档对 `.bak` 的引用，逐条处置（本仓已知有套件会扫 lib/ 目录，要确认）

**验收**：
- `lib/` 下 `.bak` = 0 个
- `lib/` 体积从 X MB 降到 Y MB（实测差值）
- 回归全绿（特别是有扫目录行为的套件）

# §3 · 明确**不做**的事（同样重要）

| # | 不做 | 为什么 |
|---|---|---|
| 1 | **不重写语义臂**（`semantic-js.js` 739 行 + `shadow-retrieval.js` 681 行） | 这是活的、有 28 个套件护着。重写风险 >> 收益 |
| 2 | **不动 RRF 融合权重**（`FUSION_RRF_K_PRE_V1`） | 没有评测集之前调权重 = 盲调。P1 做完再谈 |
| 3 | **不改 `recall()` 的对外契约**（返回值格式、scope 枚举） | v4 的 D 批要加 `scope='events'`，改契约会撞 |
| 4 | **不删 `shadow-retrieval`** | 它是校准通道（2872 命中 / 359 事件），是 P1 评测集的重要数据源 |
| 5 | **不并进 v4** | 见 §4 |

# §4 · 为什么不能并进 v4

`recall()` 在 `index.js:9153`，而 v4 的：
- **C 批**要改 `8516-8613`（注入段）
- **D 批**要改 `9153`（recall 加 scope=events）

两个改动**同一批文件、相邻行号**。并做的话：
1. diff 交织 → code review 无法区分「这是 v4 的改动」还是「这是 recall 重构」
2. 回归红了一起排查 → 不知道是哪条线引起的
3. 回滚回不干净 → 想撤 recall 重构会连带撤掉 v4 的注入改动

**结论**：**v4 做完发版后**再动 recall。现在只做「记录 + 建基线」（P1 可以提前做，因为 P1 不改 lib/）。
