## 1. 交付内容

### 1.1 规则段档位化

| 项 | 内容 |
|---|---|
| 新函数 | renderRulesSlimPre(rulesLayer, opts)（模块级，纯函数） |
| 输出 | 标题 + 引导语 + **每条规则首句（≤60 字符）** + 「共 N 条」 |
| 适用范围 | **仅 F4 运行中精简档**；其余档位给全文 |
| 守卫 | typeof renderRulesSlimPre === "function" + try/catch **fail-open 到全文** |

**为什么需要**：规则全文实测 **4,900+ 字符**。挂机自跑时无人消费，纯烧上下文。但完全不给也不行 —— 规则是硬约束，模型自跑时更需要知道边界。

**为什么 fail-open 到全文而不是空**：规则是**硬约束**。少给内容的代价（模型越界）远大于多给的代价（多烧 token）。

**实测压缩比**（真实用户级记忆 24,040 字符，抽 20 条规则）：**69.4%**（1,127 / 1,625 字符）。

### 1.2 画像段档位化

| 档位 | 是否投画像 |
|---|---|
| F1 HUMAN_FULL / F2 HUMAN_SLIM | 投 |
| F5 POST_COMPACT / F6 HANDOFF_CARRY | 投 |
| F7 HANG_COMPENSATE | 投 |
| **F3 RUN_FULL / F4 RUN_SLIM** | **不投** |
| **LEGACY** | **不投**（= 改前行为） |

**理由**（用户裁定）：画像回答的是「这个人什么样」，只有真人在场时才有意义。挂机自跑时投画像纯烧上下文，还容易让模型误把人设当技术规范。

**★实现约束（H5 套件四条判据）**：

| 判据 | 要求 |
|---|---|
| E2 | 能定位 if (s.userPortraitText) pushPart( 语句 |
| E3 | 该语句**缩进恰 4 空格**且在函数顶层（不能在 if 块内） |
| E4 | 守卫条件**只有** s.userPortraitText（不依赖 handoff/planText/eventCards） |
| E7 | 空值时 pushPart 整条不执行（零字节，连标题都不出） |

⇒ **不能**加 &&、**不能**包 if 块。最终方案：**档位判断放进文本实参**，不该投的档传**空串**，靠 pushPart 内部已有的 text === "" ⇒ return 完成零字节跳过。

### 1.3 F7 挂机代位补偿

**用户裁定（逐字）**：
> 「挂机的时候，人不在，没人说话；那模型自己跑了很多东西之后，是不是也该给一次完整版，免得它把前面的事忘了。」

| 项 | 内容 |
|---|---|
| 纯函数 | decideHangCompensatePre(accumTokens, threshold, enabled) |
| 触发条件 | enabled === true **且** 累计 token ≥ 阈值（默认 300,000） |
| 触发后 | fire: true + **累计清零**（防重复投） |
| 默认状态 | **hangCompensateEnabled: false**（用户裁定「先做但默认关，更保险」） |
| 注入侧累计 | 只在 **挂机 && !isHuman** 时累计（与 F1 的 isHuman 天然互斥，不会双投） |
| 授予键前缀 | hang:&lt;stepSeq&gt;（与 human: / water: 区分，便于诊断） |

**fail-closed 路径**：开关关 / 负累计 / NaN / 阈值 0 → 均不触发或回落默认。

## 4. 本批踩的坑

### 4.1 ★★新增模块级函数被渲染层引用 ⇒ ReferenceError（P3 同款教训的第二次）

renderRulesSlimPre 是模块级 const，而 renderMemoryDynamic 被 20+ 套件用 new Function 抽出执行，**沙箱里没有模块级符号**。

修复：typeof renderRulesSlimPre === "function" 守卫 + try/catch **fail-open 到全文**。

> **这是同一个教训的第二次**。P3 那次是 INJECT_TIERS，这次是 renderRulesSlimPre。
> 判据应该固化为：**凡在 renderMemoryDynamic 内引用模块级符号，必须 typeof 守卫或内联**。

### 4.2 ★画像段改造破坏了 H5 套件四条判据

我最初把画像段改成嵌套 if 块 —— 立刻红了 5 条（E2/E3/E4/E5/E7）。

**根因**：H5 套件的判据是**字面量正则**，要求 if (s.userPortraitText) pushPart( 在**同一行**、缩进**恰 4 空格**、条件里**没有 &&**。

**修复**：档位判断放进**文本实参**，守卫字样一个字不改，靠 pushPart 内部零字节跳过。

**教训**：「不要动被守卫的字符串」—— 改行为应该找**能改的维度**，而不是改被判据盯住的那段字面量。

### 4.3 ★测试自己的判据踩了「indexOf 先命中注释」的坑

idxSrc.indexOf("if (s.userPortraitText) pushPart") 第一次命中的是**注释里的示例文本**（我写的「守卫字样必须逐字保持 …」）⇒ B-1~B-6 全部测的是注释，不是代码。

**修复**：加 l.trim().startsWith("if (") 过滤注释行。

**这是「探针未命中」家族的又一次复现**：探针看着命中了，其实命中的是别的东西。
