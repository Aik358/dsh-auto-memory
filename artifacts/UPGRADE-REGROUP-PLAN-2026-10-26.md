## 1. 为什么重做（旧版哪里不对）

### 1.1 旧版做了什么

| 层 | 现实 |
|---|---|
| `startUpgradeJobPre` → 子代理 | 只做一件事：把 `MEMORY.md` 的条目按 **L0–L4 分层**（人之上的层 / 用户规约 / 项目规约 / 项目事件 / 纯流水） |
| `curateUnarchivedPre` → `writeCuratedEventsPre` | 另一条**独立**链，把账本→事件，但**聚类是纯确定性启发式**（目标段首行相同，或 6 小时内 2-gram 重合） |

**两者都不是「按语义重整事件」**。

### 1.2 实测旧版 curate 的产物（我踩过的坑）

在本工作区跑 `curate` + `writeCuratedEventsPre`，产出：

```
evt_ff51a338  <!--type=goal-->验证四类感知（userpercept/agent...
evt_376ce8f9  <!--typegoal-->-三项需求①事件记忆模式（日志→事件替换）...
evt_609589f4  <!--type=goal-->-**当前首要**让用户在本机真机上**重新看到...
```

**三个问题同时爆发**：

1. **KPI 事件**：一篇文章账本 = 一个事件（不合并、不拆分）
2. **事件名是垃圾**：直接取「目标段首行」，而那行是 `<!--type=goal-->` 这种未清理的 HTML 注释
3. **没有语义**：它不知道「这两篇讲的是同一件事」

> 已完整回滚（事件库恢复 2 个原始事件）。

## 2. 新版设计

### 2.1 总体流程（五阶段，人审卡在中间）

```
【0】扫描     → 遍历所有工作区，收集「源材料」与「现有事件」
   ↓
【1】粗分组   → 机械分类器只产出「候选分组 + 相似度信号」（加速器，不是决策）
   ↓
【2】AI 重整  → 子代理拿到候选 + 原文，**自己重新判断**：哪些是一件事、叫什么名、合并/拆分
   ↓
【3】出方案   → 产出一份「事件重整方案」，**只出方案不写盘**
   ↓
【4】人审     → 用户在面板预览：新增/合并/拆分/改名/归档，逐条批准
   ↓
【5】落盘     → 按批准结果写入，全程可回滚（快照 + 令牌）
```

### 2.2 关键设计决策（需要你逐条确认）

#### 决策 A：机械分类器的定位 = 「预分组建议」

| | 旧版 | 新版 |
|---|---|---|
| 产出 | **直接就是事件** | **候选分组建议**（`suggestedGroup`，可被 AI 推翻） |
| 权重 | 决策依据 | 仅作为 AI 的**输入提示** |
| 会不会写盘 | 会 | **不会** |

**实现**：现有 `groupIntoCandidateEventsPre` 保留，但输出改名为 `suggestedGroups`，并**强制标注 `confidence`**。AI 可以：
- 接受建议（说「这组确实是一件事」）
- 拆开（「这 5 篇其实是 3 件事」）
- 合并（「这两组是同一件事的两个阶段」）
- 全新分（「按目标段完全看不出，需要读正文」）

#### 决策 B：AI 的输入是什么（这是成本关键）

564 篇账本全文太大。分层投喂：

| 层 | 内容 | 每篇大小 | 用途 |
|---|---|---|---|
| L1 | **元数据**：文件名、mtime、四段标题行 | ~200 字 | 全部 564 篇都给 |
| L2 | **目标段 + 结果段** | ~400 字 | 全部给（这是判断「哪件事」的主要依据） |
| L3 | **全文** | 3–5 KB | **仅对 AI 主动要求的下钻** |

**预算估算**：564 × 600 字 ≈ **34 万字** ≈ 50 万 token。

**这个量一次装不下**，所以必须**分批**：

```
批 1: 第 1–40 篇（按时间序）→ AI 输出本批的事件草案（含「与前面批次的关系」）
批 2: 第 41–80 篇 + 批 1 的事件名清单 → AI 判断「哪些并入已有事件、哪些是新事件」
...
```

**每批 40 篇**，564 篇 ≈ **15 批**。

#### 决策 C：事件边界判据（必须明确定义，否则 AI 各批口径漂移）

> **一件事 = 一个连贯的目标从提出到达成/放弃的完整过程。**

判据（按优先级）：

| # | 判据 | 例 |
|---|---|---|
| 1 | **目标相同或演进关系** | 「修 issue #330」→「#330 的后续 review 修复」= 同一件事的延续 |
| 2 | **时间连续性**（无其他事件插入） | 同一目标中断 3 天又被拾起 ⇒ 同一件事 |
| 3 | **产物归属** | 同一批 commit / 同一个 PR / 同一个 tag ⇒ 同一件事 |
| 4 | **不合并的边界** | 目标不同（哪怕同一天）、或用户明确切换了话题 ⇒ 两个事件 |

**反例（不可合并）**：「P1 注入截流」与「§2.5 事件串行化」虽同一会话、同一天，但**目标不同** ⇒ 两个事件。

#### 决策 D：现有 8 个事件怎么处理

当前全机器共 **8 个事件**（本工作区 2 个 + `aik_auto_memory_use` 6 个）。它们有两种来源：
- **真实工作产生**（如 `evt_89786878`「项目白板」113+129 检查点）
- **v4 迁移留下**（如 `evt_dfc30819`「v4 底层改造」）

**方案**：

| 情况 | 处理 |
|---|---|
| AI 认为是**真事件且内容完整** | **保留**，只作为「已有事件」参与后续合并判断 |
| AI 认为应**并入新事件** | 标记为 `mergedInto: <新事件 id>`，**不删除**（改 status） |
| AI 认为**是垃圾/空壳** | 标记为 `superseded`，**不物理删除** |

**铁律：不物理删除任何已有事件。** 用 status 标记（`active` / `closed` / `superseded` / `mergedInto`）。

#### 决策 E：落盘策略 = 「提案 → 批准 → 写」+ 快照

```
① 生成提案  → 存到 .dsh-memory/upgrade-proposal-<ts>.json（不碰事件库）
② 用户在面板看：新增 N 个 / 合并 M 个 / 改名 K 个 / 归档 J 个
③ 用户点「批准」→ 服务端签发令牌（与现有 curate 同样的 fail-closed 机制）
④ 落盘前先快照：event-store.json → event-store.json.bak-upgrade-<ts>
⑤ 逐条写入（复用 §2.5 刚做的串行链，天然并发安全）
⑥ 落盘后**自动读回校验**：新增事件数 == 批准数？检查点守恒？
⑦ 任一步失败 ⇒ 整批回滚到快照
```

#### 决策 F：范围 = 所有工作区，但不是一次性全做

| 工作区 | 事件 | 账本 | 建议 |
|---|---|---|---|
| `--D--dsh-auto-memory--` | 2 | **591** | **主力，优先** |
| `--D--personal_issue--` | 0 | 71 | 第二批 |
| `--E--Academic_Issue--` | 0 | 16 | 第三批 |
| `--C--Users-JH Z-.dsh-aik_auto_memory_use--` | 6 | 1 | **只做事件整理，无账本** |
| 其余 9 个 | 0 | 0–1 | 跳过（没材料） |

**总计 681 篇账本**，其中本工作区 591 篇是主战场。

**建议分工作区独立跑**（用户逐个批准），而不是一次全机批。

## 3. 对「白板看板」与「prompt 注入」的影响（你特别要求考虑的）

### 3.1 白板看板现状

| 项 | 现状 |
|---|---|
| 白板 tab 模式 | **`planEventMode`** —— 显示**事件视图**（时间线 / 事件卡片 / 检查点），不是 kanban |
| 事件视图数据源 | `GET /event-list` + `GET /event-detail` |
| 数据规模 | 本工作区现在 2 个事件 / 242 检查点 |

### 3.2 重整后看板会变成什么样（必须让用户先看到）

如果 591 篇账本被重整成比如 **80 个事件**：

| 影响 | 变化 |
|---|---|
| 事件列表 | 2 → 80 条（**列表页严重变长**） |
| 每个事件卡片 | 平均检查点从 121 条 → **7 条**（671/80） |
| 滚动量 | 大幅增加 |
| 「当前在做什么」 | 从 2 个事件变成 80 个事件，**大部分是已完成的** |

**这是个真问题**：事件视图没有「按状态筛选 / 分页 / 时间轴折叠」。

**所以方案必须包含看板适配**：

| 适配项 | 做法 | 优先级 |
|---|---|---|
| **默认只看 active** | 事件视图默认筛 `status=active`，其余折叠为「已完成 N 个」 | **必须** |
| **时间轴分组** | 按「本周 / 本月 / 更早」分组折叠 | **必须** |
| **搜索/筛选** | 事件名 + 标签筛选 | 建议 |
| 分页 | 每页 20 个 + 加载更多 | 建议 |

### 3.3 prompt 注入现状（预算数据）

| 段 | 预算 | 说明 |
|---|---|---|
| 事件卡片 `renderT2Pre` | **2,400 字符** | 每段有配额：四段 900 / percept 200 / panels 150 / 检查点 900 / outcome 120 |
| 事件目录 `renderEventCatalogPre` | **400 字符** | 「卡片没展开的其他事件」的索引行 |
| 事件卡片选几个 | `pickT2EventsPre` | 只挑**当前进行中**的 1–2 个展开全文 |

**关键约束：事件数从 2 → 80，注入面预算不变（2,400 + 400）。**

这带来两个必须解决的问题：

### 3.4 ★问题 1：事件目录 400 字符装不下 80 个事件

现在 400 字符大约能列 **8–10 行**。80 个事件 ⇒ 只能列 10%，其余**静默消失**。

**方案**：

| 策略 | 做法 |
|---|---|
| **只列 active + 最近 closed** | 已完成的旧事件不占目录位（模型需要时用 `memory_recall` 检索） |
| **按需分层** | 目录只给「N 个进行中」+「最近 3 个已完成」，明确写「另有 N 个已归档，用 memory_recall 检索」 |
| 硬约束 | 事件目录**永不扩容**（400 字符是 D6 裁定），改为「压缩表示」 |

### 3.5 ★问题 2：事件卡片选谁展开

现在 `pickT2EventsPre` 挑「当前进行中」的 1–2 个。80 个事件里如果有 **5 个都是 active**怎么办？

**方案**：

| 优先级 | 判据 |
|---|---|
| 1 | `updatedAt` 最近的 active |
| 2 | 有未完成 `commitment` 的 |
| 3 | 与当前会话工作区相关的 |
| 落选处理 | 进「事件目录」一行索引 |

### 3.6 ★问题 3：事件名质量直接影响注入面

旧版事件名是 `<!--type=goal-->...` —— 这种名字进 prompt 是**纯噪声**。

**方案**：新增**事件名质量闸门**：

```
写入前校验：
  ① 不得包含 HTML 注释标记（<!-- -->）
  ② 不得以 - / * / # 等 markdown 标记开头
  ③ 长度 4–60 字（现有上限 80 太松）
  ④ 不得是「未命名工作」这类占位名
  ⑤ 必须能过「一句话说清这是什么」的人工可读性判断（AI 自评）
不合格 ⇒ 拒绝写入，要求 AI 重新命名
```

> 这条同时修掉了 §2.1 那个「HTML 注释污染注入面」的根因。

## 5. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | **AI 分批口径漂移**（第 1 批与第 15 批判断不一致） | 事件体系混乱 | 每批都带「已有事件全清单 + 判据」；最后一批做**全局复查** |
| 2 | **成本失控**（564 篇 × 15 批） | token 烧很多 | 先用 40 篇小样本跑通，确认质量再全量；每批可中断续跑 |
| 3 | **看板撑爆**（2 → 80 事件） | 用户体验崩 | 必须先做 3.2 的看板适配，**前端先于数据** |
| 4 | **prompt 注入退化** | 模型看到 80 个事件名反而更乱 | 必须先做 3.4/3.5 的注入适配，**注入先于数据** |
| 5 | **不可逆** | 用户后悔 | 快照 + 令牌 + 不物理删除 + 提案文件保留 |
| 6 | **跨工作区污染** | A 工作区的事件混进 B | 按工作区独立跑，提案文件按工作区分 |
