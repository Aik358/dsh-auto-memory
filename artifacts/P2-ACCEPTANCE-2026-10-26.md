## 1. 变更摘要

| 项 | 旧 | 新 |
|---|---|---|
| F1 触发键 | `fullInjectTokenGap = 250000`（累计新增 token） | `fullInjectWaterPct = "25,50"`（水位百分比列表） |
| 判定语义 | 距上次完整版累计新增 >= 250k 且用户说话 | 水位跨过阈值 + 用户说话 ⇒ 投一次，标记，跨下档再投 |
| 设置 UI | 无 | 文本框（逗号分隔），三面同步 |

### 1.1 为什么改（用户原话）

> 「如果你算 250 token 累计算的话，是有点太死板，你就别的别动，就把这个判断标准改成 25%、50%」
> 「这样设置里更好设置，直接填百分数就行」

**技术理由（我补充）**：250k 在不同窗口大小下语义漂移 —— 1M 窗口是 25%，128k 窗口是 195%（永远不触发）。百分比与窗口解耦。

### 1.2 为什么是「阈值列表」而不是「每 N% 一次」

用户指出：**DeepSeek Harness 实际到不了 75%**（压缩阈值 70-80%）。

若写成间隔制：会在 70% 附近产生一次「刚触发就压缩」的无用注入。列表制天然只有 25/50 两档；将来窗口变大要加 75 时**只改配置不改代码**。

## 2. 新增的两个纯函数

### 2.1 `parseWaterPctThresholdsPre(raw)` — 解析（`lib/index.js` L1702）

| 输入 | 输出 | 说明 |
|---|---|---|
| `"25,50"` | `[25, 50]` | 默认值 |
| `"50,25"` | `[25, 50]` | 自动升序 |
| `"25;50"` / `"25 50"` | `[25, 50]` | 多分隔符 |
| `"25,25,50"` | `[25, 50]` | 去重 |
| `""` / `null` / 全非法 | `[25, 50]` | 回落默认 |
| `"0"` / `"off"` / `"OFF"` | `[]` | **禁用** |
| `"150,25"` | `[25]` | >100 丢弃 |
| `"0.5,25"` | `[25]` | <1 丢弃 |
| `"25,50,75"` | `[25, 50, 75]` | 可扩展 |

### 2.2 `decideWaterPctFirePre(waterPct, thresholds, lastFired)` — 判定（L1752）

| 水位 | 已投 | 结果 | 说明 |
|---|---|---|---|
| 20% | 0 | 不触发，下一档 25 | 未到阈值 |
| 26% | 0 | **触发 @25** | 跨第一档 |
| 27% | 25 | 不触发，下一档 50 | 同档不重复 |
| 51% | 25 | **触发 @50** | 跨第二档 |
| 60% | 50 | 不触发，无下一档 | 已到顶 |
| 55% | 0 | **只触发一次 @50** | 跳档不连投 |
| 26% | 0（压缩重置） | **重新触发 @25** | 压缩后重来 |
| 任意 | — | 阈值空 ⇒ 永不触发 | 禁用 |
| 0 / NaN / 负数 | — | 不触发 | fail-closed |

> **★跳档设计（关键）**：水位可能一次从 20% 跳到 55%（跨两档）。按「最高已跨阈值」判定 ⇒ **一次跳档只投一次**，避免同轮连投两份完整版。

## 3. 注入侧接入（`lib/index.js`）

| 位置 | 内容 |
|---|---|
| L19709 起 | 水位判定块：读 `waterLevelRatio` → 算 `_waterPctNow` → 压缩回落则重置 `_waterPctFired` → 调 `decideWaterPctFirePre` |
| L19975 起 | 授予分支：`_waterFire.fire && isHuman` ⇒ 授予完整版 + 推进 `_waterPctFired` + 清 `_humanPending` |

**关键设计**：
1. **AND 条件**：水位跨阈值 **且** 本请求带真人消息。理由：水位可在 Agent 挂机自跑时跨过，那时没人消费 ⇒ 投了纯浪费，还会消耗掉「本档只投一次」的配额。
2. **不侵入既有判据**：新增一条「水位优先」旁路，命中即授予；不命中则**原样走既有逻辑**（零行为变化）。这是 P2 的硬约束 —— 现有授予逻辑已极复杂（真人旁路/首轮/轮次门槛/幂等闸）。
3. **压缩重置**：`_waterPctFired > 0 && _waterPctNow < _waterPctFired` ⇒ 清零。这是防「压缩后永远不再投」的死锁，**不是** F5 压缩检测本身（那个独立保留）。

### 5.2 变异验证

| # | 变异 | 结果 |
|---|---|---|
| m1 | `cur >= t` → `cur > t`（边界错） | **B-14 红** ✅ |
| m2 | 跳档取最低而非最高（会连投） | **B-7 红** ✅ |
| m3 | `"0"` 不再返回禁用 | **A-11 红** ✅ |
| m4 | 删 `cur <= 0` 守卫 | **无法红**（见下） |
| m5 | 删默认回落 | **A-7/A-10 红** ✅ |

**★m4 无法红的诚实说明**（按仓库纪律，不用编造判据凑绿）：
该守卫在逻辑上**冗余** —— `filter(t => cur >= t && t > prev)` 中，`prev >= 0` 且阈值 `t >= 1`（解析器已过滤 <1）⇒ 只有 `cur <= 0` 时 `crossed` 才可能非空，但此时 `t > prev` 要求 `t > 0`，而 `t >= 1` ⇒ `cur >= t` 只在 `cur >= 1` 成立 ⇒ 矛盾。
⇒ 它是**防御性代码**（防未来阈值为 0 的配置），不是当前行为的必要条件。套件覆盖的是「水位异常时 fail-closed 的**行为**」，不是「守卫这一行存在」。**已写入套件注释，不作粉饰。**
