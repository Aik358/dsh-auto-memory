### 判断：**会冲突**，而且**不能靠「静态段兜底」绕过**

`renderMemoryStatic()`（`:12082`，走 `systemPrompt.section`）实测**不含**用户规约/项目规约正文 —— 用真实规约里的独有串（`取证退出码` / `管道` / `多锚点` / `用户规约` / `项目规约`）逐条探测，结果**全部 false**。
⇒ 规约**只存在于动态完整帧里**。H2 一旦生效，真人轮（交互的绝大多数）将**完全看不到规约**。规约确实「每次全帧都在」，但全帧本身变得稀有 —— 这与「规约每次完整版必注入、不可裁剪」的精神**实质冲突**。

### 处置方案（按推荐顺序）

**方案 1（推荐）：先做 H5，再做 H2。**
在 `renderSlimSnapshotPre`（`:9856`）新增「用户规约 · 精简」段。**不能调用模块级 `renderRulesSlimPre`** —— 它有定义（`:1939`）但**全仓 0 个调用点**（grep `renderRulesSlimPre(` → 0 命中），且该函数被 20+ 套件用 `new Function` 抽取执行、沙箱里没有模块级 const。必须**内联**一份（与 `:11197 _renderRulesSlimInline` 同源同形）。

体积实测（真实规约数据，按「取首句 + 夹到 maxPer」算法）：

| maxPer | 用户规约 | 项目规约 | 合计 | 精简帧 2,219 → |
|---|---|---|---|---|
| 60 | 2,632 | 1,053 | 3,685 | 5,904（+166%） |
| 30 | 1,624 | 601 | 2,225 | 4,444（+100%） |
| 20 | 1,161 | 431 | 1,592 | 3,811（+72%） |

建议 `maxPer ≈ 24` + 硬上限 2,000 字符 + 末尾「全文用 `memory_recall` 取」指针。
**成本核算**：10 个真人 turn 现状 10×24,393 = 243,930 字符；新策略 1×24,393 + 9×(2,219+1,592) = **58,692**，仍是现状的 **24%**。H5 的增量吃掉不到 1/4 的节省。

**方案 2：H2 先做，但保留「会话首 N 个人 turn 仍给全帧」的宽限（如 N=2）。** 改动更小、体感更平滑，但偏离用户设计意图（三时机之外不该给全帧），且 N 需调参。

**方案 3：不做 H5，只在精简帧加一行「规约已启用，全文见完整版 / 用 memory_recall」。** 零成本零风险，但等于放弃约束在场，**不推荐**。

**方案 4：把规则段挪进静态 section（`:12082`）。** 每帧都在且天然是缓存锚；但会改变 system prompt 字节稳定契约 —— 静态段之所以不含规约，正因为它设计成「不随状态变化」；规则文件一变缓存锚即失效。**不建议**在本批做。

## 5. 结论

`_grantByHuman` 改成 `false` 是**正确方向**，但**不能只改这一行**：
① 必须同批把 `_humanPending` 的消费上移到该行之前（否则水位/挂机档被后续 agent 请求吃掉 —— 实测反向）；
② 必须给该请求加「定稿复读」（否则压缩后帧②降级、真人轮两帧带不同标记、交付不确定）；
③ 必须**先做 H5**（精简帧内联规则摘要；`renderRulesSlimPre` 是 0 调用点的死代码，不可直接用），否则真人轮将完全看不到规约。
