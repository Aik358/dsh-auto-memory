> **v5（2026-10-27）★根本性简化：白板优先，不再读账本** —— 用户裁定「先让 agent 读相应工作区白板 ⇒ 直接输出该工作区新版本白板内容」「之后按时间标签把 memory log 按时间依附在相应事件下」「**只读白板就行，足够精简**」。实测：只读白板 58,360 字符 ≈ **4.9 万 token**；而读账本 1,325,245 字符 ≈ 112 万 token（**23 倍**）、读账本+日志 147 万 token（**30 倍**）。★关键澄清：**白板 PLAN.md = 记忆主承载面，交接账本 handoff-*.md = 一次性接续材料**，两者不是一回事 —— 账本信息绝大部分已被白板吸收，迁移时**不读、不归组、不建事件**。新增阶段 8 含：白板/账本辨析 + 5 步流程 + 工作区扫描（排除 1,063 个测试残留）+ 章节切事件规则 + 日志按时间挂载 + ★报告必须列出全部写入的工作区。

## 阶段 3：五类分拣（每条旧条目归入且只归入一类）

| 类 | 判据（**由模型判断，不许正则**） | 去向（真实 API） |
|---|---|---|
| **人之上的层** | 「这个人是谁」「我们一起经历过什么」「他在意什么」—— 性格、偏好倾向、共同经历、情感记忆、自传 | **L0** 直接写 `~/.dsh/memory/person/event-store.json`（见阶段 4.1） |
| **用户规约** | 「跨项目通用、对我这个人的要求」—— 交付格式偏好、沟通方式约定、禁止行为 | **L1** `memory_user(action:'append')` 或 `memory_rules(op:'add')` |
| **项目规约** | 「这个项目必须怎么做」—— 硬约束、验收纪律、架构决策、路径约定 | **L2** `memory_note(kind:'note', action:'append')` |
| **项目事件** | 「这个项目在做什么、试过什么、失败过什么」 | **L3** `memory_event(action:'create'/'append')`（默认就是本工作区） |
| **纯流水** | 一次性进度记录、临时路径、已过时的计划 | `memory_log(note:...)` 保留可检索，或丢弃（原件已备份） |

### ★★L0 与 L2/L3 的边界

```
判断口诀：换个工作区打开，这条内容还应该在吗？
  应该在            ⇒ L0（人之上的层）或 L1（用户规约）
  只在这个项目有意义 ⇒ L2（项目规约）或 L3（项目事件）
```

**反例（必须避免）**：
- ❌ 把「用户偏好中文回答」写进某个工作区的 MEMORY.md ⇒ 换工作区就没了
- ❌ 把「我们上次一起调这个插件」写进工作区事件库 ⇒ 换工作区就没了
- ❌ 把「本项目端口 56877」写进 person store ⇒ 污染跨项目层

### ★★用户画像 vs 用户规约（用户明确强调，不许混）

- **用户画像 = emotional / 主观 / 生活化 / 情境化**（感觉、印象、相处方式、共同经历）
- **用户规约 = rational / 硬**（每次完整版注入的约定类内容）
- **两者不许混**。一条内容若两者都沾，**拆成两条**，分别落到 L0 与 L1。

## 阶段 4：写回（★全部使用真实存在的 API，不得臆造参数）

### 4.1 L0 人之上的层 —— 直接写文件

`memory_event` **没有 scope 参数**，不要把 person 层塞进工作区事件库（换工作区就丢）。
正确做法：读 `~/.dsh/memory/person/event-store.json`（不存在则建），按 event-store 的 16 字段结构追加事件；
每条带 `sections{goal,doing,deadend,next}` 与四类感知。写前先备份，写后 `sha256` 核对。

### 4.2 其余四类

```
L1 用户规约 → memory_user(action:'append', content)          或 memory_rules(op:'add', content)
L2 项目规约 → memory_note(kind:'note', action:'append', content)
L3 项目事件 → memory_event(action:'create', name, summary, sections{goal,doing,deadend,next})
             memory_event(action:'append', eventId, checkpoint{kind,text,panels}, userPercept{...}, agentTrace{...})
L4 纯流水   → memory_log(note, kind:'fact')
```

### 4.3 ★四类感知（v4 核心，缺了就只剩流水账）

`memory_event(action:'append')` 可带四类感知，**必须用**（不是可选装饰）：

- `userPercept` 人类侧观察 `{stage, kind, text}`
  · stage = `retrieved`(被检索到) / `delivered`(被投递) / `used`(真用上) / `mentioned`(被提到) / `accepted`(用户确认)
  · kind  = `preference`(偏好) / `state`(当前状态) / `unfinished-goal`(未完成目标) / `authorResponse`(作者回应：同意/否定/纠正/补充/质疑/拍板)
  · ★只有 `accepted` / `used` 会进「用户画像」段注入，其余是噪声
- `agentTrace` 你做了什么 `{action, result, wasRefuted}`
- `sharedGround` 已达成的共识 `{claim, confirmedBy, correction}`
- `commitment` 你对用户的承诺 `{promise, boundary, state:'open'/'kept'/'dropped'}`

**只在实质性进展时写感知**（新结论 / 验收结果 / 交付物落盘 / 用户新裁定）；纯读取、纯等待、重复确认**不算**。

### 4.4 ★四段每次变动必重写

`sections{goal,doing,deadend,next}` **反映当前状态，不是历史累积**。
每次 append 检查点后、或事件状态有任何变化时，用 `memory_event(action:'set', eventId, sections:{...})` 把四段整体重写一遍。
**只追加检查点而不更新四段 = 四段变成陈年快照。**

**每一类最多一个批次，写完立刻自检，不要边写边判。**

### 4.5 ★★★账本 → 事件的归组方法（v4 新增，本轮核心）

> ⚠️ **这是本流程最容易做错的一步。** 旧记忆有几百篇 `handoff-*.md` 账本，
> 它们不是「一个账本 = 一个事件」，而是「**若干篇账本 = 一件事**」。
> 你必须先把它们**归组**，再为每组创建一个事件。

#### 4.5.1 三类产物必须分开处理（**先分类，再动手**）

`handoff/` 下的文件不是一类东西。**先按下面的表分类，不同类走不同流程**：

| 类型 | 识别方法 | 处理方式 |
|---|---|---|
| **真账本** | 含 `## 目标` **且** 含 `## 进度与下一步` | **走语义归组**（见 4.5.2） |
| **白板快照** | 文件名 `PLAN-YYYYMMDD-*.md`，或内容以「项目全貌」「这是什么」开头 | **按日期归桶，不看内容** |
| **会话转写包** | 文件名 `prev-req-*.md`，或首行含「用户请求原文」 | **按日期归桶，只读前 5 行** |
| **说明文档** | `README*.md` / `README-白板已重写.md` 等 | 单篇成事件，或直接跳过（原件已备份） |

★ **为什么必须分开**（实测数据）：
- 白板快照每天一份、内容高度重复。让模型判断「9-08 和 9-09 的白板快照是不是同一件事」→ **必然误判**。
  按日期归桶就完事（原型实测：261 篇 → 39 个桶，零误判）。
- `prev-req-*.md` 单篇可达 **518KB**（历史消息原文）。**绝对不能读全文**，只读头部 5 行拿日期即可。

★ **机械产物的桶命名模板**（必须含日期，一天最多一个桶）：
- 白板快照 → `白板快照 · YYYY-MM-DD`
- 会话转写  → `会话转写包 · YYYY-MM-DD`

#### 4.5.2 真账本的归组判据（三条，任一成立即可）

```
① 目标相同或演进
   · 「发布 2.2.1 第一步」+「发布 2.2.1 第二步」⇒ 同一件事
   · 「修某个 bug」+「该 bug 的复查修复」⇒ 同一件事
② 时间连续
   · 相邻两篇间隔 < 6 小时，且中间没有其他目标插入
③ 产出归属相同
   · 同一 commit / 同一 PR / 同一 tag / 同一交付物
```

★★ **用户明确裁定**：**同一目标中断多日后被重新拾起 ⇒ 仍算同一件事**（不要因为隔了几天就拆开）。

**反例（必须拆成两个事件）**：
- 同一天做的两件独立事（如「注入截流」与「事件串行化」）⇒ 两个事件
- 目标不同但文件相邻 ⇒ 两个事件
- 同一会话但用户明确切换了话题 ⇒ 两个事件

#### 4.5.3 ★★★精读 + 跳读规则（**绝对禁止整文件塞进上下文**）

> **硬规则：任何一次 `read` 不得超过 8,000 字符。超过就退化成「只读 ## 目标 段」。**
> 587 篇账本全文约 124 万字符 ≈ 100 万 token，**整体读会直接爆上下文**。

**第 1 步 · 跳读建索引（不读正文）**

对每篇真账本，只取「文件名 + 修改时间 + 目标段头 3 行」，拼成一张索引表：

```bash
# 在 handoff/ 目录下执行，只取目标段前 3 行，不读全文
for f in handoff-*.md; do
  echo "=== $f $(stat -c %y "$f" 2>/dev/null | cut -d. -f1)"
  sed -n "/^## 目标/,/^## /p" "$f" | sed -n "2,4p" | cut -c1-120
done
```

★ 产出：一张 `序号 | 文件名 | 时间 | 目标摘要(≤60字)` 的表。
  587 篇 × 60 字 ≈ **3.5 万字 ≈ 3 万 token ⇒ 一次装得下**。

**第 2 步 · 归组判断（只看索引表，不读正文）**

基于索引表判断哪些序号的账本属于同一件事。**这一步不需要读任何正文。**

**第 3 步 · 精读（只读选中的，且只读结构）**

只对「已确定要归到同一事件」的篇目读正文，且**只读四段标题与首段**：

```bash
# 只读任务状态段的前 8 行，不读全篇
sed -n "/^## 任务状态/,/^## 目标/p" "某篇.md" | head -8
```

单事件平均 7 篇 × 400 字 ≈ **2,800 字 ≈ 2,300 token**，完全可控。

#### 4.5.4 事件名质量闸门（**不合格会被前端拒绝显示**）

```
✅ 合格：4–60 字，人类可读，动宾结构
   好例：「修复上下文页卡死」「注入截流方案落地」「发布 2.2.1」

❌ 不合格（必须改）：
   · 含 HTML 注释标记（<!-- -->）—— **旧版垃圾事件名的直接来源**
   · 以 markdown 标记开头（# - * >）
   · 占位名（未命名 / untitled / TODO / 待整理）
   · 纯数字或纯标点
   · 直接拿文件名（如 handoff-20261010-185158）
```

★ 若某篇账本的目标段是空的、或只有标题，**不要**拿文件名当事件名 —— 
  改用它「任务状态」段的首句，或用「YYYY-MM-DD 的某项工作」这种可读描述。

#### 4.5.5 每个事件必须带起止时间

```
members   = 属于这件事的全部账本文件名（相对 handoff/）
startMs   = 这些账本里**最早**的 mtime
endMs     = 这些账本里**最晚**的 mtime
summary   = 一句话总览（≤200 字，说清做了什么、结果如何）
sections  = {goal, doing, deadend, next} 四段（反映当前状态，见 4.4）
```

★ 时间线清晰的根本就是 `startMs`：前端按它升序排，跨天的事不会断成两半。

## 阶段 5：自检（缺一不可）

1. **条目数守恒**：旧文件总条目 N = 新五类条目之和（允许 ±0，不允许丢）
2. **抽查 10 条**：随机取旧条目，确认内容在新位置可检索到
3. **画像纯度**：`[用户画像]` 段里**不得出现技术规范**（用 3 条已知技术规范做反例）
4. **规约纯度**：`[项目规约]` 段里**不得出现性格/生活偏好**
5. **层归属**：person store 里**不得出现项目路径 / 项目名 / 端口号**
6. **L0 独立可用**：换一个工作区打开，`[用户画像]` 段**仍必须有内容**
7. **原文件 sha256 未变**（证明只备份没改）
8. **无幻影 API 调用**：全程不得出现 `memory_status({op:'upgrade-done'})` 或 `memory_event(scope:...)`
9.  **账本守恒**：`handoff/` 下「真账本」总数 = 所有事件 `members` 之和（**允许 ±0，不允许丢**）
    · 实测方法：`ls handoff-*.md | wc -l` 对比你写的所有事件 members 总和
    · 白板快照 / 会话转写包**单独计数**，不计入真账本
10. **机械产物按日期**：白板快照 / 会话转写包的事件名**必须含日期**，且**一天最多一个桶**
11. **事件名合规**：所有事件名过 4.5.4 的质量闸门，**零违规**（不得含 HTML 注释 / markdown 前缀 / 占位名）
12. **时间线完整**：每个事件都有 `startMs` / `endMs`，且 `startMs <= endMs`
13. **精读纪律**：全程**没有任何一次 read 超过 8,000 字符**（这是防爆上下文的硬指标）

## 阶段 7：★★★效率纪律（v4.1 新增 · 用户裁定「注重效率，提高速度」）

> **背景（实测数据）**：上一轮子代理跑了 **1,516 秒 / 77 次工具调用**，
> 而真正产出数据盘写的只有 **3 次（4%）**。时间分布：探路 10%、读插件源码 16%（**与本任务完全无关**）、
> 读历史备份 25%、会话取证 13%。**用户的耐心是按分钟计的，不是按小时。**

### 7.1 ★三条铁律（违反即算失败）

```
① 【不读插件源码】你在做「记忆整理」，不是「开发调试」。
   ❌ 禁止 read/grep D:/dsh-auto-memory/lib/ 下任何文件
   ❌ 禁止查 package.json / 版本号 / 工具 schema 定义
   ✅ 需要知道工具怎么用，读本文档就够了（本文档是权威）

② 【不重复前序成果】同一工作区若已存在 `.dsh-memory/migration-*/` 或 `.dsh-memory/backup/*-pre-v4/`，
   说明**已有前序子代理做过一轮**。此时：
   ✅ 只做「增量」——检查还差什么，补上即可
   ❌ 不要把已完成的备份、报告、五类分拣**重新读一遍**验证（那是重复劳动）

③ 【先探明再动手，最多 3 次探路】
   第 1 次：`pwd` + `ls` 确认当前工作区（**一次搞定，不要分 8 次问**）
   第 2 次：确认目标工作区的 handoff/ 结构
   第 3 次：确认 event-store 现状
   ⇒ **3 次之内必须开始干活**。超过 3 次探路 = 方向不明，立刻停下来重新想。
```

### 7.2 时间预算（硬指标）

| 场景 | 目标耗时 | 硬上限 |
|---|---|---|
| 单工作区、< 50 篇账本 | **< 3 分钟** | 8 分钟 |
| 单工作区、50–200 篇 | **< 8 分钟** | 20 分钟 |
| 单工作区、> 200 篇 | **< 20 分钟** | 40 分钟 |
| 多工作区批量 | 按工作区数 × 上表 | — |

**超时的自救动作**：若发现已超过硬上限仍在中途，**立刻停止扫描，用已收集的信息先落盘一批**。
宁可分两次做完，也不要一次卡死（用户看到 `phase:running` 十几分钟会以为卡死了）。

### 7.3 ★批量化：一次命令处理一批，不要一篇一命令

```bash
# ❌ 慢：每篇账本一次 read 调用（500 篇 = 500 次调用 = 至少 1 小时）
read handoff-xxx.md

# ✅ 快：一次命令批量提取 500 篇的目标段（1 次调用 ≈ 10 秒）
cd <ws>/handoff && for f in handoff-*.md; do
  echo "=== $f"
  sed -n "/^## 目标/,/^## /p" "$f" | sed -n "2,3p" | cut -c1-100
done
```

**判据：总工具调用次数应 ≈ 批数 + 事件数，而不是 ≈ 账本数。**

### 7.4 禁止的浪费行为（实测踩过，逐条对应上面的 25% / 16% / 13%）

```
❌ 为一个信息量重复 grep 同一个文件 3 次以上
❌ 用 `find` 全盘搜索插件安装位置（你不需要知道插件装在哪）
❌ 用 session_trace / session_event_search 查「我自己是谁、我在哪个会话」（你没有这个需求）
❌ 读上一个子代理写的 SELFCHECK.md / REPORT-TABLE.md 再逐条核对（信任它，做增量）
❌ 为了「确认格式对不对」去翻 event-store.js 的 schema 定义（用 memory_event 试写一条即可）
```

### 7.5 正确的最短路径（照这个顺序做，不要发明新流程）

```
第 1 步（30 秒）：定位工作区
  pwd; ls handoff/ | head -5

第 2 步（1 分钟）：批量建索引（一次命令）
  见 7.3 的 for 循环

第 3 步（2-5 分钟）：在脑内归组，不要写脚本验证归组
  ⚠️ 上一轮子代理花了 10+ 分钟写 Python 脚本反复验证「桶里有没有漏文件」——
     这是**过度自证**。归组正确性用第 4 步的「账本守恒」一个数字就能验，不需要逐桶核对。

第 4 步（批量写盘）：
  对每个事件调一次 memory_event(action:create) —— 大桶可用一次 create 带多个成员

第 5 步（30 秒）：守恒自检
  ls handoff-*.md | wc -l  对比  所有事件 members 总和
```

❌ 不能省的：

## 阶段 8：★★★白板优先（v5 核心 · 用户裁定 2026-10-27）

> **用户原话**：「先让 agent 读相应工作区白板 ⇒ **直接开始输出该工作区新版本白板内容**」
> 「之后按时间标签把 memory log 按时间依附在相应事件下就行」
> 「**只读白板就行，足够精简**」

### 8.0 ★★★先分清两类文件（这是本方案的前提，混淆了就会做错）

```
┌─────────────────────────────────────────────────────────────┐
│ 白板  handoff/PLAN.md                                        │
│   = 记忆主承载面。人类可读的项目全貌：这是什么 / 汇报口径 /   │
│     当前进展 / 当前目标 / 判据 / 版本归档 / 路径约定           │
│   ✅ **迁移时只读它**                                        │
│   ✅ 它本身就是被压缩过的记忆，读了不丢信息                   │
├─────────────────────────────────────────────────────────────┤
│ 交接账本  handoff/handoff-*.md                               │
│   = 一次性接续材料（四段：任务状态/目标/已试方案/进度与下一步）│
│   ❌ **迁移时不读、不归组、不建事件**                         │
│   ❌ 它的信息绝大部分**已被白板吸收**                          │
│   ✅ 备份留档即可（阶段 1 一次 cp -r）                        │
└─────────────────────────────────────────────────────────────┘
```

**实测成本对比（本机真实数据）**：

| 方案 | 读取量 | token | 倍数 |
|---|---|---|---|
| **只读白板（本方案）** | 58,360 字符 | **≈4.9 万** | **1×** |
| 读账本 | 1,325,245 字符 | ≈112 万 | **23×** |
| 读账本+日志 | 1,730,190 字符 | ≈147 万 | **30×** |

⇒ **只读白板快 23–30 倍，而且白板是「记忆主承载面」，信息不丢。**

### 8.1 完整流程（照做，5 步）

```
第 1 步：扫出有白板的工作区（一次命令，排除测试残留）
  见 8.2

第 2 步：读白板（每个工作区一次 read，白板通常 5K–45K 字符）
  有白板 ⇒ 读它，进第 3 步
  无白板但有日志 ⇒ 读日志（见 8.4），进第 3 步
  无白板无日志 ⇒ 跳过（不建任何事件）

第 3 步：把白板切成事件（在脑内做，不写脚本）
  规则见 8.3

第 4 步：批量落盘 memory_event(action:create)
  一节一个事件，或把强相关的几节合成一个事件
  每事件带 startMs/endMs（从章节日期推）

第 5 步：memory log 按时间挂到事件下（见 8.5）
```

### 8.2 第 1 步：扫出真实工作区（★必须先排除测试残留）

```bash
# 本机实测：1,103 个目录里只有 40 个是真的，1,063 个是测试残留
cd ~/.dsh/memory/workspaces
for d in */; do
  # 排除测试残留（这些目录名含以下关键字）
  case "$d" in
    *AppData-Local-Temp*|*dam-consolidate*|*dam-isolation*|*dam-plan-cas*|*migration-workspace*|*.cdp*) continue ;;
  esac
  [ -f "$d/handoff/PLAN.md" ] && echo "$d  PLAN=$(wc -c < "$d/handoff/PLAN.md")"
done
```

★ **判据**：扫出来的工作区数**不应该超过 50**。若超过，说明测试残留没排干净，回头检查排除规则。

### 8.3 第 3 步：白板怎么切成事件

**规则：白板的一个 `##` 二级章节 ≈ 一个事件。**

```
## 这是什么                → 不建事件（这是元信息，落 note）
## 汇报口径（用户裁定）     → 不建事件（落 L2 项目规约）
## ★当前进展与最新实况      → 建事件（取章节标题里的日期做 startMs）
## ★当前目标 · v4 底层改造  → 建事件
## 发布流程                 → 建事件
## 判据与工具               → 建事件
## 版本归档                 → 建事件（或合并进"发布线"事件）
### 子章节（###）           → 并入所属 `##` 事件，作为 checkpoint
```

**事件名**：直接用章节标题去掉 `★` 和括号注解。

```
✅ 「当前进展与最新实况」（配合 startMs 表明是哪天的）
✅ 「发布流程」「判据与工具」「版本归档」
❌ 「## ★当前进展与最新实况 · 2026-10-26（v4 收口后 · Lead 独立实测）」← 太长，去注解
```

**startMs / endMs 从哪来**：

```
① 章节标题里若有日期（如「· 2026-10-26」「（2026-10-11 · v0.1.0）」）⇒ 用它
② 没有日期 ⇒ 用该章节内正文提到的**最早**日期
③ 都没有 ⇒ 用白板文件的 mtime（`stat -c %Y`）
```

**一个 `##` 章节 = 一个事件的 checkpoint**，章节正文就是该 checkpoint 的 text。

### 8.4 无白板但有日志的工作区

```
本机实测这类工作区：dsh_debug(3篇) / Ark9Tools(4篇) / 新建文件夹(1篇) / dsh_dynamic_adjust(4篇)
合计仅 7.8 万字符 ≈ 6.6 万 token —— 很小，直接读日志。

处理：把日志按日期归组成事件，一个连续日期段 = 一个事件。
```

### 8.5 第 5 步：memory log 按时间挂到事件下（用户原话）

```
用户原话：「之后按时间标签把 memory log 按时间依附在相应事件下就行」

做法：
  ① 每个日志文件 = 一天 = `YYYY-MM-DD.md`
  ② 找到 startMs/endMs 覆盖该日期的事件
  ③ 把该日志文件的条目作为 checkpoint append 到那个事件：
       memory_event(action:"append", eventId, {
         kind:"log",
         text: <日志该日的摘要，≤300 字>,
         at: <该日 00:00 的 ms>
       })
  ④ 若某日日志找不到覆盖它的事件 ⇒ 新建一个「YYYY-MM-DD 的若干工作」事件承接

★ 不要一次 append 一天的全部原文 —— 只 append 摘要（≤300 字/天）。
  原文在日志文件里还在，检索得到。
```

### 8.6 ★进度与守恒自检

```
必做（不能省）：
  ① 有白板的工作区数 = 你处理过的工作区数（列出来对比）
  ② 每个工作区：白板 `##` 章节数 ≈ 该工作区建的事件数（可合并，但要有理由）
  ③ 每个事件都有 startMs / endMs
  ④ 事件名过 4.5.4 的质量闸门

可以省：
  ❌ 逐节核对白板正文有没有漏字（白板已经是精简的，漏一点不影响）
  ❌ 写脚本验证事件覆盖了白板的每一行
```

### 8.7 ★★报告必须写明「我实际写入了哪些工作区」

```
用户明确要求：子代理必须在报告中明确写出「我实际写入了哪些工作区」。

背景（实测事故）：从 dsh-auto-memory 派出的子代理，实际把结果写进了
  C:\Users\JH Z\.dsh\aik_auto_memory_use —— 发起方原工作区一篇没动，
  而它的 summary 里说的全是另一个工作区的事，看起来像虚报。

⇒ **报告必须包含下面这张表，一行一个工作区，不允许省略**：

| 工作区（绝对路径） | 白板章节数 | 建了几个事件 | 挂了几条日志 | 状态 |
|---|---|---|---|---|
| C:\Users\JH Z\.dsh\memory\workspaces\--D--dsh-auto-memory-- | 20 | 12 | 30 | ✅ 完成 |

★ 状态只能是：✅完成 / ⚠️部分（写明差什么）/ ❌跳过（写明原因，如「无白板无日志」）。

```
