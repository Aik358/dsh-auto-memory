## 2 · 工作流：一次只做一个工作区

```
清单第 1 个工作区 → 做完 5 步（全部写完） → 第 2 个 → ...
```

### 第 1 步 · 读（1 次 win_bash）

```bash
W="<清单里的目录名>"; D="$HOME/.dsh/memory/workspaces/$W"
echo "=== PLAN ==="; cat "$D/handoff/PLAN.md" 2>/dev/null
echo "=== LOGS ==="; for f in "$D"/[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9].md; do [ -f "$f" ] && { echo "--- $(basename "$f") ---"; sed -n '1,120p' "$f"; }; done
echo "=== EXISTING ==="; grep -o '"name": *"[^"]*"' "$D/handoff/event-store.json" 2>/dev/null | head -30
```

**读完你就有**：白板全貌、日志逐日内容、已有事件名（避免重复建）。

### 第 2 步 · 归组（脑内，不写脚本）

把「日志的一天」和「白板的一段叙述」归成事件。**三条全满足才归一事**：

| # | 判据 | 正例 | 反例 |
|---|---|---|---|
| ① | 目标相同或演进 | "v4 改造"分几次汇报，目标同一个 | "修 bug A" 和 "写文档 B" |
| ② | **时间连续**（间隔 < **30 天**；超过 30 天就是另一件事） | 9/20、9/21、9/22 | 9/20 和 11/15，中间两月没动 |
| ③ | 产出归属相同（同一文件/同一功能） | 都改 `lib/client.js` 同一功能 | 改 `lib/` 和另改 `site/` |

**归组单元 = 一篇日志 或 一段白板叙述。**

> ❌ 错误（v5 实测）：白板 14 个 `##` 章节各建一事件 → 14 碎片，64% 单检查点。
> ✅ 白板章节是**描述侧面**（约束/待办/进度），真正的事在日志里。

### 第 3 步 · 写事件（每事件 1 次 memory_event）

```
memory_event(action='create',
  name='<4-60 字，去掉 ★ 和括号注解>',
  summary='<≤400 字>',
  kind='ledger',
  confidence='high',
  startMs=<最早成员时间戳>,
  endMs=<最晚成员时间戳>,
  members=['handoff/xxx.md', '2026-10-24.md'],
  rationale='<一句话：为什么这几篇是一件事>',
  sections={ goal:'…', doing:'…', deadend:'…', next:'…' })
```

**★ `members`（来源清单）和 `rationale`（归组理由）是必填，不是可选。**
它们证明"由哪几篇归组、为什么"。缺了就退化成碎片。

### 第 4 步 · 挂日志检查点（每篇日志 1 次 append）

> **用户原话**：「memory log 按时间依附」在相应事件下（不是独立建事件）—— 日志不是独立事件，是挂到事件下的检查点。

```
memory_event(action='append', eventId='<create 返回的 id>',
  checkpoint={
    at=<该日志日期时间戳>,
    kind='log',
    goal='<该日目标>',
    state='<该日进展>',
    dead='<该日卡点，无则空串>',
    next='<该日下一步>',
    quoteRef='<该日最能代表的一句原文>',
    quoteLine=<行号>,
    text='≤300 字摘要' })
```

**★ 四段必须分别提取**，不许把整段原文塞进 goal。

**★ 溯源必须带全**（否则检查点是不可审计的传闻）：
- `quoteRef` = 该日最能代表结论的**原文摘录**（不是你的概括）
- `quoteLine` = 该句在源文件里的**行号**（能回查）
- `rel` = 源文件相对路径（如 `handoff/handoff-20261015-xxxx.md`）
- `bytes` = 源文件字节数、`sha256` = 源文件指纹（证明读的是这一版）
- 只有 `text` 没有以上字段 = **没有证据的传闻**，自检会打红

### 第 5 步 · 渲染新白板（1 次 memory_note · **不要手写正文**）

```
memory_note(kind='plan', fromEvents=true)
```

> **★★ 为什么不再手写模板**（2026-10-27 用户裁定 Q3「白板 = 事件的投影视图」）：
> 白板正文由 `plan-render.js` **从你刚写好的事件自动渲染**
> （4 节 = 当前状态 / 近期进展 / 关键约束 / 待办，全部来自事件，不用你拼模板）。
> 你手写模板会变成「事件之外的第二个真相」：事件一更新、白板不跟着变，两边就漂移。
> **你唯一要保证的是事件质量** —— 白板只是它的投影。
>
> 若渲染器报错（旧版本无 fromEvents / 渲染结果为空），才用 `fromEvents=false` + 手写兜底，
> 并在报告中注明「兜底手写」。

**写盘注意**（渲染路径已自动处理，你只需确认）：
- 旧白板的 `<!--memory:mem_*` 锚点由写盘口保护（M1 门），**不需要你抄**
- **不新增** HTML 注释
- 旧白板自动归档，不丢
- 备份纪律：**只读原样复制**，不修改原件

## 2b · ★★★ 白板是【产出物】，不是输入物（为什么「只读白板」就够了）

**白板 `handoff/PLAN.md` ≠ 交接账本 `handoff/handoff-*.md`。两者本质不同：**

| | 白板 PLAN.md | 交接账本 handoff-*.md |
|---|---|---|
| 是什么 | **记忆主承载面**（人类可读项目全貌） | **一次性接续材料**（四段式，仅用于接续） |
| 迁移时 | ✅ **只读这个** | ❌ **不读、不归组、不建事件** |

**成本实测（本机真实数据）**：

| 读法 | 字符 | ≈ token | 倍数 |

## 9 · 工具参数速查

```
memory_event(action, eventId?, name?, summary?, kind?, confidence?,
             startMs?, endMs?, members?, rationale?, sections?, outcomes?,
             constraints?, checkpoint?, constraint?,
             userPercept?, agentTrace?, sharedGround?, commitment?)

  create  → 建事件（返回 id）
  append  → 加检查点（需 eventId + checkpoint）
  set     → 改字段（name/summary/sections/status/startMs/endMs/members/rationale/kind/confidence/outcomes）
  close   → 收尾（需 outcome）
  rename  → 改名（需 name）

memory_note(kind='plan', fromEvents=true)  → 从事件渲染新白板（**首选，不要手写 content**）
memory_note(kind='plan', content='...')  → 仅渲染器故障时的兜底手写
memory_note(kind='note', action='append', content='...') → 项目规约
memory_user(action='append', content='...') → 用户规约（跨项目）
```

**四类感知**（可选，有实质进展才填）：

`userPercept` 的 `kind` 可取 **preference**（偏好）/ **state**（当前状态）/ **unfinished-goal**（未完成目标）/ **authorResponse**（作者回应：同意/否定/纠正/补充/质疑/拍板）。
★ 只有 accepted / used 会进「用户画像」段注入，其余是噪声。

---

### 四类感知以外：
- `userPercept` `{stage, kind, text}` — 用户说了什么（stage: accepted/used 才进画像）
- `agentTrace` `{action, result}` — 你做了什么
- `sharedGround` `{claim, confirmedBy}` — 双方确认的结论
- `commitment` `{promise, state}` — 对用户的承诺

**四段每次变动必重写**：`sections{goal,doing,deadend,next}` 反映**当前**状态，不是历史累积。append 检查点后若状态变了，用 `action='set'` 整体重写四段。

## 10 · 五类分拣（只在需要时用）

迁移不只是建事件。旧记忆里的条目按去向分五类：

| 类 | 判据 | 去向 |
|---|---|---|
| 人之上的层 | 「这个人是谁」「我们一起经历过什么」 | L0：直接写 `~/.dsh/memory/person/event-store.json` |
| 用户规约 | 跨项目通用的要求 | L1：`memory_user(action='append')` |
| 项目规约 | 这个项目必须怎么做 | L2：`memory_note(kind='note', action='append')` |
| 项目事件 | 这个项目在做什么 | L3：`memory_event`（主战场） |
| 纯流水 | 一次性进度、临时路径 | `memory_log` 或丢弃 |

**判断口诀**：换个工作区打开，这条内容还应该在吗？
- 应该在 ⇒ L0 或 L1
- 只在这个项目有意义 ⇒ L2 或 L3

**★ 用户画像 vs 用户规约不许混**：
- 画像 = emotional / 主观 / 情境化（印象、相处方式）
- 规约 = rational / 硬（每次注入的约定）
- 两者都沾 ⇒ **拆成两条**，分别落 L0 与 L1

> **注意**：大部分工作区只需要做 L3（建事件）+ 写新白板。L0/L1/L2 只在白板/日志里明确有这类内容时才做。
