# 测试章程 · 注入截流方案

> **依据**：INJECTION-THROTTLE-DECISION-2026-10-26.md（决定文档）
> **用途**：①给实现者的验收依据 ②给「视觉能力 + 计算机操作能力 Agent」的挂机场景真机测试指令

---

## 0. 测试分层（四层，缺一层即假完成）

| 层 | 名称 | 能抓住什么 | 抓不住什么 |
|---|---|---|---|
| **L1** | 单元/纯函数 | 单段渲染、节白名单、token 累加器 | 接线、真注入文本 |
| **L2** | 真引擎端到端 | 七档各自真触发、注入文本真含/真不含 | 视觉、真机时序 |
| **L3** | 真机（CDP/宿主） | 宿主真加载、真 token usage、真压缩 | 长时挂机 |
| **L4** | 视觉 Agent 挂机 | 长任务漂移、挂机代位补偿、真实交互 | 单点逻辑（靠 L1/L2） |

> **本仓纪律**：L1 全绿 + L2 全绿 ≠ 可用。历史上「绿但假的」家族已有 **7 种形态**（见白板）。每层都要有能红的断言。

## 2. L2 · 真引擎端到端（必须用真引擎，不许假状态桩）

### 2.1 铁律（本仓七次事故的教训）

1. **测试输入必须由被测代码自己产出** —— 不许手工塞 `engine.state.events = [...]` 这类产品不会写的字段。
2. **必须走完整链路**：`refresh()` → `renderMemoryDynamic()`，不能只测渲染函数 + 手造 state。
3. **空 store / 空数组会跳过关键分支** ⇒ 判据恒绿。必须喂 ≥1 条真实数据。
4. **每档至少 1 条**真引擎断言，否则「套件全绿」不构成功能证据。

### 2.2 必须覆盖的端到端场景

| # | 场景 | 断言 |
|---|---|---|
| E1 | 全新会话首轮 | 注入文本含白板**全文**、含规则全文、含画像 |
| E2 | 首轮后用户再说话（<250k） | 注入文本**不含**白板、**含** semantic-recall、含当前事件 |
| E3 | 首轮后新增 250k（用户说话） | 注入文本含白板全文 |
| E4 | 非人消息、第 21 个模型请求 | 走 F3，含规则全文但白板只核心 3 节 |
| E5 | 非人消息、第 5 个模型请求 | 走 F4，不含白板、规则只标题+条数 |
| E6 | 压缩事件后第一帧 | 走 F5，含白板核心节 + 「刚才压缩了」提示 |
| E7 | 新会话接续 | 走 F6，含白板全文 + 账本 |
| E8 | 挂机 300k 无用户（开关开） | 走 F7，完整版内容出现 |
| E9 | 挂机 300k 无用户（开关**关**） | 零字节，与 E8 对照 |

## 3. L3 · 真机验证（CDP / 宿主）

### 3.1 必须验证的四件事

1. **宿主真加载了新代码** —— 比对「宿主进程启动时间 vs 源码 mtime」。后端改动必须重启宿主。
2. **真 usage 能读到** —— 从宿主真实会话里抓 usage 对象，断言 `usageShapeTokensPre` 返回非 null。
3. **真压缩能检测到** —— 构造一次真实压缩（或等自然发生），断言 F5 触发。
4. **设置页文案真显示 20** —— 打开设置页截图确认（不是只查源码）。

### 3.2 取证方法（可复用，来自本仓实践）

- **客户端真实代码口径**：直接从宿主 `fetch('/plugins/??...')` 抓那个约 17.5MB 的 bundle 全文，查特征串。这是「客户端到底加载哪份代码」的**唯一真口径**，比截图/猜测可靠。
- **CDP**：注入 cookie 后用 Chrome DevTools Protocol 连 `/json/list`，抓 `Runtime.exceptionThrown` 事件 + 截图。
- **崩溃日志**：`%APPDATA%/@deepseek-ai/dsh-desktop/logs/crash-*.log`。

## 4. L4 · 视觉 Agent 挂机测试章程（用户明确要求专门做一次）

> 用户原话：「如果连续挂机模型累计输出超过了 300k tokens 没有用户的信息，就可以代位补偿一个完整版的投递（我觉得这个会有点复杂，需要做好以后专门做一次测试，可以写一个相关的测试章程去一个有视觉能力、有 computer 操作能力的 Agent 测试）」

### 4.1 测试目标

验证 **F7 挂机代位补偿**在真实长时挂机场景下：①会触发 ②触发时机正确 ③内容正确 ④不会误触发 ⑤不破坏正常流程。

### 4.2 前置条件

- 一台可用机器，装有 DSH + dsh-auto-memory 插件
- 一个**视觉能力 + 计算机操作能力**的 Agent（能看截图、能点击、能读界面）
- 测试用工作区（**不要用生产工作区**，避免污染真实记忆）
- `hangCompensateEnabled = true`（默认 false，测试时显式打开）
- `hangCompensateTokens` 调小到可测值（如 5000），避免真等 300k

### 4.3 测试步骤

| 步 | 动作 | 观察点 | 判据 |
|---|---|---|---|
| S1 | 新会话，发一条「开始挂机任务：请连续做 N 轮自我检查」 | 首轮注入是否完整 | 截图确认含白板/规则 |
| S2 | 让 Agent 连续执行，**不说话**，直到累计输出超过阈值 | 是否出现完整版重投 | 截图/日志确认 |
| S3 | 检查该次重投的内容 | 是否含白板 + 事件卡 + 目标 | 内容断言 |
| S4 | 继续挂机但**把开关关掉**，再累计超过阈值 | **不应**再触发 | 负路径确认 |
| S5 | 中途插一条用户消息 | 应走 F1/F2，不应重复触发 F7 | 不冲突 |
| S6 | 挂机中发生压缩 | 应走 F5 而非 F7 | 优先级正确 |

### 4.4 视觉 Agent 专用检查点

因为这次测试有视觉能力，**必须做界面层核对**（不能只看日志）：

1. **注入内容真的显示在界面上**吗？（有些注入只在 system prompt，界面上看不到——要区分）
2. **白板看板页是否显示新内容**？（不是只查 API）
3. **设置页开关状态**是否与配置一致？
4. **有无报错弹窗/白屏**？（吸取 P0 整树崩教训：任何一个组件抛错会让**所有页签输入框消失**）

### 4.5 必须记录的证据

| 证据 | 形式 |
|---|---|
| 每步截图 | PNG，命名 `s<step>-<desc>.png` |
| 注入文本快照 | 从宿主 API 或日志抓，存 `.txt` |
| 判定结论 | 每步「通过/不通过 + 依据」 |
| 失败复现步骤 | 精确到「第几步、什么状态、期望 vs 实际」 |

### 4.6 测试后必须做

1. 恢复 `hangCompensateEnabled = false` 和 `hangCompensateTokens = 300000`。
2. 清理测试工作区的记忆文件（**先确认不是生产工作区**）。
3. 把结论写回本文件的「测试结果」段（不要只写在聊天里）。

## 5. 变异验证（每条关键判据必须做）

> 判据纪律：**「如果被测代码错了，这条会红吗？」** 答不上来的判据等于没写。

| 判据 | 变异方式 | 期望 |
|---|---|---|
| 白板按节投递 | 把 `truncatePlanBySections` 改成直接返回 null | A1 必红 |
| 250k 累加器 | 把阈值改成 1 | B4/B5 必红 |
| 压缩检测阈值 | 把 20% 改成 1% | B5 必红（10% 回落会被误判压缩） |
| F4 不带规则正文 | 让 F4 也传规则全文 | C17 必红 |
| F7 开关 | 去掉开关判断 | C18/E9 必红 |
| 文案与常量一致 | 常量改回 10 | T1 文案断言必红 |

**变异验证流程**：改 → 跑 → 确认红 → 还原 → 跑 → 确认绿。**两步都要记录**。
