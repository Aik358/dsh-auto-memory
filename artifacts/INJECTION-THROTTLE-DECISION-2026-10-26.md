## 0. 一句话结论

**把「注入」从「一套按节截断的管道」重构为「七种档位 × 三类内容（骨架/证据/人）」的显式矩阵**。
触发由 **token 累计量**驱动（不是轮数、不是时间），并保留「用户发声必给」的硬旁路。

## 2. 七种档位（用户逐条确认，不可混为一谈）

| # | 档位 | 触发条件 |

| **F2** | **用户发声精简版** | 用户说话，但距上次完整版新增 **<250k token** |
| **F3** | **运行中完整版** | **每 20 个模型请求**一次（snapshotMinGapRounds，非用户轮） |

### 2.1 触发规则关键澄清（用户原话）

- **250k 是「两轮完整版之间间隔的 token 数」**，不是「超过 250k 才给」。
  > 「0% 是一个新对话，首轮必须完全注入；首轮之后，如果又输出了 250k 的内容，就再注入一次；再输出 250k，就再注入一次。如果中途压缩，比如说从 70% 压缩到 30% 了，那压缩完的那一段也要注入一次。」
- **用户发声不是充分条件，是必要条件**：用户说话时才可能给 F1，但只有满足 250k 间隔才给完整版。
- **累加的是「模型输出」的 token**。
- **F3 的 20 是「模型请求数」**，不是对话轮、不是工具调用次数。

### 4.1 新增段 semantic-recall（语义/情感唤回预留位）

用户原话：
> 「留一个雏形就行，具体模型训练好之后，它会在这个指引下面额外注入一块内容，类似于之前的记忆、共同记忆等内容」
> 「可以加一句【以下是自动机引擎检索到的相关情感、共同经历和用户喜好的相关内容，可做参考】这个备战未来」

- **现在填什么**：A+C 结合 —— 用户画像做基调 + userPercept（accepted/used）做共同经历。
- **不给全文**（避免量太大），只给 **<=800 字符摘要 + 一句「需要更多用 memory_read(kind=user) 拉取」**。
- **固定引导语**：【以下是自动机引擎检索到的相关情感、共同经历和用户喜好的相关内容，可做参考】
- **11 月底切换**：模型训练好后在此段下方直接追加模型驱动的召回结果，段位与引导语不变。

## 7. token 计量口径（用户选 D：混合）

> 用户原话：「用 D 吧，注意，真实 usage 可能需要及时判断，因为 usage 会通过压缩等方式发生变动，所以你读的话就需要灵活一点，并且判断有效」
> 「A 不行，因为现在这个上下文很神秘，它会乱飘。我觉得 B 还合适，或者 C 吧。B 和 C 都有官方的 API，都可以从软件里读到，总体来说更偏向于 D」

### 7.1 数据源优先级
1. **宿主显式压缩事件**（若有）—— 最高可信
2. **真实 usage**：复用现有 usageShapeTokensPre(usage)（lib/water-window.js，口径 = input + cacheRead + cacheWrite + output，含严格形状校验，形状不可信返回 null）
3. **字符估算回落**：累计字符 / 4（与 waterLevel 同源公式）

### 7.2 压缩检测（事件优先 + usage 回落）
- **优先**：宿主压缩事件钩子（需实现时确认是否存在；当前代码里**未找到显式钩子**，只有 detectProxyCompactionPre 探测第三方 bili 代理）
- **回落**：usage 突然回落 **>=20%** ⇒ 认定压缩
  > 用户明确排除「usage < 上次就认定压缩」（「A 不行，因为现在这个上下文很神秘，它会乱飘」）
- **压缩后动作**：重置 250k 计数器 + 触发 F5 + 显式告知模型「刚才压缩了，记忆在这里随时可拉」

### 7.3 有效性判断（防乱飘）
```text
读取 usage ->
  若 usageShapeTokensPre 返回 null => 该样本无效，跳过（不更新基线）
  若样本有效 => 与上次基线比较：
    - 下降 >=20% => 认定压缩，重置基线
    - 上升 or 小幅波动 => 累加 delta 到「距上次完整版的 token 数」
```

## 8. F3/F4 的 20 与 8（口径确认 + 文案修正）

### 8.1 口径
- **F3（运行中完整版）**：snapshotMinGapRounds = 20 —— **20 个模型请求**一次
- **F4（运行中精简版）**：slimEveryRounds = 8 —— 8 个模型请求一次

> 用户原话：「这个默认不是 10，已经被我延长成 20 了。你看一下，是不是设置里的文案写得有问题，因为 10 还是太短了」

### 8.2 已确认的文案缺陷（本期必修）

**位置**：lib/client.js L534 fSnapGapHint
```text
```...用来防止长任务里模型对上下文漂移。默认 10。0=每个模型请求都尝试...```
```
- **代码实际**：DEFAULT_SNAPSHOT_MIN_GAP_ROUNDS = 20（lib/index.js L513 唯一真源）
- **本机配置**：snapshotMinGapRounds = 20
- **缺陷**：设置页文案仍写「默认 10」⇒ 用户按文案理解会以为 10 就够（太短）
- **修法**：文案改为「默认 20」，并说明「20 是经实测调整后的值（原 10 偏短，长任务里模型漂移明显）」

## 9. 白板（PLAN.md）投递规则

> 用户原话：「白板只在 250k token 过后的『人说话完整版』投递，交接也投递」

| 档位 | 白板投递 |
|---|---|
| **F1 用户发声完整版** | **全文**（33KB，约 8,300 token） |
| **F6 交接文档注入** | **全文** |
| F2 / F3 / F5 / F7 | 核心 3 节：「最新实况」「当前目标」「载体分工」 |
| F4 运行中精简版 | **不投** |

### 9.1 按「节」而不是按「字符」截断
当前 truncatePlanByPriority(planText, 1200) 是字符截断 + 关键词打分，导致新内容进不去。改为：
1. **节白名单优先**：先按档位选出允许的节集合
2. **节内部再限长**：每节给独立上限（如「最新实况」<=2,000）
3. **超长时按节尾截断并标注**（不静默）

### 9.2 节名必须命中优先词
- 「★当前进展与最新实况」——「当前」+「进展」双命中
- 或直接并入现有「★当前目标」节
