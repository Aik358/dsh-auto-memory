## §2 · 四类感知：现在就填，触发条件是「实质性进展」

### 2.1 结论

| 项 | 旧认识（v1 错） | 现在（正确） |
|---|---|---|
| 是否本期填 | 「本期只建结构不用」 | **现在就填** |
| 粒度 | 只在事件级 | 事件级**容器**，条目随进展追加 |
| 节奏 | 不追加 | **实质性进展时追加**（非机械每轮） |
| 谁生产 | 未设计 | 模型在写事件/更日志时一并产出 |

### 2.2 「实质性进展」的判据（草案，供实现参照）

满足任一即算实质性进展，应追加 percept/检查点并重写四段：

- 一个**新结论**落地（决策改变、方案被否决、判据被推翻）
- 一个**验收结果**产生（套件数字、真机截图、失败归因）
- 一个**交付物**落盘（文件/sha/字节数）
- 用户给出了**新裁定或纠正**（→ 同时产 `authorResponse`）

不算：纯读取、纯等待、重复确认、心跳。

### 2.3 四类感知的字段语义（沿用 event-store 契约）

| 字段 | 内容 | 谁产生 |
|---|---|---|
| `userPercept` | 人类侧观察：stage(retrieved/delivered/used/mentioned/accepted) + kind(preference/state/unfinished-goal/**authorResponse**) | 模型读用户发言后写 |
| `agentTrace` | Agent 侧动作：action / result / wasRefuted | 模型自己写 |
| `sharedGround` | 已达成的共识：claim / confirmedBy / correction | 双方确认后写 |
| `commitments` | 承诺：promise / boundary / state(open/kept/dropped) | 承诺与兑现时写 |

> **只有 `accepted` / `used` 进用户画像** —— 这条印刷在 `memory_event` 工具描述里（C4 已落盘）。

## §3 · L0 总览：模型按时重写，随时可改可加

- **对象**：事件的 `name`（一句话，≤80 字）+ `summary`（一段话总览，≤400 字）。
- **时机**：① 每次更新事件时顺带审视；② 模型觉得「这件事的总览该变了」时**随时**改；③ 新增事件时可先给草稿名，后续可 rename。
- **重写者**：**大模型**（不是正则拼装、不是模板填充）。
- **旧做法的问题**：`summary` 仅在 create 时写一次，此后几乎不动 ⇒ 事件越长，总览越不能代表现状 ⇒ Tier-0 目录与注入面显示的是陈年简介。
- **判据**：任一 active 事件，其 `summary` 的 updatedAt 与最后检查点时间差 > 阈值 ⇒ 记为「总览过期」，注入面或 `memory_status` 应提示模型重写。

## §4 · memory_log 依附事件：这是 25 号决断，已实现且正确

```
memory_log(note, kind)
  ⇒ ① 追加事件检查点（kind='log'，panels=[{kind:'log',text}]）
  ⇒ ② 派生当日 .md（日记类，独立保留）
```

- **为什么对**：日志是「事件下四段下面的一条记录」，不是独立流水账；它同时是可被语义唤回（RAG）的细节语料。
- **v1 的错误**：把这条判成「日记行灌进事件」的缺陷。**撤回该结论。**
- **真正要注意的**：日志写事件时**应带上下文**（所属事件、当时四段快照），否则以后无法判断它属于哪次实质进展。

## §5 · 「作者回应」：新增内容类别

**定义**：作者/人类对 Agent 发言的**回应**（同意、否定、纠正、补充、质疑、拍板），是「长期人际交流中的主动唤起」的核心语料 —— 下一次对话模型应能想起「他上次对这类方案是这么回的」。

**落点（最小改动）**：`userPercept.kind` 扩一个值 `authorResponse`，字段不新增、契约不改：

```js
memory_event(action:'append', eventId, userPercept:{
  stage:'accepted'|'used'|'mentioned'|'delivered',
  kind:'authorResponse',
  text:'作者原话摘要 + 我的解读'
})
```

**判据**：① 工具描述里印出该 kind；② 召回语料含该字段（C3 已含 userPercept）；③ 画像聚合只取 accepted/used，authorResponse 亦遵守；④ 前端 percept 面板能显示该 kind 标签。

## §6 · 语义唤回 RAG：log 与 percept 是语料源

- **目标**：面向**长期人际交流**的**主动唤起**（proactive recall），不是纯关键词命中。
- **语料**：事件 name/summary/sections/checkpoints/panels + 四类感知 + 作者回应 + 每日日志。
- **现状**：`scope='events'` 已能命中 percept 独有词（C3 实测通过）；但「主动唤起」的时机决策、语料权重、模型训练仍缺 ⇒ 记为后续批次（不阻塞本轮）。
- **判据（不在本轮）**：同一 query 在「有 percept」与「无 percept」两个事件上的排序差异可复算；唤起被采纳率可从 `userPercept.stage='accepted'` 统计。

## §7 · 白板看板工作区取错（真缺陷，待修）

```js
// lib/index.js  event-list / event-detail handler
const pa = await engine.resolvePaths(undefined)   // ← 传 undefined ⇒ 回落 default runtime
```

⇒ 页面显示的是 **default runtime 工作区**的事件，不是**发起请求会话**的工作区。

**这是「混用 `this.state` 与 `stateFor(agent)`」缺陷家族第 5 种表现**（前四种：C2 `memLegacy` / H3-E `buildReadOverviewPre` / U7 `upgradeState` / `buildTierLayerInjection` + `renderSlimSnapshotPre`）。

**修法**：handler 从请求上下文取 agent（或 session workspace），用 `engine.resolvePathsWith(agent)` 等价路径解析；**禁止**再出现 `resolvePaths(undefined)`。

**判据**：① 两工作区并行打开，各自只看到自己的事件；② 单工作区无回归；③ 全仓 `resolvePaths(undefined)` 命中数 = 0（守卫）。

### 本轮三条方法论产出（比代码更值钱）

1. **同一语义两份实现只改一处 = 半修**：本轮实证两处 —— `textOfEventPre`（index.js vs event-recall.js）、`migration-prompt` 模块 vs artifacts 副本。

2. **「跑漏套件」≠「看见红但不管」**：前者暴露**制度缺陷**（清单靠人猜必有漏）⇒ 修流程；后者暴露**纪律缺陷** ⇒ 修态度。两者修法不同。
