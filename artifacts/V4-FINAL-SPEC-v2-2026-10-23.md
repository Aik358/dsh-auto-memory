# 二 · 情境化记忆框架（来自 2026-10-15 官方研究综述）

来源：https://aik358.github.io/dsh-auto-memory/landing/news/2026-10-15-relational-memory.html

## 2.1 四类记忆对象（决定事件的字段设计）

| 类别 | 操作性含义 | 例子 | 关键治理 |
|---|---|---|---|
| **用户记忆**（user memory） | 关于用户的偏好、经历、事实、目标、明确要求 | 用户不吃某食物；项目约束 | 来源、时效、纠错、敏感度、作用域 |
| **Agent 自传记忆**（agent autobiographical memory） | Agent 先前经历、可追溯的行动、曾作出的回应 | Agent 上次建议方案 B，后来被证伪 | **必须区分真实交互记录与生成式虚构背景** |
| **共同/关系记忆**（shared/relational memory） | 双方共同参与、确认或共同修订的事件与理解 | 一起完成某项目；用户纠正某项长期误解 | 双方归属、不同视角、同意与删除权 |
| **关系约定**（relational commitments） | 明确承诺、互动边界、尚未解决事项 | Agent 承诺下次先验证再建议；用户不希望主动提某话题 | 权威、履约状态、撤销与冲突处理 |

**这直接修正了我原来的设计**：我把 `userPercept` 当成唯一的「人的一侧」字段，实际至少要四个。

## 2.2 五个决策阶段（决定 percept 条目的字段）

1. **候选检索** — 哪些记忆与当前上下文/目标/关系事件可能有关
2. **激活/投递资格** — 是否允许并值得进入本次模型请求
3. **模型可见暴露与使用** — 是否真进入请求；回答是否忠实适当地利用
4. **用户可见披露** — 是否显式回指、向用户确认、或选择不提
5. **记忆治理** — 用户如何查看、纠错、限定用途、撤回、删除

> 原文：「检索到不等于应该使用；策略准许投递不等于记忆实际进入请求；进入请求不等于回答忠实使用；用户觉得回答温暖也不等于记忆事实准确。」

⇒ 每个 percept 条目**必须带 stage 字段**，不能只存文本。

    panels: [                  // 手绘3「一个检查点 = 一行面板组」
      { kind: 'state' | 'log' | 'deadend' | 'next'
            | 'userPercept' | 'commitment' | '<可扩展>', text }
    ]
  }],

  // ── 人的一侧（§2.1 四类记忆，全部带 stage）──
  userPercept:    [{ at, kind: 'preference'|'state'|'unfinished-goal',

                     text, sourceRef }],

  sharedGround:   [{ at, claim, confirmedBy: 'user'|'agent', correction, sourceRef }], // 共同记忆

  // ── 引用而非复制 ──
  constraints: ['rule:<id>', 'spec:<id>'],

  createdAt, updatedAt
}

## D2 · 未归档事件窗格（存量兼容）

### 为什么必须有
现存 **575 篇顶层账本 + 258 篇 archive = 833 篇**，全部无事件归属（`eventId` 实测 0/515）。

### 六步流程
1. **检测存量** — 扫 `handoff/` + `handoff/archive/`，凡无 `eventId` 者入列
2. **窗格展示** — 分页列出：文件 / 时间 / 目标首行 / 字节
3. **点「审理」** — 启动子代理（**批量尽量大**，见下）
4. **生成草案** — 聚类 + 抽四段 + 起事件名，产出草案 JSON（不写盘）
5. **人在环确认** — 逐条接受 / 改名 / 合并 / 丢弃
6. **写入 + 回写** — 写 event 存储；原账本只加 `eventId` 引用

### ★批量策略（用户 2026-10-23 裁定：尽量大）
> 原话：「批量可以尝试尽量多，反正子代理 1m 上下文足够」

- **子代理上下文 1M token** ⇒ 不必分批到 40 篇
- 833 篇 × 平均 1,153 字符 ≈ **960k 字符 ≈ 565k token**（按 1.7 字/token）
- **理论上一批就能全读**（565k < 1M），留出 435k 余量给输出与推理
- 保守方案：**一批 400 篇**（约 270k token），2 批跑完；或**一批全量 833 篇**
- **决定**：默认 **全量一批 833 篇**；若子代理报 token 不足，自动降为 400 篇/批
- 判据：不按「批数」设计，按「子代理能否一次看全」设计 —— **一次看全才能保证跨批一致性**

### ★聚类判据（用户 2026-10-23 裁定：LLM 自己决定，不用机械相似度）
> 原话：「聚类阈值让 llm 自己决定分析，比机械的相似度归类强」

**因此 D2 不再使用固定阈值。** 改为：

1. **子代理读全部目标段 + 任务状态段 + mtime**
2. **LLM 自主判断哪些账本属于同一件事**，并给出每个判断的**理由**
3. **必须输出判断依据**（可审计）：每条事件附
   - `members[]`：成员账本清单
   - `rationale`：为什么认为它们是一件事（一句话）
   - `confidence`：high / medium / low
4. **低 confidence 的标「待人工」**，不自动接受

**我此前用机械相似度实测的失败证据（保留，说明为什么必须换 LLM）**：
拿「确定属于同一件事」的 4 篇账本（「八项拍板」那族）算 3-gram Jaccard：

| 两篇之间 | 相似度 |
|---|---|
| 220513 ↔ 220934 | 0.182 |
| 220513 ↔ 061339 | 0.154 |
| 220513 ↔ 062627 | 0.111 |
| 220934 ↔ 061339 | 0.219 |
| 220934 ↔ 062627 | 0.308 |
| 061339 ↔ 062627 | **0.424** |

**最高只有 0.424** ⇒ 任何 ≥0.5 的阈值都会把它们拆散。这就是旧基线「575 篇 → 458 簇，91.5% 单篇」的根因。
**机械相似度在这类文本上结构性失效**（日期/序号/圈码/加粗稀释了相似度）。LLM 读语义则能直接看出「八项拍板 ①②③⑤⑥⑦⑧ 完成 → 已完成主体」是同一件事的推进。

### 成本估算（按全量一批）
- 输入：833 篇 ≈ 565k token
- 输出：事件草案（若 ~150 事件 × ~400 token）≈ 60k token
- **合计 ≈ 625k token / 全量一次**

### 四条硬约束
| # | 约束 | 判据 |
|---|---|---|
| 1 | **原件只读** | 不改账本正文，只在尾部追加 eventId 注释行；前后 sha256 全量比对，任一不一致即中止 |
| 2 | **可回滚** | 事件存储与账本引用分离：删事件只删索引，账本回到「未归档」；提供「撤销本批」 |
| 3 | **可审计** | 写 `event-curation-log.jsonl`：批号 / 输入文件清单 / 输入 sha256 / 子代理完整输出 / 人工决定 / 时间 |
| 4 | **不阻塞** | 后台任务；窗格显示进度；中途关页面不影响，重进可续 |

# 十三 · ★重要修正 · 「账本串行」是旧记录格式的产物，不是领域本质

> 用户 2026-10-23 20:5x 原话：「账本本身就是串行的，这是因为原来的记录是流水账，后面到新版事件为中心之后就不一定了，可能会存在并行？别自己来，我重要的大改动思路可能会被大量上下文冲掉」

## 13.1 我要撤回的结论

§十二 里我写过两句，**现在撤回其中一句**：

| 我写过的 | 裁决 |
|---|---|
| 「事件之间没有时间交错 —— 0 / 127」（实测数字） | ✅ **保留**，这是对**当前 833 篇旧账本**的事实陈述 |
| 「账本本身就是串行的 ⇒ 不能画甘特图多轨并行」 | ❌ **撤回**。串行是**旧记录格式（流水账）的副作用**，不是领域的本质属性 |

**为什么撤回**：
- 旧账本是「一次交接写一篇」的流水账 ⇒ 物理上不可能并发记录，这不是"事情不并行"，是"记录方式线性化"了并行
- 新的事件中心模型里，**事件是独立实体**，天然可以有多个事件同时 active
- ⇒ 所以**并行必须是一等能力（first-class）**，不能因为历史数据碰巧是串行的就把 UI 设计成串行

## 13.2 这条修正带来什么设计变化

### 变化 1：甘特图 / 泳道视图从「不做」变成「必须做」
- 旧结论：不做甘特图（因为历史数据是串行，画了就是造假）
- **新结论**：**必须做**，但按**数据能力**分两种渲染：
  - **历史档（旧账本）**：数据是串行的 ⇒ 时间流单列视图（真实反映流水账）
  - **事件档（新模型）**：数据可并发 ⇒ 泳道视图（每个事件一行，时间横向流动）
- 两档共用同一份事件 schema，只是**渲染器不同**。这不是两套数据，是**同一数据的两种投影**。

### 变化 2：事件 schema 必须显式支持并发
需要明确的字段语义（本期只定 schema，不实现调度）：
```js
event = {
  ...
  status: 'active' | 'paused' | 'closed',   // ★ 新增 paused（搁置态）
  // 时间轴不再是"一段连续区间"，而是一条可断裂的检查点序列
  checkpoints: [{ at, kind, text, sourceRef, panels }],
  // ⇒ 并发表达 = 多个 event 的 checkpoints 在时间轴上交错，各自独立
  // ⇒ 不需要 parent/child 或 lane 字段：并发就是"多个 active 事件的检查点交错出现"
}
```
**关键洞察**：并发不需要新增结构 —— 只要允许多个事件同时 `status='active'`，并且它们的 `checkpoints[].at` 互相交错，就是并行。泳道视图只是把「同一事件的所有检查点连成一行」。

### 变化 3：`paused` 状态是「搁置」的显式表达
旧账本里"搁置后拾起"只能从**空档**推断（20/127 事件有 >2h 空档，最大 40.9h）。
新模型应该**显式记录**：
- `status: 'paused'` + `pausedAt` + `pausedReason`
- 拾起时 `status: 'active'`，并追加一条 checkpoint `kind: 'resume'`
- ⇒ 将来不需要猜，直接读字段

### 变化 4：UI 三视图（不是两视图）
| 视图 | 数据前提 | 用途 |
|---|---|---|
| **时间流**（默认，历史数据） | 事件串行 | 看历史流水账 |
| **泳道 / 甘特**（新模型） | 事件可并发 | 看多条线同时推进 |
| **工作流线索**（辅助） | 从 title/summary 提 lane 标号 | 历史数据上补偿并发表达的缺失 |

- 三种视图是**同一份 events 的不同投影**，不是三份数据
- 时间流与工作流线索服务历史档；泳道服务事件档
- 切换状态存 `localStorage`

## 13.3 原型怎么验证"并发能力"
历史数据无法证明并发 UI 能工作 ⇒ **需要一份独立的合成夹具（fixture）**：
- 文件：`artifacts/wb-event-preview/fixtures/concurrent-demo.json`
- 内容：3–4 个虚构事件，检查点在时间上**真实交错**（A 的 10:00、B 的 10:20、A 的 11:00、C 的 10:40…）
- HTML 里加一个明确标注的「并发演示（合成数据）」开关
- ⚠ **绝不能把合成数据混进真实事件列表** —— 必须分区、必须标 demo
- 验收：切到并发演示能真看到多行泳道 + 事件条在不同行、时间上互相交叠

## 13.4 历史数据上的"并行"只有一种合法表达
在旧账本上，**唯一不造假**的并行表达是**工作流线索**（§十二 3b）：
- P0 跨 8 天 / 6 个断点、P1 跨 6 天 / 4 个断点 —— 这是"同一工作线被拆成多个事件，中间隔了几天"
- 但它**不能**画成连续轨道（那会掩盖断点）
- 正确画法：**分段显示 + 断点处留白**（每段是该标号的一次连续推进，段与段之间是空的）

## 13.5 一句话总结这次修正
> **旧数据串行 ⇒ 只说明旧的记录介质是线性的；新模型必须从第一天就按"可并发"设计，否则就是把历史包袱焊进架构。**

| `prev-session-5e4bc31708a451fe-...-s53.md` | 12:26:10Z | 会话转写包（机械产物） |

- 现状：**578 顶层 + 259 archive = 837 篇**（v1 基线 833）
- **归因：语料自然增长，非改动缺陷**

## 15.2 由此暴露的原型设计缺陷（★重要）

`build.mjs` 在 `assembleEvents` 里对 plan 与账本数量做**硬相等断言**：

```js
if (plan.length !== ledgers.length) throw new Error('plan=516 ledgers=517')
```

**这在原型阶段就是错的**：
- 语料每天都在长（本会话一轮就长了 4 篇）
- 每次增长都要人工补 `event-plan.tsv`，否则 build 直接炸
- ⇒ 这等于把"人工维护聚类表"焊成了硬约束

## 15.3 正确设计：未计划账本自动入「待归并」桶

```
plan 里有的账本   → 进对应事件
plan 里没有的账本 → 不 throw，自动归入 bucket「待归并」
                  → events.json 的 stats 报告 unplannedLedgers: N
```

**这个改动不只是修 bug，它正好对应 v4 的 D2「未归档事件窗格」**：
| 原型里的兜底 | v4 正式设计 |
|---|---|
| `unplannedLedgers` 桶 | 「未归档事件」窗格 |
| 人工补 `event-plan.tsv` | 点「审理」→ 子代理生成事件草案 |
| `stats.unplannedLedgers` 计数 | 注入面 `event-unarchived` 段的存量计数 |
| 验证"不炸" | 验证"存量可被审理" |

⇒ **原型提前验证了 D2 的核心机制**：语料增长不会阻断系统，只会增加待归并项。

## 15.4 基线数字的书写纪律

**双写 + 归因**，不允许只写新值：

```
PASS 源文件总数 = 837（handoff 578 + archive 259）
  基线说明：v1 为 833（575+258）；2026-10-23 12:26-12:27Z 因本会话续写新增 4 篇
  归因：语料自然增长，非改动缺陷
```

理由：只写 837 而不写 833 和归因 ⇒ 下一个人看到会以为是改动把数字弄坏的（对应既有规则「守卫/基线锁的红必须先归因再动手」）。

## 15.5 新增账本的置信度纪律

新增的 `handoff-20261023-202749.md` 是本次"刷新仪式"写的账本，内容是本段会话的交接。
- **必须标 `confidence: low`**，rationale 写「新增账本，待人工归并」
- **不得硬塞进某个已有事件** —— 归错比不归更糟（会污染事件的历史边界）
- 对应既有规则「同一事实存在互相矛盾记忆时不得擅自认定其一正确」的同源精神：**无法判断时标低置信，不猜**

## 15.6 三篇机械产物不进事件
2 篇 `prev-*` 转写 + 1 篇 `PLAN-*` 归档 = **机械产物**，进归桶（bucket），不进事件。
与 v1 的 `planSnapshot` 38 个 / `sessionTranscript` 16 个同样处理。
只有 1 篇 `handoff-*.md` 是真正的四段账本，需进事件。

# 十七 · ★2026-10-23 22:2x 追加裁定 · 倒叙 + 懒加载 + 时间轴重做

> 用户原话：「我认为有一个主要问题：现在的内容是从早到晚排列的，实际上应该是倒叙的，即默认在最下面显示最新的内容。这样正好，最前面的如果过多的话，可以懒加载防止加载压力过大，我觉得这个表现方式还是不太好，尤其是时间轴的方式，可能太小了，不太直观啊。你看看有什么升级的办法吗？你派给子代理让他去处理，有很多好的动画还有排版的 skill，你可以让他去用」

## 裁定 24 · 时序方向改为倒叙（最新在底部）
- **默认视图 = 底部是最新内容**，向上滚动 = 回溯历史
- 这与聊天/日志类应用的认知一致：**你关心的是"刚刚发生了什么"，不是"一个半月前发生了什么"**
- 当前实现是正序（早→新，从上到下），**方向错了**
- ⚠ 注意这是**方向反转，不是简单 reverse 数组** —— 会牵连：
  - 初始滚动位置必须锚到底部
  - 向上懒加载时必须保持滚动位置不跳动（scroll anchoring）
  - 键盘 ↑↓ 的语义要反过来（↑ = 更早）
  - 深链 #evt-xxx 定位后，上下文的"新/旧"指示要正确

## 裁定 25 · 历史内容懒加载
- 初始只渲染**最近 N 个**（建议 N=30~50），向上滚动到接近顶部时增量加载更早的
- 依据：127 事件 + 184 节点 + 837 检查点，全量打开是有压力的（当前 index.html 已 2.5 MB）
- ⚠ 必须防的坑：**反向无限滚动最容易出滚动跳动** —— 加载更早内容后，可视位置必须纹丝不动
- 判据：加载 30 条前后，当前视口顶部元素在屏幕上的位置变化 < 2px

## 裁定 26 · 时间轴太小、不直观，需要重做
> 用户原话：「尤其是时间轴的方式，可能太小了，不太直观啊。你看看有什么升级的办法吗？」

**当前问题诊断**（我的判断）：
| 问题 | 现状 | 后果 |
|---|---|---|
| 太窄 | 左 rail 仅 200px | 标题被截断成「M-CM6 一键交接三件套（P…」 |
| 纯文字 | 每个 tick 只有日期 + 一行标题 | 看不出时间密度、看不出跨度、看不出空档 |
| 无层级 | 127 个 tick 平铺 | 找不到"哪个月"、无法快速定位 |
| 无比例 | 每个 tick 等高，不管间隔 5 分钟还是 5 天 | 40.9 小时的搁置和 5 分钟的连续提交长得一样 |
| 与中栏重复 | rail 和中栏都在列事件 | 左侧信息密度低但占 200px |

**升级方向（供子代理参考，允许更好的方案）**：
1. **宽度**：200px → **280~340px**，让标题不用截断
2. **时间密度可视化**：spine 旁加细柱状（每天事件数），一眼看出"哪天最忙"
3. **月份/周分隔**：sticky 分隔条（如「10 月 · 23 个事件」），滚动时吸顶
4. **真实比例 vs 等距**：给一个切换 —— 「等距」（易读）vs 「按真实时间比例」（能看出搁置 40.9h 的空洞）
5. **相对时间**：近期显示「3 小时前 / 昨天」，远期显示绝对日期
6. **scroll-spy**：滚动中栏时，左 rail 自动高亮当前可视范围，并有指示器平滑跟随
7. **"今天"锚点**：底部固定一条「今天」标记，向上是历史
8. **空档可视化**：>2h 的间隔在 rail 上也断开（不只是右栏面板里提示）

## 裁定 28 · 字号太小且无自适应

### 现状实测（我读 v2 的 CSS）
| 元素 | 当前 | 判断 |
|---|---|---|
| `body` | 13px | 主阅读界面偏小 |
| `.card .ttl` 事件卡标题 | 12.8px | 偏小 |
| `.card .summary` 卡片摘要 | 11.8px | 明显偏小 |
| `.panel .pb` 面板正文 | 11.1px | 明显偏小 |
| `.panel .ph` 面板标题 | 9.5px | 很小 |
| `.tick .t` 侧栏标题 | 11.5px | 很小 |
| `.badge` 徽章 | 10px | 很小 |

### 修复要求
1. 正文基准 **14–15px**；卡片摘要 ≥13px；面板正文 ≥12.5px；**最小可读 ≥11px**
2. **字号用 `rem` 不用 `px`** ⇒ 跟随用户系统字号（apple-design Dynamic Type 原则）
3. **用户可手动调**：A- / A 三档（紧凑/标准/宽松），存 `localStorage.wbEvt.fontScale`
4. 层级用**权重 + 字号 + 行高**三者组合，不只靠字号
5. **大标题负字距、小字正字距**（apple-design：tracking 是尺寸相关的）

## 裁定 29 · 无自适应（响应式缺失）

### 现状
`.layout` 固定 `grid-template-columns: 200px 332px minmax(0,1fr)`，只有两档 `@media` 收窄（1440/1180），**本质还是三栏硬布局**。

### 要求（三档断点）
| 断点 | 布局 |
|---|---|
| **≥1440px** | 三栏（rail / 卡片 / 详情） |
| **1024–1440px** | rail 收窄 + 详情栏可收起（复用已有抽屉能力） |
| **<1024px** | **单栏堆叠** —— rail 变顶部横条或抽屉，卡片全宽，详情变全屏覆盖层（sheet） |

- 手机上要能用（可用 `mobile-native` skill：100vh bug / tap highlight / 输入框缩放 / 安全区）
- **任何断点都不得出现水平滚动条**

## 裁定 30 · 无明暗主题

### 要求
1. **三态** `auto` / `light` / `dark`，auto 跟随 `prefers-color-scheme`；存 `localStorage.wbEvt.theme`
2. 顶栏切换按钮（三态循环 + 图标）
3. **暗色不是反色**（这是最容易做丑的地方）：
   - 背景用**分层中性灰**（`#0a0d14` / `#111620` / `#171d29`），不是纯黑
   - 文字用**降饱和白**（`#e8ecf3`），不是纯白（刺眼）
   - **阴影在暗色下失效** ⇒ 改用「描边 + 提亮表面」表达层级（apple-design 材质重量原则）
   - **状态色必须重新取值**：浅色的 `#0f7b52`（完成绿）在深底上对比度不足，不能沿用
   - 徽章用**低透明度色底 + 高对比文字**，不是纯色块
4. **两套主题都过 WCAG AA**：正文对比度 ≥ 4.5:1，大字 ≥ 3:1
5. **切换不闪白**：`<html>` 上尽早应用主题（head 内联 script 读 localStorage），避免首屏白闪
6. 挂 `prefers-contrast: more` 与 `prefers-reduced-transparency: reduce` 降级
